# dstone-ai-engine — Tool 루프 제어, sm-workflow 측정과 개선 기록

> CLAUDE.md에서 분리한 상세 메모입니다. 원문 그대로 옮겼으며, 필요한 작업일 때만 읽습니다.

Tool loop control and per-Agent reasoning (2026-10-07, done instead of adopting Spring AI Alibaba — its Graph runtime would only replace `WorkFlowExecutor`, which already has sequence/branch/forEach/loop/approval, and the useful parts (context editing, tool-call limits) were small enough to build on Spring AI itself; the reviewed proposal is `docs/temp/dstone-ai-engine_SAA_통합전략_설계정리.md`). In Spring AI 2.0.1 the tool loop is an advisor (`ToolCallingAdvisor`, auto-registered, order `HIGHEST_PRECEDENCE + 300`; the memory advisor is +200, so it sits outside the loop), not something inside the chat model, so anything with a larger order runs once per LLM round. Three pieces, all attached per call in `AgentExecutor.buildSpec()`: (1) `runtime.agent.ToolCallBudgetCallback` wraps the Agent's Tools with one shared counter — limit = Agent YAML `maxToolCalls`, else `dstone.ai.agent.tool.max-calls` (100); from the last fifth on it appends "N calls left, save your result now" to Tool results (blocking without warning leaves the output file unsaved), past the limit it returns `실패: ...` without running the Tool, and after 3 such refusals it throws `AgentContractException` (step failure → `onFailure`); Sub Agent calls are not counted. (2) `runtime.agent.ToolResultCompactionAdvisor` (order −100, rules in the pure `ToolResultCompactor`): when the Tool results of the current turn add up to more than `dstone.ai.agent.tool.keep-result-chars` (200,000; 0 = off) it cuts the **oldest** ones to their first 300 chars plus a "call the Tool again if you need this" notice, never the latest result or results ≤ 600 chars; only the copy sent to the model is cut, and what is cut stays cut on later rounds (prompt cache). It is deliberately **not** a Spring bean — any `Advisor` bean would be injected into `ConfigChatClient.chatClient(...)` in place of the `defaultAdvisors` list bean and silently drop `LlmLoggerAdvisor`. (3) Spring AI's own limits (`spring.ai.tools.limits.*`, default 40 per Tool / 150 total, not per-Agent) are loosened in `conf/application.yml` (−1 / 300); when they do trip, Spring AI ends the loop with the text `Tool call limit exceeded…` as the answer (`finishReason=toolCallLimitExceeded`) and `AgentExecutor.textOf()` turns that into an `AgentContractException` instead of passing it on as the Agent's answer. Agent YAML `reasoning: none|low|medium|high` (unset = model default; **`none`, not `off` — YAML reads `off` as `false`**, a bad value fails boot) is mapped per provider in `ConfigChatClient.requestOptions(model, reasoning)`: openai/OpenRouter `reasoning_effort`, ollama think on/off, anthropic thinking disabled / budget 1024·2048·4096. Checked live on OpenRouter `qwen/qwen3.8-27b` with one small ordering question: unset 41.7 s (2,407 reasoning tokens), `none` 0.5 s (0 reasoning tokens), same answer — single runs, and the ollama/anthropic mappings have not been run. The budget (limit 2 → 2 real calls, refusal, the model wrapped up) and the compaction (keep 3,000 → oldest results cut, answer still right) were checked the same way with temporary Agents. `pilot-workflow` got a `step00` TOOL step that reads `00-request.md` without an LLM and hands it to the requirement/impact/architect/developer Agents as `input.request` (one LLM round saved per Agent; the reviewer still reads files itself; `재요구분석` routes back to `step00`), `maxToolCalls` 40 on the requirement/impact/review/architect Agents and 25 on the investigator, and `readFile`/`readFileLines`/`readFileTail` now answer `실패: 파일을 읽을 수 없습니다…` for an unreadable file so a TOOL step fails instead of passing that sentence on as file content. Not done on 2026-10-07 on purpose (partly done 2026-10-08, next paragraph): `reasoning` on the `pilot` Agents and LLM-free pre-collection of knowledge evidence (needs the requirement Agent to return entry points as structured output) — both change tuned prompts and must be measured on a real request with `dstone-knowledge` up.


**`sm-workflow` read/round pass (2026-11-05, measured on that day's 25 real Agent calls in the Windows instance's `execution.log`).** The cost is resending the whole conversation every LLM round, so rounds × Tool result size is what to cut (developer 35 rounds, context 14k → 94k tokens, 1.84M input tokens in one call). Findings: 146 of 200 `readFileLines` calls had no range (88% of the characters read); files were mostly re-read *across* steps (22 of 39 files read by ≥2 Agent calls in one run), not within one call; the architect made one Tool call per round and walked framework internals (`genexon.js`, kendo, `BaseVO` 32k chars); `sm-ready-agent` once called `getToDate` 12 times. Changes, all without adding steps: `step00` is a TOOL `getToDate` step (`save: now`; every later path is `${input}/${state.now}`, `state.ready` is gone; `sm-ready-agent.md` is no longer used but still on disk); the impact Agent writes a line range per target plus a '현재 코드' section (verbatim excerpts, ±3 lines, ≤40 lines each) into `02.impact.md` so the architect writes '변경 전' from it instead of reopening files; architect/impact/developer prompts ask for ranged reads and several independent Tool calls per answer, the architect must not follow framework/common-script internals, the developer no longer reads a copied file whole before editing; engine: `readFileLines` without `startLine`/`endLine` returns at most `dstone.ai.tool.file.max-lines-without-range` (300) lines with a notice (`FileSetTool.readItemFiles` uses the uncapped `FileTool.readNumberedLines`), `runtime.agent.RereadGuardCallback` + `ReadHistory` (per Agent call, `dstone.ai.agent.tool.reread-guard`, default true) answer a re-read of an already returned range with a notice instead of running the Tool (allowed again when the file's mtime/size changed, after a write Tool on that path, on partial overlap, or after `ToolResultCompactionAdvisor` cut results — it clears the history), `knowledgeSearch` hit body is `dstone.ai.tool.knowledge.max-content-chars` (conf 800, code default 1500), `searchInFiles` `max-search-matches` 50 in conf. `reasoning` was not changed: on qwen3.8-27b `low`/`medium` have no effect. Verified by `RereadGuardTest` (12, scripted) and the full suite (123 passing); **not yet run end to end with a real LLM**. Follow-up the same day after a real run (execution `5e47439d…`, step06: 12 rounds, 27 Tool calls, 253k input tokens, 63 s, no re-reads): the impact Agent (1.4.0) no longer opens reference files for a new feature — it lists their paths (from knowledge/search) and only reads the spot where something is registered; with no similar feature it writes "참고 기능 없음" plus one convention file per layer, and the architect (1.4.0) reads those and writes each new file's full content into the design; `searchInFiles` accepts a file path as `basePath` (searches that file only). The same run also showed that knowledge revision 58 of `testApp` still holds `sample/imageboard` files that are gone from the source, which cost three verification rounds — re-analyze after reverting source. The user's work folders are under `D:/WorkShop/00.SM`; `D:/AppHome/testApp/workshop/changes` is not used. Second follow-up the same day after two more real runs (`5bf95466…` work004 new feature, `b8c5325f…` work003 error fix + new feature; impact/architect steps were fine): (1) **reasoning was being re-sent** — Spring AI 2.0.1 `OpenAiChatModel` stores the answer's reasoning in `AssistantMessage` metadata `reasoningContent` and sends it back as `reasoning_content` on the next request, so every Tool-loop round carried all earlier reasoning (reviewer: round-1 output 31k tokens → round-2 input 2k → 33k); `common.advisors.ReasoningStripAdvisor` (order −110, per call, not a bean) removes that key from the copy sent to the model, `dstone.ai.agent.keep-reasoning` (default false) keeps it; only the openai jar uses that key. (2) The developer Agent (1.4.0) made one `replaceInFile` per round (32 rounds, 1.37M input tokens) because its prompt said "replaceInFile로 하나씩"; it now has no `replaceInFile`, puts all edits of a file into one `editFileTexts` call and calls several files in one answer (the other run, which happened to do that, took 13 rounds); it no longer checks targets with `isFileExist` before `copyFileWithReplace` (that Tool refuses an existing target), does not read reference originals, and does not re-read after a successful edit. The taskitems row-status update was kept as is (the user's choice). (3) `knowledgeSearch` result count is capped by `dstone.ai.tool.knowledge.max-top-k` (conf 5, code 10) — two `topK: 10` searches (18k chars) rode along 18 rounds. Not done at the user's choice: dropping the reviewer's `editFileTexts` status marking (it costs a second LLM round). Verified by `ReasoningStripAdvisorTest` (2, scripted) and the full suite (128 passing); not yet run end to end with a real LLM.

**`sm-workflow` efficiency pass (2026-11-03, after measuring 7 real runs).** Input is the work **folder** (a file path now fails at `step00`). Steps: `step00`/`02`/`07`/`10`/`11` TOOL `readFile` (documents reach Agents through `with`, so no LLM round is spent reading, and a document an Agent failed to save stops the run), `step01` requirement, `step03` reviewer (SUPERVISOR, `save: review`), `step04` APPROVAL only on review failure, `step05` impact, `step06` APPROVAL, `step08` architect, `step09` APPROVAL, `step12` developer. `feedback` carries the review reason and approval comments on a redo. Why each Agent's Tools are few: Tool definitions were up to 12× the prompt and go out every round; reviewer/architect/developer made 0 knowledge calls in every run, so only the impact Agent keeps knowledge Tools. The requirement Agent does no source investigation (it used to spend more knowledge calls than the impact step because its table asked for target files) and has no RAG: the RAG query was the file path, ran about once per LLM round (10–14 identical searches per Agent call) and injected ~7,800 chars of an unrelated uploaded design document. `maxAttempts` removed from architect/developer: with text output a retry only fires on budget/`LENGTH` failures and restarts the whole job. `common.advisors.AgentCallStatsAdvisor` (not a bean, per call, order −50, inside the Tool loop, call path only — not stream) logs one `dstone-ai-engine agent:` line per LLM round and a total (rounds, per-Tool counts, tokens, ms) — that is where to look when an Agent is slow; Tool arguments are not logged by it. It and `ConfigTool`'s per-call `dstone-ai-engine tool: [x] 호출 - 인자 ...` line go through a logger, because `LogUtil.sysout` writes to stdout and `bin/startApp.sh` sends stdout to `/dev/null`; other `sysout` lines are still lost in that setup. The first real run after this change was stopped: with file Tools only, the impact Agent read on to 38 rounds / 93 Tool calls (24 duplicates, 83k input tokens), tracing root causes into `genexon.js`/`BaseVO`, hence `maxToolCalls: 30`, range reads only and the 'stop at the call flow' prompt rules.
