**Pause / resume (2026-11-02).** `POST /api/ai/workflow/executions/{id}/pause` sets the `PAUSE_REQUESTED` column (a separate column because every step save rewrites `STATUS`; `updateExecution` clears it once the status is no longer `RUNNING`) and `WorkFlowExecutor` stops as `PAUSED` before the next step — a running step is never interrupted. `POST .../resume` continues a `PAUSED` or `FAILED` run asynchronously from the saved step using the currently registered definition (compare-and-set on status, so a double click runs once). The position is found by step id (`context.currentStep`), not by index; a missing id refuses the resume with 409, and `ResumePoint.warnings` flags a changed definition version or a re-run of a failed TOOL/forEach step without blocking. `WorkFlowExecutionRecovery` turns leftover `RUNNING` rows into `FAILED` at boot — safe for one instance only, so **start any test copy sharing the DB with `-Ddstone.ai.workflow.recovery.enabled=false`**. Existing DBs need `schema/03-alter-table-pause-resume.sql`. `GET /executions` now returns `{items, total, page, size}` with partial `workflowId`/`executionId` matching. Not done on purpose: editing `state`, cancelling. Verified with a real PostgreSQL and a real LLM on a spare-port copy in headless Chromium. **Rewind (2026-11-04):** `GET .../executions/{id}/rewind?fromStep=` previews and `POST .../rewind {fromStep, clearState}` re-runs from a step **that appears in the step history** (the user's rule; not `RUNNING`; `PAUSED`/`FAILED`/`DONE`/`WAITING_APPROVAL` all allowed) — range = from that step's last run (a forEach group's first row) to the end of the history; `RewindPoint.savedNames` = names the range's steps saved that are still in `state`, shown as a warning and removed only when `clearState: true` (the user chose "warn, optionally delete"); files the range's steps **created** (`RewindPoint.deleteFiles`: WRITE records with `CREATED = true`, set when the file did not exist right before the Tool call — `WorkFlowFileRecorder.missingBefore()` called from `ConfigTool.LimitedToolCallback`) are physically deleted on rewind together with folders left empty (the user's rule, 2026-11-04: "re-run deletes every artifact of the re-run steps"), while files that existed and were edited (`keptFiles`) are neither deleted nor restored — deleting them would destroy original source; rows from before the `CREATED` column (NULL) count as created only for `.md` files whose first record in the execution is that write; the range's file records are deleted too (existing DBs need `schema/05-alter-table-execution-file-created.sql`, applied to the local `dstone_ai` 2026-11-04); unused approvals in the range and a DONE run's `output` are cleared; history rows are kept and new ones appended; same `markResumed` compare-and-set. Screen: [여기서 다시] on each step's last history row in Workflow 실행 관리 → panel with the range, warnings, the delete / keep file lists and a "state 값을 지우고 시작" checkbox (off by default). Verified by `WorkFlowRewindTest` (scripted, 6 tests incl. file/empty-folder deletion; the upsert SQL was checked on the real PostgreSQL in a rolled-back transaction); the boot screen was only `node --check`ed and compiled, not driven in a browser.

**Step files and the document popup (2026-11-04).** Every file a step reads or writes through a file Tool is recorded in `AI_WORKFLOW_EXECUTION_FILE` (one row per execution/step/path/READ|WRITE, count + first/last time; existing DBs need `schema/04-alter-table-execution-file.sql`). Step executors pass a `runtime.tool.StepRef(executionId, stepId)` to `AgentExecutor.call()/callForSchema()` and `ToolExecutor.call()` (new last/second parameter, `null` from chat); it rides in the `ToolContext` (`StepRef.toolContextOf()`), Sub Agents (background too) pass the parent's on, and `ConfigTool.LimitedToolCallback` calls `runtime.workflow.file.WorkFlowFileRecorder` after each call — so LLM-chosen Tools, TOOL steps and Sub Agents are all covered. No ThreadLocal on purpose (forEach and background Sub Agents run on other threads; the existing `common.exec.ExecContext` is keyed by thread name). Which Tool touches which file is the pure table `FileAccessRule` (FileTool read/write/edit Tools, `readFiles`, `copyFileWithReplace` source READ/target WRITE, MCP filesystem `read_*`/`write_file`/`edit_file`); `실패: ...` results and `dryRun` calls are not recorded; a recording failure only logs a WARN. forEach history rows are `step[0]` but files are recorded under the bare step id. API (`WorkFlowExecutionController`, `api.service.WorkFlowFileService`): `GET .../executions/{id}/files`, `GET .../files/content?path=` (only recorded paths → else 400; ≤ `dstone.ai.workflow.file.max-read-bytes`), `POST .../files/content {path, text, baseHash}` — 403 unless `dstone.ai.workflow.file.edit-enabled` (code default false, `conf/application.yml` true, k8s ConfigMap false), 409 while `RUNNING`, for an extension outside `editable-extensions` (default `md`) or when the SHA-256 changed since opening; writes keep the file's charset (`FileTool.charsetOf`) and CRLF/LF under `FileTool.EDIT_LOCK`. An edit only reaches steps that read the file again — values already in `state` don't change. Screen: `dstone-boot` Workflow 실행 관리 — a '문서' column on the step history (chips on the last row per step), a 'step 문서' table ([모든 파일 보기] shows non-md files read-only) and a popup (`ai/assets/js/workflow-doc-viewer.js`: [보기] marked 15.0.12 → DOMPurify 3.2.6 → highlight.js from `knowledge/assets/lib`, github-markdown-css 5.8.1 light; [수정] textarea + live preview, Ctrl+S, full screen, Esc twice), proxied by `WorkFlowAdminController` `files.do`/`fileContent.do`/`saveFile.do`. Textarea, not a WYSIWYG editor: those re-format tables/whitespace and would break later `editFileTexts` matches. Verified 2026-11-04: `FileAccessRuleTest` + `WorkFlowFileTest` (scripted; the user's conf has `llmcall: true`, so run with `-Ddstone.ai.test.llmcall=false`), and engine/boot copies on 8181/7181 with the real PostgreSQL in headless Chromium (render incl. table/code colouring, `onerror` stripped, save keeps CRLF, 409 after an outside change, reload, full screen, 390px width). The WAITING_APPROVAL notice and the 403 path were not driven in a browser. Driving the boot screen in a test copy needs `-Dspring.security.enabled=false` plus `spring.autoconfigure.exclude` of the five `org.springframework.boot.security.autoconfigure.*` classes (otherwise every `/ai/**` request redirects to login).


`spring.ai.model.chat` is the default LLM provider. **Per-Agent provider (2026-11-03, the user chose this over named connections replacing `spring.ai.*`):** an Agent's `model.provider` (`anthropic`/`openai`/`ollama`) sends only that Agent to another provider, read from the unchanged `spring.ai.{provider}` block, so only one connection per kind exists (OpenRouter and a private vLLM cannot coexist). `common.config.ChatProviders` keeps a `ChatClient` per provider: the default is the shared bean, the others are built lazily on first call by directly calling the public `@Bean` methods of Spring AI's auto-configuration classes with properties bound through `Binder` (ENC values decrypt as usual), plus `ChatClient.builder(..., ToolCallingAdvisor.Builder)` and the same default advisors. `AgentRegistry.checkCallOptions()` fails boot/[검사] on an unknown value or an empty `api-key`; reachability only shows at the first call. `ConfigChatClient.requestOptions()` takes the provider first, so options match the Agent's provider. Tests use `support.TestChatProviders` (`@Primary`, returns `ScriptedChatModel` unless `llmcall` is true). Verified 2026-11-03: `SampleAgentProviderOverrideTest` scripted and once with a real Ollama call while the default is `openai` (Tool loop included); the openai/anthropic models were built from config but not called through this path, the empty-`api-key` check was not exercised, and the designer's `model.provider` select was only `node --check`ed. `model.name` gives the model directly (`AgentRegistry.modelOf()`, applied by `runtime.agent.AgentExecutor.buildSpec()` as a per-request `ChatOptions` together with `model.temperature`, `model.reasoning` and `execution.timeoutSeconds`; no `model` falls back to `spring.ai.{provider}.chat.options.model`, and a model name from a different provider only fails at that Agent's first call, not at startup). `spring.ai.anthropic.api-key` in `dstone-ai-engine/conf/application.yml` follows the same `ENC(...)` convention as DB passwords (see "Sensitive Config Encryption" above) rather than sourcing from `env.properties`. Spring AI is on the 2.x line (`spring-ai.version` in `dstone-ai-engine/pom.xml`); Azure OpenAI is not supported as a chat provider (Spring AI 2.x dropped `spring-ai-starter-model-azure-openai` — Azure remains vector-store-only).

RAG (`dstone.ai.rag.enabled`, default `false`) is delegated to `dstone-knowledge` since 2026-10-06: this engine has **no embedding model, no pgvector, no Tika, and no document API** (`spring.ai.model.embedding: none`; the pgvector starter, Tika reader, `commons-io` override, Lombok and testcontainers dependencies are gone; `spring-ai-rag` stays for `RetrievalAugmentationAdvisor`/`ContextualQueryAugmenter`). What is left is search only: `RagRetrievalChain` wraps `dstone-knowledge` `/api/search` in a custom `DocumentRetriever`, used by `ragEnabled` Agents and the `searchDocuments` Tool. Documents are uploaded straight to `dstone-knowledge` (the `dstone-boot` Knowledge screen `knowledge/search/search`, or `/api/documents`). Removed the same day at the user's request, because nothing called them any more: the engine's `/api/ai/embed/*` (`EmbedController`/`EmbedService`) and `/api/ai/rag/search` (`RagController`), the caller-prefix rule for document names, `dstone-boot`'s "문서 임베딩 관리" screen with its `DocumentController`/`DocumentService`/`DocumentDao`/`DocumentVo`/`IngestResult`, and the tables `TB_AI_DOCUMENT` + `TB_AI_SQLCONVERT` (`sampleDB`) and `vector_store` + the `vector`/`uuid-ossp`/`hstore` extensions + eight empty stray `analysis_*`/`rag_*` tables (`dstone_ai`, which now holds only the two `AI_WORKFLOW_EXECUTION*` tables). Consequences to remember: (1) **uploaded documents are shared by every caller of the engine** — there is no per-caller isolation any more (`dstone-knowledge` sees one caller, the engine; its tenancy is per its own API key), so app-level separation would have to be designed in `dstone-knowledge`; (2) embedding is asynchronous — a just-uploaded document is found by name immediately but by meaning only once its chunks are embedded (30–45 s seen, 2 minutes on a cold start); (3) search is hybrid and the similarity threshold is applied in the engine after the fact — the only exception is a not-yet-embedded hit (no score) found by a literal name in the question; embedded hits are judged by score alone (common words in a path or JSON such as `log`/`error` used to count as names); (4) RAG needs `dstone.ai.tool.knowledge.base-url`; when the search itself fails (`dstone-knowledge` slow or down) a `ragEnabled` Agent with `ragAllowEmptyContext` true (the default) **logs a WARN and goes on without reference material** instead of failing the Agent call and its whole Workflow — only `ragAllowEmptyContext: false` Agents fail; the `searchDocuments` Tool still returns `실패: ...` (which fails a TOOL step by design). A read timeout is reported as "N초 안에 답하지 않았습니다", not as "서버가 떠 있는지 확인". The chat checkbox in `dstone-boot` is labelled "올린 문서 검색(RAG)". When rebuilding after deleting files use `mvn clean package` — a plain `package` left the deleted JSP/class files inside the WAR.

**Agent Skills and background Sub Agents (2026-10-30, `org.springaicommunity:spring-ai-agent-utils` 0.13.0; the user chose "Skills + plan B" after comparing three ways to bring in the library's TaskTool).** Skills: `conf/definitions/skills/<folder>/<name>/SKILL.md` (public Agent Skills format: front matter `name` (lowercase/digits/hyphen ≤64, **must equal the folder name**) + `description` (≤1,024) + body; `license`/`compatibility`/`metadata`/`allowed-tools` accepted and ignored; other files in the folder are reference material the engine never reads — the Agent reads them with `readFile`), parsed by `YamlDefinitionLoader.parseSkill()` into `common.definition.skill.SkillDefinition`, held by `common.registry.SkillRegistry` (boot/[검사]/reload check, `DefinitionReloader` checks Skills → Agents → Workflows), referenced from an Agent's `skills: {allowed: [...]}`. `runtime.agent.SkillTool` builds one `Skill` Tool per call (library `SkillsTool.Skill` record + `SkillsInput` arg `command`, but our own Korean description and reply `Skill '<name>' 안내입니다.` + folder path; unknown name → `실패: ...`), wrapped by `limited()` and sharing the Agent's Tool budget; not switched off by chat `toolsEnabled: false`. Boot fails on an unknown skill name or a registered Tool/Sub Agent named `Skill`/`TaskOutput`; a Skill folder with reference files on an Agent without `readFile` only warns. Skill script execution is deliberately not supported (the library's `ShellTools` would bypass the shell whitelist). Plan B for Sub Agents: the library's `Task` Tool and `ClaudeSubagentExecutor` are **not** used (one `prompt` string loses the child's input schema/contract; the executor bypasses `AgentExecutor` — no engine rules, `requestOptions()` timeout, budget, compaction; it auto-adds Claude Code built-in subagents; `model`/`resume` are ignored). Instead `subAgents` accepts a list (unchanged) or `{agents: [...], background: true}` (`AgentDefinition.SubAgents`, DELEGATING creator, unknown keys fail); with background each `SubAgentToolCallback` gains an optional `run_in_background` arg (child input field of that name → boot failure) and returns `task_id: task-N` at once, and a `TaskOutput` Tool (library `TaskOutputTool` + our wrapper: missing `timeout` → 10 min, a child's non-contract exception is rethrown when its result is read so the parent fails like a sync call) is attached. `runtime.agent.SubAgentTasks` = one library `DefaultTaskRepository` **per parent call** (call()/callForSchema() close it in `finally`, stream() in `doFinally`): close skips queued tasks and interrupts running ones (an LLM request already sent cannot be recalled). Threads come from one shared fixed pool in `AgentExecutor` (`dstone.ai.agent.sub-agent.background-threads`, default 4, daemon, created lazily, `@PreDestroy` shutdown); depth stays 1, so pool tasks never wait on the same pool. Background calls count toward `sub-agent.max-calls`. Samples: `skills/sample/sql-review` (+ `checklist.md`), `agents/sample/sample-skill-agent.md`, `sample-subagent-background-agent.md`, Workflows `sample-agent-skill`, `sample-agent-subagent-background`; tests `SampleAgentSkillTest`/`SampleAgentSubagentBackgroundTest`. `ScriptedChatModel` gained `answerToolCalls(name, args, ...)`, `answerWhen(marker, ...)`/`answerToolCallsWhen(...)` (pick answers by prompt text, for concurrent parent/child calls) and `textOf(prompt)` (includes Tool results, which `Prompt.getContents()` omits), and now returns `ToolCallingChatOptions` from `getDefaultOptions()`/`getOptions()` when scripted — without that ChatClient never attaches Tools and scripted tool calls are not executed. Verified 2026-10-30: 45 of 46 tests pass with `-Ddstone.ai.test.llmcall=false` (`workflow/sm/WorkFlowTest` failed on its own because of old step ids; those tests were deleted 2026-11-05), and one real OpenRouter run each — the Skill flow (Skill → validate fails → `readFile checklist.md` → fixed → valid, ~10 s) and 3 background children collected via `TaskOutput` (44 s). The designer's Agent dialog got a Skill chip list and a background checkbox under Sub Agent (`node --check` only; not driven in a browser).

**Definition editing without restart (2026-10-20, the user chose "file path" over DB storage or YAML download).** Definitions moved from `src/main/resources/definitions` to `conf/definitions` (git-tracked, not in the jar). `common.registry.DefinitionReloader.apply(changes, write)` overlays `path → text` (null = delete) on the files on disk, parses and checks **all** Agents (`AgentRegistry.check()`) then **all** Workflows with those Agents (`WorkFlowRegistry.check(files, agents)` — validation reads Agents through `agentOf()`/`checkingAgents`, not the live registry), and only if everything passes writes the files (temp file + atomic move) and swaps both registries (`install()`, `volatile` immutable maps); any failure changes nothing. MCP definitions are not reloaded (restart).
