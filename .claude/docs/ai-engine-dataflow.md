# dstone-ai-engine — Step 간 데이터 흐름, Tool 호출, 공통 규칙

> CLAUDE.md에서 분리한 상세 메모입니다. 원문 그대로 옮겼으며, 필요한 작업일 때만 읽습니다.

Step-to-step data flow (state model, 2026-10-09): **the callee owns the contract** — an Agent declares what it takes and returns (Agent `.md` `input` / `output` in Picoschema, both default to text), a Tool's contract is its arg schema/reply, and SUPERVISOR/ROUTER/APPROVAL results are engine-fixed (their Agents must not declare `output`). A step says what to put in (`with`, required for AGENT/SUPERVISOR/ROUTER, shaped per the Agent's input schema; TOOL is an arg map), **where to keep the result** (`save: name`, plus `saveError`/`saveInput`/`saveEach`) and where to go next (`next`/`onFailure`/`routes`). All state lives in one execution-context tree with **no implicit names**: `input` (the request input as-is), `state` (what steps stored; every name declared in the Workflow's `state:`), `approvals` and `definition` (internal, not readable). There is no `steps.<id>…`, `previous`, `text` or `items`. Several steps may store to the same name (e.g. each branch of a ROUTER has `save: reply`). APPROVAL always works by `routes`: the human picks one name (decision body `{decision, approver, comment}`; `route` is accepted as an alias and `approved: true/false` maps to `APPROVED`/`REJECTED` so the unchanged dstone-boot admin screen keeps working), result `{decision, approver, comment}`, never fails; an unknown name is a 400 and the run stays waiting; `approval.requireCommentOnReject` makes a non-`APPROVED` decision without a comment a 400. `ApprovalStepExecutor` deletes the decision from `approvals` once consumed, so a flow may loop back to the same APPROVAL step and be asked again; `GET .../executions/{id}` exposes `pendingApproval {stepId, approverRole, routes, artifact}`. A Workflow declares its request contract (`input` in Picoschema, default `string`; request body is `{input, sessionId}`). A missing path is `null` (use a `:` default), a step executor exception fails the whole run, an `AgentContractException` is a step failure (→ `onFailure`) — after `execution.maxAttempts` tries when the Agent says `onInvalidOutput: RETRY` (only `AgentExecutor.call()`, i.e. AGENT steps and chat; not SUPERVISOR/ROUTER). **Logic never goes into YAML**: filtering a list, cross-checking values, rendering a document from data are Java Tools called by TOOL steps — the reason jq was removed is that `pilot-workflow.yml` had grown ~30 jq programs (validation rules, markdown templates, status decisions) that could not be unit-tested or read. Such engine-side Tools are `@AiTool(stepOnly = true)` (`ConfigTool`): never shown to an LLM (`tools.allowed` naming one fails boot, `["*"]` excludes them) and **not subject to `dstone.ai.tool.max-result-chars`**, because their results go to `state`, not into a conversation — without that exemption a Tool returning file contents is cut at 60,000 chars into invalid JSON. MCP tool calls are serialized per server (`ConfigMcp.SerializedToolCallback`). Steps do **not** share chat memory: `MessageChatMemoryAdvisor` is attached only when given a conversation id (chat API: request `sessionId`; Workflow: only AGENT/SUPERVISOR/ROUTER steps with `memory: true`, room `sessionId:stepId`; `memory` + `forEach` fails boot). Not implemented from the design document, on purpose or for lack of time: LangGraph4j, approval timeout/escalation (`approval.timeout` fails boot with "not supported yet"), artifact hashes, an approval table, definition pinning, `RULE`/`SUB_WORKFLOW` step types, `tools/tool-registry.yml`, `model.routing` (existed as a name → model map under `dstone.ai.model.routing.*` until 2026-10-11, removed at the user's request — one way to override a model, `model.name`; the old key now fails boot with a hint); `execution.timeoutSeconds` only reaches the `openai` provider. Earlier design records: `docs/temp/dstone-ai-engine-refactory-20260928-1.md`, `docs/temp/dstone-ai-engine-subagent-20261001.md`.

Paragraphs below that predate 2026-10-09 use the old key names; read them as: Agent `tools` → `tools.allowed`, `maxToolCalls` → `execution.maxToolCalls`, `reasoning` → `model.reasoning`, `ragEnabled`/`ragAllowEmptyContext` → `context.*` (removed entirely 2026-11-14 — documents are read with the `knowledge*Docs` Tools, see `ai-engine-features.md`), Agent `prompt` → the prompt file, step `ref`/`onSuccess`/`SUCCESS` → `agent` or `tool`/`next`/`END`, `${ jq }` → `${state…}`; `ConfigChatClient.requestOptions(model, reasoning)` now also takes `temperature` and `timeoutSeconds`.


`spring.ai.openai.timeout` does **not** reach chat calls on its own in Spring AI 2.0.1: `OpenAiChatModel.buildRequestOptions()` overrides the client timeout on every request with `OpenAiChatOptions.getTimeout()`, which has no config key and defaults to 60s (seen 2026-10-02: a slow model writing a long document was cut at exactly 60s — `Error reading response (원인: InterruptedIOException: timeout <- StreamResetException: stream was reset: CANCEL)`). So `ConfigChatClient.requestOptions(model)` builds the per-request options — an `OpenAiChatOptions` builder carrying that timeout when the provider is `openai`, plus the model override — and `AgentExecutor.buildSpec()` attaches it on every call; putting it in `ChatClient.defaultOptions` is not enough because a per-request `options(...)` replaces the defaults wholesale. Any new code that calls `ChatClient` without going through `AgentExecutor` must use `requestOptions()` too.


DB access is MyBatis since 2026-10-06 (it was `JdbcTemplate`): `runtime.workflow.execution.WorkFlowExecutionStore` extends `common.biz.BaseDao`, SQL lives in `sqlmap/workflow/WorkFlowExecutionDao.xml` (rows come back as `LinkedHashMap` with quoted camelCase aliases; the Store converts enum/JSON/`Timestamp`→`Instant` itself because `WorkFlowExecution` is a record). New DB code goes the same way: a `*Dao.xml` under `resources/sqlmap/` and a class extending `BaseDao`.

Tool calling has no infrastructure dependency — it's plain Java executed on demand. `common.annotation.AiTool` (meta-annotated `@Component`) marks a class containing `@org.springframework.ai.tool.annotation.Tool` methods; `common.config.ConfigTool` scans for `@AiTool` beans via `ApplicationContext.getBeansWithAnnotation` and wraps them into a `ToolCallbackProvider`, filterable per caller via `dstone.ai.tool.allowed-by-caller`. An Agent only ever sees the Tools named in its own `tools` list (there is no `toolsEnabled` switch anymore — a boolean that exposed every registered Tool was too loose for YAML written by non-developers). An `AGENT`/`SUPERVISOR` Workflow step lets the LLM pick among those through Spring AI's own tool-calling loop; a `TOOL` step calls one deterministically by name via `runtime.tool.ToolExecutor` (no LLM involved) — both paths go through the same `ConfigTool` whitelist. `ConfigTool` also wraps every Tool (local and MCP) in `LimitedToolCallback`, which cuts any single result longer than `dstone.ai.tool.max-result-chars` (default 60000) and appends a "narrow the range and call again" notice — Tool results pile up in the conversation and are re-sent on every LLM call, so one oversized result blows the context limit or the response timeout (seen 2026-10-01: a project-root file listing including `.git` made a 700KB request → `OpenAIIoException: Request failed`). `LimitedToolCallback` also answers a **cut-off Tool argument** itself: when the LLM's argument JSON does not parse (a long `writeFile` body hit `max-tokens`; reasoning tokens count against it — seen 2026-10-07 on a 12,873-char document, Spring AI only logs `Conversion from JSON failed` / `Unexpected end-of-input` and the model rewrote the whole document at the same length) it does not call the Tool and returns `실패: Tool 인자가 중간에 끊겨서 도착했습니다 …` telling the model to split the content with `writeFile` + `appendFile` (`FileUtil.appendFile`, added for this). `tools.utils.FileUtil` limits itself first (`dstone.ai.tool.file.*`: `readFileListAll` skips `exclude-dirs`, returns only per-folder file counts (`folders`) when more than `list-summary-over` (100) files are found — a project-root listing of 41,524 chars was re-sent on 17 later LLM calls despite the prompt saying "don't list the root" — and caps the count, a missing file is answered without calling `dstone-common`'s `FileUtil.readFile` (which `printStackTrace()`s a 90-line stack for every guessed path), `searchInFiles` returns capped `path:line: text` matches for a plain keyword, `readFile`/`readFileLines`/`readFileTail` cap characters); source-investigating Agents are told to `searchInFiles` first and open only the files they need, and to use `readFileLines` (`N: text` lines, optional `startLine`/`endLine`) whenever they need line numbers — with plain `readFile` a reasoning model counts lines by hand, burns the whole `max-tokens` on reasoning and returns an empty answer (`finishReason=LENGTH`, seen 2026-10-02 on `pilot-workflow` step04; `AgentExecutor.textOf()` now turns that case into an explicit `AgentContractException`, and SUPERVISOR/ROUTER failure messages carry the real reason instead of a constant `answer[null]`). `readFile` itself stays number-free because some Agents write what they read back with `writeFile`. `tools.shell.ShellExecTool`/`tools.python.PythonExecTool`/`tools.http.HttpCallTool` have no separate on/off flag — they only ever run a whitelisted script path or hit a whitelisted host (`dstone.ai.tool.shell.allowed-commands` / `.python.allowed-scripts` / `.http.allowed-hosts`, empty by default), never an LLM-supplied raw command/URL body. An empty whitelist is what keeps them inert by default; there used to be a `dstone.ai.tool.{shell,python,http}.enabled` flag documented alongside the whitelist, but it was never actually wired into the code (no `@ConditionalOnProperty` on the classes), so it was removed rather than implemented — the whitelist alone is the real gate.

Governance (PII/sensitive-word guardrails, usage logging/quota) is out of scope for this redesign, but two seams exist so it can be re-added without touching call sites: `common.config.ConfigChatClient.chatClient(...)` takes a plain `List<Advisor>` (Spring auto-collects any `@Bean Advisor`, so a governance module just adds one), and `runtime.tool.ToolExecutor.call(...)` is the single choke point every `TOOL` step call passes through.
