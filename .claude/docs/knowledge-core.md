# dstone-knowledge — 설계 규칙과 분석 Pass (M1–M5)

> CLAUDE.md에서 분리한 상세 메모입니다. 원문 그대로 옮겼으며, 필요한 작업일 때만 읽습니다.

### dstone-knowledge: Java Analysis → Knowledge Graph → RAG

Analyzes Java applications (Spring **and** legacy plain Java: Java 1.4–7 syntax, XML config, servlets, raw JDBC, JSP) into a structured knowledge model first, then projects that model into a Knowledge Graph and RAG chunks. Current state, design principles, schema and the milestone table (M0–M9) live in `docs/11.dstone-knowledge.md`; the source design is `docs/temp/Java_Application_Knowledge_Graph_RAG_Analysis_Platform_설계서_v1.0.docx`. Rules that were decided with the user and must hold for all later milestones:

- **DB-backed pipeline, never whole-project-in-memory.** Each pass handles one file, writes rows, drops the AST (`analysis_file_pass` tracks per-file/per-pass progress so a run resumes; `analysis_reference` holds not-yet-resolved references between the DECLARE and RESOLVE passes). JavaSymbolSolver's default source type solver caches every parsed file and must be replaced by a DB-index-backed solver with a bounded cache.
- **Framework-neutral core.** Scan/AST/symbols/call graph need plain Java only; Spring is one semantic-analyzer plugin among others (plain-Java entry points, Spring XML, iBATIS, Struts, JSP).
- **Lombok handled at declaration time**: generated members go in as `is_synthetic=true` symbols (no delombok — it shifts line numbers).
- **Embedding keyed by `(content_hash, model)`** in `rag_embedding`, which doubles as the resumable queue; Spring AI is used only for the embedding model call, vector SQL is MyBatis (no `PgVectorStore`).
- **`analysis_*` is the only source of truth**; `kg_node`/`kg_edge` are VIEWs, `rag_*` is always regenerable. Every analysis row carries `revision_id`; symbol ids are revision-independent hashes. Full snapshot per revision + retention.
- No LLM chat in this module — `dstone-ai-engine` Agents call its REST API through Tools.

Job model (M1, 2026-10-05): analysis starts over REST (`POST /api/projects/{id}/analyses`, local directory only — git checkout is still not implemented; an outside tool such as Jenkins is expected to check out and then call the API) and runs on `analysisJobExecutor`. `job.AnalysisJobRunner` runs every `job.AnalysisPass` bean in `order()` and skips passes already `DONE` for that revision in `analysis_revision_pass` — re-posting the same `revisionLabel` is how a dead/cancelled run resumes and how a newly added pass runs on an old revision. A new pass = a new `AnalysisPass` bean; it must be idempotent on re-run and call `context.checkCancelled()` in its loop. `AnalysisJobRecovery` marks leftover `READY`/`RUNNING` jobs `FAILED` at boot (single-instance assumption). Job threads set `SUPPRESS_SQL_LOG` so bulk writes don't flood the log. Inside a `sqlSessionBatch` transaction never touch `sqlSessionCommon` (MyBatis refuses to switch executor type mid-transaction) — `AnalysisJobReporter` progress/error writes go after the transaction. Per-file passes go through `job.FilePassRunner` (seeds `analysis_file_pass`, pulls `PENDING` files in chunks, runs each file as `prepare` → `write`, committing one file's rows plus its DONE mark in one transaction; a `FileHandler` returns `FileResult` or throws → that file `FAILED`, run continues). Passes so far: `scanner.ScanPass` (100), `incremental.CarryPass` (150), `parser.DeclarePass` (200), `resource.ResourcePass` (250), `incremental.CarryResolvePass` (290), `resolver.ResolvePass` (300), `resolver.LinkPass` (400, SQL-only), `semantic.SemanticPass` (500), `rag.DocumentPass` (600). `classes` is deliberately not in `scan.exclude-dirs` because the real sample apps under `/app/sampleApps/` (`anybiz_prd`, `cms4_prd` — exploded production WARs, outside the repo) keep their `.java` in `WEB-INF/classes`.

DECLARE (`parser`): `JavaSourceParser` tries language levels 21 → 8 → 1.4 (project `javaVersion` first) because old sources use today's keywords (`enum`, `assert`, `_`) as identifiers; `DeclarationCollector` looks at one file only — never the DB or other files — so order doesn't matter. Symbol ids are SHA-1 of `project | source root | kind | fqn[#signature]` (source root included because the same FQN really does occur twice in one project), and **signatures use parameter types as written in source** (generics erased), not resolved FQNs — resolving needs other files and would make ids order-dependent. References are stored unresolved in `analysis_reference` with the position of the *name* token (chained calls `a.get().get()` share an expression start). Anonymous classes are kind `ANONYMOUS` (`Outer$1`) and own the calls inside them; lambdas don't. `LombokExpander` adds what Lombok would generate as `is_synthetic` rows by reading annotations only — this module's own code uses no Lombok (repo-wide rule: no Lombok in dstone code). Same FQN in two files of one source root: the file named after the type wins regardless of processing order, the other is `SKIPPED` with a `DUPLICATE_TYPE` error. JSON columns are written with `common.util.JsonText` (compact), not `ConvertUtil.convertToJson` (pretty-prints). A cheap independent check of DECLARE output: named + anonymous type count equals the number of `.class` files of a compiled target.

Type solving (`symbol`): `DbTypeSolver` answers "which file declares this FQN" from `analysis_symbol`, parses only that file and keeps ASTs in a `BoundedCache` (LRU). That alone does **not** bound memory — `CombinedTypeSolver` must be built with `NoCache.create()` (its default cache pins every resolved declaration, hence every AST) and `JavaParserFacade.clearInstances()` must be called after each file. Solver order: `DbTypeSolver` → `ReflectionTypeSolver(new ResolvePass.JdkClassFilter())` → `JarTypeSolver`s. The JDK filter matters both ways: unfiltered reflection would resolve the target's `org.springframework…` against the analyzer's own Spring, while JavaSymbolSolver's built-in `jreOnly` only passes `java.`/`javax.` and misses `org.w3c.dom` etc.

RESOLVE/LINK (`resolver`, M2): **the target is never built** — jars are used when present (`symbol.ClasspathResolver`: every `*.jar` under the project folder plus the project's `classpath` field, which accepts jar files/directories separated by comma, newline or path separator, so `mvn dependency:build-classpath` output can be pasted as is) and the analysis still finishes without them. `ReferenceResolver` matches each `analysis_reference` row to its AST node by position, then tries in order: symbol solver (HIGH) → owner type known, member looked up by name/arity in that type and its in-project ancestors (HIGH if the single hit is a synthetic/Lombok member, else MEDIUM, several → LOW) → owner type external (EXTERNAL_METHOD `Type.name`, MEDIUM) → project-wide name/arity with ≤5 candidates (LOW) → `UNRESOLVED` with a reason. Owner type comes from the solver, else from the variable's declaration text + imports, a synthetic field (`log`), or the declared return type of the preceding call (builder chains); when that return type is outside the project it is qualified through the imports of the file declaring that method (or `java.lang.`) and handed to the external-owner step instead of falling to the name guess (2026-11-08, hen `EncUtil.getEncryptor().decrypt(...)` without the jasypt jar used to link three project `decrypt(String)` methods). The by-name guess skips `private` methods declared in other files (`SymbolDao.selectMethodCandidates` takes the caller's file id, cache key includes it). A scope-less call not found in the enclosing types is treated as inherited from an external supertype and is deliberately **not** guessed project-wide. Resolved declarations are mapped to `method_id` by position (file + line + name + arity), not by name, so anonymous/local class methods work. `LinkPass` builds `OVERRIDES` and `CALLS_POSSIBLE_IMPLEMENTATION` in SQL; the latter only for abstract targets — including concrete overridden methods fanned 1,553 calls of `BaseVO.setMb_id()` out to every overriding subclass (27,715 noise edges on `anybiz_prd`). Measured: 99.9% of calls resolved on the two sample WARs; with zero jars a copy of `dstone-batchadmin` still recovered 227/234 in-project call pairs, HIGH and MEDIUM edges all correct, LOW 11/27 — treat LOW as a hint only. `src/test/resources/samples/lombok-app` (calls into Lombok-generated members, no Lombok jar), `cycle-app` and `legacy-app` each carry expected results in their README. Large-scale RESOLVE (tens of thousands of files) has not been run yet.

SEMANTIC (`semantic`, M3): `SemanticPass` clears and rebuilds, in one `sqlSessionCommon` transaction, everything its plugins produce — `analysis_endpoint`, `analysis_symbol.layer`, `INJECTS` relations, `proxy_related`, and the `web.xml` rows in `analysis_resource`. A framework rule = a new `SemanticPlugin` bean (`name`/`order`/`run`); it must be a no-op on projects it doesn't apply to and should derive from `analysis_annotation`/`analysis_relation` in SQL rather than re-parse Java (annotation attributes are already JSON, so e.g. class-level + method-level `@RequestMapping` paths are joined with `jsonb_array_elements_text` in `SemanticDao.xml`). Current plugins (plus `RichClientPlugin` 510, see the rich-client paragraph below): `SpringPlugin` (100: HTTP/SCHEDULED/LISTENER endpoints, `@Autowired` field → `INJECTS`, stereotype layers HIGH), `ServletPlugin` (200: `web.xml` via `WebXmlReader`, which blocks external DTD fetches because Servlet ≤2.3 descriptors carry an internet DOCTYPE; external servlet classes such as `DispatcherServlet` are kept as method-less `SERVLET` endpoints; `HttpServlet` subclasses → CONTROLLER MEDIUM), `PlainJavaPlugin` (300: `main`, `Runnable`/`Thread`/`Callable` → THREAD, JSPs outside `WEB-INF`), `NamingLayerPlugin` (900: suffix rules, LOW, only fills what earlier plugins left null). Stored lookups (2026-11-06, see `knowledge-ui.md`): `MethodTitlePlugin` (960), `ScreenDictionaryPlugin` (970), `TableDictionaryPlugin` (980) write `METHOD_TITLE`/`METHOD_TITLE_SKIP`/`DICT_SCREEN_NAME`/`DICT_TABLE_NAME`/`DICT_COLUMN_NAME`/`SEMANTIC_STATUS` rows into `analysis_resource` so detail screens never read the project folder; add any new SEMANTIC resource type to `SemanticDao.xml` `deleteWebResources`. Annotations are matched by simple name because wildcard imports leave `annotation_fqn` null. Not handled yet: constant-valued mapping paths, inherited class-level mappings, constructor/setter injection, lambda `Runnable`s. The M5 plugins (`MyBatisPlugin`, `JspPlugin`, `StrutsPlugin`) are described below.

Rule files (2026-11-07): framework conventions moved out of the plugins into `conf/rules/*.yml` (one file = one rule set; format in `conf/rules/README.md`, docs §4.7.1). Plugins keep the *how* (SQL that links things), the files hold the *what* (annotation names, SQL-name methods + `argIndex`/`receiverTypes`/`template`, super types → layer/endpoint, name regexes, screen call/field/open/menu rules). Built-in sets `java`/`servlet`/`spring`/`mybatis`/`fallback` plus project folder `hi-japan/` (`frontend`, `backend`) reproduce the old hard-coded lists — checked on 12 revisions by snapshotting every SEMANTIC output before/after (docs §10.2). Rules to keep:
- `semantic.rule.RuleSetParser` is strict (unknown key, bad layer, bad regex → boot fails with `file path: reason`); `SemanticRuleRegistry` re-reads the folder at every SEMANTIC start, so a rule change needs only `rerunFrom=SEMANTIC`, no restart. Sets apply in `order`; layers are first-wins, so broad rules (`@Component`, name regexes) live in `fallback.yml` (900). Two sets making endpoints from the same annotation are rejected at merge.
- `autoApply: false` sets apply only when listed in the project's `ruleSets` (`analysis_project.rule_sets`). Every SEMANTIC run writes one `RULE_SET` row per applied set (name, file, 12-char hash) into `analysis_resource`; `GET /api/revisions/{id}/rules` compares them with the current files.
- Call-argument rules still link only computed names. Arg 0 comes from `arg_text`; args 1..9 from `analysis_reference.args_json` (added by DECLARE in analyzer 1.1 — older revisions need DECLARE again for `argIndex ≥ 1`). `receiverTypes` matches the RESOLVE target type (and in-project subtypes), an external `Type.name(` target, or a scope-less/`this` call from a subtype.
- `POST /api/revisions/{id}/rules/trial` runs `SemanticPass.runPlugins` inside one transaction, diffs temp-table snapshots (`RuleDao.xml` `semanticFacts`) and rolls back; `GET …/rules/candidates` lists literal-argument calls whose value equals a statement/JSP name, unknown annotations, and super types with many unlayered subtypes, each with a YAML `suggestion`.
- Screen rules (`screens.calls`/`opens`) also take `argIndex`: 0 keeps the original regex; ≥1 splits arguments up to the matching `)` (`ScreenScript.literalArguments`, ignoring commas in strings/nested brackets/comments) and uses the arg only if it is one quoted literal. Skipped non-literal calls are counted per rule into `SEMANTIC_STATUS` `SCREEN_RULES` (with `literalAt` = other positions holding a literal); candidates `screenRules` turns those into `argIndex` suggestions.
- Old keys `dstone.knowledge.semantic.screen.*` / `layer.super-types` are still read (as set `application-yml`, last, with a warning) but new rules go in files.

RAG (`rag`, M4): no manual step between analysis and search. `DocumentPass` builds FILE/TYPE/METHOD documents per Java file from DB facts plus source lines cut by line number (no re-parse; `CodeDocumentBuilder` is pure and unit-tested) and enqueues chunk hashes into `rag_embedding` as `PENDING`; `EmbeddingWorker`, a daemon thread started on `ApplicationReadyEvent`, drains that table in batches through Spring AI's `EmbeddingModel` (Ollama `bge-m3:latest`, 1024 dims, same server as `dstone-ai-engine`; `spring.ai.model.chat: none`). So a job goes `DONE` within seconds of DOCUMENT while embedding continues behind it — check `GET /api/revisions/{id}/rag`. METHOD chunks deliberately carry analysis facts as Korean text (endpoint path, layer, callees, possible implementations, callers, doc comment) ahead of the source, because a question like "주문 취소는 어디서 처리하나" doesn't resemble source text; trivial accessors get no METHOD document (`rag.skip-accessors`): `get`/`set`/`is` name, ≤3 lines **and a field of that name in the same type** — name and length alone also dropped short working methods such as `DBUtil.getConnection()`, which then could not be found at all (`anybiz_prd`: 14,762 methods → 5,375 documents). When the embedding server is down the worker counts nothing as failed and retries every 30 s; only an item that still fails when sent alone gets `attempts+1` (3 → `FAILED`). `POST /api/search` embeds the query and runs a MyBatis pgvector query filtered by revision inside a transaction with `SET LOCAL hnsw.iterative_scan = relaxed_order` — embeddings of all revisions share one HNSW index, so without iterative scan a revision filter can return too few rows. Model name and dimensions must be read through `RagSettings` everywhere (enqueue, worker, search) because the key is `(content_hash, model)`. CPU embedding here runs ~96 chunks/min. Search itself is hybrid since M6 (below). Local pitfall hit on 2026-10-05: `/opt/ollama/ollama-start.sh` refused to start because a stale `ollama-server.pid` held a number now reused as a **thread id** of another process (`kill -0` succeeds on TIDs) — check `ss -ltnp | grep 11434`, delete the pid file, start; never run `ollama-stop.sh` on a stale pid.

Non-Java resources (`resource` + `semantic`, M5, 2026-10-05): reading and linking are split — `resource.ResourcePass` (250) reads one file at a time and only stores (MyBatis/iBATIS mappers → `analysis_mapper`, `.properties`/YAML → `analysis_config`, `pom.xml`/`build.gradle`/Spring XML → `analysis_resource`), and SEMANTIC plugins link afterwards, because an `<include>` fragment may live in another file and both ends of a relation must already be in the DB. The chain is `JSP ─REQUESTS→ method ─CALLS→ … ─EXECUTES_SQL→ statement ─READS_TABLE/WRITES_TABLE→ table`, plus `method ─RENDERS→ JSP` and `JSP ─INCLUDES→ JSP`. Relation ends are no longer symbols only: a statement is `'S' + mapper_id`, a file is `'F' + file_id`, a table is just a name in `to_external` (no node). `/callees` follows `EXECUTES_SQL`/`READS_TABLE`/`WRITES_TABLE`/`RENDERS`, `/callers` includes `REQUESTS`; `/tables`, `/tables/{table}`, `/mappers`, `/resources` are in `ResourceController`. Rules to keep:

- **Secrets are never stored**: config keys/bean properties that look like `password`/`secret`/`token`/`api-key` get `****` (`value_type = MASKED`) — analysis output is searched and forwarded.
- **All XML goes through `common.util.SafeXml`** (external DTD/entities replaced by empty content — old descriptors carry an internet DOCTYPE and parsing would hang on it); YAML is read with `SafeConstructor`.
- **Statement names are computed, never guessed** (`MyBatisPlugin` + `semantic.ConstantEvaluator`): DECLARE keeps a call's first argument as written in `analysis_reference.arg_text` (only when it contains a string literal); the evaluator handles literals, `+`, field initializers of the type and its ancestors, and no-arg methods with a single `return`. Any unknown part (local variable, parameter) → the whole value is unknown. A name that is known but has no statement stays as an `UNRESOLVED` `EXECUTES_SQL` with the name in `to_external`.
- **JSQLParser only in fast mode, on the calling thread** (`semantic.SqlTableExtractor`): its fallback complex mode can run practically forever on some SQL, and its timeout feature merely stops waiting while the parse thread keeps burning CPU — that piled up dozens of threads and made SEMANTIC take ~7 minutes on `anybiz_prd`. SQL deeper than 12 parentheses or longer than 20,000 chars skips the parser. Parser failure falls back to a regex over `FROM`/`JOIN`/`INTO`/`UPDATE` (`MEDIUM`, `properties_json.via = PATTERN`) — about 30% of statements on `anybiz_prd` (530 of 1,853; 278 of those are one JSQLParser internal error, `Index -1 out of bounds`, cause not tracked down).
- **JSP Java code is converted to Java, not analyzed separately** (`parser.JspToJava`): scriptlets become the body of `_jspService()`, and every dropped character keeps its newline so line N of the converted source is line N of the JSP. A JSP without Java code is skipped by DECLARE (stays `PENDING` in `parse_status`) but still gets `RENDERS`/`REQUESTS`/`INCLUDES` and a `VIEW` document.
- `RENDERS` matches `new ModelAndView("x")`/`setViewName("x")` to the single JSP whose path ends with `x.jsp`; `REQUESTS` (MEDIUM) takes every `/path`-looking text in a JSP and keeps only exact matches with an endpoint path. A low `RENDERS` count is expected, not a bug: on `anybiz_prd` 920 of 1,405 view-name references are `"jsonView"` (a view bean) and all 463 linkable ones were linked (checked 2026-10-05). `return "order/list";` view names and Tiles are not handled.
- `StrutsPlugin` reads `struts-config.xml`/`struts.xml` itself (like `ServletPlugin` reads `web.xml`); a `DispatchAction` endpoint is linked to its type only, and Struts 2 is covered by unit tests only.
- `DocumentPass` now also writes `MAPPER` (one per statement) and `VIEW` (one per JSP) documents via `rag.ResourceDocumentBuilder`, and METHOD documents carry "executed SQL / rendered view" lines.

`src/test/resources/samples/struts-app` (Struts 1 + iBATIS + JSP, expected values in its README) is the end-to-end check for this chain, since the two real WARs have neither Struts nor iBATIS.


Hang/cycle defenses (checked by `src/test/resources/samples/cycle-app`): call-graph CTEs are bounded by `depth` (≤5) with `UNION` dedup and return each edge at its shallowest depth; the ancestor CTE in LINK stops at depth 20 and drops `type = ancestor` rows (cyclic inheritance in non-compiling source would otherwise make methods override themselves); the symbol solver's `StackOverflowError` is caught per reference; a `StackOverflowError` while parsing/walking a file is turned into a per-file `TOO_DEEP` failure in `DeclarePass` and again in `FilePassRunner` — it is an `Error`, so without that catch it kills the job and every restart dies on the same file; RESOLVE has a per-file budget (`dstone.knowledge.resolve.file-timeout-seconds`, default 120 → remaining references become `UNRESOLVED` "시간 초과", error `RESOLVE_TIMEOUT`) and checks cancellation per reference. A library call that never returns is handled by `job.FileWatchdog`: `FileHandler<T>` is split into `prepare` (read/parse/resolve, **no DB writes, no transaction**, runs on a watched worker thread) and `write` (one batch transaction on the job thread); if `prepare` exceeds `dstone.knowledge.job.file-hard-timeout-seconds` (600) the file is marked `FAILED`/`HUNG`, the worker thread is abandoned (Java cannot kill it — it may keep a core busy until restart), `FileHandler.reset()` rebuilds everything that thread was touching (RESOLVE's whole solver/resolver "engine"), and after more than `job.max-stuck-files` (3) abandons the job fails so zombie threads don't pile up. Keep heavy work in `prepare` and DB writes in `write` in any new per-file pass — that split is what lets an abandoned thread hold no connection or lock. Consequently `SymbolDao` (read by `prepare`) uses `sqlSessionCommon`; only `...InBatch` DAO methods run inside the write transaction.

DB access: single `dataSourceCommon` (`spring.datasource.common.hikari.*`, PostgreSQL `dstone_knowledge`), MyBatis `sqlSessionCommon` + `sqlSessionBatch` (`ExecutorType.BATCH`, for bulk writes inside a transaction), and a programmatic `txTemplateCommon` instead of the name-based AOP transactions other modules use (analysis runs for hours and commits every N files). Schema is manual (`src/main/resources/schema/01-init…sql` as postgres superuser, `02-create-table…sql` as the app role; idempotent). Unit tests run with `mvn -pl dstone-knowledge test` (surefire is pinned to 3.5.2 in this module's pom; Maven's default 2.17 can't run JUnit 5). `spring-boot-starter-test` carries a `spring-boot-starter-logging` exclusion — without it logback lands in the runnable jar and boot dies with `log4j-slf4j2-impl cannot be present with log4j-to-slf4j`. `src/test/resources/samples/legacy-app` is a deliberately EUC-KR, Java-1.4-syntax sample (do not re-save as UTF-8); its README holds the expected counts.
