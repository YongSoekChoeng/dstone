# dstone-ai-engine — 테스트 방법과 문서 위치

> CLAUDE.md에서 분리한 상세 메모입니다. 원문 그대로 옮겼으며, 필요한 작업일 때만 읽습니다.

Full architecture, the YAML field reference (§7) with copy-paste templates for every step type/Agent/MCP server (§8), and the API/config reference live in `docs/09.dstone-ai-engine.md` — it describes the current state only, no change history. **Tests run Workflows without a server** (since 2026-10-18; `src/test` had been deleted on 2026-10-12 after a `DefinitionFilesTest` count assertion broke the build). `support.WorkflowTestBase` is `@SpringBootTest(webEnvironment = NONE)` + `@Import(TestEngineConfig)`: the real context starts (loader, boot validation, Tools, MCP via npx), only outside systems are replaced — `InMemoryWorkFlowExecutionStore` (`@Primary` subclass of the store; the real SQL is PostgreSQL-only), a Mockito `DataSource` (only so `ConfigMapper` can build MyBatis) and `RedisTemplate` (`RateLimitFilter` injects it), and `ScriptedChatModel` (`@Primary` ChatModel next to the real provider bean; tests queue answers with `chatModel.answer(...)`, an unexpected LLM call throws so the run ends FAILED; `prompts()` records what was sent). **Switch `dstone.ai.test.llmcall`** in `conf/application.yml` (default `false`; `-Ddstone.ai.test.llmcall=true` for one run): when true the stand-in forwards `call`/`stream` to the real provider's ChatModel and ignores `answer(...)`; it must also forward `getDefaultOptions()` and `getOptions()`, otherwise ChatClient builds `DefaultChatOptions` and `OpenAiChatModel` fails with a ClassCastException. Scripted-only tests `assumeFalse(chatModel.isLlmCall())`. Verified once 2026-10-18 on the sm test with OpenRouter (the LLM picked `일반` with its own reason). Helpers `run(id, input)` (= `checkInput` + `executeSync`, i.e. the `/execute` path), `decide(...)`, `state(...)`, `stepIds(...)`, `json(...)`. `stepper(id, input)` returns a `WorkflowStepper` for step-by-step tests: `flow.step("stepId")` runs exactly that step via `WorkFlowExecutor.run(workflow, execution, stepLimit=1)` (an overload added for this; `run(workflow, execution)` = limit 0 = unlimited, same loop) and stops RUNNING at the next step; a step id that is not the current one throws AssertionError; `put(name, value)` + `jumpTo(id)` start mid-flow, `decide(decision, comment)` continues an APPROVAL. `stepper(id, stepId, stepInput)` starts at `stepId` and runs that first step with `stepInput` instead of evaluating its `with` (`WorkFlowExecutor.runStepWith()`, not for forEach steps; `flow.step(id, input)` does the same mid-run). The user asked for that per-step format: one block per step (`stepN = this.stepper(WORKFLOW_ID, "stepId", stepNParam); stepN.step("stepId"); assertThat(stepN.status())...`); `workflow/sm/RequiredToolsTest` runs step02 that way, and `workflow/sm/WorkFlowTest` keeps one test on a `@TempDir` (the scripted LLM writes no files, so the documents are created up front) — its per-step and whole-flow tests were deleted on 2026-11-05 because they still used old step ids. The static block sets `spring.profiles.active` to `wsl` (Windows: `local`) when unset and calls `setSysProperties()`, because dstone-common `LogUtil` loads `env{-profile}.properties` from the classpath on first use and would otherwise put the Windows `env.properties` (incl. `MCP_STDIO_COMMAND_PREFIX=cmd.exe /c`, which made npx time out in WSL). **Tests use main's definitions and config, no copies** (the user's decision): there is no `src/test/resources`; `WorkflowTestBase` sets `spring.config.location=file:${APP_CONF_DIR}/application.yml` and `logging.config=file:${APP_CONF_DIR}/log4j2.xml` (so test logs go to the real `execution.log`) and overrides only what the stand-ins need via `@SpringBootTest(properties=...)`: `spring.data.redis.enabled=false`, `spring.data.redis.repositories.enabled=false`, `spring.sql.init.mode=never`. **The user chose: no test-only definition files** — tests read the real `conf/definitions` through `conf/application.yml`; `definition/DefinitionReloadTest` only calls `check` (never `save`) so it writes nothing there. Do not assert definition counts. Tests live in `workflow/<folder>/` mirroring `definitions/workflows/`; file-editing Workflows use `@TempDir`; MCP tests `assumeTrue(hasTool(...))`. Two production fixes came with it: `ConfigChatClient.chatMemoryRepository()` now looks up `ObjectProvider<RedisChatMemoryRepository>` (looking up `ChatMemoryRepository` found itself when Redis was off → circular-reference boot failure), and dstone-common `EncPropertyEnvironmentPostProcessor` no longer wraps the `Inlined Test Properties` source (Spring Boot's test support casts it to `MapPropertySource`). **The build skips the test phase** (the user's decision): `dstone-ai-engine/pom.xml` sets `<skipTests>true</skipTests>`, so `mvn package`/`install` (and the root reactor build) only compile tests; run them with `mvn test -DskipTests=false` (add `-Dtest=...` for one class, `-Ddstone.ai.test.llmcall=true` for the real LLM). Definition files are still also checked by the boot-time validation.
