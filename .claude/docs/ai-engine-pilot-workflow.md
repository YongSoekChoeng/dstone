Things to remember: (1) **Agents on this path emit data, never documents** — since 2026-10-11 the four md files (`01-requirements.md`, `02-impact.md`, `04-design.md`, `04-tasks.md`, steps 13/14/21/32) are written by one extra Agent, `pilot-newdev-doc-writer-agent` (input `{document, filePath, data}`, Tools `writeFile`/`appendFile` only, `reasoning: none`, one LLM call per document, layout in its prompt; the user chose this over JSON files or no documents when the mustache templates were removed), while later steps still read `state`, never the documents — so a wrongly written document does not change the implementation and editing one by hand changes nothing downstream; verified only by a boot of the packaged jar with real Tools (no warnings), the LLM-free `sample-tool-edit-report` run and one direct chat call of the Agent with a small 요구사항정의서 input (5 s, layout as specified) — the Workflow steps themselves, the long 설계서 and `step26` have not been run with an LLM (corrections go into the approval `comment`, which becomes the Agent's `feedback`); (2) a check result is stored as `state.impactCheck` / `state.designCheck` = `{ok, problems, text, feedback}` — `text` goes into the documents, `feedback` (empty when there is no problem) into the Agent's `feedback` on a redo; (3) checks never auto-retry — a failed check is written into the doc and the human picks 재분석/재설계 (an automatic loop would spin to `maxIterations` on a persistent mistake); (4) forEach runs in parallel, so one file must not appear twice in the targets, and a partial forEach failure is routed on to the check/summary step instead of failing the run; (5) per-file design needs the names shared between files fixed up front, hence `sharedNames`; (6) `return` leaves out `state.sources`, `state.designInputs` and `state.developInputs` (file contents); (7) **only TOOL steps touch source files** — what the design fixed exactly is applied without an LLM, and the one thing left to the LLM (turning the designer's prose `removes`/`adds` into edits) is returned as `edits[{action: delete|replace|insertAfter, startLine, endLine, startText, endText, newText}]` against the numbered source, never applied by the Agent; `editFileLines` applies a file's edits all-or-nothing (line numbers refer to the file before the call; `startText`/`endText` must equal those lines, blank lines at a range edge are skipped; overlap or mismatch → nothing changed, reason in `04-tasks.md`), and appends `주의:` when the bracket balance changed, which makes the task `확인 필요`. Measured once on the `testApp` "new FAQ like the sample board" request (OpenRouter `qwen/qwen3.8-27b`): `step01` 4 s, `step09` 5 min 4 s (7 Tool calls, 9 files), `step11` 42 s with a clean check, `step17` 8 files in 27 s, and `step18` caught a real non-unique `before`. The implementation stretch was then run to the end four times on a copy of the source (same request): 10–28 s for all of it (submit to done 3 min 22 s and 3 min 45 s with instant approvals), every file that needed edits applied on the last three runs, the new Java files free of syntax errors under `javac` and the mapper well-formed — **not built, not started**. Real defects those runs produced, i.e. why a human still has to look: deleting a line took a bracket with it twice (the SQL line `OR writer_nm LIKE ...)`, and the closing `};` of a JS object — the first is why the bracket notice exists, the second was caught by it); a rename table entry `title → question` also rewrote a grid's `title:` attribute, because `copyFileWithReplace` replaces text, not words (the designer prompt now says to write such a name with its quotes or neighbours — it did on the next single run); and old names survive in comments the rename table does not list. Why the edit Agent has no Tools (measured on those six files): with `writeFile` it rewrote whole files; with `replaceInFile` and `reasoning: none` 3–4 of 6 burned all 30 calls (re-reading the finished file, resending a failed `oldText` unchanged even when the Tool quoted the file's real text, deleting and restoring an import); with `replaceInFile` and default reasoning 4 of 6 finished at 32 s–4 min 48 s each, one spent all 16,384 output tokens on reasoning and one passed 7 minutes; with no Tools, line-number edits and `none` each file took 1–27 s. The 재분석 and 참고구현재조사 routes were run once each (a path `step09` mistyped is only fixed by 참고구현재조사, not 재분석); **재설계 has not been run.** `reasoning` was set by measurement: Agents that only reshape given material (`newdev-analyzer`, `newdev-file-designer`) use `none` (the analyzer timed out at the 5-minute response limit with the default and took 42–66 s with `none`); an Agent that investigates with Tools must **not** be switched off (`newdev-reference` with `none` repeated lookups until it hit `maxToolCalls` 15); on this model `low`/`medium` have no effect, so the `reasoning: low` put on the 일반-path reviewer is inert until the model changes. On the 일반 path the prompts' `[조회 한도]` sections were removed in favour of `maxToolCalls` (requirement/impact/review/architect 40 → 32, developer 60 — the engine's "N calls left, save now" notice replaces the prompt rule), and the developer Agent got `readFileLines` plus a prompt rule that limits its knowledge Tools to "locating what the design names" (resolving the comment-vs-`tools` mismatch in favour of the `tools` list the user had edited); and the 일반-path developer Agent no longer rewrites files (`replaceInFile` for existing files, `copyFileWithReplace` + `replaceInFile` for new ones, `writeFile` only for a new file without a reference); these four were boot-checked only — that developer Agent still edits through a Tool loop, the shape that proved unstable on the 신규개발 path, so if it stalls move it to line-number edits + `editFileLines` too. File-editing Tools in `tools.utils.FileUtil` (2026-10-08): `writeFile` now saves the text verbatim and returns a result string (it used to split lines through `StringUtil.toStrArray`, which dropped line breaks and indentation, and returned `void` so a failed write looked like success), `appendFile` follows the existing file's charset and line-break style, `replaceInFile(filePath, oldText, newText)` replaces only when `oldText` occurs exactly once (CRLF/LF differences are bridged, charset kept, a miss is answered with the file's actual text at that spot, `oldText == newText` is refused; since 2026-11-04 an exact miss is retried whitespace-insensitively per whole line (`FileTool.looseMatch`, also used by `editFileTexts`): exactly one match → replaced, lines equal to an `oldText` line keep the file's original text, new lines get the file's indentation — because `sm-workflow` step13 (execution `6e02b73d…`) resent an `oldText` with 3 tabs instead of 4 87 times and spent the whole 100-call budget; covered by `tools/file/FileToolLooseMatchTest`), `copyFileWithReplace(sourcePath, targetPath, replacements)` (longest name first, single pass so a replaced spot is never replaced again, never overwrites an existing target) and `editFileLines` (above); the three editing Tools share one lock because forEach steps run in parallel. `dstone-common`'s `FileUtil.makeDir(dirPath)` now creates the directory itself, not just its parent (every caller passes a directory).
