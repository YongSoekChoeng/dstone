# dstone-knowledge — dstone-boot 화면(M8)과 노드 맵

> CLAUDE.md에서 분리한 상세 메모입니다. 원문 그대로 옮겼으며, 필요한 작업일 때만 읽습니다.

Screens (M8, 2026-10-05; node map added 2026-10-06, next paragraph): this module has no UI; the screens live in **`dstone-boot`** (`webapp/WEB-INF/views/knowledge/**.jsp`, `webapp/knowledge/assets/{js,css}`, reached via `defaultLink.do?defaultLink=knowledge/index|knowledge/search/search|knowledge/impact/impact|knowledge/diff/diff`, linked from `views/common/left.jsp` and the AI header). The browser never calls `dstone-knowledge` directly: `net.dstone.boot.knowledge.controller.KnowledgeProxyController` (`POST /knowledge/api/call.do` `{method, path, query, body}`) → `KnowledgeProxyService` forwards as is, restricted to paths under `/api/` (no `..`, `//`, `?`, `#`) and `GET`/`POST`/`DELETE`, and returns the upstream status + body untouched. It reports its own rejections as `{status, message}` `ResponseEntity`s instead of throwing, because `dstone-boot`'s global exception handling turns exceptions into HTTP 200 with a different body shape. Upload is separate (`/knowledge/api/upload.do`) and reads the file through `RequestUtil`, since `dstone-boot` runs with `spring.servlet.multipart.enabled=false` (a `MultipartFile` parameter is always empty there). Config: `interface.knowledge.base-url` (`KNOWLEDGE_HOST`/`KNOWLEDGE_PORT` in `dstone-boot/conf/env*.properties`; each profile loads exactly one env file, so a new variable must be added to all of them) and optional `interface.knowledge.api-key`. Usage help lives in the screens themselves: a "이렇게 씁니다" block with fill-in example buttons on each page and a guide page (`knowledge/guide/guide`, incl. a click-through tutorial on `struts-app` with the expected results). Every table of the revision summary is described in one dictionary, `knowledge/assets/js/knowledge-terms.js` (`SECTIONS`: path into the summary response, column meanings, meaning of each code value, how to read it; metric formulas mirror `RelationDao.xml` `insertMetrics`) — the summary screen uses it for inline meanings, per-table help and the plain-language "한눈에 보기" verdict (`project.js` `verdictBox`), and the guide page renders the same dictionary in full, so **when the summary API or a metric changes, update that file**; a response item missing from `SECTIONS` is not shown. `struts-app` deliberately has no jars, so its verdict shows call resolution 57.69% in red — the guide explains this. **Since 2026-10-20 the AI and Knowledge screens no longer use the analyzer theme** (the user called the old look not good enough for a commercial product; it replaced the 2026-10-12 "same as analyzer" format). They share one look but are separate consoles ("Dstone AI" and "Dstone Knowledge", split again at the user's request the same day — each sidebar shows only its own menu, no cross-menu): `ai/common/head.jsp` and `knowledge/common/head.jsp` load `ai/assets/css/console.css` (design tokens as CSS variables on `:root` — colors, radius, shadows, system font stack incl. Pretendard/Noto Sans KR/Malgun Gothic, no downloaded fonts — plus the shell, page header, panel cards, condition tables, buttons, inputs, list tables, status badges, messages, `kn-howto`), then `ai/assets/css/main.css` (AI parts: overview cards, chat, Workflow, designer), then `knowledge.css` for Knowledge pages; all colors come from the variables. Both `common/header.jsp` files only include `WEB-INF/views/console/sidebar.jsp` with `<jsp:param name="section" value="ai|knowledge"/>` (dark left sidebar: brand, a bordered "dstone-boot로 돌아가기" link to `/views/main` at the top, then that section's menu only; inline SVG icons, current page from `defaultLink`; under 1024px it becomes a horizontal top bar); `#page-wrapper` is a CSS grid (sidebar | `#main`, footer under main), so page JSPs kept their `#main > .container > .row > .col-12` wrappers. Each page starts with `<section class="cs-page-head">` (`p.cs-eyebrow` group name + Korean `h2` title + description); every `section.ai-panel` is a white card. Class names used by page scripts (`ai-form`, `document-list-table`, `workflow-badge-*`, `kn-*`, `wd-*`, `chat-*`) were kept, only restyled; inputs stay in condition tables (`table.ai-form` + `div.ai-form-actions`). Verified 2026-10-20 with headless Chromium on a copy at port 7181: all 11 pages load with no page/console errors at 1440px and 390px, the designer interaction test passes, the revision summary and node map render.

Node map (2026-10-06): a fifth screen, `knowledge/graph/graph` ("노드 맵"), draws the call structure with Cytoscape.js 3.34.3 — vendored at `dstone-boot` `webapp/knowledge/assets/lib/cytoscape.min.js` (no CDN, closed-network SI sites), page script `knowledge/assets/js/graph.js`; highlight.js 11.11.1 is vendored next to it (`highlight.min.js` + `highlight-github.min.css`, loaded only by `graph.jsp`) to colour the [소스 보기]/[SQL 보기] popup (language from `code.kind`/file extension, none above 300k chars). It adds nothing to the analysis: `api.service.GraphService` + `sqlmap/analysis/GraphDao.xml` only read `analysis_relation`. Three endpoints under `/api/revisions/{id}/graph`: (1) `GET /graph` — the whole map at **bundle level, never method level** (`anybiz_prd` has 15k methods): nodes are `TYPE` (nested/anonymous types folded into the outermost type, id = symbol id), `JSP` (`F`+file id, incl. its scriptlet Java), `MAPPER` (one mapper file, `M`+file id) and `TABLE` (`T:`+name); edges are method-level relations summed per node pair (`count`, strongest `confidence`), default relations = the call flow (`CALLS`, `CALLS_POSSIBLE_IMPLEMENTATION`, `EXECUTES_SQL`, `READS_TABLE`, `WRITES_TABLE`, `RENDERS`, `REQUESTS`), `relations=` can add `EXTENDS`/`IMPLEMENTS`/`INJECTS`/`INCLUDES`; (2) `GET /graph/neighborhood?id=&up=&down=` — the method-level tree around one node (bundle id, method id or `S`+mapper id; depth default 3, max 10, 3,000 edges per direction → `truncated`), node `level` 0 = picked, negative = callers, positive = callees; (3) `GET /graph/node?id=` — detail (a screen node also carries `screenName`/`screenNameVia`/`screenNameWhere` since 2026-10-25: `<title>` → Nexacro `titletext` (pure `semantic.ScreenTitle`, in `JspPlugin`/`RichClientPlugin`), else the menu name from a menu list written in the source (`semantic.ScreenMenuPlugin` 520 + pure `ScreenMenu`, rule `dstone.knowledge.semantic.screen.menu-rules: "MENU_NM=SRC_PATH"` = name key=path key, both keys inside one `{ }` or XML tag; HI-Japan `ui/main.xml` → 155 screens), stored as `analysis_resource` `SCREEN_NAME` — older revisions need `rerunFrom: SEMANTIC`; when that name has no Hangul (HI-Japan menus are Japanese) the Korean name from a screen dictionary CSV is shown instead, read live at detail time like the table dictionary (`dictionary.ScreenDictionaryReader`, `dstone.knowledge.dictionary.screen-file.{projectId}`, HI-Japan `../docs/01.analysis/01.as-is/E.기능/00-1.화면목록.csv` → all 315 WebSquare screens), with the original in `screenNameOriginal` ("원어명" row); shown as the first "화면명" row of both the side panel and the tree popup), whose `document` is the DOCUMENT-pass text from `rag_document` as is (nothing is generated; null for skipped accessors or revisions without DOCUMENT), split since 2026-10-25 by `api.service.DocumentSections` into `document` (the facts before the `소스:`/`SQL:` line) and `code` `{kind: SOURCE|SQL, text}` (chunk continuation headers removed) — the screen shows `code` only through a [소스 보기]/[SQL 보기] button and popup `#kn-code-modal` (disabled for `JSP` nodes since 2026-11-06: a VIEW document keeps only its first `MAX_VIEW_CHUNKS = 2` chunks with blank lines/indent stripped, so it is not the whole file — the user chose disabling over reading the file); for SQL `code.formatted` is an indented copy from the pure `common.util.SqlFormatter` (clauses on their own line, leading commas/AND/OR, subqueries indented; only whitespace changes — if the non-whitespace text differs from the input it returns the input), shown first with a [원문 보기] toggle; a TABLE node also carries a Korean name and columns built by `api.service.TableDictionaryService`: `koreanName`/`koreanNameSource`, `columns` (`{column, koreanName, koreanNameSource, dataType, statementCount, crud}`), `columnCoverage` (`{statements, unread}`), `dictionary` (`{db, dbMessage, ddlFiles}`). **Korean-name priority is the user's: DB → DDL COMMENT → DDL plain comment → SQL comment → Java source → dictionary file** (`koreanNameSource` = `DB`/`DDL`/`DDL_NOTE`/`SQL`/`SOURCE`/`DICT`, `koreanNameWhere` = file:line / field / SQL count). (1) DB = target-DB table/column comments via JDBC metadata `REMARKS` (`dictionary.DbCommentReader`), **optional** — only when `dstone.knowledge.dictionary.db.{projectId}.{url,username,password(ENC),schema}` is set, read live per table when the detail opens (read-only, 10 s connect / 30 s read, 10 min cache, failures cached 1 min), never stored (comments belong to the running DB, not a revision); (2) DDL = `.sql`/`.ddl` files, now scanned as language `SQL` (`DDL` if they contain `CREATE TABLE`/`COMMENT ON`, else `SQL_SCRIPT`, unread) and read by `resource.DdlReader` in RESOURCE into `analysis_resource` `DDL_TABLE`/`DDL_COLUMN` (MySQL inline `COMMENT`, Oracle/PG `COMMENT ON`); (3) SQL = mapper comments, stored per table relation by `SqlTableExtractor` in SEMANTIC (`properties_json.columnComments`/`tableComment`; Hangul-only, owner only when certain, comments after `AS alias`, after `= 'literal'` (they explain the value) and on join conditions are skipped). DDL plain comments (`commentKind = NOTE`): a comment on the `CREATE TABLE` line or on the lines directly above it (no blank line) names the table, a comment at the end of a column line or on a comment-only line just above names that column; formal COMMENTs are applied first. (6) DICT (2026-10-24, last because such files may hold names guessed from abbreviations) = a project's own table list / column dictionary CSV, `dstone.knowledge.dictionary.file.{projectId}` (comma-separated, relative to the project's `localPath`), read live by `dictionary.DictionaryFileReader` (columns found by header name, re-read when the file changes, never stored) — HI-Japan: 231 tables → 58 SQL + 167 DICT + 6 none. SQL table comments are also recognised when `FROM` is on the previous line or the table follows a comma in the FROM list (`SqlTableExtractor.ClauseTracker` checks the clause per paren level), and schema-qualified tables are recognised too (36 → 58 on HI-Japan). Since 2026-10-25 every table name is stored **without its schema** (`common.util.TableName.bare`, used by `SqlTableExtractor.normalize()` and by the table-usage/impact/graph-node API inputs): `DPHJSDBA.JZ_EMP_INFO` and `JZ_EMP_INFO` are one table, matching DDL and dictionary files, which already dropped the schema; older revisions need `rerunFrom: SEMANTIC` to merge them. (5) SOURCE = `semantic.SourceNamePlugin` (950, after MyBatisPlugin) writes `analysis_resource` `SOURCE_TABLE_NAME`/`SOURCE_NAME`: JPA `@Table` types and their fields (`@Column(name)` or the field name, `via = ENTITY`) first, then any non-static field whose name matches a column of the revision (`mb_nm`/`mbNm` → `MB_NM`, `via = NAME`, table unknown → majority vote, shown with a dashed tag); text from `@ApiModelProperty`/`@Schema(description)`/`@Comment` (`@ApiModel` on types), else the comment after `;` on the declaration line, else a Javadoc/block comment directly above — a `//` line above is ignored (usually a group heading); field comments are not stored by DECLARE, so the plugin reads those lines from the source file. All comment text goes through `common.util.KoreanName.clean` (drops trailing types like `VARCHAR(20)`, requires Hangul). Columns used in SQL come from `SqlTableExtractor.ColumnFinder` (`properties_json.columns`, owner only when certain). Older revisions need `rerunFrom: SEMANTIC` (SQL columns/comments) or a new revision (DDL, since `.sql` files were not scanned before 2026-10-24). The screen shows 테이블명 (Korean name + source tag), 물리명, then a 컬럼명/컬럼한글명/타입/SQL table. A TYPE node's `methods` carry `title` and a METHOD node carries its own `title`/`titleNote` (기능명, 2026-10-26; the relation-tree popup shows it in its own box under the node name, above [이 노드를 가운데로 다시 그리기] — that placement is what the user asked for): the first comment line above the method before any `@` tag, else `@Description`, filtered by the pure `common.util.MethodTitle` (placeholders like `(Be sure to write a brief description)`, commented-out code, lone lowercase words are dropped; synthetic methods get none); it is **read live from the source file at detail time, only when the file's SHA-256 still equals `analysis_file.checksum`** (otherwise `methodTitleNote` says why), so old revisions need no rerun — HI-Japan: 82–83% of controller/service methods, 66% of DAO methods. Rules to keep: screen relations are followed **only on the first step** (`RENDERS` going up / `REQUESTS` going down only when the picked node is a JSP — following them mid-walk turns a call tree into page navigation and drags in the whole app); `MODEL`-layer methods are skipped unless `includeModel=true` and the MODEL chip is off by default on the screen (`BaseVO` alone has 245 incoming edges); the class-level highlight on the whole map over-approximates real call paths (A→B.x, B.y→C shows A→B→C), which is exactly why the tree popup exists. The relation-tree popup has its own tier chips (2026-10-25, client-side only): hidden tiers are dropped and re-laid out, paths through hidden nodes become one dotted bypass edge between visible nodes, the picked node always stays, and the hidden set persists across reopenings. A first chip, 화면호출관계 (`SCREEN_LINK`, off by default; 2026-10-27 as 호출화면, both directions since 2026-10-28), shows the screens linked by `INCLUDES` to a screen in the tree — callers one column left (walked up to the `up` depth), callees one column right (up to the `down` depth), starting only from screens already in the tree (walking back from an added screen would follow page navigation across the app); the screen always asks with `includeScreenLinks=true` and the server marks such added nodes `screenLink: CALLER|CALLEE`; `INCLUDES` edges are drawn only while it is on. A [전체 화면] button (same day) makes the same popup cover the viewport (`.kn-graph-modal.kn-full`, then `cy.resize()` + `fit`); Esc first leaves full screen, a second Esc closes the popup. Package collapsing (auto when > 250 nodes), the tier-column layout (화면 → 컨트롤러 → 서비스 → DAO → SQL 매퍼 → 테이블), layer filters and highlighting are all client-side; the server only supplies each node's `group`. `KnowledgeProxyService` raises WebClient's 256KB buffer to 32MB for this (the `anybiz_prd` map is ~1MB and came back as a 502 before).
