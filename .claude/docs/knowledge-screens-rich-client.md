# dstone-knowledge — WebSquare/Nexacro 화면, Query XML, 거래 ID 연결

> CLAUDE.md에서 분리한 상세 메모입니다. 원문 그대로 옮겼으며, 필요한 작업일 때만 읽습니다.

Rich-client screens (2026-10-07): the screen side used to be JSP-only; `semantic.RichClientPlugin` (510) + the pure, unit-tested `semantic.ScreenScript` now cover WebSquare and Nexacro / X-Platform. SCAN classifies them (`FileClassifier`: `WEBSQUARE` = root `<html>` carrying the `http://www.inswave.com/websquare` namespace, `NEXACRO` = `.xfdl` / root `<FDL>`, `NEXACRO_APP` = `.xadl`); their **language stays `XML`**, so anything that means "screen" must test `language = 'JSP' OR file_type IN ('WEBSQUARE','NEXACRO')` (`GraphDao.xml` `isScreen`) — the graph node kind is still called `JSP` (= screen) and `subType` tells which. Such screens are never rendered by the server, so there is no `RENDERS` and no DECLARE/RESOLVE; the only link is `REQUESTS`, found two ways: (1) path text equal to an endpoint path, like JSP (`via = PATH_TEXT`, MEDIUM; `svc::order/list.do` is stripped to `/order/list.do`; a path with a literal context path such as `/hi-japan/reporting.do` is retried without its first segment → LOW); (2) **call rules** for projects whose screens call the server by a transaction ID instead of a URL — `screens.calls` in a rule file (`conf/rules/hi-japan/frontend.yml`; formerly the `dstone.knowledge.semantic.screen.call-rules` key), e.g. `doRequestAjax=perform{id}` links `HiJS.svr.doRequestAjax("JCST0200M01S", …)` to the method named `performJCST0200M01S` (HI-Japan screens also call `comLib.gfnCallService("JIAC0000M02I", …)` — 85 literal calls in 37 screens, missed until 2026-10-25 — so the shipped value is `doRequestAjax=perform{id},gfnCallService=perform{id}`; a project with several common call functions needs one rule per function; rules sharing a template must not double the `TRANSACTION` endpoints — `insertCallRuleEndpoints` skips a method that already has one, after the first run with two rules gave 1,288 instead of 644) (`via = CALL_RULE`; one method of that name → HIGH, 2–5 → LOW each, none → an `UNRESOLVED` `REQUESTS` with the name in `to_external`; `properties_json.path` holds the ID). Same "computed, never guessed" rule as statement names: only a quoted first argument counts, a variable is merely counted, and anything inside `//`, `/* */` or `<!-- -->` is ignored. Screen → screen (`<w2:wframe src>`, popups, Nexacro `Div url`) is `INCLUDES`, resolved by "path ends with" after dropping a context path / `Base::` prefix / `?query`. Screens that post a form carrying the transaction ID in a hidden field (HI-Japan print buttons: `<input name='tranId' value='JIMC1000M03S'>` → `/reporting_ji.do`, `JZCI0102C` dispatches by `tranId`) are linked by **field rules** (2026-10-27): `dstone.knowledge.semantic.screen.field-rules: "tranId=perform{id}"` (field name=method template; `name` then `value` inside one tag, quoted literal value only; same linking as call rules, `properties_json.field` instead of `function`) — 31 literal fields on HI-Japan. Screens that open another screen by a screen ID instead of a path are linked by **open rules** (2026-10-27): `dstone.knowledge.semantic.screen.open-rules: "fnOpenPage={id}.xml"` (function=path template, parsed like call rules; only a quoted first argument, unique path-end match, no self-links, `via = OPEN_RULE`) — HI-Japan `parent.scwin.fnOpenPage("JIMC1000G")` → `JIMC1000G.xml`, 113 screen → screen links; needs `rerunFrom: SEMANTIC`. Screens that open a popup through a **common script function** (`comLib.gfnOpenPopupEmp(p)` → `js/wq/com_lib.js` body opens `/ui/jz/JZCO0102P.xml`) are linked too (2026-10-29): SCAN lists `.js`/`.xjs` as language/file type `SCRIPT` (content unread), `RichClientPlugin` reads all scripts before the screens, the pure `semantic.ScriptFunctions` finds definitions (`a.b = function` at any depth, bare `function x`/`var x = function` only at top level; functions on a prototype are renamed to how screens call them, `this.x` — `pForm.x = function` where `pForm` is a top-level `var pForm = <…>.prototype` alias, or `<…>.prototype.x = function`; aliases made inside a function (Nexacro's own library IIFEs) are ignored (2026-11-08, `hen`: `pForm.gfn_comnMultiComboLoad` vs `this.gfn_comnMultiComboLoad(…)` never matched before), body end by brace counting outside strings/comments/regex) and calls (written name must end with the dotted definition name; bare names match bare calls only), screens written in a body (path or open rule, comments excluded) are merged through calls to other common functions until stable, names defined twice are dropped, a screen defining the same name itself is skipped → `INCLUDES` `MEDIUM`, `via = COMMON_SCRIPT` (`function`, `script`); call-rule calls with a literal ID inside a common function body (`gfnOneResultSearchAgnt` → `doRequestAjax("JMAT0116M01L")`) and endpoint paths written in a body (kept only when they match an endpoint as is or without the first segment) become `REQUESTS` of every screen calling it (transaction calls `MEDIUM` even for a single method, paths `MEDIUM`/`LOW` like screen paths; line = the screen's call, `commonFunction`/`script` in properties; ID-forwarding wrappers are not counted). HI-Japan revision 56: 21 such functions, +154 screen links, +394 requests (all transaction calls — its scripts hold no endpoint paths); `websquare-app` revision 57 matches its README. Needs a **new revision** (`.js` was not scanned before), not `rerunFrom`; `js/xml2json.js` (Latin-1) leaves one SCAN `ENCODING` warning. `ScreenScript` marks comment ranges in **one pass** (`commentMask`) — looking backwards per match was quadratic and one 2.3MB screen made SEMANTIC take 93 s instead of 9 s. `DocumentPass` writes `VIEW` documents for these files inside its XML handler. Verified on the real WebSquare project `/app/HI-Japan/was` (outside the repo; 1,869 Java files, 317 screens, **zero** `<xf:submission>` — every call goes through `doRequestAjax`): 680 call-rule links + 2 unresolved = the 682 (screen, ID) pairs an independent grep finds, 34 path links all correct, 399 `INCLUDES`. `src/test/resources/samples/websquare-app` and `nexacro-app` carry expected values in their READMEs; **Nexacro and the standard WebSquare submission form have only been checked on those hand-made samples**. **Query XML** (same day): that project's SQL is not MyBatis/iBATIS but JEF-framework `<document><query|combo|delete id><statement>` files, so SCAN classifies them `QUERY_XML` and `MapperXmlReader.readQueryXml` stores them in `analysis_mapper` (`mapper_type = QUERY_XML`): **namespace = file name** (`OrderD.xml` → `"OrderD.selectOrderList"`), statement type from the first SQL word after leading comments (the wrapping tag is not the type), Velocity directives (`#if(…)`/`#elseif(…)`/`#else`/`#end`) stripped with paren/quote-aware scanning while every branch's SQL is kept — same policy as mapper condition tags. Java calls them through a holder object, `new QueryProperty("File.id")`, so `MyBatisPlugin` also reads `CREATE` references whose type is in `callArguments.constructors` in `conf/rules/hi-japan/backend.yml` (formerly the `MyBatisPlugin.NAME_HOLDERS` constant) (the creating method gets the `EXECUTES_SQL`). When one statement name exists in several files, **the one under the caller's source root wins** (`statementOf`): an exploded WAR carries the same SQL file in `WEB-INF/src` and, older, in `WEB-INF/classes` (55 files there, all different) — without that rule 474 calls pointed at the stale copy. Measured on HI-Japan: 2,128 statements, 1,642 `EXECUTES_SQL` + 27 unresolved = the 1,669 literal `QueryProperty` creations, 4,589 table relations over 232 tables (parser 1,943 statements / regex 183), and the chain screen → `perform…` → service → DAO → SQL → table now walks both ways (table `JC_OUTSTDNG` → 15 screens). **Layers and transaction endpoints** (same day): that project has no annotations and one-letter class suffixes (`…M`/`…S`/`…D`), so layers come from **configured supertypes**, not names — `semantic.ConfiguredLayerPlugin` (800, MEDIUM, direct `EXTENDS`/`IMPLEMENTS` only, external FQN or in-project fqn, never overrides an earlier layer) reads `layers.superTypes` in a rule file (`conf/rules/hi-japan/backend.yml`; formerly `dstone.knowledge.semantic.layer.super-types`) (shipped with the JEF rules: `AbstractMainService=CONTROLLER` because it is what receives the screen's request, `AbstractSubService=SERVICE`, `JdbcDAO`/`JdbcRowGetter=REPOSITORY`, `BusinessVO=MODEL`); unlayered top-level types went 1,233 → 24. `RichClientPlugin` also inserts an endpoint of the new type **`TRANSACTION`** (`path` = the ID) for every public non-static method matching a call rule's template — only for rules the project's screens actually use and only when the template has ≥3 fixed characters (`{id}` alone would match everything); 644 on HI-Japan, so table impact now reports endpoints (24 for `JC_OUTSTDNG`) and METHOD documents carry `진입점: 거래 ID …`. A new endpoint type or layer rule changes TYPE/METHOD document text, i.e. re-embeds those chunks. Port 4081 on this box may be the user's Windows-side instance sharing the same PostgreSQL — booting a second instance runs `AnalysisJobRecovery` (fails any running job) and a second `EmbeddingWorker`, so check for active jobs first and start test instances on another port with `-Ddstone.knowledge.rag.embedding.enabled=false` — and from a working directory other than `bin` (e.g. the scratchpad): `ApplicationPidFileWriter` writes `application.pid` in the current directory, so a test copy started from `bin` overwrites the real instance's PID file and `stopApp.sh`/`statusApp.sh` then act on the wrong process.
