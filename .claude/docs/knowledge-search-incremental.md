Search / impact / documents / Tool (M6, 2026-10-05):

- **Hybrid search** (`SearchService`): vector hits and name hits are fused by rank (`rag.HybridRanker`, Reciprocal Rank Fusion, k=60). `rag.SearchKeywords` picks only ASCII identifier-looking tokens from the query (≥3 chars, max 8; `a.b#c` split at `.`/`#`, anything containing `/` kept whole) — no Korean words, vector search covers meaning. Name score per token in `RagDao.xml` `searchChunksByKeyword`: 3 = whole word in the document title, 2 = in the title, 1 = in the content only; ties are ordered by vector similarity, which is what keeps a ubiquitous token like `SQL` harmless. A title-exact hit (score ≥ 3) counts double in the fusion so the method you named beats a merely similar one even when it has no embedding yet. Name search needs no vector: it works before embedding finishes and, when the embedding server is down, a query with names falls back to name-only with a `warning` (no names → 503). Request adds `mode` (`HYBRID`/`VECTOR`/`KEYWORD`). **One search reads one side** (2026-11-14, `sourceTypes` removed from the API and the boot screen): `projectId`/`revisionId` present → code of that revision (`docTypes`, `layer` allowed); both absent → the caller's uploaded documents (`collections`, `documentIds` allowed); mixing the two kinds of filter is a 400. Hits carry `documentId`, `collection`, `chunkNo`, `headingPath`. **Vector hits below a minimum similarity are dropped before fusion** (2026-11-12): `dstone.knowledge.rag.search.min-score.code` 0.5 / `.document` 0.35 (`RagSettings`), overridden by request `minScore` (0 = off); name hits are never filtered. Filtering is done in Java after `searchChunks`, not in SQL, so the HNSW iterative scan does not walk the whole index for an off-topic query. Response carries `source` (`CODE`/`DOCUMENT`), `minScore` (the one threshold used), `belowMinScore`, `bestBelowMinScore`; the boot screen shows "질문과 가까운 내용이 없습니다" from them. bge-m3 measurement on code chunks: off-topic queries top-1 0.34–0.47, on-topic top-1 0.51–0.72 (table in docs/11 §4.3) — re-measure when the embedding model changes. The name query scans the revision's chunks with `strpos` (0.17 s on ~10k chunks) — add a `pg_trgm` index before chunk counts reach hundreds of thousands. **Search must not queue behind the background embedding** (2026-10-06): Ollama serves one request at a time, so the 0.1 s query embedding waited for the worker's in-flight batch — with 3,500-char chunks on this CPU-only box (no usable GPU: AMD Radeon 780M, `size_vram: 0`) a batch of 16 took 66.8 s (4 → 16.5 s, i.e. ~4 s per chunk, batching gains nothing on CPU), searches took 59–100 s while 2,400 chunks were pending, and `dstone-ai-engine`'s old automatic RAG hit its 60 s timeout and failed a `pilot-workflow` run. Two rules keep it at 1–2 s under the same backlog: `rag.EmbeddingGate` (`SearchService` marks `searchStarted()/searchFinished()` around the query embedding; `EmbeddingWorker` calls `awaitOpen()` before every batch and stays out for 1.5 s after a search) and `dstone.knowledge.rag.embedding.batch-size: 1` (raise to 8–32 only on a GPU server). Any new code that calls `EmbeddingModel` for an interactive request must go through the gate the same way. Queue-wide progress is `GET /api/system/embedding` (`EmbeddingStatusService`: totals, recent speed, `etaSeconds`, worker state, pending per project) shown as the "임베딩 현황" panel at the top of `knowledge/index` (`knowledge/assets/js/embedding.js`, refreshed every 10 s); the ETA is computed from **characters, not item counts** (embedding time is proportional to length: 500 chars ≈ 0.6 s, 3,500 chars ≈ 4 s) over the last 10 minutes. While a module runs from `target/*.jar|war`, do not rebuild it in place (`mvn clean package` replaces the file under the running JVM and can crash it on the next class load) — copy the artifact elsewhere and run the copy on another port for tests.
- **Impact analysis** (`ImpactService`, `GET /api/revisions/{id}/impact?table=|statement=|type=|methodId=`): one recursive CTE (`RelationDao.xml` `impactWalk`) starts from the methods that touch the target (depth 0) and walks up `CALLS`/`CALLS_POSSIBLE_IMPLEMENTATION`/`REQUESTS` (depth ≤ 10), carrying the weakest confidence along the path (best path wins per node); three queries reuse it for methods, endpoints and screens (`via` = `REQUESTS`/`CALLS`/`RENDERS`). An endpoint linked to a type only (Struts `DispatchAction`) is included as `LOW`, `matchedBy = TYPE`. `INCLUDES` is deliberately not followed (a shared header would drag in every page). It only follows stored relations — SQL written as Java strings (raw JDBC, e.g. `legacy-app`) has no table relation, so a table target finds nothing there.
- **General documents** (`UploadDocumentService`, `/api/documents`, multipart `file`, `sourceId`, `title`, `collection`): redesigned 2026-11-14 for Nexacro/WebSquare development guides (samples in `docs/temp/nexacro`, `docs/temp/websquare`, outside git).
  - **Collection, not project.** `rag_document.project_id` was dropped (`ALTER TABLE … DROP COLUMN IF EXISTS` in `02-create-table…sql`; code documents find their project through `revision_id` → `analysis_revision`, e.g. the "pending per project" query). An upload carries an optional `collection` (≤100 chars, no comma because Tools pass comma lists) instead. `GET /api/documents?collection=`, `GET /api/documents/collections` (counts per collection), `GET /api/documents/chunks?sourceId=&from=&to=` (≤10 chunks, for reading neighbours of a hit).
  - **Extraction** (`rag.DocumentTextExtractor`): Tika's XHTML is read by a SAX handler into `rag.DocumentBlock`s — `h1`–`h6` = heading (Word "제목 n" styles arrive this way), `p`/`li`/… = text, `tr` = one row (cells joined ` | `), `div.page` = PDF page number; embedded files are not parsed (`SkipEmbedded` — a 68 MB guide DOCX had 1,269 `div.package-entry` image names as `h1`), PDF OCR is off explicitly (`PDFParserConfig` `NO_OCR`; with embedded parsing skipped Tika's AUTO OCR threw an NPE on image-only pages), Tika's bookmark list after the pages is ignored. For a PDF, `rag.PdfOutline` reads the bookmarks with PDFBox (path + 1-based start page; cycles and >20,000 items guarded). The char cap throws `WriteLimitReachedException` and keeps what was read (`truncated`).
  - **Chunking** (`rag.DocumentChunker`, pure, `DocumentChunkerTest`): 0) drop TOC lines (dot leaders or tab + page number incl. `1,023`/`#`), PDF TOC pages (≥50% of lines are bookmark titles or TOC lines) and PDF running headers/footers (first/last 2 lines of a page, digits normalised, on ≥5 pages and ≥50% of the pages between first and last occurrence — catches per-chapter "Chapter | 15" footers); 1) sections — by heading level for Word/HTML, by bookmark for PDF (switch at the line equal to the bookmark title on its start page, else at the page start); 2) pack paragraphs up to `rag.upload.chunk-max-chars` (1,000, separate from code's 1,800), short sections join their neighbours only under the same top-level heading (the common path becomes the chunk path, deeper headings stay as a line in the body), a long section splits with a short last paragraph repeated as overlap (`upload.overlap-chars`), table rows are packed together, PDF paragraphs are joined by one newline. `.jsonl` stays one line per chunk (`rag.TextChunker`, moved here from `analysis.pass09.document`).
  - **Chunk content** starts with `[문서] title (i/n)` and `[위치] heading path (p.a-b)`; `rag_chunk.metadata_json` holds `headingPath`, `pageStart`, `pageEnd`; the document's `metadata_json.structure` is `HEADING`/`BOOKMARK`/`NONE`/`LINE`. Measured on the seven sample guides (2026-11-14, extractor + chunker only): 35–833 chunks each, average 828–974 chars, every PDF chunk has a heading path, the WebSquare DOCX (792k chars) parses in ~7 s.
  - Unchanged: `rag_document` `source_type=DOCUMENT`, `doc_type=UPLOAD`, `document_id` = `sourceId`, no revision; embedding `priority` 10 (code is 0); same `(tenant, sourceId)` replaces in one transaction; no extractable text → 400 and the old document stays. Tika needs the `commons-io` 2.20.0 override in this module's pom. Tika 3.3.1's PDF parser needs **PDFBox 3.0.x** — `dstone-common` pins `pdfbox` 3.0.7 (was 2.0.27 until 2026-11-14, which made every PDF upload die with `NoSuchFieldError`); bump both together, and `dstone-boot` excludes tess4j's `pdfbox-tools`/`pdfbox-debugger` 2.0.26. Parser `RuntimeException`/`LinkageError`/`StackOverflowError` become `TikaException` (→ 400). Tenant = caller from the API key; with auth off the tenant is null and such documents are shared. Upload size: `spring.servlet.multipart.max-file-size` 100MB here, `resources.fileUp.max-post-size` 105MB in `dstone-boot` (`FileUpUtil`, default still 15MB for other apps).
- **`rerunFrom`** on `POST /api/projects/{id}/analyses` (`{revisionLabel, rerunFrom: "DOCUMENT"}`) resets that pass and every later one (`analysis_revision_pass` + `analysis_file_pass` rows) on an existing revision — use it after changing document or semantic rules instead of editing pass rows by hand.
- `dstone-ai-engine` reads this module only through `KnowledgeTool` (code Tools + `knowledgeListDocs`/`knowledgeSearchDocs`/`knowledgeGetChunks`; its automatic RAG advisor was removed 2026-11-14). `dstone-ai-engine/k8s/configmap.yaml` is an old minimal `application.yml` — it carries no datasource and no Tool settings, so `spring.datasource`, `dstone.ai.tool.knowledge` and `KNOWLEDGE_HOST` must be added there before the Pod can use workflow history or the Tool (everything was verified with a local `bin/startApp.sh` process only).
- Verified live 2026-10-05: `sample-knowledge-agent` answered a table-impact question with a single `knowledgeImpact` call and a "where is order cancel handled" question by chaining search → table usage → callees, flagging the `LOW` endpoint and the missing JDBC table link itself.

Incremental analysis / revision diff / retention (M7, 2026-10-05):

- **A revision is still a full snapshot.** `{incremental: true}` (optional `baseRevisionId`, default = latest `READY` revision; stored in `analysis_revision.parent_revision_id`) only shortens how it is built: results of unchanged files are **copied** from the base revision, so a base revision can be deleted later without hurting its children. Falls back to a full run (response `incremental: false` + `note`) when there is no `READY` base or the base's `analyzer_version` differs.
- `CarryPass` (CARRY): same file = same path + `checksum` + SCAN classification (language, file type, module, encoding) → `analysis_file.carried_from_file_id`. For files whose base DECLARE/RESOURCE status was `DONE` it copies the per-file rows (symbol/method/field/annotation/reference, mapper/config/resource) and inserts `analysis_file_pass` rows with `carried = true`, which is what makes DECLARE/RESOURCE skip them. Base `FAILED`/`SKIPPED` files are simply reprocessed.
- `CarryResolvePass` (CARRY_RESOLVE) runs after DECLARE because resolved relations depend on other files. An unchanged file is re-resolved (not carried) when (1) any of its base relations points to a declaration in a changed/removed file, or (2) one of its base references with status `EXTERNAL`/`HEURISTIC`/`UNRESOLVED` has the name of a declaration in a new/changed file. Everything else gets its RESOLVE relations copied. It deliberately errs towards re-resolving. LINK/SEMANTIC/DOCUMENT always rebuild the whole revision (their relation types are excluded from the copy).
- The copy SQL reads column names from `information_schema` (`CarryDao.copyRows`) so a newly added column cannot be silently dropped; table names come from Java constants only. **`ANALYZE` after the bulk copy is required** — without it the planner picked a bad plan and LINK took 123 s instead of ~1 s.
- **The check that must keep passing when any pass changes:** analyze the same source once incrementally and once fully in the same project and compare every `analysis_*` table plus chunk hashes with ids replaced by paths/names — 0 differing rows on all 13 tables in two rounds on a copy of `anybiz_prd` (rename a DAO method, delete a widely used VO, add a class, edit JSP/mapper, then revert; second round based on an incremental revision). Timings there: 215 s full → 80–102 s incremental (RESOLVE 131 s → 2.5–27 s); SEMANTIC (~35 s, mostly SQL parsing) and DOCUMENT (~30 s) are what is left.
- Not detected: changed target jars (run a full analysis). Not verified: multi-module projects, tens of thousands of files.
- **Revision diff** (`DiffService`, `GET /api/revisions/{id}/diff?base=&kinds=&limit=`): `FILE`/`TYPE`/`METHOD`/`ENDPOINT`/`STATEMENT`/`TABLE_USE`/`CALL` via one FULL JOIN pattern per kind in `DiffDao.xml`; symbol/method ids are revision-independent so they are the keys, files and statements are keyed by path/name. The statement key includes "is a fragment" because real mappers reuse one id for a `<select>` and a `<sql>`. Body-only method changes show up as `FILE` `CHANGED` only (no body hash is stored). Same project only.
- **Retention** (`RetentionService`): after every successful job, keep the newest `dstone.knowledge.retention.max-revisions` (5; 0 = keep all) `READY` revisions per project, never deleting a revision with an active job or one that a running incremental job is based on; unfinished (failed/cancelled) revisions are left alone. Embeddings no chunk refers to are deleted once older than `retention.orphan-embedding-days` (30). Manual: `POST /api/projects/{id}/retention?keep=`.
