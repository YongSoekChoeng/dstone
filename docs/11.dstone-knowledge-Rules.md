# dstone-knowledge 규칙 파일 (conf/rules)

`dstone-knowledge`는 Java 소스를 분석해서 "이 메소드는 `/order/list` 주소를 처리한다", "이 클래스는 서비스다", "이 호출은 `Order.list` SQL을 실행한다" 같은 사실을 알아낸다. 그런데 이런 사실은 **언어가 정한 것이 아니라 프레임워크가 정한 관례**다. `@GetMapping`이 주소라는 것은 Spring의 약속이고, `new QueryProperty("OrderD.selectOrderList")`가 SQL 이름이라는 것은 어느 회사의 자체 프레임워크 약속이다.

이런 관례를 Java 코드에 박아 두면 새 프로젝트를 만날 때마다 분석기를 고쳐야 한다. 그래서 관례는 **규칙 파일**(`dstone-knowledge/conf/rules/*.yml`)에 적고, 분석기는 그 파일을 읽어 그대로 따른다. **새 프로젝트의 낯선 관례는 Java를 고치지 않고 규칙 파일을 더해서 해결한다.** 이 문서는 그 규칙 파일이 무엇이고, 백엔드가 그것을 어떻게 읽어서 결과로 만드는지를 처음부터 끝까지 설명한다.

> 기준: 2026-11-09 `main`, 분석기 1.2. 규칙 파일 작성법의 요약본은 `conf/rules/README.md`, 전체 분석 흐름은 [11.dstone-knowledge-분석프로세스(상세).md](11.dstone-knowledge-분석프로세스(상세).md), 결과 테이블은 [11.dstone-knowledge.md](11.dstone-knowledge.md) 5장에 있다.

## 1. 한눈에 보기

```text
 conf/rules/                                    ┌───────────────────────────── 서버 ─────────────────────────────┐
 ├─ java.yml        (order 100)                 │                                                                 │
 ├─ servlet.yml     (order 150)                 │ ① 서버가 뜰 때            SemanticRuleRegistry.check()           │
 ├─ spring.yml      (order 200)   ── 읽기 ──▶   │    모든 파일 검사. 틀리면 서버가 뜨지 않는다                      │
 ├─ jpa.yml         (order 250)                 │                                                                 │
 ├─ mybatis.yml     (order 300)                 │ ② 프로젝트 등록할 때      ruleSets 에 적은 묶음이 있는지 검사    │
 ├─ fallback.yml    (order 900)                 │                                                                 │
 └─ hi-japan/                                   │ ③ 분석의 SEMANTIC 단계    파일을 다시 읽고 → 이 프로젝트에 쓸    │
    ├─ backend.yml  (order 500)                 │    시작할 때              묶음을 고르고 → 하나로 합쳐(SemanticRules)│
    └─ frontend.yml (order 500)                 │                           → 플러그인 17개가 차례로 꺼내 쓴다     │
                                                │                                                                 │
                                                │ ④ 결과                    analysis_endpoint / analysis_symbol.layer│
                                                │                           / analysis_relation / analysis_mapper    │
                                                │                           + 쓴 묶음 기록(analysis_resource RULE_SET)│
                                                └─────────────────────────────────────────────────────────────────┘
```

- 규칙 파일 하나 = **규칙 묶음** 하나. 파일 안의 키(`endpoints`, `layers`, `callArguments` …)가 각각 다른 플러그인에게 일을 시킨다.
- 규칙은 **SEMANTIC 단계에서만** 쓴다. SCAN · DECLARE · RESOLVE는 규칙과 상관없다. 그래서 규칙을 고친 뒤에는 SEMANTIC부터만 다시 돌리면 된다(`rerunFrom: "SEMANTIC"`). 서버를 다시 띄울 필요도 없다. 분석할 때마다 파일을 다시 읽기 때문이다.
- 규칙이 하는 일은 결국 다섯 가지다.

  | 규칙 키 | 하는 일 | 결과가 들어가는 곳 |
  |---|---|---|
  | `endpoints` | 이 메소드는 **진입점**이다(주소, 스케줄, 리스너, 스레드, 거래 ID) | `analysis_endpoint` |
  | `layers` | 이 클래스는 **어느 계층**이다(CONTROLLER, SERVICE …) | `analysis_symbol.layer` |
  | `injects`, `proxies` | 이 필드는 **주입**받는다 / 이 메소드에는 **프록시**가 끼어든다 | `analysis_relation`(INJECTS), `analysis_method.proxy_related` |
  | `callArguments`, `jpa` | 이 호출(또는 애노테이션)은 **이 SQL을 실행**한다 / **이 화면을 보여 준다** | `analysis_relation`(EXECUTES_SQL, RENDERS), `analysis_mapper` |
  | `screens` | 이 화면은 **이 서버 메소드를 부른다** / **이 화면을 연다** / 이름은 이것이다 | `analysis_relation`(REQUESTS, INCLUDES), `analysis_resource`(SCREEN_NAME) |

## 2. 왜 규칙 파일인가: 코드에 남은 것과 파일로 뺀 것

| 구분 | 어디에 | 예 |
|---|---|---|
| **언어 · 표준 형식 자체의 규칙** | Java 코드 | `public static void main` 진입점, JSP 파일, `web.xml`, `struts-config.xml`, MyBatis 매퍼 인터페이스 방식(namespace = 인터페이스 이름), 호출 해석(RESOLVE), SQL 파싱, Java 문자열 SQL, 주소 상수 계산, 상위 클래스 주소 상속 |
| **프레임워크 · 회사마다 다른 관례** | 규칙 파일 | `@GetMapping`은 주소, `@Service`는 서비스, `sqlSession.selectList("x")`의 첫 인자는 SQL 이름, `AbstractMainService`를 상속하면 컨트롤러, 화면의 `doRequestAjax("거래ID")`는 서버 호출 |

경계는 간단하다. "Java라면 누구나 같은 것"은 코드에, "이 프레임워크를 쓰면 이렇다"는 파일에 둔다. Spring처럼 흔한 프레임워크의 관례도 파일(`spring.yml`)에 있다. 그래서 Spring을 쓰지 않는 프로젝트에서는 그 규칙이 맞는 코드가 없어 아무 일도 하지 않는다.

이름(SQL 이름, 화면 경로, 거래 ID)은 **계산할 수 있을 때만 잇고 짐작하지 않는다.** 규칙이 "이 메소드의 첫 인자가 SQL 이름"이라고 알려 줘도, 그 인자가 따옴표 글자나 상수로 계산되지 않으면 잇지 않는다. 짐작으로 이은 선은 영향도 분석을 틀리게 만들기 때문이다.

## 3. 폴더와 묶음

### 3.1 지금 들어 있는 묶음

| 파일 | 묶음 이름 | order | 누구에게 | 내용 |
|---|---|---|---|---|
| `java.yml` | `java` | 100 | 모든 프로젝트 | `Runnable`/`Thread`/`TimerTask`의 `run()`, `Callable`의 `call()` → THREAD 진입점 |
| `servlet.yml` | `servlet` | 150 | 모든 프로젝트 | `HttpServlet`·`GenericServlet` 상속 → CONTROLLER, `Filter` → WEB_FILTER |
| `spring.yml` | `spring` | 200 | 모든 프로젝트 | `@RequestMapping` 계열 HTTP 진입점, `@Scheduled`, 메시지 리스너, `@Autowired` 주입, `@Transactional` 등 프록시, 스테레오타입 계층, `ModelAndView` 화면 |
| `jpa.yml` | `jpa` | 250 | 모든 프로젝트 | JPA 엔티티 → 테이블, `@Query`·`@NamedQuery`, Spring Data 저장소 메소드, `createQuery`·`createNamedQuery` |
| `mybatis.yml` | `mybatis` | 300 | 모든 프로젝트 | SQL 이름을 첫 인자로 받는 `SqlSession`/`SqlMapClient` 메소드 |
| `hi-japan/backend.yml` | `hi-japan/backend` | 500 | 프로젝트 `HI-Japan`(+ 빌려 쓰는 프로젝트) | JEF 프레임워크의 상위 타입 계층, `new QueryProperty("…")` SQL 이름 |
| `hi-japan/frontend.yml` | `hi-japan/frontend` | 500 | 프로젝트 `HI-Japan`(+ 빌려 쓰는 프로젝트) | WebSquare 화면의 거래 ID 호출 함수, 출력 폼 필드, 화면 열기 함수, 메뉴 목록 |
| `fallback.yml` | `fallback` | 900 | 모든 프로젝트 | `@Component` 계층, 클래스 이름 끝말로 짐작하는 계층(LOW) |

### 3.2 묶음 이름

**묶음 이름 = 규칙 폴더 안의 경로에서 확장자를 뺀 것**이다. `spring.yml` → `spring`, `hi-japan/frontend.yml` → `hi-japan/frontend`. 파일 안에 `name:`을 적으면 이 경로와 같아야 한다(다르면 검사에서 걸린다). 프로젝트 설정의 `ruleSets`에 적는 이름이라 헷갈리지 않게 하려는 것이다.

- 확장자는 `.yml`, `.yaml` 둘 다 읽는다. 같은 이름이 둘 다 있으면 오류다.
- 하위 폴더는 3단계까지 읽는다. 마디는 영문자·숫자·`-`·`_`·`.`로 60자 이내다.
- `README.md`처럼 YAML이 아닌 파일은 건너뛴다. `.`으로 시작하는 폴더도 건너뛴다.

### 3.3 이 프로젝트에 어떤 묶음을 쓰나

분석할 때 서버는 묶음마다 아래 세 가지를 차례로 물어서 **하나라도 맞으면** 쓴다(`SemanticRuleRegistry.rulesFor`).

```text
                         묶음 하나
                            │
          ┌─────────────────┼──────────────────────┐
          ▼                 ▼                      ▼
  ① autoApply 가 true?   ② 프로젝트 폴더의 것?     ③ 프로젝트 ruleSets 에 적었나?
     (바로 아래 묶음의     (묶음 이름의 첫 마디 =     (묶음 이름 그대로, 또는
      기본값)               프로젝트 ID, 대소문자 무시)  그 묶음이 든 폴더 이름)
          │                 │                      │
          └──── 하나라도 예 ────┴──────────────────────┘
                            ▼
                       이 프로젝트에 쓴다
```

| 경우 | 예 | 쓰는가 |
|---|---|---|
| 바로 아래 묶음 | `spring` | 모든 프로젝트에 쓴다(`autoApply` 기본 `true`) |
| 프로젝트 폴더 | `hi-japan/backend`, 프로젝트 ID `HI-Japan` | 쓴다. `ruleSets`에 적지 않아도 된다 |
| 남의 프로젝트 폴더 | `hi-japan/backend`, 프로젝트 ID `hen` | 쓰지 않는다(하위 폴더의 `autoApply` 기본 `false`). A 프로젝트의 규칙이 B 분석에 끼어들지 않게 하려는 것이다 |
| 빌려 쓰기 | 프로젝트 `HI-Japan-batch`의 `ruleSets: hi-japan` | `hi-japan/` 아래 묶음을 모두 쓴다. 같은 프레임워크를 쓰는 배치 프로젝트나 표본(`websquare-app`)이 이렇게 한다 |
| 일부러 모두에게 | 하위 폴더 묶음에 `autoApply: true` | 모든 프로젝트에 쓴다 |
| 일부러 빼기 | 바로 아래 묶음에 `autoApply: false` | `ruleSets`에 적은 프로젝트에만 쓴다 |

`ruleSets`는 프로젝트를 등록하거나 고칠 때 적는다. 쉼표나 공백으로 여러 개를 잇는다.

```json
POST /api/projects
{ "projectId": "HI-Japan-batch", "localPath": "/app/HI-Japan/batch", "ruleSets": "hi-japan" }
```

등록할 때 서버가 그 이름의 묶음(또는 폴더)이 있는지 먼저 본다(`ProjectService` → `SemanticRuleRegistry.checkRuleSetNames`). 없으면 등록을 거절하고 "있는 묶음" 목록을 알려 준다.

### 3.4 순서(order)가 왜 중요한가

고른 묶음은 `order`가 작은 것부터, 같으면 이름 순으로 늘어놓는다(`order`를 적지 않으면 500). 시험 중인 묶음도 이 순서 안에 끼어든다.

순서가 결과를 바꾸는 곳은 **계층**이다. 계층은 "먼저 정한 것을 뒤에서 바꾸지 않는다". SQL로 보면 모든 계층 UPDATE에 `AND layer IS NULL`이 붙어 있다(`SemanticDao.xml`의 `updateLayerBy…`). 그래서 `@Component`처럼 뜻이 넓은 규칙은 `fallback.yml`에 두고 `order: 900`으로 맨 뒤에 돌린다. 앞에서 `@Service`나 `@Controller`로 이미 정해진 클래스는 건드리지 않고, 아무 것도 정해지지 않은 클래스에만 COMPONENT를 붙이게 하려는 것이다.

## 4. 백엔드는 규칙을 어떻게 읽고 쓰나

### 4.1 규칙 폴더의 위치

`SemanticRuleRegistry.rulesDir()`가 정한다.

1. `application.yml`의 `dstone.knowledge.semantic.rules-dir`에 값이 있으면 그 폴더
2. 없으면 시스템 속성 `APP_CONF_DIR` 아래 `rules` (보통 `/app/dstone/dstone-knowledge/conf/rules`)
3. `APP_CONF_DIR`도 없으면 작업 폴더의 `conf/rules`

폴더가 없으면 서버가 뜨지 않는다. 기본 규칙(java, spring, mybatis …)도 이 폴더에 있어서, 폴더가 없으면 진입점과 계층을 하나도 찾지 못하기 때문이다.

### 4.2 서버가 뜰 때: 전체 검사

`SemanticRuleRegistry`는 Spring bean이고, `@PostConstruct check()`가 폴더 전체를 한 번 읽는다. 로그에 이렇게 남는다.

```text
의미 분석 규칙 8묶음을 읽었습니다(/app/dstone/dstone-knowledge/conf/rules): java(2), servlet(2), spring(12), jpa(7), mybatis(1), hi-japan/backend(6), hi-japan/frontend(5), fallback(10)
```

괄호 안의 숫자는 그 묶음의 규칙 수(`RuleSet.ruleCount()`)다. 파일 하나라도 잘못 적혀 있으면 `IllegalStateException`으로 **서버가 뜨지 않고**, 메시지가 어느 파일의 어느 자리인지 알려 준다. 틀린 규칙을 모른 채 분석하면 결과가 조용히 비어 버리기 때문에, 일부러 크게 실패하게 했다.

### 4.3 파일 하나를 읽는 법: RuleSetParser

`RuleSetParser.parse(text, fileName)`가 YAML 하나를 `RuleSet` 객체 하나로 바꾼다.

1. SnakeYAML의 `SafeConstructor`로 읽는다(임의의 Java 객체를 만들지 않는다).
2. 맨 위 키는 `name`, `description`, `order`, `autoApply`, `endpoints`, `injects`, `proxies`, `layers`, `callArguments`, `screens`, `jpa`만 허락한다. **모르는 키는 오타로 보고 오류**다. 각 키 아래도 마찬가지로 허락된 키 목록이 있다.
3. 값도 검사한다.

   | 무엇 | 검사 |
   |---|---|
   | 계층 | `CONTROLLER, SERVICE, REPOSITORY, MODEL, VIEW, CONFIG, WEB_FILTER, UTIL, EXCEPTION, BATCH, COMPONENT, ASPECT` 중 하나 |
   | 진입점 종류 | 영문 대문자로 시작, 대문자·숫자·`_`로 2~20자. 새 이름(예: `BATCH_JOB`)도 된다 |
   | 애노테이션 | `@` 없는 단순 이름(Java 식별자) |
   | 상위 타입, `receiverTypes` | 점으로 이은 전체 이름 |
   | HTTP 메소드 | 대문자 3~10자 |
   | 정규식 | 실제로 컴파일해 본다. `idReplace`의 `$1`이 정규식 그룹 수를 넘으면 오류 |
   | `argIndex` | 0~9 |
   | `idMap` 대응표 | 규칙 폴더 안에 있어야 한다(밖을 가리키면 오류) |

4. 목록 자리에 값 하나만 적어도 된다(`annotations: Service`).
5. **해시**를 만든다. 파일 내용의 SHA-256 앞 12자다. 화면 규칙이 대응표(`idMap`)를 쓰면 대응표 내용도 해시에 넣는다. 그래서 대응표만 고쳐도 "규칙이 바뀌었다"를 알 수 있다.

### 4.4 분석할 때: 다시 읽고, 고르고, 합친다

SEMANTIC 단계(`SemanticPass.run`)가 시작되면 이렇게 흘러간다.

```text
SemanticPass.run(context)
  │
  ├─ ruleRegistry.rulesFor({projectId, ruleSets})
  │     ├─ loadAll()            폴더를 다시 읽는다(고친 파일이 바로 반영되는 이유)
  │     ├─ ruleSets 이름 확인    없는 묶음이면 RuleException → 분석 실패
  │     ├─ 3.3절 기준으로 고르기
  │     ├─ order, 이름 순 정렬
  │     ├─ 옛 설정 키가 있으면 application-yml 묶음을 맨 뒤에(8절)
  │     └─ new SemanticRules(chosen)   ← 묶음들을 하나로 합친다
  │
  ├─ context.setSemanticRules(rules)  ← 플러그인들이 여기서 꺼내 쓴다
  │
  └─ 한 트랜잭션 안에서 runPlugins(context)
        ├─ semanticDao.clear(revisionId)   전에 만든 SEMANTIC 결과를 지운다(다시 돌려도 결과가 같다)
        ├─ recordRuleSets()                쓴 묶음을 analysis_resource 에 RULE_SET 행으로 남긴다
        └─ 플러그인을 order 순으로 하나씩 run()
```

여기서 규칙 파일이 틀려 있으면(서버가 뜬 뒤에 고쳤는데 잘못 고친 경우) 그 분석만 실패하고 서버는 그대로 돈다. 트랜잭션 하나로 돌기 때문에 도중에 실패해도 지운 것까지 되돌아간다.

**합치는 방법(`SemanticRules` 생성자)**

- 대부분의 규칙은 묶음 순서대로 목록에 이어 붙인다. 애노테이션 이름 같은 집합은 중복을 없앤다.
- **같은 HTTP 애노테이션이 두 묶음에 있으면 오류**다. 예를 들어 `GetMapping`을 `spring`과 내 묶음에 둘 다 적으면 같은 주소가 진입점으로 두 번 생기기 때문이다. 진입점 애노테이션(`endpoints.annotations`)도 `종류/애노테이션` 단위로 같은 검사를 한다.
- 화면 규칙은 같은 함수·틀·자리·다듬기가 겹치면 하나만 남긴다. 화면 호출 규칙(`calls`) 뒤에 폼 필드 규칙(`fields`)을 붙인다.
- `jpa.naming`은 먼저 오는(order가 작은) 묶음의 것을 쓴다. 아무도 적지 않으면 `SNAKE_CASE`.

### 4.5 누가 어떤 규칙을 꺼내 쓰나: SEMANTIC 플러그인

`SemanticPlugin` 구현 bean 17개가 `order()` 순으로 돈다. 규칙을 쓰는 것은 그중 11개다.

| order | 플러그인 | 꺼내 쓰는 규칙 | 만드는 것 |
|---|---|---|---|
| 100 | `SpringPlugin` (+`HttpEndpointBuilder`) | `endpoints.http`, `endpoints.annotations`, `injects`, `proxies`, `layers.annotations` | HTTP·스케줄·리스너 진입점, 애노테이션 계층(HIGH), INJECTS 관계, `proxy_related` |
| 200 | `ServletPlugin` | (코드) | web.xml·`@WebServlet` 진입점 |
| 250 | `StrutsPlugin` | (코드) | `struts-config.xml` 액션 진입점 |
| 260 | `XmlEndpointPlugin` | `endpoints.xml` | 자체 설정 XML의 진입점(거래 ID 등) |
| 300 | `PlainJavaPlugin` | `endpoints.superTypes` | `main()`(코드), 상위 타입으로 정한 진입점(THREAD 등) |
| 390 | `JpaPlugin` | `jpa.*` | JPA statement(`analysis_mapper`, `mapper_type = JPA`)와 EXECUTES_SQL, 테이블 관계 |

- `JpaPlugin`(390)이 `@NamedQuery`를 statement로 먼저 만들어야 `MyBatisPlugin`(400)이 `em.createNamedQuery("Order.findAll")`을 그 statement에 이을 수 있다(`jpa.yml`의 `callArguments`).

플러그인은 **Java를 다시 파싱하지 않는다.** DECLARE가 넣어 둔 `analysis_annotation`, `analysis_reference`(호출 이름, `arg_text`, `args_json`)와 RESOLVE가 만든 `analysis_relation`을 규칙의 값으로 SQL을 만들어 엮는다. 그래서 큰 프로젝트에서도 SEMANTIC은 금방 끝난다.

## 5. 규칙 키 하나하나

각 키마다 **무엇을 적는지 → 소스에서 무엇을 찾는지 → DB에 무엇이 생기는지** 순서로 적는다.

### 5.1 endpoints: 진입점

진입점은 "밖에서 이 프로그램으로 들어오는 입구"다. 호출 그래프에서 아무도 부르지 않는 메소드라도 진입점이면 죽은 코드가 아니다. 영향도 분석은 진입점에서 출발한다.

#### endpoints.http: 클래스 주소 + 메소드 주소

```yaml
endpoints:
  http:
    - classAnnotations: [RequestMapping]          # 클래스에 붙은 주소 애노테이션
      pathAttributes: [value, path]               # 주소가 적힌 속성. 앞에 있는 것부터 본다
      methodAnnotations:
        - { annotation: RequestMapping, methodAttribute: method }   # HTTP 메소드를 속성에서 읽는다. 없으면 ALL
        - { annotation: GetMapping, httpMethod: GET }               # HTTP 메소드가 정해져 있다
```

```java
@RequestMapping("/order")
public class OrderController {
    @GetMapping("/list")        public String list() { … }
    @RequestMapping(value = "/save", method = RequestMethod.POST) public String save() { … }
}
```

→ `analysis_endpoint`에 두 행: `HTTP GET /order/list`, `HTTP POST /order/save`. `properties_json.annotation`에 근거 애노테이션이 남는다.

코드가 덧붙여 하는 일(규칙 없이):
- 주소가 상수면 따라가 계산한다. `@GetMapping(Urls.ORDER + "/list")`. 계산하지 못하면 진입점은 만들되 `properties_json.unresolvedPath`에 원문을 남긴다.
- 클래스에 주소가 없으면 인터페이스, 그다음 상위 클래스의 클래스 주소를 쓴다. 상위 클래스에 있는 핸들러 메소드는 그것을 물려받은 실제 컨트롤러의 진입점이 되고 `properties_json.inheritedFrom`이 붙는다.

#### endpoints.annotations: 애노테이션이 붙은 메소드

```yaml
  annotations:
    - endpointType: SCHEDULED
      annotations: [Scheduled]
      pathAttributes: [cron, fixedRate, fixedDelay, fixedRateString, fixedDelayString]   # path 에 주기를 넣는다
    - endpointType: LISTENER
      annotations: [KafkaListener, RabbitListener, JmsListener, …]
      pathAttributes: [topics, queues, destination, value]                               # path 에 토픽 · 큐 이름
```

`@Scheduled(cron = "0 0 1 * * *") void nightly()` → `SCHEDULED`, `path = "0 0 1 * * *"`, `properties_json.cron`.

#### endpoints.superTypes: 이 타입을 상속한 클래스의 메소드

```yaml
  superTypes:
    - endpointType: THREAD
      superTypes: [java.lang.Runnable, java.lang.Thread, java.util.TimerTask]
      methods: [run]          # 또는 methodPattern: '^perform'
      paramCount: 0           # 생략하면 파라미터 수를 보지 않는다
```

`class Worker implements Runnable { public void run() { … } }` → `THREAD` 진입점. `run()`은 코드에서 부르는 곳이 없어 죽은 코드처럼 보이므로 진입점으로 알아 둔다. **바로** 상속(구현)한 클래스만 본다. 상위 타입은 RESOLVE가 만든 `EXTENDS`/`IMPLEMENTS` 관계로 찾으므로, jar가 없어도 import로 전체 이름을 알면 맞는다.

#### endpoints.xml: 자체 프레임워크의 설정 XML

거래 ID와 처리 클래스를 XML에 적어 두는 프레임워크용이다.

```yaml
  xml:
    - endpointType: TRANSACTION
      files: 'config/service-.*\.xml$'   # 프로젝트 안 경로. Java 정규식, find 로 본다
      element: service                   # 요소 이름(네임스페이스 앞붙이 없이)
      pathAttribute: id                  # 주소(거래 ID)
      classAttribute: class              # 처리 클래스. 그 요소에 없으면 바깥 요소에서 찾는다
      methodAttribute: method            # 처리 메소드. 생략하면 클래스만
      pathTemplate: "{value}"            # 앞뒤 글자. 예: "{value}.do"
      httpMethod: POST                   # endpointType 이 HTTP 일 때. 생략하면 ALL
```

```xml
<service id="ORD001" class="com.order.OrderService" method="list"/>
```

→ `TRANSACTION`, `path = ORD001`, 처리 메소드 `OrderService.list`. 이 XML 파일만 `XmlEndpointReader`가 직접 읽는다(SEMANTIC이 파일을 읽는 드문 경우다. XML은 `SafeXml`로 읽는다).

### 5.2 injects, proxies

```yaml
injects:
  annotations: [Autowired, Inject, Resource]
proxies:
  annotations: [Transactional, Async, Cacheable, CacheEvict, CachePut, Retryable, PreAuthorize, Secured]
```

- `injects`: 이 애노테이션이 붙은 필드가 있으면 **필드를 가진 타입 → 필드의 타입**으로 `INJECTS` 관계를 만든다. `@Autowired OrderDao dao;` → `OrderService INJECTS OrderDao`. 의존 그래프에서 "누가 누구를 쓰나"를 본다.
- `proxies`: 이 애노테이션이 메소드나 그 클래스에 붙으면 `analysis_method.proxy_related = true`. Spring 프록시가 끼어드는 메소드라, 같은 클래스 안에서 부르면 트랜잭션이 걸리지 않는 문제 같은 것을 찾을 때 쓴다.

### 5.3 layers: 계층

계층은 화면의 노드 색, 검색 필터, "컨트롤러 → 서비스 → DAO" 흐름 보기에 쓰인다. 세 가지 방법이 있고 확실성이 다르다.

| 키 | 근거 | 확실성(`layer_confidence`) | 처리 플러그인 |
|---|---|---|---|
| `layers.annotations` | 클래스에 붙은 애노테이션 | `HIGH` | `SpringPlugin` (100) |
| `layers.superTypes` | **바로 위**의 상위 타입(전체 이름) | `MEDIUM` | `ConfiguredLayerPlugin` (800) |
| `layers.names` | 클래스 단순 이름(PostgreSQL 정규식) | `LOW` | `NamingLayerPlugin` (900) |

```yaml
layers:
  annotations:
    - { layer: CONTROLLER, annotations: [Controller, RestController] }
  superTypes:
    - { layer: CONTROLLER, types: [jef.application.services.AbstractMainService] }
  names:
    - { layer: SERVICE, pattern: '(Service|ServiceImpl|Manager)$' }
```

- 각 목록 안에서도 위에서부터 먼저 맞는 것으로 정한다.
- 이미 계층이 정해진 클래스는 건드리지 않는다(`layer IS NULL`). 그래서 `@Service`가 붙은 `OrderManager`는 이름 규칙이 아니라 애노테이션 규칙으로 `SERVICE(HIGH)`가 된다.
- 이름 규칙은 컴파일러가 만든 타입(익명 클래스 등)에는 쓰지 않는다.
- `HI-Japan`의 `AbstractMainService`는 화면 요청을 처음 받는 클래스라 CONTROLLER로 두었다. 이렇게 프레임워크의 뜻에 맞춰 고르는 것이 규칙 파일이 하는 일이다.

### 5.4 callArguments: 호출의 인자로 SQL · 화면 잇기

"이 메소드(생성자)의 n번째 인자로 넘긴 글자는 SQL 이름(또는 화면 이름)이다"를 적는다.

```yaml
callArguments:
  - target: SQL                       # SQL → EXECUTES_SQL | VIEW → RENDERS
    methods: [execute]                # 메소드 호출 이름
    constructors: [QueryProperty]     # 생성자 호출 이름(new 타입(...))
    argIndex: 1                       # 0부터. 기본 0, 최대 9
    receiverTypes: [com.fw.BaseDao]   # 호출 대상 타입(하위 타입 포함). 이름이 흔한 메소드를 좁힐 때
    template: "Order.{value}"         # 계산한 값의 앞뒤 글자. SQL 기본 "{value}", VIEW 기본 "{value}.jsp"
    exclude: '^redirect:'             # 이 정규식에 맞는 값은 버린다
```

예 세 가지(지금 묶음에 있는 것):

| 묶음 | 소스 | 결과 |
|---|---|---|
| `mybatis` | `sqlSession.selectList("Order.list", vo)` | 메소드 → statement `Order.list` `EXECUTES_SQL` |
| `hi-japan/backend` | `new QueryProperty("OrderD.selectOrderList")` | 메소드 → statement `OrderD.selectOrderList` `EXECUTES_SQL` |
| `spring` | `new ModelAndView("order/list")` | 메소드 → `…/order/list.jsp` `RENDERS` (`redirect:`·`forward:`는 뺀다) |
| `jpa` | `em.createNamedQuery("Order.findAll")` | 메소드 → `@NamedQuery(name="Order.findAll")` statement `EXECUTES_SQL` |

**백엔드가 하는 일(`MyBatisPlugin`, `JspPlugin`)**

1. `analysis_reference`에서 규칙의 메소드·생성자 이름과 같은 호출(`ref_kind = CALL`/`CREATE`)을 꺼낸다.
2. 인자 값을 얻는다. 첫 인자(`argIndex: 0`)는 DECLARE가 남긴 `arg_text`, 둘째부터는 `args_json`이다(`args_json`은 분석기 1.1부터 생겼다. 그 전 리비전은 DECLARE부터 다시 돌려야 `argIndex: 1` 이상이 맞는다).
3. 값을 **계산**한다(`ConstantEvaluator`).
   - SQL: 따옴표 글자, `+`, 그 타입과 상위 타입의 상수 필드, `return` 한 줄짜리 메소드까지. 지역 변수·매개변수가 섞이면 포기한다.
   - VIEW: 따옴표 글자 하나만 본다.
4. `exclude`로 거르고 `template`을 씌운다.
5. 잇는다.
   - SQL: 그 이름의 statement가 있으면 `EXECUTES_SQL`(`properties_json.via = STATEMENT_NAME`). 이름은 알았는데 statement가 없으면 `UNRESOLVED`로 이름만 남긴다(적용 진단의 "이름은 아는데 없는 SQL"). SQL 이름처럼 생기지 않은 값은 버린다.
   - VIEW: 그 경로로 끝나는 JSP가 **하나일 때만** `RENDERS`.
6. `receiverTypes`가 있으면 호출 대상이 그 타입일 때만 쓴다. 다음 셋 중 하나면 맞는다고 본다: RESOLVE가 그 호출을 그 타입(또는 하위 타입)의 메소드로 풀었다 / 프로젝트 밖 메소드 `타입.이름(...)`으로 풀었다 / 대상 없이(`this`·`super` 포함) 불렀고 부르는 클래스가 그 타입의 하위 타입이다.

`insert`, `update` 같은 흔한 이름은 다른 객체의 호출도 걸린다. 그래도 SQL 이름처럼 생기지 않은 값은 버리고, 그런 statement가 없으면 잇지 않으므로 잘못 이을 일은 적다. 그래도 불안하면 `receiverTypes`로 좁힌다.

### 5.5 screens: 리치클라이언트 화면 (WebSquare, Nexacro)

화면 스크립트가 서버를 주소가 아니라 **거래 ID**로 부르는 프로젝트를 위한 규칙이다. `RichClientPlugin`(510)과 `ScreenMenuPlugin`(520)이 쓴다.

```yaml
screens:
  calls:  [{ function: doRequestAjax, method: "perform{id}" }]   # 함수의 인자(거래 ID) → 서버 메소드
  fields: [{ field: tranId, method: "perform{id}" }]            # 폼 필드 값(거래 ID) → 서버 메소드
  opens:  [{ function: fnOpenPage, screen: "{id}.xml" }]        # 화면 ID → 다른 화면 파일
  menus:  [{ nameKey: MENU_NM, pathKey: SRC_PATH }]             # 메뉴 목록 → 화면 한글명
```

| 규칙 | 화면 소스 | 결과 |
|---|---|---|
| `calls` | `HiJS.svr.doRequestAjax("JCST0200M01S", …)` | 화면 → `performJCST0200M01S` 메소드 `REQUESTS` |
| `fields` | `<input type='hidden' name='tranId' value='JIMC1000M03S'/>` | 화면 → `performJIMC1000M03S` `REQUESTS` |
| `opens` | `parent.scwin.fnOpenPage("JIMC1000G", …)` | 화면 → `JIMC1000G.xml` `INCLUDES` |
| `menus` | `{'MENU_NM':'履行期間管理', …, 'SRC_PATH':'/ui/jc/JCIQ0700G.xml'}` | `JCIQ0700G.xml`의 화면명(`analysis_resource` `SCREEN_NAME`, via `MENU`) |

- 함수 이름은 마지막 마디만 적는다(`HiJS.svr.`는 없어도 맞는다).
- 기본은 첫 인자를 본다. 다른 자리면 `argIndex`를 적는다(`calls`, `opens`). 짝이 맞는 괄호까지 인자를 나누고, 문자열·중첩 괄호·주석 속 쉼표는 나누는 곳으로 보지 않는다. 그 자리의 인자가 따옴표 글자 하나일 때만 ID로 쓴다.
- 서버 메소드는 그 이름의 메소드가 있을 때, 화면은 그 경로로 끝나는 화면이 **하나일 때만** 잇는다.
- 규칙이 보는 자리가 글자가 아니어서 건너뛴 호출은 함수별로 센다. 다른 자리에 따옴표 글자가 있었으면 후보 API가 `argIndex` 규칙을 제안한다(6.1절).

**ID 다듬기** — 거래 ID와 메소드 이름이 글자 그대로 같지 않을 때. 적은 순서와 상관없이 아래 순서로 다듬은 뒤 `{id}`에 넣는다.

1. `idPattern` / `idReplace`: ID 전체가 정규식에 맞아야 하고, 맞으면 `$1`, `$2`로 바꾼다. 맞지 않는 ID는 이 규칙으로 잇지 않는다.
2. `idCase`: `UPPER` / `LOWER` / `UPPER_FIRST` / `LOWER_FIRST`.
3. `idMap`: 규칙 폴더 안의 대응표 파일에서 찾아 바꾼다. 표에 없는 ID는 잇지 않는다.

```yaml
screens:
  calls:
    # callService("SVC_ORDER_LIST") → svcOrderList 메소드
    - { function: callService, method: "{id}", idPattern: '^SVC_(.*)$', idReplace: 'svc_$1', idCase: LOWER }
    # 대응표: 한 줄에 "ID,값"(= 이나 탭도 된다), # 은 주석
    - { function: callTx, method: "{id}", idMap: order-system/tx-map.csv }
```

대응표가 있는 `calls` 규칙은 표의 ID 하나하나를 **`TRANSACTION` 진입점**으로도 올린다(메소드가 하나로 정해질 때만). 프레임워크가 그 표를 보고 메소드를 부르기 때문이다. 표의 값이 `클래스.메소드`면 그 클래스의 메소드에만 잇는다.

### 5.6 jpa: JPA와 Spring Data

`JpaPlugin`(390)과 `JavaSqlPlugin`(410)이 쓴다. 핵심은 **엔티티 이름 → 테이블 이름**을 알아내서 JPQL의 엔티티 이름을 테이블로 바꾸는 것이다.

```yaml
jpa:
  entities: [Entity]          # 엔티티 애노테이션. name 속성이 엔티티 이름(없으면 클래스 이름)
  tables: [Table]             # 테이블 이름 애노테이션(name 속성)
  naming: SNAKE_CASE          # @Table 이 없을 때: SNAKE_CASE(OrderItem → ORDER_ITEM) | AS_IS(ORDERITEM)
  queries:                    # 메소드에 붙은 쿼리. nativeAttribute 가 true 면 SQL, 아니면 JPQL
    - { annotation: Query, attribute: value, nativeAttribute: nativeQuery }
  namedQueries:               # 엔티티에 붙은 이름 있는 쿼리. container 안의 것도 읽는다
    - { annotation: NamedQuery, nameAttribute: name, attribute: query, container: NamedQueries }
    - { annotation: NamedNativeQuery, nameAttribute: name, attribute: query, container: NamedNativeQueries, native: true }
  repositories: [Repository, CrudRepository, JpaRepository, …]   # 이 타입을 상속한 인터페이스 = 저장소
  jpqlCalls: [createQuery]    # 이 메소드에 넘긴 Java 문자열은 JPQL
```

| 소스 | 결과 |
|---|---|
| `@Entity @Table(name="TB_ORDER") class Order` | 엔티티 `Order` → 테이블 `TB_ORDER` |
| `@Query("select o from Order o where o.status = ?1") List<Order> findActive(…)` | `analysis_mapper`(`JPA`, `language = JPQL`) + 메소드 `EXECUTES_SQL` + `READS_TABLE TB_ORDER` |
| `interface OrderRepository extends JpaRepository<Order, Long> { List<Order> findByName(String n); }` | `findByName`이 `TB_ORDER`를 읽는다(`DERIVED_QUERY`). `delete…`는 `WRITES_TABLE` |
| `em.createQuery("select c from Customer c")` | Java 문자열 SQL을 JPQL로 읽어 테이블로 바꾼다(`JavaSqlPlugin`) |

JPA statement는 SEMANTIC이 돌 때마다 지우고 새로 만든다. 그래서 `mapper_id`가 매번 바뀌고, 시험 적용(6.1절)을 하면 JPA 관련 `EXECUTES_SQL`·`READS_TABLE`이 "같은 수만큼 없어지고 생긴" 것으로 보인다. 내용이 바뀐 것은 아니다.

### 6.1 새 관례를 규칙으로 만드는 순서

```text
 처음 분석 ─▶ ① 적용 진단 ─▶ ② 후보 보기 ─▶ ③ 시험 적용 ─▶ ④ 파일로 저장 ─▶ ⑤ SEMANTIC 다시 돌리기
              (무엇이 비었나)  (무엇을 적을까)  (적으면 어떻게 되나)  (conf/rules/…)    (rerunFrom)
```

**① 적용 진단** — 항목마다 해결 방법이 붙어 있다: `RULE`(규칙 파일), `CLASSPATH`(jar 위치), `SETTING`(프로젝트 설정), `SOURCE`(소스 보충), `DEVELOP`(분석기 개발), `NONE`(문제없음). 실제 `hen` 리비전 102의 결과 일부다.

| 항목 | 해결 | 메시지(요약) |
|---|---|---|
| 호출 해석 | `NONE` | 메소드 호출의 98.19%가 누구를 부르는지 풀렸습니다 |
| 서버와 이어지지 않은 화면 | `RULE` | 화면 742개 가운데 335개는 서버의 무엇도 부르지 않습니다. 공통 함수에 거래 ID를 넘기는 프로젝트면 `screens.calls` 규칙을 … |
| 이름은 아는데 없는 SQL | `SOURCE` | 코드가 부르는 SQL 이름의 statement가 매퍼에 없습니다 … |
| 계층을 모르는 클래스 | `RULE` | 클래스 585개 가운데 64개는 계층을 정하지 못했고 18개는 이름 끝말로 짐작했습니다 … `layers.superTypes` … |
| 적용한 규칙 | `NONE` | 이 프로젝트 전용 규칙 폴더가 없습니다. 이 프로젝트에만 쓸 관례는 `conf/rules/hen/` 아래에 적습니다 |

**② 후보 보기** — `GET /api/revisions/102/rules/candidates?limit=2`의 실제 응답 일부다. 후보는 네 종류다.

| 키 | 무엇 |
|---|---|
| `callArguments` | 따옴표 글자를 인자로 받는 호출 가운데 그 글자가 이 프로젝트의 SQL 이름이나 JSP 화면 이름과 같은 것. 몇 번째 인자인지, RESOLVE가 가장 많이 푼 대상 타입도 함께 |
| `annotations` | 규칙이 모르는 애노테이션 가운데 많이 붙은 것. `unexplained`는 계층 없는 타입이나 진입점 아닌 메소드에 붙은 수 |
| `superTypes` | 규칙이 모르는 상위 타입 가운데 계층이 없거나 LOW인 하위 타입이 많은 것 |
| `screenRules` | 화면 규칙이 보는 자리가 글자가 아니어서 건너뛴 호출 가운데 다른 자리에 따옴표 글자가 있던 것 → `argIndex` 제안 |

```json
"superTypes": [{
  "superType": "com.frameq.hhr.rules.HrRule",
  "inProject": true, "types": 5, "unlayered": 3,
  "samples": "HrRuleAnnual, HrRuleAppointment, HrRuleHoliday",
  "suggestion": "layers:\n  superTypes:\n    - { layer: <계층을 고르세요>, types: [com.frameq.hhr.rules.HrRule] }\n"
}]
```

`suggestion`은 붙여 넣을 규칙 조각이다. **계층과 진입점 종류는 짐작이라 꼭 고친다.** Lombok·테스트·JSON 애노테이션처럼 뜻이 도구에 있는 것은 후보에서 뺀다.

**③ 시험 적용** — 규칙 묶음 글을 보내면 SEMANTIC을 **한 트랜잭션 안에서 실제로 돌려 보고** 전후를 비교한 뒤 **모두 되돌린다.** DB에 남는 것은 없다.

```bash
curl -X POST localhost:4081/api/revisions/106/rules/trial -H 'Content-Type: application/json' \
  -d '{"ruleSet": "name: jpa-app/trial\nlayers:\n  names:\n    - { layer: CONFIG, pattern: \"^Urls$\" }\n"}'
```

실제 응답(요약):

```json
{
  "trialRuleSet": "jpa-app/trial",
  "ruleSets": ["java", "servlet", "spring", "jpa", "mybatis", "jpa-app/trial", "fallback"],
  "summary": [
    { "kind": "LAYER", "category": "CONFIG(LOW)", "before": 0, "after": 1, "added": 1, "removed": 0 },
    { "kind": "RELATION", "category": "EXECUTES_SQL(HIGH)", "before": 13, "after": 13, "added": 8, "removed": 8 }
  ],
  "added": [{ "kind": "LAYER", "category": "CONFIG(LOW)", "label": "com.shop.web.Urls = CONFIG(LOW)" }],
  "note": "시험 결과는 저장하지 않았습니다. 반영하려면 규칙 파일을 …/conf/rules 에 저장하고 rerunFrom=SEMANTIC 으로 다시 돌리세요."
}
```

- 시험 묶음(`order` 기본 500)이 `mybatis`(300)와 `fallback`(900) 사이에 끼었다. 그래서 `Urls`가 `fallback`보다 먼저 CONFIG가 됐다.
- `EXECUTES_SQL` 8개가 없어지고 생긴 것은 JPA statement를 다시 만들어서다(5.6절). 수(before/after)가 같으면 내용은 그대로다.
- 시험 묶음에는 `name`이 꼭 있어야 한다. 같은 이름의 파일이 있으면 그 파일 대신 쓴다. 본문 없이 부르면 지금 파일 그대로 돌려서 "파일을 고쳤는데 다시 돌리면 무엇이 바뀌나"를 본다.
- 그 프로젝트에 분석이 돌고 있으면 409. 서버 전체에서 한 번에 하나만 돈다(`synchronized`). 큰 프로젝트는 SEMANTIC 한 번만큼(수십 초~몇 분) 걸린다.
- 처리: `RuleService.trial` → 트랜잭션을 열고 `setRollbackOnly()` → `RuleDao.createBeforeFacts` → `SemanticPass.runPlugins` → `RuleDao.createAfterFacts` → 차이 조회 → 롤백.

**④ 저장** — 공통 관례면 `conf/rules/<이름>.yml`, 한 프로젝트의 관례면 `conf/rules/<프로젝트ID>/<이름>.yml`(그 프로젝트에 저절로 쓰인다).

**⑤ 반영** — 서버를 다시 띄우지 않는다.

```json
POST /api/projects/{projectId}/analyses
{ "revisionLabel": "<같은 리비전 이름>", "rerunFrom": "SEMANTIC" }
```

### 6.2 규칙이 바뀌었는지 보기

`GET /api/revisions/{id}/rules`는 4.6절의 RULE_SET 기록과 지금 파일을 해시로 견준다.

| `status` | 뜻 |
|---|---|
| `SAME` | 분석할 때와 같다 |
| `CHANGED` | 파일(또는 대응표) 내용이 바뀌었다 |
| `REMOVED` | 그때는 썼는데 지금은 쓰지 않는다(파일을 지웠거나 `ruleSets`에서 뺐다) |
| `ADDED` | 지금은 쓰는데 그때는 없었다 |

하나라도 `SAME`이 아니면 `upToDate: false`이고, SEMANTIC부터 다시 돌려야 지금 규칙이 반영된다. RULE_SET 기록이 없는 리비전(규칙 파일이 생기기 전에 분석한 것)은 모두 `ADDED`로 나오고 `note`가 그 이유를 알려 준다.

## 7. 자주 만나는 오류

| 증상 | 원인 | 해결 |
|---|---|---|
| 서버가 뜨지 않고 `의미 분석 규칙 파일이 잘못 적혀 있습니다. <파일> <자리>: …` | 모르는 키(오타), 없는 계층 이름, 틀린 정규식, YAML 문법 오류 | 메시지의 파일·자리를 고친다 |
| `규칙 파일 폴더가 없습니다` | `rules-dir`·`APP_CONF_DIR`이 다른 곳을 가리킨다 | 4.1절의 순서로 폴더 위치를 확인한다 |
| `묶음 이름(…)은 규칙 폴더 안의 경로(…)와 같아야 합니다` | 파일을 옮기거나 이름을 바꾸면서 `name:`을 그대로 뒀다 | `name:`을 지우거나 경로와 맞춘다 |
| `HTTP 진입점 애노테이션 GetMapping 이(가) 규칙 묶음 spring 와 my-set 에 함께 있습니다` | 같은 애노테이션을 두 묶음에 적었다 | 한쪽에만 둔다. 분석 시작 때 나므로 그 분석이 실패한다 |
| 프로젝트 등록 · 분석에서 `규칙 묶음 X 이(가) 없습니다. 있는 묶음: […]` | `ruleSets`에 오타, 또는 파일을 지웠다 | 묶음 이름이나 폴더 이름을 맞춘다 |
| 규칙을 고쳤는데 결과가 그대로다 | SEMANTIC을 다시 돌리지 않았다 | `rerunFrom: "SEMANTIC"`. `GET /api/revisions/{id}/rules`의 `upToDate`로 확인한다 |
| `argIndex: 1` 규칙이 옛 리비전에서 안 맞는다 | 분석기 1.1 전에 분석해 `args_json`이 비어 있다 | DECLARE부터 다시 분석한다 |
| 시험 적용이 409 | 그 프로젝트에 분석이 돌고 있다 | 끝난 뒤에 다시 한다 |
| 규칙에 맞는 호출인데 선이 안 생긴다 | 인자가 지역 변수·매개변수라 계산되지 않는다 | 의도된 동작이다(짐작하지 않는다). SQL이면 이름은 `UNRESOLVED`로 남는다 |
