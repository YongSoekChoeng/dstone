## 1. 규칙 파일이 왜 필요한가

### 1.1 같은 기능, 다른 코드

"주문 목록을 조회한다"는 똑같은 기능을 두 회사가 이렇게 만들었다고 하자.

**A사 (Spring + MyBatis)**

```java
@Controller
@RequestMapping("/order")
public class OrderController {
    @Autowired OrderService service;

    @GetMapping("/list")
    public String list(Model model) { … return "order/list"; }
}

@Repository
public class OrderDao {
    public List<OrderVO> list() { return sqlSession.selectList("Order.selectList"); }
}
```

**B사 (자체 프레임워크)**

```java
public class OrderAct extends com.acme.fw.BaseAction {      // 화면 요청을 처음 받는 클래스
    public void list(Ctx ctx) { … }
}

public class OrderStore extends com.acme.fw.BaseDao {
    public List<OrderVO> list(Ctx ctx) { return executeList(ctx, "Order.selectList", null); }
}
```

```xml
<!-- config/service-order.xml : 거래 ID와 처리 메소드의 짝 -->
<service id="ORD001" class="com.acme.order.OrderAct" method="list"/>
```

사람은 둘 다 "컨트롤러가 요청을 받고, DAO가 `Order.selectList` SQL을 실행한다"고 읽는다. 그런데 이것은 **Java 문법이 정한 사실이 아니다.**

- `@GetMapping`이 "주소"라는 것은 Spring의 약속이다.
- `BaseAction`을 상속하면 컨트롤러라는 것은 B사의 약속이다.
- `executeList`의 **두 번째** 인자가 SQL 이름이라는 것도 B사의 약속이다.

이런 약속(관례)을 분석기 Java 코드에 박아 두면, 새 회사의 프로젝트를 만날 때마다 분석기를 고쳐야 한다.

### 1.2 그래서 관례는 파일에 적는다

`dstone-knowledge`는 관례를 **규칙 파일**(`dstone-knowledge/conf/rules/*.yml`)에서 읽는다. B사 프로젝트를 분석하려면 Java를 고치지 않고 아래 같은 파일 하나를 더하면 된다.

```yaml
# conf/rules/acme.yml
layers:
  superTypes:
    - { layer: CONTROLLER, types: [com.acme.fw.BaseAction] }
    - { layer: REPOSITORY, types: [com.acme.fw.BaseDao] }
callArguments:
  - { target: SQL, methods: [executeList], argIndex: 1, receiverTypes: [com.acme.fw.BaseDao] }
endpoints:
  xml:
    - { endpointType: TRANSACTION, files: 'config/service-.*\.xml$', element: service,
        pathAttribute: id, classAttribute: class, methodAttribute: method }
```

A사의 관례(Spring, MyBatis)도 똑같이 파일(`spring.yml`, `mybatis.yml`)에 들어 있다. Spring을 쓰지 않는 프로젝트에서는 그 규칙에 맞는 코드가 없으니 아무 일도 하지 않는다.

### 1.3 무엇이 코드에 남고, 무엇이 파일로 갔나

| 어디에 | 기준 | 예 |
|---|---|---|
| **Java 코드** | Java라면, 또는 그 표준 형식이라면 누구나 같은 것 | `public static void main`, JSP 파일, `web.xml`, `struts-config.xml`, MyBatis 매퍼 인터페이스(namespace = 인터페이스 이름), 호출 해석(RESOLVE), SQL 파싱, Java 문자열로 만든 SQL, 주소 상수 계산, 상위 클래스의 주소 물려받기 |
| **규칙 파일** | 이 프레임워크(회사)를 쓰면 이렇다 | `@GetMapping`은 주소, `@Service`는 서비스, `sqlSession.selectList("x")`의 첫 인자는 SQL 이름, `AbstractMainService`를 상속하면 컨트롤러, 화면의 `doRequestAjax("거래ID")`는 서버 호출 |

### 1.4 규칙으로 알아내는 다섯 가지

| 알고 싶은 것 | 규칙 키 | 결과가 들어가는 곳 |
|---|---|---|
| 이 메소드는 **입구**인가(주소, 스케줄, 리스너, 스레드, 거래 ID) | `endpoints` | `analysis_endpoint` |
| 이 클래스는 **어느 계층**인가(CONTROLLER, SERVICE …) | `layers` | `analysis_symbol.layer` |
| 이 필드는 **주입**받나 / 이 메소드에 **프록시**가 끼어드나 | `injects`, `proxies` | `analysis_relation`(INJECTS), `analysis_method.proxy_related` |
| 이 호출은 **어떤 SQL을 실행**하나 / **어떤 JSP를 보여 주나** | `callArguments`, `jpa` | `analysis_relation`(EXECUTES_SQL, RENDERS), `analysis_mapper` |
| 이 화면은 **어떤 서버 메소드를 부르나** / **어떤 화면을 여나** / 이름은 무엇인가 | `screens` | `analysis_relation`(REQUESTS, INCLUDES), `analysis_resource`(SCREEN_NAME) |

### 1.5 꼭 기억할 세 가지

1. **규칙은 SEMANTIC 단계에서만 쓴다.** SCAN·DECLARE·RESOLVE는 규칙과 상관없다. 그래서 규칙을 고친 뒤에는 `rerunFrom: "SEMANTIC"`으로 그 단계만 다시 돌리면 된다.
2. **서버를 다시 띄우지 않는다.** 분석할 때마다 규칙 폴더를 새로 읽는다.
3. **짐작하지 않는다.** 규칙이 "첫 인자가 SQL 이름"이라고 알려 줘도, 그 인자가 따옴표 글자나 상수로 계산되지 않으면 잇지 않는다. 짐작으로 이은 선은 영향도 분석을 틀리게 만든다(3.4절).

## 2. 따라 해 보기: B사 프로젝트에 규칙 붙이기

1.1절의 B사 프로젝트를 `acme-order`라는 ID로 등록해 처음 분석했다고 하자. 아래 화면과 숫자는 흐름을 보여 주려고 만든 **예시**다. 실제 서버의 응답 모양은 6장에 있다.

### 2.1 규칙 없이 분석하면

공통 규칙(`java`, `servlet`, `spring`, `jpa`, `mybatis`, `fallback`)만 쓰인다. B사 코드에는 Spring 애노테이션도 `sqlSession` 호출도 없으니 대부분 비어 있다.

| 클래스 / 메소드 | 계층 | 진입점 | SQL |
|---|---|---|---|
| `OrderAct` | (없음) | (없음) | — |
| `OrderStore` | (없음) | — | `list()` → (선 없음) |
| `OrderBiz` | `SERVICE (LOW)` — 이름 끝 `Biz`로 짐작 | — | — |

`OrderAct.list()`는 아무도 부르지 않는 메소드라 죽은 코드처럼 보이고, 영향도 분석도 여기서 출발하지 못한다.

### 2.2 무엇이 비었는지 묻는다: 적용 진단

Knowledge 화면 [프로젝트·분석] → 리비전 요약의 **적용 진단**(API로는 `GET /api/revisions/{id}/diagnostics`)이 해결 방법과 함께 알려 준다.

```text
계층을 모르는 클래스   RULE   클래스 120개 가운데 48개는 계층을 정하지 못했습니다 … layers.superTypes …
적용한 규칙            NONE   이 프로젝트 전용 규칙 폴더가 없습니다. conf/rules/acme-order/ 아래에 적습니다
```

`RULE`이 붙은 항목은 규칙 파일로 풀 수 있다는 뜻이다.

### 2.3 무엇을 적을지 묻는다: 후보

`GET /api/revisions/{id}/rules/candidates`가 규칙이 아직 모르는 흔적을 모아 **붙여 넣을 조각**까지 만들어 준다.

```json
"superTypes": [{
  "superType": "com.acme.fw.BaseDao", "types": 31, "unlayered": 31,
  "samples": "OrderStore, CustomerStore, ItemStore",
  "suggestion": "layers:\n  superTypes:\n    - { layer: <계층을 고르세요>, types: [com.acme.fw.BaseDao] }\n"
}],
"callArguments": [{ "kind": "CALL", "name": "executeList", "argIndex": 1, "receiverType": "com.acme.fw.BaseDao", … }]
```

`<계층을 고르세요>`처럼 계층과 진입점 종류는 분석기가 짐작할 수 없어서 비워 둔다. 사람이 채운다.

### 2.4 규칙을 적는다

이 프로젝트에만 쓰는 관례이므로 프로젝트 ID 이름의 폴더에 둔다. 폴더 이름이 프로젝트 ID와 같으면(대소문자 무시) `ruleSets`에 적지 않아도 저절로 쓰인다(4.1절).

```yaml
# conf/rules/acme-order/backend.yml   → 묶음 이름은 acme-order/backend
description: ACME 자체 프레임워크의 계층, SQL 호출, 거래 설정 XML

layers:
  superTypes:
    - { layer: CONTROLLER, types: [com.acme.fw.BaseAction] }
    - { layer: SERVICE,    types: [com.acme.fw.BaseBiz] }
    - { layer: REPOSITORY, types: [com.acme.fw.BaseDao] }

callArguments:
  # executeList(ctx, "Order.selectList", vo) — SQL 이름은 두 번째 인자
  - target: SQL
    methods: [executeList, executeOne, executeUpdate]
    argIndex: 1
    receiverTypes: [com.acme.fw.BaseDao]      # 흔한 이름이라 BaseDao 쪽 호출로 좁힌다

endpoints:
  xml:
    # <service id="ORD001" class="com.acme.order.OrderAct" method="list"/>
    - endpointType: TRANSACTION
      files: 'config/service-.*\.xml$'
      element: service
      pathAttribute: id
      classAttribute: class
      methodAttribute: method
```

### 2.5 저장하기 전에 시험해 본다

파일 내용을 그대로 보내면 SEMANTIC을 실제로 돌려 본 뒤 **모두 되돌린다.** DB에 남는 것은 없다. 시험 묶음에는 `name`이 꼭 있어야 한다.

```bash
curl -X POST localhost:4081/api/revisions/{id}/rules/trial -H 'Content-Type: application/json' \
  -d '{"ruleSet": "name: acme-order/backend\nlayers:\n  superTypes:\n ..."}'
```

응답의 `summary`에서 늘고 준 것을 확인한다.

```text
LAYER       CONTROLLER(MEDIUM)     before 0   after 22
LAYER       SERVICE(LOW)           before 19  after 0     ← 이름으로 짐작하던 것이
LAYER       SERVICE(MEDIUM)        before 0   after 19    ← 상위 타입 근거로 바뀌었다
RELATION    EXECUTES_SQL(HIGH)     before 0   after 87
ENDPOINT    TRANSACTION            before 0   after 64
```

### 2.6 저장하고 SEMANTIC만 다시 돌린다

파일을 `conf/rules/acme-order/backend.yml`로 저장하고, 서버는 그대로 둔 채 같은 리비전을 SEMANTIC부터 다시 돌린다.

```json
POST /api/projects/acme-order/analyses
{ "revisionLabel": "<같은 리비전 이름>", "rerunFrom": "SEMANTIC" }
```

### 2.7 결과

| 클래스 / 메소드 | 계층 | 진입점 | SQL |
|---|---|---|---|
| `OrderAct` | `CONTROLLER (MEDIUM)` | `list()` = `TRANSACTION ORD001` | — |
| `OrderStore` | `REPOSITORY (MEDIUM)` | — | `list()` → `Order.selectList` `EXECUTES_SQL` |
| `OrderBiz` | `SERVICE (MEDIUM)` | — | — |

이제 "`ORD001` 거래 → `OrderAct.list` → … → `Order.selectList` → `TB_ORDER` 테이블"로 이어지는 선을 따라 영향도를 볼 수 있다.

## 3. 규칙 키별 예제

모든 절은 **이런 소스가 있으면 → 이렇게 적고 → 이런 결과가 생긴다** 순서다. 예제의 규칙은 대부분 지금 들어 있는 파일(`spring.yml`, `hi-japan/*.yml` …)에서 가져왔다.

### 3.0 파일의 뼈대

```yaml
name: acme-order/backend   # 생략 가능. 적으면 규칙 폴더 안의 경로(확장자 뺀 것)와 같아야 한다
description: 사람이 읽을 설명
order: 500                 # 적용 순서. 작을수록 먼저. 기본 500 (4.2절)
autoApply: false           # 모든 프로젝트에 쓸지. 바로 아래 파일은 기본 true, 하위 폴더는 false (4.1절)

endpoints:     # 3.1  입구
injects:       # 3.2  주입
proxies:       # 3.2  프록시
layers:        # 3.3  계층
callArguments: # 3.4  호출 인자 → SQL·JSP
screens:       # 3.5  리치클라이언트 화면
jpa:           # 3.6  JPA
```

적는 법 몇 가지:

- 애노테이션은 `@` 없이 단순 이름(`Service`)으로, 상위 타입과 `receiverTypes`는 전체 이름(`com.acme.fw.BaseDao`)으로 적는다.
- 목록 자리에 값이 하나면 그냥 적어도 된다. `annotations: Service`는 `annotations: [Service]`와 같다.
- `{`나 `@`로 시작하는 값은 따옴표로 감싼다(YAML 문법). 예: `method: "{id}"`.
- 모르는 키는 오타로 보고 서버가 뜨지 않는다(7장).

### 3.1 endpoints: 입구(진입점)

진입점은 "밖에서 이 프로그램으로 들어오는 문"이다. 코드 안에서 아무도 부르지 않는 메소드라도 진입점이면 죽은 코드가 아니고, 영향도 분석은 여기서 출발한다. 네 가지 방법이 있다.

#### ① `endpoints.http` — 클래스 주소 + 메소드 주소

**소스**

```java
@RequestMapping("/order")
public class OrderController {
    @GetMapping("/list")
    public String list() { … }

    @RequestMapping(value = "/save", method = RequestMethod.POST)
    public String save() { … }
}
```

**규칙** (`spring.yml`)

```yaml
endpoints:
  http:
    - classAnnotations: [RequestMapping]          # 클래스에 붙은 주소
      pathAttributes: [value, path]               # 주소가 적힌 속성. 앞에 적은 것부터 본다
      methodAnnotations:
        - { annotation: RequestMapping, methodAttribute: method }   # HTTP 메소드를 속성에서 읽는다. 없으면 ALL
        - { annotation: GetMapping, httpMethod: GET }               # HTTP 메소드가 정해져 있다
```

**결과** — `analysis_endpoint` 두 행

| type | path | 메소드 |
|---|---|---|
| `HTTP` | `GET /order/list` | `OrderController.list` |
| `HTTP` | `POST /order/save` | `OrderController.save` |

근거 애노테이션은 `properties_json.annotation`에 남는다. 규칙이 없어도 코드가 알아서 해 주는 일이 두 가지 있다.

- **주소 상수 계산**: `@GetMapping(Urls.ORDER + "/list")`처럼 상수를 쓰면 따라가 계산한다. static import나 다른 jar의 상수라서 계산하지 못하면 진입점은 만들되 `properties_json.unresolvedPath`에 원문을 남긴다.
- **상위 타입의 주소 물려받기**: 클래스에 주소가 없으면 인터페이스, 그다음 상위 클래스의 클래스 주소를 쓴다. 상위 클래스에 있는 핸들러 메소드는 그것을 물려받은 실제 컨트롤러의 진입점이 되고 `properties_json.inheritedFrom`이 붙는다. 이때 "컨트롤러인지"는 `layers.annotations`가 정한 CONTROLLER 계층이나 주소 애노테이션으로 본다. 그래서 사내 컨트롤러 애노테이션을 쓰는 프로젝트는 그 애노테이션을 `layers.annotations`에 적어야 주소를 물려받는다.

#### ② `endpoints.annotations` — 애노테이션이 붙은 메소드

**소스**

```java
@Scheduled(cron = "0 0 1 * * *")
public void nightly() { … }

@KafkaListener(topics = "order-created")
public void onCreated(String msg) { … }
```

**규칙** (`spring.yml`)

```yaml
endpoints:
  annotations:
    - endpointType: SCHEDULED
      annotations: [Scheduled]
      pathAttributes: [cron, fixedRate, fixedDelay, fixedRateString, fixedDelayString]   # path 에 주기를 넣는다
    - endpointType: LISTENER
      annotations: [KafkaListener, RabbitListener, JmsListener, SqsListener, StreamListener, EventListener, TransactionalEventListener]
      pathAttributes: [topics, queues, destination, value]                               # path 에 토픽·큐 이름
```

**결과**

| type | path |
|---|---|
| `SCHEDULED` | `0 0 1 * * *` (`properties_json.cron`에도 남는다) |
| `LISTENER` | `order-created` |

`endpointType`은 영문 대문자로 시작하는 대문자·숫자·`_` 2~20자면 새로 지어도 된다(예: `BATCH_JOB`).

#### ③ `endpoints.superTypes` — 이 타입을 상속한 클래스의 메소드

**소스**

```java
public class MailWorker implements Runnable {
    public void run() { … }       // 코드에서 run() 을 부르는 곳이 없다
}
```

**규칙** (`java.yml`)

```yaml
endpoints:
  superTypes:
    - endpointType: THREAD
      superTypes: [java.lang.Runnable, java.lang.Thread, java.util.TimerTask]
      methods: [run]              # 또는 methodPattern: '^perform'
      paramCount: 0               # 생략하면 파라미터 수를 보지 않는다
```

**결과** — `MailWorker.run()`이 `THREAD` 진입점이 되어 죽은 코드로 보이지 않는다.

- **바로** 상속(구현)한 클래스만 본다. `A extends MailWorker`의 `run()`은 맞지 않는다.
- 상위 타입은 RESOLVE가 만든 `EXTENDS`/`IMPLEMENTS` 관계로 찾는다. jar가 없어도 import로 전체 이름을 알면 맞는다.

#### ④ `endpoints.xml` — 자체 프레임워크의 설정 XML

거래 ID와 처리 클래스를 XML에 적어 두는 프레임워크용이다.

**소스** (`config/service-order.xml`)

```xml
<services>
  <service id="ORD001" class="com.acme.order.OrderAct" method="list"/>
  <service id="ORD002" class="com.acme.order.OrderAct" method="save"/>
</services>
```

**규칙**

```yaml
endpoints:
  xml:
    - endpointType: TRANSACTION
      files: 'config/service-.*\.xml$'   # 프로젝트 안 경로. Java 정규식, 일부만 맞아도 된다(find)
      element: service                   # 요소 이름(네임스페이스 앞붙이 없이)
      pathAttribute: id                  # 주소(거래 ID)
      classAttribute: class              # 처리 클래스. 그 요소에 없으면 바깥 요소에서 찾는다
      methodAttribute: method            # 처리 메소드. 생략하면 클래스만
      pathTemplate: "{value}"            # 앞뒤 글자. 예: "{value}.do"
      httpMethod: POST                   # endpointType 이 HTTP 일 때만. 생략하면 ALL
```

**결과**

| type | path | 처리 메소드 |
|---|---|---|
| `TRANSACTION` | `ORD001` | `OrderAct.list` |
| `TRANSACTION` | `ORD002` | `OrderAct.save` |

SEMANTIC이 소스 파일을 직접 읽는 드문 경우다(`XmlEndpointReader`, XML은 `SafeXml`로 읽는다).

### 3.2 injects, proxies: 주입과 프록시

**소스**

```java
@Service
public class OrderService {
    @Autowired OrderDao dao;

    @Transactional
    public void save(OrderVO vo) { … }
}
```

**규칙** (`spring.yml`)

```yaml
injects:
  annotations: [Autowired, Inject, Resource]
proxies:
  annotations: [Transactional, Async, Cacheable, CacheEvict, CachePut, Retryable, PreAuthorize, Secured]
```

**결과**

- `injects` → `OrderService INJECTS OrderDao` (필드를 가진 타입 → 필드의 타입). 의존 그래프에서 "누가 누구를 쓰나"를 본다.
- `proxies` → `OrderService.save`의 `analysis_method.proxy_related = true`. 애노테이션이 클래스에 붙어도 그 클래스의 메소드가 모두 해당한다. "같은 클래스 안에서 부르면 트랜잭션이 걸리지 않는다" 같은 문제를 찾을 때 쓴다.

### 3.3 layers: 계층

계층은 화면의 노드 색, 검색 필터, "컨트롤러 → 서비스 → DAO" 흐름 보기에 쓰인다. 근거에 따라 세 가지 방법이 있고, 확실한 정도(`layer_confidence`)가 다르다.

| 키 | 무엇을 보나 | 확실성 | 예 |
|---|---|---|---|
| `layers.annotations` | 클래스에 붙은 애노테이션 | `HIGH` | `@Service` → SERVICE |
| `layers.superTypes` | **바로 위** 상위 타입(전체 이름) | `MEDIUM` | `extends AbstractMainService` → CONTROLLER |
| `layers.names` | 클래스 단순 이름(PostgreSQL 정규식) | `LOW` | `…Manager` → SERVICE |

**규칙**

```yaml
layers:
  annotations:
    - { layer: CONTROLLER, annotations: [Controller, RestController] }
  superTypes:
    - { layer: CONTROLLER, types: [jef.application.services.AbstractMainService] }
  names:
    - { layer: SERVICE, pattern: '(Service|ServiceImpl|Manager)$' }
```

**클래스 셋이 어떻게 정해지나**

| 소스 | 결과 | 까닭 |
|---|---|---|
| `@Service class OrderManager` | `SERVICE (HIGH)` | 애노테이션 규칙이 먼저 정했다. 이름 규칙은 빈 자리만 채운다 |
| `class JCST0200M extends AbstractMainService` | `CONTROLLER (MEDIUM)` | 애노테이션이 없어 상위 타입 규칙이 정했다 |
| `class PointManager` | `SERVICE (LOW)` | 앞의 두 규칙에 걸리지 않아 이름으로 짐작했다 |

- **한 번 정한 계층은 뒤에서 바꾸지 않는다.** 그래서 순서가 중요하다(4.2절).
- 같은 목록 안에서도 위에 적은 것부터 맞춰 본다.
- 이름 규칙은 컴파일러가 만든 타입(익명 클래스 등)에는 쓰지 않는다.
- 계층 이름은 `CONTROLLER, SERVICE, REPOSITORY, MODEL, VIEW, CONFIG, WEB_FILTER, UTIL, EXCEPTION, BATCH, COMPONENT, ASPECT` 중 하나다.
- 계층은 이름이 아니라 **프레임워크에서 하는 일**로 고른다. `HI-Japan`의 `AbstractMainService`는 이름에 Service가 들어 있지만 화면 요청을 처음 받는 클래스라서 CONTROLLER로 두었다.

### 3.4 callArguments: 호출 인자로 SQL·JSP 잇기

"이 메소드(또는 생성자)의 n번째 인자로 넘긴 글자는 SQL 이름(또는 화면 이름)이다"를 적는다.

**지금 들어 있는 예**

| 묶음 | 소스 | 결과 |
|---|---|---|
| `mybatis` | `sqlSession.selectList("Order.list", vo)` | 메소드 → statement `Order.list` `EXECUTES_SQL` |
| `hi-japan/backend` | `new QueryProperty("OrderD.selectOrderList")` | 메소드 → statement `OrderD.selectOrderList` `EXECUTES_SQL` |
| `spring` | `new ModelAndView("order/list")` | 메소드 → `…/order/list.jsp` `RENDERS` |
| `jpa` | `em.createNamedQuery("Order.findAll")` | 메소드 → `@NamedQuery(name="Order.findAll")` statement `EXECUTES_SQL` |

**적을 수 있는 것 전부**

```yaml
callArguments:
  - target: SQL                       # SQL → EXECUTES_SQL | VIEW → RENDERS(JSP)
    methods: [execute]                # 메소드 호출 이름
    constructors: [QueryProperty]     # 생성자 호출 이름(new 타입(...))
    argIndex: 1                       # 몇 번째 인자인가. 0부터, 기본 0, 최대 9
    receiverTypes: [com.fw.BaseDao]   # 호출 대상 타입(하위 타입 포함). 흔한 이름의 메소드를 좁힐 때
    template: "Order.{value}"         # 계산한 값의 앞뒤 글자. SQL 기본 "{value}", VIEW 기본 "{value}.jsp"
    exclude: '^redirect:'             # 이 정규식에 맞는 값은 버린다
```

**예 1 — 인자 자리와 앞붙이**

```java
dao.execute(ctx, "selectList");          // 이 프로젝트는 namespace 를 빼고 부른다
```

```yaml
- { target: SQL, methods: [execute], argIndex: 1, template: "Order.{value}" }
```

→ 값 `selectList`에 틀을 씌워 `Order.selectList` statement와 잇는다.

**예 2 — JSP 화면, `redirect:`는 빼기** (`spring.yml`)

```java
return new ModelAndView("order/list");      // → order/list.jsp
return new ModelAndView("redirect:/main");  // 화면이 아니라 다른 주소로 보낸다
```

```yaml
- target: VIEW
  constructors: [ModelAndView]
  methods: [setViewName]
  template: "{value}.jsp"
  exclude: '^(redirect|forward):'
```

→ 첫째만 `RENDERS`. `order/list.jsp`로 끝나는 JSP가 **하나뿐일 때만** 잇는다.

#### 어떤 값을 "안다"고 보나

이름은 계산할 수 있을 때만 잇는다(`ConstantEvaluator`).

| 소스 | SQL 규칙 | 까닭 |
|---|---|---|
| `selectList("Order.list")` | 잇는다 | 따옴표 글자 |
| `selectList(NS + "list")` (`NS`는 그 클래스나 상위 타입의 상수) | 잇는다 | 상수와 `+`는 계산한다 |
| `selectList(ns() + "list")` (`ns()`는 `return "Order.";` 한 줄) | 잇는다 | `return` 한 줄짜리 메소드까지 따라간다 |
| `selectList(prefix + "list")` (`prefix`는 지역 변수나 매개변수) | 잇지 않는다 | 실행해 봐야 아는 값이라 짐작하지 않는다 |
| `list.insert("abc def")` | 잇지 않는다 | 공백이 있어 SQL 이름처럼 생기지 않았다(영문자·숫자·`_`·`.`·`-`만 이름으로 본다) |

VIEW 규칙은 더 엄격해서 따옴표 글자 하나만 본다.

#### 이름은 아는데 SQL이 없을 때

값을 계산했는데 그 이름의 statement가 없으면:

- 이름에 점이 있으면(`Order.selectList`) `UNRESOLVED` 상태의 `EXECUTES_SQL`로 **이름만** 남긴다. 적용 진단의 "이름은 아는데 없는 SQL"이 이것이다. 매퍼 파일이 분석 대상에 없거나 이름이 틀린 경우다.
- 점이 없으면(`selectList`) namespace 없이 id만 넘기는 방식(iBATIS 기본)으로 보고, 그 id의 statement가 프로젝트에 **하나뿐일 때만** 잇는다. 아니면 버린다.
- 같은 이름이 여러 파일에 있으면 부르는 Java 파일과 같은 소스 루트에 있는 것을 고른다.

#### `receiverTypes`로 좁히기

`insert`, `update` 같은 흔한 이름은 다른 객체의 호출도 걸린다. 대부분 SQL 이름처럼 생기지 않았거나 그런 statement가 없어서 걸러지지만, 불안하면 `receiverTypes`로 좁힌다. 아래 셋 중 하나면 맞는다고 본다.

```java
class OrderStore extends com.acme.fw.BaseDao {
    void a() { baseDao.executeList(ctx, "X.a"); }   // ① RESOLVE가 BaseDao(또는 하위 타입)의 메소드로 풀었다
    void b() { executeList(ctx, "X.b"); }           // ③ 대상 없이(this·super 포함) 불렀고, OrderStore 가 BaseDao 의 하위 타입이다
}
// ② 프로젝트 밖(jar) 메소드 com.acme.fw.BaseDao.executeList(...) 로 풀린 호출도 맞는다
```

#### 옛 리비전에서 `argIndex: 1` 이상이 안 맞을 때

첫 인자는 DECLARE가 원래 남기던 `arg_text`를, 둘째부터는 `args_json`을 쓴다. `args_json`은 분석기 1.1에서 생겼다. 그 전에 분석한 리비전은 DECLARE부터 다시 돌려야 한다.

### 3.5 screens: 리치클라이언트 화면 (WebSquare, Nexacro)

화면 스크립트가 서버를 주소가 아니라 **거래 ID**로 부르는 프로젝트를 위한 규칙이다. WebSquare 화면(`.xml`)과 Nexacro 화면(`.xfdl`)에 쓰인다.

**HI-Japan 화면의 실제 예** (`hi-japan/frontend.yml`)

| 키 | 화면 소스 | 규칙 | 결과 |
|---|---|---|---|
| `calls` | `HiJS.svr.doRequestAjax("JCST0200M01S", …)` | `{ function: doRequestAjax, method: "perform{id}" }` | 화면 → `performJCST0200M01S` 메소드 `REQUESTS` |
| `fields` | `<input type='hidden' name='tranId' value='JIMC1000M03S'/>` | `{ field: tranId, method: "perform{id}" }` | 화면 → `performJIMC1000M03S` `REQUESTS` |
| `opens` | `parent.scwin.fnOpenPage("JIMC1000G", …)` | `{ function: fnOpenPage, screen: "{id}.xml" }` | 화면 → `JIMC1000G.xml` `INCLUDES` |
| `menus` | `{'MENU_NM':'履行期間管理', …, 'SRC_PATH':'/ui/jc/JCIQ0700G.xml'}` | `{ nameKey: MENU_NM, pathKey: SRC_PATH }` | `JCIQ0700G.xml`의 화면명(`analysis_resource` `SCREEN_NAME`, via `MENU`) |

- 함수 이름은 **마지막 마디만** 적는다. `doRequestAjax`라고 적으면 `HiJS.svr.doRequestAjax`도 맞는다.
- 서버 메소드는 그 이름의 메소드가 있을 때만, 화면은 그 경로로 끝나는 화면이 **하나뿐일 때만** 잇는다.
- `menus`는 화면 파일에 제목이 없을 때 메뉴 목록에서 이름을 가져온다.

#### 인자 자리가 첫 번째가 아닐 때: `argIndex`

`calls`와 `opens`는 기본으로 첫 인자를 본다.

```yaml
screens:
  opens:
    - { function: fnOpenPage, screen: "{id}.xml" }                # fnOpenPage("JIMC1000G", …)
    - { function: fnOpenPage, screen: "{id}.xml", argIndex: 1 }   # fnOpenPage(param, "JIMC1000G", …)
```

- 같은 함수에 자리가 다른 규칙을 함께 둘 수 있다. 한 호출에 둘 다 맞으면 둘 다 본다.
- 인자는 짝이 맞는 닫는 괄호까지 나눈다. 문자열 속 쉼표, 중첩 괄호(`{mode: "a, b"}`, `f(x, y)`), 주석 속 쉼표는 나누는 곳으로 보지 않는다. 괄호 짝이 맞지 않으면 잇지 않는다.
- 그 자리의 인자가 **따옴표 글자 하나일 때만** ID로 쓴다. `fnOpenPage(screenId)`처럼 변수면 건너뛴다.
- "아무 자리나 화면 이름이면 잇는다"는 없다. 자리가 호출마다 다르면 자리마다 규칙을 적는다.
- 건너뛴 호출은 함수별로 센다. 다른 자리에 따옴표 글자가 있었으면 후보 API(`screenRules`)가 `argIndex` 규칙을 제안한다.

#### 거래 ID와 메소드 이름이 다를 때: ID 다듬기

`calls`, `fields`, `opens`에 쓸 수 있다. 적은 순서와 상관없이 **항상 아래 순서로** 다듬은 뒤 `{id}`에 넣는다.

| 순서 | 키 | 하는 일 | 맞지 않으면 |
|---|---|---|---|
| 1 | `idPattern` + `idReplace` | ID **전체**가 정규식에 맞으면 `$1`, `$2`로 바꾼다 | 이 규칙으로 잇지 않는다 |
| 2 | `idCase` | `UPPER` / `LOWER` / `UPPER_FIRST` / `LOWER_FIRST` | — |
| 3 | `idMap` | 규칙 폴더 안의 대응표에서 찾아 바꾼다 | 표에 없는 ID는 잇지 않는다 |

**예 1 — 정규식과 대소문자**

```javascript
callService("SVC_ORDER_LIST", param);     // 서버 메소드 이름은 svc_order_list
```

```yaml
- { function: callService, method: "{id}", idPattern: '^SVC_(.*)$', idReplace: 'svc_$1', idCase: LOWER }
```

`SVC_ORDER_LIST` → (1) `svc_ORDER_LIST` → (2) `svc_order_list` → `svc_order_list` 메소드와 잇는다.

**예 2 — 대응표**

```javascript
callTx("ORD001", param);
```

```yaml
- { function: callTx, method: "{id}", idMap: acme-order/tx-map.csv }
```

```text
# conf/rules/acme-order/tx-map.csv  — 한 줄에 "ID,값" ("=" 이나 탭도 된다), # 은 주석
ORD001,OrderAct.list
ORD002,com.acme.order.OrderAct.save
ORD003,cancelOrder
```

- 값이 `클래스.메소드`면 그 클래스(전체 이름이 같거나 그 이름으로 끝나는 것)의 메소드에만 잇는다. 메소드 이름만 적으면 그 이름의 메소드가 하나일 때 `HIGH`다.
- 대응표가 있는 `calls` 규칙은 표의 ID 하나하나를 **`TRANSACTION` 진입점**으로도 올린다(메소드가 하나로 정해질 때만). 프레임워크가 그 표를 보고 메소드를 부르기 때문이다.
- 대응표는 규칙 폴더 밖을 가리킬 수 없다. 대응표를 고치면 묶음의 해시도 바뀐다(5.2절).
- 대응표가 없는 규칙에서는 점이 든 값(`order.list`)을 메소드 이름으로 보지 않는다.

### 3.6 jpa: JPA와 Spring Data

핵심은 **엔티티 이름 → 테이블 이름**을 알아내 JPQL에 적힌 엔티티 이름을 테이블로 바꾸는 것이다.

**규칙** (`jpa.yml`)

```yaml
jpa:
  entities: [Entity]          # 엔티티 애노테이션. name 속성이 엔티티 이름(없으면 클래스 이름)
  tables: [Table]             # 테이블 이름 애노테이션(name 속성)
  naming: SNAKE_CASE          # @Table 이 없을 때: SNAKE_CASE(OrderItem → ORDER_ITEM) | AS_IS(ORDERITEM)
  queries:                    # 메소드에 붙은 쿼리. nativeAttribute 가 true 면 SQL, 아니면 JPQL
    - { annotation: Query, attribute: value, nativeAttribute: nativeQuery }
  namedQueries:               # 엔티티에 붙은 이름 있는 쿼리. container 안의 것도 읽는다
    - { annotation: NamedQuery, nameAttribute: name, attribute: query, container: NamedQueries }
    - { annotation: NamedNativeQuery, nameAttribute: name, attribute: query, container: NamedNativeQueries, native: true }
  repositories: [Repository, CrudRepository, ListCrudRepository, PagingAndSortingRepository, ListPagingAndSortingRepository, JpaRepository]
  jpqlCalls: [createQuery]    # 이 메소드에 넘긴 Java 문자열은 JPQL
```

**소스와 결과**

| 소스 | 결과 |
|---|---|
| `@Entity @Table(name="TB_ORDER") class Order` | 엔티티 `Order` → 테이블 `TB_ORDER` |
| `@Entity class OrderItem` (`@Table` 없음) | → 테이블 `ORDER_ITEM` (`SNAKE_CASE`) |
| `@Query("select o from Order o where o.status = ?1") List<Order> findActive(…)` | `analysis_mapper`(`JPA`, `language = JPQL`) + 메소드 `EXECUTES_SQL` + `READS_TABLE TB_ORDER` |
| `interface OrderRepository extends JpaRepository<Order, Long> { List<Order> findByName(String n); }` | `findByName`이 `TB_ORDER`를 읽는다(`DERIVED_QUERY`). `delete…`는 `WRITES_TABLE` |
| `em.createQuery("select c from Customer c")` | Java 문자열 SQL을 JPQL로 읽어 테이블로 바꾼다 |
| `em.createNamedQuery("Order.findAll")` | `jpa.yml`의 `callArguments`로 `@NamedQuery` statement와 잇는다 |

- `createNativeQuery`에 넘긴 문자열은 SQL 그대로 읽는다.
- `jpa.naming`은 여러 묶음에 있으면 먼저 오는(order가 작은) 묶음의 것을 쓴다. 아무도 적지 않으면 `SNAKE_CASE`다.
- JPA statement는 SEMANTIC이 돌 때마다 지우고 새로 만들어 `mapper_id`가 매번 바뀐다. 그래서 시험 적용(6.1절)을 하면 JPA 쪽 `EXECUTES_SQL`·`READS_TABLE`이 "같은 수만큼 없어지고 생긴" 것으로 보인다. 수(before/after)가 같으면 내용은 그대로다.

### 3.7 규칙 없이 코드가 하는 일

아래는 언어(Java)와 Spring 자체의 규칙이라 규칙 파일이 없다.

- **Java 문자열 SQL**: 메소드 안에서 `"SELECT …" + …`, `sql += …`, `sb.append(…)`, 같은 클래스의 상수로 만든 글이 SQL처럼 생겼으면 SQL statement(`mapper_type = JAVA`)가 되고 테이블과 이어진다. 그 글이 `jpa.jpqlCalls`의 메소드로 넘어가면 JPQL로 읽는다. 모르는 값은 `?`로 둔다.
- **주소 상수**와 **상위 타입 주소 물려받기**: 3.1절 ①.
- `main()`, JSP 진입점, `web.xml`·`@WebServlet`, `struts-config.xml`, MyBatis 매퍼 인터페이스 방식.

## 4. 어느 묶음이 쓰이고, 어떤 순서로 쓰이나

### 4.1 묶음 이름과 고르는 기준

파일 하나 = **규칙 묶음** 하나. **묶음 이름 = 규칙 폴더 안의 경로에서 확장자를 뺀 것**이다.

```text
conf/rules/
├─ java.yml            → java
├─ servlet.yml         → servlet
├─ spring.yml          → spring
├─ jpa.yml             → jpa
├─ mybatis.yml         → mybatis
├─ fallback.yml        → fallback
├─ hi-japan/
│  ├─ backend.yml      → hi-japan/backend
│  └─ frontend.yml     → hi-japan/frontend
└─ README.md           (YAML이 아니라 건너뛴다)
```

- `.yml`, `.yaml` 둘 다 읽는다. 같은 이름이 둘 다 있으면 오류다.
- 하위 폴더는 3단계까지 읽는다. 마디는 영문자·숫자·`-`·`_`·`.`로 60자 이내다. `.`으로 시작하는 폴더는 건너뛴다.
- 파일 안에 `name:`을 적으면 경로와 같아야 한다. 프로젝트의 `ruleSets`에 적는 이름이라 헷갈리지 않게 하려는 것이다.

분석할 때 서버는 묶음마다 세 가지를 물어 **하나라도 맞으면** 쓴다.

1. `autoApply`가 `true`인가? (바로 아래 파일은 기본 `true`, 하위 폴더 파일은 기본 `false`)
2. 묶음 이름의 첫 마디가 이 프로젝트 ID인가? (대소문자 무시)
3. 프로젝트의 `ruleSets`에 이 묶음 이름이나, 이 묶음이 든 폴더 이름을 적었나?

**예로 보기** — 프로젝트 세 개가 있을 때

| 묶음 | `HI-Japan` | `HI-Japan-batch` (`ruleSets: hi-japan`) | `hen` |
|---|---|---|---|
| `spring` (바로 아래) | 쓴다 ① | 쓴다 ① | 쓴다 ① |
| `hi-japan/backend` | 쓴다 ② 자기 폴더 | 쓴다 ③ 빌려 쓰기 | **안 쓴다** |
| `hi-japan/frontend` | 쓴다 ② | 쓴다 ③ | **안 쓴다** |

`hen`에서 `hi-japan/*`를 쓰지 않는 것이 핵심이다. A 프로젝트의 규칙이 B 프로젝트 분석에 끼어들지 않는다. 표본 프로젝트 `websquare-app`도 `ruleSets: hi-japan`으로 빌려 쓴다.

기본값을 바꾸고 싶으면:

- 하위 폴더 묶음을 **모든 프로젝트에** 쓰려면 → 그 파일에 `autoApply: true`
- 바로 아래 묶음을 **원하는 프로젝트에만** 쓰려면 → 그 파일에 `autoApply: false`, 쓸 프로젝트의 `ruleSets`에 이름을 적는다

`ruleSets`는 프로젝트를 등록하거나 고칠 때 쉼표나 공백으로 이어 적는다. 서버는 그 이름의 묶음(또는 폴더)이 있는지 먼저 보고, 없으면 등록을 거절하며 있는 묶음 목록을 알려 준다.

```json
POST /api/projects
{ "projectId": "HI-Japan-batch", "localPath": "/app/HI-Japan/batch", "ruleSets": "hi-japan" }
```

### 4.2 순서(order)가 결과를 바꾸는 곳: 계층

고른 묶음은 `order`가 작은 것부터, 같으면 이름 순으로 적용한다(적지 않으면 500).

| 묶음 | order |
|---|---|
| `java` | 100 |
| `servlet` | 150 |
| `spring` | 200 |
| `jpa` | 250 |
| `mybatis` | 300 |
| `hi-japan/backend`, `hi-japan/frontend`, 새로 만든 묶음 | 500 |
| `fallback` | 900 |

계층은 **먼저 정한 것을 뒤에서 바꾸지 않는다.** (모든 계층 UPDATE에 `AND layer IS NULL`이 붙어 있다. `SemanticDao.xml`의 `updateLayerBy…`)

예를 들어 `@Service @Component class OrderService`가 있다고 하자.

- `spring`(200)의 `Service` 규칙이 먼저 SERVICE로 정한다.
- `fallback`(900)의 `Component` → COMPONENT 규칙은 이미 정해졌으니 건드리지 않는다.

`@Component`처럼 뜻이 넓은 규칙을 `fallback.yml`에 두고 `order: 900`으로 맨 뒤에 돌리는 까닭이 이것이다. 다른 규칙이 정하지 못한 클래스에만 COMPONENT를 붙인다.

**단, `order`는 같은 종류의 키끼리만 순서를 정한다.** 계층은 키마다 맡은 플러그인이 따로 돌기 때문에 묶음 순서보다 키의 차례가 먼저다(8.5절).

```text
① layers.annotations (HIGH)  모든 묶음의 것을 order 순으로   ← fallback 의 @Component 도 여기
② layers.superTypes  (MEDIUM) 모든 묶음의 것을 order 순으로
③ layers.names       (LOW)    모든 묶음의 것을 order 순으로   ← fallback 의 이름 끝말 규칙
```

그래서 이런 일이 생긴다.

| 소스 | 결과 | 까닭 |
|---|---|---|
| `class OrderBiz extends BaseBiz` (`acme-order/backend`에 `BaseBiz` → SERVICE) | `SERVICE (MEDIUM)` | ②가 ③보다 먼저라, `fallback`의 `Biz$` 이름 규칙은 빈 자리가 없다 |
| `@Component class OrderAct extends BaseAction` | `COMPONENT (HIGH)` | ①의 `fallback` `Component` 규칙이 ②의 `BaseAction` 규칙보다 먼저 돈다. `order`를 줄여도 바뀌지 않는다 |

두 번째 경우를 바꾸려면 같은 키(`layers.annotations`) 안에서 `fallback`보다 먼저 정해야 한다. 다만 애노테이션 규칙은 그 애노테이션이 붙은 클래스 **모두**에 걸리므로, 프로젝트 폴더 묶음에서 그 프로젝트의 관례가 정말 그런지 확인하고 적는다.

같은 키 안의 순서는 이렇게 고른다. 공통 규칙(`spring` 200)보다 먼저 돌아야 하면 `order`를 200보다 작게, `fallback`(900)보다만 먼저면 기본값 500이면 된다.

## 5. 쓴 규칙의 기록과 바뀐 규칙 찾기

### 5.1 리비전마다 남는 기록 (RULE_SET)

분석할 때 쓴 묶음은 `analysis_resource`에 `RULE_SET` 행으로 남는다. 실제 `jpa-app` 리비전 106의 기록이다.

| `name` | `location`(파일) | `value`(해시) | `properties_json` |
|---|---|---|---|
| `java` | `java.yml` | `0110456611a0` | `{"order": 100, "rules": 2, "autoApply": true, "description": "…"}` |
| `servlet` | `servlet.yml` | `27b6246a7d94` | `{"order": 150, "rules": 2, …}` |
| `spring` | `spring.yml` | `d1e101cdfa89` | `{"order": 200, "rules": 12, …}` |
| `jpa` | `jpa.yml` | `a7eb986666a7` | `{"order": 250, "rules": 7, …}` |
| `mybatis` | `mybatis.yml` | `bc57c9fe1295` | `{"order": 300, "rules": 1, …}` |
| `fallback` | `fallback.yml` | `17b66719490a` | `{"order": 900, "rules": 10, …}` |

해시는 파일 내용의 SHA-256 앞 12자다. 화면 규칙이 대응표(`idMap`)를 쓰면 대응표 내용도 해시에 넣는다.

### 5.2 "이 리비전 분석 뒤에 규칙이 바뀌었나?"

`GET /api/revisions/{id}/rules`가 위 기록과 지금 파일을 해시로 견준다.

| `status` | 뜻 |
|---|---|
| `SAME` | 분석할 때와 같다 |
| `CHANGED` | 파일(또는 대응표) 내용이 바뀌었다 |
| `REMOVED` | 그때는 썼는데 지금은 안 쓴다(파일을 지웠거나 `ruleSets`에서 뺐다) |
| `ADDED` | 지금은 쓰는데 그때는 없었다 |

하나라도 `SAME`이 아니면 `upToDate: false`다. SEMANTIC부터 다시 돌려야 지금 규칙이 반영된다. 규칙 파일이 생기기 전에 분석한 리비전은 기록이 없어 모두 `ADDED`로 나오고, `note`가 그 이유를 알려 준다.

## 6. 새 관례를 규칙으로 만드는 순서 (실제 응답)

2장의 흐름을 API 기준으로 다시 정리한다.

```text
 처음 분석 ─▶ ① 적용 진단 ─▶ ② 후보 보기 ─▶ ③ 시험 적용 ─▶ ④ 파일로 저장 ─▶ ⑤ SEMANTIC 다시 돌리기
              (무엇이 비었나)  (무엇을 적을까)  (적으면 어떻게 되나)  (conf/rules/…)    (rerunFrom)
```

| API | 하는 일 |
|---|---|
| `GET /api/revisions/{id}/diagnostics` | 적용 진단. 무엇을 규칙으로 풀지 알려 준다 |
| `GET /api/revisions/{id}/rules/candidates?limit=20` | 규칙이 아직 모르는 관례의 흔적과 붙여 넣을 조각 |
| `POST /api/revisions/{id}/rules/trial?samples=30` | 시험 적용 후 되돌리기 |
| `GET /api/rules` | 폴더에 있는 묶음 목록(이름, order, autoApply, 파일, 해시, 규칙 수) |
| `GET /api/revisions/{id}/rules` | 분석 때 쓴 묶음과 지금 파일 비교(5.2절) |

화면에서는 Knowledge [프로젝트·분석] → 리비전 요약의 **적용 진단** 상자만 있다. 나머지는 지금 API로만 쓴다.

### 6.1 ① 적용 진단

항목마다 해결 방법이 붙는다.

| 값 | 뜻 |
|---|---|
| `RULE` | 규칙 파일로 푼다 |
| `CLASSPATH` | jar 위치를 알려 준다 |
| `SETTING` | 프로젝트 설정을 고친다 |
| `SOURCE` | 소스를 보충한다 |
| `DEVELOP` | 분석기를 고쳐야 한다 |
| `NONE` | 문제없다 |

실제 `hen` 리비전 102의 결과 일부다.

| 항목 | 해결 | 메시지(요약) |
|---|---|---|
| 호출 해석 | `NONE` | 메소드 호출의 98.19%가 누구를 부르는지 풀렸습니다 |
| 서버와 이어지지 않은 화면 | `RULE` | 화면 742개 가운데 335개는 서버의 무엇도 부르지 않습니다. 공통 함수에 거래 ID를 넘기는 프로젝트면 `screens.calls` 규칙을 … |
| 이름은 아는데 없는 SQL | `SOURCE` | 코드가 부르는 SQL 이름의 statement가 매퍼에 없습니다 … |
| 계층을 모르는 클래스 | `RULE` | 클래스 585개 가운데 64개는 계층을 정하지 못했고 18개는 이름 끝말로 짐작했습니다 … `layers.superTypes` … |
| 적용한 규칙 | `NONE` | 이 프로젝트 전용 규칙 폴더가 없습니다. 이 프로젝트에만 쓸 관례는 `conf/rules/hen/` 아래에 적습니다 |

규칙으로 되는 것과 안 되는 것의 경계는 [11.dstone-knowledge.md](11.dstone-knowledge.md) 4.7.6절 "지원 범위"에 있다.

### 6.2 ② 후보 보기

후보는 네 종류다.

| 키 | 무엇 |
|---|---|
| `callArguments` | 따옴표 글자를 인자로 받는 호출 가운데 그 글자가 이 프로젝트의 SQL 이름이나 JSP 화면 이름과 같은 것. 몇 번째 인자인지, RESOLVE가 가장 많이 푼 대상 타입도 함께 |
| `annotations` | 규칙이 모르는 애노테이션 가운데 많이 붙은 것. `unexplained`는 계층 없는 타입이나 진입점 아닌 메소드에 붙은 수 |
| `superTypes` | 규칙이 모르는 상위 타입 가운데 계층이 없거나 LOW인 하위 타입이 많은 것 |
| `screenRules` | 화면 규칙이 보는 자리가 글자가 아니어서 건너뛴 호출 가운데, 다른 자리에 따옴표 글자가 있던 것 → `argIndex` 제안. 예: `fnOpenPage(param, "JIMC1000G")` → `argIndex: 1` |

`GET /api/revisions/102/rules/candidates?limit=2`의 실제 응답 일부:

```json
"superTypes": [{
  "superType": "com.frameq.hhr.rules.HrRule",
  "inProject": true, "types": 5, "unlayered": 3,
  "samples": "HrRuleAnnual, HrRuleAppointment, HrRuleHoliday",
  "suggestion": "layers:\n  superTypes:\n    - { layer: <계층을 고르세요>, types: [com.frameq.hhr.rules.HrRule] }\n"
}]
```

`suggestion`의 계층과 진입점 종류는 짐작이라 **꼭 사람이 고친다.** Lombok·테스트·JSON 애노테이션처럼 뜻이 도구에 있는 것은 후보에서 뺀다.

### 6.3 ③ 시험 적용

규칙 묶음 글을 보내면 SEMANTIC을 **한 트랜잭션 안에서 실제로 돌려 보고** 전후를 비교한 뒤 **모두 되돌린다.**

```bash
curl -X POST localhost:4081/api/revisions/106/rules/trial -H 'Content-Type: application/json' \
  -d '{"ruleSet": "name: jpa-app/trial\nlayers:\n  names:\n    - { layer: CONFIG, pattern: \"^Urls$\" }\n"}'
```

실제 응답(요약):

```json
{
  "trialRuleSet": "jpa-app/trial",
  "ruleSets": ["java", "servlet", "spring", "jpa", "mybatis", "jpa-app/trial", "fallback"],
  "summary": [
    { "kind": "LAYER", "category": "CONFIG(LOW)", "before": 0, "after": 1, "added": 1, "removed": 0 },
    { "kind": "RELATION", "category": "EXECUTES_SQL(HIGH)", "before": 13, "after": 13, "added": 8, "removed": 8 }
  ],
  "added": [{ "kind": "LAYER", "category": "CONFIG(LOW)", "label": "com.shop.web.Urls = CONFIG(LOW)" }],
  "note": "시험 결과는 저장하지 않았습니다. 반영하려면 규칙 파일을 …/conf/rules 에 저장하고 rerunFrom=SEMANTIC 으로 다시 돌리세요."
}
```

이 응답 읽는 법:

- `ruleSets`: 시험 묶음(`order` 기본 500)이 `mybatis`(300)와 `fallback`(900) 사이에 끼었다. 그래서 `Urls`가 `fallback`의 이름 규칙보다 먼저 CONFIG가 됐다.
- `EXECUTES_SQL` 8개가 없어지고 생긴 것은 JPA statement를 다시 만들어서다(3.6절). before/after가 13으로 같으니 내용은 그대로다.

알아 둘 것:

- 시험 묶음에는 `name`이 꼭 있어야 한다. 같은 이름의 파일이 있으면 그 파일 대신 쓴다.
- 본문 없이 부르면 지금 파일 그대로 돌린다. "파일을 고쳤는데 다시 돌리면 무엇이 바뀌나"를 볼 때 쓴다.
- 그 프로젝트에 분석이 돌고 있으면 409다. 시험은 서버 전체에서 한 번에 하나만 돈다.
- 큰 프로젝트는 SEMANTIC 한 번만큼(수십 초~몇 분) 걸린다.

### 6.4 ④ 저장, ⑤ 반영

- 여러 프로젝트가 쓰는 관례 → `conf/rules/<이름>.yml`
- 한 프로젝트의 관례 → `conf/rules/<프로젝트ID>/<이름>.yml` (그 프로젝트에 저절로 쓰인다)

반영은 서버를 다시 띄우지 않고 SEMANTIC부터 다시 돌린다.

```json
POST /api/projects/{projectId}/analyses
{ "revisionLabel": "<같은 리비전 이름>", "rerunFrom": "SEMANTIC" }
```

| 서버가 뜨지 않고 `의미 분석 규칙 파일이 잘못 적혀 있습니다. <파일> <자리>: …` | 모르는 키(오타), 없는 계층 이름, 틀린 정규식, YAML 문법 오류 | 메시지의 파일·자리를 고친다 (아래 예) |
| `규칙 파일 폴더가 없습니다` | `rules-dir`·`APP_CONF_DIR`이 다른 곳을 가리킨다 | 8.1절의 순서로 폴더 위치를 확인한다 |
| `묶음 이름(…)은 규칙 폴더 안의 경로(…)와 같아야 합니다` | 파일을 옮기거나 이름을 바꾸면서 `name:`을 그대로 뒀다 | `name:`을 지우거나 경로와 맞춘다 |
| `HTTP 진입점 애노테이션 GetMapping 이(가) 규칙 묶음 spring 와 my-set 에 함께 있습니다` | 같은 애노테이션을 두 묶음에 적었다(같은 주소가 진입점으로 두 번 생긴다) | 한쪽에만 둔다. 분석 시작 때 나므로 그 분석이 실패한다 |
| 프로젝트 등록·분석에서 `규칙 묶음 X 이(가) 없습니다. 있는 묶음: […]` | `ruleSets`에 오타, 또는 파일을 지웠다 | 묶음 이름이나 폴더 이름을 맞춘다 |
| 규칙을 고쳤는데 결과가 그대로다 | SEMANTIC을 다시 돌리지 않았다 | `rerunFrom: "SEMANTIC"`. `GET /api/revisions/{id}/rules`의 `upToDate`로 확인한다 |
| 내 규칙의 계층이 안 붙는다 | 앞선 규칙이 이미 계층을 정했다(같은 키의 앞 묶음, 또는 더 앞 차례의 키) | 4.2절. 같은 키면 `order`를 줄이고, 애노테이션 규칙이 먼저 정했으면 키의 차례를 확인한다 |
| `argIndex: 1` 규칙이 옛 리비전에서 안 맞는다 | 분석기 1.1 전에 분석해 `args_json`이 비어 있다 | DECLARE부터 다시 분석한다 |
| 시험 적용이 409 | 그 프로젝트에 분석이 돌고 있다 | 끝난 뒤에 다시 한다 |
| 규칙에 맞는 호출인데 선이 안 생긴다 | 인자가 지역 변수·매개변수라 계산되지 않는다 | 의도된 동작이다(짐작하지 않는다). 3.4절 표 참고 |

**서버가 뜨지 않는 흔한 실수**

```yaml
layer:                                   # ✗ layers 의 오타 → 모르는 키
  annotations:
    - { layer: DAO, annotations: [Dao] } # ✗ DAO 는 없는 계층 → REPOSITORY
screens:
  calls:
    - { function: callTx, method: {id} } # ✗ { 로 시작하는 값은 따옴표로: "{id}"
    - { function: callSvc, method: "{id}", idPattern: '^SVC_(.*$', idReplace: 'x_$2' }
                                         # ✗ 괄호 짝이 틀린 정규식, 그룹이 하나뿐인데 $2
```

틀린 규칙을 모른 채 분석하면 결과가 조용히 비어 버린다. 그래서 일부러 서버가 뜨지 않게 크게 실패시킨다. 서버가 뜬 뒤 파일을 잘못 고치면 그 분석만 실패하고 서버는 그대로 돈다.

## 8. 백엔드 들여다보기

규칙 파일을 쓰기만 할 사람은 여기서부터 건너뛰어도 된다.

```text
 conf/rules/*.yml
      │
      ▼ ① 서버가 뜰 때      SemanticRuleRegistry.check()   모든 파일 검사. 틀리면 서버가 뜨지 않는다
      ▼ ② 프로젝트 등록 때  checkRuleSetNames()            ruleSets 에 적은 묶음이 있는지
      ▼ ③ SEMANTIC 시작     rulesFor()                     다시 읽기 → 고르기 → 정렬 → 하나로 합치기(SemanticRules)
      ▼ ④ 플러그인 17개     order 순으로 규칙을 꺼내 SQL 로 엮는다
      ▼ ⑤ 결과              analysis_endpoint / analysis_symbol.layer / analysis_relation / analysis_mapper
                            + 쓴 묶음 기록(analysis_resource RULE_SET)
```

### 8.1 규칙 폴더의 위치

`SemanticRuleRegistry.rulesDir()`가 아래 순서로 정한다.

1. `application.yml`의 `dstone.knowledge.semantic.rules-dir`
2. 없으면 시스템 속성 `APP_CONF_DIR` 아래 `rules` (보통 `/app/dstone/dstone-knowledge/conf/rules`)
3. `APP_CONF_DIR`도 없으면 작업 폴더의 `conf/rules`

폴더가 없으면 서버가 뜨지 않는다. 기본 규칙(java, spring, mybatis …)도 이 폴더에 있어서, 폴더가 없으면 진입점과 계층을 하나도 찾지 못하기 때문이다.

### 8.2 서버가 뜰 때: 전체 검사

`SemanticRuleRegistry`(Spring bean)의 `@PostConstruct check()`가 폴더 전체를 한 번 읽고 이렇게 남긴다.

```text
의미 분석 규칙 8묶음을 읽었습니다(/app/dstone/dstone-knowledge/conf/rules): java(2), servlet(2), spring(12), jpa(7), mybatis(1), hi-japan/backend(6), hi-japan/frontend(5), fallback(10)
```

괄호 안은 그 묶음의 규칙 수(`RuleSet.ruleCount()`)다. 파일 하나라도 틀리면 `IllegalStateException`으로 서버가 뜨지 않고, 메시지에 파일과 자리가 나온다.

### 8.3 파일 하나 읽기: RuleSetParser

`RuleSetParser.parse(text, fileName)`가 YAML 하나를 `RuleSet` 하나로 바꾼다.

1. SnakeYAML `SafeConstructor`로 읽는다(임의의 Java 객체를 만들지 않는다).
2. 맨 위 키는 `name`, `description`, `order`, `autoApply`, `endpoints`, `injects`, `proxies`, `layers`, `callArguments`, `screens`, `jpa`만 허락한다. 각 키 아래도 허락된 키 목록이 있다. 모르는 키는 오류다.
3. 값을 검사한다.

   | 무엇 | 검사 |
   |---|---|
   | 계층 | `CONTROLLER, SERVICE, REPOSITORY, MODEL, VIEW, CONFIG, WEB_FILTER, UTIL, EXCEPTION, BATCH, COMPONENT, ASPECT` 중 하나 |
   | 진입점 종류 | 영문 대문자로 시작, 대문자·숫자·`_`로 2~20자 |
   | 애노테이션 | `@` 없는 단순 이름(Java 식별자) |
   | 상위 타입, `receiverTypes` | 점으로 이은 전체 이름 |
   | HTTP 메소드 | 대문자 3~10자 |
   | 정규식 | 실제로 컴파일해 본다. `idReplace`의 `$n`이 그룹 수를 넘으면 오류 |
   | `argIndex` | 0~9 |
   | `idMap` 대응표 | 규칙 폴더 안에 있어야 한다 |

4. 목록 자리의 값 하나는 목록으로 바꾼다.
5. 해시를 만든다(5.1절).

### 8.4 분석할 때: 다시 읽고, 고르고, 합친다

```text
SemanticPass.run(context)
  │
  ├─ ruleRegistry.rulesFor({projectId, ruleSets})
  │     ├─ loadAll()            폴더를 다시 읽는다(고친 파일이 바로 반영되는 이유)
  │     ├─ ruleSets 이름 확인    없는 묶음이면 RuleException → 분석 실패
  │     ├─ 4.1절 기준으로 고르기
  │     ├─ order, 이름 순 정렬
  │     ├─ 옛 설정 키가 있으면 application-yml 묶음을 맨 뒤에(8.7절)
  │     └─ new SemanticRules(chosen)   ← 묶음들을 하나로 합친다
  │
  ├─ context.setSemanticRules(rules)  ← 플러그인들이 여기서 꺼내 쓴다
  │
  └─ 한 트랜잭션 안에서 runPlugins(context)
        ├─ semanticDao.clear(revisionId)   전에 만든 SEMANTIC 결과를 지운다(다시 돌려도 결과가 같다)
        ├─ recordRuleSets()                쓴 묶음을 RULE_SET 행으로 남긴다
        └─ 플러그인을 order 순으로 하나씩 run()
```

한 트랜잭션이라 도중에 실패하면 지운 것까지 되돌아간다.

**합치는 방법 (`SemanticRules` 생성자)**

- 대부분의 규칙은 묶음 순서대로 이어 붙인다. 애노테이션 이름 같은 집합은 중복을 없앤다.
- 같은 HTTP 애노테이션이 두 묶음에 있으면 오류다. 진입점 애노테이션(`endpoints.annotations`)도 `종류/애노테이션` 단위로 같은 검사를 한다.
- 화면 규칙은 같은 함수·틀·자리·다듬기가 겹치면 하나만 남긴다. 호출 규칙(`calls`) 뒤에 폼 필드 규칙(`fields`)을 붙인다.
- `jpa.naming`은 먼저 오는 묶음의 것을 쓴다. 아무도 적지 않으면 `SNAKE_CASE`.

### 8.5 규칙을 꺼내 쓰는 플러그인

`SemanticPlugin` bean 17개가 `order()` 순으로 돈다. 규칙을 쓰는 것은 그중 11개다.

| order | 플러그인 | 꺼내 쓰는 규칙 | 만드는 것 |
|---|---|---|---|
| 100 | `SpringPlugin` (+`HttpEndpointBuilder`) | `endpoints.http`, `endpoints.annotations`, `injects`, `proxies`, `layers.annotations` | HTTP·스케줄·리스너 진입점, 애노테이션 계층(HIGH), INJECTS, `proxy_related` |
| 200 | `ServletPlugin` | (코드) | web.xml·`@WebServlet` 진입점 |
| 250 | `StrutsPlugin` | (코드) | `struts-config.xml` 액션 진입점 |
| 260 | `XmlEndpointPlugin` | `endpoints.xml` | 설정 XML의 진입점(거래 ID 등) |
| 300 | `PlainJavaPlugin` | `endpoints.superTypes` | `main()`(코드), 상위 타입으로 정한 진입점 |
| 390 | `JpaPlugin` | `jpa.*` | JPA statement(`mapper_type = JPA`), EXECUTES_SQL, 테이블 관계 |
| 400 | `MyBatisPlugin` | `callArguments`(target `SQL`) | 매퍼 인터페이스(코드), 호출 인자로 찾은 EXECUTES_SQL |
| 410 | `JavaSqlPlugin` | `jpa.jpqlCalls`(+ 엔티티 정보) | Java 문자열 SQL의 EXECUTES_SQL과 테이블 관계 |
| 500 | `JspPlugin` | `callArguments`(target `VIEW`) | JSP 진입점(코드), RENDERS |
| 510 | `RichClientPlugin` | `screens.calls`, `screens.fields`, `screens.opens` | 화면의 REQUESTS·INCLUDES, TRANSACTION 진입점 |
| 520 | `ScreenMenuPlugin` | `screens.menus` | 화면 한글명(SCREEN_NAME) |
| 800 | `ConfiguredLayerPlugin` | `layers.superTypes` | 상위 타입 계층(MEDIUM) |
| 900 | `NamingLayerPlugin` | `layers.names` | 이름 계층(LOW) |
| 950~980 | `SourceNamePlugin`, `MethodTitlePlugin`, `ScreenDictionaryPlugin`, `TableDictionaryPlugin` | (규칙 안 씀) | 한글명, 메소드 제목, 사전 |

순서의 까닭:

- `JpaPlugin`(390)이 `@NamedQuery` statement를 먼저 만들어야 `MyBatisPlugin`(400)이 `em.createNamedQuery("Order.findAll")`을 이을 수 있다.
- 계층은 애노테이션(100, HIGH) → 상위 타입(800, MEDIUM) → 이름(900, LOW) 순이다. 확실한 것부터 정하고 나중 것은 빈 자리만 채운다.
- `HttpEndpointBuilder`는 상위 클래스 주소를 물려줄 컨트롤러를 고를 때 `layers.annotations`의 CONTROLLER 계층을 본다. 그래서 `SpringPlugin` 안에서 계층을 진입점보다 먼저 계산한다.

플러그인은 **Java를 다시 파싱하지 않는다.** DECLARE가 넣어 둔 `analysis_annotation`, `analysis_reference`(호출 이름, `arg_text`, `args_json`)와 RESOLVE가 만든 `analysis_relation`을 규칙 값으로 SQL을 만들어 엮는다. 그래서 큰 프로젝트에서도 SEMANTIC은 금방 끝난다. 예외는 설정 XML(`XmlEndpointReader`)과 화면 파일을 읽는 플러그인이다.

`callArguments`를 처리하는 순서(`MyBatisPlugin`, `JspPlugin`):

1. `analysis_reference`에서 규칙의 메소드·생성자 이름과 같은 호출(`ref_kind = CALL`/`CREATE`)을 꺼낸다.
2. `argIndex` 자리의 인자를 얻는다(`arg_text` 또는 `args_json`).
3. `ConstantEvaluator`로 값을 계산한다(3.4절 표).
4. `exclude`로 거르고 `template`을 씌운다.
5. statement나 JSP를 찾아 잇는다(`properties_json.via = STATEMENT_NAME`). 못 찾으면 3.4절의 규칙대로 `UNRESOLVED`로 남기거나 버린다.
6. `receiverTypes`가 있으면 호출 대상을 확인한다.

시험 적용(`RuleService.trial`)의 처리: 트랜잭션을 열고 `setRollbackOnly()` → `RuleDao.createBeforeFacts` → `SemanticPass.runPlugins` → `RuleDao.createAfterFacts` → 차이 조회 → 롤백. 메소드가 `synchronized`라 서버 전체에서 한 번에 하나만 돈다.

### 8.7 옛 설정 키

예전에는 `application.yml`의 `dstone.knowledge.semantic.screen.call-rules` / `field-rules` / `open-rules` / `menu-rules`와 `dstone.knowledge.semantic.layer.super-types`에 규칙을 적었다. 그 값은 지금 `hi-japan/frontend.yml`, `hi-japan/backend.yml`로 옮겼다. 이 키가 남아 있으면 `application-yml`이라는 묶음으로 바꿔 **맨 뒤에** 붙여 쓰고 경고를 남긴다. 옛 설정 때문에 갑자기 서버가 못 뜨는 일이 없도록, 이 묶음만은 잘못 적힌 항목을 버리고 너그럽게 읽는다.
