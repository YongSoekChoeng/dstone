# dstone-ai-engine — 평가 사례 만들기와 교훈 남기기

Agent가 실수했을 때 그 장면을 **평가 사례**로 저장하고, 고친 뒤 같은 문제를 다시 풀려 **교훈**을 남기는 방법을 설명한다.

- 대상: Workflow를 운영하면서 Agent 정의, Skill, 모델, 엔진을 손보는 사람
- 관련 문서: [`09.dstone-ai-engine.md`](09.dstone-ai-engine.md) 15장(요약), `.claude/docs/ai-engine-agent-principles.md`(Agent를 고치는 원칙)
- 코드: `net.dstone.ai.runtime.eval` (`EvalCase`, `EvalCaseBuilder`, `EvalRunner`, `EvalWorkspace`)

## 1. 한눈에 보기

```
① 실행에서 실수를 발견
        │
② 실행 관리 > 진행 기록 > [평가 사례로 만들기]
        │   그때의 입력 + 작업 폴더 + 채점 기준
③ [그때 결과로 미리 채점]  → 핵심 기준이 ✗ 여야 한다 (LLM 호출 없음)
        │
④ Agent 평가 화면에서 3번 실행        = 기준선
        │
⑤ 실패 원인 분류 → 한 가지만 고침 (Agent 버전을 올린다)
        │
⑥ 같은 사례를 3번 실행               = 고친 뒤
        │
⑦ 비교 표를 보고 교훈을 적는다        → 문서 / Skill / 엔진
```

**평가 기능은 교훈을 자동으로 만들지 않는다.** 엔진이 해 주는 일은 같은 문제를 다시 풀리고 채점해 숫자를 남기는 데까지다. 원인을 판단하고 어디를 고칠지 정해 글로 남기는 일은 사람이 한다(8장).

## 2. 먼저 알아 둘 말

| 말 | 뜻 | 남는 곳 |
|---|---|---|
| 스냅숏 | Agent step이 돌 때 엔진이 자동으로 떠 두는 입력, 파일, 답, Tool 횟수 | `{APP_HOME}/LOGS/dstone-ai-engine/snapshot/` |
| 평가 사례 | 스냅숏에 채점 기준을 붙여 고정한 문제 | `conf/eval/{프로젝트ID}/` |
| 채점 기준(check) | "이 파일에 이 글자가 있어야 한다" 같은 판정 하나 | 사례 파일 `checks:` |
| 미리 채점 | 그때 결과로 채점해 기준이 쓸 만한지 보는 것 | 저장하지 않음 |
| 평가 실행 | LLM에게 사례를 실제로 다시 풀리는 것 | DB `AI_EVAL_RUN` |
| 기준선 | 고치기 **전** 정의로 돌린 평가 결과 | DB `AI_EVAL_RUN` |
| 교훈 | 왜 실패했고 무엇을 바꿔 얼마나 나아졌는지 적은 기록 | 사람이 적는 문서(8장) |

사례에는 두 종류가 있다.

| | Agent 사례 | Workflow 사례 |
|---|---|---|
| 재는 것 | Agent 하나의 한 회차 | 요청서부터 흐름 전체 |
| 만드는 단추 | 진행 기록의 [평가 사례로 만들기] | 실행 머리의 [Workflow 평가 사례로 만들기] |
| 시간과 비용 | 작음 | 큼 |
| 모델 바꿔 보기 | 가능 | 불가(각 Agent 정의의 모델) |
| 언제 | **대부분 이것** | 고친 효과가 최종 결과물까지 닿는지 볼 때 |

## 3. 시작하기 전 확인

| 확인 | 설명 |
|---|---|
| 스냅숏이 켜져 있는가 | `dstone.ai.workflow.snapshot.enabled: true`(기본) |
| 스냅숏이 남아 있는가 | `retention-days: 30`(기본). **30일이 지나면 지워지므로 실수를 보면 바로 사례를 만든다** |
| DB 테이블 | `AI_EVAL_RUN`(`schema/02-create-table-postgresql-dstone-ai.sql`) |
| 권한 | 사례 **저장**은 관리자만. 메뉴 "Agent 평가"도 권한이 필요하다 |
| 어느 `conf`를 쓰는가 | 사례는 **엔진이 도는 곳**의 `{APP_CONF_DIR}/eval`에 저장된다. 편집하는 저장소와 엔진이 읽는 폴더가 다르면 정의를 고친 뒤 동기화해야 한다 |
| git | `conf/eval`은 git에 올리지 않는다. 지우면 되살릴 수 없으니 중요한 사례는 따로 백업한다 |

스냅숏은 `AGENT`, `SUPERVISOR` step에만 남는다. `TOOL`, `ROUTER`, `APPROVAL`, `forEach` step에는 없다.

## 4. 따라 하기: 실패 하나를 교훈까지

예로 쓰는 상황이다. 이름은 모두 가상이다.

> 개발 Agent에게 "일정표 화면에서 예약 시간만큼 칸을 합쳐 보여 달라"고 여러 번 요청했다.
> Agent는 칸 사이 테두리만 지웠고 화면은 계속 나뉘어 보였다. 검증 Agent는 PASS를 냈다.

### 4.1 문제의 회차를 찾는다

1. 화면 **실행 관리**에서 실행을 연다.
2. **진행 기록**에서 실수한 Agent의 줄을 찾는다. 같은 step이 여러 번 돌았으면 **시각**과 그 직전 승인 의견으로 고른다.
3. 고를 회차는 **실수가 처음 드러난 회차**나 지시를 분명히 받고도 틀린 회차가 좋다. 이미 고쳐진 회차는 사례가 되지 못한다.

### 4.2 사례를 만든다

그 줄을 고르고 **[평가 사례로 만들기]** 를 누른다. 대화상자를 이렇게 채운다.

| 칸 | 예 |
|---|---|
| 사례 id | `dev-merge-cells` (영문 소문자, 숫자, 하이픈) |
| 프로젝트 | `myApp` |
| 설명 | 일정표의 이어진 예약 칸을 하나로 합치는가. 테두리만 지우면 실패 |
| 그때 일 | 같은 요청을 4번 받고도 테두리와 배경색만 바꿨다. 검증은 PASS였다 |
| 작업 폴더 | `base_dir` (Agent가 파일을 읽고 쓴 입력 폴더) |

설명은 다음 승인 의견에서 자동으로 채워진다. 석 달 뒤에 읽어도 **무엇을 재는지** 알 수 있게 고쳐 쓴다.

### 4.3 채점 기준을 넣는다

**[+ 기준 추가]** 를 눌러 1~3개를 만든다.

| 순서 | ① 무엇이 잘못됐나 | ② 어디 | ③ 어떤 모양 |
|---|---|---|---|
| 기본 | 파일을 안 만들었다·안 고쳤다 | `dev-resources/…/schedule.jsp` | 처음과 달라져 있어야 함 |
| 핵심 | 파일에 꼭 들어가야 할 내용이 빠졌다 | 같은 파일 | 찾을 글자 `colspan` |
| 핵심 | 확인하지 않고 추측했다 | Tool `knowledgeSearchDocs` | 최소 1번 |

파일 경로는 **작업 폴더 기준 상대 경로**다. 입력 칸에서 후보가 자동 완성된다.

### 4.4 미리 채점한다

**[그때 결과로 미리 채점]** 을 누른다. LLM을 부르지 않으므로 비용이 없다.

| 기준 종류 | 그때 결과가 | 판정 |
|---|---|---|
| 핵심 | ✗ 실패 | 정상. 그때 실수를 잡는다 |
| 핵심 | ✓ 통과 | 너무 느슨하다. 기준을 고친다 |
| 기본 | ✓ 통과 | 정상 |
| 기본 | ✗ 실패 | 그때 결과물이 없었다. 의도한 것이면 둔다 |

핵심 기준이 모두 ✗이면 **[저장]** 한다. `conf/eval/myApp/dev-merge-cells.eval.yml`과 자료 폴더가 생긴다.

### 4.5 저장한 사례 파일을 한 번 연다

```bash
cd {APP_CONF_DIR}/eval/myApp
cat dev-merge-cells.eval.yml
grep -rnE '[A-Za-z]:[\\/]|/(home|app|mnt)/' dev-merge-cells*     # 남은 절대경로 찾기
```

화면은 **작업 폴더**와 **프로젝트 관리의 소스 폴더**, 프로젝트 ID만 자리(`${…}`)로 바꾼다. 다른 절대경로가 남을 수 있다.

| 남은 경로 | 위험 | 조치 |
|---|---|---|
| 실제 작업 폴더의 다른 하위 경로나 다른 실행 폴더 | 평가가 **실제 산출물을 고칠 수 있다** | `${workDir}`로 바꾼다 |
| 리비전 폴더(`…/rev/<해시>/src`) 같은 소스 위치 | 리비전이 정리되면 사례가 깨진다 | `params.sourceDir`를 만들고 `${param.sourceDir}`로 바꾼다 |

### 4.6 기준선을 돌린다

1. 메뉴 **Agent 평가**를 연다.
2. 사례를 고른다.
3. 모델은 비우고 **반복 3번**으로 **[평가 시작]** 을 누른다.
4. 끝나면 **비교** 표를 본다. 예:

| 사례 | 대상 버전 | 횟수 | 채점 평균 | 전부 통과 |
|---|---|---|---|---|
| dev-merge-cells | 1.4.0 | 3 | 33% | 0/3 |

기준선이 3번 다 통과하면 사례가 실패를 재현하지 못한 것이다. 우연이었거나 기준이 느슨하다. 6장을 보고 사례부터 고친다.

### 4.7 원인을 분류하고 한 가지만 고친다

결과를 눌러 **평가 상세**의 채점, Tool 요청, 답, 작업 폴더를 본다. 8.1절 표로 실패 종류를 정한다.

예: "문서를 찾지 않고 추측했다" → 증상이 다시 보고된 회차에 쓰는 방법의 문제다. 여러 Agent가 겪을 일이므로 Skill에 적는다.

```markdown
## 같은 증상이 다시 보고됐을 때
지난번과 같은 방법으로 다시 고치지 않는다. 지난 수정이 화면에 왜 효과가 없었는지 먼저 설명하고,
프로젝트 안내에 참고 문서가 있으면 그 기능의 지원 방식을 찾아본 뒤 방법을 정한다.
```

**Agent 정의의 `version`을 올린다.** Skill이나 엔진만 고쳤어도 올린다. 비교 표는 (사례, 대상 버전, 모델)로 묶으므로 버전이 같으면 전후가 한 줄로 섞인다.

```yaml
version: 1.5.0   # 1.4.0 → 1.5.0 : 재보고된 증상의 조사 방법을 Skill에 추가
```

### 4.8 다시 돌려 비교한다

같은 사례를 같은 모델로 3번 돌린다.

| 사례 | 대상 버전 | 횟수 | 채점 평균 | 전부 통과 | Tool 평균 | 입력 토큰 평균 |
|---|---|---|---|---|---|---|
| dev-merge-cells | 1.4.0 | 3 | 33% | 0/3 | 19 | 780,000 |
| dev-merge-cells | 1.5.0 | 3 | 89% | 2/3 | 23 | 910,000 |

(숫자는 설명용 예시다.)

### 4.9 교훈을 적는다

8.3절 양식으로 남긴다. 끝이다.

## 5. 사례 만들기 화면

### 5.1 Agent 사례

| 화면의 값 | 저장되는 것 |
|---|---|
| 그 회차의 Agent 입력 | `input:`. 300자를 넘거나 여러 줄이면 `input/{이름}.txt`로 빼고 `${fixture:…}`로 읽는다 |
| 고른 작업 폴더 | step이 **시작할 때**의 내용이 `work/`가 된다 |
| 작업 폴더 경로 | `${workDir}` |
| 프로젝트 소스 폴더 | `${param.sourceDir}` |
| 프로젝트 ID | `${param.projectId}` |
| 그때 일 | 사례 파일 머리의 주석 |

- 폴더가 너무 크면(기본 20MB, 3000개) 스냅숏에 복사되지 않는다. 그 폴더는 작업 폴더로 고를 수 없다.
- 실행이 끝난 뒤의 작업 폴더로 사례를 손수 만들지 않는다. 뒤 step이 파일을 고쳤으므로 다른 장면을 시험하게 된다.

### 5.2 Workflow 사례

- 실행을 시작할 때의 요청 폴더(`_start` 스냅숏)가 `work/`가 된다.
- 사람의 승인 결정이 `approvals:`가 된다. **같은 승인 step을 여러 번 정했으면 마지막 결정만** 남는다.

> **저장한 뒤 `approvals`를 꼭 확인한다.** 평가는 그 승인에 도착할 때마다 같은 결정을 넣는다.
> 마지막 결정이 "재개발"처럼 뒤로 돌아가는 것이면 `workflow-max-steps`(기본 300)까지 계속 돌아 비용이 든다.
> 그 줄을 지우면 평가가 그 승인에서 멈추고 채점한다. 승인 의견(글)은 평가에 전달되지 않는다.

### 5.3 화면에서 고르는 증상

| ① 무엇이 잘못됐나 | 만들어지는 채점 |
|---|---|
| 파일을 안 만들었다·안 고쳤다 | `fileExists`(기본) / `fileChanged` |
| 파일에 잘못된 내용이 들어갔다 | `fileNotMatches` |
| 파일에 꼭 들어가야 할 내용이 빠졌다 | `fileContains` / `fileMatches` |
| 판정·답이 틀렸다 | `answerNotMatches` / `answerContains` / `answerMatches` / `answerEquals` |
| 답(칸)을 비워 냈다 | `answerNotEmpty`(기본) |
| 확인하지 않고 추측했다 | `toolUsed` |
| 만든 기능이 동작하지 않는다 | 화면에서 못 만든다. `http`, `dbQuery`를 파일에 직접 쓴다 |

"찾을 글자"에 A와 B를 적으면 "A 뒤에 B가 나오는 곳"을 찾는다. "항목 하나 안에서만"은 목록의 다음 항목으로, "같은 줄 안에서만"은 다음 줄로 넘어가지 않게 한다.

## 6. 좋은 채점 기준

### 6.1 원칙

1. **결과를 본다.** 방법이 여럿이면 특정 구현 글자에 묶지 않는다.
2. **그때 실수는 ✗, 올바른 답은 ✓** 가 되는지 양쪽에 맞춰 본다.
3. **1~3개면 충분하다.** 많으면 점수의 뜻이 흐려진다.
4. **산출물 확인을 하나 넣는다.** `fileExists`나 `answerNotEmpty`가 실패하면 다른 점수는 의미가 없다.
5. **문장 전체를 찾지 않는다.** 틀림을 가르는 짧은 글자만 쓴다. LLM은 매번 다르게 쓴다.

### 6.2 나쁜 기준과 고친 기준

| 나쁜 기준 | 왜 | 고친 기준 |
|---|---|---|
| `fileContains: "병합"` | 주석에 낱말만 써도 통과 | `fileMatches`로 `colspan`을 설정하는 코드 모양 |
| `fileContains: "$(tds[i]).attr(\"colspan\", span);"` | 변수 이름만 달라도 실패 | 정규식 `attr\(\s*["']colspan` |
| `answerContains: "FAIL"` | 다른 항목의 FAIL로 통과 | 해당 항목 안에서 `result=FAIL` |
| `answerNotMatches`만 하나 | 그 항목을 빼먹어도 통과 | `answerMatches`로 항목이 있음을 함께 확인 |
| `toolUsed: dbQuery`만 하나 | 부르기만 하면 통과 | 결과를 보는 기준과 함께 |

### 6.3 놓치기 쉬운 함정

| 함정 | 결과 |
|---|---|
| `answerNotMatches`의 `field` 이름을 잘못 씀 | 빈 글자에서 못 찾으므로 **항상 통과** |
| 정규식이 목록의 다음 항목까지 넘어감 | 헛통과, 헛실패 |
| 답의 목록·맵은 `{id=…, task=…, result=PASS}` 모양의 글자로 바뀜 | JSON 모양(`"result":"PASS"`)으로 쓰면 못 찾음 |
| 항목의 칸 순서는 LLM이 답한 순서를 따름 | 순서를 가정한 정규식은 실제 답으로 확인 |
| 대소문자를 가림 | `colSpan`과 `colspan`은 다름. `(?i)`로 무시 |
| `fileNotMatches`는 파일이 없으면 실패 | 의도한 동작 |
| `toolUsed`는 이름의 **앞부분**이 맞으면 셈 | `db`라고 쓰면 모든 `db…` Tool이 셈 |

## 7. 평가 돌리고 결과 읽기

### 7.1 시작

| 칸 | 설명 |
|---|---|
| params | 사례의 `params` 값. 환경이 다르면 여기서 바꾼다 |
| 모델 | 비우면 Agent·provider 기본 모델. 모델 비교를 할 때만 적는다 |
| 반복 | 1~5. 결과가 매번 다르므로 **3번 이상** |

평가는 기본적으로 한 번에 하나씩 돈다(`dstone.ai.eval.threads`). 엔진이 다시 뜨면 돌던 평가는 FAILED가 된다.

### 7.2 결과 목록과 상세

| 항목 | 읽는 법 |
|---|---|
| 상태 `DONE` | Agent가 끝까지 답했다. **통과라는 뜻이 아니다** |
| 상태 `FAILED` | Agent 호출이나 준비가 실패했다. 실패 사유를 본다. 채점은 그래도 한다 |
| 채점 `2/3` | 기준 3개 중 2개 통과. Workflow 사례는 "떠 둔 결과 → 마지막" |
| LLM 회차, Tool | 같은 점수라면 적을수록 낫다 |
| 작업 폴더 | Agent가 만든 파일이 남는다. **점수만 보지 말고 한 번은 연다** |

### 7.3 비교해서 판단하기

| 전 → 후 | 판단 |
|---|---|
| 33% → 89% | 효과 있음. 남은 실패를 열어 본다 |
| 33% → 44% | 차이가 우연일 수 있다. 3~5번 더 돌린다 |
| 100% → 100% | 사례가 전후를 가르지 못한다. 기준을 조이거나 다른 회차로 만든다 |
| 점수는 같고 토큰·시간 증가 | 고친 것이 비용만 늘렸다. 되돌린다 |
| 이 사례는 오르고 다른 사례는 내림 | 다른 일을 망가뜨렸다. 범위를 좁힌다 |

정의를 크게 바꾸면 **그 Agent의 다른 사례도** 함께 돌린다.

> 채점 기준을 바꾸면 이전 점수와 비교할 수 없다. 바꾼 뒤에는 기준선부터 다시 돌리거나 새 id의 사례로 만든다.

## 8. 교훈 남기기

### 8.1 실패를 먼저 분류한다

| 실패 종류 | 확인하는 법 | 고칠 곳 |
|---|---|---|
| 기계적으로 보장할 수 있음(저장, 횟수, 값 전달) | 코드면 항상 지킬 수 있는 일인가 | 엔진(Java) |
| 필요한 정보를 못 받음 | 상세의 입력에 그 정보가 없다 | Workflow의 `with`, TOOL step |
| 도구가 불편함 | 같은 Tool을 잘게 여러 번 부른다 | 범용 Tool |
| 성격이 다른 일을 함께 시킴 | 한 일을 하면 다른 일이 무너진다 | Workflow 구조(Agent 분리) |
| 여러 Agent가 쓸 방법을 모름 | 다른 Agent도 같은 실수를 한다 | Skill |
| 모델 능력 | 같은 사례를 다른 모델은 푼다 | 모델 선택 |
| 판단 기준이 모호함 | 위가 모두 아니다 | 프롬프트 |

위쪽에서 고칠 수 있으면 위쪽에서 고친다. 프롬프트에 한 줄 더하는 것은 마지막이다.

### 8.2 교훈을 둘 곳

| 교훈의 범위 | 둘 곳 | git |
|---|---|---|
| 어느 프로젝트에서나 맞는 방법 | 범용 Skill(`skills/…/SKILL.md`) | 올림 |
| 그 프로젝트의 관례 | `skills/projects/{프로젝트ID}/` | 올림 |
| 다시 나오면 안 되는 실수 | 평가 사례 | 올리지 않음 |
| 고친 이력과 이유 | Agent 정의 머리의 버전 주석 | 올림 |
| 측정 결과(전후 숫자) | `.claude/docs/ai-engine-tuning.md` | 올림 |

범용 Skill과 엔진에는 특정 앱의 이름이나 경로를 적지 않는다.

### 8.3 교훈 기록 양식

```markdown
## YYYY-MM-DD <한 줄 제목>

- 증상: 사람이 무엇을 봤는가
- 사례: <사례 id> (실행 <실행 ID>, <step> <회차>)
- 실패 종류: 8.1 표의 하나
- 원인: 로그와 결과에서 확인한 것 (추정은 '추정'이라고 쓴다)
- 바꾼 것: 파일과 버전
- 측정:
  | 버전 | 횟수 | 채점 평균 | 전부 통과 | 시간 | 입력 토큰 |
- 남은 것: 아직 실패하는 경우
- 일반화: 다음에 비슷한 일이 생기면 무엇부터 볼까
```

### 8.4 교훈 기록 샘플

세 건 모두 설명용 예시다.

**① 방법의 문제 → Skill**

```markdown
## 2026-01-10 같은 증상을 같은 방법으로 반복해서 고침

- 증상: 일정표 칸 병합을 네 번 요청했는데 계속 나뉘어 보임
- 사례: dev-merge-cells
- 실패 종류: 여러 Agent가 쓸 방법을 모름
- 원인: 설계서의 "빈 배경으로 이어 보이게"를 그대로 믿고 테두리만 바꿈. 문서 검색 0회
- 바꾼 것: 재보고된 증상의 조사 순서를 troubleshooting Skill에 추가, 개발 Agent 1.4.0 → 1.5.0
- 측정: 33% → 89% (각 3회)
- 남은 것: 1회는 문서를 찾고도 CSS로 해결하려 함
- 일반화: 같은 증상이 두 번 오면 지난 방법을 버리는 근거부터 요구한다
```

**② 검증의 문제 → 판정 규칙**

```markdown
## 2026-01-12 화면 모양을 글자만 보고 PASS

- 증상: 칸이 나뉘어 있는데 검증이 PASS
- 사례: verify-merge-cells
- 실패 종류: 필요한 정보를 못 받음
- 원인: 접근성 스냅숏에는 글자만 있고 칸의 폭과 병합 여부가 없음
- 바꾼 것: 모양 기준은 확인할 수단이 없으면 BLOCKED로 내고 사람이 볼 항목을 remedy에 적게 함
- 측정: 0% → 100% (각 3회)
- 남은 것: 모양을 읽는 범용 도구는 없음
- 일반화: PASS의 근거가 기준을 실제로 증명하는지 본다
```

**③ 엔진의 문제 → Workflow**

```markdown
## 2026-01-15 코드를 바꾸지 않은 재개발이 검증까지 감

- 증상: "이미 구현됨"이라 답하고 파일은 그대로인데 서버를 띄워 검증함
- 사례: dev-noop-redevelop
- 실패 종류: 기계적으로 보장할 수 있음
- 원인: 바뀐 파일이 없는지 확인하는 단계가 없음
- 바꾼 것: 개발 전후의 파일을 견주는 TOOL step 추가. 프롬프트는 그대로
- 측정: Workflow 사례에서 헛검증 0건
- 일반화: 부탁보다 확인 단계가 확실하다
```

## 9. 샘플 모음

파일 이름은 `id`와 같아야 한다. 값은 자기 프로젝트에 맞춘다.

### 9.1 개발 Agent — 파일을 제대로 고쳤나

`conf/eval/myApp/dev-merge-cells.eval.yml`

```yaml
# 같은 요청을 4번 받고도 테두리와 배경색만 바꾼 회차
id: dev-merge-cells
description: 일정표의 이어진 예약 칸을 하나로 합치는가. 테두리만 지우면 실패
agent: sm-developer-agent
fixture: myApp/dev-merge-cells
params:
  projectId: myApp
  sourceDir: /app/myApp
input:
  project_id: ${param.projectId}
  base_dir: ${workDir}
  source_dir: ${param.sourceDir}
  request: ${fixture:input/request.txt}
  design: ${fixture:input/design.txt}
  taskitems: ${fixture:input/taskitems.txt}
  instruction: ${fixture:input/instruction.txt}
  history: ${fixture:input/history.txt}
checks:
  - name: 화면 파일을 고침
    fileChanged: dev-resources/src/main/webapp/WEB-INF/views/schedule/schedule.jsp
  - name: 칸을 colspan으로 합침
    fileMatches:
      file: dev-resources/src/main/webapp/WEB-INF/views/schedule/schedule.jsp
      pattern: '(?i)(attr\(\s*["'']colspan|\.colSpan\s*=|setAttribute\(\s*["'']colspan)'
  - name: 문서를 찾아보고 방법을 정함
    toolUsed: {name: knowledgeSearchDocs, min: 1}
```

YAML의 작은따옴표 글자 안에서 작은따옴표는 `''`로 두 번 쓴다.

### 9.2 검증 Agent — 헛 PASS를 내지 않나

```yaml
id: verify-merge-cells
description: 칸이 나뉘어 있는 결과물에서 병합 기준을 PASS로 내지 않는가
agent: sm-verifier-agent
fixture: myApp/verify-merge-cells        # work/ 는 고쳐지기 전의 개발 결과
params:
  projectId: myApp
  sourceDir: /app/myApp
input:
  base_dir: ${workDir}
  source_dir: ${param.sourceDir}
  project_id: ${param.projectId}
  requirement: ${fixture:input/requirement.txt}
  design: ${fixture:input/design.txt}
  reported: ${fixture:input/reported.txt}
checks:
  - name: 결과를 냄
    answerNotEmpty: scenarios
  - name: 화면을 실제로 봄
    toolUsed: {name: browser_, min: 1}
  # 병합 항목이 있고 FAIL이나 BLOCKED여야 한다. ((?!task=).)* 는 다음 항목으로 넘어가지 않게 막는다
  - name: 병합 기준을 PASS로 내지 않음
    answerMatches:
      field: scenarios
      pattern: 'task=((?!task=).)*병합((?!task=).)*result=(FAIL|BLOCKED)'
```

`task=… result=…`는 이 Agent의 답 모양이다. 다른 Agent라면 미리 채점의 "그때 결과 보기"에서 실제 칸 이름과 순서를 확인한다. 테스트 서버를 쓰는 Agent는 11장을 먼저 읽는다.

### 9.3 설계 Agent — 있으면 안 되는 모양

```yaml
id: design-upload-style

      file: 03-1.design.md
      pattern: 'FileService\.\w*[Ss]ave\('
  - name: 업로드를 새로 짓지 않음

```

### 9.4 수정 Agent — 원인을 찾고 값을 채웠나

```yaml
id: autofix-delete-key

  design: ${file:03-1.design.md}             # 작업 폴더 파일의 내용
  verification: ${fixture:input/verification.txt}
checks:
  - name: 원인을 찾음
    answerContains: {field: causes, text: company_id}
  - name: 회사코드를 채우는 코드가 늘어남
    textIncreased:
      files: [dev-resources/src/main/java/com/example/board/BoardService.java]
      text: setCompanyId
  - name: 설계서에도 반영
```

### 9.5 답 값이 정확해야 할 때

```yaml
checks:
  - name: 컴파일 성공으로 답함
    answerEquals: {field: compiled, value: true}
  - name: 보류 없이 끝냄
    answerEquals: {field: pending, value: 0}
```

### 9.6 손으로 만드는 가장 작은 사례

화면 없이도 만들 수 있다. 파일을 두면 다시 띄우지 않아도 목록에 나온다.

```
conf/eval/myApp/
├── impact-basic.eval.yml
└── impact-basic/                 ← fixture
    ├── input/requirement.txt     ← ${fixture:…}로만 읽음(복사하지 않음)
    └── work/                     ← 작업 폴더로 복사됨
        └── 01.customer_requirement.md
```

```yaml
id: impact-basic
description: 영향도 분석서에 요청한 기능이 모두 들어가는가
agent: sm-analyze-impact-agent
fixture: myApp/impact-basic
input:
  base_dir: ${workDir}
  requirement: ${fixture:input/requirement.txt}
checks:
  - {name: 분석서 저장, fileExists: 02.impact.md}
  - {name: 첫 과제 포함, fileContains: {file: 02.impact.md, text: TASK-01}}
  - {name: 둘째 과제 포함, fileContains: {file: 02.impact.md, text: TASK-02}}
```

`input`의 칸 이름은 그 Agent 정의의 `input:`과 맞춰야 한다.

### 9.7 Workflow 사례 — API와 DB로 채점

```yaml
id: memo-full
description: 메모 등록·수정·목록이 요청서대로 동작하는가
workflow: sm-workflow
fixture: myApp/memo-full            # work/00.request.md 또는 request.file
params:
  projectId: myApp
request:
  file: 00.request.md
  append: |
    ## 프로젝트ID
    ${param.projectId}
input: ${requestDir}
approvals:                          # 자기 Workflow의 승인 step id와 결정 이름으로 바꾼다
  step09: 승인(설계진행)
  step13: 승인(개발진행, 서버 검증)
snapshotAfter: step18               # 첫 개발본을 따로 채점
server:
  projectId: ${param.projectId}
  overlayDir: ${requestDir}/${state.now}/dev-resources
checks:
  - name: 등록
    http:
      method: POST
      path: /api/memos
      body: {title: 회의, body: keep-me}
      status: 200
      save: {memoId: id}
  - name: DB에 저장
    dbQuery: {sql: "SELECT COUNT(*) AS n FROM memo WHERE title = '회의'", equals: "1"}
  - name: 수정
    http:
      method: PUT
      path: "/api/memos/${saved.memoId}"
      body: {title: 회의2, body: ""}
      status: 200
  - name: 목록에 반영
    http:
      path: /api/memos
      json: {"[0].title": 회의2}
```

`http` 채점은 로그인, 쿠키, CSRF 토큰을 처리하지 않는다. 로그인해야 하는 주소는 이 방법으로 잴 수 없다.

### 9.8 모델 비교

사례 파일은 그대로 두고 화면의 **모델** 칸만 바꿔 각각 3번 돌린다. 비교 표가 모델별로 나눠 보여 준다. Agent 사례에서만 가능하다.

## 10. 사례 파일 레퍼런스

### 10.1 맨 위 키

| 키 | 필수 | 설명 |
|---|---|---|
| `id` | ○ | 영문 소문자, 숫자, 하이픈. 파일 이름 `<id>.eval.yml`과 같아야 함 |
| `description` | | 무엇을 재는가 |
| `agent` / `workflow` | ○ | 둘 중 하나만 |
| `fixture` | | 자료 폴더(`conf/eval` 기준) |
| `copy` | | `work/` 가운데 복사할 것. 없으면 전부, `[]`면 없음 |
| `params` | | 실행 때 바꿀 수 있는 값과 기본값 |
| `request` | | `{file, append}` → 요청 폴더의 `00.request.md` |
| `input` | ○ | Agent나 Workflow의 입력 |
| `checks` | ○ | 채점 기준 |
| `approvals`, `snapshotAfter` | | Workflow 사례만 |
| `server` | `http`·`dbQuery`가 있으면 ○ | `projectId`, `overlayDir`(필수), `revision`, `deleteList` |

### 10.2 자리

| 자리 | 값 | 쓰는 곳 |
|---|---|---|
| `${workDir}` | 평가용 작업 폴더 | 어디서나 |
| `${requestDir}` | 요청 폴더(Workflow 사례는 작업 폴더와 같음) | 어디서나 |
| `${param.이름}` | `params` 값 | 어디서나 |
| `${request}` | 요청서 내용 | `input` |
| `${file:경로}` | 작업 폴더의 파일 내용 | `input` |
| `${fixture:경로}` | 자료 폴더의 파일 내용 | `input` |
| `${state.이름}` | Workflow가 멈춘 뒤의 state | `server`, `checks` |
| `${saved.이름}` | 앞 `http` 채점이 `save`한 값 | `checks` |

정해진 이름이 아닌 `${…}`(JSP 표현식 등)는 바꾸지 않는다.

### 10.3 채점 종류

| 종류 | 값 | 통과 조건 |
|---|---|---|
| `fileExists` | 경로 | 파일이 있다 |
| `fileChanged` | 경로 | 처음과 다르다(새로 생김 포함) |
| `fileContains` | `{file, text}` | 글자가 있다 |
| `fileMatches` | `{file, pattern}` | 정규식이 맞는 곳이 있다 |
| `fileNotMatches` | `{file, pattern}` | 파일이 있고 맞는 곳이 없다 |
| `textIncreased` | `{files, text}` | 글자 수 합이 처음보다 늘었다 |
| `answerContains` | `{field?, text}` | 답(칸)에 글자가 있다 |
| `answerNotEmpty` | 칸 이름 | 빈 글자, `[]`, `{}`가 아니다 |
| `answerEquals` | `{field, value}` | 값이 같다 |
| `answerMatches` | `{field?, pattern}` | 맞는 곳이 있다 |
| `answerNotMatches` | `{field?, pattern}` | 답이 있고 맞는 곳이 없다 |
| `toolUsed` | 이름 또는 `{name, min}` | 그 이름으로 시작하는 Tool을 min번 이상 요청 |
| `http` | `{method?, path, body?, status?, json?, contains?, save?}` | 적은 조건이 모두 맞음 |
| `dbQuery` | `{sql, equals}` 또는 `{sql, rows}` | 첫 값이 같거나 행 수가 같음 |

- 정규식은 Java 문법이고 `.`이 줄바꿈에도 맞는다.
- Workflow 사례의 `answer…` 채점은 답 대신 **state**를 본다.
- `json`과 `save`의 경로: `a.b`, `[0].title`, `items[*].name`, `$size`.

### 10.4 설정

| 키 | 기본 | 설명 |
|---|---|---|
| `dstone.ai.eval.location` | `{APP_CONF_DIR}/eval` | 사례 폴더 |
| `dstone.ai.eval.work-root` | `{APP_HOME}/LOGS/dstone-ai-engine/eval` | 평가 작업 폴더. 자동으로 지우지 않음 |
| `dstone.ai.eval.threads` | 1 | 동시에 도는 평가 수 |
| `dstone.ai.eval.workflow-max-steps` | 300 | Workflow 사례의 step 상한 |
| `dstone.ai.workflow.snapshot.enabled` | `true` | 스냅숏 |
| `dstone.ai.workflow.snapshot.retention-days` | 30 | 스냅숏 보관 일수 |

## 11. 주의할 점

**비용.** 평가는 실제 LLM을 부른다. 파일을 많이 읽는 개발 Agent는 한 번에 입력 토큰이 백만을 넘기도 한다. 3번 돌리면 3배다.

**격리 범위.** 새로 만드는 것은 작업 폴더뿐이다. Agent가 쓰는 Tool은 실제로 동작한다.

| Agent가 쓰는 것 | 평가 중 영향 |
|---|---|
| 파일 읽기·쓰기 | 경로가 작업 폴더면 안전. **사례에 남은 절대경로는 실제 파일에 닿는다**(4.5) |
| 소스, 지식 검색 | 지금의 소스와 문서를 읽는다. 그때와 다르면 결과도 달라질 수 있다 |
| 테스트 서버(`startTestServer`) | 개발 DB를 커밋하지 않는 연결로 쓰고 원복한다. 아래 참고 |
| 외부 시스템을 바꾸는 Tool | 실제로 바뀐다. 이런 Agent의 사례는 만들기 전에 확인한다 |

**테스트 서버를 쓰는 Agent 사례.** Agent 사례에는 Workflow 실행 ID가 없다. 평가기가 서버를 내리고 원복하는 처리는 `http`·`dbQuery` 채점용 서버에만 있다. Agent가 스스로 띄운 서버는 평가가 끝나도 바로 내려가지 않을 수 있다. 처음 돌릴 때 서버가 내려가고 DB가 원복되는지 로그로 확인한다. 원복을 확신할 수 없으면 돌리지 않는다.

**재현 한계.** 스냅숏은 입력과 파일을 고정한다. DB 데이터, 소스 리비전, 외부 서비스, 모델의 변화는 고정하지 못한다.

**Workflow 사례.** 모델을 바꿀 수 없다. 실행 관리에 요청자 `eval:…`로 남고 채점 뒤 `CANCELLED`로 닫힌다.

## 12. 문제 해결

| 증상 | 원인 | 조치 |
|---|---|---|
| "이 줄의 스냅숏이 없습니다" | 보관 기간 초과, `forEach`·TOOL step, 스냅숏 기능 이전 실행 | 새 실행에서 만든다 |
| 작업 폴더 선택지가 "복사 안 됨" | 폴더가 상한보다 큼 | 다른 입력 폴더를 고르거나 손으로 `work/`를 만든다 |
| "같은 id의 사례가 이미 있습니다" | id 중복 | 다른 id |
| 저장이 403 | 관리자가 아님 | 관리자 계정 |
| 목록에 "사례 파일이 틀렸습니다" | 모르는 키, 정규식 오류, id와 파일 이름 불일치 | 표시된 사유대로 고친다 |
| `params에 '…'가 없습니다` | `${param.…}` 오타 | `params`에 선언 |
| 채점 "파일 없음" | 경로가 작업 폴더 기준이 아님 | 평가 상세의 작업 폴더에서 실제 경로 확인 |
| 3번 다 통과(기준선) | 기준이 느슨하거나 다른 장면 | 미리 채점부터 다시 |
| 시작이 400 (Workflow) | 없는 step id, 틀린 결정 이름 | `approvals`, `snapshotAfter` 확인 |
| `테스트 서버를 띄우지 못했습니다` | 리비전 빌드, 프로젝트 DB 등록, Tomcat 설정 | 프로젝트 관리와 `env.properties` 확인 |
| 전후가 비교 표 한 줄로 합쳐짐 | Agent 버전을 올리지 않음 | 버전을 올리고 다시 돌린다 |

## 13. API

| 메서드 | 주소 | 설명 |
|---|---|---|
| GET | `/api/ai/eval/cases` | 사례 목록 |
| POST | `/api/ai/eval/runs` | 평가 시작 `{caseId, params, model, repeat}` |
| GET | `/api/ai/eval/runs?caseId=&limit=` | 결과 목록(최대 200) |
| GET | `/api/ai/eval/runs/{runId}` | 결과 상세 |
| GET | `/api/ai/eval/drafts/snapshots?executionId=` | 스냅숏 목록 |
| GET | `/api/ai/eval/drafts/step?executionId=&snapshot=` | Agent 사례 초안 |
| GET | `/api/ai/eval/drafts/execution?executionId=` | Workflow 사례 초안 |
| POST | `/api/ai/eval/drafts/preview` | 미리 채점 |
| POST | `/api/ai/eval/drafts/save` | 저장(관리자) |

API Key 인증을 켠 환경에서는 `X-API-Key` 헤더가 필요하다.

```bash
curl -s -X POST http://localhost:8081/api/ai/eval/runs \
  -H 'Content-Type: application/json' -H "X-API-Key: $API_KEY" \
  -d '{"caseId":"dev-merge-cells","repeat":3}'

curl -s "http://localhost:8081/api/ai/eval/runs?caseId=dev-merge-cells&limit=10" -H "X-API-Key: $API_KEY"
```

## 14. 체크리스트

**사례를 만들 때**

- [ ] 실수를 본 날 만들었다(스냅숏 30일)
- [ ] 실수가 드러난 회차를 골랐다
- [ ] 설명만 읽고 무엇을 재는지 알 수 있다
- [ ] 산출물 확인 하나와 핵심 기준 1~2개
- [ ] 미리 채점에서 핵심 기준이 ✗
- [ ] 남은 절대경로가 없다
- [ ] (Workflow) `approvals`에 되돌아가는 결정이 없다

- [ ] 기준선을 3번 이상 돌렸다
- [ ] 실패 종류를 분류했다
- [ ] 한 가지만 바꿨다
- [ ] Agent 버전을 올렸다
- [ ] 같은 사례, 같은 모델로 3번 이상 다시 돌렸다
- [ ] 관련 사례도 돌렸다
- [ ] 작업 폴더의 산출물을 직접 열어 봤다
- [ ] 교훈을 8.3 양식으로 남겼다
