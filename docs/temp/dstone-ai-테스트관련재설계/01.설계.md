# dstone-ai-engine 서버 기동 테스트 재설계

- 상태: 설계 확정, 구현(2026-11-26). 구현 결과와 설계에서 달라진 점은 13장.
- 범위: 프로젝트 관리, 리비전 빌드, 테스트 서버(Tomcat·Spring Boot), 개발 DB 원복, sm-workflow
- 이 문서만 보고 구현할 수 있게 썼다. 구현 중에 바뀐 결정은 이 문서에 먼저 고쳐 적는다.

---

## 1. 왜 바꾸나

지금 방식(`startSandboxServer`, `docs/09` 11.2절)의 문제는 다음과 같다.

| 문제 | 내용 |
|---|---|
| DB를 통째로 복제 | 프로젝트 관리에 등록한 DB(MySQL·PostgreSQL은 database, Oracle은 스키마)를 구조와 모든 행까지 `startSandboxServer`를 부를 때마다 복제한다. 상한은 2GB(`sandbox-max-db-mb`). 고객사 개발 DB는 훨씬 커서 사실상 늘 `BLOCKED`가 된다 |
| 준비물이 무거움 | 같은 종류의 DB 설치 폴더, Oracle 시험 전용 CDB, AppArmor 설정이 필요하다. 폐쇄망 현장에서 갖추기 어렵다 |
| Maven만 지원 | `pom.xml`이 없으면 바로 실패한다. 다중 모듈, Gradle, Ant, Eclipse 프로젝트는 띄우지 못한다 |
| 매번 전체 빌드 | 띄울 때마다 `mvn clean package`를 돌린다 |
| 동시 실행 불가 | 프로젝트마다 사본 하나와 잠금 하나를 쓴다. 같은 프로젝트의 두 번째 실행은 60초 기다리다 실패한다. 현장에서는 같은 프로젝트에 여러 요청이 동시에 돈다 |

참고로 testApp(소스 105개, WAR) 측정값(2026-11-26, 1회): DB 복제 약 20초, `mvn clean package` 16초, JVM 기동 1초, WAR 배포 11초, 합계 약 55초. 큰 레거시 앱은 빌드와 복제가 몇 분 이상으로 늘어난다.

## 2. 결정 사항

| # | 결정 |
|---|---|
| A1 | 원래 WAS 설정을 Tomcat에서 돌 수 있게 전환한다. 전환 결과는 실행 층에만 둔다. EJB나 벤더 전용 기능을 쓰는 앱은 "서버 기동 테스트 불가"를 알리고 정보는 저장한다. Workflow는 서버 기동 테스트 앞까지만 진행한다. 판정은 플랫폼 이름이 아니라 코드로 한다 |
| A2 | Tomcat의 Resources(overlay)를 쓴다. 실행마다 docBase 층과 CATALINA_BASE를 따로 만든다. 바닥 층은 엔진이 빌드해 둔 리비전 폴더이고, 고객의 소스 디렉토리는 직접 물지 않는다 |
| A3 | Spring Boot는 내장 WAS로 띄운다 |
| A4 | Java는 바뀐 것만 `compileJava`로 컴파일한다 |
| A5 | 반영은 즉시 반영, context reload, JVM 재시작으로 나눈다. Tomcat은 JVM을 실행 ID당 한 번만 띄운다(Boot는 클래스가 바뀌면 재시작). reload하면 세션이 끊긴다. 유휴 30분이 지나면 내리고, 서버가 필요한 step에서 다시 띄운다 |
| B1 | 고객사가 준 개발 DB를 그대로 쓴다. 복제하지 않는다 |
| B2 | 테스트가 끝나면 데이터를 원복한다. 방법은 엔진이 만든 감싸는 JDBC 드라이버다(6장) |
| B3 | DDL은 사람이 개발 DB에 반영한다. 테스트 중 DDL은 막는다 |
| C1 | sm-workflow의 전문가 해결 루틴을 없앤다 |
| C2 | `startTestServer`·`startSandboxServer`와 사람 시험 서버 반영 경로를 없애고 테스트 서버 Tool 하나로 합친다 |
| C3 | 요청서의 `## 프로젝트ID`를 필수로 하고 `## 소스경로`는 없앤다. 소스는 프로젝트의 현재 리비전에서 가져온다 |
| C4 | 설계에 DDL이 있으면 서버 기동 테스트 앞에 "DDL 반영 확인" 승인 step을 둔다 |
| D | 프로젝트 관리에 형상관리 계정, Java 버전 드롭다운, WAS, 빌드 항목을 넣는다(3장) |
| D4 | 리비전은 사람이 [Build]를 눌러서만 만든다. 빌드 명령은 종류별로 정해진 명령과 등록된 스크립트만 실행한다 |
| 용어 | "시험"은 "테스트"로 바꾼다. 화면, Tool 설명·결과, Skill, 문서 모두 |

기본값(모두 설정으로 바꿀 수 있음): 유휴 종료 30분, 동시 테스트 서버 3개, 보관 리비전 3개, DB 연결 점유 상한 60분, 잠금 대기 상한 30초.

### 3.2 테이블

컬럼 이름은 그대로 두고 화면 글만 바꾼다(`TEST_USER_ID`, `TEST_PASSWORD_ENC`, `TEST_STATIC_PATHS`). 새로 넣는 것:

```sql
-- ai_management_project
SCM_USERNAME        VARCHAR(200),
SCM_PASSWORD_ENC    TEXT,          -- EncUtil
WAS_CONTAINER       VARCHAR(20),   -- BOOT/TOMCAT/JEUS/WEBLOGIC/WEBSPHERE
WAS_VERSION         VARCHAR(30),
CONTEXT_PATH        VARCHAR(200),
BUILD_TYPE          VARCHAR(10),   -- MAVEN/GRADLE/ANT/SHELL/NONE
BUILD_ARGS          VARCHAR(1000), -- 정해진 명령 뒤에 붙는 인자. SHELL이면 allowed-commands 등록 이름
BUILD_WEB_ROOT      VARCHAR(1000), -- 아래 넷은 자동으로 못 찾을 때만(소스 루트 기준 상대경로)
BUILD_CLASSES_DIR   VARCHAR(1000),
BUILD_LIB_DIR       VARCHAR(1000),
BUILD_SOURCE_DIRS   VARCHAR(1000), -- NONE일 때 소스 폴더들(쉼표)
CURRENT_REVISION    VARCHAR(100)   -- ai_management_project_revision.REVISION

-- ai_management_project_db
JNDI_NAME           VARCHAR(200)

-- 새 테이블: 리비전 빌드 기록
CREATE TABLE ai_management_project_revision (
    PROJECT_ID    VARCHAR(50)  NOT NULL REFERENCES ai_management_project(PROJECT_ID) ON DELETE CASCADE,
    REVISION      VARCHAR(100) NOT NULL,  -- 폴더 이름(4.2절)
    SCM_REVISION  VARCHAR(100),           -- git commit, svn 번호. 형상관리 없으면 NULL
    STATUS        VARCHAR(10)  NOT NULL,  -- BUILDING/OK/FAILED
    KIND          VARCHAR(10),            -- WAR/BOOT(빌드 결과로 판정)
    WEB_ROOT      VARCHAR(1000),          -- 찾은(또는 입력한) 산출물 위치, 리비전 폴더 기준
    CLASSES_DIR   VARCHAR(1000),
    LIB_DIR       VARCHAR(1000),
    MAIN_CLASS    VARCHAR(300),           -- BOOT
    MESSAGE       TEXT,
    REQUESTED_BY  VARCHAR(100),
    STARTED_AT    TIMESTAMPTZ NOT NULL DEFAULT now(),
    FINISHED_AT   TIMESTAMPTZ,
    PRIMARY KEY (PROJECT_ID, REVISION)
);
```

`02-create-table-postgresql-dstone-ai.sql`에 반영하고, 기존 DB용 ALTER 문을 같은 폴더에 따로 둔다. 쿼리는 MyBatis(`*Dao.xml` + `BaseDao`). API `/api/ai/projects`는 비밀번호 대신 `hasScmPassword`만 돌려준다.

## 4. 리비전과 빌드

### 4.1 폴더

```
{작업 루트}/{프로젝트ID}/           작업 루트 = dstone.ai.tool.test-server.work-root(기본 {홈}/.dstone-ai-engine)
  rev/{리비전}/
    src/          소스 디렉토리를 복사한 것(.git, .svn, target, build 제외). 빌드는 여기서 한다
    build.log
    webapp/       WAR 산출물을 푼 것(5.1절의 바닥 층). Boot면 없음
    lib/          Boot와 "빌드 없음"일 때 의존성 jar
    classes/      "빌드 없음"일 때 엔진이 전체 컴파일한 결과
  runs/{실행ID}/  5장
```

리비전 폴더는 빌드가 끝난 뒤에는 읽기만 한다. 고객의 소스 디렉토리(`프로젝트.소스디렉토리`)는 형상관리에서 받는 기준 폴더로만 쓰고, 그 값을 바꾸지 않는다.

### 4.2 [Build]를 누르면

백그라운드 작업으로 돌고, 화면은 상태와 로그를 주기적으로 읽는다. 같은 프로젝트의 빌드는 한 번에 하나만 돌린다(두 번째 요청은 거절).

1. 형상관리가 있으면 소스 디렉토리를 갱신한다(git `fetch` + `reset --hard origin/{현재 브랜치}`는 하지 않고 `pull --ff-only`, svn `update`). 로컬 변경 때문에 실패하면 멈추고 알린다. 계정은 명령줄에 싣지 않는다(git은 `GIT_ASKPASS`, svn은 `--password-from-stdin`).
2. 리비전 이름을 정한다. 형상관리가 있으면 `{SCM 리비전 앞 12자}`, 없으면 `{yyyyMMdd-HHmmss}`. 같은 이름의 리비전이 이미 `OK`면 다시 빌드하지 않고 현재 리비전으로만 바꾼다.
3. 소스를 `rev/{리비전}/src`로 복사한다. 형상관리가 없을 때도 복사한다. 그래야 소스 디렉토리가 나중에 바뀌어도 진행 중인 실행이 영향을 받지 않는다.
4. 종류별로 정해진 명령을 그 폴더에서 실행한다. JDK는 프로젝트의 Java 버전으로 고른다. 테스트는 건너뛴다.

   | 종류 | 명령 | 화면에 미리 넣는 인자 |
   |---|---|---|
   | Maven | `mvn -B -DskipTests package {인자}` | (비움) 예: `-pl web -am` |
   | Gradle | `gradlew`가 있으면 그것, 없으면 `gradle`: `build -x test {인자}` | (비움) |
   | Ant | `ant {인자}` | 기본 target |
   | Shell | `allowed-commands`에 등록된 스크립트, 인자로 리비전 `src` 경로 | 등록 이름 선택 |
   | 빌드 없음 | 엔진이 `compileJava`의 classpath 탐색으로 소스 전체를 javac(결과 `rev/{리비전}/classes`) | 소스 폴더, lib 폴더 |

5. 산출물을 찾는다.
   - Maven WAR: `target/{finalName}/`(풀린 WAR)
   - 그 밖에 `.war`가 나왔으면 `rev/{리비전}/webapp`에 푼다(Gradle, Ant 대부분이 여기 해당)
   - Boot: `spring-boot-maven-plugin`이나 Gradle Boot 플러그인이 있으면 Boot다. 클래스 폴더와 의존성 jar(Maven은 `dependency:copy-dependencies`로 `lib/`에), 메인 클래스(Boot jar `MANIFEST`의 `Start-Class`)를 기록한다
   - 못 찾으면 상태를 `FAILED`가 아니라 "구조 입력 필요"로 두고, 화면에 웹 루트·클래스·lib 입력칸을 연다. 입력하고 다시 [Build]를 누르면 빌드 없이 구조만 검사한다
6. 빌드 자체가 실패하면(종료 코드, 도구 없음) `FAILED`로 남기고 현재 리비전은 바꾸지 않는다.
7. 성공하면 `CURRENT_REVISION`을 바꾼다. 이미 시작한 실행은 시작할 때의 리비전을 계속 쓴다(7.1절).
8. 정리: 현재 리비전과 실행 중인 실행이 쓰는 리비전을 빼고, 최근 3개까지만 남긴다.

## 5. 테스트 서버

### 5.1 실행 층

```
{작업 루트}/{프로젝트ID}/runs/{실행ID}/
  webapp/     docBase. 개발 결과(dev-resources의 webapp 쪽 파일), compileJava가 만든 클래스, 경로를 바꾼 파일, 전환한 설정
  classes/    compileJava 결과(WEB-INF/classes로 붙임. Boot면 classpath 맨 앞)
  data/       소스에 박힌 원본 절대경로를 이리로 바꾼다(5.5절)
  tomcat/     CATALINA_BASE(conf, work, temp, logs, lib에 테스트 드라이버)
  server.log, server.pid, driver.json(6.3절)
```

Tomcat Context(`tomcat/conf/Catalina/localhost/{컨텍스트}.xml`):

```xml
<Context docBase="{runs}/webapp" reloadable="false">
  <Resources>
    <PreResources  className="org.apache.catalina.webresources.DirResourceSet" base="{runs}/classes" webAppMount="/WEB-INF/classes"/>
    <PostResources className="org.apache.catalina.webresources.DirResourceSet" base="{rev}/webapp"   webAppMount="/"/>
    <!-- 산출물을 따로 입력한 경우: 웹 루트 "/", 클래스 "/WEB-INF/classes", lib "/WEB-INF/lib"를 각각 PostResources로 -->
  </Resources>
</Context>
```

바뀐 파일은 실행 층에서 먼저 찾고, 나머지는 리비전 폴더에서 읽는다. Resources는 Tomcat 8.5 이상에서만 된다. 그래서 Tomcat 7 전용 앱은 지원하지 않는다.

삭제 목록(`_delete-files.txt`)의 처리:
- JSP·정적 파일: Tomcat 기본 `RewriteValve`에 `RewriteRule ^/{경로}$ - [G]`로 막는다(410).
- Java 클래스: 사용처는 `compileJava`가 오류로 잡는다. 리비전의 클래스 파일은 남아 있으므로 이 점을 결과의 "원래 환경과 다른 점"에 적는다.

### 5.2 Tomcat과 JDK 고르기

- JDK: 프로젝트 Java 버전 → 리비전의 빌드 설정 → 클래스 파일 순서로 버전을 정하고 `JAVA_HOME_{버전}`에서 찾는다(지금과 같음).
- Tomcat: 앱이 javax(Servlet 4 이하)면 9, jakarta면 10.1 이상. 판정은 `web.xml`의 스키마와 lib의 servlet/jakarta API다. 경로는 env `TOMCAT_HOME_{9|10|11}`. 없으면 "테스트 불가(이 서버에 Tomcat {버전} 없음)"로 끝낸다. 기존 `TEST_SERVER_TOMCAT_HOME`은 없앤다.
- CATALINA_BASE는 지금처럼 설치된 Tomcat의 `conf`를 복사하고, HTTP 포트만 빈 포트로 바꾸고, shutdown 포트와 AJP는 끄고, 사람이 등록한 다른 Context는 뺀다.

### 5.3 WAS 전환과 판정

띄우기 전에 리비전을 훑어 판정한다. 결과는 리비전 기록과 테스트 서버 결과에 남긴다.

| 판정 | 기준 |
|---|---|
| 불가 | EJB(`javax.ejb`·`jakarta.ejb` import, `@Stateless`·`@Stateful`·`@MessageDriven`, `ejb-jar.xml`), 벤더 API import(`weblogic.`, `com.bea.`, `com.ibm.websphere.`, `com.ibm.ws.`, `jeus.`, `tmax.`), 벤더 전용 기능(WebLogic startup/shutdown class, `weblogic-application.xml`의 전용 리스너 등) |
| 전환 | 그 밖 |

벤더 이름 목록은 특정 앱의 값이 아니라 범용 지식이므로 엔진 설정(`application.yml`)에 둔다.

전환하는 것(모두 실행 층에만 쓴다):
- 컨텍스트 경로: 프로젝트 관리 값 → `weblogic.xml`의 `context-root` → `jeus-web-dd.xml`의 `context-path` → `ibm-web-ext.xml`의 `context-root` → Maven `<path>` → `/`
- 데이터소스: 6.2절
- JNDI: 앱이 찾는 이름(`jndi-lookup`, `JndiObjectFactoryBean`, `InitialContext.lookup("…")`의 따옴표 리터럴)을 모은다. 프로젝트 DB의 JNDI 이름과 짝지어 Context에 `<Resource>`를 만든다. 앱이 `java:comp/env` 없이 찾으면(WebLogic·JEUS에 흔함) 그 리터럴을 `java:comp/env/…`로 바꾼 파일을 실행 층에 넣는다(Java면 다시 컴파일). 짝을 못 찾은 이름이 있으면 띄우지 않고 이유를 알린다.

### 5.4 Spring Boot

- `java -cp {runs}/classes:{rev}/classes:{rev}/lib/* {메인 클래스} --server.port={빈 포트}`로 띄운다. jar를 다시 만들지 않는다.
- 바뀐 설정 파일(`application*.yml`, properties)은 `{runs}/classes`에 넣는다. classpath 앞이라 먼저 읽힌다.
- context reload가 없으므로 클래스·설정이 바뀌면 JVM을 다시 띄운다(10초 안팎).
- 테스트 드라이버 jar를 classpath에 더한다.

### 5.5 경로 치환

소스에 박힌 원본 절대경로(예: 업로드 폴더를 원본 소스 디렉토리 안으로 적어 둔 경우)를 그대로 두면, 테스트 중 업로드와 삭제가 원본 폴더에서 일어난다.

- 리비전 `src`와 개발 결과에서 `프로젝트.소스디렉토리` 경로가 든 텍스트 파일을 찾는다. 지금의 `SandboxPaths` 규칙을 다시 쓰고, 바뀐 파일을 실행 층에 넣는다.
- Java 파일이면 `compileJava`로 다시 컴파일해 `{runs}/classes`에 넣는다.
- 경로는 `{runs}/data/…`로 바꾼다. 비어 있는 폴더로 시작하므로 기존 첨부 파일은 없다. 결과의 "원래 환경과 다른 점"에 적는다.

### 5.6 테스트서버 정적 경로

지금과 같다. `/주소=폴더` 한 줄마다 실행 CATALINA_BASE에 Context 파일을 만든다. 원본 소스 디렉토리 안의 폴더는 `{runs}/data` 쪽으로 연다. Boot에서는 열지 않는다.

### 5.7 반영 방법

테스트 서버를 다시 부르면 지난번 반영 뒤 바뀐 파일을 보고 고른다(개발 결과 폴더의 크기·수정 시각 비교, 지금의 `fingerprintOf`).

| 바뀐 것 | Tomcat | Boot |
|---|---|---|
| JSP, JS, CSS, 이미지 | 실행 층에 복사(즉시). JSP는 Tomcat 기본 development 모드로 다시 컴파일된다 | 정적 파일만 복사(즉시) |
| Java, MyBatis XML, properties, `web.xml` | 복사·컴파일 뒤 context reload. Context 파일의 수정 시각을 바꿔 다시 올리고(Manager 앱 없이), 앱 경로가 응답할 때까지 기다린다 | JVM 재시작 |
| JVM 옵션, Tomcat 설정, 테스트 드라이버 | JVM 재시작 | JVM 재시작 |

reload나 재시작을 하면 세션이 끊기므로, 결과에 "다시 로그인하십시오"를 적는다. 결과에는 구간별 시간(컴파일, 복사, reload·기동)을 함께 남긴다.

### 5.8 수명과 동시 실행

| 언제 | 서버 | DB 데이터 |
|---|---|---|
| step이 끝남 | 둔다(같은 실행의 다음 step이 그대로 쓴다) | 그대로 |
| 실행이 루프를 벗어남(승인 대기, 일시정지, 실패, 끝남) | 끝남·실패면 내린다. 승인 대기·일시정지면 둔다 | rollback(원복) |
| 유휴 30분 | 내린다. 다음에 서버가 필요한 step이 부르면 다시 띄운다 | (이미 원복됨) |
| 엔진 종료·재시작 | 모두 내린다. 다음 기동 때 남은 프로세스를 표시(`-Ddstone.ai.test-server=`)로 찾아 정리한다 | 연결이 끊겨 DB가 rollback |

- 같은 실행 안의 검증 Agent와 자동 수정 Agent는 데이터를 함께 본다. 다음 회차(사람 결정 뒤)는 원복된 상태에서 시작한다.
- 실행마다 서버 하나. 같은 프로젝트를 여러 실행이 동시에 쓸 수 있다. 전체 동시 서버는 3개까지이고, 넘으면 기다린다(최대 `lock-wait-seconds`). 그래도 자리가 없으면 `BLOCKED`(cause: environment)로 끝낸다.
- 포트는 빈 포트를 고른다.

### 5.9 Tool

`tools.build.TestServerTool`(이름 유지)에 다음만 둔다.

| Tool | 인자 | 하는 일 |
|---|---|---|
| `startTestServer` | `projectId`, `revision`, `overlayDir`, `deleteList` | 떠 있지 않으면 띄우고, 떠 있으면 5.7절대로 반영한다. 결과: `success`, `cause`(code/environment), `url`, `serverLog`, `dbAliases`, `account`, `timings`, "원래 환경과 다른 점" |
| `stopTestServer` | `projectId` | 이 실행의 서버를 내리고 DB를 원복한다 |

`ddlFile` 인자는 없앤다. DDL 반영 여부는 `checkDdlApplied`(7.3절)가 본다.

지금의 묶기 규칙은 이름만 바꿔 유지한다(`SandboxRegistry` → `TestServerRegistry`): 띄운 step은 `dbQuery`를 테스트 별칭으로, `browser_navigate`를 테스트 서버 주소로 묶는다. Agent 정의의 `execution.toolPrerequisites`도 `startTestServer`로 바꾼다.

## 6. DB: 개발 DB와 원복

### 6.1 원리

앱의 모든 DB 연결을 엔진이 만든 감싸는 JDBC 드라이버(이하 테스트 드라이버)로 바꾼다.

- 실행 하나, DB 하나마다 물리 연결을 하나만 연다. autocommit은 끈다.
- 앱이 받는 연결은 모두 그 물리 연결을 감싼 것이다. `close()`는 반납만 한다.
- 앱의 `commit()`은 커밋하지 않고 새 savepoint를 잡는다. 앱의 `rollback()`은 마지막 savepoint까지만 되돌린다. 그래서 앞의 테스트 데이터는 남는다.
- 앱이 autocommit을 켠 채로 쓰면(명시적 트랜잭션 없음) 문장 하나를 단위로 본다. 문장마다 savepoint를 잡는다.
- 트랜잭션 단위(명시적이면 첫 문장부터 commit/rollback까지, 아니면 문장 하나)마다 잠금을 잡아 한 번에 한 스레드만 쓴다. 화면이 Ajax를 병렬로 불러도 섞이지 않는다.
- PostgreSQL은 문장이 실패하면 트랜잭션 전체가 막히므로, 실패한 문장은 savepoint로 되돌린 뒤 예외를 그대로 던진다.
- 실행이 루프를 벗어나거나 서버를 내리면 `rollback()`한다. 엔진이나 JVM이 죽어도 연결이 끊기면 DB가 rollback한다.
- 다른 실행과 고객 개발자에게는 커밋하지 않은 테스트 데이터가 보이지 않는다.

### 6.2 앱의 연결을 바꾸는 법

설정이 어디에 있든, 프로젝트 관리에 등록한 DB의 JDBC URL을 기준으로 찾는다.

- JNDI로 찾는 앱: 5.3절의 `<Resource>`를 테스트 드라이버로 만든다.
- 앱이 풀을 직접 만드는 앱(Spring XML의 `BasicDataSource`, properties의 URL 등): 리비전과 개발 결과의 텍스트 파일에서 등록한 URL과 드라이버 클래스를 찾아, 테스트 드라이버의 URL(`jdbc:dstonetest:{실행ID}:{원래 URL}`)과 클래스로 바꾼 파일을 실행 층에 넣는다.
- 등록한 DB 가운데 URL을 어디서도 찾지 못한 것이 있으면 띄우지 않는다. 원복을 보장할 수 없기 때문이다. 이유와 함께 `cause: environment`로 끝낸다.
- 우회 감지: 앱 JVM의 소켓은 지금처럼 `SandboxGuard`를 지나게 한다. 등록한 DB 주소로 가는 연결 수가 테스트 드라이버가 연 물리 연결 수보다 많으면, 서버를 내리고 rollback한 뒤 "테스트 드라이버를 거치지 않은 DB 연결"로 실패시킨다.
- 그 밖의 외부 접속은 지금처럼 막는다. 예외는 프로젝트별 `allow-hosts`뿐이다.

### 6.3 검증 Agent의 조회

`dbQuery`는 엔진 JVM에서 돈다. 그래서 앱 JVM의 커밋하지 않은 데이터를 직접 보지 못한다.

- 테스트 드라이버가 앱 JVM 안에서 `127.0.0.1`의 빈 포트로 조회 창구를 연다. 포트와 일회용 토큰은 `{runs}/driver.json`에 적는다.
- 엔진은 테스트 별칭(`test-{DB이름}`)으로 오는 `dbQuery`를 그 창구로 보낸다. 창구는 같은 물리 연결에서 잠금을 잡고 SELECT만 실행한다.
- 원래 DB 별칭(`프로젝트ID.DB이름`)으로 조회하면 커밋된 데이터만 보인다. 이 차이를 Tool 설명에 적는다.

### 6.4 DDL

- 테스트 중 DDL(CREATE, ALTER, DROP, TRUNCATE, RENAME, GRANT, REVOKE)은 테스트 드라이버가 실행하지 않고 SQLException을 던진다. MySQL·Oracle에서는 DDL이 그때까지의 작업을 커밋하기 때문이다.
- DDL은 사람이 개발 DB에 반영한다(7.3절).

### 6.5 한계("원래 환경과 다른 점"과 문서에 적는다)

| 한계 | 대응 |
|---|---|
| 프로시저 안의 COMMIT, 자율 트랜잭션, DB 링크 너머의 쓰기 | 되돌릴 수 없다. 결과에 "원복 보장 안 됨"으로 적는다 |
| MySQL의 트랜잭션이 없는 테이블(MyISAM 등) | 시작할 때 `information_schema`로 찾아 결과에 적는다 |
| 메일, MQ, 외부 연계 | DB 밖이다. 외부 접속 차단으로 막는다 |
| 행 잠금 | 실행당 연결 점유 60분 상한(넘으면 rollback하고 서버를 내림). 잠금 대기 30초 상한(넘으면 그 요청만 실패). 다른 실행이나 고객 개발자와 같은 행을 건드리면 기다리게 된다. 잠금 대기로 실패한 것은 Skill `test-environment`가 `BLOCKED`로 판정한다 |
| 앱이 기동하면서 도는 스케줄러 | 그 작업도 테스트 드라이버를 지나 원복된다. 다만 잠금을 잡을 수 있다 |
| DB에 저장된 파일 절대경로 | 엔진 서버에 그 경로가 실제로 있으면 테스트 중 삭제가 그 파일을 지운다. DB를 복제하지 않으므로 바꿀 수 없다. 문서의 "막지 못하는 것"에 적는다 |
| 시퀀스 | rollback해도 돌아가지 않는다. 번호가 건너뛸 뿐이라 문제 삼지 않는다 |

### 6.6 테스트 드라이버 jar

- 앱 JVM에서 돌므로 엔진과 분리한다. 외부 의존성은 없고, Java 8 바이트코드(`--release 8`)로 만든다. Java 6·7 앱은 이 드라이버를 쓸 수 없으므로 지원하지 않는다.
- 위치와 빌드 방식(엔진 모듈 안의 별도 소스 폴더를 release 8로 따로 묶는 방식, 또는 작은 Maven 모듈)은 3단계 구현 때 정해 이 문서에 적는다.
- Tomcat은 `{runs}/tomcat/lib`에, Boot는 classpath에 넣는다. 원래 드라이버(MySQL·PostgreSQL·Oracle 등)는 앱 lib에 있는 것을 그대로 쓴다.

## 7. sm-workflow

### 7.1 시작

- 요청서의 `## 프로젝트ID`가 필수다. 없으면 시작 step에서 멈춘다. `## 소스경로`는 읽지 않는다(남아 있으면 무시).
- 지금 소스경로를 읽는 step의 자리에 새 범용 TOOL step을 둔다. `resolveProjectRevision(projectId)`가 현재 리비전을 state(`projectRevision`: 리비전, 소스 루트 `rev/{리비전}/src`, 종류)에 저장한다. 그 뒤의 모든 step은 소스 경로로 `${state.projectRevision.sourceRoot}`를 쓴다.
- 빌드한 리비전이 없으면 멈추지 않고 진행한다. 서버 기동 테스트는 "빌드된 리비전 없음"으로 `BLOCKED` 처리한다.
- `compileJava`의 원본 클래스는 리비전의 클래스 폴더다. 그래서 "원본을 한 번은 빌드해 둬야 한다"는 조건은 [Build]로 대신한다.

### 7.2 전문가 해결 제거

- 개발 승인의 [전문가 해결] 선택과 그 경로의 step(yml 기준 step22~24), `sm-troubleshooter-agent`를 없앤다.
- Skill `troubleshooting`은 개발 Agent가 preload하므로 남긴다.
- 요청서 `## 시험환경` 절(DB연결, 서버로그, 반영폴더, 반영명령, 접속주소)과 반영 스크립트 경로(`TEST_SERVER_DEPLOY_SCRIPT`, `test-server-deploy`)를 없앤다. 사람이 쓰는 서버에 올리는 것은 이 Workflow의 일이 아니다.

### 7.3 DDL 반영 확인

- 컴파일 확인을 통과한 뒤, 서버 기동 테스트 앞에서 설계의 DDL 문서(`03-3.ddl(데이터베이스).md`)에 실행할 문장이 있는지 본다. 지금의 `SandboxDdl` 읽기 규칙을 쓴다.
- 문장이 있으면 승인 step "DDL 반영 확인"으로 간다. 안내문에 DDL 문서 경로를 적고, 사람이 개발 DB에 반영한 뒤 승인한다.
- 새 범용 Tool `checkDdlApplied(projectId, ddlFile)`가 DDL의 CREATE TABLE·ALTER TABLE ADD 대상이 개발 DB에 실제로 있는지 JDBC 메타데이터로 확인한다. 결과 `{route: ok | missing, missing: [...]}`. `missing`이면 서버를 띄우지 않고 `BLOCKED`(DDL 미반영)로 개발 승인에 간다.
- 같은 결정 안에서 DDL이 바뀌지 않았으면 다시 묻지 않는다.

### 7.4 그 밖

- 서버를 띄우는 step(기동 확인, 간이 확인)과 검증·자동 수정 Agent의 Tool을 `startTestServer`로 바꾼다. 인자는 `projectId`, `${state.projectRevision.revision}`, 개발 결과 폴더, 삭제 목록이다.
- 지금의 "한 step까지만 넘겨주기"는 없앤다. 서버는 실행 안에서 계속 쓴다(5.8절).
- step id 규칙: 없앤 step의 id는 다시 쓰지 않는다. 새 step은 지금 최댓값 + 1부터 붙인다. 흐름 순번은 `name` 앞의 `NN-`로 맞춘다.
- Agent 정의(`sm-verifier-agent`, `sm-auto-fix-agent`)의 프롬프트에서 `startSandboxServer`, 복제본, 시험 서버라는 말을 고친다. 고친 뒤에는 Agent 평가로 기준선과 비교한다.
- Skill `test-environment`에 판정 기준을 더한다: 기존 첨부 파일 없음(`data/`가 비어 있음), 잠금 대기 실패, DDL 미반영, 빌드된 리비전 없음은 `BLOCKED`.

## 11. 구현 단계

단계마다 끝나면 사람이 확인한다. 테스트는 `mvn test -DskipTests=false`. 실행 중인 엔진 jar를 그 자리에서 다시 빌드하지 않고, 사본을 다른 포트로 띄워 확인한다. testApp은 저장소 밖(`/app/testApp`)에 있으므로 그대로 대상으로 쓴다. 진행용 샘플은 `/app/dstone/temp/`에만 둔다.

| 단계 | 내용 | 확인 |
|---|---|---|
| 1 | 프로젝트 관리 화면·테이블·API(3장), 리비전 빌드(4장), `resolveProjectRevision` | testApp을 Maven으로 [Build] → 리비전 폴더·기록·현재 리비전. 실패·구조 입력 필요·같은 리비전 재사용 경우 |

## 12. 남은 위험

- 테스트 드라이버가 savepoint로 앱의 commit/rollback을 흉내 내는 방식은 이 설계의 가장 어려운 부분이다. 분산 트랜잭션(XA), 연결 수준 설정(격리 수준, readOnly, 스키마 전환)을 많이 쓰는 앱은 동작이 다를 수 있다. 3단계에서 먼저 확인한다.
- 설정 파일에서 URL을 찾아 바꾸는 방식은 URL을 조각으로 조립하는 앱에서 실패한다. 그때는 띄우지 않는 쪽으로 간다(안전 우선).
- Tomcat 7 전용 앱, Java 6·7 앱은 지원하지 않는다.
- 큰 레거시 앱에서 [Build] 시간과 리비전 폴더의 디스크 사용량은 아직 재지 않았다.

### 13.2 설계에서 달라진 점

- **드라이버 jar**: 별도 모듈 대신 소스를 리소스(`.javasrc`)로 두고 엔진이 처음 쓸 때 `--release 8`로 컴파일한다. 해시별로 `{작업 루트}/testdriver/`에 둔다. Maven 리소스 복사는 `.java`를 빼고 `${}`를 치환하므로 확장자를 바꾸고 치환 없이 복사한다.
- **드라이버 위치**: 실행 층 `WEB-INF/lib`가 아니라 `runs/{실행ID}/tomcat/lib`(공통 클래스로더)에 둔다. 실제 DB 드라이버는 요청 스레드의 클래스로더(앱)에서 찾는다.
- **context reload**: 이 환경의 Tomcat에는 Manager 앱이 없다. 그래서 Context 파일의 수정 시각을 바꾸고, Tomcat 로그에 그 파일 경로가 두 번(배치 시작·끝) 찍힐 때까지 기다린다. 30초 안에 시작하지 않으면 JVM을 다시 띄운다.
- **JSP 즉시 반영**: Jasper는 기본 4초 간격으로 파일을 본다. 실행 CATALINA_BASE의 `conf/web.xml`에 `modificationTestInterval=0`을 넣었다.
- **DDL 반영 확인**: 승인 step 하나(step61)와 Tool 하나(step60)로 만들었다. 사람이 "DDL 반영함"을 고르면 다시 확인하고, 아직 없으면 다시 묻는다.
- **원복 시점**: 실행이 승인 대기·일시정지로 루프를 벗어나면 서버(JVM)는 두고 DB만 원복한다. 몇 시간 동안 개발 DB에 잠금이 남지 않게 하려는 것이다.
- **삭제 목록**: 웹 파일은 Tomcat 기본 `RewriteValve`로 410을 돌려준다(Valve를 새로 만들지 않음).
- **URL을 찾지 못한 DB**: 등록한 DB가 하나도 발견되지 않을 때만 띄우지 않는다. 일부만 못 찾은 것은 "원래 환경과 다른 점"에 적고, 실제로 드라이버를 거치지 않는 연결이 생기면 서버를 내린다(우회 감지).
