## 1. 개요
처음엔 `dstone-ai-engine`의 RAG(Phase 2) 임베딩 전용으로만 설치했다 - Anthropic(Claude)은 임베딩 생성 API를 제공하지 않고, 이 환경엔 OpenAI API 키도 없어서 로컬에서 무료로 돌릴 수 있는 임베딩 모델이 필요했기 때문이다. ⚠️ **지금은 범위가 넓어졌다** - `conf/application.yml`의 `spring.ai.model.chat`이 `anthropic`이 아니라 `ollama`로 설정돼 있어서(비용 없이 로컬에서 채팅까지 테스트하려는 목적), 임베딩(`bge-m3`)뿐 아니라 **채팅(`qwen2.5-coder:7b`, 2절 참고)도 이 서버가 담당한다** - 더 이상 "채팅과는 무관"하지 않다(6절 참고). apt 패키지가 아닌 공식 tar.zst 배포판을 `/opt/ollama`에 수동 설치했고, kafka와 동일하게 systemd에 등록하지 않았다.

## 2. 설치 정보
- 버전: v0.33.3 (Linux amd64)
- 설치 방식: 수동 설치 (공식 GitHub Releases tar.zst)
- 설치 경로: `/opt/ollama`
- 모델 데이터 디렉터리: `/opt/ollama/data` (`OLLAMA_MODELS` 환경변수로 지정 - 홈 디렉터리 기본 경로 대신 kafka의 데이터 디렉터리처럼 설치 경로 안에 자체 포함시킴)
- 설치된 모델:
  - `bge-m3` - 다국어/한국어 지원 임베딩 모델, 1024차원. `dstone-ai-engine` RAG 전용, **채팅 불가**([15.ollama-webui-lite.md 8.2절](15.ollama-webui-lite.md#82-curl로-재현하면-error-모델명-does-not-support-chat) 참고)
  - `llama3.2` (3B) - [Ollama Web UI Lite](15.ollama-webui-lite.md)에서 수동 채팅 테스트용으로 처음 추가했던 모델. CPU 전용 + 가용 메모리 제약(`.wslconfig`상 이 WSL 환경 전체 할당 8GB 중, MySQL/PostgreSQL/Kafka/Jenkins 등을 함께 띄우면 `free -h` 기준 가용량이 2GB 안팎까지 줄어듦 - [02.environment.md 6.4절](../02.environment.md#64-대상-pc-준비) 참고) 때문에 가벼운 모델로 골랐다. 한동안 `dstone-ai-engine`의 `spring.ai.model.chat: ollama` 채팅 모델로도 같이 썼으나, Tool 호출(function calling)을 구조화된 형식으로 못 지키고 텍스트로 흉내만 내는 경우가 있어서 `qwen2.5-coder:7b`로 교체했다 - 지금은 Web UI Lite 수동 테스트용으로만 남아있다. 실제로 한국어 자유 응답을 시켜보면 3B급 소형 모델의 한계로 언어가 뒤섞이거나(예: 한국어 문장 중간에 영어/이탈리아어 단어가 공백 없이 끼어드는 등) 품질이 들쭉날쭉할 수 있다 - 이는 버그가 아니라 파라미터 규모의 한계다.
  - `qwen2.5-coder:7b` (7B) - `dstone-ai-engine`의 `spring.ai.model.chat: ollama` 채팅 모델(`conf/application.yml`). Ollama 라이브러리 기준 전 사이즈에 "tools" capability가 명시돼 있고, 작은 `llama3.2`보다 구조화된 Tool 호출을 더 안정적으로 지킨다고 알려져 있어서 골랐다 - 다만 7B라 `llama3.2`(3B)보다 추론이 느리다는 트레이드오프가 있다(`conf/application.yml`의 `spring.http.clients.read-timeout` 상향 조치와 함께 참고).

## 3. 설치 방법 (실제 수행된 절차)
최신 릴리스는 `.tgz`가 아니라 `.tar.zst`로 배포되므로 `zstd` 패키지가 먼저 필요하다.
```bash
sudo apt-get update -y
sudo apt-get install -y zstd

sudo mkdir -p /opt/ollama
sudo chown "$USER":"$USER" /opt/ollama
cd /opt/ollama

curl -L -o ollama.tar.zst \
  "https://github.com/ollama/ollama/releases/download/v0.33.3/ollama-linux-amd64.tar.zst"
tar --zstd -xf ollama.tar.zst
rm ollama.tar.zst
# -> /opt/ollama/bin/ollama, /opt/ollama/lib/ollama/* 생성됨

mkdir -p /opt/ollama/data /opt/ollama/logs
```

설치 확인:
```bash
/opt/ollama/bin/ollama --version
```

모델 pull(서버가 떠 있어야 함, [4절](#4-서비스-시작중지) 참고):
```bash
/opt/ollama/bin/ollama pull bge-m3
```

## 4. 서비스 시작/중지
전용 스크립트를 작성해 사용 중이다 (systemd 미등록, 수동 실행 - kafka와 동일한 PID파일 방식). 최상위 래퍼(`~/start.sh`/`~/stop.sh`가 호출):

```sh
# /usr/local/bin/start-ollama.sh
/opt/ollama/ollama-start.sh
echo "Ollama started !!! (dstone-ai-engine RAG 임베딩 전용 로컬 모델 런타임, http://localhost:11434)"
/opt/ollama-webui-lite/start.sh
echo "Ollama Web UI Lite started !!! http://localhost:3000"
```
```sh
# /usr/local/bin/stop-ollama.sh
/opt/ollama/ollama-stop.sh
echo "Ollama stopped !!!"
/opt/ollama-webui-lite/stop.sh
echo "Ollama Web UI Lite stopped !!!"
```

- `/opt/ollama/ollama-start.sh`: `OLLAMA_MODELS=/opt/ollama/data OLLAMA_HOST=[::]:11434 OLLAMA_ORIGINS=http://localhost:3000,http://127.0.0.1:3000 nohup bin/ollama serve`로 백그라운드 기동, PID를 `ollama-server.pid`에 기록. 이미 실행 중이면 중복 실행 방지. `OLLAMA_HOST=[::]:11434`(IPv6 wildcard, 리눅스에서 기본적으로 IPv4도 함께 받는 dual-stack)로 바인딩한다 - 원래 기본값(`127.0.0.1`, IPv4 전용)이었다가 [Ollama Web UI Lite](15.ollama-webui-lite.md) 연동 중 IPv6 루프백 미지원 문제로 넓혔다([7절](#7-문제-해결-ollama-web-ui-lite-연동-중-실제로-겪은-에러) 참고). mysql/redis도 WSL 네트워크 특성상 같은 이유로 바인딩을 넓힌 전례가 있다 - kind 브리지 게이트웨이(`172.18.0.1`)로의 실제 노출/방화벽 조정은 `dstone-ai-engine`을 kind에 배포하는 시점에 별도로 처리한다. `OLLAMA_ORIGINS`는 웹UI(포트 3000)의 브라우저 cross-origin 호출을 허용하기 위한 것.
- `/opt/ollama/ollama-stop.sh`: PID 파일 기준 `kill` (정상 종료 최대 30초 대기 후 `kill -9` 강제 종료).
- **(2026-09-09 추가)** `/usr/local/bin/start-ollama.sh`/`stop-ollama.sh`가 Ollama 서버와 [Ollama Web UI Lite](15.ollama-webui-lite.md)(관리 콘솔, 포트 3000)를 함께 기동/중지한다 - kafka가 [Kafbat UI](09.kafbat-ui.md)를 같이 다루는 것과 동일한 구조.

로그: `/opt/ollama/logs/ollama-server.out`

## 6. dstone 프로젝트에서의 역할
이 서버 하나를 `dstone-ai-engine`이 **두 가지 용도**로 같이 쓴다 - 임베딩(항상 이 역할)과 채팅(지금은 이 역할도 겸하고 있음, 1절 참고).

- **임베딩(RAG)**: `spring.ai.model.embedding: ollama`(`conf/application.yml`)가 이 서버를 가리킨다(`spring.ai.ollama.base-url: http://localhost:11434`, `spring.ai.ollama.embedding.model: bge-m3`). `net.dstone.ai.rag.RagService`가 문서를 청크로 쪼갠 뒤 이 임베딩 모델로 벡터화해서 [PostgreSQL(pgvector)](05.postgresql.md#6-dstone-프로젝트에서의-역할)에 저장하고, ragEnabled인 Agent의 RAG-증강 채팅이 검색 시에도 같은 `RagService`를 통해 동일한 모델로 질의를 벡터화한다(상세: [09.dstone-ai-engine.md 7절](../09.dstone-ai-engine.md#7-session--rag--security)). `dstone.ai.rag.enabled=false`(또는 미설정)면 이 서버가 없어도 `dstone-ai-engine`은 그대로 기동된다.
- **채팅**: `spring.ai.model.chat: ollama`(`conf/application.yml`)이면 `POST /api/ai/chat`의 실제 LLM 호출도 이 서버(`spring.ai.ollama.chat.options.model: qwen2.5-coder:7b`)가 처리한다 - `anthropic`/`openai`로 바꾸면 이 서버는 더 이상 채팅에 관여하지 않는다(2절 참고).

## 7. 문제 해결 (Ollama Web UI Lite 연동 중 실제로 겪은 에러)

### 7.1 웹UI에서 채팅 시 `Uh-oh! There was an issue connecting to Ollama.`
- **증상**: http://localhost:3000 페이지 자체는 정상 로딩되는데, 모델 목록 조회는 되는 경우도 있으나 채팅(`/api/chat`) 요청이 브라우저에서 실패한다.
- **원인**: Ollama가 `OLLAMA_HOST` 기본값(`127.0.0.1`, **IPv4 전용**)으로만 리슨하고 있었다. [Ollama Web UI Lite](15.ollama-webui-lite.md)를 서빙하는 Vite 개발 서버는 IPv4/IPv6를 모두 열어두는데, 브라우저가 `localhost`를 IPv6(`::1`)로 먼저 시도하면 Ollama가 IPv6 루프백은 듣고 있지 않아 그 자리에서 connection refused가 나고, 이게 브라우저 fetch() 자체의 실패(네트워크 레벨)로 이어져 위 메시지가 뜬다. CORS 문제가 아니었다 - `curl -H "Origin: ..."`로 확인한 CORS 헤더는 처음부터 정상이었음.
  ```bash
  # 진단: IPv4는 되는데 IPv6는 거부됨
  curl -4 http://127.0.0.1:11434/api/tags   # 정상
  curl -6 http://[::1]:11434/api/tags       # Connection refused
  ```
- **조치**: `OLLAMA_HOST=[::]:11434`(IPv6 wildcard - 리눅스에서 기본적으로 IPv4 연결도 함께 받는 dual-stack)로 바인딩을 넓혔다([4절](#4-서비스-시작중지) 참고). 재시작 후 `curl -6 http://[::1]:11434/api/tags`도 정상 응답하는 것으로 확인.

## 8. WSL에서 GPU미사용 으로 인한 과부하 문제

**환경**: Windows 11 + WSL2(Ubuntu) / CPU: AMD Ryzen 7 250 / iGPU: AMD Radeon 780M(아키텍처 `gfx1103`) / ROCm 7.14.x 계열.

### 8.1 증상
`qwen2.5-coder:7b`(6절 참고) 실행 중 `ollama ps` 결과가 아래처럼 GPU를 전혀 쓰지 못하고 CPU로만 돌고 있었다 (CPU-only 추론이라 응답이 느려 `read-timeout` 상향이 필요했던 것도 이 때문 - 2절 참고).
```text
PROCESSOR
100% CPU
```

### 8.2 WSL2의 AMD GPU 접근 계층
WSL2에서 AMD iGPU는 native Linux(`/dev/kfd`, `/dev/dri`)와 다른 경로를 탄다 - 이 두 장치가 없는 것이 WSL2에서는 정상이다.
```text
Windows GPU → WSL2 GPU-PV(dxgkrnl) → /dev/dxg → ROCDXG(librocdxg) → ROCm(HSA/HIP) → gfx1103
```

### 8.3 진단
```bash
ls -l /dev/dxg                    # WSL2 DirectX GPU 장치 존재 확인 (정상)
ls -ld /sys/module/dxgkrnl        # dxgkrnl 커널 모듈 확인 (정상)
rocminfo                          # 최초 실행 시 오류 발생
```
`rocminfo`가 아래 오류로 실패했다 - `/dev/dxg`가 존재하는 것만으로는 ROCm GPU 인식이 완성되지 않는다는 뜻이었다.
```text
WSL environment detected.
hsa api call failure at: ./rocminfo.cc:1324
Call returned HSA_STATUS_ERROR_OUT_OF_RESOURCES
```

### 8.4 ROCm 설치 및 dpkg 복구
```bash
sudo amdgpu-install -y --usecase=rocm --no-dkms
```
`--no-dkms`인 이유: Ryzen 7 250 / Radeon 780M 같은 APU/iGPU는 WSL2의 inbox kernel driver를 쓰는 구조라 커널 모듈 빌드(DKMS)가 불필요하다.

설치 도중 WSL VHDX 용량 부족으로 dpkg가 중단됐다(Input/output error, bus error 등). WSL 저장공간을 확보한 뒤 복구:
```bash
dpkg --configure -a
apt-get --fix-broken install
apt-get install --reinstall amdrocm-blas7.14-gfx942   # 잔존하던 gfx942 패키지 재설치
dpkg --audit                                           # 문제 없음 확인
```

Radeon 780M(gfx1103)에 필요한 패키지가 설치돼 있는지 확인:
```bash
dpkg -l | grep amdrocm-blas7.14-gfx1103
```

### 8.5 ROCDXG 누락 및 설치
WSL2에서 ROCm이 `/dev/dxg`로 GPU에 접근하려면 ROCDXG(`librocdxg`) 계층이 별도로 필요한데, 처음엔 이게 빠져 있었다.
```bash
ldconfig -p | grep -i dxg                              # 결과 없음
find /opt/rocm -iname '*dxg*' -o -iname '*wsl*'         # 결과 없음
```
설치:
```bash
cd /tmp
wget https://github.com/ROCm/librocdxg/releases/download/v1.2.1/rocdxg-roct_1.2.1_amd64.deb
sudo apt install -y ./rocdxg-roct_1.2.1_amd64.deb
sudo ldconfig
```

### 8.6 ROCm 정상화 확인
```bash
rocminfo | grep -E "Name:|Marketing Name:|Vendor Name:"
```
```text
Name:                    gfx1103
Marketing Name:          AMD Radeon(TM) 780M Graphics
Vendor Name:             AMD
```
WSL2 → ROCm 계층에서 Radeon 780M(gfx1103)이 정상적으로 인식됐다.

### 8.7 남은 문제 - Ollama는 아직 ROCm backend를 쓰지 않음
ROCm 계층을 정상화한 뒤에도 `./ollama ps`는 여전히 `100% CPU`였다. 즉 **"WSL→ROCm GPU 인식"과 "Ollama가 ROCm backend를 실제로 사용"은 별개 문제**다. 설치된 Ollama(`/opt/ollama/lib/ollama`)에는 `cuda_v12`/`cuda_v13`/`vulkan` 백엔드는 있었지만 `libamdhip64`/`librocm` 계열 ROCm 백엔드 파일은 확인되지 않아 추가 확인이 필요한 상태로 남아 있다.

향후 확인 절차:
```bash
pkill -f "ollama serve"
export HSA_ENABLE_DXG_DETECTION=1
export OLLAMA_DEBUG=1
cd /opt/ollama
./bin/ollama serve
```
다른 터미널에서:
```bash
cd /opt/ollama
./bin/ollama run qwen2.5-coder:7b
./bin/ollama ps    # PROCESSOR가 100% GPU 또는 GPU/CPU 혼합인지 확인
```

### 8.8 주의사항
ROCm 자체는 정상 동작 중이므로 아래처럼 파괴적인 정리나 ROCm 재설치는 추가로 하지 않는다.
```bash
apt purge 'amdrocm*'
apt autoremove
```
남은 작업은 Ollama의 ROCm backend 연결/선택 문제 확인이다.
