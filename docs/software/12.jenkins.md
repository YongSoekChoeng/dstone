## 1. 개요
dstone-boot, dstone-batch, dstone-batchadmin, dstone-ai-engine의 CI/CD 파이프라인(`Jenkinsfile`)을 실행하는 자동화 서버.

## 2. 설치 정보
- 버전: 2.568.3
- 설치 방식: Jenkins 공식 apt 저장소 (`pkg.jenkins.io`)
- 저장소 등록 파일: `/etc/apt/sources.list.d/jenkins.list`
```
deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/
```
- JENKINS_HOME: `/var/lib/jenkins`
- 실행 WAR: `/usr/share/java/jenkins.war`

## 3. 설치 방법
```bash
sudo mkdir -p /etc/apt/keyrings
curl -fsSL https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key | \
  sudo tee /etc/apt/keyrings/jenkins-keyring.asc > /dev/null

echo "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/" | \
  sudo tee /etc/apt/sources.list.d/jenkins.list > /dev/null

sudo apt update
sudo apt install -y jenkins
```
Jenkins는 JDK가 필요하므로 [JDK](01.jdk.md) 설치가 선행되어야 한다.

## 4. 서비스 설정
설정 파일: `/etc/default/jenkins`
```
JENKINS_USER=jenkins
JENKINS_GROUP=jenkins
JENKINS_WAR=/usr/share/java/jenkins.war
JENKINS_HOME=/var/lib/jenkins
HTTP_PORT=8080
JENKINS_ARGS="--webroot=/var/cache/jenkins/war --httpPort=8080"
```
- 포트: 8080
- `jenkins.service`는 systemd에 `enabled` 상태로 등록되어 있다 (다른 서비스와 달리 부팅 시 자동 기동 대상).

## 5. 서비스 시작/중지
```sh
# /usr/local/bin/start-jenkins.sh
sudo systemctl start jenkins
echo "Jenkins started !!!"
```
```sh
# /usr/local/bin/stop-jenkins.sh
sudo systemctl stop jenkins
echo "Jenkins stopped !!!"
```
`jenkins.service`는 [4절](#4-서비스-설정)에서 언급한 대로 **enabled**라 WSL 부팅 시 이미 떠 있는 경우가 대부분이며, 이 경우 `start-jenkins.sh`는 사실상 no-op이다. postgresql과 마찬가지로 정지 후에는 자동으로 다시 뜨지 않는다.

## 6. 초기 설정
```bash
sudo cat /var/lib/jenkins/secrets/initialAdminPassword   # 최초 관리자 비밀번호
```
브라우저에서 http://localhost:8080 접속 → 위 비밀번호 입력 → 플러그인 설치 화면에서 **"Install suggested plugins"(추천 플러그인 설치)**를 선택하면 충분하다. Git, GitHub, Pipeline(`workflow-aggregator`), SSH Credentials 등 기본 플러그인이 여기에 포함된다. **Docker/Kubernetes 전용 Jenkins 플러그인은 설치할 필요가 없다** — 네 `Jenkinsfile` 모두 `docker`/`kubectl` CLI를 `sh` 스텝으로 직접 호출하는 방식이라 플러그인이 CLI를 대신할 필요가 없기 때문이다. 이후 관리자 계정 생성 마법사를 완료하면 대시보드로 진입한다.

## 7. docker/kubectl 실행 권한
`dstone-boot` 파이프라인이 Jenkins 에이전트(로컬 실행)에서 직접 `docker build/push`, `kubectl apply`를 수행하므로 `jenkins` 시스템 계정이 `docker` 그룹에 속해 있어야 한다.
```bash
sudo usermod -aG docker jenkins
sudo systemctl restart jenkins   # 그룹 변경은 프로세스 재시작 후에 적용됨
groups jenkins                    # "jenkins docker" 확인
```
`/etc/kind/dev.config`(KUBECONFIG)도 `docker` 그룹에 read 권한이 열려 있어(`chmod g+r`) 별도 설정 없이 읽을 수 있다. `dstone-batch`/`dstone-batchadmin` 파이프라인은 배포 파일을 별도 디렉터리가 아니라 리포지토리 자기 자신(`/app/dstone/dstone-batch`, `/app/dstone/dstone-batchadmin`)에 직접 복사하므로, `jenkins` 계정이 `jysn007` 그룹(리포지토리 소유 그룹)에도 속해 있어야 하고 두 디렉터리(및 하위 `target`/`conf`/`bin`)에 그룹 쓰기 권한(setgid)이 필요하다 — 없다면 `sudo usermod -aG jysn007 jenkins && sudo systemctl restart jenkins`, `sudo chmod g+ws /app/dstone/dstone-batch /app/dstone/dstone-batchadmin`.

## 8. dstone 프로젝트에서의 역할
- `dstone-boot/Jenkinsfile`, `dstone-ai-engine/Jenkinsfile`: Maven 리액터 빌드 → Docker 이미지 빌드/푸시(로컬 레지스트리) → kind 클러스터에 `kubectl`로 배포(둘 다 완전히 동일한 패턴 - `dstone-ai-engine`은 파이프라인 자체는 준비돼 있으나 이 클러스터에서 아직 실행/최초 배포한 적은 없다)
- `dstone-batch/Jenkinsfile`, `dstone-batchadmin/Jenkinsfile`: Maven 리액터 빌드 → 리포지토리 자기 자신의 모듈 디렉터리(`/app/dstone/<module>`)로 복사 → 해당 모듈의 `bin/stopApp.sh`+`bin/startApp.sh`로 재기동(VM 스타일, systemd 미사용)
- 파이프라인 실행에는 [Maven](02.maven.md), [JDK](01.jdk.md), [Docker](10.docker.md), [kubernetes](11.kubernetes.md)(dstone-boot에 한함)가 함께 필요하다. 설계 배경은 [04.cloud-architecture.md](../04.cloud-architecture.md) 참고.

## 9. Pipeline 구축 가이드 — 개요와 범위

이 절(9~17)부터는 **특정 프로젝트에 종속되지 않는 범용 가이드**다. dstone의 기존 4개 Job(`dstone-boot-deploy` 등)은
[04.cloud-architecture.md 5절](../04.cloud-architecture.md#5-cicd-파이프라인)에 별도로 정리돼 있고(로컬
`file:///app/dstone` 체크아웃 전제), 여기서는 **"GitHub 원격 저장소를 쓰는, 이 저장소와 무관한 새 프로젝트에
Jenkins Pipeline을 처음부터 구축한다"**는 상황을 기준으로 전체 절차를 처음부터 끝까지 다룬다. 새 프로젝트에
파이프라인을 만들 때는 이 절만 보고 그대로 따라 하면 된다.

다루는 범위:
1. GitHub SSH 자격증명을 Jenkins에 등록한다 (10절)
2. Pipeline Job을 만든다 — 웹 화면으로, 또는 REST API로 (11~12절)
3. `Jenkinsfile`을 작성한다 — 표준 스테이지 구성과 완전한 예시 (13절)
4. `jenkins` 시스템 계정과 실제 배포 대상 디렉터리를 공유하기 위한 권한을 준비한다 (14절)
5. **빌드가 끝나도 배포한 서버 프로세스가 죽지 않도록** 만든다 — 이 환경에서 가장 까다로웠던 문제 (15절)
6. 빌드를 트리거하고 결과를 확인한다 (16절)
7. 자주 만나는 문제를 체크리스트로 훑는다 (17절)

전제 조건: [2~6절](#2-설치-정보)의 설치·초기 설정이 끝나 있어야 한다("Install suggested plugins"로 Git/GitHub/
Pipeline/SSH Credentials 플러그인까지 이미 설치돼 있다는 뜻).

## 10. GitHub 저장소 연결 준비 (SSH 자격증명 등록)

Jenkins는 `jenkins`라는 별도 시스템 계정으로 구동되므로(2절), 사람이 평소 쓰는 계정(예: `jysn007`)의
SSH 설정을 자동으로 물려받지 않는다. GitHub 저장소를 `git@github.com:...` SSH 주소로 체크아웃하려면
**Jenkins 전용 자격증명을 Jenkins Credentials Store에 별도로 등록**해야 한다.

### 10.1 사용할 SSH 키 결정

두 가지 방법이 있다.

- **A. 기존 개인 키 재사용** — 이미 GitHub에 등록된 사람 계정의 키(예: `~/.ssh/id_ed25519`)를 그대로
  Jenkins Credential로 등록한다. 가장 빠르지만, 그 사람 키가 접근 가능한 **모든** 저장소에 Jenkins도
  접근하게 된다(개인 개발 환경에서는 실용적인 절충).
- **B. Jenkins 전용 키 새로 발급(권장, 특히 여러 사람이 쓰는 환경)** — 저장소별 Deploy Key로 등록하면
  권한 범위를 그 저장소 하나로 좁힐 수 있다.

```bash
# B안: jenkins 전용 키를 새로 만드는 경우
sudo -u jenkins mkdir -p /var/lib/jenkins/.ssh
sudo -u jenkins ssh-keygen -t ed25519 -N "" -f /var/lib/jenkins/.ssh/github_deploy -q
sudo cat /var/lib/jenkins/.ssh/github_deploy.pub
```
출력된 공개키를 GitHub 저장소의 **Settings → Deploy keys → Add deploy key**에 등록한다(쓰기까지
필요 없으면 "Allow write access"는 체크하지 않는다). A안(개인 키 재사용)이면 이 단계는 건너뛰고
바로 아래로 넘어간다.

### 10.2 Jenkins에 known_hosts 등록

Jenkins(`jenkins` 계정)가 처음으로 `github.com`에 접속하면 호스트 키 확인에서 막힌다
(`Host key verification failed`) — 미리 등록해 둔다.
```bash
ssh-keyscan -t ed25519 github.com | sudo tee -a /var/lib/jenkins/.ssh/known_hosts
sudo chown jenkins:jenkins /var/lib/jenkins/.ssh/known_hosts
sudo chmod 600 /var/lib/jenkins/.ssh/known_hosts
```

### 10.3 Jenkins Credential로 등록

**Jenkins 관리 → Credentials → System → Global credentials (unrestricted) → Add Credentials**
- **Kind**: `SSH Username with private key`
- **Scope**: `Global`
- **ID**: 원하는 식별자(예: `github-<repo>-deploy-key`) — Job 설정에서 이 ID로 선택한다
- **Username**: `git` (GitHub SSH 규약상 항상 `git`)
- **Private Key**: `Enter directly` 선택 → 10.1에서 만든/재사용할 **개인키 전체 내용**을 붙여넣는다
  (`cat /var/lib/jenkins/.ssh/github_deploy` 또는 개인 키 파일 내용)
- **Passphrase**: 키에 암호가 없으면 비워 둔다

REST API로 등록하고 싶다면(스크립트로 여러 Job을 한 번에 준비할 때 유용) 12.3절의 방식을 그대로 쓰면 된다 —
`createCredentials` 엔드포인트에 `com.cloudbees.plugins.credentials.impl.BasicSSHUserPrivateKey` 클래스로
POST한다. 전체 예시는 12.3절 참고.

## 11. Pipeline Job 생성 — 웹 UI

1. `http://localhost:8080` 접속 → 왼쪽 메뉴 **New Item**
2. **Enter an item name**에 Job 이름 입력(예: `myapp-deploy`) → 항목 유형 **Pipeline** 선택 → **OK**
3. **General** 탭: Description에 파이프라인이 하는 일을 한 줄로 메모(선택)
4. 아래로 스크롤해 **Pipeline** 섹션:
   - **Definition**: `Pipeline script from SCM`
   - **SCM**: `Git`
   - **Repository URL**: `git@github.com:<owner>/<repo>.git`
   - **Credentials**: 10.3에서 등록한 Credential 선택
   - **Branches to build**: `*/main` (기본 브랜치 이름에 맞게)
   - **Script Path**: 저장소 루트의 `Jenkinsfile`이면 그냥 `Jenkinsfile`, 모노레포라 서브디렉터리에
     있으면 `<module>/Jenkinsfile`처럼 정확한 상대경로
5. **Save**
6. 왼쪽 메뉴 **Build Now** → Build History에 새 빌드 번호가 생기고 진행 중 표시(회전 아이콘)
7. 빌드 번호 클릭 → **Console Output**에서 실시간 로그 확인

## 12. Pipeline Job 생성 — REST API (자동화용)

Job 생성·자격증명 등록·빌드 트리거·로그 조회를 전부 REST API로도 할 수 있다 — 웹 화면 조작 없이
스크립트로 반복 가능한 구축이 필요할 때(예: 여러 프로젝트에 같은 패턴의 Job을 한 번에 찍어낼 때)
유용하다. 모든 변경 요청(POST)에는 CSRF 크럼(crumb)이 필요하다.

### 12.1 인증 확인

```bash
curl -s -u "<user>:<password-or-api-token>" -o /dev/null -w "%{http_code}\n" \
  http://localhost:8080/api/json
# 200이면 인증 OK
```
비밀번호 대신 **API 토큰**을 쓰는 게 더 안전하다 — 사용자 이름 클릭 → **Configure** → **API Token** →
**Add new Token**으로 발급.

### 12.2 크럼(CSRF 토큰) 발급 + 쿠키 유지

```bash
COOKIE_JAR=/tmp/jenkins-cookies.txt
CRUMB_JSON=$(curl -s -c "$COOKIE_JAR" -u "<user>:<token>" \
  "http://localhost:8080/crumbIssuer/api/json")
CRUMB=$(echo "$CRUMB_JSON" | python3 -c "import json,sys;print(json.load(sys.stdin)['crumb'])")
```
이후 모든 POST 요청에 `-b "$COOKIE_JAR" -c "$COOKIE_JAR" -H "Jenkins-Crumb: $CRUMB"`를 그대로 붙인다
(크럼 발급 때 받은 세션 쿠키와 짝이 맞아야 하므로, 쿠키 저장 없이 크럼만 재사용하면 `403 No valid
crumb`가 난다).

### 12.3 SSH Credential 등록 (10.3절의 REST API 버전)

```bash
python3 - <<'PYEOF'
import json
privkey = open('/path/to/private_key').read()
payload = {
    "": "0",
    "credentials": {
        "scope": "GLOBAL",
        "id": "github-myrepo-deploy-key",
        "username": "git",
        "privateKeySource": {
            "value": "0",
            "privateKey": privkey,
            "stapler-class": "com.cloudbees.jenkins.plugins.sshcredentials.impl.BasicSSHUserPrivateKey$DirectEntryPrivateKeySource"
        },
        "passphrase": "",
        "description": "GitHub SSH key",
        "$class": "com.cloudbees.jenkins.plugins.sshcredentials.impl.BasicSSHUserPrivateKey"
    }
}
json.dump(payload, open('/tmp/cred.json', 'w'))
PYEOF

curl -s -b "$COOKIE_JAR" -c "$COOKIE_JAR" -u "<user>:<token>" -H "Jenkins-Crumb: $CRUMB" \
  -X POST "http://localhost:8080/credentials/store/system/domain/_/createCredentials" \
  --data-urlencode "json@/tmp/cred.json"
```

### 12.4 Job 생성

Job 설정은 `config.xml`(Pipeline job의 XML 정의) 하나로 표현된다. 최소 구성:

```xml
<?xml version="1.1" encoding="UTF-8"?>
<flow-definition plugin="workflow-job">
  <description>myapp 배포 파이프라인</description>
  <keepDependencies>false</keepDependencies>
  <properties/>
  <definition class="org.jenkinsci.plugins.workflow.cps.CpsScmFlowDefinition" plugin="workflow-cps">
    <scm class="hudson.plugins.git.GitSCM" plugin="git">
      <configVersion>2</configVersion>
      <userRemoteConfigs>
        <hudson.plugins.git.UserRemoteConfig>
          <url>git@github.com:<owner>/<repo>.git</url>
          <credentialsId>github-myrepo-deploy-key</credentialsId>
        </hudson.plugins.git.UserRemoteConfig>
      </userRemoteConfigs>
      <branches>
        <hudson.plugins.git.BranchSpec>
          <name>*/main</name>
        </hudson.plugins.git.BranchSpec>
      </branches>
      <doGenerateSubmoduleConfigurations>false</doGenerateSubmoduleConfigurations>
      <submoduleCfg class="empty-list"/>
      <extensions/>
    </scm>
    <scriptPath>Jenkinsfile</scriptPath>
    <lightweight>true</lightweight>
  </definition>
  <triggers/>
  <disabled>false</disabled>
</flow-definition>
```

```bash
curl -s -b "$COOKIE_JAR" -c "$COOKIE_JAR" -u "<user>:<token>" -H "Jenkins-Crumb: $CRUMB" \
  -H "Content-Type: application/xml" \
  -X POST "http://localhost:8080/createItem?name=myapp-deploy" \
  --data-binary @job-config.xml
```
확인: `curl -s -u "<user>:<token>" http://localhost:8080/job/myapp-deploy/api/json`

빌드 트리거·로그 조회는 16절 참고.

## 13. Jenkinsfile 작성 가이드

로컬 VM 스타일 배포(`dstone-batch`/`dstone-batchadmin`과 같은, systemd 없이 `bin/*.sh` 스크립트로
기동하는 방식 — dstone 프로젝트의 표준 배포 방식이다)를 기준으로 한 표준 스테이지 구성이다. Docker/K8s
배포(`dstone-boot` 패턴)는 [04.cloud-architecture.md 5절](../04.cloud-architecture.md#5-cicd-파이프라인)
쪽 예시를 참고하고, 여기서는 "빌드 → 배포 디렉터리 동기화 → 프로세스 재기동" 패턴에 집중한다.

```groovy
pipeline {
    agent any

    environment {
        APP_NAME = 'myapp'
        DEPLOY_DIR = '/app/myapp'   // 실제 서비스가 도는 안정된 경로 (Jenkins 워크스페이스와 별개)
    }

    stages {
        stage('Checkout') {
            steps {
                echo '====== Git Checkout ======'
                checkout scm
            }
        }

        stage('Build') {
            steps {
                echo '====== Maven Build (fail-fast 검증용) ======'
                // Jenkins 자신의 워크스페이스에서 먼저 한 번 빌드해서 실패를 빨리 알아챈다.
                sh 'mvn -q -DskipTests clean package'
            }
        }

        stage('Sync to Deploy Dir') {
            steps {
                echo '====== 배포 경로로 동기화 ======'
                // --no-perms --no-owner --no-group --omit-dir-times: jenkins 계정이 배포 경로의
                // 기존 파일을 소유하지 않은 경우(14절) 메타데이터 변경 권한이 없어 rsync가 실패한다 -
                // 내용만 맞추면 충분하므로 메타데이터 보존은 전부 끈다.
                sh '''
                    mkdir -p ${DEPLOY_DIR}
                    rsync -rL --no-perms --no-owner --no-group --omit-dir-times \
                          --delete --exclude=.git --exclude=target ./ ${DEPLOY_DIR}/
                    chmod +x ${DEPLOY_DIR}/bin/*.sh
                '''
            }
        }

        stage('Stop Existing Process') {
            steps {
                echo '====== Stop Existing Process ======'
                sh '${DEPLOY_DIR}/bin/stopApp.sh || true'
            }
        }

        stage('Deploy') {
            steps {
                echo '====== Deploy(Build+Start) Application ======'
                // 오래 떠 있어야 하는 서버 프로세스를 여기서 띄운다면 반드시 15절을 먼저 읽는다 -
                // 아무 조치 없이 그냥 백그라운드로 띄우면 빌드가 끝나는 순간 죽는다.
                sh '${DEPLOY_DIR}/bin/startApp.sh'
            }
        }

        stage('Health Check') {
            steps {
                echo '====== Health Check ======'
                sh '''
                    sleep 15
                    ${DEPLOY_DIR}/bin/statusApp.sh
                    ${DEPLOY_DIR}/bin/statusApp.sh | grep -q RUNNING
                '''
            }
        }
    }

    post {
        success {
            echo '====== Deployment Successful ======'
        }
        failure {
            echo '====== Deployment Failed ======'
            sh 'tail -100 ${DEPLOY_DIR}/logs/*.out || true'
        }
    }
}
```

스테이지별 요점:
- **Checkout**: `checkout scm` 한 줄로 충분 — Job 설정(11/12절)에서 지정한 저장소/브랜치를
  그대로 받아온다.
- **Build**: 배포 스크립트가 어차피 다시 빌드하더라도(아래 Deploy), 여기서 한 번 먼저 빌드해 두면
  컴파일 실패가 "Build" 스테이지에서 바로 드러나 원인 파악이 쉽다.
- **Sync to Deploy Dir**: Jenkins 워크스페이스(`/var/lib/jenkins/workspace/<job>`)는 Job을 지우면
  같이 사라지는 임시 공간이다. 실제로 서비스가 참조하는 "안정된 경로"(`DEPLOY_DIR`)로 내용을
  옮겨야 한다 — dstone-batch/batchadmin처럼 **리포지토리 자기 자신의 모듈 디렉터리**를 배포 대상으로
  삼아도 되고(이 경우 이 스테이지는 필요 없다 — Checkout이 이미 그 경로), testApp처럼 **완전히 별도
  경로**를 배포 대상으로 둬도 된다(이 경우 이 스테이지로 옮겨야 한다). 권한 문제는 14절.
- **Stop Existing Process / Deploy**: 재기동은 항상 "정지 → 정리 → 기동" 순서로 한다 — `bin/startApp.sh`
  자체가 내부적으로 먼저 정지를 한 번 더 시도하더라도(멱등성 확보), 별도 스테이지로 나눠두면 Console
  Output에서 "정지가 안 돼서 실패했는지" "기동이 안 돼서 실패했는지"를 구분하기 쉽다.
- **Health Check**: `sleep`으로 기동 시간을 확보한 뒤 상태를 확인하고, 실패 시 빌드 자체를 실패
  처리한다(`grep -q RUNNING`의 종료 코드가 그대로 스테이지 실패로 이어진다).
- **post.failure**: 실패했을 때 로그 꼬리를 Console Output에 자동으로 남겨두면, 실패할 때마다 서버에
  따로 접속해서 로그를 뒤질 필요가 없다.

## 14. 배포 대상 디렉터리 권한 준비 (jenkins ↔ 다른 OS 계정 간 파일 공유)

`DEPLOY_DIR`이 `jenkins`가 아닌 다른 OS 계정(예: 평소 개발하는 `jysn007`) 소유라면, `jenkins` 계정이
그 안에 파일을 쓰거나 프로세스를 정지시킬 권한이 기본적으로 없다. 두 계정이 같은 디렉터리를 번갈아
쓰려면 아래 3가지를 갖춰야 한다.

### 14.1 그룹 공유

```bash
sudo usermod -aG <다른계정> jenkins     # 예: sudo usermod -aG jysn007 jenkins
sudo systemctl restart jenkins          # 그룹 변경은 프로세스 재시작 후에 적용됨
groups jenkins                          # "jenkins <다른계정>" 확인
```

### 14.2 ACL로 그룹 쓰기 권한 부여

`chmod g+w` + `setgid`만으로는 **나중에 새로 생기는 파일**의 권한까지 완전히 보장되지 않는다(생성
프로세스의 umask에 따라 그룹 쓰기 비트가 빠질 수 있다). ACL의 **default ACL**을 걸어두면 이후 생성되는
모든 파일/디렉터리에 확실하게 상속된다.
```bash
sudo apt install -y acl   # 최초 1회
sudo setfacl -R  -m u:<계정A>:rwX,u:<계정B>:rwX <디렉터리>      # 기존 파일에 적용
sudo setfacl -R -d -m u:<계정A>:rwX,u:<계정B>:rwX <디렉터리>      # 이후 새로 생기는 파일에도 상속
```
예) `jysn007`과 `jenkins`가 `/app/myapp`과 배포 대상 서버(예: `/opt/tomcat9`)를 둘 다 건드려야 하면
두 경로 모두에 위 명령을 각각 실행한다.

### 14.3 Maven 빌드는 `clean`으로

같은 `target/` 디렉터리를 서로 다른 계정이 번갈아 빌드하면, 상대방이 만든 파일을 "덮어쓰기"할 때
**리눅스는 소유자가 아니면 파일의 메타데이터(수정시각 등)를 바꿀 권한을 안 준다** — 그룹 쓰기 권한이나
ACL로도 이건 못 푼다(파일 내용 쓰기와 메타데이터 변경은 별개의 권한 규칙이다). `mvn package` 대신
`mvn clean package`를 쓰면 매번 `target/`을 통째로 새로 만드므로, 새로 빌드하는 쪽이 모든 파일의
소유자가 되어 이 문제를 피할 수 있다.

## 15. 빌드가 끝나도 데몬 프로세스를 살려두기 (핵심 트러블슈팅)

**증상**: `bin/startApp.sh`로 서버(Tomcat, Spring Boot 등 오래 떠 있어야 하는 프로세스)를 띄우면
Health Check까지는 `RUNNING`으로 정상 통과하는데, 빌드가 끝나고 몇 초~수십 초 뒤 그 프로세스가
(강제 종료가 아니라 애플리케이션 자체 종료 절차를 밟으면서) 조용히 죽어 있다.

**원인**: Jenkins Pipeline의 Durable Task 플러그인은 `sh` 스텝(정확히는 스텝 하나하나, 나아가 빌드
전체)이 끝나면 **그 스텝/빌드가 띄운 프로세스를 정리(kill)한다.** 이 WSL 환경에서는 아래를 전부
시도했지만 전부 실패했다 — 어떤 걸 시도하든 결국 몇 초 뒤에 조용히 죽었다.

| 시도한 방법 | 결과 |
|---|---|
| `startup.sh`가 자체적으로 `nohup ... &`로 백그라운드 실행 | 실패 |
| `nohup setsid <cmd> < /dev/null > log 2>&1 & disown` (세션 완전 분리) | 실패 |
| `BUILD_ID=dontKillMe`, `JENKINS_SERVER_COOKIE` 등 Jenkins 전용 환경변수를 실행 직전에 unset | 실패 |
| `at(1)`/`atd` 큐에 제출(별도 데몬이 실행하는 완전히 무관한 프로세스) | 실패 — `at`이 **제출 시점의
환경변수를 그대로 job 스크립트에 박아 넣기** 때문에, Jenkins 환경변수를 지우지 않고 제출하면 job에도
그대로 남아 똑같이 걸린다 |
| `at` 제출 "직전"에 Jenkins 환경변수를 unset | 실패 (그래도 죽었다 — 정확한 매칭 기준은 끝내
특정하지 못함) |
| `loginctl enable-linger jenkins` (systemd 사용자 세션이 로그아웃 후에도 유지되도록) | 실패 |

**최종 해법 — `ssh localhost`로 완전히 새 로그인 세션을 만든다.** SSH 접속은 PAM이 **처음부터 끝까지
새로운 로그인 세션**을 만들어주므로, Jenkins가 무엇을 기준으로 "자기 빌드가 띄운 프로세스"를 판단하든
그것과 아예 무관한 세션이 된다. 실전에서 검증된 유일한 방법이었다.

```bash
# 1) jenkins 전용 SSH 키 생성(최초 1회, 10.1절과 별개로 "localhost 배포용" 키를 따로 둔다)
sudo -u jenkins mkdir -p /var/lib/jenkins/.ssh
sudo -u jenkins ssh-keygen -t ed25519 -N "" -f /var/lib/jenkins/.ssh/localhost_deploy -q
sudo cat /var/lib/jenkins/.ssh/localhost_deploy.pub

# 2) 그 공개키를, 서버 프로세스를 실제로 띄울 계정(예: jysn007)의 authorized_keys에 등록
echo "<위에서 나온 공개키>" >> ~/.ssh/authorized_keys
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys

# 3) 동작 확인
sudo -u jenkins ssh -i /var/lib/jenkins/.ssh/localhost_deploy \
  -o StrictHostKeyChecking=accept-new -o BatchMode=yes jysn007@localhost 'whoami'
# "jysn007"이 출력되면 성공
```

`bin/startApp.sh`에서는 실행 계정을 구분해서, `jenkins`로 실행될 때만 이 SSH 경로를 태운다(사람이
직접 실행할 때는 `at(1)` 큐 제출만으로 충분히 잘 동작했다 — 문제는 어디까지나 Jenkins가 실행할 때만
생긴다).

```bash
START_CMD="export JAVA_HOME='$JAVA_HOME'; echo \$\$ > '$PID_FILE'; exec '<서버 실행 커맨드>' >> '<로그파일>' 2>&1"

if [ "$(whoami)" = "jenkins" ]; then
    # SSH로 실행한 명령이 <서버 실행 커맨드>를 포그라운드로 직접 물고 있으면 ssh 자체가 그 프로세스가
    # 끝날 때까지 안 끝나 버린다(빌드가 몇 분씩 멈춘다) - 그래서 SSH 너머에서도 곧바로 at(1)에
    # 다시 제출해서, ssh 명령 자체는 "예약만 하고" 즉시 끝나도록 한다.
    ssh -i /var/lib/jenkins/.ssh/localhost_deploy -o StrictHostKeyChecking=accept-new -o BatchMode=yes \
        jysn007@localhost "echo \"$START_CMD\" | at now"
else
    echo "$START_CMD" | at now
fi
```

**정지 스크립트(`bin/stopApp.sh`)도 같은 이유로 손봐야 한다** — `jenkins`는 `jysn007` 소유 프로세스를
`kill`할 권한이 없다(그룹 쓰기 권한이나 ACL과는 별개의, 리눅스의 "프로세스는 소유자나 root만 죽일 수
있다"는 규칙). 정지도 SSH 경로를 태워야 한다:
```bash
run_as_owner() {
    if [ "$(whoami)" = "jenkins" ]; then
        ssh -i /var/lib/jenkins/.ssh/localhost_deploy -o StrictHostKeyChecking=accept-new \
            -o BatchMode=yes jysn007@localhost "$1"
    else
        eval "$1"
    fi
}
run_as_owner "kill $PID"
```
**상태 확인 스크립트(`bin/statusApp.sh`)**도 `kill -0 $PID`(마찬가지로 다른 계정 소유 프로세스면
권한 오류로 항상 실패한다) 대신, 포트 응답 등 **소유권과 무관한 방법**으로 판단하게 만든다:
```bash
curl -sf -o /dev/null http://localhost:<port>/ && echo RUNNING || echo STOPPED
```

## 16. 빌드 트리거·모니터링

### 웹 UI
- Job 페이지 → **Build Now**
- 빌드 번호 클릭 → **Console Output**(실시간 로그), 상단 Stage View에서 스테이지별 성공/실패 시각 확인
- **Build History**의 공 색깔: 파란/초록 = 성공, 빨강 = 실패, 노랑 = UNSTABLE, 회색/회전 = 진행 중

### REST API
```bash
# 트리거 (12.2절의 COOKIE_JAR/CRUMB 재사용)
curl -s -b "$COOKIE_JAR" -c "$COOKIE_JAR" -u "<user>:<token>" -H "Jenkins-Crumb: $CRUMB" \
  -X POST "http://localhost:8080/job/<job-name>/build?delay=0sec"
# 응답 헤더의 Location: http://localhost:8080/queue/item/<N>/ 로 큐 아이템을 추적하거나,
# 아래처럼 lastBuild를 바로 조회해도 된다(트리거 직후 1~2초 뒤에 폴링 시작 권장).

# 최근 빌드 번호/상태 조회
curl -s -u "<user>:<token>" "http://localhost:8080/job/<job-name>/api/json" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['lastBuild'])"

# 특정 빌드 결과 폴링 (result가 null이면 아직 진행 중)
curl -s -u "<user>:<token>" "http://localhost:8080/job/<job-name>/<N>/api/json" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(d.get('result'))"

# 콘솔 로그 전체 조회
curl -s -u "<user>:<token>" "http://localhost:8080/job/<job-name>/<N>/consoleText"

# 진행 중인 빌드 중단
curl -s -b "$COOKIE_JAR" -c "$COOKIE_JAR" -u "<user>:<token>" -H "Jenkins-Crumb: $CRUMB" \
  -X POST "http://localhost:8080/job/<job-name>/<N>/stop"
```
완료까지 기다리는 폴링 루프 예시:
```bash
until curl -s -u "<user>:<token>" "http://localhost:8080/job/<job-name>/<N>/api/json" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); exit(0 if d.get('result') else 1)" 2>/dev/null
do sleep 5; done
```

자동 트리거(Poll SCM, GitHub Webhook)는 이번 가이드 범위 밖이며, dstone Job들과 마찬가지로 현재는
전부 수동(`Build Now`/REST API) 트리거만 구성한다 — 필요해지면
[04.cloud-architecture.md 5.7절](../04.cloud-architecture.md#57-자동-트리거-구성-후속-과제)의 방식을
그대로 적용할 수 있다.

## 17. 자주 발생하는 문제 체크리스트

| 증상 | 원인 | 대처 |
|---|---|---|
| `Host key verification failed` | Jenkins(`jenkins` 계정)의 known_hosts에 github.com 키가 없음 | 10.2절 |
| `git@github.com: Permission denied (publickey)` | Credential 미등록/잘못된 Credential ID 선택 | 10.3절, Job의 SCM 설정에서 Credentials 재확인 |
| `403 No valid crumb was included in the request` | REST API 호출 시 크럼 발급과 실제 요청의 쿠키가 다름 | 12.2절처럼 `-c`/`-b`로 같은 쿠키 파일을 재사용 |
| `rsync: ... failed: Operation not permitted` (chgrp/시간/권한) | `jenkins`가 배포 경로의 기존 파일을 소유하지 않아 메타데이터 변경 권한이 없음 | 13절 Sync 스테이지처럼 `--no-perms --no-owner --no-group --omit-dir-times` |
| `mvn package`가 특정 파일 복사에서 `Operation not permitted` | 다른 계정이 만든 `target/` 파일을 덮어쓰려 함(14.3절) | `mvn clean package`로 전환 |
| Health Check는 통과했는데 빌드가 끝나면 서버가 죽어 있음 | Jenkins의 빌드-종료 시 프로세스 정리 | 15절 (SSH-to-localhost) |
| `jenkins`가 `kill`/`kill -0`을 다른 계정 소유 프로세스에 실행하면 항상 실패 | 리눅스는 프로세스 종료/신호를 소유자나 root만 허용 | 15절 후반 (`stopApp.sh`/`statusApp.sh`를 SSH 경로 또는 소유권 무관 판정 방식으로) |
| `Script Path` 오타로 `Jenkinsfile not found` | Job 설정의 Script Path가 실제 파일 경로와 불일치 | 저장소 루트 기준 상대경로, 대소문자까지 정확히 |
| SSH로 원격 서버 실행 명령을 넘겼더니 빌드가 몇 분째 안 끝남 | SSH가 포그라운드 프로세스를 물고 대기 중 | 15절처럼 SSH 너머에서 `at now`로 한 번 더 위임해 ssh 자체는 즉시 리턴하게 함 |
