## 1. 개요

`dstone-batch`는 Spring Boot와 Spring Batch를 기반으로 구축된 엔터프라이즈급 배치 처리 프레임워크입니다. 반복적인 잡(Job) 설정을 표준화하고, 개발자가 비즈니스 로직에 집중할 수 있도록 설계되었습니다.

> ⚠️ Spring Cloud Task/Spring Cloud Data Flow **프레임워크 자체는 의존성으로 포함돼 있지 않다**(`pom.xml`에 `spring-cloud-*` 아티팩트 없음). 뒤에 나오는 "SCDF 연동"은 dstone이 직접 작성한 `ScdfTaskRunner`가 평범한 `RestTemplate`로 외부 SCDF 서버의 REST API(`/tasks/definitions`)를 호출하는 코드일 뿐, Spring Cloud Task의 `@EnableTask`/`TaskRepository` 같은 프레임워크 기능은 쓰지 않는다 - 6.3절/7.2절 참고.

- **Artifact ID:** `dstone-batch`
- **Packaging:** JAR (독립 실행형)
- **Main Class:** `net.dstone.batch.common.DstoneBatchApplication`
- **기본 포트:** 6081

## 5. 핵심 개념

### 5.1 잡(Job) 정의 패턴

모든 배치 잡은 `BaseJobConfig`를 상속하고 `@AutoRegJob` 어노테이션을 선언합니다:

```java
@Component
@AutoRegJob(name = "sampleJob")   // 잡 고유 이름
public class SampleJobConfig extends BaseJobConfig {

    @Override
    public void configJob() throws Exception {
        // 1. Tasklet 기반 스텝
        this.addStep(this.createStep("01.스텝1"));

        // 2. 멀티스레드 청크(Chunk) 스텝
        this.addStep(this.createMultiThreadStep(
            "02.멀티스레드스텝",
            20,                      // 청크 크기(chunkSize)
            5,                       // 스레드 수(threadNum) - Spring Batch 6부터 throttleLimit(int)가 제거되어
                                      // taskExecutor 풀 크기로만 동시 스레드 수를 제어한다(SampleJobConfig 실제 코드 참고)
            new SampleItemReader<>(),
            new SampleItemProcessor(),
            new SampleItemWriter()
        ));

        // 3. 순차 Flow 추가
        this.addFlow(this.createSimpleFlow("03.심플플로우"));

        // 4. 병렬 Split Flow 추가
        this.addFlow(this.createSplitFlow("04.스플릿플로우"));
    }
}
```

### 5.2 BaseJobConfig 제공 메소드

`BaseJobConfig`(`net.dstone.batch.common.core.BaseJobConfig`)가 **실제로 제공하는** `protected` 메소드는 이 4개뿐이다 - `configJob()` 안에서 조립한 Step/Flow/Tasklet을 실행 순서대로 등록하는 역할만 한다:

| 메소드 | 설명 |
|---|---|
| `addStep(Step)` | 순차 실행 목록에 Step 추가 |
| `addFlow(Flow)` | 순차 실행 목록에 Flow 추가 |
| `addTasklet(Tasklet)` | 순차 실행 목록에 Tasklet 추가(내부적으로 `txManagerCommon`으로 Step을 만들어 등록) |
| `getInitJobParam(key[, defaultVal])` | 이 잡 실행에 전달된 파라미터 조회 |

> ⚠️ **`createStep`/`createMultiThreadStep`/`createSimpleFlow`/`createSplitFlow`/`createTasklet`은 `BaseJobConfig`가 주는 메소드가 아니다.** 5.1절 예제의 `this.createStep(...)`처럼 보이지만, 이 5개는 전부 `SampleJobConfig`(`job001`) 같은 **각 잡 구현 클래스가 자기 안에 직접 만들어 쓰는 `private` 헬퍼 메소드**다 - `StepBuilder`/`FlowBuilder`를 감싸는 흔한 패턴을 예제가 보여주는 것일 뿐, 상속으로 물려받는 게 아니다. 새 잡을 만들 때 이 패턴이 필요하면 `SampleJobConfig.java` 원본에서 그대로 복사해 쓰면 된다.

### 5.3 @AutoRegJob 동작 방식

`ConfigAutoReg.java`가 스캔하여 어노테이션이 붙은 클래스를 Spring Batch `JobRegistry`에 등록합니다.

- `auto-register-jobs: true`(이 환경의 현재 값, `conf/application.yml`) → 애플리케이션 기동 시 `@AutoRegJob`이 붙은 잡 전부를 `JobRegistry`에 일괄 등록 (`RestApiRunner`의 `/batch/**` REST 제어용)
- `auto-register-jobs: false` → 기동 시엔 등록하지 않고, 잡 실행 시점(`ScdfTaskRunner`가 `spring.batch.job.names`를 감지했을 때)에 그 잡 하나만 개별 등록(7.1절)

```yaml

  jdbc-url: jdbc:log4jdbc:mysql://${DB_HOST}:${DB_PORT}/dataflow
  username: ENC(...)
  password: ENC(...)
  minimum-idle: 2
  maximum-pool-size: 50
  connection-timeout: 30000
  max-lifetime: 1700000
```

### 6.2 Spring Batch 설정

```yaml
spring.batch:
  initialize-schema: NEVER    # 배치 테이블 자동 생성 비활성화 (수동 SQL 실행 필요)
  job.enabled: false          # 기동 시 자동 잡 실행 비활성화 (명시적 실행만 허용)
```

> 배치 테이블 초기 생성: `src/main/resources/schema/*.sql` 스크립트를 수동 실행. Spring Batch 6부터 시퀀스 테이블명이 `BATCH_JOB_SEQ` → `BATCH_JOB_INSTANCE_SEQ`로 바뀌어, 옛 스키마로 이미 생성된 DB는 `RENAME TABLE BATCH_JOB_SEQ TO BATCH_JOB_INSTANCE_SEQ;`가 필요하다(안 하면 Job 실행 시 "Could not increment ID for BATCH_JOB_INSTANCE_SEQ sequence table" 오류).

### 6.3 SCDF(Spring Cloud Data Flow) 태스크 등록 설정

`ScdfTaskRunner.registerJosToScdf()`(7.2절)가 외부 SCDF 서버에 태스크 정의를 등록할 때 이 값을 읽는다 - Spring Cloud Data Flow의 `@ConfigurationProperties`가 아니라 `ConfigProperty.getProperty("spring.cloud.dataflow.client.server-uri")`로 dstone이 직접 조회하는, dstone 자체 관례의 설정 키다:

```yaml
spring:
  cloud:
    dataflow:
      client:
        server-uri: http://<dataflow-server>:9393
```

> ⚠️ **이 환경의 `conf/application.yml`에는 이 키가 없다** — 즉 지금은 SCDF 연동이 설정돼 있지 않고, `ScdfTaskRunner.main()`을 실행해도 `server-uri`가 비어 등록 요청이 의미 있는 주소로 나가지 못한다. SCDF 서버를 실제로 붙이려는 SI 프로젝트가 이 키를 채워야 7.2절의 등록 절차가 동작한다.

## 7. 잡 실행 방법

### 7.1 방법 1 - 패키지된 JAR 직접 실행 (`ScdfTaskRunner`)

```bash
# 1. 빌드
mvn clean package

# 2. 특정 잡 실행
java -jar -Dspring.batch.job.names=sampleJob target/dstone-batch-1.0.0-SNAPSHOT.jar

# 3. 다른 잡 실행 예시
java -jar -Dspring.batch.job.names=tableDataGenType01Job target/dstone-batch-1.0.0-SNAPSHOT.jar
```

**실행 순서:**
1. `pom.xml`의 `spring-boot-maven-plugin` 설정이 `mainClass`를 `net.dstone.batch.common.DstoneBatchApplication`으로 고정해뒀기 때문에, `java -jar`는 항상 `DstoneBatchApplication.main()`부터 시작한다.
2. `setSysProperties()` → `conf/env.properties`를 System Properties로 로드
3. 이 Spring Boot 컨텍스트가 뜨면서 `@Component`로 등록된 `ScdfTaskRunner`(=`ApplicationRunner`)가 **항상 자동으로 실행**된다. `spring.batch.job.names` 값이 있으면 그 이름의 잡을 `configAutoReg` 등록 → 조회 → `startJobExecution`까지 동기로 수행하고, 없으면 아무 것도 하지 않고 넘어간다.

> ℹ️ 이름과 클래스 위치(`runner/SimpleBatchRunner.java`) 때문에 "로컬 단건 실행 = `SimpleBatchRunner`"로 오해하기 쉽지만, `SimpleBatchRunner`는 자기 자신만의 별도 `main()`을 가진 **독립된 클래스**이고 `pom.xml`의 `mainClass`는 이 클래스를 가리키지 않는다 - 위 `java -jar` 명령이 실제로 호출하는 러너는 `ScdfTaskRunner`다. `SimpleBatchRunner`를 쓰려면 `java -cp target/dstone-batch-1.0.0-SNAPSHOT.jar net.dstone.batch.common.runner.SimpleBatchRunner spring.batch.job.names=sampleJob`처럼 클래스를 직접 지정해 호출해야 한다.

### 7.2 방법 2 - SCDF에 태스크로 등록 (현재 미설정)

`ScdfTaskRunner`에는 7.1절의 `run()`(잡 실행)과 별개로, **SCDF 서버에 이 잡들을 태스크 정의로 등록해주는** 독립된 `main()`이 있다 - `registerJosToScdf()` → `registerAllJobToDataflow()`가 `@AutoRegJob`이 붙은 잡마다 `RestTemplate.postForEntity(<server-uri>/tasks/definitions, ...)`를 호출해 이미 등록돼 있지 않은 잡만 새로 등록한다(순수 REST 호출 - Spring Cloud Data Flow 클라이언트 라이브러리를 쓰지 않는다).

```bash
# server-uri(6.3절)가 채워진 conf/application.yml 기준
java -cp target/dstone-batch-1.0.0-SNAPSHOT.jar net.dstone.batch.common.runner.ScdfTaskRunner
```

1. 위 명령으로 태스크 정의를 SCDF 서버에 등록(1회성 - 이미 등록돼 있으면 건너뜀)
2. 이후 실제 실행/스케줄링/모니터링은 SCDF UI 또는 Shell에서 그 태스크 정의를 통해 SCDF가 담당

> ⚠️ 이 환경(`conf/application.yml`)에는 `spring.cloud.dataflow.client.server-uri`가 채워져 있지 않아, 지금 이 절차는 실제로 동작 검증된 적이 없다(6.3절 참고) - SCDF 서버를 붙이는 SI 프로젝트를 위한 훅으로 남아있는 코드다.

## 9. Spring Batch 아키텍처

```
Job
├── Step 1 (Tasklet)
│     └── 단순 작업 단위
├── Step 2 (Chunk-Oriented)
│     ├── ItemReader   (데이터 읽기)
│     ├── ItemProcessor (데이터 변환/필터링)
│     └── ItemWriter   (데이터 저장)
└── Flow (여러 Step 묶음)
      └── SplitFlow (병렬 Flow)
```

**트랜잭션**: 각 청크(Chunk) 단위로 트랜잭션을 커밋하여 대용량 데이터 처리 시 안정성 확보
