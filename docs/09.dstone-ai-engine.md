## 1. 개요

`dstone-ai-engine`은 Spring AI 기반의 provider-agnostic AI 서빙 엔진이다. 이번 재설계의 핵심
아이디어는 "AI 에이전트 프로그램의 Workflow는 누가 제어하는가?"라는 질문에 대한 답이다:

```text
Workflow의 뼈대(순서/분기/병렬/루프/재시도 한도)는 Java(WorkflowExecutor)가 잡고,
Step 내부의 지능적인 판단(SQL 분석, 변환 전략, 오류 원인 파악, Tool 선택)은 LLM에게 맡긴다.
```

그리고 Workflow/Agent가 무엇을 할지는 자바 코드가 아니라 **YAML 파일**로 선언한다 -
`resources/workflows/*.yml`, `resources/agents/*.yml`을 추가/수정하는 것만으로 새 업무를
등록할 수 있고, `application.yml`이나 Java 코드를 건드릴 필요가 없다.

```text
                 ┌───────────────┐
                 │   Workflow    │ ← resources/workflows/*.yml
                 └───────┬───────┘
                         ↓
                 ┌───────────────┐
                 │     Step      │ ← WorkflowDefinition.steps (AGENT/TOOL/RAG/SUPERVISOR)
                 └───────┬───────┘
                         ↓
                 ┌───────────────┐
                 │     Agent     │ ← resources/agents/*.yml
                 └───────┬───────┘
                         ↓
                 ┌───────────────┐
                 │      LLM      │ ← 단일 Anthropic ChatClient
                 └───────┬───────┘
                         ↓
                 ┌───────────────┐
                 │     Tool      │ ← @AiTool 빈 스캔(common.config.ConfigTool)
                 └───────────────┘
```

## 2. 설계 원칙

- **엔진 전체가 단일 LLM Provider를 공유한다.** Agent별로 다른 provider를 쓰는 기능은 없다 -
  `spring.ai.model.chat` 하나로 전체가 움직인다(`ChatClient` 빈이 이 provider 하나로만 조립됨).
  다만 그 provider 안에서 **모델**은 Agent별로 override할 수 있다 - `agents/*.yml`의
  `model` 필드(비우면 `spring.ai.{provider}.chat.options.model` 공통 기본값을 그대로 씀)를
  `runtime.agent.AgentExecutor.buildSpec()`이 요청별 `ChatOptions`로 얹는다. 활성 provider가
  실제로 서빙하지 않는 모델명을 넣으면 기동 시점엔 걸러지지 않고 그 Agent를 처음 호출할 때
  런타임 에러로 드러난다.
- **람다식을 지양한다.** 컬렉션 처리는 `for`문, Spring/Java API가 함수형 인터페이스를 요구하는
  자리(`ChatClient.advisors(Consumer<AdvisorSpec>)`, `CompletableFuture.supplyAsync(Supplier)`,
  `Runnable`)는 익명 클래스로 구현한다. `switch (status) { case X -> ... }` 형태의 enhanced
  switch는 함수형 인터페이스 인스턴스를 만드는 게 아니므로 예외로 그대로 쓴다.
- **dstone-common을 최대한 재사용한다.** Redis는 `RedisUtil.getInstance()`, 설정 읽기/ENC 복호화는
  `ConfigProperty`, 로깅은 `LogUtil.sysout()`, 컨트롤러/서비스 베이스 클래스는
  `BaseController`/`BaseService`/`BaseObject`를 그대로 쓴다.
- **governance(PII/민감어 가드레일, 사용량 로깅·쿼터)는 이번 범위에서 뺐다.** 대신 나중에
  대규모 리팩토링 없이 다시 붙일 수 있도록 확장 지점만 마련해뒀다([8절](#8-governance-확장-지점)).
- **불필요한 간접 계층을 만들지 않는다.** 옛 구조의 `CapabilityDefinition`(이름 하나로
  promptName/toolsEnabled/ragEnabled 또는 processName을 대신 채워주던 계층)은 삭제했다 -
  `/api/ai/chat`은 Agent를 직접, `/api/ai/workflow/{id}`는 Workflow를 직접 가리키므로 그
  간접 계층이 더 이상 필요 없다.

## 4. 정의(Definition) → 실행(Runtime) 흐름

```text
Application
     │  aiEngine.execute("oracle-to-postgresql", ...)  ← 개념적으로는 이렇지만
     │  실제로는 REST: POST /api/ai/workflow/oracle-to-postgresql/execute
     ▼
WorkflowController
     │
     ▼
WorkflowRegistry.resolve(id, caller)   ← classpath:workflows/*.yml에서 기동 시 적재된 정의, caller 화이트리스트 검사
     │
     ▼
WorkflowExecutor.run(definition, ...)
     │
     ├── AGENT/SUPERVISOR step → AgentStepRunner → AgentRegistry.resolve(ref, caller) → AgentExecutor
     ├── TOOL step             → ToolStepRunner  → ToolExecutor → ConfigTool.findByName(caller, ref)
     └── RAG step              → RagStepRunner   → RagService.search()
```

`common.loader.YamlDefinitionLoader`는 `PathMatchingResourcePatternResolver`로
`classpath*:workflows/*.yml`, `classpath*:agents/*.yml`을 찾고, SnakeYAML로 파싱한 뒤
Jackson `ObjectMapper.convertValue()`로 definition record에 바인딩한다(record 필드 바인딩은
`pom.xml`의 `-parameters` 컴파일 옵션 덕분에 별도 생성자/애노테이션 없이 그대로 된다).
`WorkflowRegistry`/`AgentRegistry`는 `@PostConstruct`에서 이 로더를 한 번 호출해 `Map`으로
캐싱해두고, 이후 조회는 전부 메모리에서 이뤄진다(재적재는 재기동이 필요하다 - 핫 리로드는
범위 밖).

## 5. Workflow 실행 모델

`WorkflowDefinition.steps`는 `StepDefinition` 목록이다. 각 step은 `id`/`type`/`ref`와
`onSuccess`/`onFailure`(다음 step id, 또는 예약어 `SUCCESS`/`FAIL`)를 갖는다.
`WorkflowExecutor`는 이 정의를 따라가는 단순한 상태 기계다:

```text
currentId = 첫 step
loop:
    executed 횟수가 maxIterations(기본 5)를 넘으면 예외로 정지
    step = stepsById[currentId]
    outcome = runStep(step)          # AgentStepRunner/ToolStepRunner/RagStepRunner에 위임
    context.put("result", outcome.text())
    nextId = outcome.success ? step.onSuccess : step.onFailure
    nextId == null 이면:
        실패였으면 예외로 정지, 성공이었으면 목록상 다음 step(없으면 종료)
    nextId == "SUCCESS"/"FAIL" 이면: 그 자리에서 즉시 종료
    그 외: nextId가 현재 step보다 앞에 있으면 LOOP, 뒤에 있으면 NEXT_STEP으로 진행(동작은 동일 -
          로그/가독성 구분일 뿐이고, 무한루프 방지는 maxIterations 하나가 전담)
```

**성공/실패 판정 관례**: AGENT/RAG step은 항상 성공으로 취급된다.

TOOL step은 응답(원본) 텍스트가 `"실패"`로 시작하는지로 판정한다(`tools.sql.SqlSyntaxTools`가
이미 `"통과: .../실패: ..."` 형식으로 답하는 관례를 그대로 재사용). `ToolCallback.call()`의
반환값은 Spring AI가 JSON으로 감싼 값이라 `runtime.tool.ToolExecutor`가 먼저 Jackson으로 벗겨낸
뒤 이 접두사를 검사한다. Tool 응답은 결정론적인 자바 코드에서 나오므로 이 문자열 접두사 판정만
으로도 안전하다.

SUPERVISOR step은 TOOL과 달리 응답이 LLM이 만든 자유 텍스트라 같은 방식(문자열 접두사)이 안전
하지 않다 - 프롬프트가 컨벤션을 지키라고 지시해도 LLM이 매번 정확히 따른다는 보장이 없다(코드펜스로
감싸거나 다른 단어로 시작하는 이탈이 실제로 있었다). 그래서 `runtime.agent.Verdict`
(`record Verdict(boolean pass, String reason)`)로 구조화 출력을 받는다 -
`AgentExecutor.callForVerdict(...)`가 `ChatClient.call().entity(Verdict.class)`를 쓰면 Spring
AI가 이 record의 JSON 스키마를 프롬프트에 자동으로 삽입하고 응답을 그 스키마에 맞춰 파싱해준다.
`AgentStepRunner.runSupervisor()`는 `verdict.pass()`가 명시적으로 `true`일 때만 성공으로 보고,
그 외(`false` 또는 스키마 자체를 어겨 파싱이 예외로 실패한 경우)는 전부 실패로 처리한다
(fail-closed - 판정을 신뢰할 수 없으면 안전한 쪽인 실패로 취급).

**병렬 실행**: 같은 `parallelGroup` 값을 가진 인접 step들은 `CompletableFuture`로 동시에
실행되고, 결과 텍스트는 개행으로 이어붙여지며 성공 여부는 AND로 합쳐진다.

**WorkflowContext**: step들이 공유하는 값 저장소다. 관례적으로 `"input"`(최초 입력),
`"result"`(가장 최근 step 출력), `"variables"`(호출 시 넘긴 값 전체)를 담아둔다 - 옛 구조처럼
문자열 하나만 다음 step에 넘기는 대신, 이름 붙은 여러 값을 자유롭게 읽고 쓸 수 있게 한 것이
이번 재설계에서 바뀐 점이다.

## 6. Agent와 Tool

**Agent**(`common.definition.AgentDefinition`)는 "LLM에게 일을 시키는 단위"다 -
`promptName`(어떤 시스템 프롬프트를 쓸지), `toolsEnabled`/`ragEnabled`(Tool/RAG를 붙일지),
`model`(이 Agent만 다른 모델을 쓰고 싶을 때 override, 비우면 provider 공통 기본값),
`allowedCallers`(caller 화이트리스트)를 갖는다(`description`은 `WorkflowDefinition.description`과
같은 순수 문서화용 필드 - 코드는 읽지 않고, LLM에게 보내는 내용은 항상 `promptName`이 가리키는
`.st` 파일이 전담한다). `runtime.agent.AgentExecutor`가 이 정의를 읽어
`ChatClient` 요청 하나를 조립하는 유일한 지점이다 - `ChatController`(단일 대화 턴)와
`runtime.step.AgentStepRunner`(Workflow의 AGENT/SUPERVISOR step)가 똑같이 이 클래스를 거친다.
즉 같은 이름의 Agent는 직접 채팅으로 부르든 Workflow 안에서 부르든 항상 똑같이 동작한다.
`model`은 같은 provider 안에서 모델만 바꾸는 것이고(예: Anthropic이 활성 provider일 때 무거운
step만 `claude-opus-...`, 나머지는 기본값), Agent별로 다른 provider를 쓰는 기능은 여전히 없다.

**Tool**은 옛 구조와 동일하게 `@AiTool` + `@Tool` 애노테이션이 붙은 Spring 빈을
`common.config.ConfigTool`이 기동 시 스캔해서 `ToolCallbackProvider`로 묶는 방식이다(별도의
Tool Registry YAML을 새로 만들지 않았다 - `@AiTool` 스캔 자체가 이미 선언적 등록소 역할을
하고 있어서, YAML로 같은 걸 한 번 더 선언하면 두 개의 서로 다른 진실 공급원이 생기는 문제가
있었다). AGENT step에서는 어떤 Tool을 언제 호출할지 Spring AI의 `ChatClient`가 LLM과 대화를
주고받으며 알아서 정하고, TOOL step에서는 `runtime.tool.ToolExecutor`가 이름으로 직접 찾아
LLM 없이 호출한다. caller별 Tool 화이트리스트(`dstone.ai.tool.allowed-by-caller`)는
`ConfigTool`이 두 경로 모두에 동일하게 적용한다.

기본 제공 Tool: `tools.sample.DateTimeTools`(샘플), `tools.sql.SqlSyntaxTools`(SQL 문법
검증, 항상 활성), `tools.shell.ShellExecTool`/`tools.python.PythonExecTool`(화이트리스트된
스크립트만 실행), `tools.http.HttpCallTool`(허용된 호스트에만 GET). 이 세 개는 별도의
on/off 설정이 없다 - `allowed-commands`/`allowed-scripts`/`allowed-hosts`가 비어 있으면(기본값)
어떤 입력을 줘도 화이트리스트에서 못 찾아 항상 실패하므로, 화이트리스트를 안 채우는 것 자체가
곧 비활성 상태다.

## 7. Session / RAG / Security

옛 구조에서 그대로 이식했다(패키지 위치만 `common` 밑으로 정리):

- **Session** — `common.session.RedisChatMemorySession`이 Spring AI의 `ChatMemoryRepository`를
  Redis(`dstone:ai:session:{conversationId}` List)로 구현한다. `dstone.ai.session.max-messages`
  (기본 20)만큼만 최근 대화를 유지하는 슬라이딩 윈도우는 `common.config.ConfigChatClient`가
  조립한다.
- **RAG** — `rag.RagService`가 문서 적재(Tika 추출 → `TokenTextSplitter` 청킹 → pgvector 저장,
  `sourceId` upsert)/삭제/검색을 전담한다. `dstone.ai.rag.enabled=true`이고 VectorStore 빈이
  실제로 있을 때만 동작하며, caller(=tenant_id)가 있으면 청크마다 `tenant` metadata를 태깅해서
  다른 caller의 문서가 섞이지 않게 격리한다.
- **Security** — `common.security.ApiKeyAuthFilter`(`X-API-Key` 헤더 검증, `@Order(1)`)와
  `common.security.RateLimitFilter`(caller/IP별 Redis 고정 윈도우 카운터, `@Order(2)`)가
  `dstone.ai.security.auth`/`dstone.ai.security.ratelimit`로 옵트인된다(기본 둘 다 꺼짐).
  `CallerContext`가 인증된 caller를 request attribute + ChatClient Advisor context 양쪽에
  전달한다.

## 8. Governance 확장 지점

PII/민감어 가드레일, 사용량 로깅·쿼터는 이번 재설계 범위에서 뺐지만, 나중에 큰 리팩토링 없이
다시 붙일 수 있도록 두 지점을 마련해뒀다:

1. **`common.config.ConfigChatClient.chatClient(...)`가 `List<Advisor>`를 그대로 주입받는다.**
   지금은 이 리스트에 매치되는 `@Bean Advisor`가 하나도 없어서 항상 빈 리스트지만, governance
   모듈이 `@Bean Advisor piiGuardrailAdvisor() { ... }`를 하나 추가하기만 하면 Spring이 다건
   빈을 자동으로 이 리스트에 모아준다(`ObjectProvider.getIfAvailable()` 대신 평범한 `List<T>`
   주입을 쓴 이유 - 소비자가 없을 수도 있는 빈을 다루는 관용적인 Spring 방식이다).
2. **`runtime.tool.ToolExecutor.call(...)`가 모든 TOOL step 호출의 단일 통과 지점이다.**
   나중에 Tool 호출을 감사/제한하고 싶어지면 이 메서드 하나만 감싸면 된다(`ToolStepRunner`나
   `AgentExecutor`의 호출부는 손댈 필요 없음).

## 9. YAML 정의 작성법

`resources/agents/*.yml` - 한 파일에 여러 Agent를 같이 둘 수 있다:

```yaml
agents:
  - name: sql-analysis-agent
    description: Oracle SQL의 Oracle 전용 문법을 분석한다   # 순수 문서화용, 프롬프트에는 안 들어감
    promptName: oracle-sql-analyzer   # classpath:prompts/oracle-sql-analyzer/{version}.st
    toolsEnabled: false
    ragEnabled: false
    # model: claude-opus-4-...   # 비우면 spring.ai.{provider}.chat.options.model(공통 기본값) 사용
    # allowedCallers: [sample-si-project]   # 비우면 누구나 호출 가능
```

`resources/workflows/*.yml` - 파일 하나에 Workflow 하나(`workflow:` 최상위 키):

```yaml
workflow:
  id: oracle-to-postgresql
  description: Oracle MyBatis SQL을 PostgreSQL MyBatis SQL로 변환한다.
  maxIterations: 5
  steps:
    - id: analyze
      type: AGENT              # AGENT | TOOL | RAG | SUPERVISOR
      ref: sql-analysis-agent  # AGENT/SUPERVISOR는 Agent 이름, TOOL은 Tool 이름
      onSuccess: convert

    - id: validate
      type: TOOL
      ref: validateSqlSyntax
      inputTemplate: '{"sql":"{previous}"}'   # {previous}=직전 step 결과, {변수명}=요청 variables
      onSuccess: SUCCESS       # 예약어: 즉시 성공 종료
      onFailure: fix           # 실패하면 fix step으로(루프)
```

레퍼런스 구현은 각각 `dstone-ai-engine/src/main/resources/agents/sql-agents.yml`,
`.../resources/workflows/oracle-to-postgresql.yml`을 참고하면 된다. 이 Workflow는
`validate` 통과 뒤 `report`(SUPERVISOR, ref: `sql-conversion-report`)로 이어지는 구조라,
SUPERVISOR step과 구조화된 Verdict(pass/reason) 판정(`runtime.agent.Verdict`, [5절](#5-workflow-실행-모델)
참고)의 실제 사용 예시이기도 하다.

`parallelGroup`(병렬 실행) 전용 예시는 `.../resources/workflows/parallel-test.yml` - TOOL step
두 개(`validate-a`/`validate-b`)를 같은 `parallelGroup: check`로 묶어서 동시 실행시킨다. AGENT
없이 `validateSqlSyntax` Tool만 쓰므로 LLM 호출 비용 없이 바로 돌려볼 수 있고, dstone-boot의
"Workflow 비동기 테스트" 화면(`/ai/workflow.do`, workflowId 입력칸에 `parallel-test` 입력)에서
message=`validate-a`가 검증할 SQL, variables=`{"sqlB":"validate-b가 검증할 SQL"}`로 채워 제출하면
확인할 수 있다.

## 10. API 레퍼런스

### `POST /api/ai/chat` — Agent 1회 호출

```bash
curl -X POST http://localhost:8081/api/ai/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"지금 몇시야?","agent":"general-chat","variables":{"role":"비서"}}'
# → {"message":"현재 시간은 ...","provider":"anthropic","sessionId":"...","agent":"general-chat","model":"claude-sonnet-4-5-20250929"}
```

`agent`는 필수다 - `resources/agents/*.yml`에 등록된 이름이어야 하며, `promptName`은 항상 그
Agent 정의값 그대로 쓰인다. `ragEnabled`/`toolsEnabled`/`model`은 비우면(null) Agent 정의값을
그대로 쓰고, 채워 보내면 그 요청 한 번만 강제로 override한다(`common.definition.AgentDefinition`의
`toolsEnabled`/`ragEnabled`/`model`, `runtime.agent.AgentExecutor.buildSpec()` 참고) - dstone-boot
채팅 화면의 RAG/Tool 체크박스와 "모델 override" 입력칸이 이 세 필드를 그대로 실어 보낸다. 응답의
`model`은 그렇게 해석된 실제 모델명이다(요청 override > Agent 정의값 > provider 공통 기본값).

```bash
# 요청 한 번만 다른 모델로 강제(같은 provider 안에서만 가능 - 2절 참고)
curl -X POST http://localhost:8081/api/ai/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"지금 몇시야?","agent":"general-chat","variables":{"role":"비서"},"model":"claude-haiku-4-5-20251001"}'
```

### `POST /api/ai/chat/stream` — 같은 계약, SSE 스트리밍

응답이 `text/event-stream`으로 토큰 단위 흘러나온다는 점만 다르다.

### `POST /api/ai/workflow/{workflowId}/execute` — Workflow 동기 실행

```bash
curl -X POST http://localhost:8081/api/ai/workflow/oracle-to-postgresql/execute \
  -H "Content-Type: application/json" \
  -d '{"message":"SELECT NVL(name, '"'"'N/A'"'"') AS name FROM employees WHERE ROWNUM <= 10"}'
# → {"message":"SELECT COALESCE(name, 'N/A') AS name FROM employees LIMIT 10", "sessionId":"...", "workflowId":"oracle-to-postgresql"}
```

### `POST /api/ai/workflow/{workflowId}/submit` + `GET /api/ai/workflow/status/{jobId}` — 비동기

여러 step에 걸쳐 오래 걸릴 수 있는 Workflow를 위한 계약이다. Job 상태는 Redis Hash
(`dstone:ai:workflow:job:{jobId}`, 1시간 TTL)에 둔다.

```bash
curl -X POST http://localhost:8081/api/ai/workflow/oracle-to-postgresql/submit -d '{"message":"..."}'
# → {"jobId":"..."}
curl http://localhost:8081/api/ai/workflow/status/{jobId}
# → {"jobId":"...","status":"DONE","result":"...","error":null}   # status: RUNNING/DONE/FAILED
```

### `POST /api/ai/rag/documents` / `DELETE .../{sourceId}` / `POST /api/ai/rag/search`

옛 구조와 동일하다 - 문서 적재(multipart)/삭제/단독 유사도 검색(디버깅용). `dstone.ai.rag.enabled=true`
필요.

## 11. 설정 레퍼런스 (`conf/application.yml`)

| 키 | 설명 | 기본값 |
|---|---|---|
| `spring.ai.model.chat` | 엔진 전체가 공유하는 단일 provider | `anthropic` |
| `spring.ai.model.embedding` | RAG 임베딩 provider(anthropic 불가) | `ollama` |
| `dstone.ai.session.max-messages` / `.ttl-seconds` | 세션당 유지 메시지 수 / Redis TTL | `20` / `86400` |
| `dstone.ai.prompt.versions.{name}` / `.default-version` | 템플릿 버전 override | `v1` |
| `dstone.ai.tool.allowed-by-caller` | caller별 Tool 화이트리스트(List of {caller, tools}) | 없음(전체 허용) |
| `dstone.ai.rag.enabled` | RAG 기능 on/off | `false` |
| `dstone.ai.rag.ingest.chunk-size` | 청크당 최대 토큰 수 | `800` |
| `dstone.ai.rag.retrieval.top-k` / `.similarity-threshold` | 검색 결과 수 / 유사도 임계값 | `5` / `0.35` |
| `dstone.ai.security.auth.enabled` / `.keys` | API Key 인증 on/off, `{key, caller}` 목록 | `false` |
| `dstone.ai.security.ratelimit.enabled` / `.window-seconds` / `.default-limit` / `.overrides` | Rate Limit | `false` |
| `dstone.ai.tool.shell.allowed-commands` / `.python.allowed-scripts` / `.http.allowed-hosts` | 위험 Tool 화이트리스트(비어있으면 사실상 비활성) | 없음(전체 거부) |

Workflow/Agent 정의는 이 파일에 없다 - `resources/workflows/*.yml`, `resources/agents/*.yml`
참고([9절](#9-yaml-정의-작성법)).

## 13. 실제 검증 기록

2026-09-15 재설계 직후, WSL 환경(Redis/PostgreSQL+pgvector/Ollama 모두 로컬 기동)에서 실제
Anthropic 호출로 끝까지 검증했다:

- 기동 로그: `agents/*.yml`에서 Agent 4개, `workflows/*.yml`에서 Workflow 1개(`oracle-to-postgresql`)
  정상 적재, `@AiTool` 스캔으로 Tool 2개(`getCurrentDateTime`, `validateSqlSyntax`) 등록 확인.
- `POST /api/ai/chat`(agent=`general-chat`) — 일반 응답("1+1은?" → "2")과 Tool 호출 응답("지금
  몇시야?" → `getCurrentDateTime` 호출 결과로 정확한 시스템 시각 응답) 모두 확인.
- `POST /api/ai/workflow/oracle-to-postgresql/execute` — `NVL(...)`/`ROWNUM`이 들어간 Oracle SQL을
  넣었더니 analyze→convert→validate 3 step을 거쳐 `COALESCE(...)`/`LIMIT`으로 정확히 변환되고
  TOOL step(SqlSyntaxTools) 검증까지 한 번에 통과(재작성 루프 없이 종료)하는 것을 확인.
- `POST /api/ai/workflow/.../submit` + `GET /api/ai/workflow/status/{jobId}` — RUNNING → DONE
  전이와 최종 `result` 값이 동기 실행과 동일하게 채워지는 것을 확인.

## 14. 옛 구조에서 달라진 점

| 옛 구조(Phase 0~10) | 새 구조 |
|---|---|
| `capability`(이름→promptName/toolsEnabled/ragEnabled 또는 processName) | 삭제. `/api/ai/chat`은 Agent를, `/api/ai/workflow/{id}`는 Workflow를 직접 가리킴 |
| `process`(`ProcessDefinition`/`ProcessStep`, `application.yml`의 `dstone.ai.process.definitions`) | `runtime`(`WorkflowDefinition`/`StepDefinition`), 정의는 `resources/workflows/*.yml` |
| `agent`(`AgentDefinition`/`AgentRegistry`, `application.yml`의 `dstone.ai.agent.definitions`) | `common.definition`/`common.registry`, 정의는 `resources/agents/*.yml` |
| `ChatService`(단일 호출 + process 라우팅을 함께 처리) | `runtime.agent.AgentExecutor`(Agent 호출 전담) + `runtime.WorkflowExecutor`(Workflow 전담)로 분리 |
| `ProcessExecutor`의 `previousResult` 문자열 하나만 다음 step에 전달 | `WorkflowContext`(이름 붙은 여러 값을 step들이 자유롭게 읽고 씀) |
| `governance` 패키지(PII/민감어 가드레일, 사용량 로깅·쿼터) | 삭제, `List<Advisor>` 주입 지점으로 재추가 가능하게만 설계([8절](#8-governance-확장-지점)) |
| `governance.auth`/`governance.ratelimit`/`governance.tool` 설정 접두사 | `security.auth`/`security.ratelimit`/`tool`(auth/ratelimit은 계속 유지되는 핵심 기능이라 governance라는 이름을 떼어냄) |
