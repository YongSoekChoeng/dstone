# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**dstone** is a Java 21 / Spring Boot 4.1 (Spring Framework 7) enterprise multi-module framework providing:
- **dstone-common**: Shared library (JAR) — utilities, security, data access, messaging
- **dstone-boot**: Web application framework (WAR) — includes a Java source code static analyzer feature
- **dstone-batch**: Spring Batch processing framework (JAR) — standardized job development
- **dstone-batchadmin**: Web application (WAR) — manages `dstone-batch` jobs (list/detail/register screens, start/stop/restart, CRON auto-scheduling) across one or more `dstone-batch` server instances
- **dstone-ai-engine**: AI & MLOps Core Engine (JAR) — Spring AI-based, provider-agnostic AI serving platform intended for reuse across future SI projects (root package `net.dstone.ai`)
- **dstone-knowledge**: Java static analysis → Knowledge Graph → RAG data platform (JAR, root package `net.dstone.knowledge`) — under construction (M0 skeleton 2026-10-04, M1–M6 done 2026-10-05: SCAN → (CARRY) → DECLARE → RESOURCE → (CARRY_RESOLVE) → RESOLVE → LINK → SEMANTIC → DOCUMENT passes, background embedding, call-graph/endpoint/table/mapper APIs, screen → method → SQL → table chain, hybrid (vector + name) search, impact analysis, general-document upload with API-key tenants, `dstone-ai-engine` `KnowledgeTool`; M7 done 2026-10-05: incremental analysis, revision diff, retention; M8 done 2026-10-05: screens in `dstone-boot`; M9 migration: the `dstone-ai-engine` half is done 2026-10-06 — its embed/RAG now calls this module; the `dstone-boot` analyzer half is next — destructive, compare feature by feature and get the user's confirmation first)

`dstone-boot`, `dstone-batch`, `dstone-batchadmin`, `dstone-ai-engine`, and `dstone-knowledge` all depend on `dstone-common`.

## Build Commands

```bash
# Always build dstone-common first (required by other modules)
cd dstone-common && mvn clean install

# Build web app (WAR)
cd dstone-boot && mvn clean package

# Build batch (JAR)
cd dstone-batch && mvn clean package

# Build batch admin web app (WAR)
cd dstone-batchadmin && mvn clean package

# Build AI Core Engine (JAR)
cd dstone-ai-engine && mvn clean package

# Build knowledge platform (JAR)
cd dstone-knowledge && mvn clean package

# Build all from root
mvn clean install

# Skip tests
mvn clean package -DskipTests
```

## Architecture

### Configuration Pattern (all modules)

```
conf/
├── env.properties      # Sensitive config (DB credentials, Jasypt key) — loaded as System Properties at startup
├── application.yml     # App config — references ${ENV_VAR} from env.properties
└── log4j2.xml          # Logging config
```

Startup sequence: `setSysProperties()` loads `conf/env.properties` → `application.yml` is read → Log4j2 initializes.

For server deployment, comment out `application.yml` and `log4j2.xml` from `src/main/resources` in the build so that the `conf/` directory versions take precedence.

### Database

All modules use HikariCP + MyBatis + log4jdbc. The `log4jdbc` driver wraps the real driver to log SQL:

```yaml
driver-class-name: net.sf.log4jdbc.sql.jdbcapi.DriverSpy
jdbc-url: jdbc:log4jdbc:mysql://${DB_HOST}:${DB_PORT}/<database>
```

MyBatis XML mappers live under `src/main/resources/sqlmap/`.

### Sensitive Config Encryption (Jasypt)

DB passwords and other secrets in `application.yml` use `ENC(...)` format:

```yaml
password: ENC(ydLjxrknr8dD59e6E+HvxdxRaGiFa9jOCpJJDtb0uak=)
```

Decryption is **not** handled by jasypt-spring-boot-starter (it has no Spring Boot 4-compatible release) — `dstone-common`'s `net.dstone.common.config.ConfigProperty` declares a nested static `EncPropertyEnvironmentPostProcessor` (registered via `dstone-common/src/main/resources/META-INF/spring.factories`) that wraps every `PropertySource` and transparently decrypts any `ENC(...)` value using `EncUtil.getEncryptor()` (`net.dstone.common.utils.EncUtil`, PBEWithSHA256And128BitAES-CBC-BC, key hardcoded in that class) before Spring binds it — including `@ConfigurationProperties`-bound values like `ConfigDatasource`'s HikariCP passwords, which never pass through `ConfigProperty.getProperty()` at all. This applies automatically to every module that depends on `dstone-common`; no per-module `ConfigEnc`/`@EnableEncryptableProperties` bean is needed anymore. To generate a new `ENC(...)` value locally without ever typing the plaintext secret into Claude Code's chat (run this in a separate terminal, not via the assistant):

```bash
cd dstone-common && mvn -q exec:java -Dexec.mainClass=net.dstone.common.utils.EncUtil -Dexec.args="<plaintext>"
```

### Security

- **dstone-boot**: Spring Security enabled (`spring.security.enabled: true`), with custom auth handlers in `net.dstone.boot.common.security`, OAuth2 social login (Google/Naver/Kakao), and Redis-based distributed sessions (`dstone:session` namespace).
- **dstone-batch**: Spring Security excluded via `spring.autoconfigure.exclude`.
- **dstone-knowledge**: Spring Security excluded the same way. `common.security.ApiKeyAuthFilter` (`X-API-Key`, `dstone.knowledge.security.auth.enabled`, default off, `/api/system/health` exempt) sets the caller in `CallerContext`; the caller is the tenant of uploaded general documents only — code analysis results are not split per caller.
- **dstone-ai-engine**: Spring Security (and its Actuator management-endpoint security) excluded via `spring.autoconfigure.exclude` — no Spring Security filter chain. Auth is instead a lightweight opt-in servlet filter, `common.security.ApiKeyAuthFilter` (`X-API-Key` header, `dstone.ai.security.auth.enabled`), paired with `common.security.RateLimitFilter` (`dstone.ai.security.ratelimit.enabled`).

### dstone-boot: Multiple Datasources

Three independent datasources configured in `ConfigDatasource.java`:
- `common` → `sampleDB` (main app data)
- `sample` → `sampleDB` (sample data)
- `analyzer` → `analyzeDB` (code analysis results)

### dstone-boot: Source Code Analyzer

A built-in static analysis engine for Java web applications:

- `AnalysisController` → accepts async analysis requests
- `AppAnalyzer` (`net.dstone.boot.common.tools.analyzer`) → core engine
  - `.java` files: parsed with **javaparser 3.28.1** (class hierarchy, method calls, URL mappings)
  - `.jsp` files: parsed with **jsoup 1.11.3** (page structure, links)
  - MyBatis `.xml` files: parsed with **JSQLParser 4.7** (SQL, CRUD table relationships)
- Results stored in the `analyzer` datasource, visualized via `ReportController`

### dstone-batch: Job Development Pattern

All batch jobs extend `BaseJobConfig` and are annotated with `@AutoRegJob`:

```java
@Component
@AutoRegJob(name = "myJob")
public class MyJobConfig extends BaseJobConfig {
    @Override
    public void configJob() throws Exception {
        this.addStep(this.createStep("step1"));
        this.addStep(this.createMultiThreadStep("step2", 20, 5, reader, processor, writer));
        this.addFlow(this.createSplitFlow("parallelFlow"));
    }
}
```

`ConfigAutoReg.java` scans for `@AutoRegJob` and registers jobs in `JobRegistry`.

- `auto-register-jobs: true` → all jobs registered at startup (REST API mode)
- `auto-register-jobs: false` → jobs registered individually at execution time (CLI / SCDF mode)

Spring Batch metadata tables must be created manually from `src/main/resources/schema/*.sql` (`initialize-schema: NEVER`). Spring Batch 6 renamed the `BATCH_JOB_SEQ` sequence table to `BATCH_JOB_INSTANCE_SEQ` — existing databases created from an older schema file need that table renamed (or the updated `02-create-table-mysql-dstone-batch.sql` re-run) before job launches will work.

### dstone-batchadmin: Batch Job Management

Manages `dstone-batch` jobs via two mechanisms, both configured per registered batch server (`TB_BATCH_SERVER`):
- **Direct DB read** for list/detail/history — queries the target server's Spring Batch metadata tables (`BATCH_JOB_INSTANCE`/`BATCH_JOB_EXECUTION`/`BATCH_STEP_EXECUTION`) through a `RoutingDataSource` (`common/datasource/RoutingDataSource.java`) that resolves the correct `HikariDataSource` per server at runtime (built/cached by `BatchServerDataSourceRegistry`).
- **REST calls** for control actions (start/stop/restart/abandon/delete) — `common/rest/BatchRestClient.java` calls the target server's `dstone-batch` `RestApiRunner` endpoints (`/batch/startJob/{jobName}`, `/batch/stopJob/{id}`, etc.).

Two datasources:
- `common` → `batchadmin` schema (static, own login users/`TB_ADMIN_USER`, server registry/`TB_BATCH_SERVER`, job metadata/`TB_BATCH_JOB`)
- `batch` → the `RoutingDataSource` described above (dynamic, one target per registered server)

Since `RoutingDataSource` prevents MyBatis's `databaseIdProvider` from resolving per-query, MySQL/PostgreSQL differences (mainly paging syntax) are handled with an explicit `DBMS_TYPE` query parameter and `<choose>` branches in `sqlmap/job/BatchJobExecDao.xml`, rather than the `databaseId` mapper attribute.

Registered Job metadata (`TB_BATCH_JOB.JOB_NM`) must match the `@AutoRegJob(name=...)` value on the target `dstone-batch` server exactly — `dstone-batchadmin` cannot create new Job logic, only manage metadata and trigger the existing REST API. `common/scheduler/JobScheduleManager.java` uses Spring's built-in `ThreadPoolTaskScheduler` + `CronTrigger` (no Quartz) to auto-start jobs whose `SCHEDULE_USE_YN='Y'`.

Security is simplified vs. `dstone-boot`: login is required (`TB_ADMIN_USER`, `BCryptPasswordEncoder`) but there is no per-URL role/permission check — it's a single-role internal admin tool.

### dstone-ai-engine: AI & MLOps Core Engine

A Spring AI-based, provider-agnostic engine meant to be reused across future SI projects. Fully redesigned on 2026-09-15 around a **Workflow → Step → Agent → Tool** model: Java (`runtime.workflow.WorkFlowExecutor`) controls the overall sequence/branch/parallel/loop shape, while the intelligent judgment inside each step (analysis, conversion strategy, tool choice) is left to the LLM. What a Workflow or Agent actually does is declared in YAML (`resources/workflows/*.yml`, `resources/agents/*.yml`), not Java code or `application.yml` — adding a new one is a new YAML file, no redeploy-affecting code change. Step-to-step data flow (contract model 2026-09-28, jq expressions 2026-09-29): **the callee owns the contract** — an Agent declares what it takes and returns (`agents/*.yml` `input`/`output`, standard JSON Schema written as YAML under `schema:`, shorthand `input: string`/`list<string>` allowed, both default to `string`), a Tool's contract is its arg schema/reply, and SUPERVISOR/ROUTER/APPROVAL outputs are engine-fixed (their Agents must not declare `output`). APPROVAL has two modes: approve/reject (`onSuccess`/`onFailure`, output `{approved, approver, comment}`) or, when the step declares `routes`, a human-picked choice (decision body `{route, ...}`, output `{route, approver, comment}`, never fails; `routes` + `onSuccess`/`onFailure` together fails boot, an unknown `route` is a 400 and the run stays waiting). `ApprovalStepExecutor` deletes the decision from `approvals` once consumed, so a flow may loop back to the same APPROVAL step and be asked again (the last decision stays readable at `steps.<id>.output`); `GET .../executions/{id}` exposes `pendingApproval {stepId, approverRole, routes}` so the dstone-boot admin screen can render one button per route. A step only says what to put in (`input`, required for AGENT/SUPERVISOR/ROUTER, shaped per the Agent's input schema: text for string, map for object; TOOL is an arg map) and where to go next. A Workflow declares its request contract (`input`, default `string`; request body is `{input, sessionId}` — no `message`/`variables`) and its result (`output: {value, schema?}`, `value` required). All state lives in one execution-context tree with **no implicit names**: `input` (the request input as-is), `steps.<id>.{input,output,error}`, `approvals` (internal). There is no `previous`, `text`, `items` or `inputs.message`; `.steps.<id>.<anything but input/output/error>` fails startup. Every value is JSON; the only expression form is a whole value `"${ <jq> }"` over the context `{input, steps}` (`approvals` hidden), e.g. `"${ .steps.fix.output.sql // .input }"`, `'${ "(분류: " + .steps.classify.output.route + ") " + .input.message }'` — no mid-string interpolation (build text with jq `+`), no `{{ }}` (fails boot with a hint). jq was chosen over SpEL because it's side-effect free (no arbitrary Java calls from shared YAML). A missing path is `null` (use `//`), a jq runtime error fails the step (→ `onFailure`), a step executor exception fails the whole run, an `AgentContractException` is a step failure (→ `onFailure`). `${VAR}` in YAML is a separate load-time env substitution that only matches `[A-Z0-9_]+`, so it never collides with `${ .jq }`. MCP tool calls are serialized per server (`ConfigMcp.SerializedToolCallback`) because one STDIO client can't take concurrent requests. Steps do **not** share chat memory: `MessageChatMemoryAdvisor` is not a `ChatClient` default advisor — `AgentExecutor.buildSpec()` attaches it only when given a conversation id (chat API: request `sessionId`; Workflow: only AGENT/SUPERVISOR/ROUTER steps with `memory: true`, room `sessionId:stepId` via `WorkFlowExecution.conversationIdOf()`, e.g. for retry loops; `memory` + `forEach` fails boot). `spring.ai.openai.timeout` does **not** reach chat calls on its own in Spring AI 2.0.1: `OpenAiChatModel.buildRequestOptions()` overrides the client timeout on every request with `OpenAiChatOptions.getTimeout()`, which has no config key and defaults to 60s (seen 2026-10-02: a slow model writing a long document was cut at exactly 60s — `Error reading response (원인: InterruptedIOException: timeout <- StreamResetException: stream was reset: CANCEL)`). So `ConfigChatClient.requestOptions(model)` builds the per-request options — an `OpenAiChatOptions` builder carrying that timeout when the provider is `openai`, plus the model override — and `AgentExecutor.buildSpec()` attaches it on every call; putting it in `ChatClient.defaultOptions` is not enough because a per-request `options(...)` replaces the defaults wholesale. Tool loop control and per-Agent reasoning (2026-10-07, done instead of adopting Spring AI Alibaba — its Graph runtime would only replace `WorkFlowExecutor`, which already has sequence/branch/forEach/loop/approval, and the useful parts (context editing, tool-call limits) were small enough to build on Spring AI itself; the reviewed proposal is `docs/temp/dstone-ai-engine_SAA_통합전략_설계정리.md`). In Spring AI 2.0.1 the tool loop is an advisor (`ToolCallingAdvisor`, auto-registered, order `HIGHEST_PRECEDENCE + 300`; the memory advisor is +200, so it sits outside the loop), not something inside the chat model, so anything with a larger order runs once per LLM round. Three pieces, all attached per call in `AgentExecutor.buildSpec()`: (1) `runtime.agent.ToolCallBudgetCallback` wraps the Agent's Tools with one shared counter — limit = Agent YAML `maxToolCalls`, else `dstone.ai.agent.tool.max-calls` (100); from the last fifth on it appends "N calls left, save your result now" to Tool results (blocking without warning leaves the output file unsaved), past the limit it returns `실패: ...` without running the Tool, and after 3 such refusals it throws `AgentContractException` (step failure → `onFailure`); Sub Agent calls are not counted. (2) `runtime.agent.ToolResultCompactionAdvisor` (order −100, rules in the pure `ToolResultCompactor`): when the Tool results of the current turn add up to more than `dstone.ai.agent.tool.keep-result-chars` (200,000; 0 = off) it cuts the **oldest** ones to their first 300 chars plus a "call the Tool again if you need this" notice, never the latest result or results ≤ 600 chars; only the copy sent to the model is cut, and what is cut stays cut on later rounds (prompt cache). It is deliberately **not** a Spring bean — any `Advisor` bean would be injected into `ConfigChatClient.chatClient(...)` in place of the `defaultAdvisors` list bean and silently drop `LlmLoggerAdvisor`. (3) Spring AI's own limits (`spring.ai.tools.limits.*`, default 40 per Tool / 150 total, not per-Agent) are loosened in `conf/application.yml` (−1 / 300); when they do trip, Spring AI ends the loop with the text `Tool call limit exceeded…` as the answer (`finishReason=toolCallLimitExceeded`) and `AgentExecutor.textOf()` turns that into an `AgentContractException` instead of passing it on as the Agent's answer. Agent YAML `reasoning: none|low|medium|high` (unset = model default; **`none`, not `off` — YAML reads `off` as `false`**, a bad value fails boot) is mapped per provider in `ConfigChatClient.requestOptions(model, reasoning)`: openai/OpenRouter `reasoning_effort`, ollama think on/off, anthropic thinking disabled / budget 1024·2048·4096. Checked live on OpenRouter `qwen/qwen3.8-27b` with one small ordering question: unset 41.7 s (2,407 reasoning tokens), `none` 0.5 s (0 reasoning tokens), same answer — single runs, and the ollama/anthropic mappings have not been run. `pilot-workflow` has two paths since 2026-10-08 (YAML only, no Java; source proposal `docs/temp/Agent_Workflow_안정화_방안.docx`). After `step00` a ROUTER step `classify` (`pilot-request-router-agent`, no Tools, `reasoning: none`) picks `신규개발` or `일반` from the request text alone (mixed or unsure → `일반`, router failure → `일반`). **Everything written above about `pilot` Agents describes the 일반 path** (`step01`–`step07`, unchanged in shape; their new-development sections now only serve mixed requests). The 신규개발 path (`new*` steps, Agents `agents/pilot/2x.newdev-*.yml`) moves what prompts used to ask the LLM to do into the Workflow: `newRef` (Agent) only collects reference-implementation file paths → `newRefExist`/`newPack` (TOOL `isFileExist`/`readFile` with forEach) read them once without an LLM → `newAnalyze` (one LLM call, no Tools) returns requirements + layer decisions + change targets + `sharedNames` as JSON → `newExist`/`newCheck` validate in jq (FR ↔ target mapping, file exists / must not exist, target was read) → `newReqDoc`/`newImpactDoc` render `01-requirements.md`/`02-impact.md` with jq → APPROVAL → `newDesign` (AGENT forEach, one fresh call per target file, no Tools) → `newDesignCheck` (each `before` must occur exactly once in the current file, CR stripped) → `newDesignDoc` → APPROVAL → `newCopy`/`newCreate`/`newEdit`/`newAppend` (TOOL forEach: `copyFileWithReplace` with the designer's `renames`, `writeFile`, `replaceInFile` with `edits`, `appendFile`) → `newRead` (TOOL `readFileLines`) → `newDevelop` (AGENT forEach, **no Tools**, returns line-number edits) → `newApply` (TOOL `editFileLines`) → `newTasksDoc`. Things to remember: (1) **Agents on this path emit data, never documents** — the md files are rendered by TOOL `writeFile` steps, so editing them by hand changes nothing downstream (corrections go into the approval `comment`, which becomes the Agent's `feedback`); (2) a check result is read from the writing step's **input** (`.steps.newCheck.input.fileContents`) because `writeFile`'s output is only "saved"; (3) checks never auto-retry — a failed check is written into the doc and the human picks 재분석/재설계 (an automatic loop would spin to `maxIterations` on a persistent mistake); (4) forEach runs in parallel, so one file must not appear twice in the targets, and a partial forEach failure is routed on to the check/summary step instead of failing the run; (5) per-file design needs the names shared between files fixed up front, hence `sharedNames`; (6) `output.value` drops `newPack` and `newRead` (file contents); (7) **only TOOL steps touch source files** — what the design fixed exactly is applied without an LLM, and the one thing left to the LLM (turning the designer's prose `removes`/`adds` into edits) is returned as `edits[{action: delete|replace|insertAfter, startLine, endLine, startText, endText, newText}]` against the numbered source, never applied by the Agent; `editFileLines` applies a file's edits all-or-nothing (line numbers refer to the file before the call; `startText`/`endText` must equal those lines, blank lines at a range edge are skipped; overlap or mismatch → nothing changed, reason in `04-tasks.md`), and appends `주의:` when the bracket balance changed, which makes the task `확인 필요`. Tool calling has no infrastructure dependency — it's plain Java executed on demand. `common.annotation.AiTool` (meta-annotated `@Component`) marks a class containing `@org.springframework.ai.tool.annotation.Tool` methods; `common.config.ConfigTool` scans for `@AiTool` beans via `ApplicationContext.getBeansWithAnnotation` and wraps them into a `ToolCallbackProvider`, filterable per caller via `dstone.ai.tool.allowed-by-caller`. An Agent only ever sees the Tools named in its own `tools` list (there is no `toolsEnabled` switch anymore — a boolean that exposed every registered Tool was too loose for YAML written by non-developers). An `AGENT`/`SUPERVISOR` Workflow step lets the LLM pick among those through Spring AI's own tool-calling loop; a `TOOL` step calls one deterministically by name via `runtime.tool.ToolExecutor` (no LLM involved) — both paths go through the same `ConfigTool` whitelist. `ConfigTool` also wraps every Tool (local and MCP) in `LimitedToolCallback`, which cuts any single result longer than `dstone.ai.tool.max-result-chars` (default 60000) and appends a "narrow the range and call again" notice — Tool results pile up in the conversation and are re-sent on every LLM call, so one oversized result blows the context limit or the response timeout (seen 2026-10-01: a project-root file listing including `.git` made a 700KB request → `OpenAIIoException: Request failed`). `LimitedToolCallback` also answers a **cut-off Tool argument** itself: when the LLM's argument JSON does not parse (a long `writeFile` body hit `max-tokens`; reasoning tokens count against it — seen 2026-10-07 on a 12,873-char document, Spring AI only logs `Conversion from JSON failed` / `Unexpected end-of-input` and the model rewrote the whole document at the same length) it does not call the Tool and returns `실패: Tool 인자가 중간에 끊겨서 도착했습니다 …` telling the model to split the content with `writeFile` + `appendFile` (`FileUtil.appendFile`, added for this). `tools.utils.FileUtil` limits itself first (`dstone.ai.tool.file.*`: `readFileListAll` skips `exclude-dirs`, returns only per-folder file counts (`folders`) when more than `list-summary-over` (100) files are found — a project-root listing of 41,524 chars was re-sent on 17 later LLM calls despite the prompt saying "don't list the root" — and caps the count, a missing file is answered without calling `dstone-common`'s `FileUtil.readFile` (which `printStackTrace()`s a 90-line stack for every guessed path), `searchInFiles` returns capped `path:line: text` matches for a plain keyword, `readFile`/`readFileLines`/`readFileTail` cap characters); source-investigating Agents are told to `searchInFiles` first and open only the files they need, and to use `readFileLines` (`N: text` lines, optional `startLine`/`endLine`) whenever they need line numbers — with plain `readFile` a reasoning model counts lines by hand, burns the whole `max-tokens` on reasoning and returns an empty answer (`finishReason=LENGTH`, seen 2026-10-02 on `pilot-workflow` step03; `AgentExecutor.textOf()` now turns that case into an explicit `AgentContractException`, and SUPERVISOR/ROUTER failure messages carry the real reason instead of a constant `answer[null]`). `readFile` itself stays number-free because some Agents write what they read back with `writeFile`. `tools.shell.ShellExecTool`/`tools.python.PythonExecTool`/`tools.http.HttpCallTool` have no separate on/off flag — they only ever run a whitelisted script path or hit a whitelisted host (`dstone.ai.tool.shell.allowed-commands` / `.python.allowed-scripts` / `.http.allowed-hosts`, empty by default), never an LLM-supplied raw command/URL body. An empty whitelist is what keeps them inert by default; there used to be a `dstone.ai.tool.{shell,python,http}.enabled` flag documented alongside the whitelist, but it was never actually wired into the code (no `@ConditionalOnProperty` on the classes), so it was removed rather than implemented — the whitelist alone is the real gate.

### dstone-knowledge: Java Analysis → Knowledge Graph → RAG

Analyzes Java applications (Spring **and** legacy plain Java: Java 1.4–7 syntax, XML config, servlets, raw JDBC, JSP) into a structured knowledge model first, then projects that model into a Knowledge Graph and RAG chunks. Current state, design principles, schema and the milestone table (M0–M9) live in `docs/11.dstone-knowledge.md`; the source design is `docs/temp/Java_Application_Knowledge_Graph_RAG_Analysis_Platform_설계서_v1.0.docx`. Rules that were decided with the user and must hold for all later milestones:

- **DB-backed pipeline, never whole-project-in-memory.** Each pass handles one file, writes rows, drops the AST (`analysis_file_pass` tracks per-file/per-pass progress so a run resumes; `analysis_reference` holds not-yet-resolved references between the DECLARE and RESOLVE passes). JavaSymbolSolver's default source type solver caches every parsed file and must be replaced by a DB-index-backed solver with a bounded cache.
- **Framework-neutral core.** Scan/AST/symbols/call graph need plain Java only; Spring is one semantic-analyzer plugin among others (plain-Java entry points, Spring XML, iBATIS, Struts, JSP).
- **Lombok handled at declaration time**: generated members go in as `is_synthetic=true` symbols (no delombok — it shifts line numbers).
- **Embedding keyed by `(content_hash, model)`** in `rag_embedding`, which doubles as the resumable queue; Spring AI is used only for the embedding model call, vector SQL is MyBatis (no `PgVectorStore`).
- **`analysis_*` is the only source of truth**; `kg_node`/`kg_edge` are VIEWs, `rag_*` is always regenerable. Every analysis row carries `revision_id`; symbol ids are revision-independent hashes. Full snapshot per revision + retention.
- No LLM chat in this module — `dstone-ai-engine` Agents call its REST API through Tools.

Job model (M1, 2026-10-05): analysis starts over REST (`POST /api/projects/{id}/analyses`, local directory only — git checkout is still not implemented; an outside tool such as Jenkins is expected to check out and then call the API) and runs on `analysisJobExecutor`. `job.AnalysisJobRunner` runs every `job.AnalysisPass` bean in `order()` and skips passes already `DONE` for that revision in `analysis_revision_pass` — re-posting the same `revisionLabel` is how a dead/cancelled run resumes and how a newly added pass runs on an old revision. A new pass = a new `AnalysisPass` bean; it must be idempotent on re-run and call `context.checkCancelled()` in its loop. `AnalysisJobRecovery` marks leftover `READY`/`RUNNING` jobs `FAILED` at boot (single-instance assumption). Job threads set `SUPPRESS_SQL_LOG` so bulk writes don't flood the log. Inside a `sqlSessionBatch` transaction never touch `sqlSessionCommon` (MyBatis refuses to switch executor type mid-transaction) — `AnalysisJobReporter` progress/error writes go after the transaction. Per-file passes go through `job.FilePassRunner` (seeds `analysis_file_pass`, pulls `PENDING` files in chunks, runs each file as `prepare` → `write`, committing one file's rows plus its DONE mark in one transaction; a `FileHandler` returns `FileResult` or throws → that file `FAILED`, run continues). Passes so far: `scanner.ScanPass` (100), `incremental.CarryPass` (150), `parser.DeclarePass` (200), `resource.ResourcePass` (250), `incremental.CarryResolvePass` (290), `resolver.ResolvePass` (300), `resolver.LinkPass` (400, SQL-only), `semantic.SemanticPass` (500), `rag.DocumentPass` (600). `classes` is deliberately not in `scan.exclude-dirs` because the real sample apps under `/app/sampleApps/` (`anybiz_prd`, `cms4_prd` — exploded production WARs, outside the repo) keep their `.java` in `WEB-INF/classes`.

DECLARE (`parser`): `JavaSourceParser` tries language levels 21 → 8 → 1.4 (project `javaVersion` first) because old sources use today's keywords (`enum`, `assert`, `_`) as identifiers; `DeclarationCollector` looks at one file only — never the DB or other files — so order doesn't matter. Symbol ids are SHA-1 of `project | source root | kind | fqn[#signature]` (source root included because the same FQN really does occur twice in one project), and **signatures use parameter types as written in source** (generics erased), not resolved FQNs — resolving needs other files and would make ids order-dependent. References are stored unresolved in `analysis_reference` with the position of the *name* token (chained calls `a.get().get()` share an expression start). Anonymous classes are kind `ANONYMOUS` (`Outer$1`) and own the calls inside them; lambdas don't. `LombokExpander` adds what Lombok would generate as `is_synthetic` rows by reading annotations only — this module's own code uses no Lombok (repo-wide rule: no Lombok in dstone code). Same FQN in two files of one source root: the file named after the type wins regardless of processing order, the other is `SKIPPED` with a `DUPLICATE_TYPE` error. JSON columns are written with `common.util.JsonText` (compact), not `ConvertUtil.convertToJson` (pretty-prints). A cheap independent check of DECLARE output: named + anonymous type count equals the number of `.class` files of a compiled target.

Type solving (`symbol`): `DbTypeSolver` answers "which file declares this FQN" from `analysis_symbol`, parses only that file and keeps ASTs in a `BoundedCache` (LRU). That alone does **not** bound memory — `CombinedTypeSolver` must be built with `NoCache.create()` (its default cache pins every resolved declaration, hence every AST) and `JavaParserFacade.clearInstances()` must be called after each file. Solver order: `DbTypeSolver` → `ReflectionTypeSolver(new ResolvePass.JdkClassFilter())` → `JarTypeSolver`s. The JDK filter matters both ways: unfiltered reflection would resolve the target's `org.springframework…` against the analyzer's own Spring, while JavaSymbolSolver's built-in `jreOnly` only passes `java.`/`javax.` and misses `org.w3c.dom` etc.

RESOLVE/LINK (`resolver`, M2): **the target is never built** — jars are used when present (`symbol.ClasspathResolver`: every `*.jar` under the project folder plus the project's `classpath` field, which accepts jar files/directories separated by comma, newline or path separator, so `mvn dependency:build-classpath` output can be pasted as is) and the analysis still finishes without them. `ReferenceResolver` matches each `analysis_reference` row to its AST node by position, then tries in order: symbol solver (HIGH) → owner type known, member looked up by name/arity in that type and its in-project ancestors (HIGH if the single hit is a synthetic/Lombok member, else MEDIUM, several → LOW) → owner type external (EXTERNAL_METHOD `Type.name`, MEDIUM) → project-wide name/arity with ≤5 candidates (LOW) → `UNRESOLVED` with a reason. Owner type comes from the solver, else from the variable's declaration text + imports, a synthetic field (`log`), or the declared return type of the preceding call (builder chains). A scope-less call not found in the enclosing types is treated as inherited from an external supertype and is deliberately **not** guessed project-wide. Resolved declarations are mapped to `method_id` by position (file + line + name + arity), not by name, so anonymous/local class methods work. `LinkPass` builds `OVERRIDES` and `CALLS_POSSIBLE_IMPLEMENTATION` in SQL; the latter only for abstract targets — including concrete overridden methods fanned 1,553 calls of `BaseVO.setMb_id()` out to every overriding subclass (27,715 noise edges on `anybiz_prd`). Measured: 99.9% of calls resolved on the two sample WARs; with zero jars a copy of `dstone-batchadmin` still recovered 227/234 in-project call pairs, HIGH and MEDIUM edges all correct, LOW 11/27 — treat LOW as a hint only. `src/test/resources/samples/lombok-app` (calls into Lombok-generated members, no Lombok jar), `cycle-app` and `legacy-app` each carry expected results in their README. Large-scale RESOLVE (tens of thousands of files) has not been run yet.

SEMANTIC (`semantic`, M3): `SemanticPass` clears and rebuilds, in one `sqlSessionCommon` transaction, everything its plugins produce — `analysis_endpoint`, `analysis_symbol.layer`, `INJECTS` relations, `proxy_related`, and the `web.xml` rows in `analysis_resource`. A framework rule = a new `SemanticPlugin` bean (`name`/`order`/`run`); it must be a no-op on projects it doesn't apply to and should derive from `analysis_annotation`/`analysis_relation` in SQL rather than re-parse Java (annotation attributes are already JSON, so e.g. class-level + method-level `@RequestMapping` paths are joined with `jsonb_array_elements_text` in `SemanticDao.xml`). Current plugins (plus `RichClientPlugin` 510, see the rich-client paragraph below): `SpringPlugin` (100: HTTP/SCHEDULED/LISTENER endpoints, `@Autowired` field → `INJECTS`, stereotype layers HIGH), `ServletPlugin` (200: `web.xml` via `WebXmlReader`, which blocks external DTD fetches because Servlet ≤2.3 descriptors carry an internet DOCTYPE; external servlet classes such as `DispatcherServlet` are kept as method-less `SERVLET` endpoints; `HttpServlet` subclasses → CONTROLLER MEDIUM), `PlainJavaPlugin` (300: `main`, `Runnable`/`Thread`/`Callable` → THREAD, JSPs outside `WEB-INF`), `NamingLayerPlugin` (900: suffix rules, LOW, only fills what earlier plugins left null). Annotations are matched by simple name because wildcard imports leave `annotation_fqn` null. Not handled yet: constant-valued mapping paths, inherited class-level mappings, constructor/setter injection, lambda `Runnable`s. The M5 plugins (`MyBatisPlugin`, `JspPlugin`, `StrutsPlugin`) are described below.

RAG (`rag`, M4): no manual step between analysis and search. `DocumentPass` builds FILE/TYPE/METHOD documents per Java file from DB facts plus source lines cut by line number (no re-parse; `CodeDocumentBuilder` is pure and unit-tested) and enqueues chunk hashes into `rag_embedding` as `PENDING`; `EmbeddingWorker`, a daemon thread started on `ApplicationReadyEvent`, drains that table in batches through Spring AI's `EmbeddingModel` (Ollama `bge-m3:latest`, 1024 dims, same server as `dstone-ai-engine`; `spring.ai.model.chat: none`). So a job goes `DONE` within seconds of DOCUMENT while embedding continues behind it — check `GET /api/revisions/{id}/rag`. METHOD chunks deliberately carry analysis facts as Korean text (endpoint path, layer, callees, possible implementations, callers, doc comment) ahead of the source, because a question like "주문 취소는 어디서 처리하나" doesn't resemble source text; trivial accessors get no METHOD document (`rag.skip-accessors`): `get`/`set`/`is` name, ≤3 lines **and a field of that name in the same type** — name and length alone also dropped short working methods such as `DBUtil.getConnection()`, which then could not be found at all (`anybiz_prd`: 14,762 methods → 5,375 documents). When the embedding server is down the worker counts nothing as failed and retries every 30 s; only an item that still fails when sent alone gets `attempts+1` (3 → `FAILED`). `POST /api/search` embeds the query and runs a MyBatis pgvector query filtered by revision inside a transaction with `SET LOCAL hnsw.iterative_scan = relaxed_order` — embeddings of all revisions share one HNSW index, so without iterative scan a revision filter can return too few rows. Model name and dimensions must be read through `RagSettings` everywhere (enqueue, worker, search) because the key is `(content_hash, model)`. CPU embedding here runs ~96 chunks/min. Search itself is hybrid since M6 (below). Local pitfall hit on 2026-10-05: `/opt/ollama/ollama-start.sh` refused to start because a stale `ollama-server.pid` held a number now reused as a **thread id** of another process (`kill -0` succeeds on TIDs) — check `ss -ltnp | grep 11434`, delete the pid file, start; never run `ollama-stop.sh` on a stale pid.

Non-Java resources (`resource` + `semantic`, M5, 2026-10-05): reading and linking are split — `resource.ResourcePass` (250) reads one file at a time and only stores (MyBatis/iBATIS mappers → `analysis_mapper`, `.properties`/YAML → `analysis_config`, `pom.xml`/`build.gradle`/Spring XML → `analysis_resource`), and SEMANTIC plugins link afterwards, because an `<include>` fragment may live in another file and both ends of a relation must already be in the DB. The chain is `JSP ─REQUESTS→ method ─CALLS→ … ─EXECUTES_SQL→ statement ─READS_TABLE/WRITES_TABLE→ table`, plus `method ─RENDERS→ JSP` and `JSP ─INCLUDES→ JSP`. Relation ends are no longer symbols only: a statement is `'S' + mapper_id`, a file is `'F' + file_id`, a table is just a name in `to_external` (no node). `/callees` follows `EXECUTES_SQL`/`READS_TABLE`/`WRITES_TABLE`/`RENDERS`, `/callers` includes `REQUESTS`; `/tables`, `/tables/{table}`, `/mappers`, `/resources` are in `ResourceController`. Rules to keep:

- **Secrets are never stored**: config keys/bean properties that look like `password`/`secret`/`token`/`api-key` get `****` (`value_type = MASKED`) — analysis output is searched and forwarded.
- **All XML goes through `common.util.SafeXml`** (external DTD/entities replaced by empty content — old descriptors carry an internet DOCTYPE and parsing would hang on it); YAML is read with `SafeConstructor`.
- **Statement names are computed, never guessed** (`MyBatisPlugin` + `semantic.ConstantEvaluator`): DECLARE keeps a call's first argument as written in `analysis_reference.arg_text` (only when it contains a string literal); the evaluator handles literals, `+`, field initializers of the type and its ancestors, and no-arg methods with a single `return`. Any unknown part (local variable, parameter) → the whole value is unknown. A name that is known but has no statement stays as an `UNRESOLVED` `EXECUTES_SQL` with the name in `to_external`.
- **JSQLParser only in fast mode, on the calling thread** (`semantic.SqlTableExtractor`): its fallback complex mode can run practically forever on some SQL, and its timeout feature merely stops waiting while the parse thread keeps burning CPU — that piled up dozens of threads and made SEMANTIC take ~7 minutes on `anybiz_prd`. SQL deeper than 12 parentheses or longer than 20,000 chars skips the parser. Parser failure falls back to a regex over `FROM`/`JOIN`/`INTO`/`UPDATE` (`MEDIUM`, `properties_json.via = PATTERN`) — about 30% of statements on `anybiz_prd` (530 of 1,853; 278 of those are one JSQLParser internal error, `Index -1 out of bounds`, cause not tracked down).
- **JSP Java code is converted to Java, not analyzed separately** (`parser.JspToJava`): scriptlets become the body of `_jspService()`, and every dropped character keeps its newline so line N of the converted source is line N of the JSP. A JSP without Java code is skipped by DECLARE (stays `PENDING` in `parse_status`) but still gets `RENDERS`/`REQUESTS`/`INCLUDES` and a `VIEW` document.
- `RENDERS` matches `new ModelAndView("x")`/`setViewName("x")` to the single JSP whose path ends with `x.jsp`; `REQUESTS` (MEDIUM) takes every `/path`-looking text in a JSP and keeps only exact matches with an endpoint path. A low `RENDERS` count is expected, not a bug: on `anybiz_prd` 920 of 1,405 view-name references are `"jsonView"` (a view bean) and all 463 linkable ones were linked (checked 2026-10-05). `return "order/list";` view names and Tiles are not handled.
- `StrutsPlugin` reads `struts-config.xml`/`struts.xml` itself (like `ServletPlugin` reads `web.xml`); a `DispatchAction` endpoint is linked to its type only, and Struts 2 is covered by unit tests only.
- `DocumentPass` now also writes `MAPPER` (one per statement) and `VIEW` (one per JSP) documents via `rag.ResourceDocumentBuilder`, and METHOD documents carry "executed SQL / rendered view" lines.

`src/test/resources/samples/struts-app` (Struts 1 + iBATIS + JSP, expected values in its README) is the end-to-end check for this chain, since the two real WARs have neither Struts nor iBATIS.

Rich-client screens (2026-10-07): the screen side used to be JSP-only; `semantic.RichClientPlugin` (510) + the pure, unit-tested `semantic.ScreenScript` now cover WebSquare and Nexacro / X-Platform. SCAN classifies them (`FileClassifier`: `WEBSQUARE` = root `<html>` carrying the `http://www.inswave.com/websquare` namespace, `NEXACRO` = `.xfdl` / root `<FDL>`, `NEXACRO_APP` = `.xadl`); their **language stays `XML`**, so anything that means "screen" must test `language = 'JSP' OR file_type IN ('WEBSQUARE','NEXACRO')` (`GraphDao.xml` `isScreen`) — the graph node kind is still called `JSP` (= screen) and `subType` tells which. Such screens are never rendered by the server, so there is no `RENDERS` and no DECLARE/RESOLVE; the only link is `REQUESTS`, found two ways: (1) path text equal to an endpoint path, like JSP (`via = PATH_TEXT`, MEDIUM; `svc::order/list.do` is stripped to `/order/list.do`; a path with a literal context path such as `/hi-japan/reporting.do` is retried without its first segment → LOW); (2) **call rules** for projects whose screens call the server by a transaction ID instead of a URL — `dstone.knowledge.semantic.screen.call-rules: "function=methodTemplate,…"`, e.g. `doRequestAjax=perform{id}` links `HiJS.svr.doRequestAjax("JCST0200M01S", …)` to the method named `performJCST0200M01S` (`via = CALL_RULE`; one method of that name → HIGH, 2–5 → LOW each, none → an `UNRESOLVED` `REQUESTS` with the name in `to_external`; `properties_json.path` holds the ID). Same "computed, never guessed" rule as statement names: only a quoted first argument counts, a variable is merely counted, and anything inside `//`, `/* */` or `<!-- -->` is ignored. Screen → screen (`<w2:wframe src>`, popups, Nexacro `Div url`) is `INCLUDES`, resolved by "path ends with" after dropping a context path / `Base::` prefix / `?query`. `ScreenScript` marks comment ranges in **one pass** (`commentMask`) — looking backwards per match was quadratic and one 2.3MB screen made SEMANTIC take 93 s instead of 9 s. `DocumentPass` writes `VIEW` documents for these files inside its XML handler. Verified on the real WebSquare project `/app/HI-Japan/was` (outside the repo; 1,869 Java files, 317 screens, **zero** `<xf:submission>` — every call goes through `doRequestAjax`): 680 call-rule links + 2 unresolved = the 682 (screen, ID) pairs an independent grep finds, 34 path links all correct, 399 `INCLUDES`. `src/test/resources/samples/websquare-app` and `nexacro-app` carry expected values in their READMEs; **Nexacro and the standard WebSquare submission form have only been checked on those hand-made samples**. **Query XML** (same day): that project's SQL is not MyBatis/iBATIS but JEF-framework `<document><query|combo|delete id><statement>` files, so SCAN classifies them `QUERY_XML` and `MapperXmlReader.readQueryXml` stores them in `analysis_mapper` (`mapper_type = QUERY_XML`): **namespace = file name** (`OrderD.xml` → `"OrderD.selectOrderList"`), statement type from the first SQL word after leading comments (the wrapping tag is not the type), Velocity directives (`#if(…)`/`#elseif(…)`/`#else`/`#end`) stripped with paren/quote-aware scanning while every branch's SQL is kept — same policy as mapper condition tags. Java calls them through a holder object, `new QueryProperty("File.id")`, so `MyBatisPlugin` also reads `CREATE` references whose type is in `NAME_HOLDERS` (the creating method gets the `EXECUTES_SQL`). When one statement name exists in several files, **the one under the caller's source root wins** (`statementOf`): an exploded WAR carries the same SQL file in `WEB-INF/src` and, older, in `WEB-INF/classes` (55 files there, all different) — without that rule 474 calls pointed at the stale copy. Measured on HI-Japan: 2,128 statements, 1,642 `EXECUTES_SQL` + 27 unresolved = the 1,669 literal `QueryProperty` creations, 4,589 table relations over 232 tables (parser 1,943 statements / regex 183), and the chain screen → `perform…` → service → DAO → SQL → table now walks both ways (table `JC_OUTSTDNG` → 15 screens). **Layers and transaction endpoints** (same day): that project has no annotations and one-letter class suffixes (`…M`/`…S`/`…D`), so layers come from **configured supertypes**, not names — `semantic.ConfiguredLayerPlugin` (800, MEDIUM, direct `EXTENDS`/`IMPLEMENTS` only, external FQN or in-project fqn, never overrides an earlier layer) reads `dstone.knowledge.semantic.layer.super-types: "superTypeFqn=LAYER,…"` (shipped with the JEF rules: `AbstractMainService=CONTROLLER` because it is what receives the screen's request, `AbstractSubService=SERVICE`, `JdbcDAO`/`JdbcRowGetter=REPOSITORY`, `BusinessVO=MODEL`); unlayered top-level types went 1,233 → 24. `RichClientPlugin` also inserts an endpoint of the new type **`TRANSACTION`** (`path` = the ID) for every public non-static method matching a call rule's template — only for rules the project's screens actually use and only when the template has ≥3 fixed characters (`{id}` alone would match everything); 644 on HI-Japan, so table impact now reports endpoints (24 for `JC_OUTSTDNG`) and METHOD documents carry `진입점: 거래 ID …`. A new endpoint type or layer rule changes TYPE/METHOD document text, i.e. re-embeds those chunks. Port 4081 on this box may be the user's Windows-side instance sharing the same PostgreSQL — booting a second instance runs `AnalysisJobRecovery` (fails any running job) and a second `EmbeddingWorker`, so check for active jobs first and start test instances on another port with `-Ddstone.knowledge.rag.embedding.enabled=false`.

Search / impact / documents / Tool (M6, 2026-10-05):

- **Hybrid search** (`SearchService`): vector hits and name hits are fused by rank (`rag.HybridRanker`, Reciprocal Rank Fusion, k=60). `rag.SearchKeywords` picks only ASCII identifier-looking tokens from the query (≥3 chars, max 8; `a.b#c` split at `.`/`#`, anything containing `/` kept whole) — no Korean words, vector search covers meaning. Name score per token in `RagDao.xml` `searchChunksByKeyword`: 3 = whole word in the document title, 2 = in the title, 1 = in the content only; ties are ordered by vector similarity, which is what keeps a ubiquitous token like `SQL` harmless. A title-exact hit (score ≥ 3) counts double in the fusion so the method you named beats a merely similar one even when it has no embedding yet. Name search needs no vector: it works before embedding finishes and, when the embedding server is down, a query with names falls back to name-only with a `warning` (no names → 503). Request adds `mode` (`HYBRID`/`VECTOR`/`KEYWORD`) and `sourceTypes` (`CODE`/`DOCUMENT`). The name query scans the revision's chunks with `strpos` (0.17 s on ~10k chunks) — add a `pg_trgm` index before chunk counts reach hundreds of thousands. **Search must not queue behind the background embedding** (2026-10-06): Ollama serves one request at a time, so the 0.1 s query embedding waited for the worker's in-flight batch — with 3,500-char chunks on this CPU-only box (no usable GPU: AMD Radeon 780M, `size_vram: 0`) a batch of 16 took 66.8 s (4 → 16.5 s, i.e. ~4 s per chunk, batching gains nothing on CPU), searches took 59–100 s while 2,400 chunks were pending, and `dstone-ai-engine`'s RAG hit its 60 s timeout and failed a `pilot-workflow` run. Two rules keep it at 1–2 s under the same backlog: `rag.EmbeddingGate` (`SearchService` marks `searchStarted()/searchFinished()` around the query embedding; `EmbeddingWorker` calls `awaitOpen()` before every batch and stays out for 1.5 s after a search) and `dstone.knowledge.rag.embedding.batch-size: 1` (raise to 8–32 only on a GPU server). Any new code that calls `EmbeddingModel` for an interactive request must go through the gate the same way. Queue-wide progress is `GET /api/system/embedding` (`EmbeddingStatusService`: totals, recent speed, `etaSeconds`, worker state, pending per project) shown as the "임베딩 현황" panel at the top of `knowledge/index` (`knowledge/assets/js/embedding.js`, refreshed every 10 s); the ETA is computed from **characters, not item counts** (embedding time is proportional to length: 500 chars ≈ 0.6 s, 3,500 chars ≈ 4 s) over the last 10 minutes. While a module runs from `target/*.jar|war`, do not rebuild it in place (`mvn clean package` replaces the file under the running JVM and can crash it on the next class load) — copy the artifact elsewhere and run the copy on another port for tests.
- **Impact analysis** (`ImpactService`, `GET /api/revisions/{id}/impact?table=|statement=|type=|methodId=`): one recursive CTE (`RelationDao.xml` `impactWalk`) starts from the methods that touch the target (depth 0) and walks up `CALLS`/`CALLS_POSSIBLE_IMPLEMENTATION`/`REQUESTS` (depth ≤ 10), carrying the weakest confidence along the path (best path wins per node); three queries reuse it for methods, endpoints and screens (`via` = `REQUESTS`/`CALLS`/`RENDERS`). An endpoint linked to a type only (Struts `DispatchAction`) is included as `LOW`, `matchedBy = TYPE`. `INCLUDES` is deliberately not followed (a shared header would drag in every page). It only follows stored relations — SQL written as Java strings (raw JDBC, e.g. `legacy-app`) has no table relation, so a table target finds nothing there.
- **General documents** (`UploadDocumentService`, `/api/documents`, multipart): Tika text (`rag.DocumentTextExtractor`, char cap `rag.upload.max-chars`) → `rag.TextChunker` (paragraph packing up to `rag.chunk-max-chars`, short last paragraph repeated as overlap; `.jsonl` = one line per chunk) → `rag_document` (`source_type=DOCUMENT`, `doc_type=UPLOAD`, `document_id` = `sourceId`, no revision) / `rag_chunk` → `rag_embedding` with `priority` 10 (code is 0; the worker takes higher priority first so an upload does not wait hours behind a project backlog — 45 s seen with 15k chunks pending). Same `(tenant, sourceId)` replaces; a file with no extractable text is a 400 and leaves the existing document untouched. Tika needs the `commons-io` 2.20.0 override in this module's pom, same as `dstone-ai-engine`. Tenant = caller from the API key; with auth off the tenant is null and such documents are shared.
- **`rerunFrom`** on `POST /api/projects/{id}/analyses` (`{revisionLabel, rerunFrom: "DOCUMENT"}`) resets that pass and every later one (`analysis_revision_pass` + `analysis_file_pass` rows) on an existing revision — use it after changing document or semantic rules instead of editing pass rows by hand.
- `dstone-ai-engine`'s embed/RAG now runs on this module (2026-10-06, see the RAG paragraph in the `dstone-ai-engine` section); the only change on this side is `documentId` in search hits (for an upload it is the `sourceId`). `dstone-ai-engine/k8s/configmap.yaml` is an old minimal `application.yml` — it carries no datasource, no Tool settings and no RAG settings, so `spring.datasource`, `dstone.ai.tool.knowledge`, `dstone.ai.rag` and `KNOWLEDGE_HOST` must be added there before the Pod can use workflow history, the Tool or RAG (everything was verified with a local `bin/startApp.sh` process only).

Incremental analysis / revision diff / retention (M7, 2026-10-05):

- **A revision is still a full snapshot.** `{incremental: true}` (optional `baseRevisionId`, default = latest `READY` revision; stored in `analysis_revision.parent_revision_id`) only shortens how it is built: results of unchanged files are **copied** from the base revision, so a base revision can be deleted later without hurting its children. Falls back to a full run (response `incremental: false` + `note`) when there is no `READY` base or the base's `analyzer_version` differs.
- `CarryPass` (CARRY): same file = same path + `checksum` + SCAN classification (language, file type, module, encoding) → `analysis_file.carried_from_file_id`. For files whose base DECLARE/RESOURCE status was `DONE` it copies the per-file rows (symbol/method/field/annotation/reference, mapper/config/resource) and inserts `analysis_file_pass` rows with `carried = true`, which is what makes DECLARE/RESOURCE skip them. Base `FAILED`/`SKIPPED` files are simply reprocessed.
- `CarryResolvePass` (CARRY_RESOLVE) runs after DECLARE because resolved relations depend on other files. An unchanged file is re-resolved (not carried) when (1) any of its base relations points to a declaration in a changed/removed file, or (2) one of its base references with status `EXTERNAL`/`HEURISTIC`/`UNRESOLVED` has the name of a declaration in a new/changed file. Everything else gets its RESOLVE relations copied. It deliberately errs towards re-resolving. LINK/SEMANTIC/DOCUMENT always rebuild the whole revision (their relation types are excluded from the copy).
- The copy SQL reads column names from `information_schema` (`CarryDao.copyRows`) so a newly added column cannot be silently dropped; table names come from Java constants only. **`ANALYZE` after the bulk copy is required** — without it the planner picked a bad plan and LINK took 123 s instead of ~1 s.
- **The check that must keep passing when any pass changes:** analyze the same source once incrementally and once fully in the same project and compare every `analysis_*` table plus chunk hashes with ids replaced by paths/names — 0 differing rows on all 13 tables in two rounds on a copy of `anybiz_prd` (rename a DAO method, delete a widely used VO, add a class, edit JSP/mapper, then revert; second round based on an incremental revision). Timings there: 215 s full → 80–102 s incremental (RESOLVE 131 s → 2.5–27 s); SEMANTIC (~35 s, mostly SQL parsing) and DOCUMENT (~30 s) are what is left.
- Not detected: changed target jars (run a full analysis). Not verified: multi-module projects, tens of thousands of files.
- **Revision diff** (`DiffService`, `GET /api/revisions/{id}/diff?base=&kinds=&limit=`): `FILE`/`TYPE`/`METHOD`/`ENDPOINT`/`STATEMENT`/`TABLE_USE`/`CALL` via one FULL JOIN pattern per kind in `DiffDao.xml`; symbol/method ids are revision-independent so they are the keys, files and statements are keyed by path/name. The statement key includes "is a fragment" because real mappers reuse one id for a `<select>` and a `<sql>`. Body-only method changes show up as `FILE` `CHANGED` only (no body hash is stored). Same project only.
- **Retention** (`RetentionService`): after every successful job, keep the newest `dstone.knowledge.retention.max-revisions` (5; 0 = keep all) `READY` revisions per project, never deleting a revision with an active job or one that a running incremental job is based on; unfinished (failed/cancelled) revisions are left alone. Embeddings no chunk refers to are deleted once older than `retention.orphan-embedding-days` (30). Manual: `POST /api/projects/{id}/retention?keep=`.

Node map (2026-10-06): a fifth screen, `knowledge/graph/graph` ("노드 맵"), draws the call structure with Cytoscape.js 3.34.3 — vendored at `dstone-boot` `webapp/knowledge/assets/lib/cytoscape.min.js` (no CDN, closed-network SI sites), page script `knowledge/assets/js/graph.js`. It adds nothing to the analysis: `api.service.GraphService` + `sqlmap/analysis/GraphDao.xml` only read `analysis_relation`. Three endpoints under `/api/revisions/{id}/graph`: (1) `GET /graph` — the whole map at **bundle level, never method level** (`anybiz_prd` has 15k methods): nodes are `TYPE` (nested/anonymous types folded into the outermost type, id = symbol id), `JSP` (`F`+file id, incl. its scriptlet Java), `MAPPER` (one mapper file, `M`+file id) and `TABLE` (`T:`+name); edges are method-level relations summed per node pair (`count`, strongest `confidence`), default relations = the call flow (`CALLS`, `CALLS_POSSIBLE_IMPLEMENTATION`, `EXECUTES_SQL`, `READS_TABLE`, `WRITES_TABLE`, `RENDERS`, `REQUESTS`), `relations=` can add `EXTENDS`/`IMPLEMENTS`/`INJECTS`/`INCLUDES`; (2) `GET /graph/neighborhood?id=&up=&down=` — the method-level tree around one node (bundle id, method id or `S`+mapper id; depth default 3, max 10, 3,000 edges per direction → `truncated`), node `level` 0 = picked, negative = callers, positive = callees; (3) `GET /graph/node?id=` — detail, whose `document` is the DOCUMENT-pass text from `rag_document` as is (nothing is generated; null for skipped accessors or revisions without DOCUMENT). Rules to keep: screen relations are followed **only on the first step** (`RENDERS` going up / `REQUESTS` going down only when the picked node is a JSP — following them mid-walk turns a call tree into page navigation and drags in the whole app); `MODEL`-layer methods are skipped unless `includeModel=true` and the MODEL chip is off by default on the screen (`BaseVO` alone has 245 incoming edges); the class-level highlight on the whole map over-approximates real call paths (A→B.x, B.y→C shows A→B→C), which is exactly why the tree popup exists. Package collapsing (auto when > 250 nodes), the tier-column layout (화면 → 컨트롤러 → 서비스 → DAO → SQL 매퍼 → 테이블), layer filters and highlighting are all client-side; the server only supplies each node's `group`. `KnowledgeProxyService` raises WebClient's 256KB buffer to 32MB for this (the `anybiz_prd` map is ~1MB and came back as a 502 before). Hang/cycle defenses (checked by `src/test/resources/samples/cycle-app`): call-graph CTEs are bounded by `depth` (≤5) with `UNION` dedup and return each edge at its shallowest depth; the ancestor CTE in LINK stops at depth 20 and drops `type = ancestor` rows (cyclic inheritance in non-compiling source would otherwise make methods override themselves); the symbol solver's `StackOverflowError` is caught per reference; a `StackOverflowError` while parsing/walking a file is turned into a per-file `TOO_DEEP` failure in `DeclarePass` and again in `FilePassRunner` — it is an `Error`, so without that catch it kills the job and every restart dies on the same file; RESOLVE has a per-file budget (`dstone.knowledge.resolve.file-timeout-seconds`, default 120 → remaining references become `UNRESOLVED` "시간 초과", error `RESOLVE_TIMEOUT`) and checks cancellation per reference. A library call that never returns is handled by `job.FileWatchdog`: `FileHandler<T>` is split into `prepare` (read/parse/resolve, **no DB writes, no transaction**, runs on a watched worker thread) and `write` (one batch transaction on the job thread); if `prepare` exceeds `dstone.knowledge.job.file-hard-timeout-seconds` (600) the file is marked `FAILED`/`HUNG`, the worker thread is abandoned (Java cannot kill it — it may keep a core busy until restart), `FileHandler.reset()` rebuilds everything that thread was touching (RESOLVE's whole solver/resolver "engine"), and after more than `job.max-stuck-files` (3) abandons the job fails so zombie threads don't pile up. Keep heavy work in `prepare` and DB writes in `write` in any new per-file pass — that split is what lets an abandoned thread hold no connection or lock. Consequently `SymbolDao` (read by `prepare`) uses `sqlSessionCommon`; only `...InBatch` DAO methods run inside the write transaction.

DB access: single `dataSourceCommon` (`spring.datasource.common.hikari.*`, PostgreSQL `dstone_knowledge`), MyBatis `sqlSessionCommon` + `sqlSessionBatch` (`ExecutorType.BATCH`, for bulk writes inside a transaction), and a programmatic `txTemplateCommon` instead of the name-based AOP transactions other modules use (analysis runs for hours and commits every N files). Schema is manual (`src/main/resources/schema/01-init…sql` as postgres superuser, `02-create-table…sql` as the app role; idempotent). Unit tests run with `mvn -pl dstone-knowledge test` (surefire is pinned to 3.5.2 in this module's pom; Maven's default 2.17 can't run JUnit 5). `spring-boot-starter-test` carries a `spring-boot-starter-logging` exclusion — without it logback lands in the runnable jar and boot dies with `log4j-slf4j2-impl cannot be present with log4j-to-slf4j`. `src/test/resources/samples/legacy-app` is a deliberately EUC-KR, Java-1.4-syntax sample (do not re-save as UTF-8); its README holds the expected counts.

## Cloud Architecture Simulation

The WSL dev environment mirrors a cloud deployment shape: `dstone-boot` and `dstone-ai-engine` run as containerized Pods in a local `kind` Kubernetes cluster (`<module>/Dockerfile`, `<module>/k8s/`), while `dstone-batch`, `dstone-batchadmin` and `dstone-knowledge` run as VM-style processes controlled by plain shell scripts (`bin/startApp.sh`/`stopApp.sh`/`statusApp.sh` — **no systemd**). Since 2026-10-06 the `dstone-knowledge` and `dstone-ai-engine` scripts follow `dstone-boot/bin` (plus `.bat` twins for Windows, profile `local`): stdout goes to `/dev/null`, so **logs exist only where `conf/log4j2.xml` puts them** (`${APP_HOME}/LOGS/<module>/execution/execution.log` — no more `logs/<module>.out`), and the PID file `bin/application.pid` is written by the app itself (`ApplicationPidFileWriter`), not by the script; they differ from boot's only in `cd`-ing to `bin` first, honouring `DSTONE_PROFILE`, and `stopApp.sh` waiting up to 30 s for the process to exit. A crash before log4j2 starts leaves no trace — run the commented-out foreground line at the end of `startApp.sh` to see it, and MySQL/Redis/RabbitMQ/Kafka stand in for CSP-managed services outside the cluster. `dstone-ai-engine`'s manifests (`dstone-ai-engine/k8s/`) and Dockerfile follow `dstone-boot`'s pattern exactly (same namespace `dstone`, same `localhost:5000` local registry) — see `docs/04.cloud-architecture.md` for the full mapping, networking, and CI/CD design.

## CI/CD

Jenkins pipelines are defined in:
- `dstone-boot/Jenkinsfile`, `dstone-ai-engine/Jenkinsfile` — Maven reactor build → Docker build/push to a local registry (`localhost:5000`) → deploy to the `dstone` namespace in `kind` via `kubectl`
- `dstone-batch/Jenkinsfile`, `dstone-batchadmin/Jenkinsfile`, `dstone-knowledge/Jenkinsfile` — Maven reactor build → copy artifact/conf/bin to `/app/dstone/<module>` (the module's own directory in this same repo — no separate deploy tree) → redeploy via that module's `bin/stopApp.sh` + `bin/startApp.sh` (`DSTONE_PROFILE=vm`)

Jenkins Job SCM checkout must be the full monorepo root (not a per-module sparse checkout) since builds use `mvn -pl <module> -am` reactor builds and the Docker build context needs `dstone-common` alongside `dstone-boot`.
