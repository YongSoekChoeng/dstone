## 답변

`dstone-ai-engine`의 Workflow `inputs`는 **실행 요청이 반드시 지켜야 하는 입력 조건(입력 계약)**입니다. Workflow를 실행하기 전에 요청을 검사하고, 엔진 기동 시에는 YAML 안의 참조가 올바른지도 확인합니다.

---

## 1. 기본 모양

```yaml
workflow:
  id: my-workflow
  inputs:                       # 선택 항목. Map<String, FieldDefinition>
    sqlList: list<string>       # 축약형: 타입만 적음
    targetVersion:              # 확장형: 타입과 설명을 함께 적음
      type: string
      description: PostgreSQL 버전
  steps: ...
```

- `WorkFlowDefinition.inputs`: `Map<String, FieldDefinition>` (`common/definition/WorkFlowDefinition.java`)
- `FieldDefinition(type, description)`: 두 개의 `@JsonCreator`가 있어서 축약형과 확장형을 모두 받습니다 (`common/definition/FieldDefinition.java`)
  - `sql: string`: 문자열 하나로 받음(DELEGATING) → `description = null`
  - `sql: {type:…, description:…}`: 맵으로 받음(PROPERTIES)
- `inputs`에서는 `description`이 **설명용일 뿐입니다**. 검사에 쓰이지 않고 LLM에도 전달되지 않습니다. 같은 `FieldDefinition`이라도 `output.schema`에서 쓸 때는 JSON Schema에 들어가 LLM에 전달됩니다.

## 2. 쓸 수 있는 타입 (`common/schema/FieldTypes.java`)

| 타입 | 통과하는 값 (Jackson으로 역직렬화된 뒤의 Java 타입) | 통과하지 못하는 예 |
|---|---|---|
| `string` | `String` | `123`, `true` |
| `number` | 모든 `Number` (정수와 실수 모두) | `"3.5"` (문자열) |
| `integer` | `Integer` / `Long` / `BigInteger` | `3.0` (Double이 되므로 실패), `"3"` |
| `boolean` | `Boolean` | `"true"`, `1` |
| `object` | `Map` (JSON 객체) | 배열, 문자열 |
| `list<T>` | `List`이면서 **모든 항목**이 T에 맞아야 함 | 항목 하나라도 타입이 다르면 실패 |

- 중첩도 됩니다: `list<list<integer>>`, `list<object>`
- **빈 리스트 `[]`는 통과합니다.** 검사할 항목이 없기 때문입니다.
- 타입 이름은 **대소문자를 구분합니다**. `String`, `str`, `list<str>`, `array`는 모두 잘못된 타입입니다.
- `object`는 안쪽 구조를 검사하지 않습니다. 맵이기만 하면 통과합니다.

## 3. 검사 시점 두 가지

### (A) 엔진 기동 시: `WorkFlowRegistry`
1. **타입 이름 검사**: `FieldTypes.invalidFields()`로 확인하고, 잘못된 것이 있으면 **기동에 실패합니다**.
   - `x: list<str>` → `inputs의 타입 이름이 올바르지 않습니다: [x(list<str>)]`
   - `x:`처럼 값을 비워 둔 경우 → `x(null)`로 잡혀서 역시 기동에 실패합니다.
2. **`{{input.xxx}}` 참조 검사** (`WorkFlowRegistry.java:229`): `inputs`가 **비어 있지 않을 때만** 검사합니다.
   - `input.message`는 선언하지 않아도 항상 허용됩니다.
   - `input.<이름>`은 `inputs`에 선언된 이름이어야 합니다. 아니면 기동에 실패합니다.
   - 두 번째 부분(이름)만 검사하므로 `{{input.sqlList.0}}`처럼 더 깊은 경로는 기동 시에 통과합니다.

### (B) 실행 요청 시: `WorkFlowExecutionService.checkInputs()`
`/execute`(동기)와 `/submit`(비동기) 모두에서 **실행 전에** 호출됩니다 (`WorkFlowController.java:101, 127`).
- 선언된 이름마다 `request.variables[이름]`을 확인합니다.
  - 값이 없거나 `null`이면 → `이름(없음)`
  - 타입이 맞지 않으면 → `이름(list<string> 타입이어야 함)`
- 문제를 **전부 모아서** 한 번에 `IllegalArgumentException`을 던지고, 컨트롤러가 이를 **HTTP 400**으로 바꿉니다.
  ```
  workflow[sample-foreach-parallel]의 inputs 계약을 지키지 않았습니다: [sqlList(없음)]
  ```
- `inputs`에 **선언하지 않은 추가 값은 허용됩니다**. 그대로 `input.*` 아래에 들어갑니다.
- `message` 자체의 필수 여부는 `inputs`와 따로 `validateMessage()`가 검사합니다. 비어 있으면 400입니다.

## 4. 요청 값이 실행 컨텍스트에 들어가는 방식

```json
POST /api/ai/workflow/{id}/execute
{ "message": "...", "sessionId": "...", "variables": { "sqlList": ["SELECT 1 FROM dual"] } }
```
`WorkFlowContext.create(message, variables)`가 다음과 같이 만듭니다.
```
input:
  sqlList: [...]        ← variables를 그대로 복사
  message: "..."        ← 요청의 message (항상 들어감)
previous:
  text: "..."           ← 첫 step이 {{previous.text}}로 message를 받을 수 있게 넣어 둠
```
이렇게 들어간 값은 두 곳에서 씁니다.
- step의 `input`, `forEach`, Workflow `output` 템플릿: `{{input.sqlList}}`, `forEach: input.sqlList`
- Agent의 system prompt: `{sqlList}`, `{message}`. `StepInput.workflowInput`을 통해 `AgentExecutor`의 프롬프트 변수로 전달됩니다.

템플릿 값 전체가 `{{input.x}}` 하나뿐이면 **원래 타입이 유지됩니다**. 그래서 TOOL 인자에 리스트나 숫자를 그대로 넘길 수 있습니다.

## 5. 경우별 정리

| 경우 | 결과 |
|---|---|
| `inputs` 생략 또는 `{}` | 요청 검사 없음. `{{input.아무이름}}`도 기동 시 검사하지 않음. 실행 중 값이 없으면 **그 step이 실패**하고 `onFailure`를 따름. 필요하면 `??`로 대체값을 줄 수 있음 |
| `inputs` 선언, 요청이 조건을 지킴 | 정상 실행 |
| 선언한 값이 `variables`에 없거나 `null` | 400 `이름(없음)` |
| 타입이 다름 (예: `sqlList: "SELECT 1"`) | 400 `sqlList(list<string> 타입이어야 함)` |
| 리스트 항목 하나만 타입이 다름 (`["a", 1]`) | 400 |
| 선언하지 않은 값이 더 들어옴 | 허용. `{{input.extra}}`는 `inputs`가 선언되어 있으면 **기동 시 오류**라서 템플릿에서는 쓸 수 없음. system prompt의 `{extra}`로는 쓸 수 있음 |
| `inputs`에 `message`를 선언 | 코드는 허용하며, `variables`가 아니라 요청의 `message`로 검사함. message는 항상 문자열이라 `string`이 아니면 **모든 요청이 400**이 됨. 문서 권장대로 선언하지 않는 것이 맞음 |
| `variables`에 `message` 키를 넣음 | 요청의 `message`가 **덮어씀** (`input.put(MESSAGE, …)`이 나중에 실행됨) |
| 잘못된 타입 이름 또는 빈 값 | 엔진 **기동 실패** |

## 6. 실제 샘플

현재 `inputs`를 쓰는 Workflow는 `resources/workflows/sample/sample-foreach-parallel.yml` 하나입니다.
```yaml
inputs:
  sqlList: list<string>
steps:
  - id: validate-each
    type: TOOL
    ref: validateSqlSyntax
    forEach: input.sqlList      # 항목 수만큼 병렬로 실행
    input:
      sql: "{{item}}"
```
호출 예: `variables: {"sqlList": ["SELECT 1 FROM dual", "SELEC 1 FROM dual"]}`. `sqlList`가 없거나 리스트가 아니면 실행 전에 400으로 거절됩니다.
