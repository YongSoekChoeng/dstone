## 답변

네, 개념과 구조는 잘 알고 있습니다. 다만 두 제품 모두 상용 솔루션이라 공개 자료가 적습니다. 그래서 버전별 세부 API나 사내에서 따로 만든 공통 라이브러리 동작은 실제 코드를 보고 확인해야 정확합니다.

**넥사크로 (Nexacro, 투비소프트)**
- 화면은 `.xfdl`(XML) 파일에 Form, 컴포넌트, Dataset을 선언하고, 스크립트는 그 안의 `<Script>` 블록이나 `.xjs`에 둡니다.
- 서버와는 `this.transaction(svcId, url, inDatasets, outDatasets, args, callback)`으로 통신합니다. 이때 Dataset을 SSV나 XML 형식으로 주고받습니다.
- 화면은 `this.go()`, `popupdiv`, `ChildFrame`/`showModal`, `gfn_*` 같은 공통 함수로 엽니다. 서비스 URL은 `TypeDefinition.xml`의 prefix(예: `svc::`)로 풀어냅니다.
- 컴포넌트는 `Grid`·`Combo`·`Edit` 등을 쓰고, `BindItem`으로 Dataset 컬럼과 연결합니다.

**웹스퀘어 (WebSquare, 인스웨이브)**
- 화면은 XHTML 기반 `.xml` 파일입니다. `w2:` 네임스페이스 컴포넌트를 쓰고, 데이터는 `w2:dataCollection` 안의 `dataList`/`dataMap`에 둡니다.
- 서버 호출은 `xf:submission`(`ref`, `target`, `action`)을 선언한 뒤 `$p.executeSubmission()`이나 `com.sbm.execute` 같은 공통 래퍼로 실행합니다.
- 화면은 `$p.openPopup`, `wfm_*`(WFrame), `$p.url`, 공통 `com.win.openPopup` 등으로 엽니다. 스크립트는 `<script>` 블록이나 `scwin.*` 함수에 있습니다.
- 바인딩은 `ref="data:dlt_xxx.col"` 형식을 씁니다.

**이 저장소에서는**
`dstone-knowledge`가 이미 두 형식의 화면을 분석합니다. 화면, 서버 호출(TRANSACTION 엔드포인트), 화면 오픈 관계, 필드 바인딩, 공통 스크립트를 추출해서 Knowledge Graph에 연결하는 방식입니다. 관련 규칙과 설계는 `.claude/docs/knowledge-screens-rich-client.md`와 `dstone-knowledge/conf/rules/*.yml`에 있습니다. 프로젝트마다 쓰는 공통 함수 이름이 달라서, 그런 차이는 규칙 파일로 맞추도록 되어 있습니다.

넥사크로나 웹스퀘어로 하실 작업(분석 규칙 추가, 특정 화면 해석, 코드 작성 등)이 있으면 말씀해 주세요. 관련 파일을 열어 보고 진행하겠습니다.

## 답변

네, 할 수 있습니다. 다만 잘하는 일과 한계가 분명히 나뉩니다.

## 가능한 이유

두 제품 모두 화면 소스가 텍스트 파일입니다.

- 넥사크로: `.xfdl`(XML), `.xjs`(스크립트), `TypeDefinition.xml`, `.xadl`
- 웹스퀘어: 화면 `.xml`(XHTML), 공통 `.js`

Claude Code는 이 파일들을 읽고 고치고 새로 만들 수 있습니다. 화면 뒤의 서버 쪽(Spring Controller, Service, MyBatis SQL)은 원래 잘하는 영역입니다. 그래서 화면에서 DB까지 한 기능을 통째로 개발할 수 있습니다.

## 잘하는 일

- 기존 화면을 본보기로 비슷한 화면 만들기 (조회, 저장, 팝업)
- Dataset/dataList 정의, `transaction`/`submission` 호출, 콜백 처리
- 그리드 컬럼 추가, 바인딩 수정, 유효성 검사 스크립트 작성
- 화면 ID와 서비스 URL, 서버 Controller, SQL의 연결 관계를 따라가며 수정
- 공통 함수(`gfn_*`, `com.*`) 사용법을 기존 코드에서 익혀서 똑같이 쓰기
- 대량 일괄 수정 (예: 특정 공통 함수 호출 방식을 전체 화면에서 바꾸기)

## 한계

1. **눈으로 확인하기 어렵습니다.** 넥사크로 화면 배치는 `left/top/width/height` 좌표라서 파일은 고칠 수 있지만, 실제로 보기 좋게 놓였는지는 제가 직접 볼 수 없습니다. 레이아웃은 Nexacro Studio나 WebSquare Studio에서 사람이 마무리하는 편이 낫습니다.
2. **실행 확인에 제약이 있습니다.** 웹스퀘어는 엔진이 배포된 서버만 있으면 브라우저로 띄워 볼 수 있습니다. 넥사크로는 런타임이나 생성된 JS, 라이선스가 필요해서 제 쪽에서 실행까지 확인하기는 어렵습니다.
3. **공개 자료가 적습니다.** 버전별 세부 API나 컴포넌트 속성은 틀릴 수 있습니다. 프로젝트의 기존 코드, 공통 라이브러리, 개발 가이드 문서를 주시면 정확도가 크게 올라갑니다.
4. **Studio와 함께 쓸 때 조심할 점이 있습니다.** Studio가 파일을 다시 저장하면서 서식을 바꿀 수 있습니다. 넥사크로의 generate 결과물은 직접 고치지 말고 원본(`.xfdl`)을 고친 뒤 다시 생성해야 합니다.

## 실무에서 권하는 방식

1. 프로젝트 `CLAUDE.md`에 화면 규칙을 적습니다. 파일 위치, 명명 규칙, 공통 함수, 서비스 URL 규칙 같은 것들입니다.
2. 표준 화면 2~3개를 "본보기"로 정해 두고, 새 화면은 그것을 따라 만들게 합니다.
3. 스크립트, 데이터, 서버 연동은 Claude Code가 맡고, 화면 배치와 실행 확인은 개발자가 Studio에서 합니다.
4. 영향도 분석에는 이 저장소의 `dstone-knowledge`를 쓸 수 있습니다. 이 화면을 고치면 어느 서버 로직과 테이블이 영향을 받는지 미리 볼 수 있습니다.

정리하면, 코드와 로직 개발은 Claude Code로 충분히 진행할 수 있고, 화면 디자인과 실행 검증은 Studio와 사람이 맡는 분업이 현실적입니다.

## 답변

방법은 크게 네 가지입니다. 핵심은 Claude가 화면을 **직접 보면서** 고칠 수 있게 하는 것입니다.

## 1. 실행 화면을 캡처해서 보여 주기 (가장 현실적)

Claude는 이미지를 읽을 수 있습니다. 그래서 "고치기 → 띄우기 → 캡처 → 보고 다시 고치기"를 반복하게 만들면 됩니다.

- **웹스퀘어**: 엔진이 배포된 WAS에 화면을 올리고 브라우저로 엽니다. Playwright 같은 브라우저 자동화 도구나 Claude in Chrome으로 스크린샷을 찍으면 Claude가 직접 확인할 수 있습니다.
- **넥사크로**: N/17 이후 버전은 HTML5(JS)로 generate할 수 있습니다. 명령줄 배포 도구(`nexacrodeploy` 계열)로 generate한 뒤 웹 서버에 올리면 웹스퀘어와 똑같이 브라우저로 캡처할 수 있습니다. 쓰시는 버전에 명령줄 generate가 있는지는 먼저 확인해야 합니다.

이 과정을 스크립트 하나로 묶어 두면 Claude가 알아서 반복합니다.

## 2. 그림을 주고 화면으로 바꾸게 하기

화면설계서, 손그림, 기존 화면 캡처를 이미지로 주면 Claude가 그 배치를 `.xfdl`/`.xml`로 옮깁니다. 1번과 함께 쓰면 "설계 이미지와 실행 캡처를 비교해서 다른 곳 고치기"까지 할 수 있습니다. 실무 효과가 가장 큰 조합입니다.

## 3. 좌표 대신 레이아웃 명세로 작업하기

좌표(`left/top/width/height`)를 직접 고치면 실수가 잦습니다. 그래서 중간 형식을 하나 둡니다.

```yaml
# 예: 조회 화면 명세
search:
  - row: [{label: 사원명, comp: Edit, bind: EMP_NM}, {label: 부서, comp: Combo, bind: DEPT_CD}]
grid:
  dataset: ds_list
  columns: [EMP_NO:사번:80, EMP_NM:이름:120, DEPT_NM:부서:150]
buttons: [조회, 저장, 엑셀]
```

이 명세를 표준 템플릿 규칙에 맞는 좌표나 화면 XML로 바꿔 주는 작은 변환기(Java)를 만듭니다. 그러면 Claude는 명세만 고치고, 간격과 정렬은 변환기가 항상 똑같이 맞춥니다. 화면 표준을 지키기에도 유리합니다.

## 4. Studio를 직접 조작하게 하기

Claude 데스크톱 앱의 computer use를 쓰면 Claude가 Windows 화면을 보면서 Studio를 마우스와 키보드로 조작할 수 있습니다. 말 그대로 "Studio에서 그리기"입니다. 다만 느리고 정밀한 배치에서 실수가 생길 수 있어서, 마무리 확인이나 보조 용도로 쓰는 편이 맞습니다.

## 추천 조합

**2번 + 1번**을 기본으로 하고, 화면 수가 많으면 **3번**을 더합니다.

1. 설계 이미지나 기존 화면을 본보기로 줍니다.
2. Claude가 화면 파일을 생성합니다.
3. 스크립트가 generate·배포·캡처를 자동으로 돌립니다.
4. Claude가 캡처를 보고 차이를 고칩니다.
5. 마지막 미세 조정은 개발자가 Studio에서 합니다.

이 환경(WSL)에서 시작하려면 먼저 1번 루프부터 만들면 됩니다. 웹스퀘어 엔진이나 넥사크로 generate 결과물이 있으면 dstone-boot나 별도 웹 서버에 올려서 캡처까지 이어지는 스크립트를 만들어 드릴 수 있습니다. 어느 제품, 어느 버전으로 진행하실지 알려 주세요.

## 질문

그런데 ai모델을 qwen3.8-27b 를 사용한다고 할 경우에도 가능할까?

---

## 답변

가능은 합니다. 다만 Claude로 할 때와 같은 수준을 기대하기는 어렵고, 방식을 조금 바꿔야 합니다. 먼저 밝혀 둘 점이 있습니다. "Qwen3.8-27B"라는 모델의 정확한 성능은 제가 확인할 수 없습니다. 아래 내용은 27B급 공개 모델을 기준으로 한 일반적인 판단입니다.

## 1. 도구 문제: Claude Code와의 궁합

Claude Code는 Claude 모델에 맞춰 만든 도구입니다. LiteLLM 같은 프록시로 `ANTHROPIC_BASE_URL`을 바꾸면 다른 모델을 붙일 수는 있습니다. 하지만 공식 지원이 아니고, 도구 호출 형식이 어긋나거나 긴 작업 중간에 흐름을 놓치는 일이 잦습니다. Qwen을 쓴다면 Qwen Code, OpenCode, Cline, Aider처럼 여러 모델을 지원하는 에이전트 도구가 더 자연스럽습니다.

## 2. 모델 능력: 무엇이 되고 무엇이 어려운가

| 작업 | 27B급 모델 |
|---|---|
| 본보기 화면을 따라 비슷한 화면 만들기 | 대체로 됨 |
| Dataset, 바인딩, transaction 스크립트 작성 | 본보기가 있으면 됨 |
| 서버(Controller/SQL) 일반 코드 | 됨 |
| 넥사크로/웹스퀘어 고유 API 정확히 쓰기 | 학습 자료가 적어서 자주 틀림 |
| 여러 파일을 오가는 긴 작업 | 중간에 흐름을 놓치기 쉬움 |
| 좌표 계산과 배치 | 약함 |

## 3. 이미지 확인: 비전 모델인지가 관건

앞에서 말한 1번(캡처 보고 고치기)과 2번(설계 이미지를 화면으로)은 이미지를 읽는 모델이 있어야 합니다. 텍스트 전용 모델이면 이 두 방법은 쓸 수 없고, 비전(VL) 버전을 따로 써야 합니다. 작은 비전 모델은 화면 캡처에서 몇 픽셀 어긋난 것까지 잡아내기 어렵습니다.

## 그래서 작은 모델일수록 3번 방식이 맞습니다

모델이 판단할 일을 줄이고, 정해진 결과는 프로그램이 만들게 하는 방식입니다.

1. **레이아웃 명세 + 변환기**: 모델은 짧은 YAML 명세만 쓰고, 좌표와 화면 XML은 Java 변환기가 만듭니다. 모델이 약한 좌표 계산을 아예 맡기지 않는 것입니다.
2. **검증 스크립트**: XML 형식, Dataset 컬럼과 바인딩 일치, 서비스 URL 존재 여부를 자동으로 검사합니다. 오류 메시지를 모델에게 돌려주면 작은 모델도 스스로 고칠 수 있습니다.
3. **본보기와 규칙 문서**: 표준 화면 몇 개와 공통 함수 사용법을 프롬프트에 꼭 넣습니다.
4. **작업을 잘게 나누기**: "화면 하나 통째로"가 아니라 "명세 작성 → 변환 → 스크립트 작성 → 검증"처럼 나눠서 시킵니다.

이 저장소의 `dstone-ai-engine`이 바로 이 구조에 맞습니다. Workflow의 순서와 분기는 Java가 정하고 각 Step 안의 판단만 LLM이 하는 방식이라, 작은 모델로도 안정적으로 돌리기 좋습니다. Agent마다 provider를 따로 지정할 수 있어서 Ollama의 Qwen을 붙이는 것도 가능합니다.

## 현실적인 조합

- **어려운 일**(화면 표준 설계, 변환기 개발, 본보기 화면 작성)은 Claude로 합니다.
- **반복되는 일**(같은 유형 화면 수십 개 생성, 일괄 수정)은 Qwen + 변환기 + 검증 스크립트로 처리합니다.

보안 문제로 외부 모델을 쓸 수 없는 환경이라면 Qwen 단독 구성도 가능합니다. 그럴수록 변환기와 검증 스크립트를 탄탄하게 만들어 두는 것이 성패를 가릅니다. 원하시면 넥사크로나 웹스퀘어용 레이아웃 명세 형식과 변환기 설계부터 잡아 드리겠습니다.

- `dstone-knowledge` 테스트 자료에 넥사크로 샘플 앱(`nexacro-app/nxui/order/*.xfdl`)이 있고, `/app/hen`에도 `.xfdl` 파일이 있습니다.
- 넥사크로/웹스퀘어 화면 분석과 규칙 파일(`conf/rules/common`, `projects`)도 이미 있습니다.

# 계획: 폐쇄망에서 로컬 Qwen으로 넥사크로/웹스퀘어 화면 개발

## 기본 원칙
- 모델에게는 **짧은 명세만** 쓰게 하고, 화면 파일은 **프로그램이 생성**합니다.
- 모델이 낸 결과는 **항상 자동 검증**하고, 오류를 모델에게 돌려줘 스스로 고치게 합니다.
- 순서와 분기는 **Java(Workflow)가 제어**하고, 모델은 각 단계 안의 판단만 맡습니다.

## 0단계: 사전 확인 (결정할 것)
1. 대상 제품과 버전 (넥사크로 N/17/24, 웹스퀘어 5 등). 처음에는 하나만 고릅니다.
2. 실제 프로젝트의 표준 화면 유형 (조회 목록, 상세·저장, 팝업, 마스터-디테일 등)
3. 공통 라이브러리 (`gfn_*`, `com.*`)와 개발 가이드 문서가 있는지
4. 서버 사양: GPU 메모리, 모델이 텍스트 전용인지 비전(VL)도 쓸 수 있는지
5. 실행 환경: 넥사크로 명령줄 generate 가능 여부, 웹스퀘어 엔진을 띄울 WAS가 있는지

## 1단계: 화면 표준과 본보기 정리
- 화면 유형별로 본보기 화면을 2~3개 정합니다(실제 프로젝트 화면이나 샘플 앱).
- 명명 규칙, 영역 배치(검색 영역, 버튼 줄, 그리드), 간격, 공통 함수 사용법을 문서로 정리합니다.
- 결과물: 화면 표준 문서와 본보기 세트

## 2단계: 레이아웃 명세 형식 설계
- 화면 유형별 YAML 명세 형식을 정합니다(검색 조건, 그리드 컬럼, 버튼, Dataset, 서비스 호출, 팝업 오픈).
- 좌표는 넣지 않고 "몇째 줄, 몇째 칸, 몇 칸 차지"만 적습니다.
- 작은 모델도 틀리지 않게 필드 수를 줄이고 기본값을 넉넉히 둡니다.

## 3단계: 변환기 개발 (명세 → 화면 파일)
- 넥사크로는 `.xfdl`, 웹스퀘어는 `.xml`을 만드는 Java 변환기입니다.
- 좌표 계산, 정렬, 컴포넌트 id 부여, Dataset 선언, 바인딩, 기본 스크립트 틀(조회·저장·콜백)을 자동으로 만듭니다.
- 업무 로직이 들어갈 자리만 비워 두고, 그 부분을 모델이 채웁니다.
- 거꾸로 기존 화면을 명세로 바꾸는 기능도 만들어 두면 기존 화면 수정과 학습 자료 준비에 쓸 수 있습니다.

## 4단계: 검증기 개발
- XML 형식 검사
- Dataset 컬럼과 바인딩, 그리드 컬럼의 일치 여부
- `transaction`/`submission`의 서비스 URL이 실제 서버 Controller에 있는지(여기에 `dstone-knowledge` 분석 결과 활용)
- 공통 함수 이름과 인자 수 검사
- 오류는 모델이 이해하기 쉬운 짧은 문장으로 돌려줍니다.

## 5단계: 생성 Workflow 구성 (`dstone-ai-engine`)
`dstone-ai-engine`에 Workflow 정의를 추가하고, 기존 범용 Tool을 우선 쓰고 필요하면 새 범용 Tool을 만듭니다(전용 Tool은 만들지 않음).

1. 요구사항 → 명세 작성 (Qwen)
2. 명세 검증 → 실패하면 1로 (Java)
3. 명세 → 화면 파일 변환 (Java)
4. 업무 스크립트 작성 (Qwen, 본보기와 공통 함수 문서 제공)
5. 화면 검증 → 실패하면 4로 (Java, 재시도 횟수 제한)
6. 서버 쪽 Controller/Service/SQL 초안 생성 (Qwen)
7. 사람 승인 대기 → 반영

## 6단계: 화면 확인 루프 (선택)
- 비전 모델을 쓸 수 있고 실행 환경이 있으면 generate → 배포 → 캡처 → 비교 단계를 붙입니다.
- 없으면 변환기가 만든 배치를 믿고, 마지막 확인만 Studio에서 사람이 합니다.

## 7단계: 시범 적용과 측정
- 화면 유형 하나(예: 조회 목록)로 10~20개를 만들어 봅니다.
- 측정할 것: 한 번에 통과하는 비율, 재시도 횟수, 사람이 고친 양, 걸린 시간
- 결과를 보고 명세 형식, 본보기, 프롬프트를 다듬은 뒤 다른 유형으로 넓힙니다.

## 위험 요소
- **고유 API 오류**: 모델이 넥사크로/웹스퀘어 API를 지어낼 수 있습니다. 공통 함수 목록과 검증기로 막습니다.
- **모델 성능 편차**: 27B를 양자화하면 품질이 떨어집니다. 명세를 단순하게 유지하고 작업을 잘게 나눠 대응합니다.
- **Studio와의 충돌**: 변환기 출력이 Studio에서 다시 저장해도 깨지지 않는지 초기에 확인해야 합니다.
- **표준이 없는 기존 화면**: 표준이 약한 프로젝트일수록 1단계에 시간이 더 듭니다.

## 진행 순서 제안
0단계 결정 → 1·2단계(문서와 명세 형식, 코드 없음) → 3·4단계(변환기·검증기) → 5단계(Workflow) → 7단계 시범 순서로 가고, 6단계는 환경이 갖춰지면 붙입니다.

0단계의 다섯 가지 중 먼저 **대상 제품과 버전**, **로컬 서버의 GPU와 비전 모델 사용 여부**를 알려 주시면 그에 맞춰 계획을 구체화하겠습니다. 작업은 지시하실 때 시작하겠습니다.

## 질문

dstone-knowledge 의 RAG 기능을 이용해서 일반 JSP기반 프로젝트 개발하듯이 할 수는 없을까?

---

## 답변

네, 가능합니다. 오히려 그쪽이 더 자연스러운 출발점입니다. 앞 계획의 변환기는 "모델이 화면을 처음부터 만든다"는 전제였습니다. 실제 JSP 프로젝트에서 개발자가 일하는 방식은 **비슷한 기존 화면을 찾아 복사하고, 연결된 서버 코드를 따라가며 고치는 것**이고, `dstone-knowledge`가 바로 그 "찾기와 따라가기"를 해 줍니다.

## dstone-knowledge가 이미 해 주는 것 (문서 확인)

| JSP 개발할 때 하던 일 | dstone-knowledge 기능 |
|---|---|
| 비슷한 화면 찾기 | 하이브리드 검색(벡터 + 이름), 화면명(`SCREEN_NAME`: 제목, 메뉴, 사전) |
| 화면 → 서버 호출 따라가기 | `REQUESTS`: `transaction` 주소, 거래 ID 규칙(`screens.calls`), 폼 필드 |
| 공통 함수 사용법 파악 | 공통 스크립트(`.js`/`.xjs`) 분석, prototype 함수(`this.gfn_*`)까지 연결 |
| 팝업, 하위 화면 관계 | `INCLUDES`: 화면 오픈 규칙(`screens.opens`), 공통 함수를 거쳐 여는 화면 |
| 서버 → SQL → 테이블 | `CALLS`, MyBatis 분석, 테이블 한글명 |
| 고칠 때 영향 범위 | 영향도 분석(테이블·SQL·메소드 → 화면까지 역추적) |
| 개발 가이드, 컴포넌트 매뉴얼 참고 | 일반 문서 업로드(Tika) → RAG 검색 |

`hen`(넥사크로)과 HI-Japan(웹스퀘어)에 실제로 돌려 본 기록도 있습니다. 그리고 `dstone-ai-engine`에는 이것을 부르는 `KnowledgeTool`과 RAG 연동이 이미 있습니다.

## 이렇게 바뀝니다

1. 요청: "사원 목록 조회 화면, 부서 콤보와 엑셀 버튼 포함"
2. 검색: 비슷한 기존 화면 2~3개를 찾습니다(화면명, 의미 검색).
3. 따라가기: 그 화면의 공통 함수, 호출하는 Controller/Service/SQL, 여는 팝업을 그래프로 모읍니다.
4. 생성: 모델이 본보기 화면을 **복사해서 필요한 부분만 고칩니다**(이름, Dataset 컬럼, 조회 조건, SQL).
5. 검증: XML 형식, 바인딩, 호출 주소 존재 여부를 검사합니다. 서버 쪽 확인은 knowledge 분석 결과로 합니다.
6. 사람이 검토하고 Studio에서 마무리합니다.

이 방식은 작은 모델에 특히 유리합니다. 모델이 넥사크로 API를 "아는" 대신, 그 프로젝트에서 실제로 동작하는 코드를 눈앞에 두고 따라 쓰기만 하면 되기 때문입니다. 고유 API를 지어내는 문제가 크게 줄어듭니다.

## 남는 한계

1. **넥사크로 좌표**: 본보기를 복사해서 고치는 방식이면 좌표 문제가 상당히 줄어듭니다. 그래도 컴포넌트를 새로 끼워 넣으면 위치 계산이 필요합니다. 웹스퀘어는 HTML/CSS 흐름 배치를 쓰는 화면이 많아 JSP와 거의 비슷하게 다룰 수 있습니다.
2. **청크와 문맥 크기**: 확인이 필요합니다. 화면 파일 본문이 RAG 청크로 들어가는지, `.xfdl`처럼 큰 파일이 청크 한도(약 3,500자)에서 잘리는지 봐야 합니다. 잘린다면 검색은 RAG로 하고, 본보기 원문은 파일 전체를 따로 읽어 넘기는 방식이 맞습니다. 작은 모델은 문맥 창도 좁아서 넘길 양을 골라야 합니다.
3. **임베딩 속도**: 이 환경에는 쓸 수 있는 GPU가 없어 청크 하나에 약 4초가 걸린다는 기록이 있습니다. 폐쇄망 서버도 임베딩 모델을 로컬(Ollama)로 돌려야 하므로 서버 사양을 먼저 봐야 합니다. 이름 검색은 임베딩이 없어도 동작합니다.
4. **새로운 유형의 화면**: 비슷한 본보기가 없는 화면은 여전히 어렵습니다.

## 바뀐 계획

| 단계 | 내용 |
|---|---|
| 1 | 대상 프로젝트를 `dstone-knowledge`로 분석하고 규칙 파일(거래 ID, 화면 오픈, 메뉴)을 맞춥니다 |
| 2 | 개발 가이드, 공통 함수 설명, 컴포넌트 매뉴얼을 일반 문서로 올립니다 |
| 3 | 확인 작업: 화면 원문의 청크 처리 방식, 본보기 화면 + 연결 코드를 한 번에 가져오는 조회가 있는지 |
| 4 | `dstone-ai-engine` Workflow를 만듭니다: 검색 → 따라가기 → 복사·수정 → 검증 → 승인 |
| 5 | 가벼운 검증기를 만듭니다(이 단계는 계속 필요합니다) |
| 6 | 시범 적용과 측정. 넥사크로 배치 품질이 부족할 때만 레이아웃 명세와 변환기를 추가합니다 |

변환기는 필수에서 "필요하면 추가"로 내려가고, 중심이 RAG와 기존 코드 복사로 옮겨 갑니다.

3단계 확인은 조회만으로 할 수 있습니다. 원하시면 파일은 건드리지 않고 코드와 DB를 읽어서 확인해 드리겠습니다.
