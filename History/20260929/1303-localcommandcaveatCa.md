네, 해결할 수 있어요. 문제를 쪼개 보면 사실 **세 가지 문제**가 섞여 있어요.

1. **데이터 모델**: step 사이를 오가는 값의 형태가 제각각이다 (string / 객체 / 배열).
2. **표현식 문법**: `{{...}}`를 자체 파서로 해석한다.
3. **타입 정의**: 어떤 구조가 오가는지 YAML에 선언할 방법이 없다.

각각 **이미 검증된 표준**을 하나씩 가져다 쓰면 정석적인 구조가 됩니다.

---

## 1. 데이터 모델: 모든 값은 JSON

step 간에 오가는 값을 전부 **JSON 값**(Jackson `JsonNode`)으로 통일합니다. 그러면 string은 "JSON 문자열"일 뿐이라, 문자열과 객체를 따로 처리할 필요가 없어져요.

엔진은 실행 중에 **워크플로우 컨텍스트** 하나를 JSON으로 유지합니다.

```json
{
  "input": "사용자 원본 입력 (문자열 또는 객체)",
  "steps": {
    "step01": { "status": "SUCCESS", "output": { "summary": "...", "items": [ ... ] } },
    "step02": { "status": "RUNNING" }
  }
}
```

표현식은 모두 이 컨텍스트를 대상으로 평가됩니다.

## 2. 표현식: `${ }` 구분자 + jq

**구분자는 `${ }`**, **표현식 언어는 jq**를 권합니다. 이 조합이 CNCF Serverless Workflow 1.0의 방식이라, 앞서 얘기한 "어휘를 표준에 맞춘다"는 방향과도 이어져요.

```yaml
input: "${ .input }"                          # 최초 입력 그대로
input: "${ .steps.step01.output }"            # 객체 통째로 (타입 유지)
input: "${ .steps.step01.output.items[0] }"   # 배열의 첫 요소
input: "${ .steps.step01.output.items | length > 0 }"  # 조건식
```

jq를 고른 이유는 이렇습니다.
- **JSON 변환 전용 언어**라서 필드 추출, 배열 필터, 객체 재조립을 한 줄로 할 수 있어요.
- 자체 파서가 필요 없습니다. Java에서는 `jackson-jq` 라이브러리가 Jackson `JsonNode` 위에서 바로 동작해요.
- 부작용이 없어서 **YAML 작성자가 임의 코드를 실행할 수 없습니다.** 공유 엔진에서는 이게 중요해요.

**SpEL은 비추천이에요.** Spring 개발자에게 익숙하지만 `T(java.lang.Runtime).getRuntime().exec(...)`처럼 임의 Java 호출이 가능해서, 여러 앱이 YAML을 올리는 공유 엔진에는 위험합니다. 쓴다면 `SimpleEvaluationContext`로 반드시 제한해야 하고, 그러면 오히려 jq보다 표현력이 떨어져요.

덤으로 해결되는 문제도 하나 있어요. 지금의 `{{...}}`는 YAML에서 `{`가 **flow mapping 시작 문자**라 따옴표 없이 쓰면 YAML 파서가 중첩 맵으로 해석합니다. 그래서 모든 곳에 따옴표를 강제당하죠. `${`는 이 충돌이 없습니다. 다만 jq 식 안에 `: `가 들어갈 수 있으니 **"항상 큰따옴표로 감싼다"**를 작성 규칙으로 정해 두세요.

### 평가 규칙은 딱 하나만

> 값이 `${`로 시작하고 `}`로 끝나면 **표현식**이다. 평가 결과를 **타입 그대로** 넘긴다. 그 외에는 리터럴이다.

문자열 중간에 `${}`를 섞는 치환(`"요약: ${ .x }"`)은 **허용하지 않습니다.** 섞기 시작하면 "객체를 문자열 중간에 넣으면 어떻게 되나" 같은 모호한 규칙이 생겨요. 문자열 조합이 필요하면 jq로 쓰면 됩니다.

```yaml
input: "${ \"요약 대상: \" + .steps.step01.output.summary }"
```

### 프롬프트 템플릿은 별개의 문제로 분리

프롬프트 문장 안에 값을 끼워 넣는 것은 **에이전트 정의 파일의 책임**으로 분리하세요.

- 워크플로우 YAML은 **데이터 매핑**(jq)만 담당합니다.
- 에이전트의 **프롬프트 템플릿**(Spring AI `PromptTemplate`의 `{변수}` 방식)은 에이전트 파일에서 담당합니다.

이렇게 나누면 워크플로우 표현식이 단순하게 유지돼요.

## 3. 타입 정의: JSON Schema

입출력 구조는 **JSON Schema**로 선언합니다. 에이전트 정의에 출력 스키마를 두면 세 곳에서 쓸 수 있어요.

- LLM 구조화 출력: Ollama의 `format`이나 Spring AI의 JSON 스키마 출력에 그대로 전달
- step 경계에서의 검증: 스키마를 위반하면 `onFailure`로 보냄
- 로딩 시점의 참조 검증: 존재하지 않는 필드를 참조하면 경고

```yaml
# agents/testApp/testApp-agent-01.yml
id: testApp-agent-01
model: ollama/qwen2.5-coder
prompt: |
  다음 문서를 요약하고 핵심 항목을 추출하라.
  ---
  {text}
input:
  schema:
    type: object
    required: [text]
    properties:
      text: { type: string }
output:
  schema:
    type: object
    required: [summary, items]
    properties:
      summary: { type: string }
      items:   { type: array, items: { type: string } }
```

## 적용한 워크플로우

주신 구조는 최대한 유지하고, 표현식과 스키마만 바꿨어요.

```yaml
id: testApp-workflow
description: 테스트용 workflow

input:
  schema: { type: string }

output:
  value: "${ .steps.step02.output }"

steps:
  - id: step01
    type: AGENT
    ref: testApp-agent-01
    input:                                     # 객체 매핑: 에이전트 input 스키마에 맞춤
      text: "${ .input }"
    onSuccess: step02
    onFailure: FAIL

  - id: step02
    type: AGENT
    ref: testApp-agent-02
    input:
      summary: "${ .steps.step01.output.summary }"   # 필요한 필드만 골라서
      itemCount: "${ .steps.step01.output.items | length }"
      mode: strict                                    # 리터럴
    onSuccess: SUCCESS
    onFailure: FAIL
```

`input`은 **값 하나**(`"${ .input }"`)로 써도 되고, **객체 매핑**으로 써도 됩니다. 객체 매핑이면 필드마다 표현식이나 리터럴을 평가해서 JSON 객체로 조립한 뒤 에이전트에 넘겨요.

**step 타입별 출력도 고정 스키마로 정해 두세요.** 그래야 다른 step에서 안심하고 참조할 수 있습니다.

| type | output 스키마 |
|---|---|
| AGENT | 에이전트 정의의 `output.schema` |
| SUPERVISOR | `{ pass: boolean, reason: string }` |
| ROUTER | `{ route: string, reason: string }` |
| TOOL | Tool 정의의 출력 스키마 |
| APPROVAL | `{ approved: boolean, approver: string, comment: string }` |

## Java 구현 핵심

```java
// build.gradle: implementation 'net.thisptr:jackson-jq:1.0.0'
public class ExpressionEvaluator {

    private final Scope rootScope;
    private final Map<String, JsonQuery> cache = new ConcurrentHashMap<>();

    public ExpressionEvaluator() {
        rootScope = Scope.newEmptyScope();
        BuiltinFunctionLoader.getInstance().loadFunctions(Versions.JQ_1_6, rootScope);
    }

    public static boolean isExpression(JsonNode node) {
        if (!node.isTextual()) return false;
        String s = node.asText().trim();
        return s.startsWith("${") && s.endsWith("}");
    }

    /** 로딩 시점에 호출: 문법 오류를 실행 전에 잡는다 */
    public JsonQuery compile(String expr) {
        String body = expr.trim();
        body = body.substring(2, body.length() - 1).trim();
        String key = body;
        return cache.computeIfAbsent(key, k -> {
            try { return JsonQuery.compile(k, Versions.JQ_1_6); }
            catch (JsonQueryException e) {
                throw new WorkflowDefinitionException("잘못된 표현식: " + expr, e);
            }
        });
    }

    /** 실행 시점: 값 하나 또는 객체 매핑 전체를 재귀적으로 평가 */
    public JsonNode resolve(JsonNode template, JsonNode context) {
        if (isExpression(template)) {
            List<JsonNode> out = new ArrayList<>();
            try {
                compile(template.asText()).apply(Scope.newChildScope(rootScope), context, out::add);
            } catch (JsonQueryException e) {
                throw new StepExecutionException("표현식 평가 실패: " + template.asText(), e);
            }
            return out.isEmpty() ? NullNode.getInstance() : out.get(0);
        }
        if (template.isObject()) {
            ObjectNode result = JsonNodeFactory.instance.objectNode();
            template.fields().forEachRemaining(e -> result.set(e.getKey(), resolve(e.getValue(), context)));
            return result;
        }
        if (template.isArray()) {
            ArrayNode result = JsonNodeFactory.instance.arrayNode();
            template.forEach(n -> result.add(resolve(n, context)));
            return result;
        }
        return template;   // 리터럴
    }
}
```

### 로딩 시점 검증 (자체 파서 대비 가장 큰 이득)

워크플로우 YAML을 읽을 때 실행 전에 다음을 확인하고 실패시키세요.

1. 모든 표현식을 `compile` → **문법 오류**를 사전에 잡음
2. 표현식에서 `.steps.XXX`를 추출해 **존재하지 않는 step id**를 참조하는지 확인
3. `onSuccess`/`onFailure` 흐름상 **아직 실행되지 않았을 수 있는 step**을 참조하는지 확인 (예: step01이 step03의 output을 참조)
4. `onSuccess`/`onFailure`의 대상이 실제 step id이거나 예약어(`SUCCESS`, `FAIL`)인지 확인. step id로 `SUCCESS`, `FAIL`을 쓰지 못하게 막는 것도 여기서 합니다.

## 정리

| 문제 | 해결 | 표준 |
|---|---|---|
| 값의 형태가 제각각 | 모든 값을 JSON으로 통일 | JSON |
| 자체 `{{}}` 파서 | `${ }` + jq, 전체 일치일 때만 평가 | jq (Serverless Workflow 1.0과 동일) |
| 구조 선언 불가 | 에이전트/Tool/step 타입별 입출력 스키마 | JSON Schema |
| 프롬프트 치환 | 에이전트 파일의 템플릿으로 분리 | Spring AI PromptTemplate |

과제 1의 `log-analyzer`를 이 규칙으로 다시 쓰면 조건 분기는 ROUTER step과 `${ .steps.classify.output.severity == "HIGH" }` 같은 식으로 자연스럽게 표현됩니다. 먼저 `ExpressionEvaluator`를 엔진에 붙여 보시고, 기존 `{{}}` 파서를 걷어내는 과정에서 막히는 부분이 있으면 가져와 주세요.

## 답변

`{{ }}` 자체 파서를 걷어내고, 답변대로 **`"${ jq }"` 표현식 + JSON 값 + JSON Schema** 구조로 바꿨습니다. 컴파일, 기동 검증, 실제 실행까지 확인했고 커밋은 하지 않았습니다.

## 바뀐 내용

**표현식 엔진**
- `net.dstone.ai.common.schema.ExpressionEvaluator`를 새로 만들었습니다. 라이브러리는 jackson-jq 1.6.5(jq 1.7 문법)로, 현재 코드가 쓰는 Jackson 2 위에서 동작합니다.
- 규칙은 답변과 같습니다. **값 전체가 `${ … }`일 때만 계산하고 결과는 타입 그대로 넘기며, 나머지는 리터럴**입니다. 문자열 중간에 섞어 쓰면 기동 시점에 막힙니다.
- 표현식은 `{input, steps}`만 봅니다. `approvals`는 엔진 내부용이라 숨겼습니다.
- `WorkFlowExecutor`의 step input, forEach, `output.value` 처리를 모두 이 클래스로 바꿨습니다.

**기동 시점 검증 (`WorkFlowRegistry`)**
- 답변의 네 가지를 모두 넣었습니다.
  1. jq 문법 검사
  2. 없는 step 참조 검사
  3. 흐름상 먼저 실행될 수 없는 step 참조 검사 (재시도 루프처럼 되돌아오는 흐름은 허용)
  4. 이동 대상 검사, 그리고 `SUCCESS`/`FAIL`을 step id로 쓰지 못하게 막기
- 이 밖에 예전 `{{ }}`, 글자 중간의 `${ }`, 정의되지 않은 함수나 변수, 치환되지 않은 환경변수도 막습니다.
- 스키마에 없는 필드를 참조하면 답변대로 **경고**만 남깁니다.

**정리한 소스**
- 삭제: `Template.java`, `TemplateException`, `WorkFlowContext.promptVariables()`/`withItem()`, step 실행기의 `promptVariables` 파라미터, 옛 이름 안내 코드
- 대신 `ExpressionException`을 추가했습니다.

## 답변에서 한 단계 더 정한 부분

- **결과가 여러 개면 오류로 처리합니다.** 답변 코드처럼 첫 번째 값만 받으면 나머지가 조용히 사라지기 때문입니다. 리스트로 받으려면 `[ ]`로 감싸면 됩니다.
- **step id는 영문/숫자/밑줄만 허용합니다.** jq는 `.steps.validate-each`를 뺄셈으로 읽기 때문입니다. 그래서 샘플 id를 `validateEach`, `billingStep` 같은 camelCase로 바꿨습니다.
- **forEach 항목은 jq 변수 `$item`으로 들어갑니다.** 이에 맞춰 `forEach`도 `"${ .input.sqlList }"`처럼 표현식으로 적습니다.
- **Agent prompt의 `{변수}`는 이제 그 Agent 자신의 input 필드로 채웁니다.** "프롬프트 템플릿은 에이전트 파일의 책임"이라는 원칙을 따른 것입니다.
  - 그래서 글자 input인 `sample-general-chat`(`{role}` 사용)은 채팅 API의 `variables`로만 부를 수 있습니다.
  - Workflow용으로는 object input 예시인 `sample-role-reply-agent`를 새로 만들었고, router와 supervisor 샘플을 이 Agent로 바꿨습니다.
- **없는 경로를 읽으면 이제 실패가 아니라 `null`입니다**(jq 규칙). 기본값은 `??` 대신 `//`로 줍니다.

## 답변

네, 지금도 씁니다. 이번에 걷어낸 것은 `{{ }}` 치환기인 `Template`이고, 그 자리는 `ExpressionEvaluator`가 맡았습니다. `JsonSchemas`는 답변의 세 번째 축인 **"구조는 JSON Schema로 선언한다"**를 맡는 클래스라 그대로 필요합니다. 둘은 이렇게 나뉩니다.

| 클래스 | 하는 일 |
|---|---|
| `ExpressionEvaluator` | **값을 꺼내고 계산**: `"${ .steps.a.output }"`를 jq로 계산 |
| `JsonSchemas` | **값의 모양을 선언하고 검사**: Agent/Workflow의 `input`/`output` 계약 |

## 지금 쓰는 곳

| 쓰는 곳 | 메서드 | 하는 일 |
|---|---|---|
| `SchemaDefinition`, `WorkFlowOutputDefinition` | `normalize`, `string` | YAML 축약형(`list<string>`)을 표준 JSON Schema로 펼침 |
| `AgentRegistry`, `WorkFlowRegistry` | `checkSchema` | 기동 시 스키마 자체가 올바른 JSON Schema인지 검사 |
| `WorkFlowRegistry` | `typeOf`, `properties`, `required`, `allowsExtraProperties`, `arrayOf`, `checkPath` | step input 모양이 Agent 계약과 맞는지, 표현식이 읽는 필드가 스키마에 있는지(경고) |
| `WorkFlowExecutionService` | `validate` | 실행 요청 input이 Workflow input 스키마에 맞는지 확인(아니면 400) |
| `AgentExecutor`, `SchemaOutputConverter` | `validate`, `typeOf`, `toPrettyJson` | Agent input 검사, LLM 답이 output 스키마에 맞는지 검사, 형식 지시문 생성 |
| `WorkFlowExecutor` | `validate` | Workflow `output.schema` 검사 |
| `StepOutputSchemas` | 상수들 | SUPERVISOR/ROUTER/APPROVAL의 고정 출력 스키마 생성 |

public 메서드는 전부 어딘가에서 쓰이고 있어서, 안 쓰이는 코드는 없습니다.
