## 1. 부르는 쪽·불리는 쪽 탭이 비활성화된 이유

버그가 아니고 그렇게 만들어 둔 동작입니다. 두 탭은 **대상이 메소드일 때만** 켜집니다.

- `dstone-boot/src/main/webapp/knowledge/assets/js/impact.js:459`
  ```js
  function tabEnabled(name) {
      return name === "impact" || (target && target.kind === "method");
  }
  ```
  비활성 탭에 마우스를 올리면 "메소드를 대상으로 골랐을 때만 볼 수 있습니다."가 뜹니다.

이렇게 만든 이유는 API에 있습니다. 호출 관계 API(`/methods/{methodId}/callers`, `/callees`)는 메소드 ID 하나만 받습니다. 타입·테이블·SQL에는 "누가 부르는지"를 한 줄로 정할 기준점이 없습니다. 반면 영향도 API(`/impact?type=…`)는 네 종류를 모두 받습니다.

**호출 관계를 보는 방법:** 영향도 탭 아래 "메소드" 표에서 `performJADC1021M01S`나 `performJADC1021M01I`를 누르세요. 그 메소드가 새 대상이 되고 두 탭이 켜집니다. 이전 대상(타입)은 "지나온 대상"에 남으니 눌러서 돌아오면 됩니다.

## 2. 진입점·화면·메소드의 의미

리비전 195에서 `hi.ja.closing.service.JADC1021M`의 실제 영향도 결과를 기준으로 정리했습니다.

영향도는 **대상에서 시작해 "부르는 쪽" 방향으로만** 거슬러 올라갑니다. 따라가는 관계는 `CALLS`, `REQUESTS`, `CALLS_POSSIBLE_IMPLEMENTATION`, `ENCLOSES_ANONYMOUS`이고 기본 깊이는 5입니다. 그래서 JADC1021M이 **부르는** `JADC1021S`나 SQL은 결과에 나오지 않습니다. 그쪽은 불리는 쪽 탭에서 봅니다.

### 메소드 (3건)
대상에서 시작해 거슬러 올라가며 닿은 **Java 메소드** 전부입니다.
- **거리 0**은 출발점입니다. 대상이 타입이면 **그 타입에 선언된 메소드 전부**가 들어갑니다(`selectImpactMethods`, `RelationDao.xml:565`). 그래서 생성자 `<init>(ServiceContext)`까지 포함해 3건입니다.
- 거리 1 이상은 이 메소드들을 부르는 다른 Java 메소드입니다. JADC1021M을 부르는 Java 코드가 없어서 이번 결과에는 없습니다. 화면에서 거래 ID로 불리는 클래스라서 그렇습니다.
- 익명 클래스 안의 메소드는 빼고, 그것을 감싸는 바깥 메소드를 같은 거리로 보여 줍니다.

### 진입점 (2건)
닿은 메소드 가운데 **시스템 바깥에서 들어오는 입구**로 등록된 것입니다(`analysis_endpoint`). 사용자가 변경을 처음 겪는 곳이라는 뜻입니다.

| 주소 | 종류 | 처리 메소드 |
|---|---|---|
| `JADC1021M01S` | TRANSACTION | `performJADC1021M01S` |
| `JADC1021M01I` | TRANSACTION | `performJADC1021M01I` |

- 종류는 HTTP 주소, `TRANSACTION`(거래 ID), 스케줄, `main`, `THREAD` 같은 것들입니다. HI-Japan은 `perform{거래ID}` 규칙으로 거래 ID를 진입점으로 잡습니다.
- 메소드 없이 타입에만 붙은 진입점도 있습니다(Struts DispatchAction처럼 어느 메소드가 불릴지 모르는 경우). 그 타입의 메소드가 하나라도 닿으면 결과에 넣고, 짐작이라서 `LOW`로 표시합니다.

### 화면 (1건)
변경의 영향을 받는 **화면 파일**(JSP, WebSquare/Nexacro XML)입니다. 화면에 닿는 길은 세 가지이고, "이어진 방식" 칸에 적힙니다.

| 방식 | 의미 |
|---|---|
| 화면 요청 (`REQUESTS`) | 화면이 닿은 메소드의 주소나 거래 ID를 요청한다 |
| 호출 (`CALLS`) | JSP 안의 Java 코드가 메소드를 직접 부른다 |
| 화면 열기 (`RENDERS`) | 닿은 메소드가 끝난 뒤 이 화면을 연다 |

이번 결과는 `was/ui/ja/JADC1021G.xml` 하나이고, 거리 1의 **화면 요청**입니다. 소스에서 확인한 근거는 다음과 같습니다.
- `JADC1021G.xml:400`: `HiJS.svr.doRequestAjax("JADC1021M01S", …)`
- `JADC1021G.xml:478`: `HiJS.svr.doRequestAjax("JADC1021M01I", …)`

### 정리
- **메소드**: 영향이 퍼지는 Java 코드 전체이고, 거리 0이 출발점입니다.
- **진입점**: 그중 바깥에서 들어오는 입구(주소, 거래 ID, 배치 등)입니다.
- **화면**: 그 입구를 요청하거나 그 메소드가 여는 UI 파일입니다.

## 답변

## 영향도 탭은 "부르는 쪽"을 끝까지 따라간 뒤 맨 바깥 끝만 모은 요약입니다

두 탭은 같은 방향을 봅니다. 차이는 무엇을 보여 주느냐입니다.

| | 부르는 쪽 탭 | 영향도 탭 |
|---|---|---|
| 방향 | 위로 (나를 부르는 쪽) | 위로 (나를 부르는 쪽) |
| 보여 주는 것 | **경로**: 누가 누구를 어디서 부르는지, 한 칸씩 | **도착점**: 끝까지 올라가서 닿은 거래·주소와 화면 |
| 답하는 질문 | 이 호출이 어떻게 이어지나? | 이걸 고치면 **어떤 기능을 다시 테스트해야 하나?** 누구에게 알려야 하나? |

영향도에서 진입점과 화면이 핵심인 이유는 사용자와 테스터가 아는 단위이기 때문입니다. "메소드 97개가 영향받는다"는 말로는 할 일이 정해지지 않습니다. "거래 32개와 화면 22개를 다시 확인하라"는 테스트 목록이 됩니다.

## 예로 드신 메소드는 결과가 거의 비어 보일 수밖에 없습니다

`performJADC1021M01S`는 그 자체가 맨 위 입구입니다. 화면 `JADC1021G.xml`이 거래 ID로 바로 부릅니다. 그래서 올라가자마자 끝나고, 결과는 자기 자신, 자기 거래 `JADC1021M01S`, 화면 하나뿐입니다. 이 결과도 "이 메소드를 고쳐도 JADC1021G 화면의 조회 말고는 영향이 없다"는 정보이긴 합니다. 다만 부르는 쪽 탭과 다를 게 없어서 쓸모를 느끼기 어렵습니다.

대상이 깊이 있을수록 영향도의 의미가 커집니다. 같은 기능을 따라 내려가며 리비전 195에서 실제로 조회해 봤습니다.

| 대상 | 닿는 메소드 | 진입점 | 화면 |
|---|---|---|---|
| `JADC1021M#performJADC1021M01S` | 1 | 1 | 1 |
| SQL `JADC1021D.selectProfitAmt` | 3 | 1 | 1 |
| 테이블 `JA_CLOSSTS_S` | 30 | 8 | 5 |
| 테이블 `JA_TACC_C` | 97 | 32 | 22 |

`JA_TACC_C`의 컬럼 하나를 바꾸면 화면 22개와 배치 거래(`JADC1220B01I` 등)를 다시 봐야 합니다. 부르는 쪽 탭으로 이걸 알아내려면 메소드 33개에서 각각 위로 올라가 끝을 손으로 모아야 합니다. 영향도 탭은 그 작업을 한 번에 해 줍니다. 그래서 테이블·SQL·타입 대상에는 영향도 탭만 있습니다.

## 불리는 쪽은 성격이 조금 다릅니다

불리는 쪽(`JADC1021S#getList`, `JADC1021D#selectList`, SQL, 테이블 `JA_CLOSSTS_S`·`JA_TACC_C`)은 내가 고쳐서 영향받는 곳이 아닙니다. **내가 기대고 있는 곳**입니다. A를 고친다고 A가 부르는 B의 동작이 바뀌지는 않습니다(넘기는 값이 바뀌는 경우는 예외). 그래서 불리는 쪽은 고치기 전에 이해해야 할 범위이고, 영향 범위는 언제나 위쪽(부르는 쪽, 영향도)입니다.

## 정리하면

- **영향도**: 고치면 어디까지 번지나 → 다시 테스트할 거래와 화면 목록
- **부르는 쪽**: 그 번짐이 어떤 경로로 이어지나 → 근거와 경로 확인
- **불리는 쪽**: 이 코드가 무엇에 기대나 → 고치기 전에 이해할 범위

화면이 이 차이를 잘 전달하지 못하는 건 맞습니다. 손볼 만한 곳은 두 가지입니다.
1. 대상이 진입점 메소드라서 결과가 자기 자신뿐이면, "이 메소드는 입구라서 영향이 자기 거래와 화면에서 끝납니다" 같은 안내를 띄웁니다.
2. 탭 이름이나 설명을 "영향도"에서 "다시 확인할 곳(테스트 범위)"에 가깝게 바꿉니다.

원하시면 이 방향으로 고쳐 보겠습니다.

## 제안: 영향도 탭을 "변경 요약" 한 장으로

부르는 쪽·불리는 쪽 탭이 **경로**를 맡고, 영향도 탭은 **결론**만 맡는 구성입니다. 이 탭을 연 사람이 알고 싶은 것은 세 가지라고 봅니다.

1. 고치면 **어디가** 영향받나 (위로 올라간 끝)
2. 이 코드가 **무슨 데이터를** 건드리나 (아래로 내려간 끝)
3. 이 결과를 **얼마나 믿어도 되나**

### 화면 구성 (`performJADC1021M01S` 예시)

```
┌ 한 줄 결론 ──────────────────────────────────────────────┐
│ 이 메소드는 거래 JADC1021M01S의 입구입니다.                  │
│ 고치면 화면 1개(JADC1021G), 거래 1개가 영향받습니다. 모두 확실(HIGH). │
└──────────────────────────────────────────────────────┘

① 영향받는 곳 (다시 테스트할 목록)
   업무    화면                 거래 / 주소           종류
   JADC   JADC1021G.xml        JADC1021M01S         온라인 거래
   ── 배치 0 · HTTP 0 · 기타 0

② 건드리는 데이터
   테이블          읽기  쓰기   거치는 SQL
   JA_CLOSSTS_S    ●          JADC1021D.selectProfitAmt
   JA_TACC_C       ●          JADC1021D.selectProfitAmt

③ 믿을 만한가
   신뢰도  HIGH 1 · MEDIUM 0 · LOW 0
   빠졌을 수 있는 것: 경로 위의 풀지 못한 호출 0건, 깊이 제한에 걸림 없음
```

`JA_TACC_C` 같은 테이블이 대상이면 같은 틀에 값만 커집니다. ①은 업무 접두어(JADC, JACA, JADA…)별로 접힌 묶음이 되고(화면 22, 거래 32, 그중 배치 몇 개), ②는 "이 테이블을 읽는 SQL n개, 쓰는 SQL m개"로 바뀝니다.

### 각 블록의 근거와 구현 난이도

| 블록 | 의미 | 데이터 |
|---|---|---|
| 한 줄 결론 | 숫자를 문장으로. 대상이 진입점이면 그렇다고 알려 줌 | 지금 `/impact` 응답으로 가능 |
| ① 영향받는 곳 | 테스트 체크리스트. **화면과 거래를 한 행으로 묶는 것**이 핵심(지금은 따로 나옴) | 업무 접두어 묶음과 종류 구분(`endpointType`)은 화면 쪽 JS로 가능. 화면↔거래 짝짓기는 `/impact`에 필드 추가 필요 |
| ② 건드리는 데이터 | 이 변경이 데이터 정합성에 닿는지. 특히 **쓰기**가 있는지 | 메소드·타입 대상은 아래 방향 탐색이 새로 필요(`/impact`에 `touches` 추가) |
| ③ 믿을 만한가 | "영향 없음"이 정말 없는 건지, 분석이 못 이은 건지 구분 | 신뢰도 건수와 `truncated`는 이미 있음. 경로 위 UNRESOLVED 건수는 SQL 추가 필요 |

### 빼는 것

- **메소드 표**: 거리별 메소드 목록은 부르는 쪽 탭과 겹칩니다. "닿는 메소드 97개 (계층별 Controller 29 · Service 32 · DAO 33)" 한 줄로 줄이고, 누르면 부르는 쪽 탭으로 넘어가게 합니다.
- **거리 칸**: 테스트 목록에서는 의미가 적어서 마우스를 올리면 보이게만 합니다.

## 바뀐 화면
영향도 탭은 이제 "고치면 무엇을 다시 확인해야 하나"만 보여 줍니다. 호출 경로는 부르는 쪽·불리는 쪽 탭에서 봅니다.

1. **맨 위 결론**: 대상 메소드가 그 자체로 입구인지, 영향받는 화면·진입점 수와 신뢰도, 건드리는 테이블 수를 문장으로 씁니다. 분석이 놓쳤을 수 있는 곳이 있으면 경고도 띄웁니다.
2. **영향받는 곳**: 화면과 그 화면이 부르는 진입점을 한 줄로 묶은 테스트 목록입니다. 처리하는 클래스의 패키지(closing, expense…)로 업무를 나눕니다.
3. **건드리는 데이터**: 테이블마다 읽는 SQL 수와 쓰는 SQL 수를 보여 줍니다. 쓰기는 빨간색이고, 펼치면 SQL 이름이 나옵니다.
4. **믿을 만한가**: 신뢰도, 깊이 제한에 걸렸는지, 분석이 풀지 못한 호출을 보여 줍니다.
5. **닿는 메소드**: 계층별 건수 한 줄로 줄이고 목록은 접어 뒀습니다. 메소드 대상이면 "부르는 쪽 탭에서 경로 보기" 단추가 있습니다.

처음 계획의 2단계까지 했습니다. dstone-knowledge의 `/impact` 응답에 `endpoints[].screens`, `touches`, `gaps`를 새로 더했습니다.

## 확인한 것
HI-Japan 리비전 195를 시험용 사본(4181 포트)에 띄우고 헤드리스 브라우저로 확인했습니다.
- `performJADC1021M01S`: "이 메소드는 JADC1021M01S의 입구입니다…", 화면 1개, 진입점 1개, 테이블 2개(모두 읽기만)
- 테이블 `JA_TACC_C`: 화면 22개, 진입점 32개, 업무 6묶음, 읽는 SQL 39개, 쓰는 SQL 3개
- 타입 `JACA0110M`: 놓쳤을 수 있는 곳 1건(`JACA0110D.java:334 batchVOUpdate`)
- 390px 폭에서도 화면이 가로로 넘치지 않습니다.

로그인한 dstone-boot 안에서는 확인하지 않았습니다. 헤드리스 브라우저에 한글 글꼴이 없어서 글자는 화면 캡처 대신 페이지에서 뽑은 텍스트로 확인했습니다.

시험 중에 하나를 고쳤습니다. 처음에는 DAO 안의 `this.executeVOQuery(…)`처럼 프레임워크 jar가 없어서 풀지 못한 호출까지 "놓쳤을 수 있는 곳"으로 셌습니다. 그런데 이런 호출의 SQL은 규칙으로 이미 이어져 있습니다. 그래서 SQL이 이미 이어진 메소드 안의 호출은 세지 않도록 바꿨습니다.
