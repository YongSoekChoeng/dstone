## 답변

현재 dstone-ai-engine에 이미 이 기능의 뼈대가 상당 부분 구현되어 있습니다. 계획을 새로 짜기 전에 먼저 그 상태부터 확인했습니다.

## 이미 있는 것

- **`prompts/oracle-to-postgresql/v1.st`** — NVL/DECODE, `(+)` 아우터조인, ROWNUM→LIMIT/ROW_NUMBER(), START WITH...CONNECT BY→WITH RECURSIVE, 시퀀스, DUAL, 날짜변환, 대소문자 등 22개 규칙이 이미 구체적으로 박혀있는 시스템 프롬프트
- **`tools/sql/SqlSyntaxTools`** — JSQLParser로 순수 문법 검증 (항상 사용 가능)
- **`tools/sql/PostgresExplainValidationTools`** — 실제 PostgreSQL에 `EXPLAIN`을 던져 진짜 파서로 검증 (`dstone.ai.rag.enabled=true`일 때만, pgvector용 DataSource 재사용)
- **`ChatRequest`** — `promptName`+`toolsEnabled`+`requiredTool`+`provider`/`ollamaModel` 조합으로 이미 "변환 후 자기검증" 루프를 호출할 수 있는 구조

즉 이미 **"LLM이 규칙 기반 프롬프트로 변환 → Tool로 검증 → 실패하면 스스로 고쳐서 재검증"** 하는 self-correction 루프가 설계돼 있습니다. 질문 3번 구도("변환에 강점있는 tool 여러개를 조사해서 순차 호출")와는 다른 모델인데, 이게 이 상황에 더 맞는 접근입니다 — 아래에서 이유를 설명드릴게요.

## 질문 1: tool이 Java가 아니어도 되는가?

이 프로젝트의 Tool Calling 메커니즘(`ConfigTool` → `MethodToolCallbackProvider`)은 **Java 메서드 콜백만** 등록할 수 있습니다. 같은 JVM 안에서 Spring이 리플렉션으로 호출하는 구조라서요. 다만 그 Java 메서드 *내부에서* 외부 Python 스크립트/서비스를 호출하는 건 가능합니다.

그런데 `PostgresExplainValidationTools`의 주석을 보면, 이 프로젝트는 이미 한 번 이 갈림길에서 선택을 했습니다: 진짜 PostgreSQL 문법으로 검증하는 `libpg_query`는 JNI 네이티브 빌드가 필요해서 "**순수 JVM Docker/K8s 배포 방식과 안 맞다**"는 이유로 일부러 배제하고, 대신 JSQLParser(순수 JVM) + 실제 Postgres 서버 EXPLAIN(이미 붙어있는 인프라 재사용)으로 우회했습니다. `sqlglot`/`ora2pg` 같은 Python 도구를 tool로 끌어오면 같은 문제(별도 런타임, 별도 컨테이너 또는 subprocess 의존)가 재발합니다. 이 프로젝트 안에서는 **가능하지만 지금까지의 아키텍처 선택과 반대 방향**이라는 뜻이라, 굳이 끌어올 가치가 있는지는 따져봐야 합니다.

## 질문 2: RAG가 효과 있는가? 어떤 방식/문서?

**효과는 있지만, 지금 v1.st가 커버하는 22개 규칙 자체를 RAG로 옮기는 건 오히려 손해**입니다 — 정적 규칙은 프롬프트에 박아두는 게 검색 실패 리스크 없이 항상 적용되고 더 빠릅니다. RAG가 진짜 값을 내는 지점은 v1.st가 애초에 다룰 수 없는 것들입니다:

1. **PL/SQL 프로시저/패키지/트리거** — v1.st는 이 부분을 명시적으로 스코프 밖(원문 그대로 남김)이라고 선언해뒀는데, 여기에 프로젝트 특화 변환 사례를 쌓아가는 지식베이스로 쓸 수 있음
2. **이 SI 프로젝트에서 실제로 만난 특이 케이스** — "이 스키마의 이런 쿼리 패턴은 이렇게 고쳤다"는 교정 이력을 축적하는 조직 지식(organizational memory)
3. **에이전틱 RAG**(`RetrievalTools.searchKnowledgeBase` 패턴) — LLM이 v1.st 22개 규칙에 없는 낯선 구문을 만났을 때만 스스로 검색하게

문서 포맷은 산문(설명문)이 아니라 **패턴 1건 = 청크 1건**의 구조화된 형태여야 임베딩 검색이 잘 맞습니다:
```
패턴명: LISTAGG WITHIN GROUP → STRING_AGG
Oracle: LISTAGG(name, ',') WITHIN GROUP (ORDER BY id)
PostgreSQL: STRING_AGG(name, ',' ORDER BY id)
주의사항: ...
복잡도: 단순 규칙 치환
```
긴 글 하나에 여러 패턴을 섞으면 유사도 검색 품질이 떨어집니다.

## 제안하는 다음 단계

지금 있는 것을 실제로 굴려보지 않은 상태로 보입니다. 순서상:

1. **먼저 지금 있는 걸로 end-to-end 테스트** — `promptName=oracle-to-postgresql`, `toolsEnabled=true`로 실제 오라클 쿼리 몇 개(단순~복잡: ROWNUM 페이징, CONNECT BY 계층쿼리, (+) 조인)를 `/api/ai/chat`에 던져서 현재 self-correction 루프가 실제로 잘 도는지, `PostgresExplainValidationTools`가 켜져 있는지(`dstone.ai.rag.enabled=true`) 확인

3. Python tool 도입은 1~2단계를 해보고도 부족할 때만 재검토 — 지금 아키텍처와 충돌하는 선택이라 근거 없이 먼저 가져올 필요는 없어 보입니다

## 답변

`chat.jsp`는 이미 있고 동작하지만, 지금 상태로는 이 프롬프트를 테스트할 수 **없습니다** — dstone-boot 쪽 프록시 경로를 확인해보니 원인이 명확합니다.

## 막히는 지점

`chat.jsp` → `chat.js` → `dstone-boot`의 `ChatController(/ai/chat/sendMessage.do)` → `ChatService.streamChat()` → ai-engine의 `/api/ai/chat/stream`

이 경로에서 `ChatMessageRequest`(`dstone-boot/.../ai/vo/ChatMessageRequest.java:7`)가 `message`, `ragEnabled`, `toolsEnabled`만 받고 **`promptName`을 안 받습니다**. `ChatService.streamChat()`도 ai-engine에 보내는 body에 `promptName`을 안 실어보내고요(`ChatService.java:33-37`). 즉 체크박스로 "도구호출(Tool)"은 켤 수 있지만, `oracle-to-postgresql` 프롬프트를 고를 방법이 UI에 없어서 화면으로는 기본 채팅만 됩니다.

## 지금 당장 테스트하려면 → ai-engine에 직접 curl

`dstone-ai-engine`은 `POST /api/ai/chat`(스트리밍 아닌 일반 JSON, 포트 8081)을 그대로 갖고 있고, 여기엔 `promptName`/`toolsEnabled`가 이미 다 지원됩니다(`ChatRequest.java`). ai-engine은 Security가 꺼져있어(CLAUDE.md) 인증 없이 바로 호출 가능합니다. UI 없이 바로 검증 가능:

```bash
curl -s -X POST http://localhost:8081/api/ai/chat \
  -H "Content-Type: application/json" \
  -d '{
    "message": "SELECT * FROM (SELECT a.* FROM emp a WHERE a.dept_id = 10 ORDER BY a.hire_date DESC) WHERE ROWNUM <= 10",
    "promptName": "oracle-to-postgresql",
    "toolsEnabled": true
  }' | jq .
```

`(+)` 조인, `CONNECT BY` 케이스도 같은 방식으로 `message`만 바꿔 몇 번 더 돌려보면, 규칙 기반 변환 + 자기검증 루프(SqlSyntaxTools, 그리고 `dstone.ai.rag.enabled=true`면 PostgresExplainValidationTools까지)가 실제로 잘 도는지 UI 없이도 충분히 검증됩니다.

## 질문

dstone-ai-engine 에서 net.dstone.ai.tools.sql.SqlSyntaxTools 을 Tool Calling 으로 강제하고 싶으면 어떻게 하나?

## 답변

`requiredTool` 필드로 됩니다 — 이미 `ChatRequest`/`ChatService`에 구현돼 있는 기능입니다(`ChatService.java:118-130`).

## 사용법

```bash
curl -s -X POST http://localhost:8081/api/ai/chat \
  -H "Content-Type: application/json" \
  -d '{
    "message": "SELECT e.name, d.dept_name FROM emp e, dept d WHERE e.dept_id = d.dept_id(+)",
    "promptName": "oracle-to-postgresql",
    "requiredTool": "validateSqlSyntax"
  }' | jq .
```

`requiredTool`에 넣는 값은 **클래스명이 아니라 `@Tool` 메서드명**입니다. `SqlSyntaxTools.validateSqlSyntax(...)`에는 `@Tool(name=...)`을 따로 안 줬으니 등록된 tool 이름은 메서드명 그대로 `validateSqlSyntax`입니다(`ConfigTool`이 `MethodToolCallbackProvider`로 감쌀 때 이름을 그대로 씀).

## 제약 2가지 (코드에서 바로 throw됨)

- **`provider=anthropic`일 때만 동작** — `ChatService.java:119-120`에서 다른 provider면 `IllegalStateException`. Anthropic API의 `tool_choice=tool`을 그대로 쓰는 구현이라 그렇습니다. `provider` 필드를 생략하면 기본값(`spring.ai.model.chat`)이 anthropic인지 확인하세요.
- **이름이 `ConfigTool`에 등록된 tool 목록에 정확히 있어야 함** — 아니면 400(`ChatService.java:122-124`). `PostgresExplainValidationTools`와 달리 `SqlSyntaxTools`는 `@ConditionalOnProperty` 없이 항상 등록되므로 `dstone.ai.rag.enabled` 값과 무관하게 이름은 항상 목록에 있습니다.

## 주의할 점 한 가지

`requiredTool`은 이번 응답을 **무조건 tool_use로 강제**합니다(`disableParallelToolUse(true)`도 같이 걸림). `validateSqlSyntax`는 원래 v1.st 21번 규칙처럼 "변환 다 하고 나서 검증"하는 용도인데, 첫 턴부터 강제하면 LLM이 별도 사고 과정 없이 곧장 tool_use 블록 안에서 변환 결과를 만들어 넘기게 됩니다 — `toolsEnabled: true`(auto)로 둬서 LLM이 알아서 "변환 다 하고 마지막에 검증 호출"하는 흐름과 미묘하게 다른 동작입니다. 지금 하시려는 게 "검증 도구가 실제로 호출되는지 그 자체"를 확인하는 스모크 테스트라면 `requiredTool`이 맞고, "정상적인 변환 품질 + 자기검증 루프"를 보고 싶은 거면 `toolsEnabled: true`로 auto 판단에 맡기는 쪽을 쓰시는 게 맞습니다.
