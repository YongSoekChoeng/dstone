## 답변

코드를 직접 훑어봤습니다 (`StepDefinition`/`StepType`/`AgentDefinition`, `WorkFlowExecutor`, `AgentStepRunner`/`ToolStepRunner`/`ApprovalStepRunner`, `AgentExecutor`, `ToolExecutor`). 전반적으로 이미 순차/분기/병렬/루프 4패턴, Tool 화이트리스트, RAG advisor, 멀티테넌트(`allowedCallers`)까지 잘 갖춰진 상태였고, 질문하신 두 가지 지점에서 구체적으로 걸리는 부분을 찾았습니다.

**1) "여러 업무에 범용적으로 쓸 만한 구조인가?"**
기본 골격(4패턴, YAML만으로 Workflow/Agent 추가)은 범용성 요구를 충족합니다. 다만 두 가지가 확장성을 갉아먹습니다.
- 모든 step 간 전달값이 결국 "문자열 하나(`primaryText`) + 평평한 전역 변수 맵"입니다. `StepOutput.data()`가 `variables.putAll()`로 **네임스페이스 없이** 병합되는데(`WorkFlowExecutor.mergeVariables`), 병렬 그룹의 두 step이 우연히 같은 키를 리턴하면 조용히 덮어씁니다. 업무가 다양해질수록(특히 병렬 step이 늘수록) 이 충돌 위험이 커집니다.
- 분기는 사실상 성공/실패 2지선다뿐입니다(`onSuccess`/`onFailure`). 업무 로직상 3갈래 이상 분기(예: 금액 구간별 처리)가 필요하면 SUPERVISOR를 여러 개 겹치는 우회밖에 없습니다.
- 동적 개수 팬아웃(리스트를 순회하며 항목별 병렬 처리)이 안 됩니다. `parallelGroup`은 YAML 작성 시점에 개수가 고정된 그룹만 지원합니다.

**2) "step 간 포맷이 불명확한데 개선 방법?"**
정확히 짚으셨습니다. 두 군데가 원인입니다.
- **TOOL step**: 이전 AGENT step이 순수 텍스트를 뱉는다는 계약뿐이라, 실제로는 LLM이 마크다운 코드펜스나 `[변환된 SQL]` 같은 레이블을 붙여 내려주는 일이 반복적으로 관찰됐고, 그걸 정규식으로 벗겨내는 방어 코드(`ToolStepRunner.stripLlmArtifacts`)가 생겼습니다. 이건 "계약이 강제되지 않는다"는 증상입니다. `SUPERVISOR`가 이미 `Verdict` record + `.entity(Verdict.class)`로 이 문제를 풀었으니(자유 텍스트가 아니라 JSON 스키마 강제), 데이터를 다음 step이 소비해야 하는 AGENT step에도 같은 패턴(`callForEntity(Class<T>)` 같은 범용 메서드)을 열어주면 정규식 방어 없이 구조적으로 해결됩니다.
- **TOOL step 성공/실패 판정**: 응답 텍스트가 `"실패:"`로 시작하는지 문자열 매칭으로 판정합니다(`Constants.Outcome.FAIL_PREFIX`). Tool 작성자가 이 접두사 컨벤션을 깜빡하면 컴파일도 안 걸리고 조용히 "성공"으로 처리됩니다. `boolean`을 실어 나르는 작은 결과 타입(또는 실패 시 예외)으로 바꾸면 이 매직 스트링 의존을 없앨 수 있습니다.

**우선순위 제안**: SUPERVISOR의 `Verdict` 패턴을 일반 AGENT step으로 확장(구조화 출력)하는 게 가장 임팩트가 크고, `data` 병합 시 step id로 네임스페이싱하는 건 적은 변경으로 충돌 위험을 없앨 수 있습니다. TOOL 성공/실패 문자열 접두사 교체는 그다음으로 봐도 됩니다. 동적 팬아웃/다지 분기는 지금 당장 필요한 업무가 나오기 전엔 굳이 먼저 만들 필요는 없어 보입니다.

이 중에서 어떤 것부터 실제로 손댈지 정해주시면 그것부터 구현하겠습니다 — 임의로 넷 다 한꺼번에 바꾸진 않겠습니다.

## 왜 필요했나

기존 방식(`onSuccess`/`onFailure`)은 딱 두 갈래만 가능합니다. "성공하면 A로, 실패하면 B로." 그런데 업무에서는 "문의 유형이 결제 문제면 X팀으로, 배송 문제면 Y팀으로, 그 외엔 Z팀으로" 처럼 **세 갈래 이상**으로 나눠야 할 때가 많죠. 예전 구조로 이걸 하려면 SUPERVISOR(통과/실패 판정 스텝)를 여러 겹 쌓아야 했어요 — "결제 문제인가?" 판정 → 아니면 "배송 문제인가?" 판정 → ... 이런 식으로요. 번거롭고 YAML도 지저분해집니다.

**ROUTER는 이 문제를 "LLM이 이름표 하나를 고르게 하고, 그 이름표로 바로 다음 스텝을 찾는" 방식으로 한 번에 해결합니다.**

## 어떻게 동작하나 (3가지 구성요소)

**1. YAML에서 `routes`를 정의합니다** — "이런 이름표들이 있고, 각각 어디로 갈지"

```yaml
- id: classify
  type: ROUTER
  ref: inquiry-classifier-agent   # 이 Agent가 판단을 내림
  routes:
    billing: billing-step         # LLM이 "billing"을 고르면 billing-step으로
    technical: technical-step     # "technical"을 고르면 technical-step으로
    other: FAIL                   # "other"를 고르면 그냥 실패로 종료
```

`onSuccess`/`onFailure`는 아예 안 씁니다. ROUTER는 성공/실패를 판정하는 게 아니라 **"어디로 갈지 고르는" 스텝**이라서요.

**2. Agent(`inquiry-classifier-agent`)의 prompt가 "무슨 이름표를 쓸 수 있는지" 알려줘야 합니다**

```yaml
agent:
  name: inquiry-classifier-agent
  prompt: |
    사용자 문의를 읽고 다음 중 하나로 분류하라: billing(결제 관련), technical(기술 지원), other(그 외).
```

여기서 "billing"/"technical"/"other"라는 문자열이 YAML의 `routes` 키와 **정확히 일치**해야 합니다. 이건 코드가 강제해주지 못해요 — prompt를 쓰는 사람이 책임져야 하는 부분입니다.

**3. LLM은 자유 텍스트가 아니라 `RouteDecision(route, reason)`이라는 정해진 모양으로만 답합니다**

`AgentStepRunner.runRouter()`가 `agentExecutor.callForEntity(..., RouteDecision.class)`를 호출하는데, 이건 SUPERVISOR가 "통과/실패"를 자유 텍스트가 아니라 `Verdict(pass, reason)`라는 고정된 JSON 모양으로 받는 것과 완전히 같은 원리입니다. Spring AI가 "이런 모양으로 답해라"는 스키마를 자동으로 프롬프트에 끼워 넣고, 응답을 그 모양대로 파싱해줍니다. 그래서 LLM이 "음... 아마 결제 문제 같습니다" 같은 애매한 텍스트를 내놓을 여지가 없어요 — `route` 필드에 문자열 하나, `reason` 필드에 이유 하나, 이렇게만 나옵니다.

## 실행 흐름 (예시로)

1. `classify` 스텝 실행 → LLM이 문의를 보고 `RouteDecision(route="billing", reason="환불 요청 언급")`을 반환
2. `WorkFlowExecutor`가 `routes` 맵에서 `"billing"`을 찾음 → `billing-step`이 나옴
3. 다음 스텝으로 `billing-step`이 실행됨

만약 LLM이 `routes`에 없는 이름(오타를 냈거나, 엉뚱한 답을 지어냈거나)을 골랐다면? **그 자리에서 Workflow가 바로 실패로 끝납니다.** 애매하게 아무 데로나 흘러가지 않고, "route['delivery']가 routes에 정의되어 있지 않습니다" 같은 명확한 에러로 멈춥니다 — 조용히 잘못된 곳으로 가는 것보다 훨씬 안전한 실패 방식이에요.

## 알아두면 좋은 제약 2가지

- **병렬(`parallelGroup`)이나 반복(`forEachVariable`)과는 같이 못 씁니다.** 여러 개가 동시에 도는 상황에서 "누구의 route를 따라야 하는지"가 모호해지기 때문에 아예 막아놨어요. 이건 YAML을 잘못 쓰면 서버가 뜰 때(`WorkFlowRegistry`) 바로 에러로 알려줍니다 — 실행해보고 나서야 이상하게 동작하는 일이 없게요.
- **`routes`는 최소 1개는 있어야 합니다.** 갈 곳이 하나도 없는 ROUTER는 의미가 없으니 이것도 서버 기동 시점에 검증합니다.

정리하면: **ROUTER = "LLM이 정해진 이름표 중 하나를 고르고, 그 이름표가 곧 다음 스텝 주소가 되는" 다지선다 분기**입니다. SUPERVISOR가 "예/아니오"만 판정한다면, ROUTER는 "이 중에 뭐야?"를 판정한다고 보시면 됩니다.

## 핵심 비유: "재료 몇 개가 들어올지 모르는 붕어빵 틀"

`forEachVariable`이 없던 예전 방식(`parallelGroup`)은 "오늘 붕어빵 3개 구울 거야"를 **틀을 만들 때(=YAML 작성할 때)** 이미 정해놔야 했어요. 틀이 3개면 딱 3개만 구울 수 있고, 4개 굽고 싶으면 틀을 하나 더 만들어야(=YAML에 step을 하나 더 추가) 합니다.

`forEachVariable`은 틀은 하나만 만들어두고, **"오늘 재료가 몇 개 들어오든 그 개수만큼 알아서 구워라"**는 뜻이에요. 재료 개수는 Workflow가 실제로 실행되는 순간에야 알 수 있습니다(YAML 작성 시점엔 모름).

## 구체적인 예로 걸어가 볼게요

"고객 리뷰 여러 개를 각각 요약해달라"는 Workflow가 있다고 해봅시다. 리뷰 개수는 그날그날 다릅니다.

**호출할 때 이렇게 데이터를 넘깁니다:**
```json
POST /api/ai/workflow/review-summarizer/execute
{
  "variables": {
    "reviews": ["배송이 너무 늦었어요", "품질은 좋은데 포장이 별로", "완전 만족합니다!"]
  }
}
```
오늘은 3개지만, 내일은 리뷰가 10개일 수도 있죠. YAML을 쓰는 시점엔 이 개수를 알 방법이 없습니다.

**YAML은 이렇게 딱 한 번만 씁니다:**
```yaml
- id: summarize-review
  type: AGENT
  ref: review-summary-agent
  forEachVariable: reviews   # variables 안의 "reviews"라는 List를 찾아서
  itemVariable: review       # 그 안의 항목 하나하나를 {review}라는 이름으로 씀
  onSuccess: report
```

**실행되면 이런 일이 벌어집니다:**
- `variables.reviews`를 보니 항목이 3개 → `summarize-review` 스텝을 **3번, 동시에** 실행
  - 1번째: `{review}` = "배송이 너무 늦었어요"
  - 2번째: `{review}` = "품질은 좋은데 포장이 별로"
  - 3번째: `{review}` = "완전 만족합니다!"
- 각자 독립적으로 `review-summary-agent`를 불러서 자기 리뷰만 보고 요약을 만듦
- 3개가 다 끝나면 `summarize-review.results`라는 변수에 요약 3개가 배열로 모여서, 다음 `report` 스텝이 그걸 받아 씁니다

만약 리뷰가 10개로 늘어나도 **YAML은 한 글자도 안 바꿔도 됩니다** — 그냥 알아서 10번 동시에 돕니다.

## parallelGroup과 비교하면

| | parallelGroup | forEachVariable |
|---|---|---|
| 몇 번 실행할지 | YAML 작성할 때 스텝 개수로 고정(예: step 3개 적으면 3번) | 실행할 때 List 길이로 결정 (매번 다를 수 있음) |
| 각 실행이 부르는 대상 | 서로 다른 step(다른 tool/agent도 가능) | 같은 step 하나를 데이터만 바꿔서 반복 |
| 리뷰 10개로 늘면 | YAML에 step 7개 더 추가해야 함 | 아무것도 안 고쳐도 됨 |

이제 감이 좀 잡히셨을까요? 이 그림이 이해되면, 아까 여쭤봤던 "합칠까요?" 질문(같은 step 반복하는 건 forEach로, 서로 다른 step 동시 실행하는 건 못함)을 다시 판단하기 쉬워질 것 같아요.
