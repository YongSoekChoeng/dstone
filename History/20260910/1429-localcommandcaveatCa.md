## 답변

조사한 결과를 바탕으로 계획을 검토했습니다. 구조 자체는 방향이 맞지만, 실제 구현 전에 짚어야 할 지점이 몇 개 있습니다.

## 백엔드

**1. 패키지 구조가 기존 컨벤션과 다릅니다**
현재 dstone-boot는 `net.dstone.boot.controller` / `net.dstone.boot.service`처럼 계층별 flat 패키지를 쓰지 않고, `analyzer.controller`/`analyzer.service`, `sample.user.controller`/`sample.user.service`처럼 **기능 단위로 패키지를 묶는** 컨벤션입니다. AI 연동도 하나의 독립 기능(analyzer와 가장 유사한 성격)이므로 `net.dstone.boot.ai.controller`, `net.dstone.boot.ai.service`(필요시 `.vo`)로 묶는 게 기존 코드와 일관됩니다.

**2. `BaseService.getRestTemplate()` 선택은 적절하나, 스트리밍과는 안 맞습니다**
`RestFulUtil.getRestTemplate()`은 `RestTemplate` 기반이라 응답을 통으로 받은 뒤 반환합니다. 그런데 dstone-ai-engine의 `POST /api/ai/chat`(`ChatController.java`)은 애초에 `spec.user(...).call().content()`로 **스트리밍이 아닌 완전응답 API**입니다. "Ollama Web UI Lite"류 UI의 핵심 특징이 토큰 단위 스트리밍인데, 지금 엔진 쪽에 스트리밍 엔드포인트가 없어서 RestTemplate로 그대로 연동해도 어차피 스트리밍은 안 됩니다. 즉 두 가지 선택지가 있습니다:
   - (a) 지금 범위는 "로딩 스피너 → 완성된 답변 한 번에 표시"로 가고 스트리밍은 다음 단계로 미룬다 → 계획하신 RestTemplate 방식 그대로 가능.
   - (b) 진짜 토큰 스트리밍 UX를 원한다 → dstone-ai-engine에 `chatClient.stream()` 기반 SSE 엔드포인트를 먼저 추가해야 하고, dstone-boot 쪽도 RestTemplate이 아니라 `WebClient`(리액티브) 또는 SSE 프록시가 필요합니다. `BaseService.getRestTemplate()` 패턴으로는 커버가 안 됩니다.

**3. 대화(sessionId) 연속성 처리가 계획에서 빠져 있습니다**
`ChatController`는 `HttpSession`에 `sessionId`가 있으면 그걸 쓰고, 없으면 요청의 `sessionId`, 그것도 없으면 새로 UUID를 발급합니다. dstone-boot → dstone-ai-engine 호출은 서버-서버 RestTemplate 호출이라 **쿠키가 전달되지 않으므로**, ai-engine 쪽 HttpSession은 사실상 매번 비어있는 새 세션입니다. 결국 멀티턴 대화가 이어지려면 **dstone-boot의 서비스 계층이 최초 응답의 `sessionId`를 (로그인 세션이든 별도 대화 테이블이든) 직접 보관했다가 다음 요청마다 명시적으로 실어 보내야** 합니다. 이 부분을 처음부터 설계에 넣지 않으면 "매 메시지가 새 대화로 취급되는" 버그로 나타납니다.

**4. ai-engine 주소를 하드코딩하면 안 됩니다**
dstone-boot와 dstone-ai-engine은 같은 kind 클러스터, 같은 네임스페이스(`dstone`)의 Pod이므로 클러스터 내부에서는 `http://dstone-ai-engine:8081`(k8s Service DNS)로 접근해야 합니다. `localhost`는 안 됩니다(같은 Pod이 아니라서). 기존 `DB_HOST`/`REDIS_HOST`처럼 `env.properties` + `application.yml`의 `${AI_ENGINE_HOST}:${AI_ENGINE_PORT}` 패턴으로 외부화하는 걸 권합니다. 지금 `interface:` 블록(naver/kakao/google)은 전부 외부 공개 URL이라 구조가 다르니 그대로 재사용하기보다 datasource류처럼 env 변수 기반으로 가는 게 맞습니다.

**5. 보안 설정은 크게 걸릴 게 없습니다**
`ConfigSecurity`가 CSRF를 전역 disable(`http.csrf(csrf -> csrf.disable())`, `ConfigSecurity.java:93`) 해뒀고, 동적 URL 권한체크는 로그인 세션 유무만 보므로 새 URL(`/ai/**.do`, `/views/ai/**`)은 로그인 필요 화면으로 자연스럽게 들어갑니다. 별도 permitAll 등록은 필요 없습니다(로그인 없이 열 게 아니라면).

## 프론트엔드

`src/main/webapp/WEB-INF/views/ai` 위치는 기존 `views/analyzer`, `views/sample/*` 컨벤션과 맞아서 문제없습니다. 다만 범위를 먼저 정해야 합니다: 지금 ai-engine이 제공하는 옵션은 `message/sessionId/promptName/ragEnabled/toolsEnabled/requiredTool`인데, RAG는 `dstone.ai.rag.enabled`가 꺼져 있으면(현재 기본값) 쓸 수 없고, Tool은 항상 켜져 있습니다(Phase 3, 샘플 Tool만 등록됨). "Ollama Web UI Lite 스타일"이 문서 업로드/RAG 토글까지 포함하는 풀 UI를 의미하는지, 아니면 1단계로 메시지 입출력 채팅창만 먼저 만드는 건지에 따라 화면 구성이 꽤 달라집니다.

스트리밍 여부를 먼저 정하는 게 나머지(백엔드 REST 클라이언트 선택, 프론트 렌더링 방식) 설계를 좌우하는 핵심 갈림길이라 먼저 확인하고 싶습니다.

## 답변

좋습니다, 답변 다 확인했고 헷갈려하신 부분(RAG/Tool 옵션 얘기)은 "메시지 채팅창만" 선택으로 해소됐습니다 — 요약하면 dstone-ai-engine의 `/api/ai/chat`은 `message` 외에도 `ragEnabled`(문서검색 증강), `toolsEnabled`(도구호출) 같은 옵션이 있는데, 이번 1차 범위에서는 그 옵션들을 아예 안 쓰고 `message`/`sessionId`만 보내면 됩니다. 그 옵션들은 무시하면 되는 것이라 더 신경 안 쓰셔도 됩니다.

추가로 확인해보니 `net.dstone.common.biz.BaseController`에 이미 `/views/{a}/{b}` 범용 매핑이 있어서(`view2()` 메서드), 화면 오픈용 액션을 따로 만들 필요 없이 `/views/ai/chat`으로 요청하면 자동으로 `ai/chat.jsp`가 뜹니다. 그리고 `dstone-common`의 `WcUtil`은 지금 `TestBean.java`(샘플) 외엔 실사용처가 없어서(OAuth 로그인들은 안 씀) WebClient로 리팩터링해도 영향 범위가 작습니다. `spring-boot-starter-webflux`도 이미 dstone-common pom에 "RestTemplate 대신 WebClient 사용 목적"이라는 주석과 함께 들어가 있어 의존성 추가도 필요 없습니다.

최종 계획을 정리하면 다음과 같습니다.

## 백엔드

**dstone-common**
- `net.dstone.common.utils.WcUtil` — 기존 `Bean`/`execute()` API는 그대로 두고(하위 호환), `getInstance()` 싱글톤 + `getWebClient()`(reactor-netty 기반 `WebClient`, `RestFulUtil`과 동일한 커넥션타임아웃/응답타임아웃 값 적용)를 추가.
- `net.dstone.common.biz.BaseService` — `protected WebClient getWebClient() { return WcUtil.getInstance().getWebClient(); }` 추가.

**dstone-boot**
- `net.dstone.boot.ai.vo` — `AiChatRequestVo`/`AiChatResponseVo` (ai-engine의 `ChatRequest`/`ChatResponse` record와 JSON shape만 맞춘 자체 VO, 모듈 간 클래스 의존 없이 REST 계약으로만 연동).
- `net.dstone.boot.ai.service.AiChatService extends net.dstone.boot.common.biz.BaseService`
  - `HttpSession`의 `SessionListener.USER_LOGIN_SESSION_KEY` → `CustomUserDetails.getUsername()`을 `sessionId`로 사용(로그인 사용자당 대화 하나가 계속 이어짐).
  - `getWebClient().post().uri(...).bodyValue(...).retrieve().bodyToMono(AiChatResponseVo.class).block()`로 ai-engine `/api/ai/chat` 호출. (서블릿 스레드에서 `.block()` — 지금 단계는 리액티브 컨트롤러로 안 바꾸고 HTTP 클라이언트만 WebClient로 교체하는 것. 나중에 스트리밍으로 갈 때 컨트롤러까지 바꾸면 됨.)
- `net.dstone.boot.ai.controller.AiChatController extends net.dstone.boot.common.biz.BaseController`
  - `/ai/chat/sendMessage.do` (AJAX POST, jsonView) 하나만. 화면 오픈은 `/views/ai/chat` 범용 매핑으로 커버.
- `env.properties`: `AI_ENGINE_HOST`, `AI_ENGINE_PORT` 추가.
- `application.yml` (로컬 conf 및 `k8s/configmap.yaml` 양쪽): `interface.ai-engine.base-url: http://${AI_ENGINE_HOST}:${AI_ENGINE_PORT}` 형태로 추가. 로컬 실행은 `localhost:8081`, k8s는 `dstone-ai-engine:8081`(같은 네임스페이스 Service DNS)로 값만 다르게.
- `ConfigSecurity` 변경 없음(로그인 필요 화면으로 자연 편입, CSRF 이미 disable).

## 프론트엔드
- `src/main/webapp/WEB-INF/views/ai/chat.jsp` — 메시지 입력창 + 대화 리스트만 있는 단일 채팅창(사이드바 대화목록/RAG업로드/Tool토글 없음), `common/header.jsp`/`top.jsp`/`left.jsp` 레이아웃 재사용.
- `common/left.jsp`에 메뉴 항목 추가.
- 채팅 JS(`assets/js` 또는 `ai` 전용 정적 경로) — `sendMessage.do`로 AJAX POST, 응답 오면 리스트에 추가. 스트리밍이 아니므로 전송 중 로딩 인디케이터만 표시.

이대로 구현 시작할까요?

맞습니다, 정정합니다. `dstone-ai-engine/conf/application.yml:160` 확인해보니 `dstone.ai.rag.enabled: true`이고 Postgres(pgvector)/Ollama(bge-m3) 설정까지 실제로 다 붙어 있는 상태입니다. 이전에 제가 "RAG는 기본 꺼짐"이라고 한 건 CLAUDE.md 문서의 일반 설명만 보고 이 환경의 실제 conf를 확인 안 한 채 말씀드린 틀린 전제였습니다.

그러면 `ragEnabled`, `toolsEnabled` 둘 다 지금 바로 동작하는 옵션이 맞고, 체크박스로 노출하는 게 자연스럽습니다. 두 옵션 성격은 이렇습니다:

- **`toolsEnabled`**: 켜면 LLM이 필요할 때 스스로 Tool을 호출(`tool_choice=auto`). 지금은 샘플 Tool(`DateTimeTools.getCurrentDateTime`, RAG가 켜져 있으니 `RetrievalTools.searchKnowledgeBase`도 자동 등록됨) 2개가 붙어있는 상태.
- **`ragEnabled`**: 켜면 질문마다 무조건 먼저 벡터DB를 검색해서 컨텍스트로 끼워 넣음(`QuestionAnswerAdvisor`). 다만 이건 검색 대상 문서가 pgvector에 **적재되어 있어야** 의미가 있는데, 문서 적재는 `ChatController`가 아니라 별도 `RagController`(`POST /api/ai/rag/documents` 멀티파트 업로드)를 통해서만 가능합니다. 체크박스 자체는 지금 넣어도 되지만, 문서 업로드 화면이 없으면 검색할 게 없어 사실상 빈 컨텍스트로 동작합니다.

지금 pgvector에 이미 적재된 문서가 있는지는 확인 안 해봤습니다.

## 수정된 최종 계획

**백엔드 패키지** (analyzer와 동일한 기능단위 구조)
- `net.dstone.boot.ai.controller.ChatController` — `@RequestMapping("/ai/chat/*")` → `/ai/chat/sendMessage.do`
- `net.dstone.boot.ai.controller.DocumentController` — `@RequestMapping("/ai/document/*")` → `/ai/document/uploadDocument.do`(멀티파트), `/ai/document/deleteDocument.do`
- `net.dstone.boot.ai.service.ChatService`, `net.dstone.boot.ai.service.DocumentService` (둘 다 `BaseService.getWebClient()`로 ai-engine 연동)
- `net.dstone.boot.ai.vo.*` (필요한 만큼)
- (WcUtil/BaseService WebClient 추가, env.properties/application.yml AI_ENGINE_HOST·PORT 등 이전에 합의된 백엔드 항목은 그대로 유지)

**프론트엔드 — AI 전용 메뉴세트**
- `views/ai/index.jsp` — AI 메인(허브) 페이지. 컨트롤러 없이 `BaseController`의 `/views/{a}/{b}` 범용매핑으로 커버.
- `views/ai/chat/chat.jsp` — 채팅창(message/ragEnabled/toolsEnabled 체크박스)
- `views/ai/document/document.jsp` — 문서 업로드 화면
- `views/ai/common/{head,header,footer}.jsp` — analyzer처럼 자체 레이아웃. header의 nav에 메인/채팅/문서업로드 3개 항목(향후 기능 추가 시 여기 탭만 늘리면 됨).
- `webapp/ai/assets/{js,css}` — 자체 정적자원 트리(공용 assets 재사용 안 함).
- 메인 앱 `common/left.jsp`에는 진입점 링크 1개만 추가: `AI` → `/views/ai/index`.

**막히는 지점 하나**: `문서업로드` 화면에서 "지금까지 적재된 문서 목록"을 보여주려고 하는데, dstone-ai-engine의 `RagController`엔 업로드(POST)/삭제(DELETE)/검색(POST)만 있고 **적재된 sourceId 목록을 조회하는 API가 없습니다.** 그래서 두 가지 중 골라야 합니다:
1. **목록 없이 최소구성** — 업로드 폼(sourceId 직접 입력) + 삭제 폼(sourceId 직접 입력)만. 지금 뭐가 올라가 있는지는 화면에서 안 보임.
2. **dstone-boot에 자체 메타데이터 테이블 추가**(dstone-batchadmin이 `TB_BATCH_JOB`으로 배치서버의 실제 Job과 별개로 메타정보를 자체 관리하는 것과 같은 패턴) — 업로드할 때마다 `TB_AI_DOCUMENT`류 테이블에 sourceId/파일명/업로드일시를 기록해서 목록 그리드를 보여줌. 다만 이 테이블은 pgvector의 실제 적재 상태와 별개로 관리되는 것이라(싱크가 안 맞을 수 있음), 그 점 감안해야 합니다.
