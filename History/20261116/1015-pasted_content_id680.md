## 지금 화면이 어수선해 보이는 이유

1. **표 순서가 사용자의 질문이 아니라 응답 JSON 구조를 따릅니다.**
   지금 순서는 `relations.*` → `semantic.*` → `files.*` → `declarations.*` → `passes` → `rag.*` → `jobs`입니다. 사용자가 실제로 묻는 것은 "써도 되나?", "왜 안 이어졌나?", "무엇이 잡혔나?", "어떻게 돌았나?" 정도인데, 표 18개가 같은 무게로 한 줄에 늘어서 있습니다.
2. **같은 내용이 여러 곳에 나옵니다.**
   - 임베딩: 맨 위 `임베딩 현황` 패널, "한눈에 보기"의 임베딩 줄, 맨 아래 `임베딩 진행` 표까지 세 곳에 있습니다.
   - "풀지 못한 참조 살펴보기" 버튼: 한눈에 보기 바로 아래와 "풀지 못한 참조의 이유" 표 뒤에 두 번 나옵니다(`project.js:372`, `:383`).
   - 품질: `품질 지표` 표, 한눈에 보기, 적용 진단이 같은 숫자를 세 번 보여 줍니다.
   - 단계: Job 박스의 단계 진행, `단계별 진행`, `파일별 단계 결과`가 겹칩니다.
3. **작업하는 곳과 결과를 보는 곳이 한 흐름에 섞여 있습니다.** 등록 폼, 분석 시작 폼, 리비전 목록, 요약, 조사 패널이 모두 세로로 이어집니다.
4. **진단용 표가 앞에 그대로 나와 있습니다.** 인코딩, 소스 루트, 문법 수준, 자동 생성 멤버의 출처는 문제가 생겼을 때만 볼 표인데, 품질 지표와 같은 높이에 있습니다.

## 2. 미사용 분석 설계안

### 대상과 판정 기준

| 대상 | 판정 기준 | "존재한다"는 근거 |
|---|---|---|
| **테이블** | DDL·사전·DB에는 있는데, 어떤 SQL도 읽거나 쓰지 않음(`READS_TABLE`·`WRITES_TABLE` 없음) | DB 메타데이터(설정했을 때) > DDL 파일 > 테이블 사전 CSV. 셋 다 없으면 "판단할 근거 없음"으로 표시 |
| **SQL statement** | 매퍼에 있는데 어떤 메소드도 실행하지 않음(`EXECUTES_SQL` 없음) | `analysis_mapper` |
| **클래스** | 들어오는 관계(호출, 주입, 상속·구현, 타입 사용, new)가 없고 진입점도 아님 | `analysis_symbol` |
| **메소드** | 부르는 곳이 없고, 진입점도 아니고, 바깥(프레임워크) 메소드를 재정의한 것도 아님 | `analysis_method` |
| **화면 (JSP 등)** | 어디서도 열거나 포함하지 않고(`RENDERS`·`REQUESTS`·`INCLUDES` 없음) 메뉴에도 없음 | `analysis_file` |

### 꼭 넣어야 할 장치: 신뢰도
정적 분석에서 "안 쓴다"는 판정은 틀리기 쉽습니다. 리플렉션, XML에 적힌 빈, 이름을 계산해서 부르는 SQL, 그리고 **풀지 못한 참조** 때문입니다. 그래서 목록마다 판정 등급을 붙이자고 제안합니다.
- **미사용 확실**: 들어오는 참조가 없고, 같은 이름을 노린 못 푼 참조도 없음
- **미사용 추정**: 못 푼 참조 중에 이 이름을 노린 것이 있음 → 실제로는 쓰일 수 있음
- **사용 중으로 침**: Spring 빈 XML, `web.xml`, 규칙 파일의 진입점에 적힌 클래스, `main()`, 직렬화 메소드 등

호출률이 낮은 리비전이면 개요에 "호출률이 80% 아래라 미사용 판정을 믿기 어렵습니다" 같은 경고를 함께 띄웁니다.

### 화면
- **개요 탭**: 카드 한 장, 예: `미사용  테이블 12 · SQL 40 · 클래스 31`
- **미사용 탭**:
  - 위쪽에 대상별 숫자 카드 5개(확실/추정을 나눠 표시). 카드를 누르면 아래에 목록이 열림
  - 목록 열: 이름, 한글명/기능명(이미 있는 사전 활용), 위치(파일:줄), 판정 등급, 근거
  - 행을 누르면 노드 맵 상세로 이동하고, 목록은 CSV로 내려받을 수 있음
- **계산 위치**: Java를 다시 파싱하지 않고 `analysis_*` 테이블에서 SQL로 구합니다(dstone-knowledge 규칙). 새 Pass 없이 조회 API(`/api/revisions/{id}/unused/...`)로 만들 수 있어, 예전 리비전에도 바로 적용됩니다.

### 정해 주실 것: "미사용"의 범위
- **A. 직접 참조가 0인 것만** (권장, 1차) — 이유를 한 줄로 설명할 수 있고 오판도 적습니다.
- **B. 진입점에서 닿지 않는 것 전부** — 죽은 코드끼리만 서로 부르는 덩어리까지 잡아서 더 강력합니다. 대신 진입점을 하나라도 놓치면 멀쩡한 코드가 대량으로 "미사용"이 됩니다.

A로 먼저 만들고, B는 미사용 탭 안의 "진입점에서 닿지 않음" 보기로 나중에 덧붙이는 순서를 권합니다.
