## 답변

맞습니다. 확인해보니 실제 동작에는 문제가 없지만, 관찰하신 내용은 정확합니다.

**`dstone-ai-engine/conf/application.yml`**의 168~171번 줄을 보면:

```yaml
# tool:
#     allowed-by-caller:
#         - caller: sample-si-project
#           tools: getCurrentDateTime,validateSqlSyntax
```

`dstone.ai.tool.allowed-by-caller`는 실제 값으로 존재하지 않고, **주석 처리된 예시**로만 남아 있습니다.

**그런데 이게 버그는 아닙니다.** `ConfigTool.allowedToolNames()`가 참조하는 `ConfigProperty.getListProperty()`(`dstone-common`)는 키가 없을 때 예외 없이 빈 `ArrayList`를 반환하도록 되어 있습니다 (`Binder.get(env).bind(...).orElseGet(ArrayList::new)`).

그래서 흐름은:
1. `allowedToolNames(caller)` → `getListProperty("dstone.ai.tool.allowed-by-caller")` → 빈 리스트
2. 빈 리스트를 순회하지만 매칭되는 `caller` 항목이 없음
3. 루프 끝까지 못 찾고 `null` 반환 → `toolCallbackProvider(caller)`에서 "화이트리스트 없음 = 전체 허용"으로 처리

즉, `ConfigTool.java` 34번째 줄 주석에 적힌 "설정에 없는 caller는 화이트리스트가 없는 것으로 보고 등록된 Tool 전체를 허용한다"는 설계가 의도한 그대로 동작하는 상태입니다. `application.yml`의 주석은 이 policy를 실제로 켜고 싶은 SI 프로젝트가 참고할 수 있도록 형식만 남겨둔 것으로 보입니다(`ApiKeyAuthFilter`/`RateLimitFilter`의 `keys`/`overrides`도 같은 List-of-Map 컨벤션을 쓰는 걸로 봐서 일관된 패턴).

정리하면: 코드가 참조하는 프로퍼티가 실제 설정에는 없는 게 맞고, 이는 "미설정 시 전체 허용"이라는 안전한 기본값으로 설계된 것이라 문제 없습니다. 다만 원하시면 주석을 해제하는 대신 문서(`docs/09.dstone-ai-engine.md`)나 yml 주석에 "기본은 비활성화 상태(예시용)"라는 점을 좀 더 명확히 적어둘 수도 있습니다.

## 답변

# 1. dstone-ai-engine Tool 구조 분석

## 전체 흐름

```
[Tool 선언]                    [Tool 등록]                    [Tool 사용]
tools/*/XxxTools.java    →    ConfigTool                →    ① AGENT/SUPERVISOR step (LLM이 스스로 선택)
  @AiTool                     (@PostConstruct에서              AgentExecutor.buildSpec()
  @Tool 메소드                  빈 스캔 → Provider 조립)          → spec.tools(configTool.toolCallbackProvider(caller))
                                                              → Spring AI의 자체 tool-calling 루프

                                                            ② TOOL step (이름으로 직접 호출, LLM 미개입)
                                                              ToolStepRunner → ToolExecutor.call(caller, toolName, json)
                                                              → configTool.findByName(caller, toolName)
```

### ① Tool 선언 (`tools/` 패키지)
`@AiTool`(메타애노테이션 `@Component`)을 클래스에 붙이고 그 안에 Spring AI의 `@Tool` 메소드를 두면 끝. 현재 5종:
- `sample.DateTimeTools` — 등록 방식을 보여주는 샘플
- `sql.SqlSyntaxTools` — JSQLParser로 SQL 문법 검증(자기수정 루프용)
- `shell.ShellExecTool` / `python.PythonExecTool` / `http.HttpCallTool` — 기본 비활성(`dstone.ai.tool.{shell,python,http}.enabled=false`), 화이트리스트된 스크립트/호스트만 실행

### ② 등록 (`ConfigTool`)
`@PostConstruct`에서 `ApplicationContext.getBeansWithAnnotation(AiTool.class)`로 스캔 → `MethodToolCallbackProvider`로 묶어 `ToolCallbackProvider` 하나를 만듦. Spring AI는 `@Tool` 메소드를 자동으로 찾아주지 않으므로(Bean 스캔 후 명시적으로 `toolObjects(...)`에 넘겨야 함) 이 조립 자체가 필요한 배선.

### ③ caller별 화이트리스트
`dstone.ai.tool.allowed-by-caller`(현재 application.yml엔 예시로만 주석 처리, 미설정 시 전체 허용)를 조회해서 caller가 쓸 수 있는 Tool 이름만 필터링. **이 필터링이 딱 한 곳(`ConfigTool.allowedToolNames`)에만 있고**, 아래 두 소비처가 공통으로 그걸 거쳐간다.

### ④ 소비처 (2가지 경로, 둘 다 `ConfigTool`을 거침)
- **AGENT/SUPERVISOR step** (`AgentExecutor.buildSpec()` 5번) — `agent.toolsEnabled()`(또는 `ChatController`의 요청별 override)가 true면 `configTool.toolCallbackProvider(caller)`를 `ChatClient`에 붙임 → 어떤 Tool을 언제 부를지는 LLM이 Spring AI의 tool-calling 루프 안에서 판단
- **TOOL step** (`ToolStepRunner` → `ToolExecutor`) — Workflow YAML에 `ref`로 지정된 Tool 이름을 `configTool.findByName(caller, toolName)`으로 직접 찾아 LLM 없이 호출(결정적 검증용, 예: `validateSqlSyntax`)

두 경로 모두 `ConfigTool`을 통해서만 caller의 화이트리스트를 통과한 Tool에 접근하며, 그 외 클래스는 `ApplicationContext`나 원시 `ToolCallback` 목록을 직접 다루지 않는다.

# 2. `ConfigTool`이 반드시 필요한가

**필요하다.** 세 가지 근거:

1. **Spring AI의 Tool 등록은 자동이 아니다.** `@Tool` 메소드가 붙은 빈이 있어도 Spring AI가 알아서 `ChatClient`에 태워주지 않는다 — `MethodToolCallbackProvider.builder().toolObjects(...)`로 누군가는 명시적으로 조립해야 한다. `ConfigTool.discover()`가 그 배선 역할을 한다.

2. **caller별 화이트리스트는 이 엔진만의 도메인 요구사항이라 Spring AI가 대신해줄 수 없다.** `dstone-ai-engine`은 여러 SI 프로젝트가 공유하는 단일 엔진이라(CLAUDE.md에도 명시된 설계 의도), 한 앱에게만 허용된 Tool을 다른 앱이 못 쓰게 막는 로직이 필요하다. 이건 라이브러리가 아니라 이 프로젝트가 직접 구현해야 하는 부분이고, `ConfigTool`이 그 유일한 구현 지점이다.

3. **두 소비 경로(AGENT의 LLM 주도 호출 / TOOL의 이름 직접 호출)가 화이트리스트 로직을 공유해야 한다.** `ConfigTool`이 없다면 `AgentExecutor`와 `ToolExecutor`가 각자 `ApplicationContext` 스캔 + 화이트리스트 파싱을 중복 구현하거나(로직 불일치 위험), 서로 다른 규칙을 적용할 위험이 생긴다. `ToolExecutor`의 주석("모든 TOOL 호출이 반드시 여길 거치므로... governance가 감사/제한하고 싶어지면 이 클래스 하나만 감싸면 된다")과 동일한 이유로, `ConfigTool`도 "Tool 접근 정책"의 단일 지점 역할을 한다.

## 사소하게 짚을 점 (필요성 판단과는 별개)

`toolCallbackProvider()`(인자 없는 버전, 60번 줄)는 현재 코드베이스 어디서도 호출되지 않는다 — `discover()` 내부 로그도 `toolNames()`를 쓰지 `toolCallbackProvider()`를 쓰지 않는다. caller 없이 "전체 Tool 무조건 다 허용" 용도로 남겨둔 공개 API로 보이는데, 실사용처가 없다면:
- 향후 caller 개념이 없는 내부 호출용으로 의도적으로 열어둔 것인지
- 아니면 단순히 죽은 코드인지

확인이 필요하다. 지금 당장 문제는 아니지만, `docs/09.dstone-ai-engine.md`에 이 메소드의 용도가 언급돼 있는지 한번 대조해볼 만하다.

그러면 caller별 화이트리스트가 설정되지 않은 지금 같은 경우 모든 tool에 대한 권한이 허용된다는 뜻인가?

---

## 답변

네, 맞습니다. 정확히는 두 단계로 나눠서 봐야 합니다.

**1) 화이트리스트 자체가 없는 지금 상황**

`ConfigTool.allowedToolNames(caller)`가 항상 `null`을 반환합니다.
- `allowed-by-caller` 설정이 없으니 `getListProperty()`는 빈 리스트 → 루프에서 매칭되는 `caller` 항목을 못 찾음 → `null` 리턴
- `caller` 자체가 `null`인 경우(예: `dstone.ai.security.auth.enabled=false`라 인증 없이 caller가 항상 null)도 바로 `null` 리턴

그리고 `toolCallbackProvider(caller)`에서 `allowedToolNames == null`이면 필터링 없이 `this.toolCallbackProvider`(등록된 Tool 전체)를 그대로 돌려줍니다. 즉 **caller를 구분하지 않고 등록된 모든 Tool에 접근 가능**합니다.

**2) 단, "모든 Tool"의 범위에는 두 가지 조건이 걸려 있습니다**

- **어떤 Tool이 "등록된" 상태인지**는 `@AiTool` 빈이 실제로 스캔됐는지에 달려 있습니다. 현재는 `DateTimeTools`, `SqlSyntaxTools`는 항상 등록되지만, `ShellExecTool`/`PythonExecTool`/`HttpCallTool`은 각자 `dstone.ai.tool.{shell,python,http}.enabled=false`(기본값)면 애초에 `@AiTool` 빈 자체가 안 뜰 가능성이 높습니다(정확한 활성화 방식은 각 Tool 클래스 확인 필요 — `@ConditionalOnProperty` 류로 빈 등록 자체를 막고 있다면 화이트리스트와 무관하게 처음부터 Tool 목록에 없음).
- **Agent/Workflow 쪽에서 Tool 사용 자체를 켰는지**도 별도입니다. `AgentDefinition.toolsEnabled()`(또는 `ChatController`의 요청별 override)가 `false`면 화이트리스트 허용 여부와 무관하게 그 호출에는 Tool이 아예 안 붙습니다.

**요약:** 지금은 "caller별 차등"이 꺼져 있는 상태이므로, Tool 사용이 켜진 Agent/Workflow는 등록된 Tool 전체(그리고 shell/python/http처럼 자체 enabled 플래그로 빈이 떠 있다면 그것도 포함)에 접근할 수 있습니다. 여러 SI 프로젝트가 이 엔진을 공유하기 시작하는 시점에는 `dstone.ai.tool.allowed-by-caller`를 실제로 채워 넣어야 의도한 격리가 동작합니다.

## 답변

## parallelGroup 설명

`StepDefinition.parallelGroup`(문자열 필드)에 **같은 값**을 넣은 인접 step들을, `WorkflowExecutor`가 동시에 실행해주는 기능입니다. "순차/분기/병렬/루프 4패턴" 중 병렬 담당입니다.

**동작 방식** (`WorkflowExecutor.java`):

1. `run()`이 현재 step을 실행하기 전에 `parallelGroupOf(steps, step)`을 호출해서, 같은 `parallelGroup` 값을 가진 step들을 전체 목록에서 모읍니다(79번 줄). `parallelGroup`이 비어있으면 자기 자신 하나만 담긴 목록을 돌려줘 기존 순차 실행과 동일하게 동작합니다.
2. 그룹 크기가 2개 이상이면 `runParallel()`(171번 줄)이 각 step을 `CompletableFuture.supplyAsync(...)`로 동시에 던지고 `CompletableFuture.allOf(...).join()`으로 전부 끝날 때까지 기다립니다.
3. 결과는 각 step의 `outcome.text()`를 개행으로 이어붙인 하나의 문자열로 합치고, 하나라도 실패하면 전체를 실패(`allSuccess=false`)로 취급합니다.
4. 다음 step 결정은 **그룹의 마지막 step 기준**으로 합니다(83번 줄 주석) — 즉 그룹 내 각 step이 각자 `onSuccess`/`onFailure`를 가져도, 실제 분기 판단은 YAML상 그룹의 마지막 step에 적힌 값만 쓰입니다. 그룹 중간 step들의 `onSuccess`/`onFailure`는 사실상 무시됩니다(주의할 부분).

`CompletableFuture.supplyAsync`는 기본 `ForkJoinPool.commonPool()`을 씁니다 — 별도 전용 스레드풀을 구성하지 않았습니다.

## 테스트 환경 여부

맞습니다, **지금은 실제로 검증해볼 수 있는 환경이 아닙니다.**

- `src/main/resources/workflows/` 안에는 `oracle-to-postgresql.yml` 하나뿐이고, 이건 `analyze → convert → validate → (실패시 fix 루프)`로 **순수 순차 + 루프** 패턴만 씁니다. `parallelGroup`을 쓰는 Workflow YAML이 프로젝트 전체에 하나도 없습니다.
- CLAUDE.md에 기록된 "2026-09-15 live-verification"도 이 순차 Workflow 하나만 sync/async로 검증한 기록이고, 병렬 분기는 실행해본 적이 없습니다.
- `src/test/` 디렉터리 자체가 없습니다(`spring-boot-starter-test` 의존성은 pom.xml에 있지만 실제 테스트 코드가 전무). 즉 JUnit으로 `WorkflowExecutor.runParallel()`을 단위 테스트할 장치도 없는 상태입니다.

**실제로 테스트하려면** 다음이 필요합니다:
1. `parallelGroup`이 같은 값을 가진 step 2개 이상을 포함한 Workflow YAML 하나 새로 작성 (TOOL step끼리 묶으면 LLM 호출 비용/네트워크 의존 없이 로컬에서 바로 검증 가능 — 예: `validateSqlSyntax`를 서로 다른 입력으로 두 번 부르는 임시 Workflow)
2. `WorkflowController`의 `/execute` 또는 `/submit`+`/status`로 실제 호출해보거나, `src/test/java`를 새로 만들어 `WorkflowExecutor`를 직접 단위 테스트
3. AGENT step을 포함해서 병렬 검증하고 싶다면 Anthropic API 키와 실제 호출 비용이 필요(TOOL만으로는 LLM 개입 없는 병렬 실행 자체는 검증 가능하지만, "AGENT 두 개가 진짜 동시에 LLM 호출하는지"까지 보려면 API 호출이 필요)

원하시면 최소한의 검증용 테스트 Workflow YAML(TOOL 2개를 parallelGroup으로 묶은)을 하나 만들어서 로컬에서 바로 돌려볼 수 있는 형태로 준비해드릴 수 있습니다.

**3. 테스트 방법**

dstone-ai-engine을 재기동한 뒤, dstone-boot 화면에서:
- `workflowId`: `parallel-test`

## 근거

`result`는 `this.call(...)` → `AgentExecutor.call(...)` → `ChatClient` 응답 텍스트를 그대로 반환받은 값입니다. `ConfigTool`의 `Tool`처럼 Java 코드가 반환값의 형식을 통제하는 게 아니라, **LLM이 생성한 자연어 텍스트**입니다. `StepType.SUPERVISOR`의 자바독에도 이미 이렇게 명시돼 있습니다:

> "...Agent의 프롬프트 자체가 '통과: .../실패: 이유' 형식으로 답하도록 작성돼 있어야 한다(**강제 장치는 없다** - 프롬프트 설계 컨벤션이다)."

즉 설계자도 이게 "약속"이지 "보장"이 아니라는 걸 알고 그렇게 남겨둔 상태입니다.

## `TOOL` step과 비교하면 왜 더 위험한지

같은 `startsWith(FAILURE_PREFIX)` 패턴을 `ToolStepRunner`도 씁니다만, 그쪽은 `SqlSyntaxTools.validateSqlSyntax()`처럼 **자바 코드가 직접** `"통과: ..."`/`"실패: ..."` 중 하나만 리턴하도록 결정론적으로 작성돼 있어서 실제로 보장됩니다. 반면 `SUPERVISOR`의 `result`는 그 보장 장치가 없는 LLM 응답이라, 지난번 fix-agent에서 봤던 것과 **완전히 같은 종류의 문제**가 여기서도 똑같이 재현될 수 있습니다:

- LLM이 "실패:" 대신 "오류:", "불가:", 혹은 자연어 설명으로 시작하면 → `startsWith("실패")`가 `false` → **실패인데 성공으로 오판**
- 코드펜스나 개행이 앞에 붙으면(예: ` ```\n실패: ...`) → 역시 `startsWith` 불일치로 성공 오판
- "실패"라는 단어가 응답 중간에는 나오지만 맨 앞이 아니면 → 역시 성공 오판

## 더 근본적인 문제: fail-open 구조

지금 로직은 `startsWith(FAILURE_PREFIX)`가 아니면 전부 성공으로 취급하는 **fail-open**(애매하면 통과) 구조입니다. `TOOL` step은 결정론적 코드라 fail-open이어도 안전하지만, `SUPERVISOR`는 LLM 텍스트를 그대로 fail-open으로 판정하기 때문에, 컨벤션에서 조금만 벗어나도 "감독이 실패라고 판단했는데 Workflow는 성공으로 알고 다음 단계로 넘어가는" 조용한 오작동이 생길 수 있습니다.

다만 참고로, 현재 `resources/agents/*.yml`/`resources/workflows/*.yml` 어디에도 `SUPERVISOR` 타입을 실제로 쓰는 정의가 없습니다(코드/enum에만 존재, 실사용 사례 없음) — 그래서 아직 실제 장애로 터진 적은 없고, 잠재적 위험 상태입니다.

## 고칠 방향 (원하시면 진행하겠습니다)

- **fail-closed로 전환**: `"통과"`로 시작할 때만 성공, 그 외(빈 문자열, "실패", 그 어떤 형식 이탈이든)는 전부 실패로 처리 — 애매한 응답을 안전한 쪽(실패)으로 처리
- **방어적 트리밍**: 판정 전에 코드펜스/선행 공백을 벗겨내기(지난번 TOOL step 이슈와 동일한 종류의 방어)
- 근본적으로는 SUPERVISOR가 실사용되기 시작할 때, 프롬프트 쪽에도 "정확히 이 형식으로만 답하라"는 규칙을 명시해야 하지만, 그것만으론 이번 대화에서 봤듯 100% 신뢰할 수 없으므로 코드 쪽 방어가 같이 필요합니다.

Spring AI 로 워크플로우 와 에이전트 작성중에 서브 에이전트를 여러개 수행 시키는 부분이 있는데 각 에이전트들이 LLM을 호출해.  그런데 개별적인 에이전트의 작업이 성공했는지 실패했는지를 판단하기 위한 기준이 LLM 호출이라 확정적(강제적)이지않아. 좋은 방법이 없을까? 필요하다면 공통적인 시스템 프롬프트를 적용하고 싶은데... 물론 이게 확정적이지는 않지만 이거라도 한다면 좋은 문구가 뭘까?

---

## 답변

좋은 질문입니다. 결론부터 말하면, **텍스트 접두사 컨벤션은 근본적으로 확정적일 수 없고**, 프롬프트 문구는 그 신뢰도를 올려주는 보조 수단이지 해결책은 아닙니다. 신뢰도 순으로 옵션을 정리하면:

## 방법 (신뢰도 순)

1. **구조화 출력(Structured Output)** — Spring AI `ChatClient`의 `.call().entity(SomeRecord.class)`를 씀. `record Verdict(boolean pass, String reason)` 같은 타입을 주면 Spring AI가 JSON 스키마 지시문을 자동으로 프롬프트에 삽입하고 응답을 그 타입으로 파싱해줍니다. `boolean`이라 `startsWith("통과")` 같은 문자열 매칭 자체가 아예 없어지는 게 핵심 — "통과"/"실패" 사이의 오타, 코드펜스, 접두사 위치 이탈 같은 문제 자체가 구조적으로 사라집니다. (완전히 확정적이진 않습니다 - 모델이 스키마를 어겨서 파싱 자체가 실패할 순 있지만, 그건 "판정을 잘못 내림"이 아니라 "파싱 예외"라서 코드에서 명확히 잡아낼 수 있는 실패로 바뀝니다.)
2. **강제 Tool-call(함수 호출)** — `reportVerdict(boolean pass, String reason)` 같은 `@Tool`을 만들고 마지막 턴에 그 함수를 강제로 부르게 함. 모델의 전용 함수 호출 채널을 쓰기 때문에 자유 텍스트보다 스키마 준수율이 대체로 더 높습니다.
3. **판정을 분리(LLM-as-judge 패턴)** — 작업 수행 Agent와 "이 결과가 맞는지 판정만 하는" 별도의 작은 Agent를 분리. 판정 전용 Agent는 프롬프트가 단순해서(할 일이 "판정"뿐) 구조화 출력을 적용하기 쉽고, 작업 Agent는 형식 강박 없이 본연의 일에만 집중하게 됨.
4. **지금 쓰는 텍스트 접두사 컨벤션 + 공통 시스템 프롬프트** — 가장 손이 덜 가지만 가장 약함. 그래도 안 하는 것보단 낫습니다.

이 프로젝트(`AgentExecutor.buildSpec()`이 `.call().content()`만 쓰는 구조)에 가장 잘 맞는 현실적 다음 단계는 **1번**입니다. `SUPERVISOR`처럼 판정이 목적인 step 타입에 한해 `.entity(Verdict.class)`로 바꾸는 건 큰 리팩토링 없이 `AgentExecutor`에 판정 전용 오버로드 하나 추가하는 정도로 가능합니다.

## 그래도 공통 프롬프트를 쓰고 싶다면

각 Agent 고유 프롬프트(`promptName`이 가리키는 `.st` 파일) 뒤에 공통으로 덧붙일 문구는 이런 식을 추천합니다:

```
[판정 형식 - 반드시 준수]
당신의 답변은 반드시 다음 두 접두사 중 정확히 하나로, 다른 어떤 문자보다도 먼저 시작해야 합니다:
- "통과: " 뒤에 결과나 결론
- "실패: " 뒤에 실패 사유(무엇이, 왜 문제인지 구체적으로)

1. "통과"/"실패" 외의 다른 표현(성공/완료/오류/문제없음 등)으로 시작하지 마십시오.
2. 접두사 앞에 인사말, 설명, 마크다운 코드펜스(```), 공백이나 개행을 절대 두지 마십시오 - 응답의 첫 글자부터 "통과" 또는 "실패"여야 합니다.
3. 판단이 애매하거나 확신이 없으면 "통과"가 아니라 "실패"로 답하고, 이유에 "불확실"이라고 명시하십시오.
4. "통과"/"실패" 둘 중 하나만 고르십시오 - 조건부로 답하거나 둘을 같이 쓰지 마십시오.
```

3번 규칙이 특히 중요합니다 — 지난번에 `AgentStepRunner.runSupervisor()`를 fail-closed로 바꿔둔 것과 같은 방향이라, 모델이 애매하게 답해도 "통과" 쪽으로 새지 않고 실패로 떨어지게 유도합니다.

이 문구를 실제로 어떻게 붙일지는 설계 선택이 필요합니다 — `PromptTemplateRegistry.render()`가 Agent 고유 프롬프트 뒤에 자동으로 이 공통 footer를 붙이게 할 수도 있고, `AgentExecutor.buildSpec()`에서 SUPERVISOR 타입일 때만 두 번째 `.system(...)`으로 추가할 수도 있습니다. 원하시면 1번(구조화 출력)과 이 공통 프롬프트 footer 중 어느 쪽으로 갈지 정해서 바로 구현해드릴까요?
