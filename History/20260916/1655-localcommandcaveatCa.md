## 답변

로그만으로는 원인이 안 보여서, Ollama 서버(`localhost:11434`, 이 샌드박스에서도 접근 가능했음)에 dstone-ai-engine과 똑같은 tool 정의로 직접 요청을 보내 재현해봤습니다.

## 로그 자체에 대한 판단
두 블록 모두 `START`만 찍혀있고 `END`/에러 로그가 없습니다 — 이건 로그를 여기까지만 캡처했다는 뜻이지, 요청이 중간에 실패했다는 의미는 아닙니다. `ConfigCallLog`는 진입 로그만 있어서 이 로그만으로는 tool 호출이 왜 텍스트로 새는지 알 수 없었습니다.

## 직접 재현한 결과
`sample-system` 프롬프트 + `getCurrentDateTime` tool 정의를 그대로 써서 Ollama `/api/chat`에 직접 요청(Spring AI 완전히 우회, non-stream, temperature=0까지 고정)해도 **똑같이** 재현됩니다:

```json
"message": {
    "role": "assistant",
    "content": "{\"name\": \"getCurrentDateTime\", \"arguments\": {}}"
}
```

`message.tool_calls` 필드 자체가 없습니다. → **dstone-ai-engine 코드(`AgentExecutor`/`ConfigTool`) 문제가 아닙니다.** 둘 다 Spring AI의 네이티브 `.tools(...)` API로 정상적으로 tool을 넘기고 있고, streaming 여부와도 무관하게 재현됩니다.

## 진짜 원인
`ollama show qwen2.5-coder:7b`로 템플릿을 보면:

```
For each function call, return a json object with function name and arguments within <tool_call></tool_call> with NO other text.
<tool_call>
{"name": <function-name>, "arguments": <args-json-object>}
</tool_call>
```

즉 Ollama 서버는 모델 응답에서 **`<tool_call>...</tool_call>` 태그**를 찾아 그 안의 JSON을 `tool_calls`로 파싱합니다. 그런데 실제 생성된 답은 태그 없이 순수 JSON만 나왔고, 그래서 Ollama 파서가 이걸 구조화된 tool call로 인식하지 못하고 그냥 `content` 텍스트로 흘려보낸 겁니다. temperature=0에서도 동일하게 재현되는 걸 보면 확률적 요행이 아니라, 이 7B(Q4_K_M 양자화) 모델이 형식(태그) 준수를 안정적으로 못 지키는 문제입니다.

이건 정확히 `docs/software/14.ollama.md` 2절에 이미 기록된 "llama3.2에서 tool 호출을 텍스트로 흉내만 내던" 증상과 같은 종류이고, `qwen2.5-coder:7b`로 바꿨는데도 재현된 거라 — Ollama가 `tools` capability를 표시해주는 모델이어도 quantized 소형 모델은 형식 준수가 신뢰할 수 없다는 게 재확인된 셈입니다.

## 참고로 확인한 것
- `qwen2.5-coder:7b`, `qwen2.5-coder:3b`, `llama3.2`는 `/api/tags`상 `capabilities: ["tools"]`로 표시돼 있음(태그 자체는 정상).
- streaming/non-streaming, temperature 0/기본값 모두 동일 재현 — dstone 쪽 스트리밍 처리 로직 이슈는 아님.
