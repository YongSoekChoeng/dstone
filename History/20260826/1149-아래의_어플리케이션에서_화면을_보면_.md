## 4. What `JobOperator.stop()` actually does under the hood

`jobOperator.stop(executionId)`:
1. Looks up the running `JobExecution` by id.
2. Sets its `BatchStatus` to `STOPPING` and persists it via the `JobRepository` (an UPDATE to `BATCH_JOB_EXECUTION`).
3. Returns immediately. **It does not touch the running thread, does not throw an exception into it, does not call `Thread.interrupt()`.**

For a **chunk-oriented step** (`.chunk(...)`), Spring Batch's `ChunkOrientedTasklet`/`RepeatTemplate` machinery re-checks `stepExecution.isTerminateOnly()` after every chunk commit (between `read`/`process`/`write` batches). If it's true, it throws a `JobInterruptedException`, which propagates up and flips the step/job to `STOPPED`. This is why chunk steps usually respond to stop fairly quickly (bounded by commit-interval size).

For a **plain custom `Tasklet`** (as here), there is no chunk boundary and no automatic re-check point. `TaskletStep.execute()` just calls your `tasklet.execute(contribution, chunkContext)` once and waits for it to return a `RepeatStatus`. The *only* way Spring Batch can know to stop mid-flight is if **your own code**, while it's still running, notices the STOPPING state and exits voluntarily — typically by periodically checking:

```java
if (contribution.getStepExecution().isTerminateOnly()) {
    throw new JobInterruptedException("Job stopped by user request");
}
```

inside the tasklet's loop. If the tasklet never checks this (as `TableInsertTasklet` doesn't), `JobOperator.stop()` has literally no mechanism to reach into that thread and stop it — the JobExecution just sits at `STOPPING` until the tasklet naturally finishes and returns, at which point Spring Batch notices the STOPPING flag on completion and marks the execution `STOPPED` (rather than `COMPLETED`) even though all the work already ran. This exactly matches the symptom reported.

Thread interruption (`Thread.currentThread().isInterrupted()`) is a *separate*, alternative mechanism, and it only comes into play if something actually calls `Thread.interrupt()` on the executing thread — which brings us to point 5.

## 5. TaskExecutor wiring — is anything interrupt-capable in play?

Two different executor layers exist, and neither will forcibly interrupt this tasklet's blocking loop:

- **Job-launch level**: `/app/dstone/dstone-batch/src/main/java/net/dstone/batch/common/config/ConfigJob.java:47-58` — `asyncJobLauncher` is a `TaskExecutorJobLauncher` using a `SimpleAsyncTaskExecutor` (line 53). This executor's only job is to run `Job.execute()` asynchronously on a new thread so the REST call returns immediately after starting; it has no notion of "cancel" — `SimpleAsyncTaskExecutor` doesn't track submitted `Runnable`s for later interruption, and nothing in `JobOperator.stop()` asks it to interrupt anything.
- **Step level**: as noted in point 2, the `TaskletStep` for `tableDataGenType01Job` is built with **no** `.taskExecutor(...)` at all — meaning the tasklet runs synchronously on the very same thread that `TaskExecutorJobLauncher`'s `SimpleAsyncTaskExecutor` spawned to run the whole job. Spring Batch never calls `Thread.interrupt()` on that thread as part of `stop()` processing, with or without an executor.
- Additionally, `TableInsertTasklet` creates its **own private** `ExecutorService` (`Executors.newFixedThreadPool`) for the parallel insert workers, which is entirely outside Spring's/Spring Batch's knowledge — even if Spring Batch *did* interrupt the outer step thread, that would only unblock the outer thread's `future.get()` call (throwing `InterruptedException`, which is not currently caught for that purpose), while the actual worker threads inside the private `ExecutorService` would keep running uninterrupted, since `Future.cancel(true)` is never called on them.

Net effect: there is no interrupt-based safety net anywhere in this chain. This is a fully non-cooperative Tasklet.

### 5. Root cause

**This is scenario (b), not (a).** The restart mechanism (both in `dstone-batchadmin` and `dstone-batch`) is implemented correctly — it's a genuine `JobOperator.restart(executionId)` against the same `JobInstance`/`JobExecution` chain, not a fresh `JobLauncher.run()` with a new `JobInstance`.

What actually happens on restart, step by step:
1. `jobOperator.restart(executionId)` creates a new `JobExecution` tied to the **same** `JobInstance`.
2. Spring Batch correctly determines Step 1 (`TableDeleteTasklet`'s step) was already `COMPLETED` in the prior execution, and since `allowStartIfComplete` is left at its default (`false`), Step 1 is **skipped** — the previously-inserted ~5000 rows are **not** deleted again.
3. Step 2 (`workerStep`) had status `STOPPED`, so Spring Batch correctly resumes it — but "resuming" a chunk-oriented step only restores progress if the `ItemReader` is an `ItemStream` that persisted its position into the step's `ExecutionContext`. Here, the reader is a plain `ItemReader` (no `ItemStream`), so Spring Batch has literally nothing to restore. A brand-new `@StepScope` reader bean is instantiated, `queue` is `null`, and `read()` calls `fillQueue()` which regenerates the **entire** `dataCnt` (20000) items again from `i=0`.
4. The chunk-oriented writer then inserts all 20000 "new" rows on top of the ~5000 rows already committed and left untouched from step 1 not re-running → total 25000. This matches the exact reported numbers (5000 + 20000 = 25000), which is strong confirmation of this diagnosis (if the delete tasklet had instead been re-run, the result would have been a clean 20000, not 25000 — but it correctly didn't re-run, which is precisely why the leftover 5000 stack with a fresh 20000).

**Conclusion: root cause is (b)** — the restart machinery works exactly as designed, but `TableDataGenType02JobConfig`'s anonymous `ItemReader` has zero `ExecutionContext` checkpointing, so the chunk step re-reads/re-inserts from item 1 every time it is restarted, even though Spring Batch itself correctly resumed the same `JobInstance` and correctly skipped the already-completed delete step.

### Concrete fix

Make the reader an `ItemStream` that persists/restores its progress, e.g.:

```java
    return new AbstractItemReader() {  // AbstractItemReader would need to extend ItemStreamSupport, or implement ItemStream directly
        private static final String READ_COUNT_KEY = "reader.readCount";
        private int dataCnt;
        private int currentIndex = 0;

        @Override
        public void open(ExecutionContext executionContext) {
            currentIndex = executionContext.getInt(READ_COUNT_KEY, 0);
        }

        @Override
        public void update(ExecutionContext executionContext) {
            executionContext.putInt(READ_COUNT_KEY, currentIndex);
        }

        @Override
        public Map&lt;String, Object&gt; read() {
            if (dataCnt == 0) {
                dataCnt = Integer.parseInt(this.getJobParam("dataCnt").toString());
            }
            if (currentIndex &gt;= dataCnt) {
                return null; // end of data
            }
            Map&lt;String, Object&gt; row = new HashMap&lt;&gt;();
            row.put("TEST_ID", StringUtil.filler(String.valueOf(currentIndex), 8, "0"));
            row.put("FLAG_YN", "N");
            row.put("INPUT_DT", DateUtil.getToDate("yyyyMMddHHmmss"));

            return row;
        }

```

**고치는 방법**: Reader를 `ItemStream`을 구현하도록 바꿔서, chunk 커밋마다 현재까지 읽은 개수(index)를 `ExecutionContext`에 저장(`update`)하고, restart 시 그 값을 복원(`open`)해서 `currentIndex`부터 이어서 생성하도록 하면 됩니다. 가장 깔끔한 방법은 `AbstractItemCountingItemStreamItemReader`를 상속해서 `doRead()`만 구현하는 것 — 이 클래스가 읽은 개수 기반 체크포인트 저장/복원을 이미 프레임워크 레벨에서 처리해줍니다.

- `AbstractItemReader<I>` (dstone-batch 공통 베이스)에 `ItemStreamSupport`/`ItemStream` 지원을 추가하거나, `TableDataGenType02JobConfig.itemReader()`가 `AbstractItemCountingItemStreamItemReader<Map<String,Object>>`를 직접 상속하는 새 클래스로 교체

## 요약

`/app/dstone/dstone-batch/.../job002/items/TableInsertTasklet.java`를 협조적(stop-aware) 방식으로 수정했습니다.

**변경 내용**
1. `AtomicBoolean stopRequested`를 만들어 워커 스레드들과 공유
2. 각 워커의 insert 루프에서 매 행마다 `stopRequested`를 체크 — true면 지금까지 처리한 만큼만 마지막 `flushStatements()`/`commit()`으로 커밋하고 조기 종료
3. 기존처럼 `future.get()`으로 무한 블로킹하지 않고, `Future::isDone`을 300ms 간격으로 폴링하면서 그때마다 `stepExecution.isTerminateOnly()`(= stop 요청 여부)를 체크 → 감지되면 `stopRequested`를 켜서 모든 워커에게 전파
4. 모든 워커가 끝난 뒤, `stopRequested`가 켜져 있었다면 `JobInterruptedException`을 던짐 — Spring Batch의 `AbstractStep`이 이 예외를 특별 취급해서 `BatchStatus`를 `FAILED`가 아닌 **`STOPPED`**로 정확히 반영함

**결과**: stop 명령을 보내면 최대 300ms(폴링 간격) + 진행 중이던 마지막 1행 정도의 지연 안에 실제로 작업이 멈추고, 그 시점까지 insert된 행까지만 남습니다. 더 이상 "STOPPING 상태로 계속 있다가 전체 작업이 끝나야 STOPPED로 바뀌는" 현상은 발생하지 않습니다.

Maven이 이 환경에 없어 실제 컴파일은 못 했고, import/시그니처를 손으로 재확인했습니다. 실제 배치서버에서 `mvn clean package` 후 `tableDataGenType01Job` 실행 → stop 테스트로 확인해보시길 권합니다.
