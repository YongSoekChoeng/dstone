# AI Core Engine (dstone-ai-engine) 설계 계획

## 0. 먼저 확정하고 가야 할 전제 2가지

**① 레포 편입 방식**
제안하신 모듈 구성(`dstone-common` + `dstone-ai-engine`)만 보면 기존 dstone 모노레포와 별도의 새 레포로 보이는데, 저는 **기존 dstone 모노레포의 5번째 모듈로 편입**하는 걸 추천합니다.
- 이유: `dstone-common`(보안/데이터접근/메시징 공통 유틸)을 그대로 재사용, Jenkins/K8s 배포 패턴·conf 구조·Jasypt 암호화 컨벤션을 새로 만들 필요 없음.
- 다만 향후 특정 SI사업에서 "이 엔진만 별도로 떼서 납품"해야 하는 상황이 실제로 생기면, 그때 git subtree로 분리하면 됩니다. 지금 미리 분리 레포로 시작하는 건 과설계라고 봅니다.

**② 배포 형태**
`dstone-boot`처럼 **API 서버(K8s Pod)로 배포**하되, 내부 패키지를 처음부터 "엔진 로직(provider 무관)"과 "REST API 계층"으로 분리해두는 걸 추천합니다. 트래픽/재사용 요구가 커지면 그때 `dstone-ai-core`(라이브러리) / `dstone-ai-server`(API)로 모듈만 쪼개면 되고, 초기엔 단일 모듈+패키지 분리로 충분합니다.

이 두 전제에 이견 있으시면 먼저 말씀해주시고, 없으면 이 전제로 아래 계획을 진행하겠습니다.

## 1. 설계 원칙

1. **Provider 무관(agnostic)** — OpenAI/Anthropic/Azure OpenAI/사내망 로컬모델(vLLM, Ollama) 등을 설정만 바꿔 교체 가능해야 함. SI마다 요구 LLM이 다를 걸 전제.
2. **도메인 로직 ↔ AI 인프라 로직 분리** — SI 프로젝트별 비즈니스 프롬프트/워크플로우는 확장 포인트로 빼고, 엔진 자체는 순수 "AI 인프라"만 담당.
3. **기존 dstone 컨벤션 계승** — `conf/env.properties`+`application.yml` 패턴, Jasypt `ENC(...)`로 API Key 암호화, log4j2, 필요시 MyBatis/HikariCP(대화이력·메타데이터 저장용).
4. **점진적 확장(YAGNI)** — 처음부터 Agent/MLOps 풀세트를 만들지 않고 Phase별로 늘려감.

## 2. 패키지 구조안 (`net.dstone.ai`)

```
net.dstone.ai
├── config          // ChatClient/VectorStore/DataSource 등 Spring 설정
├── gateway         // LLM Provider 추상화 계층
│   └── provider/   // openai, anthropic, azure, local(ollama/vllm) 어댑터
├── prompt          // 프롬프트 템플릿 관리/버저닝
├── rag
│   ├── ingest      // 문서 적재·청킹
│   ├── embedding
│   └── retrieval   // VectorStore 연동
├── agent           // Tool/Function calling, 오케스트레이션, memory
├── session         // 대화 세션/히스토리 (Redis 재사용)
├── governance      // Guardrail, PII 필터, rate limit, 비용 트래킹
├── observability   // 토큰 사용량, 트레이싱, 평가 결과 로깅
├── api             // REST Controller (Chat/RAG/Admin API)
└── common          // ai-engine 자체 공통유틸 (dstone-common과 별개, AI 특화)
```

## 3. 기술 스택 검토

| 영역 | 추천 | 대안/비고 |
|---|---|---|
| LLM 연동 | **Spring AI** — SpringBoot 3.5 스택과 자연스럽게 통합, `ChatClient`/`VectorStore` 표준 추상화 제공 | LangChain4j — RAG/Agent 기능이 더 성숙. Spring AI로 부족한 부분만 부분 도입 검토 |
| Vector Store | **Redis Vector Search** — 기존 인프라(REDIS_HOST) 재사용, 신규 인프라 추가 없음 | 스케일 필요 시 Qdrant(경량, K8s 친화적) 전환. pgvector는 신규 Postgres 필요해 후순위 |
| 관측성 | 기존 log4j2 체계에 토큰/비용 로그 필드 추가 | SI 확산 이후 Langfuse, Prometheus+Grafana 검토 |
| 배치 연계 | 임베딩 재적재, 세션 정리, 정기 평가는 **dstone-batch**에 `@AutoRegJob`으로 위임 | 엔진이 직접 스케줄링하지 않음 — 기존 아키텍처 재사용 |

## 4. 로드맵

| Phase | 내용 |
|---|---|
| 0. 스켈레톤 | pom 리액터 편입, conf 패턴, 단일 provider로 Chat API "hello world" |
| 1. Model Gateway | 멀티 provider 추상화, 프롬프트 템플릿, 세션/히스토리(Redis) |
| 2. RAG | 문서 적재→임베딩→검색, RAG API |
| 3. Agent/Tool | Function calling, Tool 등록 체계, 단순 오케스트레이션 |
| 4. 거버넌스/MLOps | 비용·토큰 추적, Guardrail, 평가(Eval) 파이프라인, dstone-batch 연계 |
| 5. 첫 SI 적용 | 실사업에 적용 → 실사용 패턴 확인 후 core/server 모듈 분리 여부 결정 |

## 5. SI 확산을 위한 설계 포인트

- 각 SI 프로젝트별 커스터마이징은 **설정(프로필) + 확장 인터페이스**로 처리 (예: `PromptResolver`, `ToolRegistry` 등 SPI). 엔진 코드 포크 없이 설정/구현체 추가만으로 재사용.
- `dstone-ai-engine`을 지금 세분화하지 않는 이유: 실제 재사용 패턴을 1~2개 SI사업에 적용해보기 전엔 어디서 잘라야 할지 알 수 없음. Phase 5 이후 판단.

## 답변

로컬 환경(`env`, 쉘 설정, `.env` 파일)에서 찾아봤는데 `ANTHROPIC_API_KEY`는 어디에도 저장되어 있지 않습니다. `~/.claude/.credentials.json`은 있지만 이건 Claude Code CLI 로그인용 OAuth 세션 토큰이라 이번 `dstone-ai-engine`(Spring AI Anthropic 연동)에 필요한 Console API 키(`sk-ant-...`)와는 완전히 다른 인증 방식이라 재사용할 수 없습니다.

**기존에 만든 키는 값을 다시 볼 방법이 없습니다** — Anthropic Console 정책상 API 키는 **생성 직후 딱 한 번만** 전체 값을 보여주고, 그 이후로는 목록에서 끝 몇 자리만 마스킹되어 보입니다(`sk-ant-...ab3f` 같은 식). 그때 복사해두지 않았다면 서버 쪽에도 원문이 남아있지 않아 관리자도 복구해줄 수 없습니다.

**해야 할 일**
1. https://console.anthropic.com → **Settings → API Keys** 에서 예전에 만든 키가 목록에 남아있는지 확인 (있어도 값은 못 봄, 존재 여부만 확인)
2. 혹시 다른 곳(비밀번호 관리자, 메모, 다른 프로젝트 `.env` 등)에 복사해둔 게 있는지 확인
3. 못 찾으면 그 키는 **폐기(Delete)** 하고 **새 키를 발급**하는 게 유일한 방법입니다 — 새로 만드는 데 제약이나 추가 비용은 없습니다.

새 키를 발급하시면, 그걸 `conf/env*.properties`에 어떻게 안전하게 반영할지(로컬만 수정 / Jasypt 암호화 / k8s Secret 분리)는 이전에 여쭤봤던 방식 중에 골라주시면 그에 맞게 반영하겠습니다.
