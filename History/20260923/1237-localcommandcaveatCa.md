**조사하면서 확인한 사실**
- `runtime.workflow.WorkFlowContext`는 아무도 참조하지 않는 죽은 클래스
- `StepFlow.error()`/`waitingApproval()`, `StepStatus.ERROR`/`WAITING_APPROVAL`은 정의만 있고 실제로 한 번도 만들어지지 않는 죽은 분기 (grep으로 확인)

- YAML 14개 파일이 `type: AGENT/TOOL/...` 문자열을 그대로 쓰고 있어, **StepType enum 이름 자체는 바꾸지 않는 쪽**으로 잡았습니다

**세 가지 요청에 대한 방향**
1. **패키지 정리**: `StepType`/`McpTransport`를 `common.definition` → `common.consts`로 이동. `runtime.status`(10개 클래스 뒤섞임)는 패키지 자체를 폐지하고, 각 클래스를 실제 주인(`runtime.agent`/`runtime.tool`/`runtime.step`/`runtime.workflow.execution`) 옆으로 재배치.
2. **StepType 분류**: Runner 구조(AgentStepRunner/ToolStepRunner/ApprovalStepRunner)가 이미 LLM 호출 여부로 나뉘어 있으므로, YAML 값은 그대로 두고 `StepType`에 `Kind.AGENT_CALL / DETERMINISTIC` 분류만 추가해서 코드가 그 구분을 선언적으로 답할 수 있게 함.
3. **IN/OUT 정리**: `StepOutput+StepResult+StepPayload`를 Java 21 sealed interface `StepOutcome`(Success/Routed/Failure/Pending)으로, `StepFlow+StepStatus`를 `WorkflowTransition`(NextStep/Loop/Done/Failed)으로 통합해 죽은 값과 중복 타입을 제거.

주석은 이동/재구성된 부분만 최소 수정하고, 새로 생기는 타입에만 짧은 설명을 붙이는 원칙으로 잡았습니다. 문서 끝(§9)에 진행 전 확인이 필요한 결정 사항 5가지를 남겨뒀습니다 — sealed interface 도입 여부, WorkFlowContext 삭제 여부, ToolOutput 개명 여부, Kind 분류 활용 범위, 진행 방식(한 번에 vs 단계별)입니다.

## 답변

Windowsローカル環境で発生したエラーを直しました。実際に何が原因で、どう直したか説明します。

**原因**
Windowsの`npx`は実体が`.cmd`(バッチスクリプト)で、JavaのProcessBuilderは`cmd.exe`を経由しないと`.cmd`/`.bat`を直接起動できません。それで「지정된 파일을 찾을 수 없습니다」(CreateProcess error=2)が出ていました。あわせて、MCPサンプルのサンドボックスパスがLinux用の絶対パス(`/app/dstone/...`)にハードコーディングされていたので、Windowsではそこも合っていませんでした。

**直した内容**
1. `YamlDefinitionLoader`に `${VAR_NAME}` プレースホルダ解決を追加 — `conf/env{-profile}.properties`が起動時にSystemプロパティとして設定する値(`APP_HOME`など、`application.yml`の`${...}`と同じ仕組み)を、workflows/agents/mcpのYAML文字列の中でも使えるようにしました。
2. `ConfigMcp`に `MCP_STDIO_COMMAND_PREFIX` というSystemプロパティ対応を追加 — 値があればSTDIO起動コマンドの先頭にそのまま連結します。
3. `conf/env.properties`(Windowsローカル用)に `MCP_STDIO_COMMAND_PREFIX=cmd.exe /c` を追加(WSL/k8s用のenvファイルには不要なので追加していません)。
4. `sample-filesystem-mcp.yml` とそれを使うAgent/Workflowのハードコードされた絶対パスを、すべて `${APP_HOME}/dstone-ai-engine/mcp-sandbox/sample` に置き換え。
