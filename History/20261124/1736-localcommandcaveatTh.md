## 근본 원인: 모델이 반복에 빠졌는데, 엔진에 그걸 알아채고 멈추는 장치가 없었습니다

### 1. 출발점: 마무리 단계에서 모델이 반복에 빠졌습니다
- `sm-developer-agent`는 26회차까지 할 일을 모두 끝냈습니다. 컴파일이 통과했고 taskitems 기록도 마쳤으니, 다음 회차에는 최종 답만 내면 됐습니다.
- 그런데 27회차부터는 출력이 매번 약 212토큰으로 거의 같았고, 같은 인자로 같은 Skill만 불렀습니다. 앞 회차들의 추론 글을 합친 길이가 회차마다 수십 자씩만 늘었으니, 회차마다 새로 한 생각은 몇 줄뿐이었다는 뜻입니다. 모델이 무언가를 판단하며 부른 게 아니라 같은 행동을 기계적으로 되풀이한 것입니다.
- 이번만의 일이었습니다. 최근 닷새 동안 `sm-developer-agent`는 12번 모두 성공했습니다. 11-24 오전 실행(`daa7c276`)에서는 taskitems를 기록한 바로 다음 회차에 답을 냈습니다. 로그를 모두 살펴봐도 같은 호출을 연달아 부른 기록은 지금까지 최대 17번이었습니다(`sm-architect-agent` readFileLines), 30번은 처음입니다.
- 그래서 프롬프트나 Skill 내용의 문제로 보기 어렵습니다. 27B 모델(qwen3.8-27b)이 큰 컨텍스트(63k)에서 "할 일 끝 → 답 내기"로 넘어갈 때 가끔 반복에 빠지는 모델 특성 쪽이 맞습니다. Skill 본문에도 Agent 프롬프트에도 다시 부르라는 내용은 없습니다.

### 2. 진짜 문제: 엔진에 반복을 끊는 장치가 없었습니다
엔진은 "일을 하며 Tool을 많이 부르는 것"과 "같은 호출을 같은 인자로 계속 되풀이하는 것"을 구분하지 못했습니다. 있는 장치는 모두 이 경우를 막지 못했습니다.

| 장치 | 이번에 막지 못한 이유 |
|---|---|
| `maxToolCalls` 120 | 횟수만 셉니다. 30번 반복은 한도 안이었습니다 |
| `reread-guard` | 파일 읽기만 봤습니다. Skill은 대상이 아니었습니다(방금 고친 부분) |
| `RunawayRetryAdvisor` | 답도 Tool 호출도 없이 끝난 회차만 잡습니다. 이번 회차들은 매번 Tool을 불렀습니다 |

여기에 가설이 하나 있습니다(확인은 못 함). 앞 회차의 추론 글을 빼고 보내기 때문에(`ReasoningStripAdvisor`), 모델은 "이미 다 끝냈다"고 생각했던 흔적을 다시 보지 못합니다. 대화에는 같은 호출과 결과가 줄지어 쌓여 가니, 작은 모델일수록 그 모양을 그대로 따라 하기 쉽습니다.

### 3. 피해를 키운 것: 비용 상한이 없었고, 원인도 남지 않았습니다
- 반복 때문에 실패했다는 오류가 아니라 402라는 엉뚱한 오류로 끝나서 원인이 가려졌습니다. 그 전까지 30회차 동안 입력이 63k에서 117k 토큰으로 불어나며 비용이 계속 나갔습니다.
- 진단에 쓸 기록이 부족했습니다. LLM 로그에는 첫 요청(REQ)만 남고, 예외로 끝나면 응답(RES)이 남지 않습니다. 추론 글도 몇 자를 뺐는지만 기록됩니다. 그래서 27회차에 모델이 왜 Skill을 불렀는지는 끝내 확인할 수 없었습니다.

### 막는 방법
방금 고친 Skill 반복 방지는 이번 증상(Skill 반복)만 막습니다. 다른 Tool을 같은 인자로 되풀이하는 경우는 여전히 열려 있습니다.

- **범용 엔진 원칙(근본 대책):** 같은 Tool을 같은 인자로 연달아 K번(예: 3번) 부르면 먼저 안내를 돌려주고, 그래도 계속하면 step을 "반복 호출"이라는 분명한 이유로 실패시킵니다. 사람이 원인을 바로 알 수 있고 비용도 그 자리에서 멈춥니다.
- **범용 엔진 원칙(진단):** step이 예외로 끝나도 마지막 몇 회차의 모델 출력(추론 글 앞부분 포함)을 LLM 로그에 남깁니다.

- **평가 사례:** 이 실행의 step17 스냅숏으로 평가 사례를 만들어 두면, 엔진을 고친 뒤 반복이 다시 나오는지 비교할 수 있습니다.
- **모델:** 지금은 모든 Agent를 qwen3.8-27b로 쓰는 POC 조건이라 바꾸지 않았습니다. 이런 일이 자주 생긴다면 마무리가 중요한 Agent부터 더 큰 모델을 검토할 만합니다.

| 경우 | 예 (이 엔진의 Tool) |
|---|---|
| 기다리며 상태를 확인할 때 | 시험 서버를 띄운 뒤 `httpGet`으로 뜰 때까지 다시 찔러 보기 |
| 백그라운드 일의 결과를 받을 때 | `TaskOutput`을 `block: false`로 불러 Sub Agent가 끝났는지 보기 |
| 밖에서 바뀌는 값을 볼 때 | 서버 로그 다시 읽기, 다른 작업 뒤의 `dbQuery`, Playwright MCP의 화면 스냅숏 |

반대로 이번 Skill처럼 결과가 매번 똑같은 읽기용 Tool이나, `writeFile`처럼 같은 인자로 다시 불러 봐야 바뀌는 게 없는 Tool은 다시 불러도 얻는 게 없습니다.

참고로 "컴파일 → 고치기 → 다시 컴파일"은 사이에 다른 Tool이 끼므로 "연달아"에 해당하지 않습니다. 중간에 다른 Tool이 불리면 셈을 처음부터 다시 하면 됩니다.

### 제안하는 판단 기준
1. **결과가 바뀌었으면 반복으로 보지 않습니다.** 인자가 같아도 답이 달라졌다면 무언가 진행된 것이니 셈을 처음부터 다시 합니다. 서버가 뜨는 중에 응답이 바뀌거나 로그가 늘어나는 경우가 여기에 해당합니다.
2. **인자와 결과가 모두 같은 호출이 연달아 나오면 셉니다.** 3번째에는 본문 대신 "같은 결과가 이미 위에 있다"는 안내를 주고, 그래도 5번째까지 가면 step을 "반복 호출"로 실패시킵니다.
3. **기다리는 용도의 Tool은 Tool 쪽에서 표시합니다.** `httpGet`이나 `TaskOutput`은 서버가 뜨기 전까지 "접속 안 됨"처럼 같은 결과가 몇 번 나오는 게 정상입니다. 이런 Tool은 `@AiTool`에 표시를 달아 셈에서 빼거나 한도를 크게 줍니다. Tool의 성질이니 범용 원칙에 맞고, 특정 Workflow를 알 필요도 없습니다. MCP Tool은 엔진이 성질을 모르니 기본 규칙(2번)을 따르게 하고, 필요하면 MCP 정의 파일에서 Tool별로 뺄 수 있게 합니다.

이 기준을 이번 실행에 대 보면, Skill이 30번 모두 같은 본문을 돌려줬으므로 29회차에 안내, 31회차에 실패로 멈췄을 겁니다. 입력은 63k 근처에서 멈추고 실패 이유도 "반복 호출"로 분명히 남습니다.

### 잘못 걸렸을 때의 피해
정상 호출이 실수로 걸려도 첫 단계는 안내라서, 모델이 다른 행동을 하면 그대로 이어집니다. 실패까지 가려면 결과가 똑같은 호출을 5번 연달아 해야 하고, 그런 경우는 기다리는 용도의 Tool 말고는 사실상 없습니다.

이 기준(결과가 같을 때만 셈, 3번째 안내, 5번째 실패, 기다리는 용도의 Tool 표시)으로 진행할까요? 횟수나 셈에서 뺄 Tool을 바꾸고 싶으시면 함께 말씀해 주세요.
