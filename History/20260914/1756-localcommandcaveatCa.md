# dstone-ai-engine 아키텍처 계획

## 1. 전체 방향

`dstone-ai-engine`은 여러 `dstone.boot` 응용앱이 **공유하는 단일 AI Execution Platform**으로 설계한다.

```text
┌───────────────┐   ┌───────────────┐   ┌───────────────┐
│ dstone.boot   │   │ dstone.boot   │   │ dstone.boot   │
│  (앱 A)       │   │  (앱 B)       │   │  (앱 C)       │
└───────┬───────┘   └───────┬───────┘   └───────┬───────┘
        │ AI Request(+tenant)                   │
        └───────────────────┼───────────────────┘
                            ▼
        ┌─────────────────────────────────────────┐
        │              dstone-ai-engine            │
        │              (단일 공유 엔진)             │
        │                                           │
        │  Tenant Context ─┬─ Capability            │
        │                  ├─ Process Engine         │
        │                  ├─ Agent Runtime          │
        │                  ├─ RAG Runtime            │
        │                  ├─ Tool Runtime           │
        │                  ├─ Model Runtime          │
        │                  └─ Governance             │
        └─────────────────────────────────────────┘
```

핵심 원칙은 두 가지다.

> **dstone.boot은 "무엇을 원하는가(Capability)"만 정의하고, dstone-ai-engine은 "어떻게 수행할 것인가"를 결정한다.**
> **하나의 엔진을 여러 앱이 쓰지만, 앱은 서로의 데이터·Tool·Agent를 절대 침범할 수 없다.**

두 번째 원칙이 단일/전용 엔진 구조와의 결정적 차이이며, 이번 계획에서 가장 먼저 확정해야 할 부분이다.

---

## 2. AI Capability 개념

AI 기능은 `ai.chat(...)` 같은 범용 호출이 아니라 **Capability** 단위로 노출한다.

```text
oracle-to-postgresql
java-code-review
document-summary
proposal-generation
architecture-review
```

사용 예:

```java
AiRequest request = AiRequest.builder()
        .tenantId("hdmf")                 // 호출 앱 식별
        .capability("oracle-to-postgresql")
        .input(oracleSql)
        .build();

AiResponse response = aiEngine.execute(request);
```

`dstone.boot`은 내부적으로 몇 개의 Agent가 몇 번 반복하는지, RAG를 쓰는지, 어떤 LLM인지 알 필요가 없다. 다만 **공유 엔진이므로 `tenantId`는 모든 요청에 필수**다.

## 3. Tenant Context — 공유 엔진의 전제 조건

여러 앱이 하나의 엔진을 쓰기로 한 순간, 이 계층이 나머지 모든 계층보다 먼저 확정되어야 한다. 나중에 끼워 넣기 가장 어려운 부분이기 때문이다.

```text
Tenant Context
 │
 ├── tenant_id 강제 (API Gateway 진입점에서부터)
 ├── 인증 토큰(JWT)의 tenant claim → 이후 계층은 재조회 없이 전파받음
 ├── 비동기 실행(Agent 큐, 백그라운드 작업)에서도 컨텍스트 유실 방지
 │    → MDC / 커스텀 ExecutionContext에 명시적으로 실어 나름
 └── "tenant_id 없는 요청/쿼리는 실행 자체를 차단" 원칙
```

Tenant Context는 아래 4개 계층에 각각 다른 방식으로 적용된다.

```text
             Tenant Context
                   │
   ┌───────┬───────┼───────┬────────┐
   ▼       ▼       ▼       ▼        ▼
 RAG     Tool    Agent   Process  Quota/Log
(데이터  (권한   (역할   (오버   (비용/실행
 격리)   화이트  세트    라이드)  량 격리)
         리스트) 제한)
```

- **RAG**: 벡터 인덱스를 앱별 컬렉션/네임스페이스로 분리하거나, 최소한 tenant_id 메타데이터 필터를 검색 쿼리에 강제한다. 금융/보험권 컴플라이언스 요건상 논리 분리보다 물리(컬렉션/스키마) 분리가 요구될 가능성이 높다.
- **Tool**: 앱마다 허용된 Tool 화이트리스트를 두고, Tool Registry가 실행 시점에 tenant_id 기준으로 권한을 검증한다. 특히 ShellTool/PythonTool은 앱별로 파일시스템·네트워크 접근 범위가 달라질 수 있다.
- **Agent**: 앱별로 사용 가능한 Agent/Team 구성을 제한할 수 있어야 한다.
- **Process**: 공통 템플릿 + 앱별 오버라이드 구조로, 같은 Capability라도 앱마다 세부 단계 수/승인 조건이 달라질 수 있게 한다.
- **Quota/Log**: 한 앱의 무거운 작업이 다른 앱의 응답 지연을 유발하지 않도록 앱별 동시 실행 수·토큰 사용량 쿼터를 두고, 모든 로그에 tenant_id를 태깅해 비용 배분(chargeback)과 감사 조회 분리가 가능하게 한다.

## 4. API Gateway — 동기/비동기 계약 분리

Agentic 워크플로우는 수 초~수 분이 걸릴 수 있으므로, 단일 동기 API로는 결국 재설계가 필요해진다. 처음부터 계약을 분리한다.

```text
AiEngine API
 │
 ├── execute()   — 동기: 단순 LLM 호출, 짧은 RAG 질의
 │
 └── submit()    — 비동기: Agent/Team 작업, 장시간 Process
       │
       ├── jobId 반환
       ├── 폴링: getStatus(jobId)
       └── 콜백/SSE: 진행상황 스트리밍
```

폐쇄망 환경에서는 엔진과 앱이 물리적으로 분리 배치될 수 있으므로, 프로토콜(REST/gRPC) 선택 시 네트워크 제약도 함께 검토한다.

## 5. AI Process의 내부 구조

```text
oracle-to-postgresql
        │
        ▼
   AI Process
        │
        ├── Analyze
        ├── RAG
        ├── Convert
        ├── Validate
        └── Review
```

Process를 설정(YAML/JSON)으로 정의할 수 있게 만드는 것이 "AI 프로세스 설정의 유연성"의 핵심이다. 단, 지원 패턴을 처음부터 무한정 늘리지 않고 **순차 실행 / 조건 분기 / 병렬 실행 / 루프** 4가지로 제한해 시작한다.

```yaml
ai:
  processes:
    oracle-to-postgresql:
      tenant-override-allowed: true      # 앱별 오버라이드 허용 여부
      model:
        provider: ollama
        name: qwen3-coder
      steps:
        - id: analyze
          type: agent
          agent: sql-analyzer
        - id: retrieve
          type: rag
          knowledge: oracle-postgresql
        - id: convert
          type: agent
          agent: sql-converter
        - id: validate
          type: tool
          tool: sql-validator
        - id: review
          type: agent
          agent: sql-reviewer
      max-iterations: 5
```

Workflow Engine으로 발전시키면:

```text
START
  │
  ▼
ANALYZE ─▶ RAG ─▶ CONVERT ─▶ VALIDATE
                                │
                    ┌───────────┴───────────┐
                   FAIL                    PASS
                    │                       │
                    ▼                       ▼
                 CONVERT                 REVIEW ─▶ END
```

## 6. Agent 구성

```text
Agent
 ├── Single Agent
 ├── Multi Agent
 │    ├── Sequential
 │    ├── Parallel
 │    └── Supervisor
 └── Team
      ├── Planner
      ├── Worker
      ├── Reviewer
      └── Supervisor
```

처음부터 모든 것을 Agent로 만들기보다, 첫 실전 Capability(Oracle → PostgreSQL)를 구현하면서 필요한 만큼만 추상화를 확보한다. AEF에서 이미 검증한 멀티 액터(PM/Architect/Dev/QA) 하네스 설계 경험을 Agent Runtime의 역할 정의·프로세스 제어 방식에 재사용할 수 있다.

### 예: SQL Migration Team

```text
                SQL Migration Team
                       │
                 ┌─────▼─────┐
                 │ Supervisor│
                 └─────┬─────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   SQL Analyzer    SQL Converter   SQL Reviewer
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                 SQL Validator
                       │
                  pass / fail
                       │
                 ┌─────▼─────┐
                 │ Supervisor│
```

## 7. Tool Runtime — 실행 격리가 핵심

자체 Java 프로그램과 외부 shell/Python/OS 프로그램을 같은 Tool 추상화로 묶되, **보안 경계는 완전히 다르게 설계**한다.

```text
Tool
 │
 ├── JavaTool        (인프로세스, 상대적으로 안전)
 ├── PythonTool       ┐
 ├── ShellTool         ├─ 샌드박싱 필수
 ├── HttpTool          │  (권한 제한 계정, 실행 화이트리스트,
 ├── DatabaseTool      │   타임아웃, 리소스 제한, 전체 로깅)
 └── MCP Tool         ┘
```

Agent 입장에서는 `sql-validator`라는 이름만 보이고, 실제 구현이 Python(sqlglot)인지 Java(JDBC)인지는 몰라도 된다 — **Agent와 Tool 구현을 분리**하는 것이 핵심이다.

### Tool Registry

```text
Agent
  │
  ▼
ToolRegistry (+ tenant 권한 검증)
  │
  ├── sql-validator
  ├── oracle-parser
  ├── file-reader
  └── shell-executor
```

Spring AI Tool Calling과 자연스럽게 연결할 수 있다.

## 10. Governance — 공유 엔진에서는 선택이 아니라 필수

Agent와 Shell/Python Tool을 실행할 수 있게 되면, 특히 여러 앱이 공유하는 구조에서는 보안·통제가 구조의 일부가 되어야 한다.

```text
AI Engine
    │
    ▼
Governance
    │
    ├── Authentication / Authorization
    ├── Tenant Isolation           ← 공유 엔진이라 추가됨
    ├── Tool Permission (tenant별)
    ├── Model Permission
    ├── Data Permission
    ├── Quota (tenant별 동시 실행 수 / 토큰)
    ├── Execution Timeout
    ├── Max Iteration
    ├── Audit (tenant_id 태깅, 조회 권한 분리)
    └── PII Masking
```

ShellTool / PythonTool / FileTool / DatabaseTool에는 AI에게 무제한 권한을 주지 않는다.

## 14. 가장 중요한 주의점

**처음부터 "범용 Agent Framework + 완전한 멀티테넌시"를 한 번에 만들려 하지 않는다.**

1차 목표는 다음 정도로 좁힌다.

```text
AI Engine
   ↓
Tenant Context (최소: tenant_id 강제 + Tool/RAG 격리)
   ↓
Capability
   ↓
Process
   ↓
Agent / RAG / Tool
```

1차 구현 대상은 실제 진행 중인 업무:

```text
Oracle → PostgreSQL   (AIA IW Modernization Phase 1)
```

이고, 이 과정에서 실제로 필요해지는 추상화만 남긴다. 테넌트 격리 수준도 처음엔 "화이트리스트 + 컬렉션 분리 + 로그 태깅" 정도로 최소화하고, 실제 두 번째 앱이 붙을 때 요구사항 차이를 보고 정교화하는 것이 안전하다.

## 15. 개발 Roadmap

### Phase 1 — AI Engine Core + Tenant Context
`AiEngine`, `AiRequest`(tenantId 필수), `AiResponse`, `Capability`, `CapabilityRegistry`. 목표: `aiEngine.execute(request)`가 tenant 검증과 함께 동작.

### Phase 2 — Process Engine
`ProcessDefinition`, `ProcessStep`, `ProcessExecutor`. YAML 기반으로 Agent → RAG → Tool → Agent 순차 실행.

### Phase 3 — Tool Runtime + 권한 화이트리스트
Java/Python/Shell/HTTP/Database Tool Registry, tenant별 허용 Tool 검증 포함.

### Phase 4 — RAG Runtime + 데이터 격리
Knowledge/Document/Chunk/Embedding/VectorStore/Retriever, tenant별 컬렉션 분리 포함.

### Phase 5 — Agent Runtime
Agent, SubAgent, Supervisor, Team.

### Phase 6 — Agentic Process 고도화
Planning → Execution → Observation → Reflection → Retry → Validation (PLAN-ACT-OBSERVE-REVIEW-REPLAN 구조로 발전).

### Phase 7 — Governance 전체 + Quota/Chargeback
Permission, Security, Audit, Cost, Token, Timeout, PII, Tool Policy, tenant별 쿼터/비용 집계.

### Phase 8 — API 동기/비동기 계약 완성
`submit()` + jobId 폴링/SSE, 두 번째 앱(dstone.boot 인스턴스) 온보딩을 통한 격리 수준 검증.

## 결론

가장 먼저 확정해야 할 계층은 다음 4개다.

```text
Tenant Context   ← 공유 엔진이므로 신규 추가, 나중에 끼워 넣기 가장 어려움
    ↓
Capability
    ↓
Process
    ↓
Agent / RAG / Tool
```

이 구조를 먼저 확정하면, 진행 중인 **Oracle → PostgreSQL 변환 Agent**를 첫 번째 Capability이자 첫 번째 tenant(HDMF 또는 AIA)로 구현하면서, 이후 다른 앱·다른 Capability로 자연스럽게 확장할 수 있다.

### 권장 핵심 원칙

1. `dstone.boot`은 AI 내부 구현을 몰라야 한다.
2. 모든 요청은 `tenantId`를 필수로 가지며, 공유 엔진 내에서 데이터·Tool·Agent가 격리된다.
3. AI 기능은 `Capability`로 추상화한다.
4. Capability의 실행 과정은 `Process`로 분리하고, 설정 기반으로 변경 가능하게 한다.
5. Agent / RAG / Tool / Model은 각각 독립 Runtime으로 만든다.
6. Tool은 구현 방식(Java/Python/Shell/HTTP/DB)과 Agent를 분리하고, 외부 프로세스 실행은 반드시 샌드박싱한다.
7. Team / Sub-Agent / Supervisor는 Agent Runtime에서 관리한다.
8. Governance(권한, 쿼터, 감사, PII)는 선택이 아니라 공유 엔진의 전제 조건이다.
9. Spring AI는 Model/Tool Calling 하부 구현에 활용하고, `dstone-ai-engine`은 그 위에서 자체 AI Execution Platform 역할을 담당한다.

## 답변

계획이 승인되어 플랜 모드는 종료됐지만, 원래 요청은 "계획을 말해달라"였으니 실제 구현은 어디서부터 시작할지 확인부터 하겠습니다.

**요약**: 문서의 8-Phase 로드맵 기능은 전부 반영하되, 기존 컨벤션(작은 응집 패키지, 옵트인 플래그, List-of-Map 바인딩)을 그대로 확장하는 방식으로 설계했습니다.
