# dstone-ai-engine 아키텍처 계획 검토

## 1. 전체 방향

`dstone-ai-engine`은 단순한 AI 호출 라이브러리가 아니라, `dstone.boot`에서 AI 기능을 필요에 따라 위임받아 수행하는 **AI Execution Platform**으로 설계하는 것이 좋다.

```text
┌─────────────────────────────────────────────────────────────┐
│                    Application Layer                        │
│                       dstone.boot                           │
│                                                             │
│  업무 API / Batch / Migration / Admin / etc.               │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           │ AI Request
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                    dstone-ai-engine                         │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ AI Service / Execution API                            │  │
│  │                                                       │  │
│  │  ai.execute(...)                                      │  │
│  │  ai.chat(...)                                         │  │
│  │  ai.agent(...)                                        │  │
│  │  ai.workflow(...)                                     │  │
│  └───────────────────────┬───────────────────────────────┘  │
│                          │                                  │
│              ┌───────────▼───────────┐                      │
│              │ Execution Orchestrator│                      │
│              └───────────┬───────────┘                      │
│                          │                                  │
│       ┌──────────────────┼───────────────────┐              │
│       ▼                  ▼                   ▼              │
│   Agent Runtime       RAG Runtime        Tool Runtime       │
│       │                  │                   │              │
│       ▼                  ▼                   ▼              │
│   Agent / Team       Retrieval          Java Tool           │
│   Sub-Agent          Embedding          Python              │
│   Planner             Vector DB          Shell               │
│   Reviewer            Document          External API         │
│                                                             │
│              ┌─────────────────────────┐                    │
│              │ Model / Provider Layer  │                    │
│              │ Spring AI              │                    │
│              │ Ollama / OpenAI / ...  │                    │
│              └─────────────────────────┘                    │
└─────────────────────────────────────────────────────────────┘
```

핵심은 **`dstone.boot`이 AI의 내부 구현을 몰라야 한다**는 것이다.

---

## 2. 가장 중요한 설계 원칙

다음 원칙을 명확하게 정의하는 것을 권장한다.

> **dstone.boot은 "무엇을 원하는가"만 정의하고, dstone-ai-engine은 "어떻게 AI를 통해 수행할 것인가"를 결정한다.**

예를 들어 `dstone.boot`에서 Oracle SQL 변환을 한다면:

```java
AiRequest request = AiRequest.builder()
        .capability("oracle-to-postgresql")
        .input(oracleSql)
        .build();

AiResponse response = aiEngine.execute(request);
```

`dstone.boot`은 다음을 몰라도 된다.

```text
어떤 LLM?
RAG를 사용하는가?
Tool Calling 하는가?
어떤 Tool?
몇 개의 Agent?
Sub Agent가 있는가?
Reviewer가 있는가?
몇 번 반복하는가?
```

이것들은 전부 `dstone-ai-engine`이 결정한다.

## 3. AI Capability 개념

AI 기능을 단순히 `ai.chat(...)`로만 만들지 않는 것이 좋다.

대신 **Capability**를 중심으로 설계한다.

예:

```text
oracle-to-postgresql
java-code-review
document-summary
proposal-generation
sql-analysis
architecture-review
code-migration
document-classification
```

사용 예:

```java
aiEngine.execute(
    AiRequest.of(
        "oracle-to-postgresql",
        oracleSql
    )
);
```

이렇게 하면 `dstone.boot`은 AI 내부 프로세스와 독립될 수 있다.

---

## 4. AI Capability의 내부 구조

예를 들어:

```text
oracle-to-postgresql
        │
        ▼
   AI Process
        │
        ├── Analyze
        ├── RAG
        ├── Tool
        ├── Generate
        ├── Validate
        └── Review
```

여기서 **AI Process를 설정으로 정의할 수 있게 만드는 것**이 "AI 프로세스 설정의 유연성"을 해결하는 핵심이다.

---

## 5. AI Process를 설정 기반으로 관리

예를 들어 다음과 같이 구성할 수 있다.

```yaml
ai:
  processes:

    oracle-to-postgresql:

      model:
        provider: ollama
        name: qwen3-coder

      steps:

        - id: analyze
          type: agent
          agent: sql-analyzer

        - id: retrieve
          type: rag
          knowledge: oracle-postgresql

        - id: convert
          type: agent
          agent: sql-converter

        - id: validate
          type: tool
          tool: sql-validator

        - id: review
          type: agent
          agent: sql-reviewer

      max-iterations: 5
```

이렇게 하면 Java 소스를 변경하지 않고 AI 프로세스를 변경할 수 있다.

## 7. Agent 구성

현재 구상한 Team / Sub-Agent 구조는 좋은 방향이다.

다만 다음과 같이 단계적으로 추상화하는 것을 권장한다.

```text
Agent
 ├── Single Agent
 │
 ├── Multi Agent
 │    ├── Sequential
 │    ├── Parallel
 │    └── Supervisor
 │
 └── Team
      ├── Planner
      ├── Worker
      ├── Reviewer
      └── Supervisor
```

처음부터 모든 기능을 Agent로 만들기보다는 실제 요구사항을 통해 필요한 추상화를 확보하는 것이 좋다.

## 9. Tool Runtime은 별도 계층으로 분리



또는:

```text

       │
       └── Java
             │
             └── PostgreSQL JDBC
```

일 수도 있다.

**Agent와 Tool 구현을 분리하는 것이 핵심이다.**

## 결론

현재 단계에서 가장 먼저 확정해야 할 핵심 계층은 다음 3개다.

```text
Capability
    ↓
Process
    ↓
Agent / RAG / Tool
```

그리고 `Team / Sub-Agent`는 Agent Runtime 위에 구성한다.

이 구조를 먼저 확정하면 현재 진행 중인 **Oracle → PostgreSQL 변환 Agent**를 첫 번째 Capability로 구현하면서, 이후 Java Migration, 문서 분석, RFP 분석, Architecture Review 등으로 자연스럽게 확장할 수 있다.

### 권장 핵심 원칙

1. `dstone.boot`은 AI 내부 구현을 몰라야 한다.
2. AI 기능은 `Capability`로 추상화한다.
3. Capability의 실행 과정은 `Process`로 분리한다.
4. Process는 설정 기반으로 변경 가능하게 한다.
5. Agent / RAG / Tool / Model은 각각 독립 Runtime으로 만든다.
6. Tool은 Java/Python/Shell/HTTP/DB 등 구현 방식과 Agent를 분리한다.
7. Team / Sub-Agent / Supervisor는 Agent Runtime에서 관리한다.
8. Shell/Python/DB 등의 실행 권한은 Governance에서 통제한다.
9. 처음부터 범용 Agent Framework를 만들지 말고 Oracle → PostgreSQL을 첫 번째 실전 Capability로 삼는다.
10. Spring AI는 Model 및 Tool Calling 등의 하부 구현에 활용하고, `dstone-ai-engine`은 그 위에서 자체적인 AI Execution Platform 역할을 담당하게 한다.

## 답변

Looked at the actual code before reacting — it's already ahead of the CLAUDE.md phase table (`governance/guardrail` PII advisor, `governance/usage` cost/usage advisor, `prompt`, `session`, `tools/sql` with a real `SqlSyntaxTools`, `ConfigTool` scanning `@AiTool` beans). No `rag/`, `agent/`, `capability`, or `process` yet — so this is still a single-agent, tool-calling engine, nothing workflow/multi-agent about it yet.

**Direction: right idea, wrong scope right now.**

The core principle — "boot only says *what*, engine decides *how*" via a `Capability` — is good and cheap to add. The rest of the reference doc (YAML Process/Workflow engine with conditionals/loops/parallel/human-approval, Agent Team/Supervisor/SubAgent) is a full custom orchestration framework, and building that *before* there's more than one real capability is the exact premature-generalization trap section 17 of the doc itself warns against. Two concrete conflicts with decisions already made in this repo:

1. **CLAUDE.md's Phase 3 explicitly says**: "orchestration is Spring AI's built-in tool-calling loop, not a custom engine." The reference plan's Process Engine + Agent Team reverses that call. If you want to reverse it, that should be a deliberate decision, not something that slides in because a diagram looked good.
2. **Governance already exists as Advisors** (`PiiGuardrailAdvisor`, `UsageLoggingAdvisor`) wired at the `ChatClient` level from day one — but the reference roadmap puts `ShellTool`/`PythonTool` in Phase 3 and Governance in Phase 7. A tool that can run arbitrary shell/Python must be allow-listed and sandboxed *before* it exists, not four phases later. This is the highest-risk item in the whole plan and needs to move up, not down.

**What I'd actually recommend:**

- Keep the existing Phase 0–4 roadmap as the backbone — don't replace it.
- Add a thin `capability` package now: `Capability` (name → prompt template + allowed tool set) + `CapabilityRegistry` + `AiEngine.execute(AiRequest)`. That alone buys the "boot doesn't know internals" property with almost no new machinery.
- Implement Oracle→PostgreSQL as **one** capability using what already exists — single agent, `ChatClient` tool-calling loop, tools shaped like `SqlSyntaxTools`/a new validator tool. No Process engine, no Team/Supervisor.
- Defer the YAML workflow engine and multi-agent Team/Supervisor entirely until a **second** real capability shows you actually need branching or multiple cooperating agents — generalize from two concrete cases, not zero. (Spring AI 2.x has no built-in multi-agent orchestration either — Team/Supervisor would be fully hand-rolled and is a lot to maintain speculatively.)
- If/when Shell/Python tools get built, they go in with governance (permission + sandboxing) from the same commit, following the pattern already set by the PII/usage advisors.

## 답변

이건 제가 만든 capability 연결 로직의 버그가 아니라, **`llama3.2`(로컬 Ollama)가 Tool 호출을 "진짜 구조화된 호출"이 아니라 그냥 텍스트로 흉내 내서 답해버린 것**입니다.

## 왜 이런 일이 생기나

Ollama API는 모델이 Tool을 쓰고 싶을 때 응답의 `message.tool_calls`라는 별도 구조(Spring AI `OllamaApi.Message.ToolCall`)에 담아서 보내야 합니다. Spring AI의 `ToolCallingManager`는 **그 구조화된 필드만 보고** "이건 Tool 호출이다"라고 판단해서 실제로 `validateSqlSyntax`를 실행합니다.

그런데 `llama3.2`(특히 3B급 작은 모델)는 가끔 이 구조화된 필드 대신, 그냥 일반 답변 텍스트(`message.content`) 안에 `{"name":"validateSqlSyntax","parameters":{...}}` 같은 **Tool 호출처럼 생긴 문자열을 그냥 써버립니다**. Spring AI 입장에서는 이게 그냥 "평범한 답변 텍스트"일 뿐이라, Tool을 실행하지도 않고 그 텍스트를 그대로 최종 답변으로 돌려준 겁니다 — 그래서 자기수정 루프(검증→재작성)도 아예 한 번도 안 돌았습니다.

거기에 더해, 원본 SQL(`NVL('', '3')`)에 있던 홑따옴표를 이 가짜 JSON 문자열 안에 욱여넣으면서 모델이 이스케이프까지 잘못 처리해서(`\", \", \\"3\\\"`) 더 알아보기 힘든 모양이 됐습니다 — 이것도 모델이 만든 결과물이지 저희 쪽 인코딩 문제는 아닙니다.

## 선택지

- **Anthropic으로 전환**(`spring.ai.model.chat: anthropic`) — Claude는 구조화된 tool_calls를 훨씬 안정적으로 지킵니다. 이 capability 하나만 비용이 발생하는 구조라, 운영 대상 기능이면 이쪽이 제일 안전합니다.
- **더 큰/Tool-calling에 강한 로컬 모델로 교체**(예: `llama3.1:8b`, `qwen2.5-coder` 등) — 무료 유지하면서 안정성만 올리는 방향. `ollama pull`로 새 모델을 받고 `conf/application.yml`의 `spring.ai.ollama.chat.options.model`만 바꾸면 됩니다.
- 지금처럼 `llama3.2`를 유지한다면, 이런 "가짜 Tool 호출 텍스트"가 가끔 섞여 나올 수 있다는 한계를 감수해야 합니다(모델 신뢰성 문제라 코드로 100% 막기는 어렵습니다).
