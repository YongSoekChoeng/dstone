## 답변

좋은 방향이라고 봅니다. 지금은 [Build]를 깜빡하면 에러 없이 옛 소스로 분석하고 개발합니다. 다만 조건 몇 가지를 같이 넣어야 합니다. 아직 코드는 바꾸지 않았습니다.

## 지금 동작
- `resolveProjectRevision`은 DB에 적힌 현재 리비전을 읽기만 합니다.
- [Build]는 `git pull`/`svn update` → 소스 복사 → 빌드를 백그라운드 스레드에서 합니다. 같은 SCM 리비전이 이미 성공했으면 다시 빌드하지 않습니다. 그래서 바뀐 것이 없을 때는 갱신 비용이 거의 없습니다.

## 권하는 모양
| 항목 | 제안 |
|---|---|
| 켜는 방법 | Tool 인자 `refresh`를 두고 `sm-workflow.yml`에서 `refresh: true`로 지정합니다. 갱신할지는 Workflow가 정합니다. |
| 빌드 호출 | 버튼과 같은 로직을 끝날 때까지 기다리는 메소드로 부릅니다. 이미 빌드 중이면 끝나기를 기다렸다가 그 결과를 씁니다. |
| 형상관리가 없는 프로젝트 | 갱신하지 않고 지금처럼 현재 리비전을 씁니다. 리비전 이름이 빌드 시각이라 실행할 때마다 전체를 다시 빌드하게 됩니다. |
| 갱신·빌드 실패 | 이전 리비전으로 넘어가지 않고 로그와 함께 실패시킵니다. 조용히 옛 소스를 쓰면 이 기능을 넣는 의미가 없습니다. |

## 같이 해결해야 할 것
1. **리비전 삭제 위험 (지금도 있는 문제)**: 오래된 리비전을 지울 때 보호 표시(`runs/{실행ID}/revision.txt`)는 테스트 서버를 띄울 때 생기고 내릴 때 지워집니다. 승인 대기 중인 실행의 리비전은 보호되지 않을 수 있습니다(`keep-revisions` 기본 3). 자동 빌드를 하면 리비전이 자주 늘어나므로, 끝나지 않은 실행의 `state.projectRevision`을 기준으로 보호하도록 먼저 고쳐야 합니다.
2. **코드 분석 결과와의 어긋남**: `knowledgeFeatureCode`는 dstone-knowledge가 분석한 줄 번호로 리비전 소스를 읽습니다. 소스만 새로워지면 엉뚱한 줄을 가져올 수 있습니다. 우선은 분석한 리비전과 다를 때 결과에 경고를 남기고, 재분석까지 자동으로 돌리는 것은 따로 판단하는 편이 낫습니다. 두 리비전을 비교할 값이 있는지는 더 확인해야 합니다.
3. **권한**: [Build]는 관리자만 누를 수 있는데, 이렇게 바꾸면 Workflow를 실행하는 사람 누구나 빌드를 일으킵니다. 사내 도구라 허용해도 된다고 보지만 결정은 필요합니다.
4. **시간과 원본 폴더**: 새 커밋이 있으면 첫 step이 몇 분 걸리고 실행 스레드를 잡고 있습니다. step 시간 제한에 걸리지 않는지 구현할 때 확인해야 합니다. 소스 디렉토리에 로컬 변경이 있으면 `git pull --ff-only`가 실패해 실행이 시작되지 않을 수 있습니다.

실행 중간에는 지금처럼 처음 정한 리비전을 끝까지 씁니다. step59로 되감았을 때만 새로 받게 됩니다.

진행한다면 1번 수정과 `refresh` 추가를 함께 하고, 2번은 경고까지만 넣겠습니다. 이대로 할까요?

## 10명이 동시에 쓰면
`keep-revisions: 3`은 동시 사용자 수 제한이 아니라 지우지 않고 남길 리비전 수입니다.

- **수정 전**: 승인을 기다리는 실행의 리비전은 보호되지 않았습니다. 그 뒤로 새 빌드가 3번 쌓이면 소스 폴더가 지워질 수 있었습니다.
- **수정 후**: 끝나지 않은 실행이 쓰는 리비전은 3개를 넘어도 남습니다. 10건이 서로 다른 리비전을 쓰면 10개가 모두 남고, 그만큼 디스크를 씁니다. 같은 리비전을 쓰면 하나만 남습니다.

실제로 먼저 걸리는 것은 다른 한도입니다.

| 항목 | 현재 값 | 10명일 때 |
|---|---|---|
| 동시 실행 `pool.max-running` | 8 | 2명은 `QUEUED`로 기다립니다. |
| 같은 프로젝트 빌드 | 한 번에 1건 | 첫 실행이 빌드하는 동안 나머지는 기다립니다. 새 커밋이 없으면 형상관리 갱신만 하고 지나갑니다. |
| 서로 다른 프로젝트 빌드 | 제한 없음 | 최대 8개가 동시에 빌드될 수 있어 메모리와 CPU를 봐야 합니다. |
| 테스트 서버 `max-servers` | 3 | 4번째부터 60초 기다린 뒤 환경 문제로 테스트를 못 합니다. **가장 먼저 부족해질 값입니다.** |

빌드를 기다리는 실행도 실행 슬롯을 차지합니다. 한 프로젝트의 긴 빌드에 8명이 몰리면 다른 프로젝트 실행도 그동안 대기합니다. 10명이 쓸 계획이면 `max-servers`를 서버 메모리에 맞춰 올리는 것을 권합니다. 이 값은 바꾸지 않았습니다.

## 바꾼 것
- **리비전 갱신**: `resolveProjectRevision`에 `refresh` 인자를 추가하고 `sm-workflow`(2.13.0)에서 켰습니다. 갱신이나 빌드에 실패하면 이전 리비전으로 넘어가지 않고 실행이 실패합니다. 형상관리가 없거나 빌드 설정이 없는 프로젝트는 지금처럼 동작합니다.
- **중복 빌드 방지**: 기다리는 동안 같은 리비전의 빌드가 실패했으면 다시 빌드하지 않고 그 결과를 받습니다.
- **리비전 보호**: 대기, 진행, 승인 대기, 일시정지 중인 실행의 리비전은 남깁니다. 실패한 실행의 것은 다시 돌릴 수 있게 7일간 남깁니다(`keep-failed-days`, 새 설정).
- **분석 결과 경고**: dstone-knowledge의 분석 리비전 이름이 소스 리비전과 맞지 않으면 참고 코드 문서 첫머리에 경고를 남깁니다. 분석 리비전 이름을 커밋 해시가 아닌 자유로운 이름으로 붙였다면 소스가 같아도 경고가 나옵니다. 재분석은 자동으로 돌리지 않습니다.
- **문서**: `docs/09` 두 문서와 `.claude/docs/ai-engine-features.md`를 갱신했습니다.

## 알아 둘 점
- 권한은 제안대로 두어서, Workflow를 실행하는 사람이면 누구나 빌드를 일으킵니다. 빌드 기록에는 실행 요청자가 남습니다.

## 답변

상황마다 다릅니다. 띄우기 전에 알 수 있는 문제는 안전하게 거절하지만, 몇 가지는 새는 구멍이 있습니다. 코드만 읽고 판단한 것이고 직접 재현하지는 않았습니다.

## 정상적으로 걸러지는 경우
`success=false`, `cause=environment`가 되고, 자동 수정 없이 사유(`serverError`)를 들고 개발 승인(step19)으로 갑니다.

- EJB나 벤더 API를 쓰는 앱
- 외부 접속을 막을 수 없는 NIO 라이브러리가 있는 앱
- 등록한 DB의 JDBC URL도 JNDI 이름도 찾지 못한 경우 (URL을 조각으로 조립하는 앱)
- 맞는 Tomcat이 없거나, DB 인증 실패 또는 `No suitable driver`로 기동에 실패한 경우
- 기동하거나 다시 반영한 직후, 드라이버를 거치지 않은 DB 연결이 보이는 경우 (서버를 내립니다)

DB를 원복할 수 없다고 판단하면 띄우지 않는 것이 원칙입니다. 이 경우에도 컴파일과 형식 검사는 끝난 상태라 사람이 보고 승인할 수 있습니다.

## 구멍
| 상황 | 일어나는 일 | 위험 |
|---|---|---|
| **목록에 없는 DB 드라이버** (Tibero, MSSQL 등)를 설정에 직접 지정 | URL만 `jdbc:dstonetest:`로 바뀌고 드라이버 클래스는 그대로라 기동에 실패할 가능성이 큽니다. 오류 문구가 판정 패턴에 없으면(예: Hikari의 `claims to not accept jdbcUrl`) `cause=code`가 됩니다. | 자동 수정 Agent가 멀쩡한 코드를 고치려 합니다. |
| 앱이 연결을 **벤더 타입으로 형변환** (`(OracleConnection) conn`) | 앱이 받는 것은 `java.sql.Connection`만 구현한 프록시라 `ClassCastException`이 납니다. | 개발 결함으로 오인해 `FAIL` → 자동 수정으로 갑니다. |
| 앱이 **`unwrap()`으로 원래 연결**을 꺼냄 | 실제 물리 연결이 그대로 나옵니다. | 그 연결로 `commit()`하면 개발 DB에 **실제 반영**됩니다. |
| **기동 뒤에 처음 생기는 우회 연결** | 우회 검사는 기동 직후와 재반영 직후에만 합니다. 화면 검증 중에 생긴 연결은 다음 `startTestServer` 호출이 없으면 확인하지 않습니다. | 커밋돼도 **아무 경고 없이** 끝날 수 있습니다. |
| 소켓으로 잡히지 않는 접속 (Oracle OCI 등) | 잡지 못하는 주소를 찾는 코드(`SandboxPaths.unguardedDatabase`)는 있지만 테스트 서버에서 부르지 않습니다. URL을 못 바꾼 연결이면 우회 검사에도 걸리지 않습니다. | 원복되지 않습니다. |
| 프로시저 안의 `COMMIT`, 자율 트랜잭션, DB 링크, MyISAM | 원복되지 않습니다. `docs/09`에 한계로 적혀 있습니다. | 알려진 한계입니다. |

목록에 없는 DB라도 드라이버 클래스를 지정하지 않는 앱은 자동 탐색으로 원래 드라이버를 찾으므로 동작할 수 있습니다.

## 고친다면
1. **데이터 보호**: 실행이 멈추거나 끝날 때도 우회 연결을 검사해 결과에 남깁니다. `unwrap()`은 원래 연결을 내주지 않게 막고, 잡지 못하는 DB 주소는 기동 전에 거절합니다.
2. **오판 방지**: 드라이버 때문에 생긴 오류(`claims to not accept`, `dstonetest`, 프록시 `ClassCastException`)는 `environment`로 분류합니다. 화면 검증 중에 나는 것은 `test-environment` Skill에서 `BLOCKED`로 가르게 합니다.
3. **지원 확대**: Tibero 같은 드라이버 클래스를 코드가 아니라 설정으로 추가할 수 있게 합니다.

1번은 개발 DB에 실제로 쓰일 수 있는 문제라 먼저 고치기를 권합니다. 다만 우회 검사는 일이 벌어진 뒤에 알리는 장치라, 원복을 보장할 수 없는 앱은 프로젝트 설정에서 테스트 서버를 끌 수 있게 하는 것도 방법입니다. 어디까지 진행할까요?

`dstone-testdriver.jar`는 사람이 관리하는 산출물이 아닙니다. 엔진이 필요할 때 만들고 다시 쓰는 캐시라서 git에 올리거나 따로 배포하지 않습니다.

## 흐름
| 단계 | 내용 |
|---|---|
| 원본 | `dstone-ai-engine/src/main/resources/testdriver/…`의 `TestDriver`, `Holder`, `Control` `.javasrc` 3개. 엔진 jar에 리소스로 들어갑니다. |
| 생성 시점 | 테스트 서버를 띄울 때 `TestDriverJar.ensure()`를 부릅니다. 같은 jar가 있으면 그대로 씁니다. |
| 빌드 | 엔진의 JDK로 `--release 8` 컴파일하고 `META-INF/services/java.sql.Driver`를 넣어 묶습니다. 엔진이 JRE에서 돌면 실패합니다. |
| 위치 | `{work-root}/testdriver/{해시}/dstone-testdriver.jar`. `work-root`를 비우면 `~/.dstone-ai-engine`입니다. |
| 버전 | 해시는 `.javasrc` 3개 내용의 SHA-256 앞 16자리입니다. 소스가 바뀌면 새 폴더에 새로 만듭니다. |
| 사용 (Tomcat) | 실행별 `CATALINA_BASE/lib`에 복사합니다. 서버를 내릴 때 함께 지워집니다. |
| 사용 (Boot) | `java -cp`에 캐시의 jar 경로를 그대로 넣습니다. |

이 PC에는 2026-11-26에 만든 약 16KB짜리 하나가 있습니다. 드라이버를 고치려면 `.javasrc`를 수정하고 엔진을 다시 빌드해 띄우면 됩니다. 다음 테스트 서버 기동 때 새 jar가 만들어집니다.

## 약한 부분
- **옛 버전을 지우지 않습니다.** 크기가 작아 당장 문제는 없습니다.
- **해시에 빌드 방식은 들어가지 않습니다.** `TestDriverJar`의 컴파일 옵션이나 패키징 코드만 바꾸면 옛 jar를 계속 씁니다. 이때는 `testdriver` 폴더를 지워야 합니다.
- **엔진 여러 대가 `work-root`를 함께 쓰면 경합할 수 있습니다.** 잠금(`synchronized`)은 JVM 하나 안에서만 유효하고 임시 파일 이름이 `dstone-testdriver.jar.tmp`로 고정이라, 처음 만들 때 겹치면 깨진 jar가 남을 수 있습니다. 시험용 사본을 다른 포트로 띄우면 해당될 수 있습니다.
- **깨진 jar는 스스로 복구하지 않습니다.** 파일이 있으면 내용을 확인하지 않고 씁니다. 해당 해시 폴더를 지우면 다시 만듭니다.

Boot 서버가 떠 있는 동안에는 jar를 직접 참조하므로 `testdriver` 폴더는 테스트 서버가 모두 내려간 상태에서 지우세요.

고친다면 임시 파일 이름을 매번 다르게 하고 해시에 빌드 옵션을 포함하는 정도면 충분합니다. 몇 줄이면 되니 원하시면 앞의 드라이버 보완과 함께 처리하겠습니다.

## 답변

네, **커밋하지 않은 파일이 9개** 있습니다. 모두 이번 대화에서 만든 리비전 자동 갱신과 리비전 보호 변경입니다. **푸시하지 않은 커밋은 없고**, `main`은 `origin/main`과 같습니다. stash도 없습니다.

| 구분 | 파일 |
|---|---|
| 코드 | `ProjectBuildService.java`, `ProjectRevisionTool.java`, `KnowledgeFeatureTool.java` |
| 테스트 | `ProjectBuildServiceTest.java` |
| 설정·정의 | `conf/application.yml`, `sm-workflow.yml` (2.13.0) |
| 문서 | `docs/09.dstone-ai-engine.md`, `docs/09.dstone-ai-engine-sm-workflow.md`, `.claude/docs/ai-engine-features.md` |

최근의 `history: …` 커밋들은 자동으로 만들어져 이미 푸시된 대화 이력입니다. 테스트 드라이버 질문에서는 파일을 바꾸지 않았습니다.

커밋과 푸시가 필요하면 말씀해 주세요. `sm-workflow.yml`에서 `refresh: true`를 켠 상태라, 반영하면 형상관리를 쓰는 프로젝트는 실행할 때마다 갱신합니다. 실제 git/svn 저장소로는 아직 시험하지 않았습니다.
