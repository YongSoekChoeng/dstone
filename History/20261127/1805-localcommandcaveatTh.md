## 바뀐 것

**1. 검증 결과를 기준별로 누적**
- 범용 Tool `mergeByKey`를 만들었습니다. 같은 기준 ID는 새 결과로 바꾸고, 이번에 확인하지 않은 기준은 지난 결과를 남깁니다.
- 남긴 항목에는 `carried: true`가 붙어, 이번에 다시 본 것과 구분됩니다.
- 자동 수정, 실패 판정, 다음 검증은 누적 결과(`verificationAll`)를 받습니다.
- 설계를 다시 승인해 개발 폴더를 비우면 누적 결과도 비웁니다. 새로 만든 코드에 옛 PASS가 남지 않게 하려는 것입니다.

**2. 확인 순서 지정** (`sm-verifier-agent` 2.3.0)
- `알린 오류 → 바뀐 파일 관련 → 지난 FAIL·BLOCKED → 나머지` 순으로 봅니다.
- 이번에 확인한 기준만 답하고, 여러 기준을 한 줄로 묶지 않습니다.

그 밖에 `sm-auto-fix-agent`(2.3.0)는 `carried`인 FAIL을 고치기 전에 지금 코드에 원인이 남았는지 먼저 확인합니다. step이 둘 늘어(`step62` 누적, `step63` 비우기) 화면의 순번이 22번부터 밀렸고, 개발 승인은 40에서 42가 됐습니다. 문서도 맞춰 고쳤습니다.

## 답변

`.work-copy`는 **다음 검증 때 "무엇이 어떻게 바뀌었는지" 비교하려고 두는 지난번 작업 폴더의 사본**입니다. 오류나 찌꺼기가 아니라 의도해서 만드는 폴더입니다.

## 언제, 무엇이 생기나

`sm-workflow`의 검증 전 바뀐 파일 확인 step(`step40`, 화면 순번 31)이 서버를 띄우기 전에 만듭니다. 위치는 `work004/.work-copy/20261127-1650/`이고 실행 시각마다 하나입니다. 지금 크기는 168KB입니다.

1. 지금 작업 폴더를 사본과 비교해 바뀐 줄(diff)을 만듭니다.
2. 사본을 지우고 지금 내용으로 다시 복사합니다.

`compile-check` 폴더, 바이너리 파일, 너무 큰 파일은 복사하지 않습니다.

## 왜 필요한가

만든 diff는 다음 개발(`sm-developer-agent`)과 자동 수정(`sm-auto-fix-agent`)에 전달됩니다. 설계서의 '수정 이력'은 Agent가 직접 쓴 설명이라 틀릴 수 있기 때문입니다. 실제로 실행 0fb4c669에서는 재개발이 잘 되던 코드를 잘못 바꾸고 이력에도 반대로 적었고, 다음 재개발이 그 설명을 믿어 엉뚱한 곳만 고쳤습니다.

## 왜 실행 폴더 밖에 두나

작업 폴더(`work004/20261127-1650`) 안에 두면 Agent가 파일을 찾다가 **옛 코드를 지금 코드로 알고 읽을 수 있습니다.**

## 지워도 되나

- **끝난 실행의 폴더는 지워도 됩니다.** 자동으로 지우는 기능이 없어서 실행할 때마다 하나씩 쌓입니다.
- **진행 중이거나 승인 대기 중인 실행의 폴더는 두세요.** 지우면 다음 회차에 바뀐 줄 대신 "지난 내용이 없습니다"로 전달됩니다. 실행이 실패하지는 않지만 비교 정보를 잃습니다.

실행 5def8189(`20261127-1650`)는 마지막 확인 때 개발 승인 대기였습니다. 끝난 실행의 사본을 자동으로 지우길 원하시면 추가할 수 있습니다.
