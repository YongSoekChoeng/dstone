## 답변

## 1. Sonnet 답변에 대한 의견

진단은 대체로 맞습니다. "개발 Agent에게는 관측할 Tool이 없다", "프롬프트보다 Workflow 구조와 Tool 문제다"라는 분류도 프로젝트 원칙에 맞습니다. 기술 내용도 맞습니다. `$.when()`에 ajax를 두 개 넘기면 각 인자는 `[data, status, jqXHR]`입니다. 다만 몇 가지는 다르게 보거나 순서를 바꾸고 싶습니다.

**① 사람이 알린 오류를 관측 경로로 보내자는 제안: 방향은 맞지만 더 싼 방법이 있습니다.**
전문가 해결 경로를 되살리지 않아도 됩니다. 재개발한 결과는 이미 step18 → step29 → step35를 지나 `sm-verifier-agent` 검증을 받습니다. 이번 실패는 검증이 "등록한 내용이 안 보인다"는 사람의 지시를 **재현해야 할 시나리오로 다루지 않은 것**이 원인입니다. 그래서 먼저 `${arrival}`에 담긴 사람의 오류 신고를 검증 Agent가 반드시 재현하도록 할 것을 권합니다. 고치는 일은 지금처럼 자동 수정이 합니다. 그러면 11-26 결정을 되돌리지 않아도 됩니다.

**② 테스트 데이터: 새 Tool보다 기존 Tool을 넓히는 것이 먼저입니다.**
step60 `checkDdlApplied`는 테이블과 컬럼만 봅니다. DDL 문서의 INSERT 행이 개발 DB에 있는지도 보게 하면 이번 "회의실 0건"은 사람 승인(step61) 단계에서 바로 걸렸을 것입니다. 범용이고 비용도 적습니다. 테스트 연결에 INSERT를 넣는 Tool은 그다음 단계입니다. 이때 "운영에 반영할 초기 데이터"와 "테스트용 데이터"를 구분하지 않으면 혼란이 생기니 주의해야 합니다.

**③ 변경 이력을 사실로 주자는 제안: 찬성합니다. 이미 절반은 있습니다.**
step40 `fileChanges`가 바뀐 파일 목록은 만듭니다. 여기서 diff 본문(크기 제한 포함)까지 만들게 해서 자동 수정과 재개발에 넘기면 됩니다.

**④ 평가 사례: 순서를 맨 앞으로 옮겨야 합니다.**
①~③을 고치기 **전에** 이번 step 스냅숏으로 기준선을 떠 두어야 효과를 비교할 수 있습니다.

**빠진 점:** "출력 한도 6만 토큰을 다 쓰고 추론이 맴돈다"는 것은 모델 성능이 아니라 튜닝 문제(reasoning 예산, `ai-engine-tuning.md`)로 따로 분류해야 합니다. 그리고 제가(Claude Code) 추적에 성공한 핵심은 큰 모델이어서라기보다 **여러 실행의 기록을 넘나들며 대조했기 때문**입니다. 엔진이 그 기록을 Agent에게 읽게 해 주면 27B 모델도 상당 부분 따라올 수 있습니다. 이 점은 아래 2번과도 이어집니다.

## 2. sm-workflow 호출 구조 정리

추적하기 어려운 이유는 정의 파일에서 세 가지, 엔진에서 한 가지입니다.

| 원인 | 실제 모습 |
|---|---|
| 판단 전용 step이 많음 | 62개 step 중 12개(step28, 30, 31, 36, 42~44, 51, 54~56, 60)가 `containsValue`/`countUp`으로 갈림길만 만듦 |
| 같은 문서를 여러 곳에서 다시 읽음 | 설계서와 태스크아이템을 step14/15, 20/21, 32/33, 41에서 따로 읽음 |
| 같은 일을 하는 경로가 여러 개 | 개발 Agent 호출이 step17·57·58 세 곳, 서버 기동이 step29·45 두 곳. step47은 step02가 이미 읽은 projectId를 다시 읽음(중복) |
| 흐름 순번이 어긋남 | name 앞 순번이 `58-영향도 분석`, `52-아키텍처 설계`, `47-2-…`처럼 흐름 순서와 맞지 않음. 헤더 주석 86줄은 버전별 변경 이력이라 현재 흐름을 읽기 어려움 |
| **엔진이 "어디서 왔는지"를 남기지 않음** | `AI_WORKFLOW_EXECUTION_STEP_HISTORY`에 이전 step과 탄 route 값이 없음. 역추적이 어려운 진짜 원인 |

정리안은 효과가 큰 순서로 적었습니다. 모두 성능을 떨어뜨리지 않고, 오히려 step 수와 이력 행이 줄어듭니다.

1. **실행 이력에 `FROM_STEP_ID`와 `ROUTE` 기록하기(엔진)**
   step마다 "step36에서 FAIL=true로 들어옴"이 남으면 실행 관리 화면에서 경로를 한 줄로 보여 줄 수 있습니다(예: `step17 → 54 → 18 → 53 → 28 → 60 → …`). 엔진은 이미 `${arrival}`을 계산하므로 값만 저장하면 됩니다. 정의 파일을 하나도 고치지 않고 역추적 문제를 가장 크게 줄이는 방법입니다. Agent에게 "이 실행의 경로와 이전 결과"를 읽는 범용 Tool로 열어 주면 1번에서 말한 대조 능력도 같이 생깁니다.

2. **판단 전용 step을 엔진 기능으로 흡수하기**
   - 횟수 제한: step에 `limit: {max: 2, scope: decision, over: step19}` 같은 속성을 두면 step31, 42, 51, 55, 56이 사라집니다.
   - 값 분기: 이미 있는 ROUTER나 `routes`가 Tool 결과 대신 `${state.x}` 값으로 바로 갈리게 하면 step43/44 같은 `containsValue`가 사라집니다. 값 경로만 읽으므로 "YAML에 로직 금지" 원칙에도 어긋나지 않습니다.
   - 예: step13에서 고른 검증 수준이 step42~44 세 step을 거치던 것이 분기 한 번으로 줄어듭니다.

3. **"문서 다시 읽기"를 한 곳으로 모으기**
   여러 파일을 한 번에 읽는 범용 Tool(`readFiles` → `state.docs.design` 등)을 두고, 개발·자동 수정·검증 앞에서 같은 step 하나를 지나게 합니다. 읽기 step 7개가 1~2개로 줄어듭니다.

- 그래서 개발 승인 의견을 `reported` 입력으로 따로 넘기고, 검증 Agent가 "사람이 알린 오류:" 기준으로 재현하게 했습니다.
- 목록 기준은 화면에 행이 보여야 PASS로 했습니다. 비었을 때 DB에도 행이 없으면 BLOCKED, DB에는 있는데 화면에 없으면 FAIL입니다.

## ④ 실제로 바뀐 줄(diff)을 넘김
- `fileChanges`에 사본 폴더 인자를 더해, 바뀐 줄을 diff로 만듭니다. 사본은 Agent가 옛 코드를 읽지 않도록 작업 폴더 밖에 둡니다.
- 자동 수정과 재개발 Agent가 이 diff를 받아, 지난 수정이 무엇을 바꿨는지 설계서 수정 이력이 아니라 실제 변경으로 봅니다.
