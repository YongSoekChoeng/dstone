## 답변

`[FILE] ` 접두어를 떼어낸 것은 LLM이나 MCP 서버가 아니었습니다. `dstone-ai-engine`의 `ToolStepRunner` 코드 안에 있던 정규식이 떼어냈습니다. 그것도 원래 다른 용도로 만든 정규식이 우연히 맞아떨어진 것이었습니다.

붙여주신 로그는 리팩터링 전 코드로 실행한 결과입니다. `inputTemplate`, `{previous}`, `VARIABLES_JSON`이 보이는 걸로 알 수 있습니다. 옛 코드 기준으로 보면 이렇게 동작했습니다.

**처리 순서 (옛 `ToolStepRunner.run()`)**
```java
String normalized = this.stripLlmArtifacts(input.renderedText());   // ① 앞 step 출력 정리
String jsonInput  = this.renderToolInput(definition.inputTemplate(), normalized, ...); // ② {previous}에 끼워넣기
```
1. `list` step의 결과는 `[FILE] notes.txt`였고, 이 값이 `__previous`에 저장됐습니다.
2. `read-notes` step이 시작될 때, 이 값을 `{previous}` 자리에 넣기 전에 `stripLlmArtifacts()`가 먼저 실행됐습니다.
3. 이 함수 안에 아래 정규식이 있었습니다.
   ```java
   LEADING_LABEL = Pattern.compile("^\\[[^\\[\\]\\n]{1,60}\\]\\s*\\n*");
   ```
   뜻은 "맨 앞에 있는 `[최대 60자 레이블]`과 뒤따르는 공백을 지운다"입니다. `[FILE] `가 이 모양과 똑같아서 지워졌고 `notes.txt`만 남았습니다.
4. 그 결과가 `.../sample/{previous}`에 들어가 `.../sample/notes.txt`가 됐습니다. 로그의 `ToolExecutor.call()` 입력이 바로 이 값입니다.

**원래는 무엇을 위한 정규식이었나**
- AGENT step의 LLM은 "레이블 붙이지 마"라고 지시해도 `[변환된 SQL]` 같은 머리말이나 코드펜스(```)를 자꾸 붙였습니다.
- 그래서 TOOL step에 넘기기 전에 그런 군더더기를 벗겨내려고 만든 방어 코드였습니다.
- MCP의 `[FILE]` 표기를 처리하려고 만든 게 아니었고, 옛 YAML 주석에도 "정식 기능이 아니라 정규식이 우연히 맞아떨어지는 것"이라고 적혀 있었습니다.
- 파일이 두 개 이상이면 `[FILE] a.txt\n[FILE] b.txt`에서 첫 번째 `[FILE] `만 지워집니다. 그러면 여러 줄이 그대로 경로에 붙어서 실패합니다.

**현재 코드에서는**
이번 리팩터링(`c73c3fe`)에서 이 암묵적인 정리 로직을 없앴습니다. 지금은 `stripLlmArtifacts`나 `LEADING_LABEL`이 코드에 없습니다. 대신 YAML에서 명시적으로 파일명을 뽑습니다.
```yaml
- id: list
  output:
    parse: lines
    pattern: '^\[FILE\] (.+)$'     # [FILE] 줄만 남기고, 괄호 그룹(파일명)만 추출
- id: read-notes
  forEach: steps.list.data.lines   # 파일 개수만큼 병렬 반복
  itemVariable: fileName
  input:
    path: "{{input.message}}/{{fileName}}"
```
이제는 이 YAML 설정이 `[FILE] ` 접두어를 떼어냅니다. 파일이 여러 개여도 파일마다 따로 읽습니다.

한 가지 주의할 점이 있습니다. 지금 테스트한 환경(Windows `D:/...`)은 옛 빌드로 실행 중입니다. 새 코드로 다시 빌드해서 띄우려면 그 환경의 PostgreSQL에서도 컬럼 이름을 먼저 바꿔야 합니다.
```sql
ALTER TABLE AI_WORKFLOW_EXECUTION RENAME COLUMN VARIABLES_JSON TO CONTEXT_JSON;
```
또 새 YAML에서는 message에 `.../mcp/server-filesystem/sample`처럼 디렉토리 절대경로를 넣어야 합니다.

## 1. 소스 정리

**삭제할 코드가 없었습니다.** 클래스, 메서드, 필드, 상수, import를 모두 참조 횟수로 검사했습니다. 이전 리팩터링에서 옛 코드가 이미 다 지워진 상태였습니다. 호출하는 곳이 안 보이는 메서드들은 Spring이 직접 부르는 것들이었습니다(컨트롤러, `@PostConstruct`, `@Bean`, `@Tool`, AOP, 인터페이스 구현).
- `approverRole`만 코드에서 읽는 곳이 없습니다. 다만 YAML에서 쓰는 기록용 항목이고, 지우면 그 YAML의 기동이 실패하므로 남겼습니다.

**주석을 고쳤습니다.**
- **틀린 이름 7곳 수정:** 옛 클래스 이름(`RedisChatMemorySession`, `DateTimeTools`, `WorkflowController`)과 옛 패키지 경로(`runtime.workflow.execution.WorkFlowExecutionService`)를 실제 이름으로 바꿨습니다. `conf/application.yml`에 남아 있던 `structuredOutput`/`primaryText` 설명도 `output.schema` 기준으로 고쳤습니다.
- **빠진 주석 추가:** 이번 리팩터링에서 바뀐 파일 가운데 주석이 없던 곳에 쉬운 말로 설명을 붙였습니다.
  - Tool/Agent/Approval 러너 3개의 `run()`
  - `WorkFlowExecutionStore`의 DB 행 변환 메서드 3개
  - `WorkFlowExecutor`의 승인 대기 결과 메서드

## 2. 문서 정리 (`docs/09.dstone-ai-engine.md`)

현재 기능만 설명하도록 새로 썼습니다.
- **변경 이력 제거:** "검증 상태"와 "이전 구조에서 달라진 점" 두 절, 그리고 본문 곳곳의 "2026-09-XX부터…" 같은 문구를 모두 뺐습니다.
- **§7 YAML 레퍼런스 신설:**
  - Workflow, Step, Agent, MCP 서버의 항목을 표로 정리했습니다(필수 여부와 기본값 포함).
  - StepType별로 쓸 수 있는 항목을 표로 정리했습니다. 잘못 쓰면 기동이 실패하는 조합도 표시했습니다.
  - step마다 `{{steps.<id>.data.<키>}}`로 꺼낼 수 있는 키 목록을 넣었습니다.
  - 값 타입과 템플릿 참조 문법을 정리하고, 샘플 Workflow/Agent 목록을 넣었습니다.
- **§8 YAML 템플릿 샘플 신설:** 복사해서 쓸 수 있는 뼈대를 넣었습니다.
  - Workflow 전체 뼈대
  - step 스니펫 10종: AGENT, AGENT+schema, TOOL(text/json/lines), SUPERVISOR, ROUTER, APPROVAL, forEach, 재시도 루프
  - Agent 뼈대 5종: 기본, Tool 사용, RAG 사용, SUPERVISOR용, ROUTER용
  - MCP 서버 뼈대 2종: STDIO, SSE
- **기존 문서의 틀린 내용 수정:**
  - Tool 로깅 AOP는 `ToolExecutor.*`에 걸려 있습니다(문서에는 `tools.*` 패키지로 적혀 있었습니다).
  - 스키마 SQL 파일 이름을 실제 이름(`01-init…`, `02-create-table…`)으로 고쳤습니다.
  - 빠져 있던 `GET /api/ai/chat`(Agent 목록 조회)을 추가했습니다.
