## 순서를 정하는 방법

"step의 순서"를 그림에서 흐름을 따라가는 순서로 정했습니다. YAML 목록 순서를 쓰면, 그림에서 새로 끼워 넣은 step이 목록 맨 끝에 붙어 번호도 맨 뒤가 되기 때문입니다.

- 시작 step에서 출발해 화살표를 따라가며 처음 만나는 순서대로 번호를 줍니다.
- 한 step에서 화살표를 따라가는 순서는 `onFailure` → `next` → `routes`(적힌 순서) → `rejectTo`입니다. 그래서 실패나 갈래로 빠지는 step은 갈라진 step 바로 다음 번호를 받습니다(sm-workflow의 step04 → step05와 같은 모양).
- 이미 번호를 받은 step으로 되돌아가는 화살표는 다시 따라가지 않습니다.
- 어디에서도 이어지지 않는 step은 맨 뒤에 붙습니다.
- 지금 첫 step이 `step01`이면 01부터, 아니면 00부터 매깁니다.

이 규칙을 지금 있는 Workflow 21개 모두에 돌려 봤는데 id가 하나도 바뀌지 않았습니다. 다만 이름으로 된 id(`sample-*`의 `classify` 등)는 디자이너에서 저장하면 `stepNN`으로 바뀝니다.

## 번호를 바꿀 때 같이 바뀌는 것
- `next`, `onFailure`, `routes`, `rejectTo`가 가리키는 대상
- `steps` 목록 순서
- 노드 위치, 꺾는 점, 연결점
- `state` 설명에 적힌 `stepNN`(예: "step14 step의 결과")
- 결과 안내 끝에 바뀐 내용이 붙습니다. 예: `(step id를 순서대로 다시 매겼습니다: aa → step00, fix → step01 …)`
- 잘못 바뀌었으면 [되돌리기]로 원래대로 돌릴 수 있습니다.
- 바꿀 것이 없으면 YAML을 다시 만들지 않으므로 파일 중간의 주석도 그대로 남습니다.
- YAML 탭에서 고친 글자를 [그림에 반영]하지 않은 채 누르면 채번하지 않고, 그렇다고 안내합니다. 이때는 고친 글자를 그대로 보내야 하기 때문입니다.

## 바뀐 채번 규칙
1. **성공 경로 먼저.** 시작에서 출발해 성공 쪽으로 이어지는 step을 END에 닿을 때까지 차례로 매깁니다.
   - AGENT/TOOL/SUPERVISOR는 `next`를 따라갑니다. `next`가 비어 있으면 엔진처럼 목록상 다음 step으로 갑니다.
   - ROUTER/APPROVAL은 `routes`에 **맨 먼저 적힌 경로**를 따라갑니다.
2. **갈래는 그다음.** 성공 경로에서 갈라지는 `onFailure`, 두 번째 이후 `routes`, `rejectTo` 쪽 step은 갈라진 순서대로 모아 두었다가, 성공 경로를 다 매긴 뒤 같은 방법으로 매깁니다.
3. 어디에서도 이어지지 않는 step은 맨 뒤에 붙습니다.
4. 목록 순서가 바뀌면, `next`를 비워 둔 step은 목록상 다음 step이 달라질 수 있습니다. 그래서 원래 가던 곳을 그 step의 `next`에 직접 적어 흐름이 바뀌지 않게 합니다.

화살표 대상, 노드 위치, state 설명의 `stepNN`을 같이 바꾸는 것과 [되돌리기]가 되는 것은 전과 같습니다.

## 이유

채번 순서는 이렇습니다.
1. **성공 경로를 먼저 매깁니다.** 시작부터 각 step의 `next`, 승인 step이면 첫 경로(`승인`)를 따라 END까지 갑니다.
   사전작업(00) → 고객요청서 읽기(01) → 고객요청사항 분석(02) → 분석서 읽기(03) → 분석 리뷰(04) → 영향도 분석(05) → … → 기존개발디렉토리초기화(12) → 개발(13) → 개발 승인(14) → END
2. **갈래는 성공 경로를 다 매긴 뒤에 붙입니다.** "리뷰 불통과 처리 결정"은 분석 리뷰(04)가 실패했을 때만 가는 `onFailure` 갈래라서 성공 경로에 없습니다. 그래서 맨 끝 번호인 **step15**를 받습니다.

전에 15개일 때 이 step이 step14가 된다고 말씀드렸는데, step이 하나 늘어서 step15가 된 것입니다.

## 다른 방식을 원하시면
갈래 step을 갈라진 step 바로 뒤에 두고 싶다면(리뷰 불통과 처리 = step05, 영향도 분석 = step06 …) 첫 번째 구현 방식으로 되돌리면 됩니다. 그 방식은 실패나 갈래 쪽 step에 갈라진 step 바로 다음 번호를 줍니다. 원하시는 쪽을 말씀해 주시면 그렇게 맞추겠습니다.

## 규칙
첫 step부터 화살표를 따라가며 처음 만나는 순서대로 매깁니다. 한 step에서는 `onFailure` → `next` → `routes`(적힌 순서) → `rejectTo` 순으로 따라갑니다. 그래서 실패나 갈래 쪽 step이 갈라진 step 바로 다음 번호를 받습니다.

두 번째 방식에서 추가한 보완은 그대로 두었습니다. 목록 순서가 바뀌면 `next`를 비워 둔 step은 엔진이 가는 곳(목록상 다음 step)이 달라질 수 있습니다. 그래서 그런 step에는 원래 가던 곳을 `next`로 직접 적습니다. 처음 방식에는 이 처리가 없었습니다.

- 엔진의 Tool 결과 상한(`max-result-chars` 60,000자)은 TOOL step에도 걸립니다. 그래서 60,000자를 넘는 문서는 여전히 잘립니다.

**sm-workflow 1.3.1**: 문서를 읽어 다음 Agent에 넘기는 step 4개(`01`, `02`, `03-1`, `03-2` 문서)에 `maxChars: 60000`을 넣고, 파일 맨 위 주석에 이유를 적었습니다.

**검증**
- 34,019자 파일을 TOOL step으로 읽으면 `maxChars`가 없을 때는 30,074자(잘림 안내 포함), `maxChars: 60000`이면 34,019자 전부 읽혔습니다.
- 새 단위 테스트 `FileToolReadTest`(3건)를 포함한 관련 테스트가 통과했고, sm-workflow 엔진 검사도 통과했습니다.
- 전체 테스트에서 `RequesterContextTest` 2건이 실패하지만, 이번 변경을 빼고 돌려도 똑같이 실패하는 원래 있던 문제입니다. 사용자 헤더를 API 키가 있을 때만 믿도록 바뀐 뒤 테스트가 따라가지 않은 것으로 보입니다.

**문서**: `docs/09.dstone-ai-engine.md`(Tool 표의 `readFile`)와 `.claude/docs/ai-engine-tuning.md`(이번 사례 기록)를 고쳤습니다.

## 2. LLM이 한 일을 추측한 방법
추측이라기보다 **남아 있는 기록을 겹쳐 보고, 직접 보지 못한 부분은 범위를 좁혀 가는 방식**입니다. 순서는 이렇습니다.

1. **어디서 멈췄는지 찾기 (DB)**
   `ai_workflow_execution`의 `error_message`와 `ai_workflow_execution_step_history`에서 실패한 step, 걸린 시간, 실패 사유를 봅니다. 여기서 "step14, `finishReason=LENGTH`, 누적 91,631토큰"까지 나옵니다.

2. **호출 흐름을 시간순으로 재구성하기 (`execution.log`)**
   엔진이 남기는 두 종류의 줄을 시각순으로 뽑았습니다.
   - `AgentCallStatsAdvisor`: LLM 호출마다 입력·출력 토큰과 요청한 Tool
   - `ConfigTool`: Tool 호출마다 인자와 결과 크기

   이렇게 하면 "4회차까지 정상으로 Tool을 부르다가, 5회차에서 Tool 없이 60,000토큰"처럼 **어느 라운드에서 무엇이 달라졌는지**가 보입니다. 정상 라운드의 출력은 수백~수천 토큰이니, 60,000토큰은 한눈에 이상값입니다.

3. **바깥 사건과 시각 맞춰 보기 (파일 시각)**
   파일과 폴더의 수정 시각(`ls --full-time`)을 로그 시각과 비교했습니다. "소스를 11:28:47에 넣었는데 마지막 요청은 11:28:23에 나갔다"는 판단이 여기서 나왔습니다. 모델이 볼 수 없었던 일을 원인 후보에서 빼는 단계입니다.

4. **모델의 머릿속 직접 보기 (LLM 응답 로그)** ← 가장 결정적인 단계
   RES 로그의 `reasoningContent`(추론 글)를 꺼내 처음과 끝을 읽고, **같은 줄이 몇 번 나오는지 세었습니다.**
   - 첫 사례: 547줄 중 서로 다른 줄 107개, "impact.md 작성." 32번
   - 이번 사례: 같은 문장 하나가 끝까지 반복

   반복되는 문장이 곧 모델이 막힌 지점입니다. 이번에는 "design document got truncated"라는 말이 직접 나와서, REQ 로그에서 실제로 잘렸는지("앞 30000자만" 안내문)를 찾아 확인했습니다.

5. **코드로 원인 따라가기**
   "30000"이라는 숫자로 소스를 검색해 `FileTool.DEFAULT_MAX_READ_CHARS`와 `max-read-chars` 설정을 찾았습니다. TOOL step 결과가 그대로 `state.design`에 들어간다는 것도 확인했습니다.

6. **성공과 실패 비교하기**
   같은 Agent의 성공 사례와 나란히 놓고 시간, 라운드 수, 마지막 라운드 출력, 추론 길이를 비교했습니다. 하나만 보면 우연인지 원인인지 구분이 안 되기 때문입니다.

**구분해서 말씀드린 것**
- 4번 로그가 없던 경우(첫 분석의 10:33, 10:51, 10:55 실패)는 "추정"이라고 밝혔습니다.
- 로그가 생긴 뒤에는 "확인"이라고 했습니다.
- 숫자(토큰, 시각, 반복 횟수)는 모두 로그에서 그대로 꺼낸 값입니다.

**앞으로 이 방법이 잘 통하려면**: 지금처럼 LLM 응답 로그를 켜 두는 것이 가장 중요합니다. 다만 이 로그는 Agent 호출 한 번마다 첫 요청과 마지막 응답만 남깁니다. 중간 라운드에서 루프가 생기면 그 라운드의 추론은 보이지 않습니다.

- **자동 갱신 중**:
  - 다른 페이지로 넘겼거나 줄을 직접 골랐으면 그 페이지에 머뭅니다. 보던 페이지가 갑자기 바뀌지 않습니다.

## 2. 설계 Agent (`sm-architect-agent.md` 1.5.0)
- **지적이 있으면 설계서를 새로 쓰지 않습니다.** 기존 산출물을 읽고 지적과 관련된 부분만 `editFileTexts`로 고칩니다. 앞선 지적으로 고친 내용(예: 12:35의 UPLOADS 수정)이 다음 재설계에서 사라지지 않게 하려는 것입니다.

## 문제점

**1. 생성한 코드를 Workflow 안에서 아무도 검증하지 않음 (가장 큼)**
- 개발 step은 파일을 쓰고 "completed: 17"로 끝납니다. 컴파일도 실행도 해 보지 않습니다.
- 그래서 사람이 컴파일러와 테스터 역할을 하고 있습니다. "ImageBoardController 컴파일 오류", "UPLOADS가 없음"은 컴파일만 했어도 Workflow 안에서 잡혔을 오류입니다.

**2. 재작업할 때마다 처음부터 다시 만듦**

## 2. 지워야 하는 파일은? (질문하신 부분)
Agent가 파일을 직접 지우지 않게 하고, **삭제 목록**으로 처리합니다.
- 설계 Agent는 지울 파일을 '변경 상세'와 태스크에 "파일 삭제"로 적습니다.
- 개발 Agent는 그 경로를 `dev-resources/_delete-files.txt`에 소스 루트 기준 상대경로로 한 줄씩 적습니다. 원본에 있던 파일이든, 앞서 `dev-resources`에 만든 파일이든 똑같이 적습니다.
- 컴파일 확인은 이 목록의 파일을 사본에서 지운 뒤 컴파일합니다. 실제 반영할 때도 이 목록대로 지우면 됩니다.

`dev-resources`를 언제 비우는지는 바꾸지 않았습니다.
- 처음 개발할 때와 재설계 뒤에는 비웁니다(step13). 설계서가 기준이라 새로 만드는 것이 맞고, 이제 설계 Agent가 지적된 곳만 고치므로 설계 자체가 흔들리지 않습니다.
