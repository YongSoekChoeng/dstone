## 순서를 정하는 방법

"step의 순서"를 그림에서 흐름을 따라가는 순서로 정했습니다. YAML 목록 순서를 쓰면, 그림에서 새로 끼워 넣은 step이 목록 맨 끝에 붙어 번호도 맨 뒤가 되기 때문입니다.

- 시작 step에서 출발해 화살표를 따라가며 처음 만나는 순서대로 번호를 줍니다.
- 한 step에서 화살표를 따라가는 순서는 `onFailure` → `next` → `routes`(적힌 순서) → `rejectTo`입니다. 그래서 실패나 갈래로 빠지는 step은 갈라진 step 바로 다음 번호를 받습니다(sm-workflow의 step04 → step05와 같은 모양).
- 이미 번호를 받은 step으로 되돌아가는 화살표는 다시 따라가지 않습니다.
- 어디에서도 이어지지 않는 step은 맨 뒤에 붙습니다.
- 지금 첫 step이 `step01`이면 01부터, 아니면 00부터 매깁니다.

이 규칙을 지금 있는 Workflow 21개 모두에 돌려 봤는데 id가 하나도 바뀌지 않았습니다. 다만 이름으로 된 id(`sample-*`의 `classify` 등)는 디자이너에서 저장하면 `stepNN`으로 바뀝니다.

## 번호를 바꿀 때 같이 바뀌는 것
- `next`, `onFailure`, `routes`, `rejectTo`가 가리키는 대상
- `steps` 목록 순서
- 노드 위치, 꺾는 점, 연결점
- `state` 설명에 적힌 `stepNN`(예: "step14 step의 결과")
- 결과 안내 끝에 바뀐 내용이 붙습니다. 예: `(step id를 순서대로 다시 매겼습니다: aa → step00, fix → step01 …)`
- 잘못 바뀌었으면 [되돌리기]로 원래대로 돌릴 수 있습니다.
- 바꿀 것이 없으면 YAML을 다시 만들지 않으므로 파일 중간의 주석도 그대로 남습니다.
- YAML 탭에서 고친 글자를 [그림에 반영]하지 않은 채 누르면 채번하지 않고, 그렇다고 안내합니다. 이때는 고친 글자를 그대로 보내야 하기 때문입니다.

## 바뀐 채번 규칙
1. **성공 경로 먼저.** 시작에서 출발해 성공 쪽으로 이어지는 step을 END에 닿을 때까지 차례로 매깁니다.
   - AGENT/TOOL/SUPERVISOR는 `next`를 따라갑니다. `next`가 비어 있으면 엔진처럼 목록상 다음 step으로 갑니다.
   - ROUTER/APPROVAL은 `routes`에 **맨 먼저 적힌 경로**를 따라갑니다.
2. **갈래는 그다음.** 성공 경로에서 갈라지는 `onFailure`, 두 번째 이후 `routes`, `rejectTo` 쪽 step은 갈라진 순서대로 모아 두었다가, 성공 경로를 다 매긴 뒤 같은 방법으로 매깁니다.
3. 어디에서도 이어지지 않는 step은 맨 뒤에 붙습니다.
4. 목록 순서가 바뀌면, `next`를 비워 둔 step은 목록상 다음 step이 달라질 수 있습니다. 그래서 원래 가던 곳을 그 step의 `next`에 직접 적어 흐름이 바뀌지 않게 합니다.

화살표 대상, 노드 위치, state 설명의 `stepNN`을 같이 바꾸는 것과 [되돌리기]가 되는 것은 전과 같습니다.

## 답변

규칙대로 나온 결과입니다. 바로 전에 바꾼 채번 규칙("시작~END까지 지나가는 순서")이 그렇게 정합니다.

## 이유
Windows 쪽 `sm-workflow.yml`(10:33 저장본)은 step이 16개입니다. "기존개발디렉토리초기화" step이 새로 들어가서 그렇습니다. WSL 저장소에는 아직 이 변경이 없고 15개입니다.

채번 순서는 이렇습니다.
1. **성공 경로를 먼저 매깁니다.** 시작부터 각 step의 `next`, 승인 step이면 첫 경로(`승인`)를 따라 END까지 갑니다.
   사전작업(00) → 고객요청서 읽기(01) → 고객요청사항 분석(02) → 분석서 읽기(03) → 분석 리뷰(04) → 영향도 분석(05) → … → 기존개발디렉토리초기화(12) → 개발(13) → 개발 승인(14) → END
2. **갈래는 성공 경로를 다 매긴 뒤에 붙입니다.** "리뷰 불통과 처리 결정"은 분석 리뷰(04)가 실패했을 때만 가는 `onFailure` 갈래라서 성공 경로에 없습니다. 그래서 맨 끝 번호인 **step15**를 받습니다.

전에 15개일 때 이 step이 step14가 된다고 말씀드렸는데, step이 하나 늘어서 step15가 된 것입니다.

## 다른 방식을 원하시면
갈래 step을 갈라진 step 바로 뒤에 두고 싶다면(리뷰 불통과 처리 = step05, 영향도 분석 = step06 …) 첫 번째 구현 방식으로 되돌리면 됩니다. 그 방식은 실패나 갈래 쪽 step에 갈라진 step 바로 다음 번호를 줍니다. 원하시는 쪽을 말씀해 주시면 그렇게 맞추겠습니다.

## 답변

채번 방식을 갈래 step이 갈라진 step 바로 뒤 번호를 받는 방식으로 되돌렸습니다. 8181 포트 사본에서 브라우저로 확인했습니다.

## 규칙
첫 step부터 화살표를 따라가며 처음 만나는 순서대로 매깁니다. 한 step에서는 `onFailure` → `next` → `routes`(적힌 순서) → `rejectTo` 순으로 따라갑니다. 그래서 실패나 갈래 쪽 step이 갈라진 step 바로 다음 번호를 받습니다.

두 번째 방식에서 추가한 보완은 그대로 두었습니다. 목록 순서가 바뀌면 `next`를 비워 둔 step은 엔진이 가는 곳(목록상 다음 step)이 달라질 수 있습니다. 그래서 그런 step에는 원래 가던 곳을 `next`로 직접 적습니다. 처음 방식에는 이 처리가 없었습니다.

## 확인 결과
- **Windows 쪽 sm-workflow(16개)**: 리뷰 불통과 처리 결정 **step15 → step05**. 영향도 분석부터 개발 승인까지는 하나씩 밀려 step06~step15가 됩니다. 화살표 대상과 state 설명도 맞게 바뀌었습니다.
  - 아직 저장하지 않았다면, 디자이너에서 열고 [저장]하면 이 번호로 저장됩니다.
- **WSL 저장소의 Workflow 21개**: 모두 번호가 그대로입니다.
- **`next`를 비워 둔 step이 있는 시험 Workflow**: 순서가 바뀌어도 원래 가던 곳이 `next: step02`로 들어가 흐름이 유지됐습니다.
- 스크립트 오류는 없었습니다.

`workflow-designer.js`(채번 로직과 id 칸 안내 문구)와 `docs/09.dstone-ai-engine.md`(18.7절)를 고쳤습니다. 앞서 고친 Workflow 테스트 화면의 실행 ID 클릭 수정 3개 파일과 함께 아직 커밋하지 않았습니다.
