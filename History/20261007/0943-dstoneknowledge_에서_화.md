---

## 답변

맞습니다. 확인해 보니 `dstone-knowledge`에는 리치클라이언트 처리가 전혀 없습니다. 코드와 문서 어디에도 WebSquare / Nexacro / X-Platform / MiPlatform 관련 내용이 없고, 화면은 JSP 하나만 전제로 만들어져 있습니다.

## 지금 리치클라이언트 프로젝트를 분석하면 생기는 일

| 제품 | 화면 파일 | 현재 동작 |
|---|---|---|
| Nexacro / X-Platform | `.xfdl`, `.xadl`, `.xjs` | `FileClassifier.languageOf()`가 모르는 확장자라 SCAN 목록에도 안 들어갑니다. |
| WebSquare | `.xml` (`w2:` 네임스페이스) | 파일 목록에는 들어가지만 화면으로 알아보는 규칙이 없습니다. |
| 공통 스크립트 | `.js` | 스캔 대상이 아닙니다. |

- **서버 쪽은 영향이 없습니다.** 컨트롤러가 Spring이면 엔드포인트, 호출 그래프, SQL, 테이블까지는 그대로 나옵니다.
- **화면 쪽이 통째로 빕니다.** `화면 ─REQUESTS→ 메소드` 연결을 `JspPlugin`만 만들기 때문에, 영향 분석의 "영향받는 화면"과 노드 맵의 화면 열이 비고, 화면(`VIEW`) 문서가 없어 화면 이름으로 검색도 안 됩니다.
- **`RENDERS`도 생기지 않습니다.** 리치클라이언트는 서버가 화면을 열어 주지 않고 데이터만 돌려주므로, 화면 연결은 `REQUESTS` 하나에 달려 있습니다.

## 넣는다면

구조는 지금 틀에 그대로 얹을 수 있습니다. SCAN에 확장자와 파일 용도를 추가하고, 제품별 `SemanticPlugin`이 화면 파일에서 요청 주소를 뽑아 `REQUESTS`를 만들고, `DocumentPass`가 `VIEW` 문서를 쓰면 됩니다. 영향 분석과 호출 트리는 `REQUESTS`만 생기면 따라오지만, 노드 맵은 화면 노드를 JSP로 묶고 있어서 "화면"으로 넓혀야 합니다.

어려운 부분은 주소 추출입니다.

- **Nexacro / X-Platform**: `transaction("id", "svc::/order/list.do", ...)`의 `svc::` 접두어는 `.xadl`이나 `typedefinition`의 서비스 정의를 읽어 실제 경로로 풀어야 합니다.
- **WebSquare**: `<xf:submission action="...">`은 쉽게 읽히지만, 스크립트 안에서 `$p.ajax`나 공통 함수로 부르는 경우가 섞여 있습니다.
- **공통 함수 래핑**: 실무 프로젝트는 대부분 `gfn_transaction(...)` 같은 공통 함수로 감싸고 주소를 변수나 인자로 넘깁니다. 그래서 `.js`/`.xjs`도 읽어야 하고, `ConstantEvaluator`처럼 "계산되는 것만 연결하고 모르면 미해결로 남긴다"는 원칙을 스크립트에도 적용해야 합니다.

## 진행하려면 필요한 것

지금 있는 샘플 두 개(`anybiz_prd`, `cms4_prd`)는 둘 다 JSP 기반이라 검증할 대상이 없습니다. 공통 함수 래핑 방식은 프로젝트마다 달라서, 실제 소스 없이 만들면 `struts-app`처럼 손으로 만든 샘플만 통과하는 규칙이 될 가능성이 큽니다.

1. 실제 리치클라이언트 프로젝트 소스(일부라도)를 `/app/sampleApps/`에 둘 수 있을까요?
2. 세 제품 중 어느 것부터 할까요? 소스가 없다면 Nexacro부터 권합니다. X-Platform과 파일 형식·`transaction` 방식이 거의 같아 규칙 하나로 두 제품을 덮을 수 있습니다.

정해 주시면 설계안(추가할 파일 종류, 관계, 플러그인, 화면·문서 변경 범위)부터 정리하겠습니다.
