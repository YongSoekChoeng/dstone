## 지금 리치클라이언트 프로젝트를 분석하면 생기는 일

| 제품 | 화면 파일 | 현재 동작 |
|---|---|---|
| Nexacro / X-Platform | `.xfdl`, `.xadl`, `.xjs` | `FileClassifier.languageOf()`가 모르는 확장자라 SCAN 목록에도 안 들어갑니다. |
| WebSquare | `.xml` (`w2:` 네임스페이스) | 파일 목록에는 들어가지만 화면으로 알아보는 규칙이 없습니다. |
| 공통 스크립트 | `.js` | 스캔 대상이 아닙니다. |

- **서버 쪽은 영향이 없습니다.** 컨트롤러가 Spring이면 엔드포인트, 호출 그래프, SQL, 테이블까지는 그대로 나옵니다.
- **화면 쪽이 통째로 빕니다.** `화면 ─REQUESTS→ 메소드` 연결을 `JspPlugin`만 만들기 때문에, 영향 분석의 "영향받는 화면"과 노드 맵의 화면 열이 비고, 화면(`VIEW`) 문서가 없어 화면 이름으로 검색도 안 됩니다.
- **`RENDERS`도 생기지 않습니다.** 리치클라이언트는 서버가 화면을 열어 주지 않고 데이터만 돌려주므로, 화면 연결은 `REQUESTS` 하나에 달려 있습니다.

## 넣는다면

구조는 지금 틀에 그대로 얹을 수 있습니다. SCAN에 확장자와 파일 용도를 추가하고, 제품별 `SemanticPlugin`이 화면 파일에서 요청 주소를 뽑아 `REQUESTS`를 만들고, `DocumentPass`가 `VIEW` 문서를 쓰면 됩니다. 영향 분석과 호출 트리는 `REQUESTS`만 생기면 따라오지만, 노드 맵은 화면 노드를 JSP로 묶고 있어서 "화면"으로 넓혀야 합니다.

어려운 부분은 주소 추출입니다.

- **Nexacro / X-Platform**: `transaction("id", "svc::/order/list.do", ...)`의 `svc::` 접두어는 `.xadl`이나 `typedefinition`의 서비스 정의를 읽어 실제 경로로 풀어야 합니다.
- **WebSquare**: `<xf:submission action="...">`은 쉽게 읽히지만, 스크립트 안에서 `$p.ajax`나 공통 함수로 부르는 경우가 섞여 있습니다.
- **공통 함수 래핑**: 실무 프로젝트는 대부분 `gfn_transaction(...)` 같은 공통 함수로 감싸고 주소를 변수나 인자로 넘깁니다. 그래서 `.js`/`.xjs`도 읽어야 하고, `ConstantEvaluator`처럼 "계산되는 것만 연결하고 모르면 미해결로 남긴다"는 원칙을 스크립트에도 적용해야 합니다.

## 무엇을 넣었나

- **쿼리 XML 읽기**: `<document><query|combo|delete id><statement>` 파일을 `QUERY_XML`로 분류해 SQL로 읽습니다. 네임스페이스는 파일 이름이고, Velocity 지시문(`#if … #end`)은 떼고 안의 SQL은 모두 남깁니다.
- **호출 연결**: `new QueryProperty("파일명.쿼리ID")`를 SQL 호출로 봅니다. 그 객체를 만든 DAO 메소드가 SQL을 실행하는 것으로 잇습니다.
- **중복 파일 처리**: 같은 SQL 파일이 `WEB-INF/src`와 `WEB-INF/classes`에 둘 다 있으면, 호출한 Java와 같은 소스 루트의 것을 고릅니다. HI-Japan은 55개 파일이 겹치고 전부 `src`가 최신인데, 처음에는 오래된 `classes` 쪽으로 이어져서 고쳤습니다.

## 답변

계층 규칙과 거래 ID 진입점을 넣었고 HI-Japan에서 확인했습니다. 커밋은 하지 않았습니다.

## 무엇을 넣었나

- **계층 규칙**: 이름 끝 글자(`M`/`S`/`D`) 대신 상위 클래스로 계층을 정합니다. 한 글자 끝말은 아무 클래스에나 맞는데, 이 프로젝트는 역할마다 정해진 프레임워크 클래스를 상속하기 때문입니다. 규칙은 설정 `dstone.knowledge.semantic.layer.super-types`에 "상위 타입=계층"으로 적습니다.
- **거래 진입점**: 거래 호출 규칙의 이름 틀(`perform{id}`)에 맞는 공개 메소드를 진입점 종류 `TRANSACTION`으로 올립니다. 주소 자리에는 거래 ID가 들어갑니다.

기본 설정에 넣어 둔 규칙은 이렇습니다.

| 상위 클래스 | 계층 |
|---|---|
| `AbstractMainService` | `CONTROLLER` |
| `AbstractSubService` | `SERVICE` |
| `JdbcDAO`, `JdbcRowGetter` | `REPOSITORY` |
| `BusinessVO` | `MODEL` |

`AbstractMainService`(…M 클래스)를 `CONTROLLER`로 둔 것은 제 판단입니다. 화면의 요청을 처음 받는 자리라서 노드 맵의 화면 → 컨트롤러 → 서비스 → DAO 열에 맞췄습니다. `SERVICE`가 맞다고 보시면 설정에서 한 단어만 바꾸면 됩니다.

| | 전 | 후 |

- **검색**: 메소드 문서에 "진입점: 거래 ID JCST0200M01S", "계층: CONTROLLER"가 들어가 거래 ID로 찾을 수 있습니다.

## 확인하지 못한 것 / 한계

- **노드 맵 화면**: 계층 값이 API로 내려오는 것까지만 확인했고, 브라우저에서 열이 실제로 나뉘는 모습은 보지 않았습니다.
