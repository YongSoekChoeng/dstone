## 답변

4번 실패한 원인부터 말씀드리면, 모델이 약해서라기보다 **Agent가 실행 중인 시스템을 한 번도 보지 않고 코드만 읽어 추측했기 때문**입니다. 실행 기록을 따라가 보니 진짜 원인도 따로 있었습니다.

## 1. 삭제가 안 되는 진짜 원인

삭제 SQL의 조건 `mb_id`에 값이 들어가지 않습니다.

- `imageboard-mapper.xml:84`: `DELETE ... WHERE mb_id = #{mb_id} AND seq = #{seq}`
- `ImageBoardController.java:121`: 로그인 사용자 `user`를 가져오기만 하고 넘기지 않습니다.
- `ImageBoardService.java:65-66`: 새 VO를 만들고 `seq`만 넣습니다.

그래서 `mb_id = NULL` 조건으로 0건이 지워지고, 서버는 오류 없이 `count: 0`을 돌려줍니다. 화면은 목록을 다시 읽으니 "삭제가 안 된다"로만 보입니다. 원본 `SampleBoardController.toModels()`(125줄)는 `vo.setMb_id(user.getMb_id())`를 넣으므로, 이 부분만 비교했어도 찾을 수 있었습니다.

작업 폴더는 D: 드라이브에 있어 고치지 않았습니다(`/app/dstone` 밖은 수정하지 않는 규칙).

## 2. 왜 4번 다 놓쳤나 (실행 로그 기준)

| 회차 | 모델 | Tool 호출 | 결과 |
|---|---|---|---|
| 09:43 | qwen | 파일 검색·읽기 26, 수정 3, 컴파일 1 | 등록 문제 수정 |
| 09:56 | qwen | 파일 검색·읽기 20, 수정 4, 컴파일 1 | **사람이 서버 로그를 붙여 줘서** 그 오류는 정확히 고침 |
| 10:14, 10:17 | gpt-oss | — | 빈 답으로 실패 |
| 10:29 | qwen | 파일 검색·읽기 39, 수정 2, 컴파일 1 | 체크박스를 고쳤지만 근거가 약했고 `mb_id`는 놓침 |

- **관측 Tool을 한 번도 쓰지 않았습니다.** `dbQuery`는 허용돼 있고 testApp DB도 등록돼 있는데 다섯 번 모두 0회였습니다. 삭제한 뒤 SELECT 한 번이면 행이 그대로 있다는 게 드러났을 겁니다.
- **증상에 근거가 없었습니다.** "여전히 삭제가 안 돼"만 받으면 Agent는 추측할 수밖에 없습니다. 서버 로그가 함께 온 2회차만 정확히 고쳤습니다.
- **확인 수단이 컴파일뿐입니다.** 고친 게 실제로 동작하는지 확인할 방법이 없어서 추측으로 고친 결과도 그대로 통과했습니다.
- **입력이 계속 불어났습니다.** qwen 회차는 30라운드 동안 입력이 누적 약 120만 토큰이었습니다. 27B 모델에서는 정확도가 떨어질 수밖에 없습니다.

`ai-engine-agent-principles.md`의 분류로 보면 **입력 문제 + Skill(방법) 부족 + 검증 구조 부족**입니다. 모델을 바꾸는 것만으로는 해결되지 않습니다.

## 3. 개선 방법 (효과 큰 순)

1. **디버깅 Skill 추가 (`troubleshooting`, 바로 가능)**
   - 증상 유형마다 먼저 볼 것을 정합니다. 예를 들어 "오류 없이 반영 안 됨"이면 반환 건수와 `dbQuery`로 DB 상태부터 확인합니다.
   - **SQL 파라미터 대조표**를 채우게 합니다. 매퍼의 `#{...}`마다 그 값을 넣는 코드를 파일:줄로 적습니다. 이번 `mb_id`는 이 표로 바로 걸립니다.
   - 같은 Skill을 `sm-developer-agent`에도 preload하면 이런 버그가 애초에 덜 생깁니다.
2. **이번 사례를 평가 세트에 추가 (`SmAgentEvalTest`)**
   - 10:29 회차 입력을 그대로 쓰고, `causes`에 `mb_id`가 들어 있는지 판정합니다.
   - 그러면 Skill, qwen과 gpt-oss, 아래 개선들의 효과를 감이 아니라 수치로 비교할 수 있습니다.
3. **증거를 넣는 구조**
   - 개발 승인에서 [전문가 해결]을 고를 때, 브라우저 Network 응답이나 서버 로그를 붙여 달라는 안내를 띄웁니다.
   - 사람이 증거를 붙이지 않으면 Agent가 먼저 `dbQuery`로 확인할 내용을 정하게 합니다.
4. **재현까지 하는 Agent (가장 큰 변화, 작업도 큼)**
   - 브라우저 MCP(Playwright, 오프라인 설치 가능)로 실제 화면을 누르고 콘솔·네트워크를 보게 합니다. MCP 정의는 이미 지원합니다.
   - 전제 조건이 있습니다. 지금은 dev-resources를 testApp에 사람이 직접 반영해야 하므로, 이 반영을 자동으로 하는 범용 Tool이 먼저 필요합니다.
5. **엔진에서 빈 답 재시도**: 오전에 말씀드린 gpt-oss 빈 답 대책입니다.

**추천은 1+2를 먼저 하는 것입니다.** 폐쇄망 POC에서도 그대로 쓸 수 있고, 이번 사례로 효과를 바로 측정할 수 있습니다. 그다음 3, 여유가 있을 때 4를 하면 됩니다. 1+2부터 진행할까요?

## 3번: 증거를 넣는 구조

인터넷에 연결할 일이 없습니다.
- **승인 화면 안내 문구:** ai-engine의 정적 화면만 고치면 됩니다.
- **Workflow·Agent 정의 수정:** `conf/definitions` 아래 파일만 바꿉니다.
- **`dbQuery`로 확인:** 이미 있는 Tool입니다. testApp DB(MySQL)만 내부망에서 닿으면 됩니다.

## 4번: 재현까지 하는 Agent

부품 세 가지 모두 오프라인으로 할 수 있습니다.

| 부품 | 오프라인에서 하는 법 | 주의할 점 |
|---|---|---|
| **Playwright MCP 서버** (`@playwright/mcp`) | 인터넷이 되는 PC에서 설치한 `node_modules`나 `npm pack`으로 만든 tgz를 반입합니다. MCP 정의의 `command`에는 `npx -y`가 아니라 로컬 경로를 적습니다(`node .../@playwright/mcp/cli.js`). | 지금 샘플(`sample-filesystem.yml`)은 `npx -y`라서 실행할 때 내려받으려고 합니다. 폐쇄망에서는 실패합니다. |
| **브라우저** | Windows에 이미 깔린 Edge를 쓰면(`--browser msedge`) 브라우저를 따로 내려받지 않아도 됩니다. 이 PC에도 Edge가 있습니다. Chromium을 쓰려면 `ms-playwright` 폴더를 통째로 복사합니다. | 고객사 PC 정책 때문에 Edge 자동 조작이 막혀 있는지 미리 확인해야 합니다. |
| **Node.js** | 설치 파일 하나만 반입하면 됩니다. | Windows라면 `MCP_STDIO_COMMAND_PREFIX`(`cmd.exe /c`)가 필요합니다. 이미 지원합니다. |
| **dev-resources를 testApp에 반영하는 범용 Tool** | 파일 복사와 앱 재시작이라 네트워크가 필요 없습니다. Java 재빌드는 Maven 로컬 저장소가 이미 차 있어야 합니다. 지금 `compileJava`도 같은 조건으로 돌고 있습니다. | JSP·매퍼는 복사만으로 반영되지만, Java를 고쳤으면 재시작해야 합니다. |

## 오프라인보다 더 따져 볼 점

- **모델이 감당할 수 있는 양:** 브라우저 MCP는 화면 상태(접근성 트리)를 통째로 돌려줘서 토큰을 많이 씁니다. 지금도 qwen 27B가 한 번 실행에 누적 약 120만 토큰을 썼으므로, 4번은 2번 평가 세트로 먼저 감당이 되는지 재 보고 들여야 합니다.
- **로그인:** testApp은 로그인과 CSRF가 있습니다. 시험용 계정을 정의 파일 입력으로 받아야 합니다. 비밀번호는 `ENC(...)`로 넣습니다.
- **고객 운영 환경을 건드리지 않게:** 브라우저로 실제 데이터를 지우게 되므로, 재현은 시험 서버에서만 하도록 Workflow에서 막아야 합니다.

정리하면 3번은 지금 당장 할 수 있습니다. 4번은 오프라인 장벽보다 토큰과 시험 환경 준비가 더 큰 일입니다. 순서는 처음 제안대로 **1+2 → 3 → 4**를 권합니다. 1+2부터 시작할까요?
