## 진행 계획

### 0. 프로젝트 관례 Skill을 Agent에서 떼어 내기 (엔진 + 정의)
- **엔진:** `skills.allowed`에 폴더 단위 지정(예: `projects/**`)을 허용합니다. 그 폴더 아래 Skill이 모두 후보가 되고, Agent는 설명을 보고 맞는 것만 부릅니다.
- **정의:** `gnx-crud-screen`을 `skills/projects/` 아래로 옮기고, 설명은 "패키지가 `kr.co.gnx`인 소스" 같은 **코드 모양**으로 적습니다. Agent 5개에는 `projects/**` 한 줄만 둡니다.
- **효과:** 새 프로젝트는 Skill 폴더 하나만 추가하면 되고, Agent·Workflow는 고치지 않습니다.

### 1. 범용 디버깅 Skill `troubleshooting` (정의)
- 증상 유형마다 먼저 볼 것을 표로 둡니다. 예: "오류 없이 반영 안 됨 → 반환 건수·DB 상태 / 화면 오류 → 콘솔·네트워크 / 서버 오류 → 로그 스택"
- **값 대조표**를 채우게 합니다. 화면 → 요청 → Controller → SQL 파라미터마다 그 값을 넣는 곳을 파일:줄로 적고, 빈 칸이 생기면 그곳을 원인 후보로 봅니다.
- 고친 뒤에는 무엇으로 확인했는지 적게 하고, 확인하지 못했으면 사람이 볼 것을 적게 합니다.
- 특정 앱·라이브러리 이름은 넣지 않습니다. `sm-troubleshooter-agent`에는 preload로, `sm-developer-agent`에는 예방용으로 같은 Skill을 붙입니다.

### 2. 평가 세트에 사례 추가 (테스트)
- 오늘 실행의 5회차 입력을 사례로 넣고, `causes`에 SQL 조건값이 빠졌다는 지적이 있는지 판정합니다.
- 소스 경로와 DB 연결은 지금처럼 시스템 속성으로 받아 특정 앱에 묶지 않습니다.

### 3. 증거를 넣는 구조 (화면 + 요청서 + Workflow)
- **요청서:** 선택 항목 `## 시험환경`을 추가합니다. DB 연결 별칭, 접속 URL, 시험 계정, 서버 로그 경로, 반영 명령을 적습니다. 범용 Tool `readMarkdownSection`으로 읽어 Agent 입력으로 넘기고, 이 항목이 없으면 지금처럼 동작합니다.
- **승인 화면:** 의견칸에 "재현 순서, 브라우저 네트워크 응답, 서버 로그를 붙이면 정확해집니다"라는 안내를 넣습니다. 특정 Workflow에 묶이지 않는 범용 문구로 씁니다.
- **Agent:** DB 연결 별칭을 받았으면 `dbQuery`로 상태를 먼저 확인하게 합니다. 서버 로그 경로를 받았으면 `readFileLines`로 끝부분을 읽게 합니다.

### 4. 재현하는 Agent (Tool + MCP + Workflow)
- **반영 Tool:** 범용 Tool `applyOverlay`를 새로 만듭니다. 덮어쓸 폴더, 대상 경로, 지울 목록, 이후 실행할 명령을 인자로 받습니다. 명령은 기존 `ShellExecTool`의 허용 목록을 그대로 따릅니다. 대상 앱의 재시작·빌드 방법은 요청서의 `시험환경`이 정합니다.
- **브라우저:** Playwright MCP 정의를 추가합니다. 로컬 설치 경로로 실행해 오프라인에서도 돌게 하고, `시험환경`이 있을 때만 Agent가 씁니다.
- **Workflow:** 전문가 해결은 "반영 → 재현 → 고침 → 재반영 → 재확인" 순서로 돕니다. `시험환경`이 없으면 지금처럼 코드 분석만 합니다.

### 5. 엔진에서 빈 답 재시도
- 답이 비었고 Tool 호출도 없이 끝나면, Agent 설정과 상관없이 한 번 더 부릅니다.
- 실패 사유도 "LLM 응답이 JSON이 아닙니다: "(뒤가 빈칸) 대신 "모델이 빈 답을 냈습니다"로 남깁니다.
