## 질문

dstone-boot>ai 의 workflow designer 에서
approval 에 대한 편집은 어떻게 하지?

---

## 답변

APPROVAL은 전용 창이 없고, **캔버스의 step과 화살표를 눌렀을 때 오른쪽 속성 칸**에서 편집합니다.

## 1. step 추가
왼쪽 팔레트의 **APPROVAL**을 캔버스로 끌어다 놓으면 됩니다. 승인자 역할(`approverRole`)은 `PL`로 미리 채워집니다.

## 2. 승인 설정: step 클릭

| 항목 | 내용 |
|---|---|
| `id` / `name` | step ID와 사람이 읽는 이름 |
| `approval.artifact` | 무엇을 승인하는지 적는 이름 |
| `approval.approverRole` | 결정할 사람의 역할 |
| `approval.requireCommentOnReject` | 체크하면 `APPROVED`가 아닌 결정에 의견이 꼭 있어야 함(없으면 400) |
| `save` | 결정 결과 `{decision, approver, comment}`를 저장할 state 이름 |

## 3. 결정 경로: 화살표로 연결
승인자가 고를 선택지는 `routes`이고, **화살표 하나가 선택지 하나**입니다.

1. step의 동그라미를 끌어 다음 step이나 END/FAIL에 놓습니다.
2. 경로 이름은 첫 화살표가 `APPROVED`, 둘째가 `REJECTED`, 그다음부터 `경로1`, `경로2`…로 자동으로 붙습니다.
3. 이름이나 갈 곳을 바꾸려면 화살표를 눌러 **경로 이름**과 **가는 곳**을 고칩니다. `진행`, `재작업`, `중단`처럼 자유롭게 지어도 되고, 이 이름이 승인 화면의 버튼이 됩니다.

반려 후 고쳐서 다시 승인받게 하려면 `REJECTED` 화살표를 앞 step으로 이으면 됩니다. 되돌아간 step에서 `${state.approval.comment:}`로 승인자의 의견을 읽을 수 있습니다(`save: approval`인 경우).

## 4. 저장
**[검사]** 후 저장합니다. YAML 탭에서 직접 고쳐도 되고, 결과는 이런 모양입니다.

```yaml
- id: step03
  type: APPROVAL
  approval:
    artifact: analysis-document
    approverRole: PL
    requireCommentOnReject: true
  save: approval
  routes:
    APPROVED: step04
    REJECTED: step02
```

`save`에 적은 이름은 Workflow의 `state:`에도 선언되어 있어야 합니다. 빠지면 검사에서 실패합니다.

## 주의할 점
- **`artifact` 도움말이 실제와 다릅니다.** 디자이너에는 "승인자에게 보여 줄 값(표현식)"이라고 나오지만, 엔진은 `${state.x}`를 풀지 않고 적힌 글자 그대로 `pendingApproval`에 내보냅니다. 게다가 실행 관리 화면(`workflow-admin.js`)은 이 값을 표시하지 않으니, 지금은 승인자가 산출물 내용을 화면에서 볼 수 없습니다.
- **`approverRole`은 표시용입니다.** 서버가 권한을 검사하지 않으므로 누구나 결정할 수 있습니다.
- **`next`와 `onFailure`는 쓸 수 없습니다.** APPROVAL의 화살표 종류는 경로(`routes`)뿐입니다.
- **`approval.rejectTo`는 화면에서 새로 만들 수 없습니다.** YAML에 이미 있는 값은 화살표로 표시되며, 새로 만들 때는 `REJECTED` 경로를 쓰면 됩니다.

실제 승인과 반려는 디자이너가 아니라 **관리자 > Workflow 실행 관리** 화면에서 합니다. 이 내용은 코드를 읽고 확인했으며, 화면을 직접 띄워 보지는 않았습니다.

## 답변

**코드에서 일부러 뺐기 때문입니다.** 아래쪽 점은 나가는 전용, 위쪽 점은 들어오는 전용으로 정해져 있습니다(`workflow-designer.js:1147-1148`).

```js
var SOURCE_PORTS = ["out", "left", "right"];   // 나가는 쪽: 아래, 왼쪽, 오른쪽
var TARGET_PORTS = ["in", "left", "right"];    // 들어가는 쪽: 위, 왼쪽, 오른쪽
```

| 연결점 | 나가는 쪽 | 들어가는 쪽 |
|---|---|---|
| 위(`in`) | 불가 | 가능 |
| 아래(`out`) | 가능 | 불가 |
| 왼쪽, 오른쪽 | 가능 | 가능 |

그래서 나가는 쪽 목록에도 **위**가 없습니다. 이 제한은 목록에만 있는 게 아니라 세 군데에 걸려 있습니다.

- **그림에서 끌어 잇기:** `validateConnection`(1199행)이 아래쪽 점에 화살표를 놓지 못하게 막습니다.
- **저장된 배치 값:** `portsOf`(1596행)와 `setEdgePorts`(1605행)는 목록에 없는 값을 기본값(아래에서 나가 위로 들어감)으로 되돌립니다.
- **노드 종류:** 시작 노드에는 아래쪽 점만, END/FAIL 노드에는 위쪽 점만 기본으로 붙습니다.

이유가 주석에 적혀 있지는 않습니다. 위에서 아래로 흐르는 배치(dagre)에 맞춰 위쪽은 입구, 아래쪽은 출구로 정하고, 2026-10-21에 좌우 점을 추가하면서 양방향을 허용한 것으로 보입니다(커밋 `791d089d`).

이 값은 그림에만 쓰이고 실행에는 영향이 없으므로, 기술적인 제약은 아닙니다. 아래쪽으로 들어가게 하려면 `TARGET_PORTS`에 `"out"`을 넣는 것만으로는 부족합니다. 끌어 놓기가 되도록 아래쪽 점의 자석 설정과 `validateConnection`도 함께 손봐야 합니다.

## 답변

이제 모든 노드의 위·아래·왼쪽·오른쪽 점을 나가는 쪽과 들어가는 쪽 어디로든 쓸 수 있습니다. 화면 설명과 `docs/06.dstone-boot.md`도 함께 고쳤고, 커밋은 하지 않았습니다.

## 바뀐 내용
- **연결점 목록:** 설정 칸의 나가는 쪽과 들어가는 쪽 모두 위·아래·왼쪽·오른쪽 네 가지가 나옵니다.
- **끌어서 잇기:** 어느 점에서 끌어 어느 점에 놓아도 연결됩니다. 위쪽 점도 이제 끌기를 시작할 수 있습니다.
- **시작·END·FAIL·없는 step 상자:** 이 노드들에도 네 점이 모두 생겼습니다.

## 남겨 둔 제한
시작으로 들어오는 화살표와 END/FAIL에서 나가는 화살표는 계속 막습니다. 연결점 문제가 아니라, YAML로 표현할 수 없는 흐름이기 때문입니다.

## 확인하지 못한 부분
- **저장 후 다시 열기:** 정의 파일이 바뀌지 않도록 저장을 끄고 테스트해서, 새 연결점이 `layout.json`에 저장됐다가 복원되는지는 돌려 보지 못했습니다. 기존 저장 방식을 그대로 쓰고, 값 검사 목록만 네 점으로 넓혔습니다.
- **dstone-boot를 거친 전체 경로:** 로그인 계정 없이 테스트하느라 화면 스크립트는 소스 파일을 직접 읽게 했고, 엔진 호출도 dstone-boot를 거치지 않고 바로 보냈습니다.

## 답변

**LLM이 판정 JSON 앞에 설명 문장을 한 줄 붙이면 발생합니다.** 판정 자체는 `pass: true`였는데, 답의 형식 때문에 실행이 실패했습니다. 코드를 읽고 내린 결론이고, 재현해 보지는 않았습니다.

```
모든 6개 TASK의 상태가 통과로 확인되었고, ...   ← 이 문장 때문에 실패
{"pass": true, "reason": "..."}
```

Windows나 D드라이브 문제는 아닌 것으로 보입니다. 이 판정 코드에는 OS에 따라 달라지는 부분이 없고, 파일 읽기와 수정도 끝난 뒤 마지막 답을 검사하다 실패했기 때문입니다.

## 언제 발생하나
다음 조건이 겹치면 발생합니다.

1. **엔진의 엄격한 검사:** `AgentExecutor.convert()`는 답 전체가 JSON이어야 통과시킵니다. 답 전체를 감싼 코드펜스만 벗겨 주고, JSON 앞뒤에 다른 글자가 있으면 실패 처리합니다.
2. **Tool을 쓰는 긴 작업:** "JSON만 답하라"는 지시는 사용자 메시지 끝에 한 번만 들어갑니다. 이 step은 87초 동안 파일을 읽고 표를 고쳤는데, 이렇게 작업이 길어지면 마지막에 작업을 요약하는 문장을 붙이기 쉽습니다. 이 부분은 추정입니다.
3. **프롬프트의 반환 지시:** `[반환]`에 "true 반환", "false 반환"이라고만 있고, 마지막 답의 형식은 적혀 있지 않습니다.
4. **재시도 없음:** SUPERVISOR와 ROUTER가 쓰는 `callForSchema()`에는 재시도가 없습니다. Agent에 `onInvalidOutput: RETRY`를 적어도 적용되지 않습니다. 그래서 한 번 틀리면 바로 `onFailure`로 넘어가고, step02는 `onFailure: FAIL`이라 Workflow가 그대로 끝납니다.

같은 일은 다른 step에서도 날 수 있습니다. ROUTER와 output 필드를 선언한 AGENT도 같은 검사를 거칩니다. 다만 AGENT는 `RETRY`를 설정하면 다시 호출합니다.

## 예방법

| 순서 | 방법 | 효과 | 한계 |
|---|---|---|---|
| 1 | **엔진 수정:** 답 전체가 JSON이 아니면, 답 안에서 스키마에 맞는 마지막 JSON을 찾아 사용 | 이번 같은 실패가 모든 Agent에서 사라짐 | Java 수정과 재기동 필요 |
| 2 | **Workflow 분리:** AGENT(리뷰하고 표 수정) → TOOL(`readFile`) → Tool 없는 SUPERVISOR(판정만) | 판정 step이 답만 내므로 설명 문장이 붙을 여지가 줄어듦 | step이 늘어남 |
| 3 | **프롬프트 수정:** 아래 문구를 `[반환]`에 추가 | 지금 바로 적용 가능 | 줄어들 뿐 완전히 막지는 못함 |

```
[반환]
- 모든 Tool 작업을 마친 뒤 마지막 답은 JSON 하나만 적는다. 그 앞뒤에 요약이나 설명을 쓰지 않는다.
- 상태값이 모두 통과면 pass는 true, 통과가 아닌 항목이 있으면 false로 적는다.
- 판정 근거는 reason에 적는다.
```

**권장 조합은 1번과 2번입니다.** 3번은 엔진을 고치기 전 임시 조치로 쓸 수 있습니다.

단순 재시도만 넣는 것은 권하지 않습니다. 이 Agent는 답하기 전에 파일을 고치므로, 다시 호출하면 수정 작업도 되풀이됩니다. 게다가 재시도할 때는 표가 이미 `통과`로 바뀌어 있어 `대기`를 찾는 작업부터 어긋날 수 있습니다.

## 답변

그러면 답의 내용대로 리뷰 작업은 끝난 상태이고, 실패한 것은 마지막 판정 형식뿐입니다. 다만 **실패한 실행을 이어서 돌릴 수는 없습니다.** 실행 관리 API에는 조회와 승인 결정만 있고, 실패한 step부터 재개하는 기능이 없습니다. 결국 `sm-workflow`를 처음부터 다시 돌려야 합니다.

## 다시 실행할 때
그대로 다시 실행하면 step01이 `01.customer_requirement.md`를 새로 쓰고, step02가 그 문서를 다시 리뷰합니다. 표가 이미 `통과`인 문제는 step01이 파일을 덮어쓰면 자연히 해결됩니다. 프롬프트상 그렇게 동작할 것으로 보이며, 실행해서 확인한 것은 아닙니다. 대신 지켜 둘 점이 있습니다.

- **기존 문서:** 분석 내용이 달라질 수 있으니, 지금 문서를 남기고 싶으면 다른 이름으로 복사해 두세요.
- **재발 가능성:** 프롬프트와 엔진이 그대로라면 step02에서 같은 오류가 다시 날 수 있습니다. 그래서 다시 돌리기 전에 앞서 드린 `[반환]` 문구부터 넣으세요.

디자이너의 Agent 창이나 `conf/definitions/agents/sm/sm-requirement-analyze-reviewer-agent.md`를 직접 고치면 됩니다. 직접 고쳤다면 [엔진 다시 읽기]를 누르세요. 재기동은 필요 없습니다.

## 답변

엔진을 고쳐서, 이번처럼 JSON 앞뒤에 설명이 붙었다는 이유로는 이제 실패하지 않습니다. 다만 실제 LLM으로는 아직 돌려 보지 않았고, 미리 넣은 답으로만 테스트했습니다. 커밋도 하지 않았습니다.

## 바뀐 동작
LLM의 답을 다음 순서로 처리합니다.

| 단계 | 처리 | 결과 |
|---|---|---|
| 1 | 답 전체가 계약에 맞는 JSON인지 확인 | 맞으면 그대로 사용 |
| 2 | 답 전체가 JSON이 아니면 답 안에서 계약에 맞는 JSON을 찾음 | 찾으면 사용, 여럿이면 마지막 값 사용 |
| 3 | 그래도 없으면 형식 변환 호출을 한 번 더 함 | 계약에 맞으면 사용 |
| 4 | 변환도 안 되면 | 처음 오류로 실패 |

이번 오류는 2단계에서 LLM을 다시 부르지 않고 해결됩니다. 3단계 호출은 답 글자만 넘기고 Tool을 붙이지 않으므로, 파일을 다시 고치거나 판정을 새로 하지 않습니다. 재시도 설정이 없는 SUPERVISOR와 ROUTER, 그리고 JSON 형식으로 답하는 AGENT와 채팅에도 똑같이 적용되어, Agent마다 프롬프트를 고칠 필요가 없습니다.

## 그래도 실패하는 경우
다음 경우는 일부러 실패로 남겼습니다. 통과시키면 틀린 판정이 그대로 다음 단계로 넘어갈 수 있기 때문입니다.

- **답에 판정이 없는 경우:** "잘 모르겠습니다"처럼 필수 값을 알 수 없는 답은 변환하지 않습니다.
- **답이 끊긴 경우:** 출력 토큰 한도에 걸려 잘린 답을 변환하게 하면 나머지를 지어낼 수 있습니다.
- **답이 빈 경우:** 옮길 내용이 없습니다.

통신 오류와 Tool 호출 한도 초과도 그대로 실패합니다. 이 형식 문제와는 다른 오류입니다.

## 적용 방법
Windows PC에서 실행 중이니 다음 순서로 적용하면 됩니다.
