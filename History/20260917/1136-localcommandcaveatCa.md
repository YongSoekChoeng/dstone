## 답변

**결론: 하고 볼 만하다 — 단, "provider 오버라이드"가 아니라 "같은 provider 안에서 model 오버라이드"로 범위를 좁혀야 싸게 먹힌다.**

**왜 이 경계가 생기는지**
`ConfigChatClient`가 `spring.ai.model.chat` 하나로 고정된 provider의 `ChatModel`을 받아 `ChatClient` 빈을 딱 하나만 조립하고(`ConfigChatClient.java:69`), `AgentExecutor`도 그 빈 하나만 주입받아 씀(`AgentExecutor.java:34`). 즉 지금 구조는 애초에 "provider 하나"가 전제라, agent마다 다른 **provider**(예: 이 agent는 Ollama, 저 agent는 Anthropic)를 쓰게 하려면 ChatClient를 provider별로 여러 개 만들고 agent→provider 라우팅을 새로 넣어야 하는 큰 재설계다. 반면 같은 provider 안에서 **model**만 바꾸는 건 Spring AI의 `ChatOptions.builder().model(...)`을 요청 스펙에 `.options(...)`로 얹기만 하면 되는, 이미 열려 있는 기능이다.

**영향 범위 (model-only override 기준)**
- `AgentDefinition` (`common/definition/AgentDefinition.java:19`) — nullable `model` 필드 1개 추가
- `common/loader/YamlDefinitionLoader` — 코드 수정 불필요. record 필드는 Jackson `convertValue`로 자동 바인딩됨
- `AgentExecutor.buildSpec()` (`runtime/agent/AgentExecutor.java:100`) — 기존 rag/tools override와 같은 패턴으로 `if (agent.model() != null) spec.options(ChatOptions.builder().model(agent.model()).build())` 한 단락 추가
- `agents/*.yml` — 바꾸고 싶은 agent에만 `model:` 한 줄 추가(opt-in), 나머지는 그대로
- `docs/09.dstone-ai-engine.md`, `CLAUDE.md` — 둘 다 "Agent별 provider override 없음"이라고 명시돼 있는데, 이게 바뀌는 건 아니고 "provider override는 여전히 없음 / model override는 가능"으로 문구만 정정하면 됨

**리스크**
- 활성 provider와 안 맞는 model 문자열(예: provider=ollama인데 `model: gpt-4o`)을 넣어도 기동 시 걸러지지 않고 그 agent 첫 호출에서야 런타임 에러로 드러남. 시작 검증(`AgentRegistry` 쪽에 provider별 허용 모델 화이트리스트 체크)을 추가할 수도 있지만, 지금 이 모듈이 prompt/agent 설정 오류를 다루는 수준(런타임에 실패)과 일관되게 일단 검증 없이 가는 게 범위상 적당해 보임.

작업량 자체는 작고(레코드 필드+실행부 5줄 안팎+YAML), "새 기능 = YAML 파일"이라는 이 모듈의 기존 설계 철학과도 맞다. 진행할지 결정되면 바로 구현해줄게.

## 답변

`caller`를 "요청 전체가 공유하는 컨텍스트"에 심어두는 코드야. 하나씩 풀어볼게.

**1. `caller`가 뭔지부터**
`caller`는 "이 API를 호출한 앱/서비스가 누구인지"를 나타내는 문자열이야(멀티테넌트의 tenant 같은 개념). `ApiKeyAuthFilter`가 `X-API-Key` 헤더로 인증에 성공하면 `CallerContext.set()`으로 그 요청의 `HttpServletRequest`에 심어두고, `ChatController`가 `CallerContext.get(servletRequest)`로 꺼내서 `AgentExecutor.buildSpec()`까지 넘겨준 값이야. 인증 자체가 꺼져 있으면(`dstone.ai.security.auth.enabled=false`) 아무도 이 값을 채워주지 않으니 `caller`는 항상 `null`이야 — 그래서 `if (caller != null)`로 감싼 거고.

**2. `spec.advisors(Consumer<AdvisorSpec>)`가 하는 일**
Spring AI의 `ChatClient`는 요청을 조립할 때 "Advisor 체인"이라는 걸 거쳐. Advisor는 실제 LLM 호출 앞뒤를 감싸는 인터셉터(미들웨어)라고 생각하면 돼 — 예를 들어 2번 단계에서 이미 등록되는 `MessageChatMemoryAdvisor`가 이 체인의 일부야.

`spec.advisors(Consumer<AdvisorSpec> customizer)`는 "새 Advisor를 추가"하는 게 아니라, **지금 요청에 딸린 공유 컨텍스트 맵(`Map<String,Object>`)에 key-value를 하나 써넣는 것**뿐이야. `AdvisorSpec.param(key, value)`가 바로 그 "써넣기"고. 이 맵은 체인에 있는 모든 Advisor가 나중에 자기 코드 안에서 `context.get(key)`로 다시 꺼내 쓸 수 있어.

즉 여기서 하는 일을 코드로 풀면:
```java
spec = spec.advisors(a -> a.param("net.dstone.ai.security.caller", caller));
```
(프로젝트 컨벤션상 람다 대신 익명 `Consumer` 클래스로 풀어 쓴 것뿐, 의미는 동일)

이미 2번 단계에서 `ChatMemory.CONVERSATION_ID` 파라미터를 똑같은 방식으로 심어뒀지 — 그건 `MessageChatMemoryAdvisor`가 실제로 읽어서 "이 sessionId의 대화 기록을 이어서 써줘"라고 동작해. 7번 단계는 그 패턴을 똑같이 따라 하되, key만 `Constants.Security.Caller.ADVISOR_CONTEXT_KEY`(값은 `"net.dstone.ai.security.caller"`)로 바꾼 거야.

**3. 그런데 지금은 누가 이걸 읽고 있나?**
사실 지금 이 시점엔 **아무도 안 읽어**. 등록된 Advisor는 `ConfigChatClient`가 붙이는 `MessageChatMemoryAdvisor` 하나뿐이고, 걔는 세션ID만 보지 caller는 안 봐. 즉 지금 이 코드는 "동작에 영향을 주는" 코드가 아니라, **나중을 위해 미리 깔아둔 배선**이야.

CLAUDE.md/설계문서에 나오는 "Governance 확장 지점"이 정확히 이거야 — PII 필터링, caller별 사용량 로깅/쿼터 체크 같은 기능(governance)을 이번 재설계 범위에서는 안 만들었는데, 나중에 그런 기능이 필요해지면 `@Bean Advisor governanceAdvisor() { ... }` 하나만 새로 등록하면 돼. Spring이 그 Advisor를 자동으로 체인에 끼워주고, 그 Advisor 코드 안에서 `context.get("net.dstone.ai.security.caller")`로 "이번 요청은 누가 보냈는지"를 바로 꺼내 쓸 수 있어 — `AgentExecutor`나 `ChatController`를 다시 고칠 필요 없이.

**비유하자면**: 요청 하나가 지나가는 동안 옆에 "이 요청 보낸 사람: OOO"라고 적힌 메모지를 붙여두는 거야. 지금은 그 메모를 읽는 사람이 없어서 그냥 붙어만 있지만, 나중에 검사원(governance Advisor)이 오면 메모를 보고 "이 사람 요청은 이렇게 처리해야지"라고 판단할 수 있게 미리 준비해둔 거지.

## 답변

`sessionId`를 "대화방 번호"로 advisor 체인에 꽂아 넣으면, 이미 등록되어 있는 `MessageChatMemoryAdvisor`가 그 번호로 Redis에서 과거 대화를 찾아와 프롬프트에 끼워 넣고, 답변 후 다시 저장해주는 구조야. 지난번 caller 얘기랑 구조는 똑같은데(=`param()`으로 컨텍스트에 값 하나 심기), 차이는 **이걸 실제로 읽어서 동작하는 Advisor가 이미 존재한다**는 점이야.

**1. `ChatMemory.CONVERSATION_ID`는 그냥 "키 이름" 상수야**
Spring AI가 미리 정해둔 문자열 하나일 뿐이야(`"chat_memory_conversation_id"` 같은 값). `a.param(ChatMemory.CONVERSATION_ID, sessionId)`는 "이번 요청의 공유 컨텍스트 맵에 `{그 키: sessionId}`를 넣어라"는 뜻이야.

**2. 누가 이 값을 읽나 — `MessageChatMemoryAdvisor`**
`ConfigChatClient.chatClient()`를 보면:
```java
advisors.add(MessageChatMemoryAdvisor.builder(chatMemory).build()); // 세션 메모리 - 항상 마지막(가장 안쪽)
```
이 Advisor가 **모든 `ChatClient` 요청에 항상 끼어 있어**. 얘가 하는 일이 딱 두 단계야.

**3. LLM 호출 전 (before)**
- 컨텍스트 맵에서 `CONVERSATION_ID` 값(=우리가 넣은 `sessionId`)을 꺼냄
- `ChatMemory`(구현체는 `ConfigChatClient.chatMemory()`가 만드는 `MessageWindowChatMemory`)에게 "이 sessionId로 지금까지 쌓인 메시지 목록 줘"라고 물어봄
- `MessageWindowChatMemory`는 실제 저장은 안 하고, `ChatMemoryRepository` 구현체인 `RedisChatMemorySession.findByConversationId(sessionId)`를 호출해서 Redis에서 가져옴 (키: `dstone:ai:session:{sessionId}`, 값: 메시지들이 순서대로 담긴 Redis List)
- 가져온 과거 메시지들(User/Assistant 주고받은 것들)을 **지금 보낼 프롬프트 맨 앞에 끼워 넣음** → 그래서 LLM 입장에서는 "시스템 프롬프트 + 이전 대화 전체 + 이번 사용자 메시지"를 한꺼번에 받게 되고, 자연스럽게 이전 맥락을 기억하는 것처럼 답할 수 있음

**4. LLM 호출 후 (after)**
- 이번 턴의 사용자 메시지 + LLM이 생성한 답변을 다시 같은 `sessionId`로 `ChatMemory`에 저장
- `MessageWindowChatMemory`가 `dstone.ai.session.max-messages`(기본 20)개까지만 남기고 오래된 것부터 잘라낸 뒤, `RedisChatMemorySession.saveAll(sessionId, 잘린목록)`을 호출 → Redis에서 그 키를 지우고(`delete`) 새 목록을 통째로 다시 씀(`rightPushAll`)

**5. `sessionId` 값 자체는 어디서 오나**
`dstone-boot`의 `ChatService.resolveSessionId()`가 **로그인한 사용자 ID**를 그대로 `sessionId`로 써서 매 요청 실어 보내. 그래서:
- 같은 사용자가 계속 메시지를 보내면 → 매번 같은 `sessionId` → 같은 Redis 키 → 대화가 이어짐
- 다른 사용자(다른 `sessionId`)면 → 완전히 다른 Redis 키 → 서로 대화 안 섞임

**6. 만약 이 코드가 없었다면?**
`MessageChatMemoryAdvisor`가 "이 요청이 어느 대화방 소속인지" 알 방법이 없어져. Spring AI는 이럴 때 기본값(빈 문자열 등 고정 conversationId)을 쓰게 되는데, 그러면 서버에 접속한 **모든 사용자의 대화가 하나의 대화방으로 뒤섞이거나**, 혹은 매 요청 새 대화방으로 취급돼서 이전 맥락을 아예 기억 못 하게 돼.

정리하면: 2번 단계는 "메모지를 붙여만 두는" 7번 단계와 달리, **이미 그 메모지를 읽는 담당자(`MessageChatMemoryAdvisor`)가 있고, 그 담당자가 Redis를 실제로 읽고 쓰는 진짜 동작**이라는 게 핵심 차이야.
