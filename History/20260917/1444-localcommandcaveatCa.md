## 원인 및 수정 내용

**원인**: `RagService.getRagSpecAdvisor()`가 `QuestionAnswerAdvisor`를 커스텀 프롬프트 템플릿 없이 생성하고 있었습니다. Spring AI 기본 템플릿은 "컨텍스트에 없으면 모른다고 답하라(If the answer is not in the context, inform the user that you can't answer the question)"고 강제하는 지식-베이스 QA용 문구입니다.

`sql-conversion-agent`(convert step)는 `ragEnabled: true`인데, 정작 이 Agent의 system prompt(`oracle-to-postgresql/v1.st`)에는 Oracle→PostgreSQL 변환 규칙이 전부 들어있습니다 — RAG는 어디까지나 보조 참고자료여야 합니다. 그런데 검색된 RAG 문서가 이번 MERGE 문 케이스와 관련 없다 보니, LLM이 기본 템플릿의 지시를 그대로 따라 "컨텍스트가 관련 없어서 답할 수 없다"며 변환 자체를 거부했고, 그 거절 문구가 그대로 다음 단계(validate → 문법 오류 → fix)로 흘러들어가면서 루프가 헛돌게 된 것입니다.

**수정**: `RagService.java`에 커스텀 `PromptTemplate`을 추가해 `QuestionAnswerAdvisor.builder(...).promptTemplate(...)`으로 지정했습니다. 새 템플릿은 "컨텍스트가 도움이 되면 참고하고, 아니면 무시한 채 이미 갖고 있는 지식/시스템 프롬프트 규칙으로 작업을 끝까지 수행하라"고 지시합니다. 이 메서드는 `ragEnabled=true`인 모든 Agent가 공유하는 지점이라, 현재 유일한 사용처인 sql-conversion-agent뿐 아니라 앞으로 추가될 RAG 기반 Agent에도 동일한 원칙(전문가 system prompt + RAG는 보조)이 적용됩니다.

**원인 1 (변환 누락)**: `convert` step이 실제로 변환을 안 하고 analyze 단계의 입력 포맷(`[원본 SQL]`/`[변환 포인트]` 라벨)까지 그대로 되돌려주고 있습니다. 실제로 쓰이는 프롬프트(`prompts/oracle-to-postgresql/v1.st`)에는 "설명/인사말/마크다운 코드펜스를 출력하지 말라"는 규칙만 있고, `[원본 SQL]`/`[변환 포인트]` 같은 입력 포맷 표기 자체를 출력하지 말라는 규칙이 빠져 있습니다. (참고로 `prompts/oracle-sql-converter/v1.st`라는 어디서도 참조되지 않는 orphan 프롬프트 파일에는 이 규칙이 있는데, 실제 Agent(`sql-convert.yml`)는 `promptName: oracle-to-postgresql`을 가리켜서 그 파일이 아니라 규칙이 빠진 쪽을 쓰고 있습니다.)

**원인 2 (JSON 파싱 실패)**: `ToolStepRunner.jsonEscape()`가 `\`, `"`, `\n`만 이스케이프하고 `\r`(캐리지리턴) 등 다른 제어문자는 그대로 둡니다. LLM 출력에 CRLF 줄바꿈이 섞여 있으면 이스케이프 후에도 raw `\r` 바이트가 JSON 문자열 안에 그대로 남아 무효한 JSON이 되고, `MethodToolCallback`의 JSON→Map 변환이 깨집니다.

두 가지 다 고치겠습니다.

## 수정 내용

1. **`prompts/oracle-to-postgresql/v1.st`** — 출력 형식 규칙(22번)에 `[원본 SQL]`/`[변환 포인트]` 같은 입력 형식 표기를 절대 출력하지 말라는 규칙을 추가했습니다. 변환할 게 없다고 판단되는 경우에도 라벨 없이 SQL 본문만 반환하도록 명시했습니다.

2. **`ToolStepRunner.jsonEscape()`** — 수동 `replace()` 체인(`\`, `"`, `\n`만 처리) 대신 Jackson의 `JsonStringEncoder.quoteAsString()`을 쓰도록 바꿨습니다. `\r`을 포함해 JSON 문자열에 필요한 모든 제어문자 이스케이프를 안정적으로 처리합니다.
