## 답변

Implementation is complete. Summary of what was built in `/app/dstone/dstone-batchadmin`:

**Architecture** (registered as a new module in root `pom.xml`, port 7082, WAR):
- Two datasources: `common` (own schema `dstone_batchadmin` — login users, server registry, job metadata) and a dynamic `RoutingDataSource` that opens a connection per registered `dstone-batch` server for direct, paged reads of its `BATCH_JOB_INSTANCE`/`EXECUTION`/`STEP_EXECUTION` tables.
- `BatchRestClient` calls the existing `dstone-batch` `RestApiRunner` REST endpoints for start/stop/restart/abandon/delete.
- MySQL/PostgreSQL differences (paging syntax, date parsing) are handled via a `DBMS_TYPE` query param and `<choose>` branches in the mapper XML, since a routing datasource can't use MyBatis's automatic `databaseId` detection.
- `JobScheduleManager` uses Spring's built-in `ThreadPoolTaskScheduler` + `CronTrigger` (no Quartz) to auto-fire jobs whose schedule is enabled.
- Login/security mirrors `dstone-boot`'s structure but simplified to "must be logged in" (no per-URL role table) since this is a single-role internal tool; passwords are BCrypt-hashed.

**Screens**: login, main (dashboard with counts), 배치서버 관리 (CRUD + health check), 배치JOB 목록조회 (paged, filtered by server/date-range/JOB아이디/JOB명, with 시작/중지/재시작), 배치JOB 상세조회 (수행이력 + step/파라미터 drill-down), 배치JOB 등록 (metadata + CRON schedule).

**Seed data**: `TB_ADMIN_USER` gets a default `admin` / `admin1234` account; `01-init-mysql-...sql` creates a `batchadmin`/`batchadmin123` MySQL user — both DDL scripts (MySQL and PostgreSQL) are under `src/main/resources/schema/`.

During review I caught and fixed 3 real bugs: a missing `js/common.js` asset (would have broken every AJAX form), a missing `PAGE_NUM` parse on page-2+ requests, and the server-list query excluding `DB_PASSWORD` — which the datasource registry also relied on, so it would have silently failed to connect to any batch server's DB. I also updated `CLAUDE.md` with the new module.

**Caveat**: this sandbox has no `mvn` binary, so I couldn't run `mvn compile`/`package` to confirm it builds — I did a thorough manual cross-check instead (namespaces/statement IDs between DAOs and mapper XML all match, bean wiring traced through for cycles, etc.), but you should run `mvn clean install` from the repo root before deploying.

## 답변

Fixed. Root cause: `index.html` redirected the browser to `/views/login`, which relies on a generic passthrough method (`view1()`) inherited from `dstone-common`'s `BaseController`. That passthrough only resolves to a bare URL when the controller carries **no class-level `@RequestMapping` prefix** — but every controller in batchadmin has one (`/job/*`, `/server/*`, `/main/*`, `/com/login`), so Spring combines the prefix with the method pattern instead (e.g. `/job/*/views/{viewlevel1}`), and `/views/login` never matches anything. It fell through to the static-resource handler and 404'd — exactly the `NoResourceFoundException` you hit. The left-menu's `/views/main` link had the identical latent bug and would have broken the same way right after login.

Changes:
- `index.html` now redirects to `/com/login/loginGo.do` (the real, already-`permitAll`'d login-page endpoint) instead of `/views/login`.
- `MainController` gets an explicit `@RequestMapping("/main.do")` method returning the `main` view; `top.jsp` and `left.jsp` now link to `/main/main.do` instead of `/views/main`.
- Removed the now-dead `/views/login` entry from `ConfigSecurity`'s permitAll list.

I traced the whole nav flow end-to-end with these changes (`/` → login → submit → success → main → menu clicks → logout) and none of it depends on that fragile passthrough anymore — every screen now goes through a real, explicitly-mapped controller method.
