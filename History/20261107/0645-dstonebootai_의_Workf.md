# dstonebootai_의_Workf

> 생성일시: 2026-11-07 06:45

## 질문

dstone-boot>ai 의 Workflow 실행 관리를 10~20 명 가량의 개발자가 각자의 업무를 가지고 동시에 작업을 해도 시스템에 문제가 없을까?

---

## 답변

엔진 쪽 비동기 실행 구조(스레드 풀, DB 저장, 동시성 처리)를 확인하고 있습니다. 조금만 더 보고 정리하겠습니다.

---

## 답변

**결론부터 말씀드리면, 10~20명이 화면을 조회하고 관리하는 정도는 괜찮습니다. 하지만 각자 Workflow를 동시에 실행하면 문제가 생길 곳이 몇 군데 있습니다.** 부하 테스트는 하지 않았고, 코드를 읽어서 판단한 결과입니다.

## 바로 문제가 될 수 있는 것

**1. 실행 스레드 수에 한도가 없고, 사람이 늘면 일부 실행이 멈춘 것처럼 보입니다**
- `WorkFlowExecutionService.submitAsync()`(87행)는 `CompletableFuture.runAsync()`를 Executor 없이 부릅니다. 그래서 JVM 공용 `ForkJoinPool.commonPool()`에서 돌아갑니다. 주석에도 "전용 스레드풀·대기열·동시 실행 제한 없음"이라고 적혀 있습니다.
- 공용 풀 스레드는 CPU 코어 수보다 하나 적습니다. 이 PC는 12코어라 11개입니다. Workflow는 LLM 응답을 몇 분씩 기다리며 스레드를 붙잡습니다. 게다가 forEach의 병렬 반복(`WorkFlowExecutor` 365행)도 같은 풀을 씁니다.
- 20명이 forEach가 있는 Workflow를 동시에 돌리면 11개가 금방 찹니다. 그 뒤 제출된 실행은 상태가 `RUNNING`인데 실제로는 시작조차 안 한 채 줄을 섭니다. 화면에서는 "멈췄다"로 보입니다.
- 클라우드에서 Pod에 CPU limit을 걸면 동작이 반대로 바뀝니다. 2코어 이하로 잡히면 공용 풀이 작업마다 새 스레드를 만들어 제한이 아예 없어집니다. 지금 `k8s/deployment.yaml`에는 limit이 없습니다.

**2. 승인(decision)이 동기 방식이고, 동시에 누르면 중복 실행됩니다**
- `decide()`(`WorkFlowExecutionService` 113행)는 상태를 확인한 뒤 `workFlowExecutor.run()`을 **HTTP 요청 스레드에서 직접** 돌립니다. 다음 승인 단계나 끝까지 가야 응답이 오므로 몇 분이 걸릴 수 있습니다. 그동안 boot와 엔진 양쪽 Tomcat 스레드가 하나씩 묶입니다.
- `resume`은 `markResumed()`로 상태를 조건부로 바꿔서 두 번 눌러도 한 번만 성공합니다. 반면 `decide`에는 이런 보호가 없습니다. 두 사람이 같은 건을 동시에 승인하거나 한 사람이 버튼을 두 번 누르면, 같은 실행이 두 스레드에서 동시에 돌아 state와 파일이 서로 덮어써집니다.

**3. 엔진은 한 대로만 운영할 수 있습니다**
- `WorkFlowExecutionRecovery`는 서버가 뜰 때 `RUNNING`으로 남은 실행을 **전부** `FAILED`로 바꿉니다. 그래서 replica를 2개 이상 둘 수 없고 `replicas: 1`로 고정돼 있습니다.
- 엔진을 재배포하면 그 순간 모든 개발자의 실행 중인 작업이 실패 처리됩니다. 1번 때문에 줄 서 있던 실행도 포함됩니다.

**4. LLM 호출 한도**
- 모든 실행이 API 키 하나를 함께 씁니다. 20건이 Tool 호출을 반복하면 provider의 분당 요청·토큰 한도(429)에 걸리기 쉬운데, `max-retries: 1`이라 곧바로 step 실패로 이어집니다.
- 특히 OpenRouter `:free` 모델이 기본 provider로 설정돼 있다면 무료 모델은 한도가 매우 낮아서 몇 명만 동시에 써도 막힙니다.
- 엔진 쪽에 provider별 동시 호출 수를 제한하는 장치가 없습니다.

## 여러 사람이 함께 쓸 때의 문제

**5. 사용자 구분이 없습니다**
- boot는 엔진을 같은 신원 하나로 호출합니다. 그래서 실행 관리 화면에는 모든 사람의 실행이 섞여 보입니다.
- 누구든 다른 사람의 실행을 일시정지, 되감기, 승인하거나 문서를 저장할 수 있습니다. 승인자(`approver`)도 화면에서 직접 입력하는 글자일 뿐입니다.

**6. 목록 조회가 무겁습니다**
- 목록 쿼리(`searchExecutionList`)가 행마다 `CONTEXT_JSON` 전체를 읽습니다. 컨텍스트가 큰 실행이 많으면 10건 목록도 수 MB가 됩니다.
- `ORDER BY CREATED_AT`에 맞는 인덱스도 없습니다. 20명이 화면을 자주 새로 고치면 엔진 DB와 메모리 부담이 커집니다. Hikari 풀(10)이 바로 부족하지는 않겠지만 여유가 크지 않습니다.

**7. 파일 충돌**
- Workflow의 Tool은 엔진 쪽 파일 시스템에 직접 읽고 씁니다. 두 사람이 같은 프로젝트 경로를 대상으로 돌리면 서로의 결과를 덮어씁니다.
- 화면에서 저장할 때는 hash로 충돌을 검사하지만, Workflow가 파일을 쓸 때는 잠금이 없습니다.

## 고칠 순서 (제안)

1. 실행 전용 스레드 풀을 따로 둡니다. 동시 실행 수에 상한을 두고, 넘치면 `QUEUED` 상태로 대기시킵니다. forEach도 별도의 제한된 풀로 옮깁니다. 이게 가장 효과가 큽니다.
2. `decide`는 조건부 UPDATE로 한 번만 성공하게 하고, 실행은 비동기로 넘깁니다. `resume`과 같은 방식입니다.
3. boot가 로그인 사용자를 caller로 넘기게 하고, 목록 필터와 조작 권한을 사용자 기준으로 나눕니다.
4. LLM 호출에 provider별 Semaphore를 두고, 429가 나면 재시도 간격을 점점 늘리게 합니다.
5. 목록 쿼리에서 `CONTEXT_JSON`을 빼고 `CREATED_AT` 인덱스를 추가합니다.
6. 여러 대로 늘려야 한다면 recovery를 "내 인스턴스가 맡은 실행만" 실패 처리하도록 바꿉니다. 실행 소유 인스턴스와 heartbeat를 기록하면 됩니다.

1, 2번은 수정 범위가 작고 효과가 바로 나타납니다. 원하시면 이 두 가지부터 고치겠습니다.
