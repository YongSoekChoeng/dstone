## 답변

첫 2회(memo-1, search-1)를 동시에 돌리는 중입니다. 지금까지 상황을 정리합니다.

**끝난 것**
1. **ojdbc가 든 MySQL WAR 확인**: testApp WAR(ojdbc6·ojdbc8 포함)가 예외 설정(sandbox-trusted-libs) 없이 격리 기동됐습니다.
   - HTTP 응답은 200이었습니다.
   - 원본 DB와 원본 사이트 접근은 막혔습니다.
   - 시험 전후 원본 DB 체크섬이 같았습니다.
2. **바뀐 가드로 실제 LLM 검증 고리 재확인**(qwen3.8-27b, buggy1 사례): 심어 둔 결함 3개를 검증→수정→재검증 3바퀴 안에 모두 고쳤습니다.
   - 이 사례와 무관한 HTTP 채점도 등록·수정·삭제 모두 ok입니다.
   - 가드가 정상 흐름을 거절한 경우는 없었습니다.
   - 원본 DB에는 아무것도 남지 않았습니다.
3. **측정 준비**(모두 `/app/dstone/temp/bench.HtG19X`, git에서 제외):
   - **합성 앱**: 직원 목록이 있는 작은 Spring Boot + MySQL 앱입니다.
   - **요청서 3종**: 신규 메모 CRUD, 기존 직원 목록에 검색·페이징 추가, 공지사항 업무 규칙입니다.
   - **일회용 원본 DB**: MySQL 24306을 따로 띄웠습니다.
   - **knowledge 시험 인스턴스**: 4181 포트에 일회용 PostgreSQL 25432를 붙였습니다. 실제 knowledge DB는 건드리지 않았고, 합성 앱 분석과 임베딩까지 마쳤습니다.
   - **하니스**: 요청서부터 개발 승인(step17)까지 돌립니다. 승인은 모두 진행 쪽으로 자동 선택합니다.
   - **채점기**: LLM 없이 HTTP와 DB만으로 채점합니다. 대상은 첫 개발본(처음 컴파일 직후)과 step17 도착본 두 가지입니다.

**환경에서 바꾼 것**
- Ollama가 재부팅 뒤 PID 파일만 남은 상태였습니다. `docs/software/14.ollama.md`에 적힌 조치대로 PID 파일을 지우고 다시 띄웠습니다.

**남은 것**
- 전체 실행 15회 중 첫 2회가 진행 중입니다. 이 2회가 끝나면 걸린 시간을 보고 남은 13회의 예상 시간을 알려 드리겠습니다.
- 실행이 끝나면 실패 원인을 분류하고 결과를 `.claude/docs/ai-engine-tuning.md`에 기록합니다.
- 작업 트리에 커밋하지 않은 변경(Oracle 격리, 가드 수정)이 남아 있습니다. 측정이 끝난 뒤 커밋·푸시할지 다시 여쭙겠습니다.

## 답변

지금 돌고 있는 작업은 **sm-workflow를 요청서부터 끝까지 실제 LLM으로 돌렸을 때 개발 결과가 얼마나 제대로 동작하는지 재는 측정**입니다. 지난 세션 재개 메모의 "요청서 3종 × 5회 전체 실행으로 첫 개발본 통과율 측정"에 해당합니다.

**왜 하나**
지금까지는 이미 만들어 둔 개발본을 넣고 step16부터 자동 검증·수정 고리만 시험했습니다. 요청서에서 시작해 요구사항 → 영향도 → 설계 → 개발 → 컴파일 → 자동 검증·수정까지 한 번에 돌린 적은 없습니다. `ai-engine-tuning.md`에도 "Not measured: a full run from a request"로 남아 있습니다.

**어떻게 재나**
1. **대상 앱**: temp에 만든 작은 합성 앱(직원 목록만 있는 Spring Boot + MySQL)입니다. 판매용 저장소에 특정 앱이 들어가지 않게 하려고 testApp은 쓰지 않았습니다.
2. **요청서 3종**: 성격이 다른 요청 세 가지입니다.
   - memo: 새 테이블로 메모 등록·수정·삭제 화면을 만든다
   - search: 기존 직원 목록에 이름·부서 검색과 페이징을 넣는다
   - notice: 공지사항을 만든다(필수값, 기간 검증, 게시 기간 안의 것만 보이기 같은 업무 규칙)
3. **실행**: 요청서마다 5회씩, 모두 15회입니다. 사람이 누르는 승인은 모두 진행 쪽으로 자동 선택하고, 개발 승인(step17)에 도착하면 멈춥니다.
4. **채점**: LLM 판단은 쓰지 않습니다. 결과물을 일회용 DB 복제본 위에 띄운 뒤 HTTP로 API를 직접 부르고 DB를 조회해 맞는지 봅니다. 예를 들어 "이름에 '민'을 넣으면 4명이 나오는가", "종료일이 시작일보다 앞이면 400을 주는가" 같은 것입니다.
   - **첫 개발본**: 처음 컴파일한 직후의 결과
   - **최종본**: 자동 검증·수정을 거쳐 step17에 도착한 결과

   두 점수를 비교하면 자동 검증 고리가 실제로 얼마나 도움이 되는지도 보입니다.

**지금 상태**
- memo-1과 search-1 두 건이 동시에 돌고 있습니다.
- 받쳐 주는 것들:
  - 원본 DB: 일회용 MySQL(24306)
  - knowledge 시험 인스턴스: 4181 포트, 일회용 PostgreSQL에 붙임. 영향도 Agent가 프로젝트ID가 있으면 knowledge Tool로 조사하기 때문에 필요합니다.
  - Ollama: knowledge가 임베딩에 씁니다.
- 실제 DB, 4081·8081 인스턴스, 저장소 코드는 건드리지 않습니다.

**끝나면**
- 첫 2회가 끝나면 걸린 시간을 보고 나머지 13회가 얼마나 걸릴지 알려 드리겠습니다.
- 15회를 다 돌리면 실패를 원인별로 나누고 결과를 `.claude/docs/ai-engine-tuning.md`에 적어 보고합니다.

참고로 모델은 OpenRouter의 qwen3.8-27b라서 실행마다 호출 비용이 듭니다. 회수를 줄이거나 방향을 바꾸고 싶으시면 지금 말씀해 주세요.

## 답변

결과는 크게 네 군데에 씁니다.

**1. 어디를 고칠지 정한다**
15회의 실패를 원인별로 나눕니다(CLAUDE.md 규칙의 분류: 엔진/입력/Tool/Workflow 구조/Skill/모델/프롬프트). 예를 들면 이렇습니다.
- 요구사항에는 있는데 설계에서 빠졌다 → 설계 Agent나 리뷰 단계 문제
- 설계는 맞는데 코드가 틀렸다 → 개발 Agent나 Skill 문제
- 검증 Agent가 PASS라고 했는데 채점에서는 틀렸다 → 검증 고리의 빈틈
- 서버가 뜨지 않거나 Tool이 실패했다 → 엔진·Tool 문제

어느 칸에 실패가 몰리는지 보고 다음에 고칠 곳을 고릅니다. 프롬프트에 한 줄을 더하는 식으로 감에 의존하지 않으려는 것입니다.

**2. 고친 뒤 비교할 기준선이 된다**
같은 요청서, 같은 채점기, 같은 앱을 그대로 두었으니 Workflow나 Agent를 바꾼 뒤 다시 돌리면 나아졌는지 나빠졌는지가 숫자로 나옵니다. 지금까지는 step16 이후만 쟀기 때문에 앞 단계(요구사항·설계)를 고쳐도 효과를 확인할 방법이 없었습니다.

**3. 자동 검증 고리(2.4.0)가 값을 하는지 판단한다**
첫 개발본 점수와 최종본 점수의 차이가 자동 검증·수정이 실제로 건진 몫입니다.
- 차이가 크면 이 고리를 유지하고 더 키울 근거가 됩니다.
- 차이가 작거나 오히려 망가뜨리면 걸리는 시간과 비용에 비해 효과가 없다는 뜻이라 구조를 다시 봐야 합니다.

검증 Agent의 PASS 판정과 채점 결과가 얼마나 일치하는지도 나옵니다. 사람이 개발 승인 화면에서 그 판정을 얼마나 믿어도 되는지 알 수 있습니다.

**4. 판매·POC 자료로 쓴다**
"폐쇄망에서 쓸 만한 27B급 모델로 요청서 하나를 넣으면 몇 분 만에, 몇 % 확률로 동작하는 개발본이 나온다"는 실제 수치가 생깁니다. 결과는 `.claude/docs/ai-engine-tuning.md`에 기록하고, 필요하면 `docs/09`의 운영 설명에도 반영합니다.

**한계도 같이 적습니다**
- 대상이 작은 합성 앱이고 로그인이 없습니다. 큰 레거시 앱에서의 통과율은 이보다 낮을 가능성이 큽니다.
- 회당 5회라서 대략적인 경향만 보입니다. 정밀한 비율로 읽으면 안 됩니다.
- 사람이 하는 승인을 모두 진행 쪽으로 눌렀습니다. 사람이 중간에 지적해서 고치는 효과는 들어 있지 않습니다.

그래서 이 결과는 "제품이 이만큼 된다"는 보증으로 쓰기보다, 다음에 고칠 곳을 정하고 고친 효과를 확인하는 데 주로 쓸 생각입니다.
