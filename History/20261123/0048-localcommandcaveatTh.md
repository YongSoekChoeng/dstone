# humanizer: 한국어 AI 작문 패턴 감지 및 교정기

## 소개

당신은 AI가 생성한 텍스트의 특징적인 패턴을 감지하고 교정하는 한국어 글쓰기 분석 전문가입니다. 당신의 전문성은 과학적 언어학 연구, 특히 KatFishNet 논문(ArXiv 2503.00032v4)에 기반하고 있으며, 이 논문은 인간이 작성한 텍스트와 LLM이 생성한 한국어 텍스트 사이의 측정 가능한 차이를 식별했습니다.

**중요한 컨텍스트**:
- 이 스킬은 **한국어 텍스트에만** 집중하며, 영어 번역이나 다른 언어는 다루지 않습니다
- 검출 패턴은 높은 정확도(쉼표 패턴: 94.88% AUC, 품사 다양성: 82.99% AUC, 띄어쓰기: 79.51% AUC)를 가진 **실증적 언어학 분석**에 기반합니다
- 당신의 목표는 원래의 의미와 의도를 보존하면서 텍스트를 **자연스럽게 인간이 작성한 것처럼** 만드는 것입니다
- 우선순위에 따라 구성된 6개 카테고리의 40가지 고유 패턴을 분석하며, 각 패턴은 S1/S2/S3 심각도로 분류됩니다

## 작업 설명

실행될 때 다음을 수행합니다:

1. **한국어 텍스트 읽기** - 사용자가 제공한 텍스트(인자, 대화 컨텍스트, 또는 파일)
2. **텍스트 분석** - 아래에 설명된 40가지 검출 패턴에 대해 분석
3. **AI 작문 마커 식별** - 각 발견 사항에 대한 과학적 근거와 함께
4. **텍스트 재작성** - 자연스럽고 인간이 작성한 것처럼 들리도록
5. **수정된 버전 제시** - 주요 변경 사항의 요약과 함께(선택적)

**프로세스 가이드라인**:
- 항상 원래의 의미와 사실적 내용을 보존하세요
- 적절한 격식 수준(격식체 vs 반말)을 유지하세요
- 완벽함보다 자연스러움에 집중하세요
- 중요한 변경 사항에 대한 근거를 설명하세요
- 텍스트가 AI 마커를 거의 보이지 않으면, 이미 자연스럽다고 인정하세요

## 한국어 AI 작문 특징

LLM이 생성한 한국어 텍스트는 인간의 글쓰기와 측정 가능하게 다른 고유한 언어적 패턴을 보입니다:

- **문장부호**: 과도한 쉼표 사용(61% vs 인간 26%), 영어식 쉼표 배치
- **띄어쓰기**: 의존명사 띄어쓰기의 경직된 일관성(SD=0.02 vs 인간의 변동성)
- **어휘 다양성**: 낮은 품사 다양성, 명사 과다 사용, 동사/형용사 빈곤
- **어휘**: 일반적 서술어 과다 사용(중요하다, 핵심적, 효과적, 지속가능한, 혁신적)
- **구조**: 단조로운 문장 리듬, 3박자 리스트, 과도한 접속사

이러한 패턴은 LLM 학습 데이터 편향과 확률적 텍스트 생성에서 나타나며, 한국어 원어민 독자에게 부자연스럽게 느껴질 수 있습니다.

## 검출 패턴 (총 40가지)

### 패턴 분류 체계

모든 패턴은 검증 수준과 심각도에 따라 메타데이터를 포함합니다.

**검증 수준**:
- **✅ 과학적**: KatFishNet 논문(ArXiv 2503.00032v4, 2025) 등 외부 문헌으로 검증된 패턴 — 검증 필드에 인라인 인용 (예: `검증: ✅ 과학적 (KatFishNet, 94.88% AUC)`)
- **📊 경험적**: 실무 관찰을 기반으로 한 커뮤니티 기여 패턴

**심각도(severity)**:
- **S1 (Critical)**: 한 번만 나와도 AI 신호로 결정적. 무조건 수정 권장.
- **S2 (Strong)**: 1~2회 허용, 3회+ 반복 시 AI 신호. 빈도 기반 판정.
- **S3 (Weak)**: 단독으로는 약한 신호이나 다른 패턴과 중첩될 때 결정적.

**자연도 등급(Naturalness Grade)** — v1.6.0 신설:

윤문 후 텍스트의 자연스러움을 한 글자로 요약. 출력 형식의 "자연도 등급" 라인에 표시.

- **A**: S1 0건 + S2 ≤ 2 — 자연스러움 거의 완벽 (인간이 작성한 것처럼 읽힘)
- **B**: S1 1~2건 또는 S2 3~5건 — 자연스럽지만 사소한 AI 흔적
- **C**: S1 3+건 또는 S2 6+건 — AI 흔적 명확, 추가 윤문 권장
- **D**: 다중 카테고리 위반 (S1 5+건 + S2 8+건) 또는 변경률 가드 트리거 발생

자연도 등급은 윤문 **후** 텍스트에 적용 — 윤문 결과의 품질을 한 줄로 평가. 사용자가 결과를 신뢰할 수 있는지 빠르게 판단하도록 돕습니다.

각 패턴에는 다음 3필드 메타데이터가 포함됩니다:
- **검증**: 검증 수준 (✅ 과학적 / 📊 경험적), 외부 문헌은 인라인 인용
- **심각도**: S1 / S2 / S3 + 정의
- **버전**: 패턴이 추가된 스킬 버전

### 변경률 가드 (Over-rewriting Guard)

자연스러운 버전을 작성한 후 **변경률**을 자체 추정해 과도한 교정을 방지하세요.

**변경률 계산**:
- 원본과 자연스러운 버전을 어절 단위로 비교
- 변경된 어절 / 전체 어절 비율 (대략적, 0~100%)
- 단순 띄어쓰기·문장부호 변경은 제외하고 의미 단위 변경만 카운트

**임계값**:
- **<30% (정상)**: 그대로 출력
- **30~50% (경고)**: 출력 끝에 "변경률 N%로 다소 큼. 의미 보존 재확인 권장" 한 줄 추가
- **>50% (중단)**: 출력하지 말고 사용자에게 확인 요청
  - 메시지: "변경률이 N%로 과도합니다. 원본 의미가 변경됐을 가능성이 있습니다. 더 보수적으로 재작성해드릴까요?"
  - 사용자 동의 시 보수적으로 재작성 후 30% 이내로 다시 시도

**근거**: 과도한 교정은 원본의 의미·뉘앙스·작성자 톤을 잃을 위험이 있음. 정량 임계로 자체 검증해 의미 보존 원칙을 강화.

## 답변

## 결론

**Workflow의 뼈대는 괜찮지만 품질을 보장하는 구조는 아직 아닙니다.** 결과가 흔들리는 데는 qwen 탓도 있지만, 더 큰 원인은 **설계 단계에서 코드가 사실상 확정되는데 그 코드가 동작하는지 사람이 실행해 보기 전까지 아무도 검증하지 않는 것**입니다.

정의 파일과 엔진 코드, 오늘 work002(이미지게시판)로 돌린 실행 2건(`f2cf12b3`, `86b3660b`)의 로그와 산출물, 저장된 평가 결과를 읽고 판단했습니다. 새로 실행하거나 고친 것은 없습니다.

## 1. 구성은 잘되어 있는가

| 영역 | 평가 | 이유 |
|---|---|---|
| 흐름 제어, 원본 보호 | 좋음 | 순서·분기·승인은 Java가 맡고 결과는 `dev-resources`에만 씀 |
| 요구사항 분석 | 보통 | 누락은 잡지만 "확인 필요"를 사람에게 묻지 않고 통과 |
| 영향도·설계 | **취약** | 참고 기능과 구조가 실행마다 바뀌고 검증이 없음 |
| 개발 | 안정적 | 설계서를 거의 그대로 옮김. 설계가 틀리면 그대로 틀림 |
| 검증 | **가장 취약** | 자동 검증은 Java 컴파일뿐. JSP·JS·SQL·실제 동작은 사람 몫 |
| 전문가 해결 | 과부하 | 예외 경로인데 실제로는 주 개발 경로가 됨 |

실측값은 이렇습니다.
- 사람의 결정이 각각 13번, 9번 필요했고, 그중 개발 후 수정 지시가 9번, 5번이었습니다.
- 전문가 해결이 전체 입력 토큰 4,800만의 **75%**, LLM 시간 116분의 **65%**를 썼습니다.

## 2. 무엇이 문제인가

### ① 결함은 개발이 아니라 설계에서 생깁니다
- 같은 설계서로 개발만 6번 돌리니 파일 42개 중 39개가 설계서 코드와 일치했고, 나머지도 97% 이상 같았습니다.
- 수정 이력에 남은 런타임 결함 12건 중 11건은 개발 Agent가 처음 받은 설계서에 이미 있었습니다(잘못된 코드 또는 필요한 코드 누락).
- 결함 유형도 반복됩니다. `mb_id` 누락과 Kendo 체크박스 오류는 두 실행에서 똑같이 났고, 컬럼 길이 초과와 세션 미설정 NPE도 있었습니다. 전부 `javac`로는 못 잡습니다.

### ② 지침이 엉뚱한 Agent에 가 있습니다
- 값 누락을 막는 `troubleshooting`의 "값 대조표"는 **옮겨 적는 개발 Agent**에게만 미리 주고, **코드를 만드는 설계 Agent**에게는 없습니다.
- `source-investigation`은 "공통 유틸 내부는 따라가지 않는다"고 합니다. `FileService.imageSave`가 세션을 요구하는 것을 놓치기 쉬운 규칙입니다.
- `document-writing`은 "다시 점검하지 말고 바로 저장하라"고 합니다. 추론 폭주를 막으려던 규칙인데 설계 자기검토까지 막습니다.
- 개발 Agent는 자기에게 없는 Tool(`knowledge*`, `dbQuery`)을 쓰라는 Skill을 받습니다.

### ③ 프로젝트 관례가 빠져서 설계가 크게 갈렸습니다

| | 08:48 실행 | 18:19 실행 |
|---|---|---|
| `gnx-crud-screen` Skill | 있음 | **없음**(12:51 `c7639058`에서 삭제) |
| 참고한 기능 | 샘플게시판 | 회원사관리 |
| 패키지 | `test.imageboard` | `system.image` |
| 기존 공통 파일 수정 | 0개 | **5개**(Base 3개, FileService, FileVO) |

삭제된 Skill 첫 줄이 "기본 참고 기능은 샘플게시판이다"였습니다. 각 1회라 단정은 못 하지만 유력한 원인입니다. 제품에서 뺀 것은 맞는데 **현장에서 넣을 자리가 빈 채로 남았습니다.** 다만 Skill이 있던 실행도 결함은 많았으므로, 관례는 일관성을 높일 뿐 검증을 대신하지 못합니다.

### ④ Workflow 자체의 버그입니다(코드로 확인, 재현 실행은 안 함)

| 위치 | 문제 |
|---|---|
| step24·25 이후 | 개발 뒤에 영향도나 요구사항을 고치면 step10이 설계서를 새로 씀. **재개발·전문가 해결로 고친 내용이 사라짐** |
| step14 → 15 | 개발 폴더를 비워도 `compileError`가 남아, 없는 파일의 옛 오류를 "먼저 고치라"고 전달 |
| step06 → 25 | 사람의 결정이 `arrival`을 덮어써서 **리뷰어의 지적이 지시로 전달되지 않음** |
| step05 | LLM 호출의 형식 실패와 실제 불통과가 같은 경로로 감 |
| step05 → 07 | "확인 필요"가 있어도 통과. 두 실행 모두 뒤에서 답하느라 영향도 재작성이나 설계 수정이 생김 |
| step12·18·20 | 설계서를 60,000자에서 자르고 진행. 최근 설계서가 이미 47,519자 |
| 요구분석 Agent | `${input.instruction}이 있을 경우`가 값으로 치환되어, 비어 있으면 깨진 문장이 됨 |

### ⑤ 평가가 품질을 재지 못합니다
- `developer-write`의 설계서에는 알려진 결함(세션 미설정, 이미지 URL null 덮어쓰기, 삭제 시 `mb_id` 누락)이 남아 있는데도 **6번 모두 10/10**이었습니다. 파일이 생겼는지만 보기 때문입니다.
- 평가 사례도 저장소에서 빠져 `temp/eval`에만 있습니다. 이 상태로는 무엇을 고쳐도 나아졌는지 알 수 없습니다.

### ⑥ 모델의 한계도 있습니다
Agent 호출 38번 중 5번이 60,000토큰 추론 폭주였고 약 21분(전체의 18%)을 버렸습니다. 다만 이것은 시간과 실패율의 문제이고, ①의 결함과는 따로 봐야 합니다.

## 3. 어떻게 개선할까

핵심은 **LLM이 매번 잘하게 만들기보다, 틀린 결과가 다음 단계로 못 넘어가게 만드는 것**입니다.

| 순서 | 개선 | 방법 | 효과 |
|---|---|---|---|
| **1** | 측정 기준 | 요청서 3종(오류수정·CRUD·업무규칙)을 5회씩 실행. 지표는 "첫 개발본의 시나리오 통과율"과 "사람 개입 횟수". 대상 앱 사례는 저장소 밖에 보관 | 이후 판단의 근거 |
| **2** | 버그 수정 | step14에 `saveError: compileError`, 리뷰 사유는 `reference`로 전달, 설계가 있으면 재작성 대신 수정 경로, 문서가 잘리면 실패 | 고친 것이 사라지지 않음 |
| **3** | 질문을 앞으로 | 요구분석이 `questions[]`를 내고, 영향도 전에 사람이 답함 | 재작성 감소 |
| **4** | 관례 고정 | 현장용 `skills/projects`를 저장소 밖에서 주입. 참고 기능과 수정 금지 공통 파일을 영향도 승인 때 확정 | 실행 간 편차 감소 |
| **5** | 정적 게이트 | 범용 Tool로 '변경 전' 일치, 허용 밖 파일 수정, Mapper 파라미터와 값 설정, 컬럼 길이, JSP·JS·XML 문법을 검사 | 실행 전에 결함 차단 |
| **6** | 동작 게이트 | 개발 승인 **전에** 검증 Agent가 시험 DB·임시 서버·브라우저로 완료 기준을 실행. 실패하면 2회까지 자동 수정 | **효과가 가장 큼** |
| **7** | 역할 재배치 | 설계서는 결정·인터페이스·DDL·값 대조표·참고 파일까지만. 코드는 개발 Agent가 층별로 쓰고 바로 검증 | 사람이 읽을 수 있는 설계, 작은 작업 단위 |
| **8** | 모델 | 추론 전용 토큰 상한, OpenRouter provider 고정, 폐쇄망과 같은 서빙 환경에서 재측정 | 폭주와 환경 편차 감소 |

6번은 시험 DB에 DDL을 자동 반영할 수 있어야 합니다. 지금은 DDL이 항상 '보류'라 자동 검증이 불가능하니 이 정책부터 정해야 합니다. 7번은 개발 쪽 편차를 키울 수 있으므로 5·6번 뒤에 하십시오.

# Java는 람다 없이 쓰기

이 저장소의 Java 코드는 람다 식과 메서드 참조를 쓰지 않는다. 모듈을 가리지 않는 상시 규칙이다.

## 왜

사용자가 2026-09-20에 dstone-ai-engine의 람다를 모두 예전 스타일로 바꿔 달라고 했고, 앞으로 만드는 소스에도 계속 적용하라고 했다. 한 번 하고 끝나는 정리가 아니다.

## 이렇게 쓴다

- 함수형 인터페이스(`Comparator`, `Runnable`, `RowMapper`, `CompletableFuture` 콜백 등) → **익명 내부 클래스**
- Stream 체인 → 가능하면 **일반 for 문**

```java
// 쓰지 않는다
list.sort((a, b) -> a.getName().compareTo(b.getName()));
names.forEach(System.out::println);

// 이렇게 쓴다
list.sort(new Comparator<Item>() {
    @Override
    public int compare(Item a, Item b) {
        return a.getName().compareTo(b.getName());
    }
});
for (String name : names) {
    System.out.println(name);
}
```

## 기존 코드를 고칠 때

- 손대는 코드에 람다가 있으면, 따로 요청이 없어도 익명 클래스/반복문으로 바꾼다.
- 깊게 중첩된 Stream 파이프라인처럼 바꾸면 지나치게 장황해지는 경우에는 **말없이 람다를 남겨 두지 말고 사용자에게 물어본다.**

## 끝내기 전 확인

바꾼 Java 파일에 `->` 와 `::` 가 남아 있지 않은지 검색해 본다.

# 쉽고 친근한 주석 쓰기

## 오해하지 말 것

**주석을 줄이라는 뜻이 아니다.** 이 코드베이스는 원래 "왜 이렇게 했는지", 결정 배경, 이력을 길게 풀어 쓰는 한글 주석을 쓴다 (dstone-ai-engine의 `ConfigTool`, `CallerContext` 등). 그 관례는 그대로 이어간다. 바꾸는 것은 **말투와 문장**이다.

```java
// 피한다
// 조건부 빈 등록에 기인한 의존성 부재 가능성을 고려하여 지연 조회 방식을 채택함.

// 이렇게 쓴다
// RAG를 꺼 두면 이 빈이 아예 없다.
```
