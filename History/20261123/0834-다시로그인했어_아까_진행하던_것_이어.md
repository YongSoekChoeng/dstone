## 답변

첫 2회(memo-1, search-1)를 동시에 돌리는 중입니다. 지금까지 상황을 정리합니다.

**끝난 것**
1. **ojdbc가 든 MySQL WAR 확인**: testApp WAR(ojdbc6·ojdbc8 포함)가 예외 설정(sandbox-trusted-libs) 없이 격리 기동됐습니다.
   - HTTP 응답은 200이었습니다.
   - 원본 DB와 원본 사이트 접근은 막혔습니다.
   - 시험 전후 원본 DB 체크섬이 같았습니다.
2. **바뀐 가드로 실제 LLM 검증 고리 재확인**(qwen3.8-27b, buggy1 사례): 심어 둔 결함 3개를 검증→수정→재검증 3바퀴 안에 모두 고쳤습니다.
   - 이 사례와 무관한 HTTP 채점도 등록·수정·삭제 모두 ok입니다.
   - 가드가 정상 흐름을 거절한 경우는 없었습니다.
   - 원본 DB에는 아무것도 남지 않았습니다.
3. **측정 준비**(모두 `/app/dstone/temp/bench.HtG19X`, git에서 제외):
   - **합성 앱**: 직원 목록이 있는 작은 Spring Boot + MySQL 앱입니다.
   - **요청서 3종**: 신규 메모 CRUD, 기존 직원 목록에 검색·페이징 추가, 공지사항 업무 규칙입니다.
   - **일회용 원본 DB**: MySQL 24306을 따로 띄웠습니다.
   - **knowledge 시험 인스턴스**: 4181 포트에 일회용 PostgreSQL 25432를 붙였습니다. 실제 knowledge DB는 건드리지 않았고, 합성 앱 분석과 임베딩까지 마쳤습니다.
   - **하니스**: 요청서부터 개발 승인(step17)까지 돌립니다. 승인은 모두 진행 쪽으로 자동 선택합니다.
   - **채점기**: LLM 없이 HTTP와 DB만으로 채점합니다. 대상은 첫 개발본(처음 컴파일 직후)과 step17 도착본 두 가지입니다.

**환경에서 바꾼 것**
- Ollama가 재부팅 뒤 PID 파일만 남은 상태였습니다. `docs/software/14.ollama.md`에 적힌 조치대로 PID 파일을 지우고 다시 띄웠습니다.

**남은 것**
- 전체 실행 15회 중 첫 2회가 진행 중입니다. 이 2회가 끝나면 걸린 시간을 보고 남은 13회의 예상 시간을 알려 드리겠습니다.
- 실행이 끝나면 실패 원인을 분류하고 결과를 `.claude/docs/ai-engine-tuning.md`에 기록합니다.
- 작업 트리에 커밋하지 않은 변경(Oracle 격리, 가드 수정)이 남아 있습니다. 측정이 끝난 뒤 커밋·푸시할지 다시 여쭙겠습니다.
