3. **측정 준비**(모두 `/app/dstone/temp/bench.HtG19X`, git에서 제외):

   - search: 기존 직원 목록에 이름·부서 검색과 페이징을 넣는다

   - **첫 개발본**: 처음 컴파일한 직후의 결과
   - **최종본**: 자동 검증·수정을 거쳐 step17에 도착한 결과

**지금 상태**

## 답변

결과는 크게 네 군데에 씁니다.

**1. 어디를 고칠지 정한다**
15회의 실패를 원인별로 나눕니다(CLAUDE.md 규칙의 분류: 엔진/입력/Tool/Workflow 구조/Skill/모델/프롬프트). 예를 들면 이렇습니다.
- 요구사항에는 있는데 설계에서 빠졌다 → 설계 Agent나 리뷰 단계 문제
- 설계는 맞는데 코드가 틀렸다 → 개발 Agent나 Skill 문제
- 검증 Agent가 PASS라고 했는데 채점에서는 틀렸다 → 검증 고리의 빈틈
- 서버가 뜨지 않거나 Tool이 실패했다 → 엔진·Tool 문제

어느 칸에 실패가 몰리는지 보고 다음에 고칠 곳을 고릅니다. 프롬프트에 한 줄을 더하는 식으로 감에 의존하지 않으려는 것입니다.

**2. 고친 뒤 비교할 기준선이 된다**
같은 요청서, 같은 채점기, 같은 앱을 그대로 두었으니 Workflow나 Agent를 바꾼 뒤 다시 돌리면 나아졌는지 나빠졌는지가 숫자로 나옵니다. 지금까지는 step16 이후만 쟀기 때문에 앞 단계(요구사항·설계)를 고쳐도 효과를 확인할 방법이 없었습니다.

**3. 자동 검증 고리(2.4.0)가 값을 하는지 판단한다**
첫 개발본 점수와 최종본 점수의 차이가 자동 검증·수정이 실제로 건진 몫입니다.
- 차이가 크면 이 고리를 유지하고 더 키울 근거가 됩니다.
- 차이가 작거나 오히려 망가뜨리면 걸리는 시간과 비용에 비해 효과가 없다는 뜻이라 구조를 다시 봐야 합니다.

검증 Agent의 PASS 판정과 채점 결과가 얼마나 일치하는지도 나옵니다. 사람이 개발 승인 화면에서 그 판정을 얼마나 믿어도 되는지 알 수 있습니다.

**4. 판매·POC 자료로 쓴다**
"폐쇄망에서 쓸 만한 27B급 모델로 요청서 하나를 넣으면 몇 분 만에, 몇 % 확률로 동작하는 개발본이 나온다"는 실제 수치가 생깁니다. 결과는 `.claude/docs/ai-engine-tuning.md`에 기록하고, 필요하면 `docs/09`의 운영 설명에도 반영합니다.

**한계도 같이 적습니다**
- 대상이 작은 합성 앱이고 로그인이 없습니다. 큰 레거시 앱에서의 통과율은 이보다 낮을 가능성이 큽니다.

## 답변

'Agent 평가' 메뉴는 **Agent 하나를 같은 문제로 여러 번 다시 풀게 해서 채점하고, 그 점수를 DB에 쌓는 기능**입니다. Workflow 전체가 아니라 Agent 한 명을 따로 시험합니다.

## 데이터가 쌓이는 과정

**1. 사례(시험 문제)를 파일로 만들어 둔다**
`conf/eval/**/<id>.eval.yml` 파일 하나가 사례 하나이고, 옆에 자료 폴더가 붙습니다. 실제 실행에서 실패했거나 잘 됐던 순간을 그대로 떠 둔 것입니다.
- 어느 Agent에게 풀게 할지 (예: `sm-architect-agent`)
- 그때의 입력: 요청서, 요구사항·영향도 문서, 사람의 승인 의견 등
- 채점 기준(`checks`): 정답 파일을 두지 않고 기계가 확인할 수 있는 조건만 적습니다
  - 예: "03-1.design.md를 저장했나", "설계서에 TS_300이 들어갔나", "dbQuery를 썼나"
  - 채점 종류: `fileExists`, `fileContains`, `fileChanged`, `textIncreased`, `answerContains`, `toolUsed` 등

**2. 화면에서 실행한다**
사례를 고르고, 필요하면 모델과 경로 같은 params를 바꾼 뒤 반복 수(기본 3, 최대 5)를 정해 시작합니다.
- 실행은 `EvalRunner`가 대기열에서 하나씩 처리합니다(평가 스레드 기본 1개).
- 한 번의 실행은 이렇게 돕니다: 자료를 새 작업 폴더에 복사 → 실제 LLM으로 그 Agent 호출 → checks로 채점 → 저장.

**3. `AI_EVAL_RUN` 테이블에 한 줄씩 쌓인다**
한 줄에 담기는 것:
- 사례, Agent 버전, 모델
- 통과한 채점 수와 전체 수, 항목별 결과
- 걸린 시간, LLM 호출 횟수, Tool 호출 횟수, 토큰
- 작업 폴더 경로

작업 폴더는 지우지 않고 남기므로 Agent가 실제로 쓴 결과물을 나중에 열어 볼 수 있습니다.

**4. 화면이 비교 표로 묶어 보여 준다**
(사례, Agent 버전, 모델)별 평균을 보여 줍니다. 그래서 "버전 2.0 → 2.1에서 통과율이 어떻게 변했나", "qwen과 다른 모델 중 어느 쪽이 나은가"가 한 표에 나옵니다.

## 용도

Agent를 고친 효과를 감이 아니라 숫자로 확인하는 데 씁니다. CLAUDE.md 규칙의 순서는 이렇습니다.
1. Agent가 실패하면 프롬프트를 고치기 **전에** 그 순간을 사례로 떠 둡니다. 자료가 금방 바뀌거나 지워지기 때문입니다.
2. 고치기 전 정의로 돌려 기준선을 잽니다. 이때 실패해야 쓸모 있는 사례입니다. 고치기 전에도 통과하면 개선 효과를 가르지 못합니다.
3. 프롬프트, Skill, 모델을 고칩니다.
4. 같은 사례를 3번 이상 다시 돌려 기준선과 비교합니다.
5. 측정 결과는 `ai-engine-tuning.md`에 남깁니다.

다른 Agent 고칠 때 예전 사례가 깨지지 않았는지 보는 회귀 확인용으로도 쓰입니다.

## 지금 하는 통과율 측정과의 차이

| | Agent 평가 메뉴 | 지금 돌리는 측정 |
|---|---|---|
| 대상 | Agent 한 명 (한 step) | Workflow 전체 (요청서 → step17) |
| 채점 | 파일·답·Tool 사용 여부 | 결과물을 띄워 HTTP·DB로 실제 동작 확인 |
| 시간 | 한 번에 몇 분 | 한 번에 수십 분 |
| 쓰임 | 특정 Agent를 고친 효과 확인 | 어느 단계가 약한지 찾기 |

측정에서 실패가 특정 Agent에 몰리면, 그 실패 순간을 Agent 평가 사례로 떠 두고 그 Agent를 고치면서 메뉴로 반복 확인하는 식으로 이어집니다.

## 이 구조가 가진 문제

- 사례 없이 결과만 남아서, 결과를 눌러도 같은 사례로 다시 돌릴 수 없습니다.
- 사례 파일을 고친 뒤 같은 ID로 돌리면, 내용이 다른 사례의 결과가 비교 표에서 한 줄로 섞입니다. 결과 행에 사례 내용의 지문(해시)을 남기지 않기 때문입니다.

1. `temp/eval`을 `conf/eval`로 복사(또는 `dstone.ai.eval.location`을 그쪽으로 지정)해서 지금 화면에서 다시 돌릴 수 있게 한다. `conf/eval`은 git 제외로 두어야 합니다.
2. 결과 행에 사례 지문을 남기고, 사례 파일이 없는 결과는 화면에 "사례 없음"으로 표시하도록 고친다.
