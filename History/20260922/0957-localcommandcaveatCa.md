## 답변

PDF 제안서(Braincrew "DeepCode" 전사 코드에이전트 구축안)를 확인했고, 요청하신 건 그중 "승인 게이트가 있는 SDLC 오케스트레이션" 개념을 dstone-ai-engine 기존 Workflow 엔진으로 구현하는 것으로 판단했습니다. 계획을 `/app/dstone/docs/temp/dongyang-plan.md`에 정리했고, 핵심만 요약하면:

**스코프 판단**: 제안서 전체(3채널 UI, 위키DB, GPU 추론서버, 격리실행)는 별도 인프라 도입 사업이고, dstone-ai-engine이 대체할 대상이 아닙니다. 실제 요청은 8단계 승인 프로세스이고, 이건 이미 있는 `Workflow → Step(AGENT/TOOL/APPROVAL) → Agent → Tool` 구조, 특히 `APPROVAL` 스텝(승인될 때까지 멈췄다가 이어감, Postgres에 영속 저장 — 몇 주짜리 대기도 안전)이 정확히 이 용도로 설계돼 있습니다.

**설계**: `resources/workflows/dongyang/dongyang-sdlc.yml` 하나의 긴 Workflow로 8단계 전체(3개 승인 게이트: 분석/설계 검수 → 개발명세서 PL승인 → 최종 코드 PL승인, 각각 반려 시 재작성 루프백)를 표현. 신규 Agent 3개(analysis/spec-writer/codegen), 신규 Tool 2개(JiraTool, JenkinsTool — 기존 HttpCallTool엔 인증 헤더가 없어서 새로 필요)를 만들면 됩니다.

**보완이 필요하다고 판단한 것**:
1. `approverRole`은 현재 감사 기록용일 뿐 실제 권한 검증이 아님 — "PL 승인" 게이트인데 아무나 승인 API를 호출할 수 있는 상태
2. 5단계 "AI 소스 생성"을 실제 파일/Git 커밋까지 자동화할지, 1차는 텍스트 산출물(JIRA 첨부)로 안전하게 시작할지
3. 제안서의 "위키형 지식DB"는 새로 안 만들고 dstone-ai-engine에 이미 있는 RAG(pgvector+Ollama)를 재사용하는 걸 권장

**확인 필요한 것**: JIRA가 Cloud/Server인지와 인증 방식, JIRA→엔진 웹훅 도달 가능 여부, 코드 생성 대상 저장소, Jenkins Job 재사용 여부, PL 권한 검증 수준.

Phase 0(JiraTool/JenkinsTool 뼈대)부터 시작할지, 아니면 위 질문에 대한 답부터 받고 진행할지 말씀해 주시면 이어서 진행하겠습니다.
