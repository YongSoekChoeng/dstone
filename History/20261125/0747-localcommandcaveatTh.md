# 개발 승인(step19)의 진행 루트

개발 승인은 개발과 컴파일 확인, 자동 검증까지 끝난 뒤 사람(PL)이 결과를 보고 다음 길을 고르는 단계입니다. 무엇을 고르느냐에 따라 **어디까지 되돌아가서 다시 할지**가 정해집니다.

| 선택 | 되돌아가는 범위 | 고치는 주체 |
|---|---|---|
| 재개발 | 개발만 다시 | 개발 Agent (`sm-developer-agent`) |
| 전문가 해결 | 개발만 다시, 대신 깊이 파고듦 | 문제 해결 Agent (`sm-troubleshooter-agent`) |
| 설계 수정 | 설계부터 다시 | 문서 수정 Agent (`document-revise-agent`) |
| 영향도 수정 | 영향도분석부터 다시 | 문서 수정 Agent (`document-revise-agent`) |
| 요구사항 수정 | 요구사항부터 다시 | 문서 수정 Agent (`document-revise-agent`) |

모든 루트에서 **승인할 때 적은 의견**이 엔진을 거쳐 다음 Agent의 `instruction`(`${arrival}`)으로 넘어갑니다. 그래서 무엇을 고칠지는 의견란에 구체적으로 적어야 합니다.

---

## 1. 재개발 → step20 (21-재개발 전 설계서 다시 읽기)

**언제 쓰나:** 설계는 맞는데 코드가 조금 잘못됐을 때 씁니다. "이 메소드에서 null 처리가 빠졌다"처럼 고칠 곳이 분명한 경우입니다.

**흐름:**
```
step20 설계서 다시 읽기 → step21 태스크아이템 목록 다시 읽기
 → step17 개발 → step18 컴파일 확인 → (자동 검증) → step19 개발 승인
```

**핵심:**
- 개발 폴더(`dev-resources`)를 **비우지 않습니다**. 처음부터 새로 짜지 않고 지금 있는 결과를 고칩니다.
- 설계서를 다시 읽는 이유는 지난 개발이나 전문가 해결이 설계서에 고친 내용을 적어 두었을 수 있어서입니다. 최신 설계서를 줘야 그 내용을 되돌리지 않습니다.
- 개발 Agent는 코드를 고치면서 그 내용을 설계서에도 옮겨 적습니다. 그래서 나중에 설계 수정으로 개발 폴더를 비우더라도 재개발에서 고친 내용은 남습니다.

## 2. 전문가 해결 → step22 (23-전문가 해결 전 설계서 다시 읽기)

**언제 쓰나:** 컴파일은 되는데 실제로 돌리면 동작하지 않을 때 씁니다. 원인을 모르거나 재개발로 해결되지 않은 경우입니다. **본 증상을 의견에 적어야 합니다**(예: "저장 버튼을 누르면 500 오류").

**흐름:**
```
step22 설계서 다시 읽기 → step23 태스크아이템 목록 다시 읽기
 → step24 전문가 해결 → step18 컴파일 확인 → (자동 검증) → step19 개발 승인
```

**재개발과 다른 점:**
- `sm-troubleshooter-agent`가 코드만 보지 않고 직접 확인합니다. 프로젝트 DB를 조회하고, 격리 시험 서버(`startSandboxServer`)를 띄워 브라우저로 증상을 재현한 뒤 고친 결과를 다시 확인합니다.
- 격리를 지원하지 않는 프로젝트에서만 원래 DB에 붙는 임시 시험 서버(`startTestServer`)를 씁니다.
- 로그인이 필요하면 프로젝트 관리에 등록한 시험계정을 씁니다. 요청서에는 계정을 적지 않습니다.
- 원인과 수정 내용은 설계서에도 남깁니다.
- 이 Agent가 실패하면 개발 승인(step19)으로 바로 돌아옵니다.

## 3. 설계 수정 → step25 (26-설계서 수정)

**언제 쓰나:** 코드 문제가 아니라 설계가 잘못됐을 때 씁니다. 테이블 구조, 화면 구성, 처리 방식을 바꿔야 하는 경우입니다.

**흐름:**
```
step25 설계서 수정 → step13 설계 승인
 → (승인 시) step14·15 설계서·목록 읽기 → step16 개발 폴더 비우기
 → step17 개발 → step18 컴파일 확인 → … → step19 개발 승인
```

**핵심:**
- 설계 문서 3개(`03-1.design.md`, `03-2.taskitems.md`, `03-3.ddl(데이터베이스).md`)를 고칩니다. 새로 쓰지 않고 의견으로 지시받은 부분만 고칩니다.
- 컴파일 오류가 있었다면 그 내용도 참고 자료(`reference`)로 함께 넘깁니다.
- 고친 설계서를 **설계 승인에서 다시 확인받습니다**. 이때 검증 수준(화면 검증, 기동만 확인, 컴파일만)도 다시 고릅니다.
- 승인하면 **개발 폴더를 비우고 새로 개발합니다**. 설계서에서 빠진 파일이 개발 폴더에 남지 않게 하려는 것입니다. 재개발과 전문가 해결로 고친 내용은 설계서에 적혀 있으므로 사라지지 않습니다.

## 4. 영향도 수정 → step26 (27-영향도분석서 수정)

**언제 쓰나:** 영향 범위를 잘못 잡았을 때 씁니다. 빠뜨린 프로그램이나 테이블이 있거나, 건드리지 말아야 할 곳까지 넣은 경우입니다.

**흐름:**
```
step26 영향도분석서 수정 → step09 영향도 분석 승인
 → (승인 시) step10 영향도분석서 읽기 → step11 기존 설계서 확인
 → step37 기존 설계서 맞춤 → step13 설계 승인 → … (3번과 같은 길로 개발)
```

**핵심:**
- `02.impact.md`에서 지시받은 부분만 고친 뒤 영향도 분석 승인을 다시 받습니다.
- 설계서는 이미 있으므로 새로 쓰지 않습니다. step37이 **바뀐 영향도분석서에 어긋나는 곳과 빠진 곳만** 설계서에서 고칩니다. 재개발과 전문가 해결로 고친 내용('## 수정 이력')은 영향도분석서와 어긋나지 않으면 그대로 둡니다.
- 그다음은 설계 승인부터 3번과 같습니다.

## 5. 요구사항 수정 → step27 (28-고객요구사항분석서 수정)

**언제 쓰나:** 요청을 잘못 이해했을 때 씁니다. 결과를 보니 고객이 원한 것과 다르다는 걸 알게 된 경우입니다. 가장 멀리 되돌아가는 선택입니다.

**흐름:**
```
step27 요구사항분석서 수정 → step04 요구사항분석서 읽기 → step05 요구사항 리뷰
 → step07 기존 영향도분석서 확인 → step38 기존 영향도분석서 맞춤
 → step09 영향도 분석 승인 → … (4번과 같은 길: 설계서 맞춤 → 설계 승인 → 개발)
```

**핵심:**
- `01.customer_requirement.md`에서 지시받은 부분만 고칩니다.
- 고친 요구사항은 **리뷰 Agent(`sm-requirement-analyze-reviewer-agent`)의 리뷰를 다시 받습니다**. 통과하지 못하면 리뷰 불통과 처리 결정(step06)에서 사람이 다시 고릅니다.
- 그 뒤 문서가 차례로 맞춰집니다. 영향도분석서는 step38이, 설계서는 step37이 바뀐 요구사항에 어긋나는 부분만 고칩니다. 승인도 영향도, 설계, 개발 순서로 다시 받습니다.

## 한눈에 보기

```
요구사항 ──► 영향도 ──► 설계 ──► 개발 ──► 컴파일·검증 ──► 개발 승인
   ▲           ▲         ▲        ▲                          │
   │           │         │        ├── 재개발 ────────────────┤
   │           │         │        └── 전문가 해결(재현·확인) ─┤
   │           │         └────────── 설계 수정 ──────────────┤
   │           └──────────────────── 영향도 수정 ────────────┤
   └──────────────────────────────── 요구사항 수정 ──────────┘
```

**모든 루트에 공통인 원칙**
1. **새로 쓰지 않고 고칩니다.** 앞 문서가 바뀌어도 뒤 문서는 어긋난 부분만 맞춥니다. 그래야 재개발이나 전문가 해결로 고친 내용이 사라지지 않습니다.
2. **다시 돌 때는 화면 검증까지 합니다.** 설계 승인에서 "기동만 확인"이나 "컴파일만"을 골랐더라도 그 생략은 첫 검증에만 적용됩니다. 재개발, 전문가 해결, 문서 수정을 거쳐 다시 오면 화면 검증까지 합니다(step42가 횟수를 셉니다).
3. **어느 길로 가든 마지막에는 개발 승인(step19)으로 돌아옵니다.** 그래서 만족할 때까지 이 선택을 반복할 수 있습니다.

**고르는 기준:** 코드만 틀렸으면 재개발, 왜 안 되는지 모르겠으면 전문가 해결, 만드는 방법이 틀렸으면 설계 수정, 고칠 범위가 틀렸으면 영향도 수정, 요청을 잘못 이해했으면 요구사항 수정을 고릅니다.
