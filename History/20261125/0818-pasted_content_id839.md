## 답변

## 먼저 알아 둘 것: 개발 승인(step19)

`20-개발 승인`(step19)은 개발 결과를 사람(PL)이 보고 다음에 할 일을 고르는 곳입니다. 다음 경우에 여기로 옵니다.

- 컴파일 확인(step18)이 실패했을 때
- 자동 검증을 마쳤을 때
- 검증을 생략하기로 했을 때
- 자동 수정을 정해진 횟수만큼 다 썼을 때

어느 길을 고르든 고른 결정과 승인 의견을 엔진이 다음 Agent에 넘깁니다.
- `instruction: ${arrival}`: 이번에 고른 결정과 적은 의견
- `history: ${decisions:}`: 이 실행에서 지금까지 내려진 결정 전체

**승인 의견에 적은 글이 곧 Agent가 받는 작업 지시입니다.** 무엇을 고칠지 구체적으로 적을수록 결과가 좋아집니다.

## 1. 재개발 → step20

**쓰는 때:** 설계는 맞는데 개발 결과에 고칠 곳이 있을 때. 지난 결과를 지우지 않고 그 위에서 고칩니다.

| 순서 | 노드 | 하는 일 |
|---|---|---|
| ① | **step20** `21-재개발 전 설계서 다시 읽기` (TOOL `readFile`) | `03-1.design.md`를 다시 읽어 `state.design`을 새 내용으로 바꿉니다. 지난 개발·전문가 해결·자동 수정이 설계서에 적어 둔 고친 내용까지 반영하려는 것입니다. 파일이 없거나 60,000자를 넘으면 실행이 실패로 멈춥니다. |
| ② | **step21** `22-재개발 전 태스크아이템 목록 다시 읽기` (TOOL `readFile`) | `03-2.taskitems.md`를 다시 읽어 `state.taskitems`에 넣습니다. 지난 개발이 적은 완료·보류 상태가 들어 있습니다. |
| ③ | **step17** `18-개발` (AGENT `sm-developer-agent`) | **개발 폴더를 비우는 step16을 거치지 않습니다.** `dev-resources`에 있는 지난 결과에서 지시와 관련된 곳만 고칩니다. 재개발에서는 사람의 지시가 설계서보다 앞섭니다. 지시 때문에 설계서와 달라진 곳은 보류로 두지 않고, 고친 뒤 설계서에도 옮겨 적습니다(`designSynced`). 지난 컴파일 오류(`compile_error`)가 있으면 그것부터 고칩니다. 끝내기 전에 `compileJava`로 직접 컴파일해 보고 최대 3번까지 고칩니다. |
| ④ | **step18** `19-컴파일 확인` (TOOL `compileJava`) | 바뀐 파일만 원본 위에 올려 다시 컴파일합니다. 실패하면 오류를 `compileError`에 담아 **step19로 돌아옵니다.** 통과하면 ⑤로 갑니다. |
| ⑤ | **step28** `29-자동 검증할 프로젝트 확인` | 요청서의 `## 프로젝트ID`를 읽습니다. 없으면 자동 검증을 할 수 없으니 step19로 갑니다. |
| ⑥ | **step42** `30-첫 검증인지` (`countUp`, max 1) | 이미 검증한 적이 있으면 `over`가 나와, 설계 승인에서 검증 생략(컴파일만, 기동만)을 골랐더라도 **화면 검증으로 갑니다.** |
| ⑦ | step41 → step40 → step29 → step35 → step36 | 설계서 다시 읽기 → 지난 검증 뒤 바뀐 파일 찾기 → 격리 서버 기동 → `sm-verifier-agent`의 동작 검증 → FAIL이 있는지 확인 |
| ⑧ | FAIL이나 코드 탓의 기동 실패가 있으면 step31 → 32 → 33 → 34 | 자동 수정(`sm-auto-fix-agent`)을 하고 step18로 돌아갑니다. **이번 결정 하나에 최대 2번까지**입니다. 다 쓰면 step19로 옵니다. |
| ⑨ | 문제가 없으면 **step19** | 다시 개발 승인으로 옵니다. |

**정리:** 읽기 → 고치기 → 컴파일 → (자동 검증·자동 수정) → 개발 승인
**의견 예:** "목록 화면 조회 버튼을 누르면 날짜 조건이 빠짐. 시작일·종료일 조건을 넣을 것"

## 2. 전문가 해결 → step22

**쓰는 때:** 컴파일은 되는데 **실제로 돌리면 동작하지 않고**, 원인을 모를 때. 승인 의견에 **본 증상**을 적습니다.

| 순서 | 노드 | 하는 일 |
|---|---|---|
| ① | **step22** `23-전문가 해결 전 설계서 다시 읽기` | step20과 같습니다. 최신 설계서를 `state.design`에 넣습니다. |
| ② | **step23** `24-전문가 해결 전 태스크아이템 목록 다시 읽기` | step21과 같습니다. |
| ③ | **step24** `25-전문가 해결` (AGENT `sm-troubleshooter-agent`, reasoning high) | 증상에서 원인을 따라갑니다(화면 → Controller → SQL → 테이블). 동작하는 기존 기능이나 라이브러리 소스와 비교합니다. 이 Agent만 쓸 수 있는 도구가 있습니다. **knowledge 조회**(호출 관계, 테이블 사용처), **프로젝트 DB 조회**(`dbQuery` 등), **격리 시험 서버**(`startSandboxServer`)를 띄워 브라우저로 재현하고 확인하기입니다. 격리를 지원하지 않는 프로젝트에서만 원래 DB에 붙는 `startTestServer`를 씁니다. 시험계정은 프로젝트 관리에 등록된 것을 씁니다. 고친 내용은 `dev-resources`에 반영하고, 설계서와 태스크아이템 목록에도 남깁니다. |
| | 답(`state.troubleshoot`) | 원인과 근거(파일:줄), 고친 것, 설계서와 달라진 점, 확인 방법, 못 푼 것, 화면 재현 여부(`reproduced`), 컴파일 결과 |
| ④ | 성공하면 **step18** | 이후는 재개발의 ④~⑨와 똑같습니다(컴파일 → 자동 검증 → 개발 승인). |
| ④' | Agent가 실패하면 **step19** | 바로 개발 승인으로 돌아옵니다. |

**재개발과 다른 점:** 재개발은 "이렇게 고쳐라"라고 지시하는 것이고, 전문가 해결은 "이렇게 안 된다"는 증상을 주고 원인 찾기를 맡기는 것입니다.
**의견 예:** "등록 버튼을 누르면 500 오류. 로그에 `Unknown column 'REG_DT'`"

## 3. 설계 수정 → step25

**쓰는 때:** 개발 결과를 보니 **설계 자체가 잘못됐을 때.** 설계서를 고치고 개발을 처음부터 다시 합니다.

| 순서 | 노드 | 하는 일 |
|---|---|---|
| ① | **step25** `26-설계서 수정` (AGENT `document-revise-agent`) | 문서 세 개를 고칩니다. 주 문서는 `03-1.design.md`이고, `03-2.taskitems.md`와 `03-3.ddl(데이터베이스).md`는 함께 맞춥니다. **지시받은 곳만 고치고 나머지는 한 글자도 바꾸지 않습니다.** 앞서 재개발이나 전문가 해결로 남긴 수정 이력도 그대로 둡니다. 마지막 컴파일 오류는 `reference`로 함께 받습니다. 주 문서를 실제로 고쳐 저장했는지는 엔진이 확인합니다(`requiredWrites`). |
| ② | **step13** `14-설계 승인` (APPROVAL) | 고친 설계서를 사람이 다시 승인합니다. 고를 수 있는 것: 승인(개발진행) / 기동만 확인 / 컴파일만 / 설계 수정(다시 ①) / 설계 다시 작성(step12, 처음부터 새로) / 영향도 수정(step26) / 중지 |
| ③ | 승인하면 **step14 → step15** | 고친 설계서와 태스크아이템 목록을 읽습니다. |
| ④ | **step16** `17-기존개발디렉토리초기화` (`deleteDir`) | **`dev-resources`를 비웁니다.** 설계서에서 빠진 파일이 남지 않게 하려는 것입니다. 지난 재개발·전문가 해결로 고친 것은 이미 설계서에 옮겨 적혀 있어서 사라지지 않습니다. 이때 `compileError`도 비워집니다. |
| ⑤ | **step17** `18-개발` | 고친 설계서대로 **새로** 개발합니다. |
| ⑥ | step18 이후 | 재개발의 ④~⑨와 같습니다. 이미 검증한 적이 있으면 설계 승인에서 검증 생략을 골랐더라도 화면 검증을 합니다. |

**의견 예:** "삭제를 물리 삭제가 아닌 `DEL_YN='Y'` 논리 삭제로 바꿀 것"

## 한눈에 비교

| 고른 길 | 처음 고치는 것 | 다시 거치는 사람 승인 | 개발 폴더 | 뒤 문서 처리 |
|---|---|---|---|---|
| 재개발 | 개발 결과 | 없음, 바로 개발 승인 | **유지**(덧고침) | 고친 내용을 설계서에 옮겨 적음 |
| 전문가 해결 | 개발 결과(원인 추적) | 없음, 바로 개발 승인 | **유지** | 고친 내용을 설계서에 남김 |
| 설계 수정 | 설계서·목록·DDL | 설계 승인 | **비우고 새로** | — |
| 영향도 수정 | 영향도분석서 | 영향도 승인, 설계 승인 | **비우고 새로** | 설계서를 맞춤(step37) |
| 요구사항 수정 | 요구사항분석서 | (리뷰), 영향도 승인, 설계 승인 | **비우고 새로** | 영향도(step38)와 설계서(step37)를 맞춤 |

알아 둘 점 세 가지:
- **뒤 문서는 새로 쓰지 않고 맞춥니다**(2.3.0). 그래서 앞 문서를 고쳐도 재개발·전문가 해결로 고친 내용이 남습니다. 처음부터 새로 쓰는 것은 "~ 다시 작성"을 고를 때뿐입니다.
- **검증 생략(컴파일만, 기동만)은 첫 검증에만** 적용됩니다. 한 번이라도 검증을 했다면 어느 길로 돌아오든 화면 검증까지 합니다.
- **자동 수정 횟수(2번)는 결정마다 새로 셉니다**(`scope: ${decisions:}`). 개발 승인에서 무엇이든 새로 고르면 다시 2번까지 자동 수정합니다.
