## 답변

`dstone-ai-engine/conf/application.yml:26`의 설정이고, **로컬 Ollama로 채팅 모델을 돌릴 때 응답을 기다리다 "Read timed out"으로 끊기는 것을 막기 위한 값**입니다.

- **무엇을 정하나**: Spring Boot가 만들어 주는 HTTP 클라이언트(`RestClient.Builder`)의 응답 대기 시간입니다.
- **왜 5분인가**: Spring AI의 `OllamaApi`가 이 `RestClient.Builder`를 그대로 씁니다. 이 장비의 Ollama는 CPU 추론이라 프롬프트가 길거나 Tool 호출이 붙으면 응답이 오래 걸리는데, 값을 올려 두지 않으면 답이 오기 전에 연결이 끊깁니다.
- **언제 영향이 없나**: 설정 파일의 주석에 따르면 provider가 anthropic이나 openai(OpenRouter 포함)일 때는 이 값이 영향을 주지 않습니다. openai 쪽 타임아웃은 `ConfigChatClient.requestOptions()`가 요청마다 따로 넣습니다.

정리하면 provider를 `ollama`로 쓸 때만 의미가 있는 설정입니다. 지금처럼 OpenRouter만 쓴다면 없어도 동작은 같겠지만, Ollama로 바꾸는 순간 다시 필요해지므로 그대로 두는 편이 낫습니다.

`dstone-knowledge/conf/application.yml:68`에도 같은 키가 `300s`로 있는데, 그쪽은 목적이 다릅니다. 임베딩 서버(Ollama)가 응답하지 않을 때 끝없이 기다리지 않게 하려는 상한입니다.

## 답변

Mustache는 `dstone-ai-engine`에서 **`renderTemplate` Tool 한 곳**에서만 쓰입니다. Workflow의 TOOL step이 LLM 없이 데이터를 틀 파일에 끼워 문서나 새 파일 내용을 만들 때 쓰는 용도입니다.

**엔진 쪽(Java)**
- `tools/template/TemplateRenderer.java` — jmustache(`com.samskivert:jmustache`)를 직접 부르는 유일한 클래스입니다. 틀 내용과 데이터를 받아 글자를 돌려주며, 파일은 읽거나 쓰지 않습니다.
- `tools/template/TemplateTool.java` — `renderTemplate(template, data, filePath)` Tool입니다. `definitions/templates/` 아래의 틀 파일을 읽어 `TemplateRenderer`로 넘기고, `filePath`가 있으면 결과를 파일로 저장합니다. step 전용 Tool이라 LLM에게는 보이지 않습니다.

**틀 파일 (`definitions/templates/`, 6개)**

| 틀 파일 | 쓰는 곳 |
|---|---|
| `pilot/newdev-requirements.md.mustache` | `pilot-workflow` `step13` — `01-requirements.md` |
| `pilot/newdev-impact.md.mustache` | `pilot-workflow` `step14` — `02-impact.md` |
| `pilot/newdev-design.md.mustache` | `pilot-workflow` `step21` — 설계 문서 |
| `pilot/newdev-newfile.mustache` | `pilot-workflow` `step25`/`step26` — 참고 구현이 없는 새 소스 파일의 내용 |
| `pilot/newdev-tasks.md.mustache` | `pilot-workflow` `step32` — `04-tasks.md` |
| `sample/edit-report.md.mustache` | `sample-tool-edit-report` — 결과 보고서 |

`pilot-workflow`에서는 신규개발 경로에서만 쓰고, 일반 경로는 Agent가 문서를 직접 씁니다. step 번호는 `CLAUDE.md` 기록 기준이고, YAML에서 `renderTemplate`을 부르는 위치는 `pilot-workflow.yml`의 353·366·477·550·637행입니다.

## 답변

`sample-override`는 샘플 Agent 하나(`sample-model-override-agent`)가 쓰는 "모델 별명"이고, 이 설정은 그 별명을 실제 모델 이름으로 바꿔 주는 값입니다. 엔진 기능에 꼭 필요한 값이 아니라, "Agent 하나만 다른 모델로 돌리기" 기능의 예시를 위해 있습니다.

**어떻게 동작하나**
- 엔진은 모든 Agent가 같은 provider의 기본 모델(`spring.ai.{provider}.chat.options.model`)을 씁니다.
- Agent YAML에 `model.routing: sample-override`라고 적으면, 그 Agent를 호출할 때만 `dstone.ai.model.routing.sample-override`에 적힌 모델(`qwen/qwen-2.5-coder-32b-instruct`)로 바꿔서 부릅니다.

**왜 YAML에 모델 이름을 직접 안 적고 설정을 거치나**
- 실행 환경(로컬, k8s, 고객사)마다 쓸 수 있는 모델이 달라도 Agent 정의 파일은 그대로 두고 `application.yml`만 바꾸면 되게 하려는 것입니다.
- 직접 적는 방법(`model.name`)도 있지만 둘을 함께 쓸 수는 없습니다.

**이 줄이 없으면**
- `sample-model-override-agent`가 이 이름을 쓰고 있어서 기동이 실패합니다(`AgentRegistry.java:139`의 검사). 오타 난 별명이 조용히 기본 모델로 돌아가는 일을 막으려고 일부러 기동 때 막아 둔 것입니다.
- 이 Agent를 부르는 곳은 `sample-agent-model-override` Workflow 하나뿐입니다.

정리하면, 샘플 Agent와 그 Workflow를 지우면 이 설정도 필요 없어집니다. 반대로 실제 Agent에 모델을 따로 주고 싶을 때는 같은 자리에 별명을 하나 더 추가하면 됩니다. 이때 `conf/application.yml`과 `k8s/configmap.yaml` 양쪽에 넣어야 합니다.

## 답변

네, 맞습니다. Agent YAML에서 모델을 오버라이드하는 키는 `model` 블록이고, 그 안에 방법이 두 가지 있습니다.

```yaml
agent:
  model:
    name: qwen/qwen-2.5-coder-32b-instruct   # 방법 1: 모델 이름을 직접 적는다
```

```yaml
agent:
  model:
    routing: sample-override                 # 방법 2: 별명을 적고, 실제 이름은 application.yml에서 찾는다
```

- **`model.name`**: 모델 이름을 YAML에 바로 적습니다. `application.yml` 설정이 필요 없습니다.
- **`model.routing`**: 별명만 적고, 엔진이 `dstone.ai.model.routing.<별명>` 값을 읽어 모델 이름으로 씁니다. `sample-override` 설정이 필요한 것은 이 방법을 쓸 때뿐입니다.
- 둘을 함께 적으면 기동이 실패합니다. 둘 다 없으면 provider의 기본 모델을 씁니다.

그래서 `sample-model-override-agent`를 `model.name` 방식으로 바꾸면 `dstone.ai.model.routing.sample-override` 줄은 지워도 됩니다. 지금은 그 샘플이 `routing` 방식을 보여 주려고 일부러 별명을 쓰고 있어서 설정이 남아 있는 것입니다.

참고로 `model` 블록에는 모델 선택 외에 `temperature`와 `reasoning`도 함께 들어갑니다.
