## 답변

원인을 확인했습니다. 분석 데이터 문제가 아니고, **노드 맵의 "이름으로 찾기"가 SQL statement는 찾지 않기 때문**입니다.

**`JADB3010D.selectListAdd`의 정체**

`selectListAdd`는 Java 메소드가 아니라 Query XML에 있는 **SQL statement**입니다.
- `was/WEB-INF/src/hi/dao/biz/ja/JADB3010D.xml:1254` — `<query id="selectListAdd">`
- `hi/ja/closing/dao/JADB3010D.java`에는 `<init>`과 `selectList(JADB3010VO)` 메소드 두 개만 있습니다. `selectList` 안에서 `new QueryProperty("JADB3010D.selectListAdd")`로 이 SQL을 부릅니다.

**찾기가 실패하는 과정** (`dstone-boot/src/main/webapp/knowledge/assets/js/graph.js:574` `find()`)

1. 지도에 있는 노드 3,035개의 이름에서 `jadb3010d.selectlistadd`를 찾습니다. statement는 노드가 아니고 매퍼 노드(`JADB3010D`, QUERY_XML) 안에 든 항목이라 맞는 노드가 없습니다.
2. 그러면 `.`에서 잘라 "클래스.메소드"로 다시 찾습니다(`findMethods`). 이때 **종류가 `TYPE`/`JSP`인 노드만** 봅니다. 그래서 매퍼 노드는 빠지고 DAO 클래스 `hi.ja.closing.dao.JADB3010D`만 걸립니다.
3. 그 클래스의 메소드 중에 `selectListAdd`라는 이름은 없습니다. 결과적으로 "클래스 1개에 이름에 selectlistadd이(가) 들어간 메소드가 없습니다"라는 안내가 나옵니다.

분석 결과에는 문제가 없습니다. 리비전 209의 매퍼 노드 상세에 `JADB3010D.selectListAdd`(1254~2103줄, `JA_TOTAL_CLOS_S`·`JZ_CMNS_DET` 읽기)가 정상적으로 들어 있습니다.

**지금 바로 찾으려면**
- `JADB3010D`만 입력해서 찾습니다. 클래스와 매퍼 노드가 함께 걸리고, "찾기"를 한 번 더 누르면 매퍼 노드로 넘어갑니다. 상세 패널의 statement 목록에 `selectListAdd`가 보입니다.
- 이 SQL을 실행하는 코드를 보려면 `JADB3010D.selectList`로 찾으면 됩니다. DAO 메소드의 관계 트리가 열립니다.

원하시면 `JADB3010D.selectListAdd`처럼 입력했을 때 매퍼 노드의 statement 이름도 찾도록 `find()`를 고치겠습니다. 찾으면 해당 매퍼 노드로 이동하고 그 statement를 강조합니다. 고칠까요?

**헷갈리는 지점 세 가지**

1. **"곳"이 무엇인지 알 수 없습니다.** 아래 구역의 4곳 + 57곳 = 61은 진입점 카드의 61과 같지만, 우연히 맞는 것처럼 보입니다. 화면 카드의 60과는 어디에서도 맞지 않습니다. 화면만 있고 진입점이 없는 줄도 1곳으로 세기 때문에, 프로젝트에 따라서는 진입점 카드와도 맞지 않습니다.
2. **"확실"의 기준이 카드와 구역에서 다릅니다.** 줄이 확실한지는 진입점의 신뢰도만 보고 정합니다. 그래서 "다시 테스트할 곳(확실)" 4줄 안에 추정(MEDIUM) 화면 5개가 들어 있습니다. 카드는 "화면 확실 0"이라고 하는데, 확실 구역에 화면이 보이는 셈입니다.
3. **카드와 구역의 짝이 보이지 않습니다.** 카드 ①·②는 위쪽 두 구역(다시 테스트할 곳, 추정 관계)과, 카드 ③·④는 맨 아래 두 구역(건드리는 데이터, 확인 필요)과 짝입니다. 하지만 카드 이름, 순서, 배치 어디에도 그런 연결이 드러나지 않습니다.

**고치는 방향 제안**
- **카드를 아래 구역과 1:1로 맞춥니다.**
  - 다시 테스트할 곳 (확실 N · 추정 M)
  - 화면 수
  - 쓰는 SQL
  - 확인 필요
  - 카드 숫자는 구역 제목의 숫자와 똑같이 맞추고, 카드를 누르면 해당 구역으로 이동합니다.
- **구역 제목에 단위를 적습니다.** 예: "다시 테스트할 곳 4곳 (진입점 4 · 화면 5)".
- **줄의 확실·추정을 화면까지 포함해 정합니다.** 줄에서 가장 약한 관계를 기준으로 삼거나, 확실 구역 안의 추정 화면에 "추정" 표시를 지금보다 눈에 띄게 붙입니다. 가장 약한 관계를 기준으로 하면 위 예에서 확실 4줄 중 일부가 추정으로 내려갑니다.

| MEDIUM | `PATH_TEXT` — 화면에 적힌 `/…do` 주소 글자가 진입점 주소와 같음 | 1,118 |
| MEDIUM | `COMMON_SCRIPT` — 공통 스크립트(`hslLib.xjs` 등) 함수 안의 주소 | 336 |
| HIGH | — | 0 |

영향도의 화면 신뢰도는 대상에서 화면까지 이어진 길 가운데 가장 약한 관계로 정해집니다. 화면 → 진입점 관계가 전부 MEDIUM이니, 화면 항목도 모두 MEDIUM이 됩니다.

**H-Energy 화면 소스의 모양** (`wabDtMgmt_M.xfdl:624`)
```js
var strSvc = "insertWabDtAutoCrt";
var strUrl = "/hhr/ws/insertWabDtAutoCrt.do";
...  // 이어서 strUrl 을 거래 함수에 넘긴다
```

**HIGH가 붙는 경우는 하나뿐입니다** (`ScreenLinker.java:489`)
- 규칙 파일의 `screen: - call: 함수(ID)`에 맞는 호출이어야 합니다.
- ID 자리가 **따옴표 글자**여야 합니다.
- 그 ID에 맞는 메소드가 하나여야 합니다.
- 화면 소스에 직접 적힌 호출이어야 합니다(공통 함수 안이면 MEDIUM).

HI-Japan은 `doRequestAjax("JCST0200M01S", …)`처럼 거래 ID를 바로 적기 때문에 HIGH가 나옵니다. H-Energy는 두 가지 이유로 HIGH가 나올 수 없습니다.
1. 프로젝트 규칙 파일(`conf/rules/projects/` 아래)이 없습니다. 지금 있는 것은 `hi-japan`뿐입니다.
2. 규칙을 만들어도 거래 함수에 넘기는 값이 `strUrl` **변수**입니다. "이름은 따옴표 글자만 인정하고 추측하지 않는다"는 원칙 때문에 규칙으로 잇지 못하고, 주소 글자 일치(MEDIUM)로만 이어집니다.

즉 지금 MEDIUM은 버그가 아니라 설계대로입니다. "화면에 그 주소 글자가 있다"는 것만 확인했고, 실제로 그 주소로 호출한다는 것까지는 증명하지 못했다는 뜻입니다.

**HIGH로 올리려면** 분석기를 넓혀야 합니다. 같은 함수 안에서 따옴표 글자를 **한 번만** 대입한 지역 변수(`var strUrl = "/…do"`)를 거래 함수에 넘기면, 그 글자로 계산해 HIGH(또는 그에 준하는 신뢰도)로 잇는 방식입니다. 추측이 아니라 계산이므로 원칙에도 맞습니다. 대신 H-Energy의 거래 함수 이름을 확인해 규칙 파일을 새로 만들어야 하고, 분석 단계(SEMANTIC)를 다시 돌려야 합니다. 진행할까요?
