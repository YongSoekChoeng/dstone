## 답변

`sm-auto-fix-agent`가 `Skill` Tool을 `gnx-crud-screen` 인자로 5번 연달아 불렀고, 매번 결과가 같았다는 건 코드 분석으로 확인했습니다. 다만 5번 모두 결과가 같았던 이유는 가설입니다. Windows 쪽 로그와 실행 이력(`d9f0bcc0`)은 이 WSL 저장소에 없어서 실제 기록으로는 확인하지 못했습니다.

## 확인한 것

- 중단 문구는 `RepeatCallGuardCallback.java:127`에서 나옵니다. 같은 Tool을 같은 인자로 불렀고 결과까지 같으면 센다는 장치입니다. 5번째(`fail-at`)에 끊습니다.
- `Skill` Tool(`SkillTool.java`)은 같은 Skill을 두 번째 부르면 본문 대신 짧은 안내를 돌려줍니다. 이 경우 5번 연속이 되려면 6번 불러야 합니다. 그런데 오류는 5번이라고 했으니, 호출마다 Skill 본문이 통째로 돌아왔다는 뜻입니다. `ReadHistory.skills` 장부가 매번 비어 있었다는 얘기입니다.

## 의심하는 원인

이 장부를 비우는 곳이 `ToolResultCompactionAdvisor.java:97`입니다. 대화에 쌓인 Tool 결과가 `keep-result-chars`(기본 200000자)를 넘으면 오래된 결과를 앞 300자만 남기고 줄입니다. 이때 `readHistory.clear()`가 읽은 파일 기록과 받은 Skill 기록을 모두 지웁니다.

추정되는 흐름은 이렇습니다.

1. `sm-auto-fix-agent`는 시험 서버 로그, 브라우저 스냅숏, 네트워크 요청 같은 큰 결과를 많이 받습니다. 그래서 압축이 계속 일어납니다.
2. 8,365자짜리 `gnx-crud-screen` 본문은 압축 기준(600자)을 넘어, 가장 먼저 300자로 줄어듭니다. 줄인 자리에는 "같은 Tool을 다시 부르십시오"라는 문구가 붙습니다.
3. 모델이 그 문구대로 `Skill`을 다시 부릅니다. 장부가 비어 있으니 본문 전체가 돌아옵니다.
4. 다음 호출에서 또 압축되면서 같은 일이 되풀이됩니다. 결과가 매번 같아서 반복 호출로 끊깁니다.

2026-11-24에 30번 반복했을 때 만든 장치끼리, 그러니까 압축 안내문과 중복 호출 방지가 서로 부딪히는 것으로 보입니다.

이 가설이 맞는지 확인하려면 Windows 쪽 `execution.log`에서 `d9f0bcc0` 실행 시점을 찾아 아래 두 가지를 보면 됩니다.

- `대화에 쌓인 Tool 결과가 …자라서 오래된 것부터 줄였습니다`가 Skill 호출 사이사이에 찍혔는지
- `이미 받은 Skill '…'을 또 불러서 본문 대신 안내만 돌려줬습니다`가 한 번도 없었는지

## 제안하는 수정

원인이 맞다면 `ToolResultCompactionAdvisor`가 `readHistory.clear()`로 전부 지우는 대신, 줄인 결과에 해당하는 항목만 지우게 하는 방향이 맞습니다. Skill 본문은 줄여도 앞부분이 남으니, 모델이 필요하면 `readFile`로 SKILL.md를 다시 읽게 안내하는 방법도 있습니다.

1. **프롬프트의 "Skill troubleshooting을 따른다"가 모델을 Skill Tool로 이끕니다.** 이 두 Skill은 `skills.preload`라서 프롬프트 뒤에 이미 붙어 있고 Skill Tool 목록에는 없습니다. `sm-auto-fix-agent.md`는 "Skill troubleshooting", "Skill test-environment"라고만 적어서, 모델이 Tool로 불러야 하는 줄 알고 실패합니다. 이 실패가 Skill Tool 반복의 시작입니다.
2. **모델이 마무리를 못 합니다.** 일을 다 한 뒤 최종 답을 내야 하는데 Tool만 부릅니다. Skill 안내문이 "최종 답을 내십시오"라고 두 번 말했는데도 따르지 않았습니다. 이번 반복은 이 증상이 Skill 호출로 나타난 것입니다. 이전 실행 `9f14f909`의 30번 반복도 같은 모양입니다.

## 제안

- `sm-auto-fix-agent.md`의 "Skill troubleshooting을 따른다", "Skill test-environment로 보아"를 "아래에 붙은 troubleshooting 안내를 따른다"처럼 고칩니다. `skills.preload` 대상은 Tool로 부르지 않는다고 한 줄 적습니다. 다른 Agent 정의에도 같은 문구가 있는지 같이 보겠습니다.
- `RepeatCallGuardCallback`이 중단할 때 지금까지 쓴 파일과 마지막 정상 Tool 호출을 오류에 함께 남깁니다. 그러면 일이 끝났는지가 한눈에 보입니다. (선택)

## 1. 모델이 왜 마무리를 못 했는지부터 확인하기
지금 로그에는 모델이 마지막에 무슨 말을 했는지가 없어서, 원인이 둘 중 무엇인지 모릅니다.
- **(a) 모델 문제**: qwen이 "다 했다"는 판단을 못 하고 습관적으로 Tool을 부릅니다. 이 경우 22회차 이후 stopTestServer와 Skill을 되풀이한 모양과 맞습니다.
- **(b) 답 형식 문제**: `causes`/`changes`/`unresolved`로 최종 답을 내려다 실패하거나 거부당하고, 그때마다 Tool로 도망갑니다.

확인은 간단합니다. 반복에 걸렸을 때 마지막 몇 회차의 모델 출력(본문 텍스트와 Tool 요청)을 `execution.log`나 `llm/` 로그에 남기면 됩니다. 지금은 REQ 로그가 호출의 첫 요청만 남아서 이 부분이 안 보입니다. 다음 번에 같은 일이 나면 바로 판별되도록 로깅을 먼저 넣는 걸 권합니다.

## 2. 가드가 끊을 때 상태를 오류에 남기기
`RepeatCallGuardCallback`이 중단할 때, 그 호출에서 쓴 파일과 마지막으로 성공한 Tool 이름을 오류 문구에 붙입니다. 사람이 "일은 끝났는데 답만 못 냈다"를 바로 알아봅니다. `AgentExecutor`가 `writtenPaths`와 `succeededTools`를 이미 갖고 있어서 변경이 작습니다.

## 3. 끝난 일을 버리지 않는 재시도
이번 실행은 21회차까지 DDL과 설계서 수정을 마쳤는데, 전체가 실패 처리되어 그 시간이 버려졌습니다. 반복 호출로 끊기면 한 번만 다시 불러 보는 방법이 있습니다.
- 재시도에서는 Tool을 빼고 "작업은 끝났다. 지금까지 쓴 파일은 이것이다. 최종 답만 내라"고 시킵니다.
- Tool 없이 부르면 반복 자체가 불가능해서 가장 확실합니다.
- 다만 Agent 호출 결과의 의미가 바뀌는 엔진 변경입니다. 모든 Agent에 적용할지, `requiredWrites`가 이미 채워진 경우로 한정할지 정해야 합니다. 한정하는 쪽이 안전합니다. 쓴 파일이 있다는 것은 일이 됐다는 증거이기 때문입니다.

## Agent 한 번 호출이 끝나는 구조

1. `WorkFlowExecutor`가 AGENT step을 `AgentExecutor.call()`로 부릅니다.
2. `call()`은 `maxAttempts`만큼 시도합니다. `AgentContractException`이 나면 지난 실패 사유와 지난 답(`failure.answer()`)을 `retryNote`로 붙여 다시 부릅니다.

- `startSandboxServer`는 일회용 DB로 격리하지만, 프로젝트 잠금은 그대로 공유합니다. 그래서 격리 서버끼리도 프로젝트당 하나씩만 뜹니다.
- `sandboxError`에 이 거절이 들어가면 그 실행은 자동 검증을 건너뛰고 개발 승인으로 넘어갑니다. 두 번째 실행이 검증 없이 `DONE`이 된 것이 이 경우입니다.
- 그래서 병렬 시험의 결과는 검증을 거치지 않은 것으로 봐야 하고, 순차로 돌린 4회분만 자동 검증을 거쳤습니다.

격리 서버끼리는 포트와 DB가 서로 달라서 원리상 동시에 띄워도 될 것 같습니다. 이 잠금이 꼭 필요한지는 확인하지 못했습니다. 병렬 실행이 필요하면 따로 살펴보겠습니다.

## 2. `startTestServer`가 꼭 필요한가

**쓰는 곳은 한 곳입니다.** 도구 목록에 넣은 Agent는 `sm-troubleshooter-agent`뿐입니다. 자동 검증과 자동 수정 Agent는 의도적으로 뺐고, 프롬프트도 격리 서버가 `cause: environment`로 실패했을 때만 쓰라고 합니다.

**실제로는 안 쓰였습니다.** 이 엔진의 전체 로그(WSL, Windows, 11-21~11-26)를 세어 보니 `startTestServer`는 11-22에 22번 불렸고, 격리 서버가 생긴 11-23 이후에는 0번입니다. `startSandboxServer`는 200번 넘게 불렸습니다.

**격리 서버로 못 하는 구성에서만 필요합니다.** 격리 서버가 못 띄우면 환경 실패로 끝나는데, 이때 `startTestServer`만 띄웁니다.

| 격리 서버가 못 하는 것 | `startTestServer` |
|---|---|
| SQL Server, MariaDB, Tibero 등 MySQL·PostgreSQL·Oracle 밖의 DB | 원래 DB에 붙어서 띄움 |
| Gradle, 다중 모듈, Maven 플러그인 기동(`tomcat7:run`, `jetty:run`) | 플러그인 방식으로 띄움 |
| NIO 접속 라이브러리(Lettuce, Kafka, Netty 등)가 든 앱 | 격리 장치 없이 띄움 |
| 프로젝트ID가 없는 요청 | 폴더 이름 키로 띄움 |

**결론**
- 지금 시험 대상 `testApp`(MySQL, Maven WAR, Tomcat)에서는 필요 없습니다. 격리 서버로 충분합니다.
- 다만 이 제품은 고객 환경이 제각각(금융권, 폐쇄망)이라 위 구성이 나올 수 있고, 그때는 `startTestServer`가 유일한 재현 수단입니다. 그래서 지금 지우면 그 고객에서는 "BLOCKED, 사람이 확인"으로 후퇴합니다.
- 위험은 그대로입니다. 원래 DB에 붙어서 등록·삭제가 실제 데이터를 바꿀 수 있고, 지키는 장치는 프롬프트의 "기존 데이터를 건드리지 않는다"뿐입니다.

**선택지**
1. **그대로 둔다.** 11-23 이후 호출이 0번이어서 현재 영향은 없습니다.
2. **기본 끄기(권하는 쪽).** `test-server.allow-unisolated: false`를 기본값으로 두고, 격리를 지원하지 않는 고객 현장에서만 켭니다. 원래 DB에 쓰는 도구가 기본으로 열려 있는 상태가 사라집니다.
3. **지운다.** 가장 단순하지만 위 구성의 고객에서는 전문가 해결의 화면 재현이 불가능해집니다.

## 답변

## 1. 공통 뼈대 (둘 다 `TestServerTool.start()` 하나를 지납니다)

1. **자리 잡기**: 작업 루트 아래 `{프로젝트키}-server[-N]/` 폴더 하나를 잡고, 그 안의 `server.lock`에 파일 잠금을 겁니다. 격리 서버는 비어 있는 첫 자리를, `startTestServer`는 첫 자리만 씁니다.
2. **재사용 판단**: 같은 실행이 바로 앞 step에서 같은 입력으로 띄운 서버가 살아 있으면 새로 띄우지 않고 그대로 돌려줍니다.
   - 입력 경로와 개발 결과 파일의 크기·수정 시각이 모두 같아야 합니다.
   - 같은 step 안에서 다시 부르면 늘 새로 띄웁니다.
3. **남은 프로세스 정리**: `server.pid`의 프로세스를 명령줄 표시(`-Ddstone.ai.test-server=키`)로 확인한 뒤 내립니다.
4. **사본 만들기**: `applyOverlay`가 원본에 개발 결과를 얹고 삭제 목록을 반영합니다. 원본은 읽기만 합니다. 다른 원본으로 만든 사본이면 새로 만듭니다.
5. **포트와 JDK 정하기**: 빈 포트를 고르고, 프로젝트 관리의 Java 버전 → pom → 클래스 파일 순서로 JDK를 정합니다. 못 찾으면 엔진의 JDK를 씁니다.
6. **빌드와 기동**: `mvn clean package`로 만든 뒤 띄웁니다. 출력은 `server.log`로 보냅니다.
7. **접속 대기**: HTTP 응답이 올 때까지 기다리고(기본 600초), WAR는 앱 경로가 404면 앱 시작 실패로 봅니다.
8. **수명 관리**: 띄운 step이 끝나면 다음 step 하나까지만 두고, 실행이 루프를 벗어나거나 엔진이 내려가면 모두 내립니다(`StepEndListener`).

## 2. `startTestServer` — 단순 임시 서버

- **DB**: 사본 안의 설정 그대로 **원래 DB**에 붙습니다. 복제도 막는 장치도 없습니다.
- **띄우는 방식**: pom을 보고 고릅니다.
  - WAR이고 `tomcat-home`이 있으면 설치된 Tomcat + 자리 안의 전용 CATALINA_BASE
  - 아니면 `tomcat7:run`, `spring-boot:run`, `jetty:run` 플러그인
- **WAR + Tomcat 방식**: 설치된 Tomcat의 `conf`를 복사해 HTTP 포트만 바꾸고 shutdown·AJP는 끕니다. 사람이 등록한 다른 앱의 Context는 띄우지 않습니다.
- **결과**: 접속주소, 서버로그 경로, 시험계정 줄(비밀번호는 자리표시자)을 돌려줍니다.

## 3. `startSandboxServer` — 격리 서버

위 뼈대의 4번(사본) 뒤에 `TestSandbox.create()`가 끼어듭니다. 하나라도 못 만들면 원래 DB로 대신 띄우지 않고 실패합니다. 실패 원인은 `code`(개발 결과)와 `environment`(환경)로 알려 줍니다.

**① DB 격리** (MySQL 기준, 실제로 쓴 경우)
- 프로젝트 관리의 DB 구성이 지원 종류인지 확인합니다(MySQL·PostgreSQL·Oracle, 프로젝트당 한 종류).
- 원래 DB 크기를 읽기 전용으로 확인하고(`sandbox-max-db-mb` 초과면 거절), 문자셋·`sql_mode`·`lower_case_table_names`를 읽어 옵니다.
- 자리 안 `sandbox/` 폴더에 **mysqld를 따로 띄웁니다**(빈 포트, 일회용 datadir). 같은 서버에 이름만 다른 DB를 만들지 않는 이유는, DDL에 `DROP DATABASE`나 `다른DB.테이블`이 있어도 원래 서버에 닿을 길이 없게 하려는 것입니다.
- 원래 DB에서 `mysqldump`로 읽기만 해서 이 mysqld에 적재합니다(비밀번호는 환경변수로 넘김).
- 계정 4종을 만듭니다: 엔진 관리용, DDL 실행용(복제 DB에만 권한), `dbQuery` 읽기용, 앱 계정(프로젝트 관리에 있는 계정 그대로, 복제 DB에만 권한).
- DDL 파일은 문법을 먼저 검사하고(롤백 블록은 실행하지 않음) 복제본에만 반영합니다. 이미 있는 것은 건너뛰고 알립니다.

**② 네트워크 격리** (`SandboxGuard`)
- 엔진이 SOCKS 프록시처럼 동작하는 문(listener)을 엽니다. 앱 JVM에는 `JAVA_TOOL_OPTIONS=-DsocksProxyHost=127.0.0.1 -DsocksProxyPort=…`를 넣습니다.
- 앱의 새 소켓은 모두 이 문을 지납니다. 원래 DB 주소로 가는 연결은 복제본으로 돌리고, 나머지는 끊습니다. 허용 목록(`sandbox-allow-hosts`)과 앱 자기 포트만 열립니다.
- `JAVA_TOOL_OPTIONS`를 쓰는 이유는 기동 스크립트가 `JAVA_OPTS`를 덮어써도, 자식 JVM이 떠도 들어가기 때문입니다.
- 띄운 뒤 서버 로그에서 이 옵션을 JVM이 받았는지 확인하고, 없으면 내립니다.
- 빌드 JVM에는 원래 DB로 가는 연결만 복제본으로 돌리는 별도 문(`buildGuard`)을 줍니다.

**③ 산출물 검사**: 빌드한 WAR나 jar를 열어 NIO 접속 라이브러리(Lettuce, Kafka, Netty 등)가 있는지 봅니다. 프록시를 우회할 수 있어 격리를 보장하지 못하므로 있으면 띄우지 않습니다.

**④ 파일 경로**: 사본의 파일과 복제 데이터 속 원본 폴더 경로를 사본 경로로 바꿔서, 앱이 파일을 원본에 쓰지 않게 합니다.

**⑤ Agent 묶기** (`SandboxRegistry`): 띄운 step 동안 `dbQuery`는 복제본 별칭(`sandbox-<8자리>.testApp`)으로, `browser_navigate`는 시험 서버 주소로 묶습니다. 띄우기 전에는 `execution.toolPrerequisites`가 `dbQuery`와 브라우저 Tool을 막습니다(자동 검증·자동 수정 Agent).

**⑥ 내릴 때**: 서버 프로세스 트리를 내리고(정상 종료 후 10초 뒤 강제), 프록시 문을 닫고, mysqld를 끄고 `sandbox/` 폴더를 지웁니다. 사본 폴더는 남깁니다.

## 4. 한눈에 비교

| | `startTestServer` | `startSandboxServer` |
|---|---|---|
| DB | 원래 DB에 직접 | 매번 새 mysqld에 복제 |
| DDL 반영 | 안 함 | 복제본에만 |
| 외부 접속 | 제한 없음 | 소켓을 엔진 문으로 보내 허용한 곳만 |
| 파일 경로 | 원본 설정 그대로 | 사본 경로로 치환 |
| 기동 방식 | WAR+Tomcat, 또는 Maven 플러그인 | Spring Boot `java -jar`, 또는 WAR+Tomcat만 |
| 동시 실행 | 첫 자리만 | 자리마다 최대 `sandbox-max-parallel` |

한 가지 한계: 네트워크 격리는 JVM 소켓 수준이라 NIO나 네이티브 접속은 잡지 못합니다. 그래서 산출물 검사로 걸러서 못 띄우는 쪽을 택한 것입니다.

## 답변

격리 서버는 대용량 DB를 복제하지 않습니다. 상한을 넘으면 서버를 띄우지 않고 실패합니다. 아래는 소스(`SandboxMysql`, `OracleClone`, `SandboxProcess`)를 읽은 결과입니다.

## 크기 상한

- **상한 값**: 설정 `dstone.ai.tool.test-server.sandbox-max-db-mb`이고 기본은 2048MB(2GB)입니다. DB 하나마다 적용됩니다.
- **크기 계산**: MySQL은 복제를 시작하기 전에 `information_schema.TABLES`의 `DATA_LENGTH` 합계를 읽기 전용으로 확인합니다. 인덱스 크기는 이 값에 들어 있지 않습니다. 인덱스까지 포함하면 실제 디스크 사용량은 더 큽니다. Oracle은 스키마 크기를 같은 방식으로 확인합니다.
- **초과 시**: 복제를 시작하지 않고 아래 안내로 실패합니다.
  - 안내 문구: "DB가 NNNN MB라 복제하지 않습니다(`sandbox-max-db-mb`). 작은 개발 DB를 프로젝트 관리에 등록하십시오."
  - 실패 원인은 `environment`입니다. 코드를 고쳐도 소용없는 실패로 분류되어 자동 수정이 손대지 않습니다. sm-workflow는 `sandboxError`에 이유를 남기고 자동 검증을 건너뛴 채 개발 승인으로 넘어갑니다.
- **원래 DB로 대신 띄우지는 않습니다.** 크기 때문에 격리가 안 되면 검증이 안 되는 쪽을 택한 것입니다.

## 상한 안쪽에서도 드는 비용
- **전체 복제**: 부분 복제, 샘플링, 스키마만 복제하는 옵션은 없습니다. `mysqldump --single-transaction`으로 모든 테이블의 구조와 데이터를 한 번에 받아 일회용 mysqld에 적재합니다.
- **시간**: 서버를 띄울 때마다 덤프와 적재를 다시 합니다. DB가 클수록 시간이 늘어납니다. 같은 입력으로 바로 다음 step이 다시 부르면 서버를 재사용하므로 다시 복제하지 않지만, 고친 뒤 다시 띄우면 복제부터 새로 합니다.
- **타임아웃**: 외부 명령(덤프, 적재) 하나는 900초 안에 끝나야 하고, 넘기면 실패합니다. 서버 기동 대기는 별도로 600초입니다.
- **디스크**: 덤프 파일(`dump.sql`), 적재용 파일(`load.sql`), 일회용 datadir이 자리 폴더 안에 생겼다가 서버를 내리면 지워집니다. 적재가 끝나면 덤프와 적재 파일은 바로 지웁니다. 동시 실행이 N개면 N배가 필요합니다.
- **복제본 크기 확인**: 지금 `testApp`은 작은 DB라서 복제가 수십 초입니다(이번 시험에서 step29가 약 30초).

## 대용량 DB 프로젝트에서의 선택지
1. **작은 개발 DB를 프로젝트 관리에 등록**(안내 문구가 권하는 방법). 운영 DB가 아니라 소량의 대표 데이터가 든 개발 DB를 가리키게 합니다. 가장 안전합니다.
2. **상한을 올림**: 복제 시간, 디스크, 900초 타임아웃에 걸리지 않는 범위에서만 가능합니다.
3. **격리 검증을 포기**: 그 프로젝트는 자동 검증을 건너뛰고 사람이 확인합니다. 이때 `startTestServer`로 원래 DB에 붙이는 길이 열려 있었지만, 앞서 진단한 위험 때문에 기본으로 끄는 방향을 제안드렸던 것입니다.

## 답변

좋은 방향입니다. 다만 "스키마 + 소량 mock"만으로는 자동 검증이 깨지는 경우가 많아서, 테이블 크기에 따라 복제 방식을 나누는 방식을 권합니다.

## 스키마만 + mock 데이터가 부딪히는 문제

이 워크플로의 자동 검증은 화면에 로그인하고 목록을 보고 등록·삭제를 눌러 보는 것입니다. 이것이 의존하는 데이터가 있습니다.

| 필요한 데이터 | 스키마만 만들면 |
|---|---|
| 로그인 계정(`tbsy_member` 등) | 로그인 자체가 안 돼서 모든 화면 검증이 BLOCKED |
| 메뉴·권한(`tbsy_resource` 등) | 메뉴가 안 떠서 화면에 못 들어감(요청서가 메뉴 위치를 명시함) |
| 공통코드, 설정 테이블 | 콤보박스가 비고, 코드 조인이 빈 결과 |
| FK로 엮인 업무 데이터 | 목록이 비어 "기존 데이터가 보이는가" 같은 기준을 검증 못 함 |

mock 데이터를 자동 생성하는 것도 어렵습니다. 컬럼 타입만으로는 제약(FK, 유니크, 체크, 업무 규칙)을 만족하는 값을 못 만들고, 도메인 값(코드, 상태값)은 알 수 없습니다. 잘못 만들면 검증이 가짜 실패(FAIL)를 냅니다.

## 권하는 방식: 테이블별 크기 정책 (스키마는 전부, 데이터는 크기로 나눔)

1. **스키마(구조)는 항상 전체 복제**합니다(`mysqldump --no-data` 상당). 이것은 작고 정확합니다.
2. **데이터는 테이블 크기로 나눕니다.**
   - 작은 테이블(예: 행 수나 크기 기준 이하): 전체 복제. 계정, 메뉴, 공통코드가 여기에 해당합니다.
   - 큰 테이블: 앞의 N행만 복제(`mysqldump --where="1 limit N"`) 하거나 비웁니다. 로그·이력·거래 테이블이 여기에 해당합니다.
3. **프로젝트별로 덮어씁니다.** 프로젝트 관리에 "항상 전체", "구조만", "N행" 지정 칸을 둡니다. 큰 테이블인데 로그인에 꼭 필요하다면 전체로 지정합니다.
4. **FK**는 부분 복제 때 고아 행이 생기지만, 덤프가 적재 중에 FK 검사를 끄므로 적재는 됩니다. 앱이 고아 행을 만나는 경우는 드물고, 있으면 "원래 환경과 다른 점"에 적습니다.
5. **mock 데이터는 넣지 않습니다.** 검증 Agent가 화면에서 직접 등록하는 데이터를 쓰고, 소량 샘플은 실제 데이터에서 가져옵니다. mock 생성은 범용으로 만들기가 어렵고 가짜 실패를 만들 위험이 있습니다.

효과: 상한 때문에 아예 못 쓰던 대용량 DB가, 크기가 작은 핵심 테이블 위주로 복제되어 자동 검증이 가능해집니다. `sandbox-max-db-mb`는 "복제 후 예상 크기"를 기준으로 다시 검사하면 됩니다.

## 한계와 구현 범위
- **MySQL**은 `mysqldump`의 `--no-data`, `--where`, `--ignore-table`로 비교적 쉽습니다. **PostgreSQL**은 `pg_dump`에 행 제한 옵션이 없어서 테이블별 `COPY (SELECT … LIMIT N)`를 따로 만들어야 합니다. **Oracle**은 `OracleClone`의 복제 방식이 달라서 별도 작업입니다. 첫 단계는 MySQL만 하고 나머지는 이어서 하는 것이 현실적입니다.
- 테이블 크기와 행 수는 `information_schema`에서 읽어 오므로 추가 접속 권한은 필요 없습니다.
- 부분 복제는 "처음 N행"이라 대표성이 낮을 수 있습니다. 로그인 계정이 큰 테이블의 뒤쪽에 있으면 빠질 수 있어, 프로젝트 지정(전체)이 안전망입니다.

## 진행 제안
1단계로 MySQL에 크기 정책(작은 테이블 전체, 큰 테이블 N행 또는 구조만)과 프로젝트별 덮어쓰기를 구현하고, 상한 검사를 복제 후 예상 크기 기준으로 바꿉니다. 큰 테이블 임계값 기본은 행 수 10만, 큰 테이블 샘플 행은 1천을 제안합니다.

## 상한과 지금의 약점
- 동시 격리 서버는 프로젝트마다 `sandbox-max-parallel`(기본 4)개까지입니다. 자리마다 사본(약 1.1GB), 일회용 mysqld, Tomcat, Maven 빌드, 브라우저가 따로 필요해서 장비 용량으로 정해야 합니다.
- **5번째 실행이 오면** 자리가 날 때까지 `lock-wait-seconds`(기본 60초)만 기다리고, 그래도 없으면 거절됩니다. 거절되면 `sandboxError`가 남고 그 실행은 자동 검증을 건너뛴 채 개발 승인으로 넘어갑니다.
- 검증 하나가 몇 분(3~10분) 걸리니, 60초는 줄을 서기에 너무 짧습니다. 이전에 병렬 시험에서 두 번째 실행이 검증 없이 `DONE`이 된 것과 같은 모양이 상한을 넘을 때 다시 생깁니다. 그래서 기다림을 "최대 몇 분, 순서대로"로 늘리는 것이 맞습니다.
- 엔진 전체의 동시 실행은 `WorkFlowThreadPools`가 8개로 묶고(대기열 50개), LLM 호출은 provider별 동시 요청 수로 묶입니다. 검증이 몰리는 현장에서는 이 숫자들과 같이 봐야 합니다.

## 같은 서버에서 여러 엔진을 띄우는 경우
- 자리 잠금은 작업 루트의 파일 잠금이라, 같은 장비·같은 `work-root`를 쓰는 엔진끼리는 자리를 나눠 씁니다.
- 장비가 다르면 작업 루트도 따로라서 서로 영향이 없습니다.

## 제안
- 자리가 모두 찼을 때의 기다림을 길게 늘리고(예: 10분), 대기 중임을 결과에 알려 주면 줄 서는 동작이 됩니다. 기다림이 그 정도로 길어지면 그 시간에도 `Tool` 호출이 막혀 있으니, 대기 한도와 `maxToolCalls`, 단계 시간 한도와의 관계를 같이 확인해야 합니다.
- 자리 수와 장비 용량은 현장 설정(`sandbox-max-parallel`)으로 둡니다.

## 답변

네, 맞습니다. DB는 **서버를 띄울 때마다 새로 복제**하고, 내릴 때 지웁니다. 실행(개발자)마다 따로 복제하는 것이 아니라 `startSandboxServer` 호출마다 복제합니다.

## 복제되는 시점과 횟수
| 상황 | 복제 |
|---|---|
| 개발자 3명의 실행이 동시에 검증 | 3번(각자 일회용 mysqld와 복제본) |
| 같은 실행이 step29에서 띄우고 step35가 같은 입력으로 다시 부름 | 1번(서버와 DB를 그대로 재사용) |
| 자동 수정 뒤 다시 띄움 | 이전 복제본을 지우고 **새로 복제**(처음 상태로 돌아감) |
| 개발 승인 대기, 일시정지, 실행 종료 | 복제본 없음(그 실행의 서버를 모두 내리면서 같이 지움) |

이번 시험에서 한 실행이 검증을 3번 돌았을 때 mysqld와 복제가 3번 만들어졌습니다.

## 복제가 만드는 것
- 원래 DB에서 `mysqldump`로 읽기만 해서(원래 DB는 안 바뀝니다), 서버마다 따로 띄운 mysqld에 적재합니다. 서버끼리는 DB 인스턴스, 포트, 데이터 폴더가 모두 다릅니다.
- 그래서 개발자1의 시험 중 등록·삭제가 개발자2의 DB에 보이지 않습니다. 매번 같은 시작 상태에서 시작하는 것이 이 방식의 장점입니다.
- DDL은 이 일회용 복제본에만 반영됩니다. `dbQuery`는 `sandbox-<8자리>.testApp` 별칭으로 그 복제본만 봅니다.

## 비용
- **원래 DB 부하**: 동시 검증 N개면 원래 DB를 `mysqldump`로 N번 읽습니다. `--single-transaction`이라 잠금은 걸지 않지만 읽기 부하는 생깁니다. 개발 DB라면 대개 괜찮지만 큰 DB면 앞에서 말한 크기 정책이 필요합니다.
- **디스크**: 복제본 크기 × 동시 서버 수입니다.
- **시간**: 서버를 띄울 때마다 덤프와 적재 시간이 듭니다. `testApp`은 작은 DB라 약 30초였습니다.

## 줄일 수 있는 방법(아직 구현하지 않음)
- **덤프 한 번, 적재 여러 번**: 같은 프로젝트의 원래 DB 덤프를 잠깐 캐시해 두고(예: 몇 분) 여러 서버가 그 덤프에서 적재하면 원래 DB를 읽는 횟수가 줄어듭니다. 대신 덤프 이후 바뀐 원래 DB 데이터가 반영되지 않는 시차가 생깁니다.
- 앞에서 제안한 **크기 정책(스키마 전체 + 큰 테이블은 N행)**을 적용하면 덤프와 적재가 모두 가벼워집니다.

두 가지는 서로 보완되는 관계입니다. 크기 정책이 먼저 필요하고, 덤프 캐시는 동시 검증이 많은 현장에서 효과가 큽니다. 어느 쪽부터 진행할까요?

| 방법 | 원복 정확도 | 다른 개발자가 같은 DB를 쓸 때 | 필요한 것 |

| ⑤ **DB 전체 되돌리기**: Oracle Flashback Database 등 | 완전 | **다른 사람 데이터까지 되돌아감** | 현실적이지 않음 |

**제 판단**: 정확도와 안전을 같이 만족하는 것은 ①(DB 변경 이력)과 ③(앱 안 기록)입니다. ①은 DB 종류별로 따로 만들어야 하고 서버 설정(바이너리 로그)이 전제입니다. ③은 DB 종류와 무관하지만 구현이 크고 불안정합니다. ②는 다른 개발자와 DB를 같이 쓰면 남의 데이터를 망가뜨릴 수 있어 권하지 않습니다.

## 답변

제가 생각한 구조는 서버 바이너리를 복사하지 않습니다. 이미 지금도 바이너리는 공유합니다. 말씀하신 "한 서버에 웹앱만 실행별로 올리는" 방식은 제 구조와 다르고, 장단점이 있어서 비교해서 설명드립니다.

## 지금 구조 (실측)
자리 폴더 하나(1.1GB) 안을 열어 봤습니다.

| 항목 | 크기 | 내용 |
|---|---|---|
| `app/src` 등 | 약 242MB | 원본 소스 사본(개발 결과를 얹은 것) |
| `app/target` | 413MB | Maven 빌드 결과 |
| `tomcat/conf` | 240KB | 설치된 Tomcat의 설정 복사본 (포트만 변경) |
| `tomcat/webapps` | 411MB | 배포한 WAR를 풀어 놓은 앱 |
| `tomcat/logs`, `work`, `temp` | 약 3MB | 서버 로그와 임시 파일 |

- **Tomcat 바이너리(`/opt/tomcat9`, 429MB)는 복사하지 않습니다.** 모든 자리가 같은 설치본을 `CATALINA_HOME`으로 같이 쓰고, 자리마다 `CATALINA_BASE`(설정, 로그, 배포한 앱)만 따로 둡니다. 이것이 Tomcat이 원래 지원하는 "바이너리 하나, 인스턴스 여럿" 방식입니다.
- 1.1GB의 대부분은 서버가 아니라 **실행마다 달라지는 앱**입니다(소스 사본, 빌드 결과, 풀어 놓은 WAR). 어떤 구조를 택해도 실행마다 따로 있어야 하는 것들입니다.
- 인스턴스마다 JVM 프로세스가 하나씩 뜹니다(포트도 하나씩).

## 제가 말씀드린 "실행별 폴더"
`{프로젝트키}-{실행id}` 폴더에 위 항목(앱 사본, 빌드, CATALINA_BASE)만 두고 Tomcat 바이너리는 그대로 공유합니다. 실행 id를 8자리로 줄인 것은 Windows 경로 길이(260자) 때문이었습니다. Maven 산출물 경로가 깊어서 UUID 전체(36자)를 쓰면 걸릴 수 있습니다. 8자리가 아니어도 되고, 충돌을 피하려고 폴더 안에 전체 id를 적은 표지 파일을 두고 확인하면 됩니다.

## 말씀하신 구조: 프로젝트마다 Tomcat 하나, 웹앱만 실행별로
가능은 하지만 비용이 있습니다.

| 항목 | 실행별 Tomcat 인스턴스 (제 구조) | 프로젝트당 Tomcat 하나 + 웹앱만 실행별 |
|---|---|---|
| 디스크 | 앱 사본 + 빌드 + 풀어 놓은 WAR | 같음. 앱은 실행마다 달라서 줄지 않음 |
| 메모리 | JVM 인스턴스 수만큼 | JVM 하나. 절약됨(인스턴스당 300~600MB 수준) |
| 격리 | 한 실행이 멈추거나 OOM이어도 다른 실행은 무사 | **한 JVM을 공유**. 한 앱의 무한루프, OOM, `System.exit`, 스레드 누수가 모든 실행을 죽임 |
| 포트 | 실행마다 빈 포트 하나 | Tomcat은 포트를 서버 설정(`Connector`/`Service`)으로 정해서 **기동 중에 포트를 추가하는 것이 표준 기능이 아님**. 한 포트에 컨텍스트 경로(`/exec1`, `/exec2`)로 나누면 포트는 하나지만 앱이 컨텍스트 경로를 `/`로 가정하면 깨짐 |
| JVM 옵션 | 실행마다 따로(JDK 버전, 메모리, 옵션) | 모든 앱이 하나를 공유 |
| 재배포 | 실행이 끝나면 인스턴스를 내리면 끝 | 앱을 내렸다 올릴 때 클래스로더·메타스페이스 누수가 쌓여 결국 재기동 필요 |
| 로그 | 실행마다 `logs/` 분리 | 하나로 섞임(앱 자체 로그 설정으로 나눠야 함) |
| 정리 | 폴더와 프로세스를 지우면 끝 | 한 앱만 안전하게 내리고 지우는 로직 필요 |

디스크는 줄지 않고, 얻는 것은 JVM 메모리뿐입니다. 반면 격리가 약해지는 대가가 큽니다. 이 시험 서버는 개발자가 방금 만든 미완성 코드를 돌리므로, 한 앱이 다른 개발자의 실행을 죽일 수 있는 구조는 위험합니다.

## 권하는 구조
1. **Tomcat 바이너리는 프로젝트마다 하나(지금처럼 공유)**, **인스턴스는 실행마다 하나**(`CATALINA_BASE` + 빈 포트). 이것이 말씀하신 "바이너리는 하나, 실행별로 포트를 따로"의 실질적인 구현입니다. 차이는 JVM이 실행마다 하나라는 점입니다.
2. 디스크를 줄이려면 WAS와 무관하게 아래를 쓸 수 있습니다.
   - 풀어 놓은 WAR(411MB)를 복사하지 않고 `docBase`로 `app/target/{앱}`을 직접 가리킵니다. 실행마다 약 400MB가 줄어듭니다.
   - 소스 사본(242MB)은 하드링크로 만들면 바뀐 파일만 새로 쓰게 되어 줄일 수 있습니다. 다만 구현이 복잡하고 Windows에서 제약이 있어서 필요할 때만 합니다.
3. 실행 폴더는 실행이 끝났을 때(완료, 실패, 중단) 삭제하고, 승인 대기 중에는 서버만 내리고 사본은 남깁니다. 엔진이 재기동하면 남은 폴더를 정리합니다.

한 JVM 방식이 꼭 필요한 이유(메모리가 부족하다 등)가 있으시면 알려 주세요. 그렇다면 컨텍스트 경로 방식의 앱 호환 문제를 먼저 확인해 봐야 합니다. 없다면 위 권장 구조로 진행하겠습니다.

| WAR + Tomcat | 설치된 Tomcat에 전용 `CATALINA_BASE`를 만들어 띄움 |
| WAR + Tomcat 없음 | pom의 `tomcat7`/`jetty`/`spring-boot` Maven 플러그인으로 띄움(앱의 서블릿 API와 플러그인이 부딪쳐 못 뜨는 경우가 있음) |
| WildFly, WebLogic, JEUS, WebSphere 등 | **지원 안 함.** "띄울 방법을 찾지 못했습니다"로 실패. 요청서 `## 시험환경`에 반영폴더·반영명령이 있을 때만 사람이 쓰는 서버에 올림(전문가 해결 한정) |

## WAS를 늘릴 때의 방향: 띄우는 방식을 교체 가능한 단위로 분리
WAS마다 다른 것은 네 가지뿐입니다. 이것을 하나의 인터페이스로 묶고 종류별 구현을 둡니다.

| 단계 | 인터페이스가 하는 일 |
|---|---|
| 인스턴스 만들기 | 설치본은 공유하고 실행별 설정·로그·배포 폴더만 만든다 |
| 앱 올리기 | WAR를 배포 위치에 두거나 가리킨다 |
| 띄우기·접속 확인 | 포트를 정하고 프로세스를 띄운 뒤 준비됐는지 본다 |
| 내리기 | 프로세스와 자식 프로세스를 내린다 |

종류별로는 이렇게 됩니다.

| WAS | 실행별 인스턴스 방식 | 난이도 |
|---|---|---|
| Tomcat | `CATALINA_BASE` (지금 있음) | 있음 |
| Jetty | `JETTY_BASE` 폴더 + `jetty.http.port` | 쉬움. Tomcat과 개념이 같음 |
| WildFly(JBoss) | standalone 모드의 `-Djboss.server.base.dir`로 실행별 설정 폴더 + `-Djboss.socket.binding.port-offset`으로 포트 분리, `standalone/deployments`에 WAR 배포 | 중간. 관리 포트(9990)와 모듈 설정도 같이 옮겨야 함 |
| Spring Boot | 이미 지원 | 있음 |
| WebLogic, JEUS, WebSphere(상용) | 도메인/프로파일 단위. 실행마다 도메인을 복사하려면 WLST 같은 전용 스크립트와 라이선스·기동 시간(수십 초~수 분) 부담 | 어려움 |

## 상용 WAS는 어떻게 하나
상용 WAS를 실행마다 새로 띄우는 것은 라이선스와 기동 비용 때문에 현실적이지 않은 현장이 많습니다. 방법은 세 가지입니다.

1. **대체 서버로 시험**(권하는 기본값). 앱을 Tomcat이나 Spring Boot로 띄우고 결과에 "원래 환경과 다른 점"으로 적습니다. 이미 있는 장치(Skill `test-environment`)가 그 차이 때문에 생긴 실패를 `BLOCKED`로 처리하게 합니다. 단, 상용 WAS의 JNDI DataSource나 WAS 전용 설정(`weblogic.xml`, `jboss-web.xml`)에 의존하는 앱은 대체 서버에서 DB 연결부터 안 됩니다. 그 설정을 Tomcat의 `context.xml` 리소스로 옮겨 주는 변환이 필요한데, 앱마다 달라 자동화하기 어렵습니다.
2. **사람이 쓰는 시험 서버에 배포**. 이미 있는 경로(`applyOverlay` + `runShellScript`)입니다. 다만 이 서버는 여러 실행이 같이 쓰므로 실행별 독립은 아닙니다.
3. **고객이 제공한 기동 스크립트를 실행별로 호출**: 프로젝트마다 "인스턴스 만들기·배포·기동·종료" 명령 템플릿을 설정으로 받는 방식입니다. 엔진은 WAS를 몰라도 되고, 실행 id와 포트를 변수로 넘깁니다. 범용성은 가장 높고 구현량은 가장 적지만, 설정은 현장 몫입니다.

## 제안
- 인터페이스(위의 네 단계)를 먼저 만들고, 구현은 **Tomcat(현재 것을 옮김), Spring Boot, Jetty, WildFly** 순서로 시작합니다.
- 상용 WAS용으로는 3번(고객 제공 명령 템플릿)을 범용 구현으로 하나 두고, 1번(대체 서버 + 차이 명시)을 안내합니다.
- 프로젝트 관리에 "WAS 종류"를 추가합니다(없으면 pom으로 추정하는 지금 방식을 유지).

이 제품을 도입할 고객사의 WAS 분포를 아시면 알려 주세요. 구현 우선순위가 달라집니다. 예를 들어 금융권에서 WebLogic이나 JEUS가 대부분이라면 3번을 먼저 만들어야 합니다.

## 앱이 WAS에 의존하는 것들과 대체 가능성
| 의존 | Tomcat에서 대체 | 자동화 |
|---|---|---|
| JNDI DataSource(`java:comp/env/jdbc/xxx`) | `context.xml`의 `Resource` | **쉬움** |
| 컨텍스트 루트(`weblogic.xml`, `jboss-web.xml`, `jeus-web-dd.xml`의 값) | 컨텍스트 경로 | 쉬움 |
| 도메인의 공용 lib(JDBC 드라이버 등), JVM 시스템 속성 | Tomcat `lib`와 기동 옵션 | 쉬움 |
| 서블릿 필터·리스너 등 표준 웹 설정 | 그대로 동작 | 해당 없음 |
| JTA 트랜잭션(여러 DB, XA) | Atomikos, Narayana 같은 라이브러리를 앱에 추가 | 어려움(앱 설정 변경 필요) |
| JMS, MDB, EJB | 별도 브로커·EJB 컨테이너 필요 | **사실상 불가** |
| WAS 전용 API(`weblogic.*`, `jeus.*` 클래스, 시작 클래스, Work Manager) | 대응 없음 | 불가 |
| WAS 보안 영역(SSO, 사용자 저장소) | 대응 설정 필요 | 불가 |
| 클래스로더 우선순위 차이 | 앱별 설정 | 앱마다 다름 |

## 현실적인 접근: 앱은 그대로 두고 환경을 채운다
- **JNDI는 벤더 설정을 읽지 않고 프로젝트 관리의 DB 등록 정보로 채웁니다.** WebLogic의 `config.xml`이나 JEUS의 `domain.xml`을 파싱하는 것은 벤더마다 따로 만들어야 합니다. 대신 소스에서 JNDI 이름(`jdbc/xxx`)을 찾아서 프로젝트 DB와 매핑하면 벤더와 무관해집니다. 매핑은 프로젝트 관리에 "JNDI 이름 → DB 별칭"으로 한 번 적고, 엔진은 그 값으로 Tomcat `context.xml`을 생성합니다.
- 컨텍스트 루트와 공용 lib는 프로젝트 관리의 설정(추가 lib 폴더, 시스템 속성)으로 받습니다.
- 앱 코드나 `WEB-INF` 파일은 건드리지 않습니다. 시험 서버 사본에 환경만 다르게 줍니다.
- 이런 대체는 이미 있는 "원래 환경과 다른 점"으로 결과에 적고, `test-environment` Skill이 그 차이 때문에 생긴 실패를 `BLOCKED`로 처리하게 합니다.

## 한계 (분명히 말씀드려야 하는 부분)
- **Tomcat에서 통과해도 그 WAS에서 통과한다는 보증은 아닙니다.** 업무 로직과 화면은 검증되지만 WAS 고유 동작(클래스로더, 트랜잭션 전파, 보안)은 놓칩니다. 이것은 격리 서버가 DB를 흉내 낼 때와 같은 한계입니다.
- JMS, EJB, JTA, WAS 전용 API를 쓰는 앱은 자동 검증 대상에서 빼고 `BLOCKED`로 사람에게 넘기는 것이 맞습니다. 이런 앱이 고객 앱의 어느 비율인지 모릅니다. 금융권 레거시에는 흔합니다.
- 그래서 앱 구조를 바꾸는 "변환기"는 만들기 어렵고 위험합니다. 환경을 채우는 어댑터는 범위가 분명하고 안전합니다.

## 참고: 시험 대상 앱은 이미 해당 없음
`testApp`은 JNDI, WebLogic, JBoss 관련 참조가 하나도 없고, DataSource를 Spring 설정(`context-datasource.xml`)과 `globals.xml`의 JDBC URL로 직접 정의합니다. 즉 WAS가 제공하는 것이 없어 Tomcat에서 바로 뜹니다. 상용 WAS 앱도 이런 Spring 직접 설정 방식이면 변환 없이 Tomcat에서 뜰 가능성이 높습니다. 실제로 필요한 것은 JNDI 의존 여부를 먼저 감지하는 일입니다.

## 제안
1. **의존 감지**: 소스를 훑어 JNDI 사용, WAS 전용 클래스·설명자, EJB/JMS/JTA 사용을 찾아 "Tomcat으로 시험 가능한가"를 판정합니다. dstone-knowledge가 이미 분석한 소스 관계(`analysis_*`)를 쓰면 새로 파싱할 필요가 적습니다.
2. **JNDI 어댑터**: JNDI DataSource를 프로젝트 DB로 채우는 것부터 구현합니다. 가장 흔하고 효과가 큰 항목입니다.
3. 가능 범위 밖인 앱은 명확한 이유와 함께 `BLOCKED`로 사람에게 넘깁니다.

이 방향이면 앞서 말씀드린 "WAS 종류별 구현"은 Tomcat과 Spring Boot 위주로 줄이고, 상용 WAS 확장은 어댑터로 처리할 수 있습니다. 이 방향으로 정리해도 될까요?
