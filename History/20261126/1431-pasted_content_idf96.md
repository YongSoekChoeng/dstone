A. 질문
    dstone-ai-engine 의 테스트 방식에 대해서 상의하고자 해.
    너무 복잡하고 무거운 테스트 방식은 효율성 측면에서 바람직하지 않은 것 같아.
    서버테스트방식을 이런 방식으로 가능한가?

    <WAS관련>
    1. 소스내의 사용 WAS관련설정을 기준WAS인 TOMCAT 에서 돌아갈 수 있게 전환.(EJB 불가)
    2. TOMCAT 의 overlay 기능 이용.(실행마다 overlay 와 CATALINA_BASE 별도 생성)
    3. java는 바뀐 것만 컴파일하고, 시그니처나 상수가 바뀌면 역참조까지 컴파일.
    4. 반영은 즉시반영과 context reload로 나누고, JVM 재시작은 실행id당 한번만 진행.

    <DB관련>
    1. 고객사에서 개발DB는 제공하는 것으로 전제.
    2. DB가 제공되지 않을 경우는 DB관련 실측은 소스에서 논리적으로 해결.
    3. 개발DB가 제공되었을 때 테스트를 통해서 진행 된 변경정보는 테스트가 끝나면 원복.


---------------------------------------------------------------------------------------------------
B. 답변
  WAS 관련

  1. Tomcat 전환: 가능합니다. 다만 두 가지를 정해야 합니다.
  - 전환 결과는 원본 소스가 아니라 실행별 CATALINA_BASE(context.xml)나 overlay에만 둡니다. 원본 소스의 WAS 설정을 고치면, 그 변경이 고객사에 납품할
    변경분에 섞여 들어갑니다.
  - Tomcat 버전은 프로젝트마다 정해야 합니다. Tomcat 10 이상은 jakarta.*라서 javax.* 레거시 앱은 돌지 않습니다. 앱의 Servlet 버전과 JDK 버전에 따라
    Tomcat 9(또는 8.5)를 고르고, 프로젝트 설정에 넣어 둡니다.
  - 전환 대상은 대부분 JNDI 이름(WebLogic·JEUS는 java:comp/env 없이 쓰는 경우가 많음), context root, 벤더 디스크립터(weblogic.xml,
    jeus-web-dd.xml)입니다. EJB 외에 weblogic.*·jeus.* 클래스를 직접 import한 코드도 전환할 수 없습니다. 이런 앱은 시작 전에 "서버 테스트 불가"로
    판정해 두는 것이 좋습니다.

  2. overlay + 실행별 CATALINA_BASE: 그대로 가능합니다. 남는 문제는 하나입니다. overlay로는 파일 삭제를 표현할 수 없습니다. 삭제가 드물다면 "삭제가
  있는 실행은 서버 테스트에서 그 파일이 남아 있다고 보고 진행하고, 판정할 때 알린다" 정도로 단순하게 처리해도 됩니다.

  3. 부분 컴파일: 더 단순하게 바꾸길 권합니다. 역참조를 찾아 컴파일하려면 의존 분석이 필요해서 무거워집니다. 대신 다음처럼 합니다.
  - 평소에는 바뀐 파일만 컴파일합니다.
  - public 시그니처나 상수가 바뀌었으면 소스 전체를 컴파일합니다. 대부분의 앱은 전체 javac도 수십 초 안에 끝나고, 판단 로직이 "바뀌었나/아닌가"
    하나로 줄어듭니다.

  4. 즉시 반영 / context reload / JVM 재시작 1회: 가능합니다. 두 가지만 알아 두면 됩니다.
  - reload를 여러 번 하면 레거시 앱에서 메모리 누수(PermGen/Metaspace)가 쌓일 수 있습니다. "reload N회 넘으면 JVM 재시작" 같은 안전장치 하나는 두는
    게 좋습니다.
  - reload하면 세션이 사라지므로 헤드리스 테스트는 매 라운드 로그인부터 다시 해야 합니다.

  DB 관련

  1. 개발 DB 제공 전제: 좋습니다.

  2. DB가 없으면 논리 검증: 가능합니다. 다만 범위를 분명히 해야 합니다.
  - 레거시 앱은 대개 DB가 없으면 기동 자체가 실패합니다(데이터소스 초기화 실패). 그래서 "DB 없음"은 사실상 서버 테스트 전체를 생략하고 정적·논리
    검증만 한다는 뜻이 됩니다.
  - 논리 검증 결과는 PASS가 아니라 "논리 검증만 함"으로 따로 표시해야, 실측한 결과와 섞이지 않습니다.

  3. 테스트 후 원복: 가장 가벼운 방법은 "커밋하지 않는 연결"입니다.

  대역 WAS의 데이터소스는 엔진이 정의하므로, 이렇게 만들 수 있습니다.
  - 실행 ID 하나에 DB 연결 하나만 열고 autocommit은 끕니다.
  - 앱이 연결을 요청하면 항상 그 연결을 돌려주고, commit()은 무시하고 close()도 실제로 닫지 않습니다.
  - 테스트가 끝나면 rollback() 한 번으로 원복합니다.

  이 방식의 장점은 다음과 같습니다.
  - 변경 기록도, 되돌리기 SQL도, 벤더별 코드도 필요 없습니다.
  - 다른 실행이나 고객사 개발자에게 테스트 데이터가 보이지 않습니다. 커밋되지 않았기 때문입니다.
  - 한 연결을 같이 쓰므로, 앱 안에서는 방금 저장한 데이터가 바로 조회됩니다.

  다만 한계가 셋 있습니다.

  ┌──────────────────────────────────────────────┬──────────────────────────────────────────────────────────────────────────────────────────────┐
  │                     한계                     │                                             대응                                             │
  ├──────────────────────────────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────┤
  │ DDL은 되돌릴 수 없음 (Oracle·MySQL은 DDL이   │ DDL이 있는 요청은 엔진이 실행한 DDL을 기록해 두고, 끝나면 역 DDL(DROP TABLE, DROP COLUMN)을  │
  │ 자동 커밋, PostgreSQL만 롤백 가능)           │ 실행. 컬럼 타입 변경·삭제처럼 되돌릴 수 없는 DDL은 사람 승인을 받거나 서버 테스트에서 제외   │
  ├──────────────────────────────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 잡은 행 잠금이 테스트 내내 유지됨: 고객      │ 실행당 테스트 시간 상한을 두고, 넘으면 강제 rollback                                         │
  │ 개발자가 같은 행을 고치면 기다리게 됨        │                                                                                              │
  ├──────────────────────────────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 요청이 동시에 오면 한 연결을 같이 씀: 화면이 │ 프록시에서 요청을 직렬화(연결 사용을 한 번에 하나로). 테스트 속도에는 거의 영향 없음         │
  │  Ajax를 병렬로 부르면 충돌 가능              │                                                                                              │
  └──────────────────────────────────────────────┴──────────────────────────────────────────────────────────────────────────────────────────────┘

  시퀀스 값은 rollback해도 되돌아가지 않지만 문제는 없습니다. 번호가 조금 건너뛸 뿐입니다.

  ---

  정리

  제안하신 방식으로 충분히 갈 수 있고, 보완할 점은 다섯 가지입니다.
  1. 전환 결과는 원본 소스가 아니라 실행별 설정에만 둡니다. 
  2. Tomcat 버전은 프로젝트마다 정합니다(javax/jakarta).
  3. 역참조 컴파일 대신 "시그니처가 바뀌면 전체 컴파일"로 단순화합니다.
  4. DB 원복은 "커밋하지 않는 단일 연결 + 종료 시 rollback"으로 하고, DDL만 역 DDL로 따로 처리합니다.
  5. DB가 없는 경우는 서버 테스트를 생략하고, 결과를 "논리 검증만 함"으로 구분합니다.

  이 방향이 괜찮으시면, 다음에는 현재 구현(startSandboxServer, 시험 서버 인계 등)과 비교해 무엇을 남기고 무엇을 바꿀지 정리해 드리겠습니다.

## 검토 결과

다른 세션의 답은 지금 구현을 보지 않고 낸 설계로 보입니다. 제안의 상당수는 이미 있고, **DB 원복 방식(커밋하지 않는 단일 연결)은 채택하지 않기를 권합니다.**

### 시간이 드는 곳

오늘 testApp 격리 서버를 한 번 띄운 기록입니다. 1회 측정이고, 구간은 로그와 파일 시각으로 추정했습니다.

| 구간 | 시간 |
|---|---|
| DB 복제(경로 치환 포함) | 약 20초 |
| `mvn clean package` | 16초 |
| JVM 기동 | 약 1초 |
| WAR 배포(그중 Spring 초기화 4초) | 11초 |
| 접속 확인 등 | 약 7초 |
| **합계** | **약 55초** |

바로 뒤의 검증 Agent는 약 3분 30초, LLM 호출 122회를 썼습니다. 서버 기동을 줄여도 전체 시간은 크게 줄지 않습니다.

### 항목별 판단

| 제안 | 지금 상태 | 판단 |
|---|---|---|
| Tomcat 기준 전환 | WAR는 설치된 Tomcat 한 개, Boot는 `java -jar` | **보완 채택.** JNDI 리소스 생성과 javax/jakarta별 Tomcat 선택이 없습니다 |
| overlay + 실행별 CATALINA_BASE | 프로젝트별 사본 + 전용 CATALINA_BASE, 한 번에 한 실행 | **보류** |
| 부분 컴파일 | `compileJava`가 바뀐 파일과 그것을 쓰는 파일을 컴파일 | **이미 있음.** "시그니처가 바뀌면 전체 컴파일"은 필요 없습니다 |
| 즉시 반영 | 없음. 고치면 처음부터 다시 띄움 | **채택** |
| context reload, JVM 1회 | 없음 | **비채택.** 아끼는 것이 JVM 기동 1~2초인데 누수와 상태 관리가 따라옵니다 |
| 개발 DB 직접 사용 + 원복 | 일회용 복제본, 원래 DB는 읽기만 | **비채택** |
| DB가 없으면 논리 검증 | `BLOCKED`와 이유를 달고 개발 승인으로 | **이미 있음** |

overlay를 보류하는 이유는 격리입니다. 지금은 사본 안의 원본 폴더 경로를 사본 경로로 바꾸는데, 원본을 docBase로 겹쳐 쓰면 앱이 원본 폴더에 파일을 쓸 수 있습니다.

### 단일 연결 rollback을 반대하는 이유

- **검증이 안 됩니다.** 검증 Agent의 `dbQuery`는 다른 연결이라 커밋하지 않은 데이터를 보지 못합니다.
- **전제가 맞지 않습니다.** testApp은 데이터소스를 앱의 Spring XML(`BasicDataSource`)에서 만듭니다. 엔진이 정하려면 앱 설정을 바꾸거나 JDBC를 가로채야 합니다.
- **결함을 가립니다.** `commit()`을 무시하면 트랜잭션 경계 오류가 PASS로 나옵니다. 앱의 `rollback()`은 그때까지의 시험 데이터를 모두 지웁니다.
- **원복이 보장되지 않습니다.** MySQL과 Oracle은 DDL을 실행하면 그 연결의 DML까지 커밋합니다. 프로시저 안의 COMMIT이나 비트랜잭션 테이블도 되돌릴 수 없고, 역 DDL은 도중에 실패할 수 있습니다.
- **고객 DB에 영향을 줍니다.** 시험하는 동안 행 잠금이 유지됩니다.

고객이 개발 DB를 준다는 전제는 지금 방식으로도 충족됩니다. 복제 원본으로 읽기만 하므로 원복할 것이 없습니다. "격리를 보장 못 하면 원래 DB로 대신하지 않는다"는 저장소 규칙과도 맞습니다. 다만 복제하려면 설치 폴더(Oracle은 시험 전용 서버)가 필요하고, DB 크기는 기본 2GB까지입니다.

## 계획

1. **구간별 시간 기록.** 복제, 빌드, 기동 시간을 로그와 결과에 남깁니다. 큰 앱에서는 비중이 다를 수 있어 이후 판단의 근거로 씁니다.
2. **다시 띄우는 비용 줄이기.**
   - DB 복제본은 실행이 루프를 벗어날 때까지 유지하고, DDL이 바뀌면 새로 만듭니다. 앞 회차의 데이터가 남으므로 초기화 수단은 둡니다.
   - WAR를 풀어서 배포하고, JSP·정적 파일만 바뀌었으면 떠 있는 서버에 복사합니다.
   - Java·XML이 바뀌었으면 `compileJava` 결과를 반영하고 JVM을 다시 띄웁니다. 첫 기동은 지금처럼 전체 빌드합니다.
   - 예상 효과는 두 번째 회차부터 55초가 20초 안팎, JSP만 고치면 거의 0초입니다. 아직 재 보지 않은 추정입니다.
3. **띄울 수 있는 앱 늘리기.** 프로젝트별 Tomcat 선택, 프로젝트 관리의 DB로 JNDI 리소스 생성, `weblogic.*`·`jeus.*` 사용 앱의 사전 판정을 넣습니다.

판매할 제품이라면 **3번의 가치가 2번보다 크다고 봅니다.** 2번은 실행당 1~2분을 줄이는 정도이고, 3번은 시험하지 못하던 앱을 시험하게 합니다. 순서는 1 → 3 → 2를 권합니다.

아직 아무것도 고치지 않았습니다. 두 가지만 정해 주세요.

- 이 순서로 진행할까요?
- 복제할 수 없는 고객 환경(Tibero, 대용량 DB 등)이 실제로 예상되나요? 그렇다면 단일 연결 방식보다 "스키마 전체 + 데이터 일부 복제"나 DB 종류 추가를 먼저 검토하겠습니다.

# humanizer: 한국어 AI 작문 패턴 감지 및 교정기

## 소개

당신은 AI가 생성한 텍스트의 특징적인 패턴을 감지하고 교정하는 한국어 글쓰기 분석 전문가입니다. 당신의 전문성은 과학적 언어학 연구, 특히 KatFishNet 논문(ArXiv 2503.00032v4)에 기반하고 있으며, 이 논문은 인간이 작성한 텍스트와 LLM이 생성한 한국어 텍스트 사이의 측정 가능한 차이를 식별했습니다.

**중요한 컨텍스트**:
- 이 스킬은 **한국어 텍스트에만** 집중하며, 영어 번역이나 다른 언어는 다루지 않습니다
- 검출 패턴은 높은 정확도(쉼표 패턴: 94.88% AUC, 품사 다양성: 82.99% AUC, 띄어쓰기: 79.51% AUC)를 가진 **실증적 언어학 분석**에 기반합니다
- 당신의 목표는 원래의 의미와 의도를 보존하면서 텍스트를 **자연스럽게 인간이 작성한 것처럼** 만드는 것입니다
- 우선순위에 따라 구성된 6개 카테고리의 40가지 고유 패턴을 분석하며, 각 패턴은 S1/S2/S3 심각도로 분류됩니다

## 작업 설명

실행될 때 다음을 수행합니다:

1. **한국어 텍스트 읽기** - 사용자가 제공한 텍스트(인자, 대화 컨텍스트, 또는 파일)
2. **텍스트 분석** - 아래에 설명된 40가지 검출 패턴에 대해 분석
3. **AI 작문 마커 식별** - 각 발견 사항에 대한 과학적 근거와 함께
4. **텍스트 재작성** - 자연스럽고 인간이 작성한 것처럼 들리도록
5. **수정된 버전 제시** - 주요 변경 사항의 요약과 함께(선택적)

**프로세스 가이드라인**:
- 항상 원래의 의미와 사실적 내용을 보존하세요
- 적절한 격식 수준(격식체 vs 반말)을 유지하세요
- 완벽함보다 자연스러움에 집중하세요
- 중요한 변경 사항에 대한 근거를 설명하세요
- 텍스트가 AI 마커를 거의 보이지 않으면, 이미 자연스럽다고 인정하세요

## 한국어 AI 작문 특징

LLM이 생성한 한국어 텍스트는 인간의 글쓰기와 측정 가능하게 다른 고유한 언어적 패턴을 보입니다:

- **문장부호**: 과도한 쉼표 사용(61% vs 인간 26%), 영어식 쉼표 배치
- **띄어쓰기**: 의존명사 띄어쓰기의 경직된 일관성(SD=0.02 vs 인간의 변동성)
- **어휘 다양성**: 낮은 품사 다양성, 명사 과다 사용, 동사/형용사 빈곤
- **어휘**: 일반적 서술어 과다 사용(중요하다, 핵심적, 효과적, 지속가능한, 혁신적)
- **구조**: 단조로운 문장 리듬, 3박자 리스트, 과도한 접속사

이러한 패턴은 LLM 학습 데이터 편향과 확률적 텍스트 생성에서 나타나며, 한국어 원어민 독자에게 부자연스럽게 느껴질 수 있습니다.

## 검출 패턴 (총 40가지)

### 패턴 분류 체계

모든 패턴은 검증 수준과 심각도에 따라 메타데이터를 포함합니다.

**검증 수준**:
- **✅ 과학적**: KatFishNet 논문(ArXiv 2503.00032v4, 2025) 등 외부 문헌으로 검증된 패턴 — 검증 필드에 인라인 인용 (예: `검증: ✅ 과학적 (KatFishNet, 94.88% AUC)`)
- **📊 경험적**: 실무 관찰을 기반으로 한 커뮤니티 기여 패턴

**심각도(severity)**:
- **S1 (Critical)**: 한 번만 나와도 AI 신호로 결정적. 무조건 수정 권장.
- **S2 (Strong)**: 1~2회 허용, 3회+ 반복 시 AI 신호. 빈도 기반 판정.
- **S3 (Weak)**: 단독으로는 약한 신호이나 다른 패턴과 중첩될 때 결정적.

**자연도 등급(Naturalness Grade)** — v1.6.0 신설:

윤문 후 텍스트의 자연스러움을 한 글자로 요약. 출력 형식의 "자연도 등급" 라인에 표시.

- **A**: S1 0건 + S2 ≤ 2 — 자연스러움 거의 완벽 (인간이 작성한 것처럼 읽힘)
- **B**: S1 1~2건 또는 S2 3~5건 — 자연스럽지만 사소한 AI 흔적
- **C**: S1 3+건 또는 S2 6+건 — AI 흔적 명확, 추가 윤문 권장
- **D**: 다중 카테고리 위반 (S1 5+건 + S2 8+건) 또는 변경률 가드 트리거 발생

자연도 등급은 윤문 **후** 텍스트에 적용 — 윤문 결과의 품질을 한 줄로 평가. 사용자가 결과를 신뢰할 수 있는지 빠르게 판단하도록 돕습니다.

각 패턴에는 다음 3필드 메타데이터가 포함됩니다:
- **검증**: 검증 수준 (✅ 과학적 / 📊 경험적), 외부 문헌은 인라인 인용
- **심각도**: S1 / S2 / S3 + 정의
- **버전**: 패턴이 추가된 스킬 버전

### 빠른 참조

**카테고리별 우선순위와 대표 패턴**:

1. **문장부호** (7가지, 최고: 94.88% AUC) - 쉼표 과다, 영어식 배치, 연결어미 뒤 쉼표, 콜론 과다
2. **띄어쓰기** (3가지, 높음: 79.51% AUC) - 경직된 의존명사, 보조용언, 숫자 띄어쓰기
3. **품사 다양성** (3가지, 높음: 82.99% AUC) - 명사 과다, 동사/형용사 빈곤
4. **어휘** (10가지, 중간) - AI 유행어, 불필요한 한자어, 영어 직역, 복수형 과다, 대명사 과다, 지시관형사 과다, 주어 생략 미흡, AI 결말 표현, hype 어휘 군집, ~적 N 추상 체인
5. **구조** (4가지, 중간) - 문장 리듬, 3박자, 접속사, 경어체
6. **번역투** (13가지, 높음: 경험적) - 조사 번역투(에 대해/통해/있어서), 동사 잉여(가지고 있다), 피동 남용(되어진다/에 의해), 가능 표현 남발(할 수 있다), 미래 단정(~것이다 남발)

전체 40가지 패턴 목록과 상세 내용은 각 카테고리 참조 문서 참조.

## 작업 흐름

### 1단계: 텍스트 받기

- 사용자가 인자, 대화, 또는 파일 경로를 통해 한국어 텍스트를 제공합니다
- 파일 경로가 주어지면 Read 도구를 사용하여 내용을 로드합니다
- 텍스트가 대화 컨텍스트에 있으면 추출합니다

### 2단계: 모든 패턴에 대해 분석

다음을 체계적으로 확인합니다:
- **문장부호 패턴 (1-7)**: 쉼표 개수, 위치 확인, 불필요한 사용 식별, 영어식 콜론 사용 확인
- **띄어쓰기 패턴 (8-10)**: 의존명사 띄어쓰기 일관성, 보조용언 띄어쓰기, 숫자 띄어쓰기 확인
- **품사 패턴 (11-13)**: 명사/동사/형용사 비율 추정, 명사화 구문 식별
- **어휘 패턴 (14-20, 37-39)**: AI 유행어, 한자어 과다 사용, 영어 직역, 복수형 '-들' 과다 사용, 대명사 과다, 지시관형사 과다, 주어 생략 미흡, AI 결말 관용구·결말 공식·결말 단언, hype 어휘 군집, ~적 N 추상 체인 확인
- **구조 패턴 (21-24)**: 문장 길이 변동, 목록 패턴, 접속사, 경어체 균일성 확인
- **번역투 패턴 (25-36, 40)**: 조사 번역투(에 대해/통해/있어서), 동사 잉여(가지고 있다), 피동 남용(되어진다/에 의해), 가능 표현 남발(할 수 있다), 미래 단정(~것이다 남발) 확인

감지한 패턴에 필요한 **상세 참조 파일을 로드**하세요.

### 3단계: 발견 사항 식별

감지된 각 패턴에 대해:

- 이 패턴이 왜 AI 작문을 나타내는지 설명하세요

### 4단계: 텍스트 재작성

- 원래의 의미와 사실적 내용을 보존하세요
- 적절한 격식 수준을 유지하세요
- 감지된 모든 패턴에 대한 교정을 적용하세요
- 자연스러움과 인간다운 흐름에 집중하세요
- 한국어 원어민이 작성한 것처럼 들리게 만드세요

### 4.5단계: 의미 보존 자체검증 (필수)

자연스러운 버전을 출력하기 전에 다음 6항을 자체 점검합니다. **위반 사항이 발견되면 해당 부분을 수정한 뒤 재점검합니다.**

- [ ] **수치·날짜·고유명사**: 원본의 숫자, 날짜, 인명, 기관명, 제품명이 모두 보존되었는가?
- [ ] **인과관계 방향**: "X 때문에 Y" → "Y 때문에 X"로 뒤바뀌지 않았는가?
- [ ] **부정 표현**: "있다/없다", "가능/불가능", "찬성/반대"가 반전되지 않았는가?
- [ ] **직접 인용**: 큰따옴표 안 직접 인용은 그대로인가?
- [ ] **핵심 주장·결론**: 원본의 메시지·결론이 변경되지 않았는가?
- [ ] **격식 수준**: 원본의 격식체/반말이 일관되게 유지되었는가?

위반 사항이 없으면 출력 형식의 "주요 변경 사항 요약" 끝에 "✓ 의미 보존 검증: 6항 모두 통과"를 명시합니다. 위반이 있었다면 수정 사항을 함께 기록합니다.

## 중요 사항

### 의미 보존
- 사실적 내용이나 핵심 메시지를 절대 변경하지 마세요
- 모든 주요 정보를 그대로 유지하세요
- 작성자의 의도된 톤과 목적을 유지하세요

### 변경률 가드 (Over-rewriting Guard)

자연스러운 버전을 작성한 후 **변경률**을 자체 추정해 과도한 교정을 방지하세요.

**변경률 계산**:
- 원본과 자연스러운 버전을 어절 단위로 비교
- 변경된 어절 / 전체 어절 비율 (대략적, 0~100%)
- 단순 띄어쓰기·문장부호 변경은 제외하고 의미 단위 변경만 카운트

**임계값**:
- **<30% (정상)**: 그대로 출력
- **30~50% (경고)**: 출력 끝에 "변경률 N%로 다소 큼. 의미 보존 재확인 권장" 한 줄 추가
- **>50% (중단)**: 출력하지 말고 사용자에게 확인 요청
  - 메시지: "변경률이 N%로 과도합니다. 원본 의미가 변경됐을 가능성이 있습니다. 더 보수적으로 재작성해드릴까요?"
  - 사용자 동의 시 보수적으로 재작성 후 30% 이내로 다시 시도

**근거**: 과도한 교정은 원본의 의미·뉘앙스·작성자 톤을 잃을 위험이 있음. 정량 임계로 자체 검증해 의미 보존 원칙을 강화.

### 격식 유지
- 원래의 격식 수준(격식체 vs 반말)을 존중하세요
- 텍스트가 격식체(비즈니스, 학술)라면 격식체를 유지하되 자연스럽게 하세요
- 텍스트가 반말(블로그, 소셜 미디어)이라면 더 대화적으로 만드세요
- 리듬을 위해 같은 격식 범위 내에서 어투를 다양화할 수 있습니다

### 자연스러움 집중
- 목표는 인간이 작성한 것처럼 들리게 하는 것이지, 완벽하게 만드는 것이 아닙니다
- 자연스러운 한국어 글쓰기는 약간의 불규칙성과 개인적 스타일을 가지고 있습니다
- 작성자의 목소리를 바꿀 정도로 과도하게 교정하지 마세요

### 근거 설명
- 주요 변경 사항에 대해서는 간단히 이유를 설명하세요
- 40가지 검출 기준의 특정 패턴을 참조하세요
- 사용자가 무엇이 텍스트를 AI 생성처럼 vs 인간처럼 들리게 하는지 이해하도록 도와주세요

### 문화적 감수성
- 한국 문화적 맥락과 기대를 인식하세요
- 한국어 독자는 직접성과 효율성을 중시합니다
- 원래의 톤과 일치하지 않는 한 지나치게 화려하거나 극적인 언어를 피하세요
- 영어와 다른 한국어 글쓰기 관습을 존중하세요

### 과학적 근거
- 당신의 교정은 실증적 언어학 연구에 기반합니다

## 자연스러운 버전

### 검토 결과

다른 세션의 답은 지금 구현을 보지 않고 설계한 것 같습니다. 제안 중 상당수는 이미 구현돼 있습니다. 다만 커밋하지 않는 단일 연결로 DB를 되돌리는 방식은 쓰지 않는 편이 좋겠습니다.

### 서버를 띄울 때 걸리는 시간

오늘 testApp 격리 서버를 한 번 띄운 기록입니다. 한 번만 잰 값이고, 구간은 로그와 파일 시각으로 추정했습니다.

| 구간 | 시간 |
|---|---|
| DB 복제(경로 치환 포함) | 약 20초 |
| `mvn clean package` | 16초 |
| JVM 기동 | 약 1초 |
| WAR 배포(그중 Spring 초기화 4초) | 11초 |
| 접속 확인 등 | 약 7초 |
| 합계 | 약 55초 |

이어서 실행한 검증 Agent는 약 3분 30초 동안 LLM을 122번 호출했습니다. 서버 기동을 줄여도 전체 시간은 크게 달라지지 않습니다.

### 항목별 판단

| 제안 | 지금 상태 | 판단 |
|---|---|---|
| Tomcat 기준 전환 | WAR는 설치된 Tomcat 하나에 올리고, Boot는 `java -jar`로 실행 | 보완해서 채택. JNDI 리소스 생성과 javax/jakarta에 맞는 Tomcat 선택이 빠져 있음 |
| overlay + 실행별 CATALINA_BASE | 프로젝트별 사본과 전용 CATALINA_BASE를 쓰고, 한 번에 한 실행만 허용 | 보류 |
| 부분 컴파일 | `compileJava`가 바뀐 파일과 그 파일을 쓰는 파일을 컴파일 | 이미 있음. 시그니처가 바뀌었다고 전체를 컴파일할 필요는 없음 |
| 즉시 반영 | 없음. 고치면 처음부터 다시 띄움 | 채택 |
| context reload, JVM 1회 기동 | 없음 | 채택하지 않음. 아끼는 시간은 JVM 기동 1~2초인데 메모리 누수와 상태 관리 부담이 생김 |
| 개발 DB를 직접 쓰고 원복 | 일회용 복제본을 쓰고 원래 DB는 읽기만 함 | 채택하지 않음 |
| DB가 없으면 논리 검증 | 이유와 함께 `BLOCKED`로 표시하고 개발 승인으로 넘김 | 이미 있음 |

overlay는 격리 때문에 보류합니다. 지금은 사본 안에 적힌 원본 폴더 경로를 사본 경로로 바꿉니다. 원본을 docBase로 두고 겹쳐 쓰면 앱이 원본 폴더에 파일을 쓸 수 있습니다.

### 단일 연결 rollback을 쓰지 않으려는 이유

- 검증 Agent의 `dbQuery`는 다른 연결을 쓰기 때문에 커밋하지 않은 데이터를 볼 수 없습니다.
- testApp은 데이터소스를 앱의 Spring XML(`BasicDataSource`)에서 만듭니다. 이를 엔진이 정하려면 앱 설정을 바꾸거나 JDBC를 가로채야 합니다.
- `commit()`을 무시하면 트랜잭션 경계가 잘못된 코드도 PASS가 됩니다. 반대로 앱이 `rollback()`을 부르면 그때까지 쌓은 시험 데이터가 모두 사라집니다.
- 원복을 장담할 수 없습니다. MySQL과 Oracle은 DDL을 실행하면 그 연결의 DML까지 커밋합니다. 프로시저 안에서 COMMIT한 것과 트랜잭션이 없는 테이블은 되돌릴 수 없고, 역 DDL도 도중에 실패할 수 있습니다.
- 시험하는 동안 고객 DB에 행 잠금이 남습니다.

지금 방식도 고객이 개발 DB를 준다는 전제에 맞습니다. 복제할 때 읽기만 하므로 되돌릴 것이 없고, "격리를 보장하지 못하면 원래 DB로 대신하지 않는다"는 저장소 규칙도 지킵니다. 대신 DB 설치 폴더(Oracle은 시험 전용 서버)가 있어야 하며, 복제할 수 있는 크기는 기본 2GB까지입니다.

### 계획

1. 복제, 빌드, 기동에 걸린 시간을 로그와 결과에 남깁니다. 큰 앱은 비중이 다를 수 있어 이후 판단에 필요합니다.
2. 다시 띄우는 시간을 줄입니다.
   - DB 복제본은 실행이 루프를 벗어날 때까지 유지하고, DDL이 바뀌면 새로 만듭니다. 앞 회차의 데이터가 남으므로 초기화 방법도 둡니다.
   - WAR를 풀어서 배포합니다. JSP나 정적 파일만 바뀌었으면 떠 있는 서버에 복사합니다.
   - Java나 XML이 바뀌었으면 `compileJava` 결과를 반영한 뒤 JVM을 다시 띄웁니다. 처음 띄울 때는 지금처럼 전체를 빌드합니다.
   - 두 번째 회차부터 55초가 20초 안팎으로 줄고, JSP만 고치면 거의 0초가 될 것으로 봅니다. 아직 재 보지는 않았습니다.
3. 시험할 수 있는 앱의 범위를 넓힙니다. 프로젝트별 Tomcat 선택과 프로젝트 관리의 DB를 이용한 JNDI 리소스 생성을 추가하고, `weblogic.*`이나 `jeus.*`를 쓰는 앱은 시작 전에 가려냅니다.

판매할 제품이라면 3번이 2번보다 중요합니다. 2번으로 줄이는 시간은 실행당 1~2분 정도지만, 3번을 하면 지금 시험하지 못하는 앱도 시험할 수 있습니다. 그래서 1 → 3 → 2 순서를 권합니다.

아직 고친 것은 없습니다. 두 가지를 정해 주세요.

- 이 순서로 진행할까요?
- Tibero나 대용량 DB처럼 복제할 수 없는 고객 환경이 실제로 있을까요? 있다면 단일 연결 방식보다 "스키마 전체와 데이터 일부 복제"나 지원 DB 추가를 먼저 검토하겠습니다.

## 답변

Sonnet의 결론 중 DB 쪽은 대부분 동의합니다. WAS 쪽은 제안의 가장 큰 장점을 놓쳤다고 봅니다.

## 동의하는 점

- **DB는 지금처럼 일회용 복제본을 쓰는 게 맞습니다.** 커밋하지 않는 단일 연결 방식을 막는 결정적인 이유는 세 가지입니다.
  - MySQL과 Oracle은 DDL을 실행하면 앞의 DML까지 암묵적으로 커밋합니다. 그런데 sm-workflow는 `03-3.ddl`을 반영합니다.
  - 고객 개발 DB에 시험하는 내내 행 잠금이 남습니다.
  - 앱이 직접 만드는 커넥션 풀(testApp의 `BasicDataSource`)을 엔진이 바꾸려면 JDBC를 가로채야 합니다.
- **context reload는 할 필요가 없습니다.** Spring 초기화는 reload해도 다시 하므로 줄어드는 시간은 몇 초입니다. 대신 메모리 누수와 세션이 끊기는 부담이 생깁니다.
- **DB가 없을 때의 처리는 이미 있습니다.** 이유를 붙여 `BLOCKED`로 표시합니다.

## 동의하지 않거나 보완할 점

**1. 사용자 제안의 핵심은 Maven 없이 띄우는 것입니다.**

overlay로 반영하고 바뀐 Java만 컴파일하면 빌드 도구에 기대지 않고 서버를 띄울 수 있습니다. 지금 `TestServerTool`은 `pom.xml`이 없으면 바로 실패하고, Maven 단일 모듈만 지원합니다. 국내 SI 레거시는 Eclipse/Ant 프로젝트에 `WEB-INF/lib`를 그대로 쓰는 경우가 많아서, 이 제약이 속도보다 더 큰 문제입니다.

`compileJava`는 Eclipse `.classpath`와 `WEB-INF` 구조도 읽습니다. 바뀐 파일을 쓰는 원본 파일까지 함께 컴파일하고, 결과 클래스를 `outputDir`에 남깁니다. 그래서 다음 경로를 WAR 방식의 기본으로 삼을 수 있습니다.

> 원본의 배포 구조(풀린 webapp) 사본 + 개발 결과 + `compileJava`가 만든 클래스 → 전용 CATALINA_BASE

이렇게 하면 Sonnet 계획의 2번(다시 띄우는 비용 줄이기)과 3번(띄울 수 있는 앱 늘리기)이 한 작업이 됩니다. 속도가 빨라지는 것은 덤으로 따라옵니다. Sonnet이 "부분 컴파일은 이미 있음"으로 넘긴 것은, 그 기능을 컴파일 확인에만 쓰고 있다는 점을 보지 못한 것입니다.

**2. 측정값이 작은 앱 하나에서 나왔습니다.**

testApp은 소스 파일이 105개라서 `mvn clean package`가 16초에 끝났습니다. 파일이 수천 개인 레거시라면 빌드만 몇 분이 걸릴 수 있습니다. 그런 앱에서는 "서버 기동은 병목이 아니다"라는 결론이 바뀝니다. 지금 근거로는 "줄여도 효과가 작다"고 단정하기 어렵습니다.

**3. 사용자가 말한 "무겁다"는 실행 시간보다 준비 부담일 수 있습니다.**

격리 코드는 약 3,700줄입니다(SOCKS 중계, Oracle PDB·Data Pump, 경로 치환). 현장에서는 같은 종류의 DB 설치 폴더, Oracle 시험 전용 CDB, AppArmor 설정까지 필요합니다. 폐쇄망 고객사에서 이것을 갖추기는 쉽지 않습니다. 복제는 기본으로 두더라도, 복제를 못 하는 현장에서 어떻게 할지 정해 두어야 합니다. 지금은 전문가 해결 Agent만 원래 DB에 붙는 `startTestServer`를 대신 쓰고, 자동 검증은 `BLOCKED`에서 멈춥니다.

**4. Sonnet이 든 반대 이유 중 두 가지는 기술적으로 풀 수 있습니다.**

- `dbQuery`가 다른 연결이라 커밋 전 데이터를 못 본다는 문제는 엔진이 같은 연결로 보내면 해결됩니다.
- 앱의 `rollback()`이 앞의 시험 데이터까지 지운다는 문제는 savepoint로 처리할 수 있습니다.

그래서 이 둘은 반대 근거로 약합니다. 결론은 같지만, 근거는 위의 세 가지(DDL 커밋, 잠금, 커넥션 가로채기)로 좁히는 게 정확합니다.

## 제 계획

1. **WAR 방식에 Maven 없는 경로를 추가합니다.** 원본의 클래스(`WEB-INF/classes` 또는 빌드 결과)와 `compileJava` 결과를 풀린 webapp 사본에 얹어 띄웁니다. Maven 프로젝트도 이 경로를 쓰면 다시 띄울 때 `clean package`를 하지 않아도 됩니다.
2. **Tomcat 쪽 범위를 넓힙니다.**
   - javax/jakarta에 맞춰 프로젝트별로 Tomcat을 고릅니다.
   - 프로젝트 관리의 DB로 JNDI 리소스를 만듭니다. `java:comp/env`가 붙지 않은 이름은 사본에서만 바꿉니다.
   - `weblogic.*`이나 `jeus.*`를 import한 앱은 시작 전에 "시험 불가"로 가려냅니다.
3. **구간별 시간을 기록합니다.** 큰 레거시 앱에서 한 번 재 보고, DB 복제본을 회차 사이에 유지할지 정합니다.
4. **복제할 수 없는 현장의 방침을 정합니다.** 이것은 사용자가 정할 일입니다.

마지막으로 하나 여쭙겠습니다. 고객사 앱이 Maven이 아닌 구조(Eclipse/Ant, `WEB-INF/lib`)일 가능성이 높다면 1번부터 하는 게 맞습니다. 대부분 Maven이라면 Sonnet이 권한 순서대로 해도 큰 차이는 없습니다. 어느 쪽인가요?

## 답변

네. 지금 구현은 프로젝트 관리에 등록한 DB를 통째로 복제합니다. 그것도 `startSandboxServer`를 부를 때마다 처음부터 다시 합니다.

## 지금 복제하는 범위

DB 서버 전체를 복제하는 것은 아닙니다. 다만 등록된 DB 하나하나는 구조와 데이터를 모두 복제합니다.

| DB | 복제 단위 | 방법 | 범위 |
|---|---|---|---|
| MySQL | 등록한 database | 일회용 `mysqld`를 따로 띄우고 `mysqldump`로 읽어 넣음 | 모든 테이블과 모든 행, 트리거, 루틴 |
| PostgreSQL | 등록한 database | 일회용 PostgreSQL을 띄우고 `pg_dump`로 읽어 넣음 | 모든 스키마, 테이블, 행 |
| Oracle | 앱 계정의 스키마 | 시험 전용 CDB에 PDB를 만들고 Data Pump로 가져옴 | 스키마 전체. 복제 뒤 테이블마다 행 수를 원본과 맞춰 봄 |

크기가 `sandbox-max-db-mb`(기본 2048MB)를 넘으면 복제하지 않습니다. 이때는 "작은 개발 DB를 등록하라"며 실패합니다. 일부 테이블만 복제하거나 데이터를 줄여서 복제하는 기능은 없습니다.

## 앞에서 한 제 판단을 고칩니다

이 점을 놓고 보면 "DB는 복제본이 맞다"고 한 제 말은 조건을 달아야 했습니다. testApp은 작아서 복제가 20초 만에 끝났습니다. 하지만 고객사 개발 DB는 보통 수십 GB가 넘고, 운영 DB를 그대로 떠 온 경우도 많습니다. 그러면 이렇게 됩니다.

- 2GB 상한에 걸려 자동 검증이 거의 언제나 `BLOCKED`로 끝납니다.
- 상한을 올리면 복제 한 번에 몇십 분이 걸리고, 그만큼 디스크도 차지합니다.

그래서 사용자가 말한 "무겁다"는 지적은 맞습니다. 통째 복제는 작은 DB에서만 쓸 수 있는 방식입니다.

## 그렇다고 단일 연결 rollback으로 가자는 것은 아닙니다

DDL을 실행하면 앞의 작업까지 암묵적으로 커밋되는 문제, 고객 DB에 잠금이 남는 문제는 DB 크기와 상관없이 그대로 남습니다. 큰 DB에 맞는 현실적인 방법은 복제하는 양을 줄이는 쪽입니다.

1. **구조는 전부, 데이터는 일부만 복제합니다.**
   - 모든 테이블의 구조와 코드성 테이블처럼 작은 테이블은 통째로 복제합니다. 앱이 처음 뜰 때 읽는 데이터이기 때문입니다.
   - 큰 테이블은 구조만 만들거나 최근 N행만 가져옵니다.
   - 시험 대상 테이블(영향도분석서·설계서에 나온 것과 knowledge의 CRUD 분석)은 행 수 상한 안에서 가져옵니다.
   - 행 수를 줄이면 FK가 끊길 수 있습니다. 그래서 일부만 가져온 테이블은 FK 없이 넣고 결과에 적습니다.
2. **복제본을 회차 사이에 다시 씁니다.** 한 실행 안에서는 처음에만 복제하고, 다음 회차에는 DDL만 새로 반영합니다.
3. 그래도 안 되는 현장은 고객이 시험 전용 DB를 따로 주는 경우만 허용합니다. 이때도 원래 DB로 대신 시험하지는 않습니다.

1번을 하면 복제 시간이 DB 크기가 아니라 시험에 필요한 데이터 양만큼 걸립니다. 다만 데이터가 일부만 있으니 "목록에 이전 데이터가 안 보인다" 같은 결과는 환경 차이로 보고 `BLOCKED`로 처리해야 합니다. Skill `test-environment`에 그 판단 기준을 더해야 합니다.

## 답변

그렇다면 데이터를 일부만 복제하는 방식을 먼저 만들어야 합니다. 지금처럼 통째로 복제하면 고객 현장에서는 자동 검증이 거의 언제나 `BLOCKED`로 끝납니다.

## 설계안

**1. 구조는 전부, 데이터는 테이블마다 따로 정합니다.**

먼저 원래 DB에서 테이블별 크기를 읽습니다. MySQL은 `information_schema.TABLES`, PostgreSQL은 `pg_total_relation_size`, Oracle은 `user_segments`에서 읽고, 원래 DB에는 읽기만 합니다. 그 결과로 테이블마다 다음 셋 중 하나를 고릅니다.

| 분류 | 기준 | 복제 |
|---|---|---|
| 통째 | 작은 테이블(예: 10MB 이하). 코드·메뉴·권한처럼 앱이 뜰 때 읽는 것은 대개 여기 들어감 | 구조와 모든 행 |
| 지정 | 시험 대상 테이블, 프로젝트 관리에 적은 조건 | 구조와 조건에 맞는 행(행 수 상한 있음) |
| 구조만 | 그 밖의 큰 테이블 | 구조와 최근 N행(단일 PK면 PK 내림차순, 없으면 순서 없이 N행) |

크기 상한(`sandbox-max-db-mb`)은 원래 DB 크기가 아니라 실제로 복제할 양에 적용합니다.

**2. 어떤 테이블을 넣을지는 인자와 프로젝트 설정으로만 정합니다.**

엔진은 특정 Workflow나 앱을 몰라야 하므로 두 경로로 받습니다.

- `startSandboxServer`에 테이블 목록 인자를 추가합니다. sm-workflow는 영향도분석서·설계서의 테이블과 knowledge CRUD 분석 결과를 이 인자로 넘깁니다.
- 프로젝트 관리에 "시험 복제 조건"을 한 줄에 하나씩 적습니다. 예: `TB_USER=USER_ID IN ('tester01')`, `TB_ORDER=REG_DT >= SYSDATE-30`.

두 번째가 필요한 이유는 사용자 테이블 같은 큰 테이블입니다. 시험계정의 행이 빠지면 로그인부터 실패합니다.

**3. FK는 남기되, 복제한 데이터는 검사하지 않습니다.**

데이터를 일부만 가져오면 부모 행이 빠질 수 있습니다. 그래서 넣는 동안만 FK 검사를 끕니다.

- MySQL: `FOREIGN_KEY_CHECKS=0`
- PostgreSQL: `session_replication_role=replica`
- Oracle: 제약을 끄고 넣은 뒤 `ENABLE NOVALIDATE`

이렇게 하면 제약 자체는 남으므로, 시험 중에 앱이 새로 넣는 행은 FK 검사를 받습니다. FK 결함을 놓치지 않습니다.

**4. DB마다 복제 방법을 이렇게 바꿉니다.**

- MySQL: 구조는 `mysqldump --no-data`로, 데이터는 테이블별 `--where`로 가져옵니다.
- PostgreSQL: 구조는 `pg_dump --schema-only`로, 데이터는 테이블별 `COPY (SELECT … LIMIT N)`로 가져옵니다.
- Oracle: Data Pump 네트워크 가져오기의 `QUERY` 절로 가져옵니다. 행 수 대조는 원본 전체가 아니라 조건으로 센 행 수와 맞춥니다.

**5. 복제본을 회차 사이에 다시 씁니다.**

한 실행에서 복제는 처음 한 번만 합니다. 다음 회차에는 원본 DDL만 새로 반영하고, 시험 데이터를 지우는 것은 초기화 옵션으로 둡니다. 실행이 끝나면 지금처럼 복제본을 지웁니다.

**6. 판정 기준을 고칩니다.**

시험 서버 결과의 "원래 환경과 다른 점"에 "데이터 일부만 복제: 테이블별 행 수"를 적습니다. Skill `test-environment`에는 "목록에 원래 데이터가 없다", "참조 데이터가 없어 화면이 비어 있다"를 환경 차이(`BLOCKED`)로 보는 기준을 더합니다.

## 미리 알아 둘 한계

- 데이터를 줄이면 페이지 나누기, 대량 데이터에서만 나는 성능 문제, 통계 화면은 검증할 수 없습니다. 이런 완료 기준은 `BLOCKED`로 나옵니다.
- 시험계정의 행이 어느 테이블에 있는지는 사람이 프로젝트 관리에 처음 한 번 적어야 할 수 있습니다. 로그인이 실패하면 결과에 그렇다고 알립니다.
- 큰 DB는 구조만 복제해도 테이블이 수천 개라 몇 분이 걸릴 수 있습니다. 5번(복제본 재사용)이 함께 있어야 하는 이유입니다.

| | 지금 | 제안(Tomcat overlay) |

겹쳐서 반영한다는 점은 같습니다. 차이는 바닥에 원본 폴더 자체를 깔고 바로 쓰느냐, 복사본을 쓰느냐입니다.

## 원본을 바로 쓰면 생기는 문제

testApp에 실제 예가 있습니다. `kr/co/gnx/config/Startup.java:53`의 업로드 폴더가 `/app/testApp/uploadData/DEV_CMS4_PRD`로, 원본 폴더 안을 가리킵니다.

1. **앱이 원본 폴더에 씁니다.**
   - 지금은 사본의 소스와 복제 DB에 들어 있는 원본 경로를 사본 경로로 바꾸고(`SandboxPaths`) 그 사본을 빌드합니다. 그래서 시험 중에 올린 파일은 사본에 쌓이고, [삭제]를 눌러도 사본의 파일만 지워집니다.
   - 원본을 docBase로 쓰면 바꾼 사본이 없습니다. 이 경로 치환이 빠지면 업로드와 삭제가 고객 원본 폴더에 그대로 일어납니다. `getRealPath()`로 경로를 구하는 앱도 마찬가지입니다. 개발 결과가 아닌 원본 파일을 덮어쓸 수도 있습니다.
2. **삭제 목록을 반영할 수 없습니다.** 앞에 얹는 방식으로는 원본 파일을 없는 것처럼 만들 수 없습니다. Sonnet도 짚은 점입니다.

## 풀 수는 있습니다

1번은 이렇게 하면 됩니다. 원본 경로가 들어 있는 파일만 바꿔서 얹는 층에 넣고, Java 파일이면 다시 컴파일해 넣습니다. 이 경우 원본에는 읽기만 합니다.

다만 치환은 소스에 적힌 경로에만 통합니다. 앱이 원본 폴더 안을 상대경로나 `getRealPath()`로 찾아 쓰는 경우는 잡지 못합니다. 지금 방식은 그런 경우에도 사본에 쓰게 되어 안전합니다. 제가 보류라고 한 이유가 이것입니다. 막을 수 없는 경우가 하나 생기는 대신 얻는 것이 첫 복사 시간뿐이라면 바꿀 만하지 않다고 봤습니다.

## 다시 정리하면

- **실행별 CATALINA_BASE**는 격리와 상관없습니다. 같은 프로젝트를 여러 실행이 동시에 시험해야 한다면 할 만합니다. 지금은 두 번째 실행이 잠금에 걸려 60초 기다린 뒤 실패합니다.
- **원본을 docBase로 직접 쓰는 overlay**는 원본에 쓰기가 일어날 수 있어서 하지 않는 편이 좋습니다. 사본을 만드는 비용은 처음 한 번뿐이고, 그다음부터는 지금도 바뀐 파일만 복사합니다.

동시 실행이 필요하면 실행마다 사본을 따로 둬야 해서 디스크가 실행 수만큼 듭니다. 고객 현장에서 같은 프로젝트에 여러 요청이 동시에 돌 일이 있을까요? 없다면 지금 구조를 유지하고, 앞서 말한 일부 복제와 Maven 없는 경로에 집중하는 것을 권합니다.

```
    webapp/             실행 전용 docBase. 개발 결과, compileJava가 만든 클래스, 경로를 바꾼 파일
    data/               원본 경로를 이리로 바꿈(업로드 폴더 등)
    tomcat/             실행 전용 CATALINA_BASE(conf, work, logs)
    db/                 실행 전용 DB 복제본(일부 복제)
```

- Tomcat 설정은 이렇게 합니다. `docBase`는 `runs/{실행ID}/webapp`, `PostResources`는 `base`입니다. 바뀐 것은 실행 층에서 먼저 찾고, 나머지(lib, 바뀌지 않은 JSP·클래스)는 공용 층에서 읽습니다.
- 앱이 새로 만드는 파일은 docBase인 실행 층에 쌓입니다. 소스에 박힌 원본 경로는 `data/`로 바꿉니다. 고객 원본은 읽기만 합니다.
- 공용 층(`base`)은 원본 소스가 바뀌었을 때만 새로 만듭니다. 그동안 다른 실행이 쓰지 못하게 프로젝트 잠금은 이 작업에만 겁니다. 시험은 실행끼리 잠금 없이 동시에 돌아갑니다.
- 앱이 `getRealPath()`로 이미 있는 파일을 덮어쓰면 공용 층이 바뀔 수 있습니다. 그래서 실행이 끝날 때 공용 층이 바뀌었는지 확인하고, 바뀌었으면 다시 만들고 결과에 적습니다. 고객 원본에는 닿지 않습니다.
- 삭제 목록은 실행 층의 `WEB-INF/web.xml`에 막는 설정을 넣는 대신 컴파일·기동 단계에서 처리합니다. Java 클래스는 `compileJava`가 이미 삭제 목록 사용처를 오류로 잡습니다. JSP·정적 파일은 실행 층에 "없음" 표시를 두고, 그 주소로 들어오면 404를 돌려주는 Valve 하나로 처리합니다.

실행마다 매번 하던 `mvn clean package`도 없어집니다. 실행 층에는 `compileJava` 결과만 들어가기 때문입니다. 그래서 앞서 말한 "Maven 없는 경로"가 이 구조에 그대로 포함됩니다. 공용 층은 Maven이면 엔진이 한 번 빌드하고, Maven이 아니면 고객이 준 빌드 결과(`WEB-INF/classes`)를 씁니다.

Spring Boot(`java -jar`) 앱은 jar를 풀어 두고 실행 층의 클래스를 classpath 앞에 두는 방식으로 같은 구조를 씁니다.

## 동시 실행에서 새로 생기는 문제

- **자원**: MySQL·PostgreSQL은 실행마다 DB 서버를 하나씩 띄우고, Oracle은 PDB 한도(Free 16개, XE·19c 무상판 3개)가 있습니다. 그래서 동시에 띄울 수 있는 격리 서버 수를 설정으로 두고, 넘으면 기다리게 합니다.
- **기존 업로드 파일**: `data/`는 처음에 비어 있으므로, 기존 게시물의 첨부 파일이 404로 나옵니다. 같은 디스크면 하드링크로 연결하고, 아니면 "원래 환경과 다른 점"에 적어 `BLOCKED`로 판정하게 합니다. 하드링크는 그 파일을 제자리에서 고쳐 쓰면 원본도 바뀝니다. 업로드 폴더는 보통 원본 소스 안이 아니라 고객 서버의 별도 폴더라서, 기본값은 링크하지 않는 쪽으로 두겠습니다.

## 답변

정리안의 방향은 좋습니다. 무거운 부분(DB 복제, Maven 빌드, 통째 복사)을 모두 덜어 냅니다. 다만 B(데이터 원복)는 그대로 두면 구멍이 있고, A2는 고객 원본에 파일이 써지는 문제가 남습니다. 항목별로 보겠습니다.

## A. WAS

**A1. Tomcat 전환과 프로젝트별 WAS·DB 정보 등록: 동의합니다. 세 가지를 더해야 합니다.**
- 전환한 설정은 실행 층(`runs/{실행ID}`)에만 둡니다. 원본이나 개발 결과에 섞이면 납품 변경분에 들어갑니다.
- WAS 정보에 Tomcat 버전(설치 경로)을 넣습니다. javax 앱은 Tomcat 9 이하, jakarta 앱은 10 이상이어야 합니다.
- 띄우기 전에 판정합니다. EJB, `weblogic.*`·`jeus.*` import가 있으면 "서버 시험 불가"로 끝냅니다.

**A2. 실행별 overlay와 CATALINA_BASE: 공용 층 없이도 됩니다.**

Tomcat은 여러 폴더를 웹앱의 서로 다른 위치에 붙일 수 있습니다(`webAppMount`). 그래서 원본이 Tomcat 구조가 아니어도 복사 없이 바로 겹칠 수 있습니다.

```
docBase                          = runs/{실행ID}/webapp            (쓰기 가능, 실행 전용)
PostResources /                  = 원본/src/main/webapp            (읽기)
PostResources /WEB-INF/classes   = 원본/target/classes             (읽기)
PostResources /WEB-INF/lib       = 의존성 jar들                    (읽기, compileJava가 이미 구하는 목록)
```

다만 빠진 것이 하나 있습니다. 소스에 박힌 원본 안의 절대경로입니다. testApp의 `Startup.java:53`이 업로드 폴더를 `/app/testApp/uploadData/...`로 갖고 있습니다. 이대로 띄우면 시험 중의 업로드와 삭제가 고객 원본 폴더에서 일어납니다. 그래서 다음 두 가지를 넣어야 합니다.
- 실행 층에 `data/`를 두고, 원본 경로가 든 파일은 경로를 바꿔 실행 층에 넣습니다. Java 파일이면 다시 컴파일합니다.
- 앱이 `getRealPath()`로 이미 있는 파일을 덮어쓰면 원본이 바뀝니다. 막을 수는 없으니, 실행이 끝날 때 원본의 해당 폴더가 바뀌었는지 확인하고 알립니다.

**A3. 바뀐 Java만 `compileJava`로 컴파일: 동의합니다.** 원본의 `target/classes`가 최신이어야 한다는 전제는 지금과 같습니다. MyBatis XML·properties처럼 `src/main/resources`에서 바뀐 파일은 실행 층의 `WEB-INF/classes`에 복사합니다.

**A4. 즉시 반영, context reload, JVM 1회: 이 구조에서는 받아들일 만합니다.**

앞에서 Sonnet과 저는 reload를 반대했습니다. 그때는 매번 `mvn clean package`를 하는 구조였습니다. 빌드가 없어지면 다시 띄우는 비용이 reload와 비슷해지므로 둘 중 어느 쪽이든 큰 차이는 없습니다. 자동 수정은 결정 하나마다 최대 2번이라 reload 횟수도 적고, 누수 걱정도 작습니다.

| 바뀐 것 | 반영 |
|---|---|
| JSP, JS, CSS, 이미지 | 실행 층에 복사(즉시) |
| class, XML, properties, `web.xml` | context reload |
| JVM 옵션, Tomcat 설정 | JVM 재시작 |

정할 것이 둘 있습니다.
- **reload하면 세션이 끊깁니다.** 검증 Agent에게 다시 로그인하라고 결과에 적어야 합니다.
- **JVM을 언제까지 둘지 정해야 합니다.** 사람 승인은 20~40분, 길면 몇 시간 기다립니다. 실행 ID당 한 번만 띄우려면 그동안 서버를 살려 둬야 하고, 동시 실행 수만큼 메모리를 씁니다. 지금은 승인 대기에 들어가면 내립니다. 제안은 "승인 대기 중에도 두되, 유휴 N분이 지나면 내린다"입니다.

## B. DB: 방향은 따르되, 원복 방법과 조건을 분명히 해야 합니다

고객 DB가 크고 동시 실행도 있다면 복제를 포기하는 것은 이해됩니다. 남는 것은 원복 방법입니다. 가볍고 범용적인 방법은 앞에서 말한 "커밋하지 않는 연결"뿐입니다. 이 방식은 동시 실행에서는 오히려 유리합니다. 실행끼리 서로의 시험 데이터를 보지 못하고, 엔진이나 Tomcat이 죽으면 DB가 알아서 rollback하기 때문입니다.

**구현:** A1에서 설정을 전환할 때, 실행 층의 데이터소스를 엔진이 만든 감싸는 JDBC 드라이버로 바꿉니다. 이 드라이버가 실행당 DB마다 물리 연결 하나를 잡고 다음처럼 동작합니다.
- autocommit은 끕니다.
- `commit()`은 무시하고 `close()`는 반납으로 처리합니다.
- 앱의 `rollback()`은 savepoint까지만 되돌립니다. 그래서 앞의 시험 데이터가 지워지지 않습니다.
- 동시 요청은 한 번에 하나씩 처리합니다.
- 실행이 끝나면 rollback합니다.

**풀어야 할 것:**

| 문제 | 대응 |
|---|---|
| DDL. MySQL·Oracle은 실행하는 순간 그때까지의 작업도 커밋됨 | DDL은 시험 트랜잭션 밖에서 사람 승인 뒤 개발 DB에 실제로 반영하고 되돌리지 않습니다. 개발 DB에 새 테이블을 만드는 것은 어차피 납품 과정이기 때문입니다. PostgreSQL만 트랜잭션 안에서 처리합니다 |
| 검증 Agent의 `dbQuery`는 엔진 JVM에서 돌아서, 앱 JVM의 커밋 전 데이터를 못 봄 | 감싸는 드라이버가 실행 전용 포트로 조회 창구를 열고, `dbQuery`가 그 별칭으로 보내게 합니다 |
| 시험 중 잡은 행 잠금 때문에 고객 개발자나 다른 실행이 기다림 | 실행당 시간 상한, 잠금 대기 시간 상한(넘으면 그 요청만 실패) |
| 프로시저 안의 COMMIT, 자율 트랜잭션, DB 링크 너머의 쓰기 | 되돌릴 수 없습니다. 결과에 "원복 보장 안 됨"으로 적습니다 |
| 메일, MQ, 외부 연계 호출 | DB 밖이라 되돌릴 수 없습니다. 지금의 `SandboxGuard`처럼 외부 접속을 막는 것은 남기길 권합니다 |

## 답변

지난번보다 범위가 분명해졌습니다. 새로 들어간 A1의 플랫폼 판정과 C3의 소스 갱신에서 문제가 하나씩 보입니다. 특히 C3는 동시 실행과 부딪힙니다.

## 새로 들어간 항목

**A1. WebLogic·WebSphere·JEUS라서 불가로 판정하는 것은 범위가 너무 넓습니다.**

그 WAS에서 돌던 앱도 대부분 평범한 Servlet/Spring 앱입니다. 바꿀 것이 `weblogic.xml`·`jeus-web-dd.xml` 같은 벤더 설정과 JNDI 이름뿐이라면 Tomcat으로 옮길 수 있습니다. 그래서 판정 기준은 플랫폼 이름이 아니라 코드여야 합니다.

| 판정 | 기준 |
|---|---|
| 불가 | EJB(`javax.ejb`, `ejb-jar.xml`), `weblogic.*`·`com.ibm.websphere.*`·`jeus.*` import, 벤더 전용 기능(WebLogic startup class 등) |
| 전환 | 그 밖. 벤더 설정은 Tomcat `context.xml`로 옮기고, JNDI 이름을 맞추고, 프로젝트 DB로 리소스를 만듭니다 |

불가로 판정되면 사용자 말대로 정보는 저장하고, 서버 기동 시험 앞까지만 진행합니다. 이때 검증 결과는 PASS가 아니라 "서버 시험 안 함(이유)"으로 남겨, 사람이 승인할 때 보이게 하겠습니다.

**C3. 형상관리에서 최신 소스를 받는 step은 동시 실행과 부딪힙니다.**

- 실행 A가 원본 폴더를 PostResources로 물고 시험하는 중에 실행 B가 시작하면, B가 같은 폴더를 갱신합니다. A의 서버 밑에서 소스가 바뀝니다.
- 같은 실행 안에서도 문제가 됩니다. 설계서와 개발 결과는 받은 시점의 소스를 기준으로 썼는데, 나중에 원본이 바뀌면 개발 결과가 엉뚱한 파일 위에 얹힙니다.
- 소스만 바뀌고 `target/classes`는 그대로라 `compileJava`와 서버가 옛 클래스를 씁니다.

그래서 이렇게 바꾸길 권합니다.
- **제자리에서 갱신하지 않고, 리비전별 폴더로 받습니다.** 예: `{프로젝트ID}/src/{리비전}/`. 실행은 시작할 때 받은 리비전을 state에 적고, 끝까지 그 폴더만 씁니다. 같은 리비전은 여러 실행이 함께 읽고, 아무도 쓰지 않는 옛 리비전은 지웁니다.
- **받은 뒤 한 번 전체 컴파일합니다.** 결과는 `{프로젝트ID}/src/{리비전}-classes/`에 둡니다. 빌드 도구에 기대지 않도록 `compileJava`의 classpath 탐색으로 전체 javac를 돌립니다. 이것이 A2·A3의 "원본 클래스"가 됩니다.
- **형상관리 정보가 없으면 프로젝트.소스디렉토리를 그대로 씁니다.** 이때는 원본 클래스가 최신이어야 한다는 전제를 결과에 적습니다.
- **인증은 저장하지 않습니다.** 엔진 서버의 SSH 키나 SVN 인증 캐시를 쓰고, 실패하면 그 이유로 멈춥니다.

이렇게 하면 프로젝트.소스디렉토리가 고객 개발자의 작업 폴더여도 건드리지 않습니다.

## 남아 있는 항목

**A2. 구조 해석:** 자동으로 해석할 대상과 순서는 다음과 같습니다.
1. Maven(`src/main/webapp`)
2. Eclipse WTP(`.settings/org.eclipse.wst.common.component`에 배포 매핑이 그대로 있음)
3. Eclipse `.classpath`
4. `WEB-INF` 구조
5. Gradle

못 찾으면 프로젝트 관리에서 웹 루트, 소스 폴더, lib 폴더를 직접 적게 합니다. Ant 프로젝트는 대개 이 경로로 갑니다.

그리고 지난번에 말한 것이 아직 빠져 있습니다. 소스에 박힌 원본 안 절대경로(testApp의 업로드 폴더)는 `runs/{실행ID}/data/`로 바꿔야 합니다. 그러지 않으면 시험 중 업로드와 삭제가 원본 폴더에서 일어납니다. 구조에 `data/`를 넣겠습니다.

**A4. 결정이 남은 두 가지:** reload하면 세션이 끊겨 다시 로그인해야 합니다. 그리고 승인을 기다리는 동안 JVM을 살려 둘지 정해야 합니다. 제안은 "유휴 N분이 지나면 내리고, 다음에 다시 띄운다"입니다.

**B. 원복:** 지난번 설계(커밋하지 않는 연결을 감싸는 드라이버, 실행 종료 시 rollback)로 가겠습니다. DDL을 어떻게 다룰지는 아직 답을 받지 못했습니다.

**C2. 통일:** 동의합니다. Tool 하나(`startTestServer`)로 합치고 다음을 걷어 냅니다.
- `startSandboxServer`
- `sandbox`의 DB 복제 코드
- 요청서 `시험환경`의 반영폴더·반영명령

`SandboxGuard`(외부 접속 차단)와 `SandboxPaths`(경로 치환)는 새 Tool에서 다시 씁니다. Agent의 `toolPrerequisites`, `ToolCallGate`의 별칭 묶기, 평가(`EvalRunner`의 `server:`), CLAUDE.md의 "복제본으로만" 규칙, `docs/09` 11장도 함께 고칩니다.
