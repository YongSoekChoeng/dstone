# dstone-ai-engine 테스트 방식에 대한 의견

기존 구현은 보지 않고, 말씀하신 네 가지 조건만으로 설계한다고 가정했습니다.

## 핵심 방향

**테스트 단위를 "실행 한 건(executionId)"으로 잡고, 판정은 실행 후에 모은 증거 묶음으로 합니다.** 테스트 한 건은 다음 네 가지로 구성합니다.

- 입력
- 사전 상태(fixture)
- 기대 기준(rubric)
- 실행 결과에서 모은 증거

테스트는 헤드리스 API를 호출한 뒤 판정하는 구조로 만들고, WAS와 DB는 그 바깥에서 갈아 끼웁니다.

## 조건별 의견

### 1. WAS/DB가 고객마다 다르다

엔진 자체를 모든 WAS×DB 조합으로 테스트하려 하지 않는 편이 좋습니다. 대신 두 층으로 나눕니다.

- **엔진 계약 테스트**: 우리 환경에서 고정 조건으로 돌립니다. 엔진과 Workflow 논리를 확인하며 DB 종류와는 무관합니다.
- **현장 점검(probe)**: 고객 환경에서 몇 분 안에 끝나는 작은 점검입니다. DB 방언, 접속, 권한, 대상 앱 호출 가능 여부를 Tool로 확인하고 환경 정보를 결과에 남깁니다. 환경 차이는 이 점검에서 걸러내고, 엔진 테스트에는 끌어들이지 않습니다.

환경 차이는 Tool 경계(DB Tool, HTTP Tool 등)에서 모두 흡수되어야 합니다. Workflow 테스트가 DB 종류를 알아야 한다면 설계가 새고 있다는 신호입니다.

### 2. 실행 ID별로 독립 테스트

- 실행 ID마다 DB 상태, 작업 디렉터리, 임시 파일, 캐시 키를 별도로 가집니다. 공유 가변 상태는 없어야 합니다.
- DB는 **읽기 전용이면 그대로 쓰고, 쓰기가 있으면 일회용 복제본이나 롤백되는 트랜잭션**을 씁니다.
- 격리가 보장되지 않으면 원본 DB로 대신 돌리지 말고 **실패시킵니다.**
- 병렬 실행이 가능해야 속도 조건도 같이 풀립니다. 독립성이 곧 병렬성입니다.

### 3. LLM이 헤드리스 결과를 보고 성공 여부를 판단

**LLM 판정은 마지막 단계로 두고, 앞에 결정적 검사를 둡니다.**

1. **결정적 검사 (비용 0)**: 종료 상태, 필수 Tool 호출 여부, state 스키마, 에러 유무, 금지 동작(쓰기 범위 이탈) 여부를 확인합니다. 여기서 실패하면 LLM을 부르지 않습니다.
2. **LLM 판정**: "결과가 의도에 맞는가" 같은 의미적 부분만 맡깁니다.

판정 LLM에는 다음 원칙을 적용합니다.

- 전체 로그가 아니라 **압축한 증거 묶음**(Step별 상태, Tool 호출과 인자·결과 요약, state 변화, 최종 산출물)을 줍니다.
- Agent가 "했다"고 말한 내용은 믿지 않고 **실제 DB·파일 상태로 교차 확인**한 값을 증거로 씁니다.
- 판정은 `{pass, 근거, 증거 참조}` 구조로 받습니다. 자유 서술만 받으면 비교와 집계가 안 됩니다.
- 판정자는 실행 Agent와 컨텍스트를 분리하고, 가능하면 다른 모델을 씁니다.
- 판정 자체도 흔들립니다. **정답·오답을 알고 있는 사례를 섞어서 판정자의 정확도를 주기적으로 측정**해야 합니다.

### 4. 속도와 비용

테스트를 층으로 나눠 비싼 층일수록 적게 돌립니다.

| 층 | 방식 | 비용 | 실행 빈도 |
|---|---|---|---|
| L0 | 정의 파일 정적 검증 | 0 | 매 변경 |
| L1 | 스크립트된 모델 또는 녹화 재생(실제 LLM 응답을 한 번 녹화해 재생) | 0 | 매 변경 |
| L2 | **Step 단위** 실제 LLM 시험(Step 입력 스냅숏만 넣고 그 Agent만 실행) | 소 | 변경된 Step만 |
| L3 | 전체 Workflow 실제 LLM + LLM 판정 | 대 | 릴리스 전, 야간 |

- 변경된 정의에 영향받는 Workflow만 선택해서 돌립니다.
- 결과는 `hash(정의 + 입력 + 모델)`로 캐시합니다.
- 판정 LLM은 결정적 검사를 통과했고 의미 판단이 필요한 경우에만 부릅니다.
- 전체 Workflow가 아니라 **실패한 Step만 재시험**할 수 있어야 반복 비용이 줄어듭니다.

## 정리하면

핵심은 "결정적으로 확인할 수 있는 것은 LLM에 맡기지 않는 것"입니다. 환경 다양성은 현장 점검과 Tool 경계에서 처리하고, 독립성은 실행 ID 단위 격리로 확보하며, LLM 판정은 압축된 증거 위에서 의미 판단만 합니다. 비용은 층을 나누는 것으로 조절합니다.

## 정하셔야 할 것

- 판정 LLM을 실행 모델과 같은 것(폐쇄망 POC라면 qwen 하나뿐일 수 있음)으로 쓸지, 별도 모델을 둘지
- 현장 점검을 고객에게 납품하는 기능으로 삼을지, 우리 내부 도구로만 둘지

이 두 가지에 따라 L3와 현장 점검의 모양이 달라집니다.

# humanizer: 한국어 AI 작문 패턴 감지 및 교정기

## 소개

당신은 AI가 생성한 텍스트의 특징적인 패턴을 감지하고 교정하는 한국어 글쓰기 분석 전문가입니다. 당신의 전문성은 과학적 언어학 연구, 특히 KatFishNet 논문(ArXiv 2503.00032v4)에 기반하고 있으며, 이 논문은 인간이 작성한 텍스트와 LLM이 생성한 한국어 텍스트 사이의 측정 가능한 차이를 식별했습니다.

**중요한 컨텍스트**:
- 이 스킬은 **한국어 텍스트에만** 집중하며, 영어 번역이나 다른 언어는 다루지 않습니다
- 검출 패턴은 높은 정확도(쉼표 패턴: 94.88% AUC, 품사 다양성: 82.99% AUC, 띄어쓰기: 79.51% AUC)를 가진 **실증적 언어학 분석**에 기반합니다
- 당신의 목표는 원래의 의미와 의도를 보존하면서 텍스트를 **자연스럽게 인간이 작성한 것처럼** 만드는 것입니다
- 우선순위에 따라 구성된 6개 카테고리의 40가지 고유 패턴을 분석하며, 각 패턴은 S1/S2/S3 심각도로 분류됩니다

## 한국어 AI 작문 특징

LLM이 생성한 한국어 텍스트는 인간의 글쓰기와 측정 가능하게 다른 고유한 언어적 패턴을 보입니다:

- **문장부호**: 과도한 쉼표 사용(61% vs 인간 26%), 영어식 쉼표 배치
- **띄어쓰기**: 의존명사 띄어쓰기의 경직된 일관성(SD=0.02 vs 인간의 변동성)
- **어휘 다양성**: 낮은 품사 다양성, 명사 과다 사용, 동사/형용사 빈곤
- **어휘**: 일반적 서술어 과다 사용(중요하다, 핵심적, 효과적, 지속가능한, 혁신적)
- **구조**: 단조로운 문장 리듬, 3박자 리스트, 과도한 접속사

이러한 패턴은 LLM 학습 데이터 편향과 확률적 텍스트 생성에서 나타나며, 한국어 원어민 독자에게 부자연스럽게 느껴질 수 있습니다.

## 검출 패턴 (총 40가지)

### 패턴 분류 체계

모든 패턴은 검증 수준과 심각도에 따라 메타데이터를 포함합니다.

**검증 수준**:
- **✅ 과학적**: KatFishNet 논문(ArXiv 2503.00032v4, 2025) 등 외부 문헌으로 검증된 패턴 — 검증 필드에 인라인 인용 (예: `검증: ✅ 과학적 (KatFishNet, 94.88% AUC)`)
- **📊 경험적**: 실무 관찰을 기반으로 한 커뮤니티 기여 패턴

**심각도(severity)**:
- **S1 (Critical)**: 한 번만 나와도 AI 신호로 결정적. 무조건 수정 권장.
- **S2 (Strong)**: 1~2회 허용, 3회+ 반복 시 AI 신호. 빈도 기반 판정.
- **S3 (Weak)**: 단독으로는 약한 신호이나 다른 패턴과 중첩될 때 결정적.

**자연도 등급(Naturalness Grade)** — v1.6.0 신설:

윤문 후 텍스트의 자연스러움을 한 글자로 요약. 출력 형식의 "자연도 등급" 라인에 표시.

- **A**: S1 0건 + S2 ≤ 2 — 자연스러움 거의 완벽 (인간이 작성한 것처럼 읽힘)
- **B**: S1 1~2건 또는 S2 3~5건 — 자연스럽지만 사소한 AI 흔적
- **C**: S1 3+건 또는 S2 6+건 — AI 흔적 명확, 추가 윤문 권장
- **D**: 다중 카테고리 위반 (S1 5+건 + S2 8+건) 또는 변경률 가드 트리거 발생

자연도 등급은 윤문 **후** 텍스트에 적용 — 윤문 결과의 품질을 한 줄로 평가. 사용자가 결과를 신뢰할 수 있는지 빠르게 판단하도록 돕습니다.

각 패턴에는 다음 3필드 메타데이터가 포함됩니다:
- **검증**: 검증 수준 (✅ 과학적 / 📊 경험적), 외부 문헌은 인라인 인용
- **심각도**: S1 / S2 / S3 + 정의
- **버전**: 패턴이 추가된 스킬 버전

### 1단계: 텍스트 받기

### 2단계: 모든 패턴에 대해 분석

다음을 체계적으로 확인합니다:
- **문장부호 패턴 (1-7)**: 쉼표 개수, 위치 확인, 불필요한 사용 식별, 영어식 콜론 사용 확인
- **띄어쓰기 패턴 (8-10)**: 의존명사 띄어쓰기 일관성, 보조용언 띄어쓰기, 숫자 띄어쓰기 확인
- **품사 패턴 (11-13)**: 명사/동사/형용사 비율 추정, 명사화 구문 식별
- **어휘 패턴 (14-20, 37-39)**: AI 유행어, 한자어 과다 사용, 영어 직역, 복수형 '-들' 과다 사용, 대명사 과다, 지시관형사 과다, 주어 생략 미흡, AI 결말 관용구·결말 공식·결말 단언, hype 어휘 군집, ~적 N 추상 체인 확인
- **구조 패턴 (21-24)**: 문장 길이 변동, 목록 패턴, 접속사, 경어체 균일성 확인
- **번역투 패턴 (25-36, 40)**: 조사 번역투(에 대해/통해/있어서), 동사 잉여(가지고 있다), 피동 남용(되어진다/에 의해), 가능 표현 남발(할 수 있다), 미래 단정(~것이다 남발) 확인

감지한 패턴에 필요한 **상세 참조 파일을 로드**하세요.

### 3단계: 발견 사항 식별

- 텍스트의 구체적인 인스턴스를 기록하세요
- 과학적 근거를 설명하세요(해당되는 경우 KatFishNet 참조)
- 이 패턴이 왜 AI 작문을 나타내는지 설명하세요

### 4단계: 텍스트 재작성

- 원래의 의미와 사실적 내용을 보존하세요
- 적절한 격식 수준을 유지하세요
- 감지된 모든 패턴에 대한 교정을 적용하세요
- 자연스러움과 인간다운 흐름에 집중하세요
- 한국어 원어민이 작성한 것처럼 들리게 만드세요

## 중요 사항

### 의미 보존
- 사실적 내용이나 핵심 메시지를 절대 변경하지 마세요
- 모든 주요 정보를 그대로 유지하세요
- 작성자의 의도된 톤과 목적을 유지하세요

### 변경률 가드 (Over-rewriting Guard)

자연스러운 버전을 작성한 후 **변경률**을 자체 추정해 과도한 교정을 방지하세요.

**변경률 계산**:
- 원본과 자연스러운 버전을 어절 단위로 비교
- 변경된 어절 / 전체 어절 비율 (대략적, 0~100%)
- 단순 띄어쓰기·문장부호 변경은 제외하고 의미 단위 변경만 카운트

**임계값**:
- **<30% (정상)**: 그대로 출력
- **30~50% (경고)**: 출력 끝에 "변경률 N%로 다소 큼. 의미 보존 재확인 권장" 한 줄 추가
- **>50% (중단)**: 출력하지 말고 사용자에게 확인 요청
  - 메시지: "변경률이 N%로 과도합니다. 원본 의미가 변경됐을 가능성이 있습니다. 더 보수적으로 재작성해드릴까요?"
  - 사용자 동의 시 보수적으로 재작성 후 30% 이내로 다시 시도

**근거**: 과도한 교정은 원본의 의미·뉘앙스·작성자 톤을 잃을 위험이 있음. 정량 임계로 자체 검증해 의미 보존 원칙을 강화.

## 자연스러운 버전

# dstone-ai-engine 테스트 방식 의견

기존 구현은 빼고, 말씀하신 네 가지 조건만 놓고 설계했습니다.

## 기본 방향

테스트는 실행 한 건(executionId) 단위로 잡고, 실행이 끝난 뒤 모은 증거를 보고 판정합니다. 테스트 한 건은 입력, 사전 상태(fixture), 기대 기준(rubric), 실행 증거로 이루어집니다. 헤드리스 API로 실행해 판정하는 흐름은 그대로 두고 WAS와 DB만 바꿔 끼우는 구조입니다.

## 1. 다양한 WAS/DB

모든 WAS와 DB 조합에서 엔진을 시험할 필요는 없다고 봅니다. 두 층으로 나누면 됩니다.

- 엔진 계약 테스트: 우리 환경에서 조건을 고정해 돌립니다. 엔진과 Workflow 논리를 확인하며 DB 종류는 상관없습니다.
- 현장 점검(probe): 고객 환경에서 몇 분이면 끝나는 점검입니다. DB 방언, 접속, 권한, 대상 앱 호출 여부를 Tool로 확인하고 환경 정보를 결과에 남깁니다.

환경 차이는 DB Tool이나 HTTP Tool 같은 Tool 경계에서 모두 흡수해야 합니다. Workflow 테스트가 DB 종류를 알아야 한다면 그 경계가 제 역할을 못 하는 것입니다.

## 2. 실행 ID별 독립 테스트

- DB 상태, 작업 디렉터리, 임시 파일, 캐시 키를 실행 ID마다 따로 둡니다. 함께 고치는 상태는 없어야 합니다.
- 읽기만 하면 원본 DB를 그대로 쓰고, 쓰기가 있으면 일회용 복제본이나 롤백 트랜잭션을 씁니다.
- 격리를 보장할 수 없으면 원본 DB로 대신 돌리지 말고 실패시킵니다.
- 서로 독립이면 병렬로 돌릴 수 있어 속도 문제도 함께 풀립니다.

## 3. LLM의 성공 판정

LLM은 마지막에 씁니다.

1. 코드 검사(비용 없음): 종료 상태, 필수 Tool 호출, state 스키마, 에러, 쓰기 범위 이탈을 확인합니다. 여기서 걸리면 LLM은 부르지 않습니다.
2. LLM 판정: 결과가 의도에 맞는지처럼 코드로 가릴 수 없는 부분만 맡깁니다.

판정 LLM은 이렇게 씁니다.

- 전체 로그 대신 압축한 증거를 줍니다. Step별 상태, Tool 호출의 인자와 결과 요약, state 변화, 최종 산출물입니다.
- Agent가 "했다"고 한 말은 믿지 않습니다. 실제 DB와 파일 상태를 확인해 증거로 씁니다.
- 판정은 `{pass, 근거, 증거 참조}` 형식으로 받습니다. 서술만 받으면 비교하거나 집계하기 어렵습니다.
- 판정자는 실행 Agent와 컨텍스트를 나누고, 가능하면 다른 모델을 씁니다.
- 판정도 틀릴 수 있습니다. 정답을 아는 사례를 섞어 판정 정확도를 주기적으로 잽니다.

## 4. 속도와 비용

비싼 층일수록 덜 돌립니다.

| 층 | 방식 | 비용 | 실행 시점 |
|---|---|---|---|
| L0 | 정의 파일 검증 | 없음 | 변경할 때마다 |
| L1 | 스크립트 모델 또는 녹화한 LLM 응답 재생 | 없음 | 변경할 때마다 |
| L2 | Step 입력 스냅숏으로 해당 Agent만 실제 LLM 실행 | 작음 | 바뀐 Step만 |
| L3 | 전체 Workflow를 실제 LLM으로 실행하고 LLM이 판정 | 큼 | 릴리스 전, 야간 |

- 바뀐 정의의 영향을 받는 Workflow만 골라 돌립니다.
- 결과는 `hash(정의 + 입력 + 모델)`로 캐시합니다.
- 판정 LLM은 코드 검사를 통과했고 의미 판단이 필요할 때만 부릅니다.
- 실패한 Step만 다시 시험할 수 있어야 반복 비용이 줄어듭니다.

## 정하셔야 할 것

- 현장 점검을 고객에게 납품할지, 내부 도구로만 둘지

두 결정에 따라 L3와 현장 점검의 모양이 달라집니다.

## 답변

제 의견은 한 문장입니다.

**실행 한 건마다 격리된 환경에서 Workflow를 헤드리스로 돌리고, 코드로 먼저 걸러낸 뒤 통과한 것만 LLM이 판정하게 하자.**

예를 들어 "SM 요청을 처리하는 Workflow"를 시험한다면 이렇게 흘러갑니다.

1. 이 실행 ID 전용 DB 복제본과 작업 폴더를 만듭니다. 만들지 못하면 원본을 쓰지 않고 실패 처리합니다.
2. API로 Workflow를 실행합니다.
3. 코드가 검사합니다. 정상 종료했는지, 꼭 불러야 할 Tool을 불렀는지, 허용하지 않은 곳에 쓰지 않았는지 봅니다. 하나라도 어기면 여기서 실패입니다.
4. LLM이 판정합니다. 실행 기록 요약과 실제 DB·파일의 변화를 보고 "요청한 일이 해결됐는가"에 합격이나 불합격, 그 근거를 냅니다.
5. 복제본을 지웁니다.

네 가지 조건은 이렇게 풀립니다.

| 조건 | 제 선택 |
|---|---|
| 다양한 WAS/DB | 모든 조합을 시험하지 않습니다. 차이는 Tool 안에서 흡수하고, 고객 환경에서는 접속과 권한을 확인하는 짧은 점검만 따로 돌립니다. |
| 실행 ID별 독립 | DB와 파일을 실행마다 따로 둡니다. |
| LLM 성공 판정 | 판정하되 Agent의 말이 아니라 실제 결과를 증거로 줍니다. |
| 속도와 비용 | 평소에는 바뀐 Step만 시험하고, 전체 Workflow는 릴리스 전에만 돌립니다. |

앞에서 여쭌 두 가지에 대한 제 생각도 말씀드리겠습니다.

- **판정 모델**: 일단 실행 모델을 그대로 쓰되 컨텍스트는 분리합니다. 정답을 아는 사례로 재 봐서 자주 틀리면 그때 별도 모델을 둡니다.
- **현장 점검**: 납품 기능에 넣습니다. 고객 환경이 제각각이라 설치할 때와 장애가 났을 때 가장 먼저 필요합니다.

이 중에 동의하기 어렵거나 더 구체적으로 듣고 싶은 부분이 있으면 말씀해 주세요.

## 가능합니다

WAS 쪽은 제안하신 방식이 그대로 되고 가볍기도 합니다. 손봐야 할 곳은 DB 원복입니다.

## WAS

| 항목 | 판단 | 주의할 점 |
|---|---|---|
| Tomcat으로 전환 | 조건부 가능 | 아래 참고 |
| overlay와 CATALINA_BASE 분리 | 가능 | Tomcat `PreResources`로 원본 위에 변경분만 얹습니다. 포트는 실행마다 다르게 줍니다. |
| 바뀐 것만 컴파일 | 가능 | 아래 참고 |
| 즉시 반영과 context reload | 가능 | JSP와 정적 파일은 즉시 반영하고, class·설정·Mapper XML은 reload합니다. |

**Tomcat 전환**

- 원본 소스는 고치지 않고, 전환 설정은 CATALINA_BASE와 overlay에만 둡니다.
- Tomcat 버전은 소스에 맞춥니다(`javax`는 9, `jakarta`는 10 이상).
- EJB 말고도 WAS 전용 API, JTA/XA, JMS를 쓰면 안 돌 수 있습니다. 시작 전에 검사해 "시험 불가"를 먼저 알려야 합니다.
- 기동할 때 도는 배치·스케줄러와 외부 연계는 꺼야 합니다. 그대로 두면 시험 서버가 개발 DB나 외부 시스템을 건드립니다.
- Tomcat에서 통과해도 운영 WAS에서의 동작까지 보장하지는 않습니다. 결과에 이 점을 적어야 합니다.

**컴파일**

- 상수는 호출하는 class에 값이 복사되어 bytecode만으로는 역참조를 찾지 못합니다.
- 그래서 역참조를 계산하지 말고, 시그니처나 상수가 바뀌면 **전체를 컴파일해 달라진 class만 overlay에 넣는** 쪽을 권합니다. 더 단순하고 빠뜨릴 일이 없습니다. 전체 컴파일이 너무 느린 현장에서만 역참조 방식을 검토하면 됩니다.
- 삭제한 class는 overlay로 지울 수 없으니 따로 처리해야 합니다.

**JVM**: 실행당 한 번 띄우는 것을 원칙으로 하고, reload가 실패하거나 메모리가 샐 때만 예외로 재기동을 허용해야 합니다.

## DB

개발 DB를 여럿이 같이 쓰면 "나중에 원복"은 보장하기 어렵습니다. 시험 중에 프로세스가 죽거나 다른 사람이 같은 행을 고치면 되돌릴 수 없고, DDL과 시퀀스 증가, 프로시저 안의 COMMIT도 남습니다.

그래서 **원복하지 말고 애초에 commit하지 않는 방식**을 권합니다.

- Tomcat의 DataSource를 감싸 `commit`을 막고, 시험 시나리오가 끝날 때마다 rollback합니다. 프로세스가 죽어도 DB가 알아서 되돌립니다.
- 결과 확인은 rollback 전에 같은 연결로 조회합니다.
- 잠금이 걸리므로 시나리오를 짧게 끊고, 같은 DB에 쓰는 시험은 한 번에 하나만 돌립니다.
- DDL이나 자체 COMMIT처럼 막을 수 없는 작업이 있으면 실행하지 않고 논리 검토로 넘깁니다.

DB가 없을 때의 논리 검토는 좋습니다. 다만 결과는 합격이 아니라 **"미실측"** 으로 구분해야 합니다. 기동할 때 DB를 읽는 앱은 DB 없이 서버가 아예 뜨지 않을 수도 있습니다.

## 먼저 확인할 것

저장소 규칙에는 "자동 쓰기 시험은 일회용 복제본에서만 한다"고 되어 있습니다. 개발 DB에 직접 시험하려면 이 규칙을 바꿔야 합니다. **commit을 막는 조건으로 개발 DB를 허용**하는 쪽을 추천하는데, 괜찮으신가요?
