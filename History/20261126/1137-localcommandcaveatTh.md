## 답변

# dstone-ai-engine 테스트 방식에 대한 의견

기존 구현은 보지 않고, 말씀하신 네 가지 조건만으로 설계한다고 가정했습니다.

## 핵심 방향

**테스트 단위를 "실행 한 건(executionId)"으로 잡고, 판정은 실행 후에 모은 증거 묶음으로 합니다.** 테스트 한 건은 다음 네 가지로 구성합니다.

- 입력
- 사전 상태(fixture)
- 기대 기준(rubric)
- 실행 결과에서 모은 증거

테스트는 헤드리스 API를 호출한 뒤 판정하는 구조로 만들고, WAS와 DB는 그 바깥에서 갈아 끼웁니다.

## 조건별 의견

### 1. WAS/DB가 고객마다 다르다

엔진 자체를 모든 WAS×DB 조합으로 테스트하려 하지 않는 편이 좋습니다. 대신 두 층으로 나눕니다.

- **엔진 계약 테스트**: 우리 환경에서 고정 조건으로 돌립니다. 엔진과 Workflow 논리를 확인하며 DB 종류와는 무관합니다.
- **현장 점검(probe)**: 고객 환경에서 몇 분 안에 끝나는 작은 점검입니다. DB 방언, 접속, 권한, 대상 앱 호출 가능 여부를 Tool로 확인하고 환경 정보를 결과에 남깁니다. 환경 차이는 이 점검에서 걸러내고, 엔진 테스트에는 끌어들이지 않습니다.

환경 차이는 Tool 경계(DB Tool, HTTP Tool 등)에서 모두 흡수되어야 합니다. Workflow 테스트가 DB 종류를 알아야 한다면 설계가 새고 있다는 신호입니다.

### 2. 실행 ID별로 독립 테스트

- 실행 ID마다 DB 상태, 작업 디렉터리, 임시 파일, 캐시 키를 별도로 가집니다. 공유 가변 상태는 없어야 합니다.
- DB는 **읽기 전용이면 그대로 쓰고, 쓰기가 있으면 일회용 복제본이나 롤백되는 트랜잭션**을 씁니다.
- 격리가 보장되지 않으면 원본 DB로 대신 돌리지 말고 **실패시킵니다.**
- 병렬 실행이 가능해야 속도 조건도 같이 풀립니다. 독립성이 곧 병렬성입니다.

### 3. LLM이 헤드리스 결과를 보고 성공 여부를 판단

**LLM 판정은 마지막 단계로 두고, 앞에 결정적 검사를 둡니다.**

1. **결정적 검사 (비용 0)**: 종료 상태, 필수 Tool 호출 여부, state 스키마, 에러 유무, 금지 동작(쓰기 범위 이탈) 여부를 확인합니다. 여기서 실패하면 LLM을 부르지 않습니다.
2. **LLM 판정**: "결과가 의도에 맞는가" 같은 의미적 부분만 맡깁니다.

판정 LLM에는 다음 원칙을 적용합니다.

- 전체 로그가 아니라 **압축한 증거 묶음**(Step별 상태, Tool 호출과 인자·결과 요약, state 변화, 최종 산출물)을 줍니다.
- Agent가 "했다"고 말한 내용은 믿지 않고 **실제 DB·파일 상태로 교차 확인**한 값을 증거로 씁니다.
- 판정은 `{pass, 근거, 증거 참조}` 구조로 받습니다. 자유 서술만 받으면 비교와 집계가 안 됩니다.
- 판정자는 실행 Agent와 컨텍스트를 분리하고, 가능하면 다른 모델을 씁니다.
- 판정 자체도 흔들립니다. **정답·오답을 알고 있는 사례를 섞어서 판정자의 정확도를 주기적으로 측정**해야 합니다.

### 4. 속도와 비용

테스트를 층으로 나눠 비싼 층일수록 적게 돌립니다.

| 층 | 방식 | 비용 | 실행 빈도 |
|---|---|---|---|
| L0 | 정의 파일 정적 검증 | 0 | 매 변경 |
| L1 | 스크립트된 모델 또는 녹화 재생(실제 LLM 응답을 한 번 녹화해 재생) | 0 | 매 변경 |
| L2 | **Step 단위** 실제 LLM 시험(Step 입력 스냅숏만 넣고 그 Agent만 실행) | 소 | 변경된 Step만 |
| L3 | 전체 Workflow 실제 LLM + LLM 판정 | 대 | 릴리스 전, 야간 |

- 변경된 정의에 영향받는 Workflow만 선택해서 돌립니다.
- 결과는 `hash(정의 + 입력 + 모델)`로 캐시합니다.
- 판정 LLM은 결정적 검사를 통과했고 의미 판단이 필요한 경우에만 부릅니다.
- 전체 Workflow가 아니라 **실패한 Step만 재시험**할 수 있어야 반복 비용이 줄어듭니다.

## 정리하면

핵심은 "결정적으로 확인할 수 있는 것은 LLM에 맡기지 않는 것"입니다. 환경 다양성은 현장 점검과 Tool 경계에서 처리하고, 독립성은 실행 ID 단위 격리로 확보하며, LLM 판정은 압축된 증거 위에서 의미 판단만 합니다. 비용은 층을 나누는 것으로 조절합니다.

## 정하셔야 할 것

- 판정 LLM을 실행 모델과 같은 것(폐쇄망 POC라면 qwen 하나뿐일 수 있음)으로 쓸지, 별도 모델을 둘지
- 현장 점검을 고객에게 납품하는 기능으로 삼을지, 우리 내부 도구로만 둘지

이 두 가지에 따라 L3와 현장 점검의 모양이 달라집니다.
