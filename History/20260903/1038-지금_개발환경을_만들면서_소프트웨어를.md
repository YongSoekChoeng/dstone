## 전체 방향에 대한 의견

말씀하신 접근 방식(MySQL/RabbitMQ/Redis/Kafka = CSP 매니지드 서비스로 간주, dstone-boot = K8s Pod, dstone-batch/batchadmin = VM)은 실제 클라우드 아키텍처와 매핑이 잘 되는 좋은 설계라고 생각한다. 정리하면 이렇게 대응된다.

| dstone 구성요소 | 클라우드 유사 개념 | WSL 구현 |
|---|---|---|
| MySQL/Redis/RabbitMQ/Kafka | RDS / ElastiCache / Amazon MQ / MSK (매니지드) | 기존 설치된 서비스 그대로, k8s 클러스터 **바깥**에서 네트워크로만 접근 |
| dstone-boot | EKS/GKE 위 Deployment (stateless 웹 티어) | kind 클러스터에 Pod로 배포 |
| dstone-batch | EC2 (배치 워커 VM) | systemd 서비스로 상주 |
| dstone-batchadmin | EC2 (배치 관제/스케줄러 VM) | systemd 서비스로 상주, batch에 REST 호출 |
| Jenkins | 자체 관리형 CI 서버(EC2/VM에 상주) | 지금처럼 WSL에 그대로 두는 것이 맞음 (아래 설명) |

## Jenkins를 온프레미스(VM)에 두는 게 맞는가?

맞다. 실제로도 이게 표준 패턴이다.
- **Jenkins Controller(마스터)**는 `JENKINS_HOME`에 잡 설정/빌드 이력/크리덴셜이 영구 저장돼야 해서, K8s의 일회성 Pod보다는 **영속 스토리지가 있는 VM(EC2)** 에 두는 게 일반적이다. 클라우드에서도 Jenkins를 "서버리스"로 굴리는 경우는 드물다.
- 반면 **Jenkins Agent(빌드 실행기)**는 Kubernetes Plugin을 붙여서 빌드마다 kind 클러스터에 임시 Pod로 띄웠다가 끝나면 없애는 방식이 요즘 클라우드 네이티브 패턴이다(오토스케일 빌드 인프라 흉내).

즉 지금 구조(WSL의 VM 성격 호스트에 Jenkins Controller)는 그대로 두고, 여유가 되면 나중에 Kubernetes Plugin으로 에이전트만 kind 안에 넣는 식으로 발전시키면 된다.

## CI/CD 파이프라인 구성안

```
checkout
 └─ mvn -pl dstone-common clean install     (공통 의존성 먼저)
 └─ [dstone-boot]
     mvn -pl dstone-boot clean package
     docker build (multi-stage) → 로컬/사설 레지스트리 push
     kubectl apply / kubectl set image  (kind 컨텍스트)
     헬스체크 (actuator 등으로 스모크 테스트)
 └─ [dstone-batch]
     mvn -pl dstone-batch clean package
     scp/rsync 로 배치 "VM"에 jar 복사
     ssh로 systemd 서비스 재시작 (stop → 교체 → start)
     헬스체크
 └─ [dstone-batchadmin]
     동일 패턴 (WAR + systemd or 내장 톰캣)
```

`dstone-boot`은 이미지 빌드→레지스트리→`kubectl` 배포 흐름(ECR→EKS 흐름과 동일), `dstone-batch`/`dstone-batchadmin`은 아티팩트 배포+SSH 방식(SSM/CodeDeploy 흐름과 유사)으로 파이프라인 자체가 갈라지는 게 핵심 포인트다. Jenkins Credentials에 SSH 키·레지스트리 인증·DB 비번을 등록해서 쓰면 Secrets Manager를 흉내낼 수 있다.
