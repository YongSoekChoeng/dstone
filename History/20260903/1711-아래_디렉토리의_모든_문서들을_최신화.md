원인을 찾았습니다. **Redis의 `protected-mode` 때문**입니다.

**진단 결과:**
- Redis는 문서(`cloud-architecture.md`)대로 `172.18.0.1:6379`에 정상적으로 바인딩되어 있고, Pod(`10.244.0.5`)→Redis TCP 연결 자체는 성공합니다.
- 하지만 Redis가 응답한 실제 에러는:
  ```
  -DENIED Redis is running in protected mode because protected mode is enabled 
  and no password is set for the default user. In this mode connections are only 
  accepted from the loopback interface...
  ```
  즉 `bind`로 IP를 열어놨어도, Redis 자체의 `protected-mode`가 "loopback이 아닌 곳에서 온 연결"을 비밀번호 없이는 거부하고 있습니다.
- 참고로 MySQL(`3306`)은 같은 방식으로 테스트해보니 정상 연결됩니다 — Redis만의 문제입니다.

**해결 방법**: WSL에는 sudo 접근 권한이 없어 제가 직접 고칠 수 없습니다. 아래 명령을 직접 실행해주세요 (`!` 접두사로 이 세션에서 실행 가능):

```bash
sudo sed -i 's/^protected-mode yes/protected-mode no/' /etc/redis/redis.conf
sudo systemctl restart redis-server
```

`cloud-architecture.md`에 이미 기술된 설계 의도(“kind 네트워크에서만 추가로 열어주고 그 외 인터페이스로는 노출하지 않는다”, `bind-address`를 이용한 접근범위 제한)를 실제 보안 경계로 삼고 있으므로, `protected-mode`는 비활성화해도 설계상 문제 없습니다(bind로 이미 kind 브리지 대역으로만 제한돼 있음).

적용 후 확인 방법:

## 답변

`kind-registry`는 표준 **Docker Registry v2**(`registry:2` 이미지 그대로, Docker Hub/ECR/GCR을 구성하는 것과 동일한 오픈소스 컴포넌트)를 로컬에 하나 띄운 것입니다. 이 프로젝트에서 하는 정확한 역할은 **"`docker build`로 만든 이미지를 kind 클러스터의 Pod가 실제로 pull해갈 수 있게 중계하는 사설 이미지 저장소"** 입니다 — 클라우드였다면 ECR/GCR이 하던 일을 대신합니다.

**동작 원리 (지금 실제로 확인한 구성):**

1. **저장소 역할**: `docker push localhost:5000/dstone-boot:<tag>`로 push하면 이 컨테이너에 이미지 레이어/매니페스트가 저장됩니다. (`GET /v2/_catalog` 같은 레지스트리 API로 조회 가능 — 지금 안에는 `dstone-boot`의 `latest`/`kafka-fix` 두 태그만 있음)

2. **호스트 접근용 포트 매핑**: `docker run -p 127.0.0.1:5000:5000 ... registry:2`로 떠 있어서, WSL 호스트에서 `docker push/pull localhost:5000/...`가 직접 됩니다.

3. **kind 네트워크에 연결**: `kind-registry`(`172.18.0.3`)가 `dev-control-plane`(`172.18.0.2`)과 같은 `kind` 도커 브리지 네트워크에 연결돼 있어서, 클러스터 노드 컨테이너가 `kind-registry:5000`이라는 이름으로 이 레지스트리에 도달할 수 있습니다.

4. **containerd 미러 설정 (핵심)**: kind 노드 안의 `/etc/containerd/config.toml`에 아래처럼 미러 규칙이 박혀 있습니다:
   ```
   [plugins."io.containerd.grpc.v1.cri".registry.mirrors."localhost:5000"]
     endpoint = ["http://kind-registry:5000"]
   ```
   즉 Pod의 `image: localhost:5000/dstone-boot:...`를 노드가 그대로 해석하면 원래는 "노드 자기 자신의 5000번 포트"를 찾아야 하는데(실패), 이 미러 규칙 덕분에 containerd가 자동으로 `kind-registry:5000`(실제 레지스트리 컨테이너)으로 요청을 돌려줍니다. `kind create cluster` 시 `containerdConfigPatches`로 주입됩니다(`/usr/local/bin/k8s-start.sh` 안에 있음).

5. **실제 증거**: 방금 배포된 dstone-boot Pod의 `imageID`가 `localhost:5000/dstone-boot@sha256:...`로 찍혀 있어, 위 경로로 실제 pull이 일어났음을 확인했습니다.

**알아둘 점**: `-v`(볼륨) 없이 컨테이너 자체 writable layer에만 이미지를 저장하므로, `docker rm kind-registry`로 컨테이너를 지우면 그 안의 이미지도 전부 사라집니다(재시작만 하는 건 괜찮음). 인증도 없는 완전 오픈 상태라 dev 전용이고, UI는 없이 API만 있습니다(이전 답변 참고).
