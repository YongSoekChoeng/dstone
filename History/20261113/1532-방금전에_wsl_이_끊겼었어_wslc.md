# 방금전에_wsl_이_끊겼었어_wslc

> 생성일시: 2026-11-13 15:32

## 질문

방금전에 wsl 이 끊겼었어. .wslconfig 를 수정해서 다시 띄웠고. 지난 작업중에 미완된게 있나?

---

## 답변

미완된 작업은 없습니다. 마지막 기록까지 확인했습니다.

**끊기기 전 작업**
- 영향도 화면의 "부르는 쪽" 표 정리는 `7eba480c`로 커밋해서 푸시까지 마쳤습니다. 지금 로컬과 `origin/main`이 같고, 작업 트리에 바뀐 파일도 없습니다.
- 그 뒤 WSL이 끊긴 원인을 조사했습니다. WSL이 Windows 메모리 한도를 넘어서 끊긴 것으로 보고 `.wslconfig`를 고친 뒤 `wsl --shutdown`을 걸었는데, 이 세션은 여기서 끝났습니다.

**`.wslconfig` 반영 확인**
- `free -h`에서 메모리 총계가 **7.8Gi**로 나옵니다. `memory=8GB`가 적용됐습니다.
- 줄 끝에 있던 주석은 윗줄로 옮겨져 있습니다. 그래서 `autoMemoryReclaim=gradual`과 `sparseVhd=true`도 이제 제대로 적용될 것입니다.

**지금 떠 있는 것**
- MySQL(3306), PostgreSQL(5432), Redis(6379), Jenkins(8080), Kafka(9092)가 떠 있습니다.
- dstone 앱(4081, 7081, 8081)은 하나도 떠 있지 않습니다.

**남은 일** (원래 직접 하시기로 한 부분)
1. Windows 쪽 클론에서 `git pull`을 받습니다.
2. dstone-knowledge와 dstone-boot를 다시 빌드해서 띄웁니다.
3. testApp을 다시 분석합니다. 분석기 버전을 1.3으로 올려서, 증분 분석으로 요청해도 전체 분석으로 돕니다.

WSL 쪽 앱이 필요하면 말씀해 주세요. `bin/startApps.sh`로 띄우겠습니다. WSL 메모리를 8GB로 줄였으니 kind 클러스터까지 모두 띄울 때 메모리가 모자라지 않은지도 함께 보겠습니다.

## 답변

지금은 안정적이지만 여유가 거의 없습니다. 15:31에 확인한 값입니다.

**한눈에 보기**

| 항목 | 지금 | 판단 |
|---|---|---|
| Windows 커밋 | 35.4 / 40.5GB (87%) | 남은 여유 약 5GB |
| WSL 커밋(vmmemWSL) | 8.05GB | 8GB 한도에 도달 |
| WSL 안 가용 메모리 | 546Mi, 스왑 922Mi 사용 | 꽉 참 |
| 메모리 압박(PSI) | avg60 0.12%, avg300 0.14% | 대기는 거의 없음 |
| CPU | 98% 유휴 (부하 5.3은 앱 기동 직후 값) | 여유 있음 |
| OOM·hang 로그 | 없음 | 문제 없음 |
| Windows 메모리 부족 경고 | 재기동 뒤로는 없음 (마지막은 15:16, 재기동 전) | 문제 없음 |

**좋아진 점**
- 전에는 WSL이 12GB까지 커져서 Windows 커밋 한도를 넘었고, 그때 VM이 끊겼습니다. 지금은 WSL이 8GB에서 멈춥니다. 그래서 WSL 안에서 메모리가 모자라도 VM이 끊기지 않고 스왑을 쓰거나, 최악의 경우 리눅스 OOM으로 프로세스 하나만 죽습니다.
- Oracle XE가 내려가 있고 Eclipse도 하나만 떠 있습니다.

**WSL 안에서 메모리를 많이 쓰는 프로세스** (RSS 기준)
1. Ollama `bge-m3` 임베딩 모델: **2.4GB**. 앱을 띄울 때 dstone-knowledge가 임베딩을 돌리면서 올라왔습니다. 15:36에 keep-alive가 끝나면 메모리를 돌려줍니다.
2. dstone-boot, dstone-knowledge, dstone-ai-engine: 각각 0.9, 0.87, 0.68GB입니다. `-Xmx1024m`이라서 더 커질 수 있습니다.
3. MySQL 0.47GB, Jenkins 0.34GB, Kafka 0.33GB(`-Xms1G`라서 1GB까지 큽니다), Kafbat UI 0.17GB, RabbitMQ 0.11GB, Ollama WebUI 0.11GB입니다.

**남아 있는 위험**
- **WSL 안:** 분석하면서 임베딩을 돌리면 Ollama 2.4GB와 앱 세 개의 힙이 한꺼번에 커집니다. 그러면 스왑을 많이 쓰면서 느려지고, 심하면 OOM으로 프로세스 하나가 죽을 수 있습니다. VM이 끊기지는 않습니다.
- **Windows 쪽:** 남은 여유는 약 5GB입니다. Chrome(탭 30개, 커밋 4GB)이 늘거나 Eclipse·Oracle XE를 더 띄우면 다시 한도에 가까워집니다.
- **kind 클러스터:** Docker가 꺼져 있어서 지금은 kind가 떠 있지 않습니다. 지금 구성에 kind까지 띄우면 8GB로는 모자랍니다.

**권장** (필요하면 바로 진행하겠습니다)
1. 지금 안 쓰는 Jenkins, Kafka와 Kafbat UI, Ollama WebUI(3000)를 내립니다. 1~2GB 정도 확보됩니다.
2. 앱 세 개의 힙을 `-Xmx768m` 정도로 낮출지 검토합니다. 실제 사용량을 본 다음에 정하겠습니다.
3. Windows에서 쓰지 않는 Chrome 탭을 정리합니다.

분석이 끝날 때까지 상태를 주기적으로 봐 드릴까요? 스왑이나 Windows 커밋이 위험한 수준까지 오르면 알려 드리겠습니다.
