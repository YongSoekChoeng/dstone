## 답변

미완된 작업은 없습니다. 마지막 기록까지 확인했습니다.

**끊기기 전 작업**
- 영향도 화면의 "부르는 쪽" 표 정리는 `7eba480c`로 커밋해서 푸시까지 마쳤습니다. 지금 로컬과 `origin/main`이 같고, 작업 트리에 바뀐 파일도 없습니다.
- 그 뒤 WSL이 끊긴 원인을 조사했습니다. WSL이 Windows 메모리 한도를 넘어서 끊긴 것으로 보고 `.wslconfig`를 고친 뒤 `wsl --shutdown`을 걸었는데, 이 세션은 여기서 끝났습니다.

**`.wslconfig` 반영 확인**
- `free -h`에서 메모리 총계가 **7.8Gi**로 나옵니다. `memory=8GB`가 적용됐습니다.
- 줄 끝에 있던 주석은 윗줄로 옮겨져 있습니다. 그래서 `autoMemoryReclaim=gradual`과 `sparseVhd=true`도 이제 제대로 적용될 것입니다.

**지금 떠 있는 것**
- MySQL(3306), PostgreSQL(5432), Redis(6379), Jenkins(8080), Kafka(9092)가 떠 있습니다.
- dstone 앱(4081, 7081, 8081)은 하나도 떠 있지 않습니다.

**남은 일** (원래 직접 하시기로 한 부분)
1. Windows 쪽 클론에서 `git pull`을 받습니다.
2. dstone-knowledge와 dstone-boot를 다시 빌드해서 띄웁니다.
3. testApp을 다시 분석합니다. 분석기 버전을 1.3으로 올려서, 증분 분석으로 요청해도 전체 분석으로 돕니다.

WSL 쪽 앱이 필요하면 말씀해 주세요. `bin/startApps.sh`로 띄우겠습니다. WSL 메모리를 8GB로 줄였으니 kind 클러스터까지 모두 띄울 때 메모리가 모자라지 않은지도 함께 보겠습니다.

## 지금 화면의 문제

1. **공통 설정이 아래 칸에 있습니다.** 프로젝트와 리비전은 아래쪽 "영향도 분석" 칸에 있는데, 위쪽 "호출 관계"도 이 값을 씁니다. 그래서 위에서 검색하려면 먼저 아래로 내려가 프로젝트를 골라야 합니다.
2. **안내문과 실제 배치가 반대입니다.** "이렇게 씁니다"에는 "위 칸(영향도 분석)", "아래 칸(호출 관계)"이라고 적혀 있는데, 실제 화면에서는 호출 관계가 위에 있습니다.
3. **대상을 고르는 곳이 두 군데입니다.** 영향도는 대상 칸에 직접 입력하고, 호출 관계는 메소드나 테이블을 찾아서 고릅니다. 위에서 [영향도]나 테이블 이름을 누르면 결과가 아래 칸에 나오고 화면이 아래로 내려갑니다. 사용자는 지금 무엇을 보고 있는지 놓치기 쉽습니다.
4. **결과끼리 이어지지 않습니다.** "부르는 쪽" 결과와 영향도 결과가 각자 다른 자리에 쌓입니다. 영향도의 메소드 표에서 그 메소드의 부르는 쪽을 바로 볼 수도 없습니다.
5. **같은 개념을 다르게 보여 줍니다.**
   - 깊이 입력이 두 개입니다("따라갈 깊이" 2, "깊이" 5).
   - 부르는 쪽 표는 `CommonCodeController#get(…)`처럼 짧은 이름과 한글 관계를 쓰지만, 영향도 표는 전체 이름과 `REQUESTS/RENDERS/CALLS` 같은 원문을 씁니다.

## 개선 방향: 대상 하나 → 결과 탭 셋

화면을 **"대상을 고른다 → 그 대상에 대한 결과를 탭으로 본다"** 한 흐름으로 합칩니다.

```
┌ 프로젝트 [testApp ▾]  리비전 [#127 2026-11-13 ▾] ─────────────┐   ← 맨 위, 화면 전체에 적용
├ ① 대상 찾기 ───────────────────────────────────────────────┤
│ [메소드 ▾] [getCommonCodeService      ] (타입 일부: [     ]) [찾기] │
│  후보 목록: BaseController#getCommonCodeService()  base/…:38  [선택] │
├ ② 선택한 대상 ─────────────────────────────────────────────┤
│ [메소드] BaseController#getCommonCodeService() 을(를) 고치면       │
│          kr.co.gnx.base.BaseController · BaseController.java:38 · 계층 │
│  경로: TB_CODE › CodeDao#select… › BaseController#getCommon…  ← 지나온 대상 │
├ ③ [영향도 12] [부르는 쪽 30] [불리는 쪽 8] ───── 깊이 [5] ──────┤
│  (선택한 탭의 결과)                                             │
└──────────────────────────────────────────────────────────────┘
```

- **① 대상 찾기:** 종류(메소드/테이블/SQL/타입)와 이름을 입력하는 칸을 하나로 합칩니다. 메소드와 테이블은 지금 있는 검색 API로 후보 목록을 보여 줍니다. SQL과 타입은 검색 API가 없으므로 지금처럼 정확한 이름을 입력하면 바로 대상으로 정합니다.
- **② 대상 카드:** 지금의 "○○을(를) 고치면" 머리글을 탭 위에 한 번만 보여 줍니다. 세 탭이 모두 이 대상에 대한 결과라는 점이 바로 보입니다.
- **③ 탭:**
  - **영향도:** 요약 카드, 진입점, 화면, 메소드 표. 대상이 테이블이면 읽기/쓰기 필터가 이 탭에만 나옵니다.
  - **부르는 쪽 / 불리는 쪽:** 메소드일 때만 쓸 수 있습니다. 테이블이나 SQL이면 탭을 흐리게 하고, 그 이유를 툴팁으로 보여 줍니다.
  - 깊이 입력은 탭 막대에 하나만 둡니다. 기본값은 탭마다 다르게(영향도 5, 호출 2) 두고, 값을 바꾸면 결과를 다시 불러옵니다.
  - 탭 이름의 건수는 결과를 불러온 탭만 보여 줍니다.
- **결과에서 바로 다음 대상으로:** 영향도와 부르는/불리는 쪽 표에 나온 메소드 이름을 누르면 그 메소드가 새 대상이 됩니다. 지나온 대상은 ②의 "경로"에 남고, 누르면 그 대상으로 돌아갑니다. 테이블 이름을 누를 때도 같습니다.
- **표기 통일:** 영향도 표도 부르는 쪽 표와 같은 형식(짧은 이름 + 툴팁, 한글 관계 이름, `파일:줄` 근거)으로 바꿉니다. 길게 쓴 섹션 제목의 설명은 "이렇게 씁니다"와 툴팁으로 옮깁니다.
- **주소창 보존:** 프로젝트, 리비전, 대상, 탭을 URL 해시에 저장합니다. 새로고침이나 뒤로 가기를 해도 같은 화면이 나오고, 링크를 다른 사람에게 전달할 수도 있습니다.

  - 메소드는 `BoardDAO#deleteBoard`처럼 타입까지 적어서 좁힐 수 있습니다.
- **② 결과:** 맨 위에 "○○을(를) 고치면" 머리글이 한 번 나오고, 그 아래 탭 세 개(영향도, 부르는 쪽, 불리는 쪽)가 모두 이 대상에 대한 결과입니다.
  - 부르는 쪽과 불리는 쪽 탭은 대상이 메소드일 때만 쓸 수 있습니다. 다른 종류일 때는 흐리게 표시되고, 마우스를 올리면 이유가 나옵니다.
  - 깊이 칸은 하나만 두었습니다. 기본값은 영향도 탭이 5, 호출 관계 탭이 2입니다.
- **결과에서 바로 다음 대상으로:** 결과 표에 나온 메소드, SQL, 테이블 이름을 누르면 그것이 새 대상이 됩니다. 지나온 대상은 "지나온 대상" 줄에 남고, 누르면 그 대상으로 돌아갑니다.
- **표기 통일:** 영향도 표도 부르는 쪽 표와 같은 형식(짧은 이름, 한글 관계 이름, `파일:줄`)으로 바꿨습니다.
- **주소창 보존:** 새로 고침이나 브라우저 뒤로 가기를 해도 같은 화면이 나오고, 지금 보는 화면을 링크로 전달할 수 있습니다.
- **안내 반영:** "이렇게 씁니다", 사용 안내의 따라 하기 ③④, 문서(`docs/11` 4.1절, `.claude/docs/knowledge-ui.md`)를 새 화면에 맞게 고쳤습니다.

**dstone-knowledge는 바꾸지 않았습니다.** SQL 검색(`/mappers`)과 타입 검색(`/symbols`) API가 이미 있었습니다. 그래서 다시 빌드할 것은 dstone-boot 하나뿐입니다.

**확인한 것**
- WSL 메모리가 빠듯해서 dstone-boot를 하나 더 띄우지 않았습니다. 대신 정적 파일을 내주고 실제 4081 API로 요청을 넘기는 시험 서버를 만들어 헤드리스 크롬으로 시험했습니다.
- 시험한 흐름은 메소드 찾기와 자동 선택, 탭 전환, 깊이 변경, SQL과 메소드 링크로 대상 바꾸기, 지나온 대상으로 돌아가기, 뒤로 가기, 새로 고침, 테이블의 읽기/쓰기 필터입니다. 모두 동작했고 콘솔 오류도 없었습니다.
- 시험하면서 문제 세 가지를 찾아 고쳤습니다. 대상을 바꿔도 탭에 이전 건수가 남는 것, 지나온 대상으로 돌아갈 때 방금 보던 대상이 다시 쌓이는 것, 정확한 이름을 적어도 바로 골라지지 않는 것입니다.
- 1150px와 390px 너비에서 화면을 찍어 봤습니다. 좁은 화면에서 표가 찌그러지던 문제는 표 안에서만 가로로 스크롤되게 고쳤고, 페이지 전체에는 가로 스크롤이 생기지 않습니다.
- **보지 않은 것:** 로그인한 실제 dstone-boot 화면에서는 아직 보지 않았습니다. 시험 서버로 본 화면에는 왼쪽 메뉴가 없습니다.

지금 7081에 떠 있는 dstone-boot는 고치기 전 빌드라서, 바뀐 화면을 보려면 dstone-boot를 다시 빌드해서 띄워야 합니다. Windows 쪽에서 보신다면 먼저 `git pull`을 받으세요. WSL 쪽에서 띄우기를 원하시면 말씀해 주세요.
