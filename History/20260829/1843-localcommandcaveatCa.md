## 질문

현재 dstone 프레임워크 구조에서 메소드 호출 시 로그가 남게 되어있는데 특정한 메소드(특히 polling 형식)에 대해서만 남지 않게 하려면 어떻게 해야 할까?
net.dstone.boot.common.config.ConfigAspect 에서 하드코딩 해야하나?
그리고 쿼리로그도 같이 적용하고 싶은데... 어떤 방법이 가장 효과적일까?

## 답변

현재 구조를 보면 두 로깅이 완전히 다른 메커니즘이라 접근법을 나눠야 합니다.

## 1. 메소드 호출 로그 (ConfigAspect)

`if(methodName.equals("poll..."))` 식으로 Aspect 안에 하드코딩하는 건 피하는 게 좋습니다 — 폴링 메소드가 늘어날 때마다 공통 모듈(`dstone-boot`/`dstone-batchadmin` `ConfigAspect.java`)을 계속 고쳐야 하고, 어떤 메소드가 로그에서 빠지는지 Aspect 코드를 열어보지 않으면 알 수 없습니다.

대신 **커스텀 어노테이션 + 포인트컷 제외**가 이 구조에 가장 자연스럽습니다:

```java
// dstone-common
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface NoAspectLog {}
```

```java
@Around("execution(* net.dstone.*..*Service*.*(..)) && !@annotation(net.dstone.common.config.NoAspectLog)")
public Object doServiceProfiling(ProceedingJoinPoint joinPoint) throws Throwable { ... }
```

Dao도 동일하게. 폴링 메소드 쪽에 `@NoAspectLog` 한 줄만 붙이면 되고, Aspect 자체는 한 번만 수정하면 끝입니다. 이 방식이면 앞으로 "이 메소드도 로그 빼주세요" 요청이 와도 Aspect를 다시 안 건드려도 됩니다.

## 2. 쿼리 로그 (log4jdbc)

여기가 까다로운 지점인데, 지금 `conf/log4j2.xml`을 보면 SQL 타이밍 로그는 `jdbc.sqltiming` 로거 하나가 전역으로 INFO를 찍고 있습니다. log4jdbc는 로거 단위 on/off만 지원하고 **SQL문/호출 메소드 단위 필터링 기능이 없어서**, 애노테이션만으로는 쿼리 로그를 못 끕니다.

가장 효과적인 방법은 위 애노테이션과 **MDC(ThreadContext)를 연결**하는 것입니다:

1. `ConfigAspect`의 Dao Around 어드바이스에서, 대상 메소드에 `@NoAspectLog`가 붙어 있으면 `proceed()` 전후로 `ThreadContext.put("SUPPRESS_SQL_LOG", "Y")` / `ThreadContext.remove(...)` (try-finally)
2. `log4j2.xml`의 `jdbc.sqltiming` Logger에 `ThreadContextMapFilter`를 붙여서 그 키가 "Y"면 DENY:

```xml
<Logger name="jdbc.sqltiming" level="INFO" additivity="false">
    <ThreadContextMapFilter onMatch="DENY" onMismatch="NEUTRAL">
        <KeyValuePair key="SUPPRESS_SQL_LOG" value="Y"/>
    </ThreadContextMapFilter>
    <AppenderRef ref="console"/>
    <AppenderRef ref="rollingFile"/>
</Logger>
```

이렇게 하면 커스텀 Filter 클래스도 필요 없고(log4j2 내장 기능), Dao 메소드 하나에 애노테이션 하나 붙이는 걸로 "메소드 호출 로그 + 그 안에서 나가는 쿼리 로그"가 동시에 꺼집니다 — 스위치가 하나라 관리 포인트도 하나입니다.

트레이드오프: MDC는 쓰레드 경계를 못 넘으므로, 폴링 메소드가 별도 쓰레드/비동기로 쿼리를 던지면(`@Async`, 별도 ExecutorService 등) 이 방식이 안 먹습니다. 그런 케이스가 있는지 알려주시면 그 부분도 반영해서 설계할게요.

원하시면 `dstone-common`에 어노테이션 추가하고 `dstone-boot`/`dstone-batchadmin`의 `ConfigAspect` 및 각 `log4j2.xml`에 반영하는 작업을 진행하겠습니다.
