## 답변

제안하신 방향에서 가장 좋은 부분은 **Agent가 자기 input/output 계약을 직접 갖는 것**입니다. 다만 몇 군데는 지금 구조와 겹치거나 모호합니다.

## 지금 이미 있는 것

| 제안 | 현재 코드 |
|---|---|
| workflow `input` + type | `workflow.inputs`가 이미 있습니다. 필드 이름 → 타입 형태이고, 실행 전에 검사해서 틀리면 400으로 거절합니다 (`WorkFlowDefinition.java`) |
| workflow `output` + type | `workflow.output`이 있지만 **타입이 아니라 템플릿**입니다 (예: `"{{steps.convert.output.sql}}"`) |
| step `output.type: object` + 스키마 | AGENT step의 `output`에 필드 맵을 적으면 LLM 답을 그 모양의 JSON으로 강제합니다 |
| agent `input`/`output` | **없습니다.** 새로 생기는 부분입니다 |

## 좋은 점: 출력 모양을 Agent가 갖는 것

- **프롬프트와 출력 모양은 원래 한 몸입니다.** 예시의 `testApp-analysis-agent` 프롬프트는 "응답 전체가 곧 분석/설계서"라고 되어 있는데, step에서 `output: object`를 강제하면 둘이 부딪힙니다. 스키마가 Agent YAML에 같이 있으면 이런 불일치가 한눈에 보입니다.
- **재사용이 쉬워집니다.** 같은 Agent를 쓰는 step마다 `output`을 다시 적을 필요가 없습니다. `/api/ai/chat`으로 Agent를 직접 부를 때도 구조화된 답을 받을 수 있습니다.
- **기동 시 검증이 더 강해집니다.** `{{steps.analyze.output.name}}` 같은 참조를 `WorkFlowRegistry`가 ref로 연결된 Agent의 스키마와 대조해서, 없는 필드면 부팅 단계에서 실패시킬 수 있습니다.

## 바꾸는 게 좋을 부분

1. **step에서 input/output `type`을 또 적는 건 중복입니다.** Agent가 계약을 가지면 step은 "무엇을 넣을지"(input 템플릿)와 흐름(onSuccess/onFailure)만 적으면 됩니다. 양쪽에 다 적게 하면 서로 어긋나는 경우가 반드시 생깁니다. 계약은 Agent 한 곳에만 두는 걸 권합니다.

2. **참조는 Agent id가 아니라 step id로 해야 합니다.** `testApp-analysis-agent.output.User.name`은 같은 Agent를 두 step에서 쓰거나 루프로 다시 돌면 어느 실행 결과인지 알 수 없습니다. 지금처럼 `{{steps.analyze.output.name}}`이 맞습니다. 스키마의 `title`("User")은 경로에 들어가지 않고, 문장 속에 섞어 쓰려면 `{{ }}`로 구분해야 합니다.

3. **workflow `output`에는 타입 말고 "값을 어디서 가져올지"도 필요합니다.** 제안대로 타입과 스키마만 있으면 어느 step의 결과를 최종 결과로 쓸지 알 방법이 없습니다. `value`(지금의 템플릿)와 `schema`(선택)를 함께 두는 형태를 권합니다.

4. **JSON Schema를 `|` 문자열로 넣지 말고 YAML로 바로 쓰는 게 낫습니다.** JSON Schema는 YAML로 그대로 표현할 수 있습니다. 문자열로 넣으면 들여쓰기나 쉼표 실수를 부팅 전에 잡기 어렵습니다. 대신 지금의 `FieldDefinition`(평평한 필드 + `list<T>`)으로는 중첩 객체, `minimum`, 선택 필드(`required`)를 표현할 수 없으니, 이 부분은 JSON Schema로 넓힐 가치가 있습니다. 간단한 경우를 위해 `name: string` 같은 축약형도 계속 허용하면 좋겠습니다.

5. **Agent `input`의 object 타입은 쓸모가 작습니다.** LLM에게 가는 건 결국 사용자 메시지 문자열 하나라서, object 입력도 JSON 문자열로 바꿔 보낼 뿐입니다. 선택 항목으로 두되 우선순위는 낮게 잡는 걸 권합니다.

## 정하실 것

1. **step의 `output`을 없애고 Agent 쪽으로 완전히 옮길까요?** 저는 완전히 옮기는 걸 권합니다. 샘플 YAML과 `docs/09`도 같이 고쳐야 합니다.
2. **스키마를 JSON Schema로 넓힐까요, 아니면 지금의 필드 맵을 유지할까요?** JSON Schema로 넓히면 값 검사에 json-schema-validator 같은 라이브러리가 하나 더 필요합니다.
3. **Agent `input` 스키마는 이번에 넣을까요, 미룰까요?**

정해 주시면 그대로 설계 문서와 구현에 반영하겠습니다.

## 1. `{{ }}`를 없애기 어려운 이유

`{{ }}`는 **글자 그대로의 문장과 참조를 구분하는 유일한 표시**라서 없애기 어렵습니다.

```yaml
input: "steps.analyze.output.name 에 대한 행동패턴을 분석해줘."
```

표시가 없으면 엔진은 `steps.analyze.output.name`이 참조인지, LLM에게 그대로 보낼 글자인지 알 수 없습니다. 다른 표시도 마땅치 않습니다.
- `${ }`는 이미 기동 시 환경변수 치환에 쓰고 있습니다.
- `$steps...`처럼 앞 기호만 붙이면 참조가 어디서 끝나는지 애매합니다.

그래서 `{{ }}`는 유지하는 걸 권합니다. 대신 **값 전체가 `{{ x }}` 하나뿐이면 원래 타입을 그대로 넘기는 규칙**(이미 `Template`에 있습니다)을 모든 곳에 똑같이 적용하겠습니다. 이렇게 하면 `value: "{{steps.analyze.output}}"`는 문자열로 바뀌지 않고 객체 그대로 전달됩니다.

## 2. 암묵적인 항목 정리

`text`와 같은 성격의 항목이 더 있습니다. 전부 정리하는 안입니다.

| 지금 | 바뀐 뒤 | 샘플 사용처 |
|---|---|---|
| `steps.x.text` | **삭제.** `steps.x.output` 하나로 통일합니다. Agent 출력이 string이면 output이 문자열이고, object면 객체입니다 | 7곳 |
| `inputs.message` (요청의 message가 자동으로 들어감) | **삭제.** workflow `input` 스키마가 정한 값만 들어옵니다 | 11곳 |
| `previous.*`, 그리고 step `input`을 비우면 `{{previous.text}}`로 채우는 기본값 | **삭제.** step `input`은 필수로 바꾸고, 항상 `steps.<id>`로 명시합니다. 루프에서 "직전 step"이 무엇인지 헷갈리는 문제도 함께 사라집니다 | 6곳 |
| `steps.x.items` (forEach 결과) | **삭제.** forEach step의 `output`이 항목별 output의 리스트가 됩니다 | 2곳 |
| workflow `output`을 비우면 마지막 step의 text가 결과 | **삭제.** `output.value`를 필수로 바꿉니다 | — |
| `steps.x.error` | **유지를 권합니다.** 데이터가 아니라 실패 정보입니다. 실패 사유를 다시 넣어 재시도하는 루프에 필요합니다 | 4곳 |
| `steps.x.input` | 유지합니다. YAML 키와 이름이 같아서 암묵적인 항목이 아닙니다 | — |

## 3. `inputs` → `input` 통일: 찬성

YAML 키 이름과 컨텍스트 이름을 맞춘다는 기존 원칙과도 맞습니다. workflow `input`도 Agent와 같은 `schema` 모양으로 맞추겠습니다.

- 참조는 `{{input}}`(string일 때) 또는 `{{input.requirement}}`(object일 때)가 됩니다.
- step 안에서 `{{input.x}}`는 **workflow 입력**을 가리키고, 각 step의 입력은 `{{steps.<id>.input}}`으로 구분됩니다. 이 점을 문서에 명시하겠습니다.
- 2026-09-25에 넣은 "옛 `input.` 이름을 쓰면 이름 바꾸라는 힌트와 함께 기동 실패" 규칙은 방향이 반대가 되므로 `inputs.` 쪽 힌트로 바꿉니다.

## 4. output이 없으면 `schema: {type: string}`: 찬성

"자유 텍스트"라는 별도 경로 없이, 로더가 `{type: string}` 스키마로 채워 넣어서 모든 Agent가 스키마를 갖게 하겠습니다. 명시적으로 적어도 됩니다.
- **string일 때는 JSON 형식을 강제하지 않고** 답 원문을 그대로 output으로 씁니다. 긴 설계서를 JSON 문자열로 감싸면 품질과 토큰 양 모두 손해이기 때문입니다.
- number/integer/boolean/object/array는 JSON으로 받아서 스키마로 검증합니다.

## 5. 새로 생기는 문제들

**① TOOL step의 `output: text|json|lines`**
"계약은 호출 대상 한 곳에만"이라는 원칙에 따르면 TOOL도 같은 방식이어야 합니다.
- **입력 계약:** Spring AI가 이미 `@Tool` 메서드 파라미터(와 MCP tool)로부터 inputSchema를 만들어 둡니다. 기동 시 TOOL step의 `input` 키를 이 스키마와 대조하겠습니다.
- **출력:** step에서 선언하지 않습니다. Tool 응답이 JSON이면 객체나 배열로, 아니면 문자열로 `output`에 넣습니다.
- `lines`+`pattern`은 타입 선언이 아니라 "호출하는 쪽의 가공"입니다. 그래서 step의 `parse: lines` + `pattern`으로 이름을 바꿔 남기는 걸 권합니다. MCP `list_directory`처럼 텍스트로 답하는 Tool 때문에 필요합니다.

**② SUPERVISOR / ROUTER**
이 두 step의 답 모양(`{pass, reason}`, `{route, reason}`)은 엔진이 정합니다. 그래서 여기서 ref로 쓰는 Agent에 `output`이 선언되어 있으면 기동 오류로 처리하겠습니다. 값은 `steps.x.output.pass`, `steps.x.output.route`로 꺼냅니다.

**③ JSON Schema 안에서의 축약형**
`name: string`은 표준 JSON Schema가 아닙니다. 그래서 **로더가 `properties`/`items` 안의 축약형만 `{type: string}`으로 펼친 뒤** 표준 스키마로 검증기와 LLM에 넘기겠습니다. 최상위 `output: string`도 `output: {schema: {type: string}}`의 축약형으로 허용합니다.

**④ Agent `input`이 object일 때**
step `input`이 TOOL처럼 맵이 됩니다(값마다 템플릿). 렌더링한 뒤 Agent의 input 스키마로 검증하고, JSON 문자열로 바꿔 사용자 메시지로 보냅니다.

**⑤ API가 바뀌어 dstone-boot도 고쳐야 합니다**
- `WorkFlowRequest(message, sessionId, variables)`가 `(input, sessionId)`로 바뀝니다. `input`은 스키마에 따라 문자열이거나 객체입니다.
- `ChatRequest.message`도 `input`으로 바뀝니다.
- dstone-boot의 `workflow.jsp`, `WorkFlowTestRequest`, `ChatMessageRequest`, `WorkFlowTestService`가 이 API를 호출하고 있어서 함께 수정해야 합니다.

**⑥ 검증 라이브러리**
Spring Boot 4는 Jackson 3를 씁니다. networknt `json-schema-validator`가 Jackson 3와 호환되는지 구현 전에 먼저 확인하겠습니다. 호환이 안 되면 다른 라이브러리를 고르겠습니다.

## 바뀐 것

- **계약은 Agent가 가집니다.** Agent YAML에 `input`/`output`을 두고, `schema:` 아래에 JSON Schema를 YAML로 그대로 적습니다.
  - `output: string`, `list<string>` 같은 축약형도 됩니다.
  - 둘 다 비워 두면 `string`입니다.
- **step에는 `output` 키가 없습니다.**
  - step은 `input`(무엇을 넣을지)과 다음 이동만 적습니다.
  - TOOL의 `lines`/`pattern`은 삭제했습니다. 이제 Tool 응답이 JSON이면 그 값을, 아니면 글자를 그대로 씁니다.
- **숨은 이름을 모두 없앴습니다.** 컨텍스트에는 `input`, `steps.<id>.{input, output, error}`, `approvals`만 남습니다.
  - `text`, `previous`, `items`, `inputs.message`를 없앴습니다.
  - "input을 비우면 직전 결과", "output을 비우면 마지막 결과" 같은 기본값도 없앴습니다.
- **Workflow:** `inputs`는 `input`(스키마)으로, `output`은 `{value(필수), schema(선택)}`로 바꿨습니다.
- **SUPERVISOR/ROUTER/APPROVAL:** output 모양은 엔진이 정합니다. 이 step이 부르는 Agent에 `output`이 있으면 기동이 실패합니다.
- **API(한 번에 변경):**
  - 채팅: `{agent, input, variables}` → `{output}`
  - Workflow: `{input, sessionId}` → `{status, output}`
- **검증 라이브러리:** Spring AI가 이미 쓰는 networknt json-schema-validator 3.0.1을 pom에 같은 버전으로 명시했습니다. Jackson 3 타입이 엔진 코드로 새지 않도록 문자열 API만 씁니다.
- **MCP 샘플:** `lines`/`pattern` 삭제에 맞춰 `list_directory` 대신 JSON으로 답하는 `directory_tree`를 씁니다.

## 알아두실 동작 변화

- AGENT류 step의 `ref`가 없는 Agent를 가리키면 이제 실행 중이 아니라 **기동 시** 실패합니다.
- SUPERVISOR/ROUTER에서 LLM 호출 자체가 실패하면(API 오류 등) `onFailure`로 가지 않고 **Workflow 전체가 FAILED**가 됩니다. `onFailure`를 따르는 건 계약 위반뿐입니다.
- ROUTER가 routes에 없는 이름을 고르면 즉시 FAILED가 아니라 **step 실패**로 `onFailure`를 따릅니다.
- 구현 중에 발견한 점: Agent prompt에 JSON 예시를 중괄호로 적으면 Spring AI가 변수로 읽어 호출 때 실패합니다. 샘플에서는 중괄호를 뺐고, 가이드에 주의사항으로 적었습니다.

이번 코드 변경과는 관계없는 **Windows PC의 실행 환경 문제**입니다. 엔진을 띄운 Java 프로세스가 `npx`를 찾지 못하고 있습니다. Windows PC에 직접 접근할 수 없어서 거기서 재현하거나 수정해 보지는 못했습니다. 아래는 로그와 코드로 판단한 내용입니다.

## 원인

- 깨진 한글은 cmd.exe가 낸 `'npx'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는 배치 파일이 아닙니다.`입니다.
- 이 메시지는 `conf/env.properties`의 `MCP_STDIO_COMMAND_PREFIX=cmd.exe /c`가 적용돼서 cmd.exe까지는 실행됐다는 뜻입니다.
- 문제는 그 cmd.exe가 받은 **PATH에 Node.js(npx)가 없다는 것**입니다.
- 그래서 MCP 서버 프로세스가 곧바로 끝났고, 엔진이 닫힌 파이프에 쓰려다 `파이프가 닫히는 중입니다`와 `Client failed to initialize` 오류가 뒤따라 났습니다.

## 엔진 기동 자체는 막히지 않아야 정상입니다

- `ConfigMcp`는 서버마다 try-catch로 접속합니다. 실패하면 `dstone-ai-engine mcp: [sample-filesystem] 접속 실패 ...` 로그만 남기고 넘어갑니다.
- 이번 변경으로 추가한 Tool 인자 검사도 `directory_tree`를 못 찾으면 `[경고]` 로그만 남깁니다.
- 로그 끝에 `Started DstoneAiEngineApplication`이 찍혔다면 서버는 떠 있는 상태입니다. MCP를 쓰는 기능만 동작하지 않습니다.
  - 해당 기능: `sample-mcp-filesystem-list` Workflow, `sample-mcp-filesystem-agent`
- 만약 기동 자체가 실패했다면 로그의 마지막 `Caused by`를 보내 주세요.

## 해결 방법 (Windows PC에서)

1. 새로 연 cmd 창에서 `where npx`를 실행합니다.
   - 경로가 나오지 않으면 Node.js가 설치돼 있지 않은 것입니다. Node.js LTS를 설치합니다.
2. 경로가 나오는데도 같은 오류라면, 엔진을 띄운 IDE나 터미널이 Node.js 설치 **전**에 열려서 예전 PATH를 쓰고 있는 경우가 대부분입니다. IDE를 완전히 종료한 뒤 다시 실행합니다.
3. nvm-windows처럼 사용자 PATH에만 등록되는 설치 방식이라면, 엔진을 실행하는 계정과 실행 방식(서비스 등)에서도 그 PATH가 보이는지 확인합니다.

npx 설치 여부와 상관없이 동작하게 하려면, 환경별 properties에 npx 절대경로를 두고 `mcp/*.yml`의 `command`에서 `${...}`로 참조하는 방식으로 바꿀 수 있습니다. 필요하시면 말씀해 주세요.

## 답변

새 cmd 창에서는 `npx`가 실행되니 Node.js 설치와 PATH 등록은 정상입니다. 그렇다면 **엔진을 띄운 프로세스가 예전 PATH를 물려받았을 가능성**이 가장 큽니다.

- Windows 프로그램은 자기가 **시작될 때의** 환경변수를 계속 씁니다.
- 그래서 Node.js를 설치(또는 PATH 수정)하기 전에 열어 둔 IDE는 새 PATH를 모릅니다. 그 IDE에서 띄운 엔진과, 엔진이 실행하는 `cmd.exe /c npx ...`도 모두 예전 PATH를 씁니다.

## 해결 순서

1. **IDE를 완전히 종료했다가 다시 실행**한 뒤 엔진을 다시 띄웁니다.
   - 창만 닫지 말고 작업 관리자에서 IDE 프로세스가 남아 있지 않은지 확인합니다.
   - 대부분 이것으로 해결됩니다.
2. 그래도 안 되면 IDE의 실행 설정(Run Configuration → Environment 탭)에서 PATH를 따로 덮어쓰고 있지 않은지 확인합니다.
3. 원인을 확실히 보려면, 엔진을 띄우는 것과 같은 방식으로 연 터미널(IDE 안의 터미널 등)에서 `where npx`를 실행해 봅니다. 여기서 못 찾으면 그 프로세스의 PATH 문제가 맞습니다.

## 환경을 타지 않게 고치는 방법(선택)

PATH와 상관없이 항상 동작하게 하려면, `where npx`로 나온 절대경로(예: `C:\Program Files\nodejs\npx.cmd`)를 설정에 두고 MCP 설정이 그 값을 쓰게 바꾸면 됩니다.

`where npx` 결과를 알려 주시면 그 방식으로 바꿔 드리겠습니다. 이때 WSL/k8s용 properties에도 `npx` 값을 함께 넣겠습니다.
