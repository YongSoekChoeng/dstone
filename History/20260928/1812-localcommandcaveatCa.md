## 답변

## 원인

Workflow의 `output`을 `output: string`으로 적은 것이 에러의 원인입니다.

로그의 핵심은 이 줄입니다.
```
[workflow.output] workflow.output은 value(와 schema)를 가진 맵입니다. 예: output: {value: "{{steps.마지막step.output}}"}
... no String-argument constructor ... from String value ('string')
```
`string`, `list<string>` 같은 축약형은 스키마 자리(Workflow `input`, Agent `input`/`output`)에서만 쓸 수 있습니다. Workflow의 `output`은 스키마가 아니라 "최종 결과를 무엇으로 만들지"를 적는 곳이라서 `WorkFlowOutputDefinition`, 즉 `{value, schema?}` 맵이어야 합니다. 그런데 `"string"`이라는 문자열이 들어와서 Jackson이 객체로 바꾸지 못했습니다.

## 이것만 고치면 다음에 걸릴 문제들

YAML 파일을 앞에서부터 읽다가 첫 오류에서 멈추기 때문에, 아래 문제들은 아직 에러로 나오지 않았을 뿐입니다.

1. **step02의 `output:` 키**: step에는 `output` 키가 없습니다. 위 줄의 `output: {value: ...}`는 step이 아니라 Workflow 레벨로 옮겨야 합니다. 그대로 두면 "AGENT step의 output은 없어졌습니다" 에러가 납니다.
2. **`testApp-agent-02.yml`에 `input` 키가 두 번 있음**: 두 번째 `input: string`이 첫 번째 object 스키마를 덮어씁니다(SnakeYAML은 같은 키가 또 나오면 뒤의 값을 씁니다). 아마 두 번째 줄은 `output: string`을 쓰려던 것으로 보입니다.
3. **step02의 `input: {value: "{{steps.step01.output}}"}`**:
   - agent-02의 input이 결국 `string`이 되므로, map을 넣으면 모양이 맞지 않아 기동 검증에서 실패합니다.
   - 2번을 고쳐서 input이 object 스키마가 되더라도, `value`는 그 스키마의 properties에 없는 키입니다. 그리고 필수 키 3개(`1. 요청 배경/목적 요약` 등)가 빠져 있으니 역시 맞지 않습니다.
   - step01의 output이 이미 같은 모양의 object이므로, `"{{steps.step01.output}}"`를 그대로 넘기면 됩니다. `{{x}}` 하나만 단독으로 쓰면 값의 타입(object)이 그대로 유지됩니다.

## 답변

`/status/{executionId}`로 조회하면 결국 **`FAILED`**가 나옵니다. step01이 어떻게 끝나든 step02에서 확실히 실패합니다. 아래 내용은 설정 파일과 코드를 읽고 예상한 결과이고, 실제로 실행해 보지는 않았습니다.

## 진행 순서

**0. 요청 접수**: `/submit`은 input 검사(`checkInput`)를 통과했습니다. 워크플로우 input이 `string`이고 파일 경로 문자열이 들어왔기 때문입니다. 그래서 바로 `executionId`와 함께 접수 응답이 나가고, 실제 실행은 비동기로 진행됩니다.

**1. step01 (testApp-agent-01): 결과가 매번 다를 수 있음**
- Agent는 `/app/dstone/docs/temp/dongyang-plan.md`라는 **경로 문자열만** 받습니다.
- `toolsEnabled: false`라서 파일을 읽을 방법이 없습니다. 프롬프트의 "해당 문서를 읽어서"는 실행될 수 없는 지시입니다.
- output이 object 스키마이므로 사용자 메시지 끝에 "이 스키마 모양의 JSON으로만 답하라"는 지시문이 붙습니다(`AgentExecutor.java:185`). 그런데 시스템 프롬프트는 "별도 형식 없이 이 응답 전체가 곧 분석/설계서"라고 해서 두 지시가 서로 충돌합니다.
- 그래서 결과는 두 가지 중 하나입니다.
  - **JSON으로 답한 경우**: 스키마를 통과해 성공합니다. 하지만 내용은 "문서를 열람할 수 없음" 같은 말이거나 파일명(dongyang-plan)만 보고 지어낸 추측입니다. 실제 문서 내용은 전혀 반영되지 않습니다.
  - **"파일을 읽을 수 없습니다" 같은 일반 문장으로 답한 경우**: JSON 파싱이나 스키마 검증에서 실패해 `AgentContractException`이 나고, `onFailure: FAIL`로 곧바로 **FAILED**가 됩니다.

**2. step02 (testApp-agent-02): 반드시 실패**
- `testApp-agent-02.yml`에는 아직 `input` 키가 두 번 들어 있습니다. SnakeYAML 기본 설정(`new Yaml()`)은 키가 중복되면 뒤의 값을 쓰기 때문에, 이 Agent의 input은 **`string`**이 되고 output도 기본값 `string`이 됩니다.
- step02의 input은 `"{{steps.step01.output}}"` 하나만 있는 참조라서 **object 타입 그대로** 넘어갑니다.
- `toUserMessage()`의 input 검사(`AgentExecutor.java:152-155`)에서 object가 string 스키마와 맞지 않아 `agent[testApp-agent-02]의 input 모양이 맞지 않습니다: [...]`가 발생합니다.
- 이는 step 실패로 처리되고(`AgentStepExecutor.java:55`), `onFailure: FAIL`에 따라 워크플로우가 **FAILED**로 끝납니다. LLM은 호출되지 않습니다.

## 기동 검증에서 걸러지지 않은 이유

기동 시 검사는 두 가지만 확인합니다.
- step input의 겉모양: 템플릿 문자열이 string input Agent와 맞는지
- `{{steps.step01.output}}` 경로가 실제로 존재하는지

"하나만 있는 참조가 가리키는 값의 타입(object)이 받는 쪽 스키마(string)와 맞는지"는 확인하지 않습니다. 그래서 이 불일치는 실행 중에야 드러납니다. 필요하면 이 부분을 기동 검증에 추가할 수 있습니다.

## 제대로 동작하게 하려면

1. **agent-02**: 두 번째 `input: string`을 `output: string`으로 바꿉니다. 지난번에 말씀드린 부분인데 아직 반영되지 않았습니다.
2. **agent-01이 파일을 읽을 수 있게 하기**: 다음 중 하나를 고르면 됩니다.
   - 문서 **내용 자체**를 workflow input으로 넣기
   - 파일을 읽는 TOOL step(예: MCP filesystem의 `read_text_file`)을 step01 앞에 두고, 그 결과를 agent-01에 넘기기
   - agent-01을 `toolsEnabled: true`로 바꾸고 파일을 읽는 Tool을 쓸 수 있게 하기
3. **agent-01 프롬프트 정리**: "별도 형식 없이 응답 전체가 문서" 문장을 빼거나 "각 항목을 문장 목록으로 작성"처럼 바꿔서 JSON 출력 지시와 충돌하지 않게 합니다.

## 답변

아직 Anthropic 응답을 기다리는 중일 가능성이 가장 높습니다. 요청이 끊어졌다가 재시도되는 것으로 보고 있습니다. 이 판단은 설정과 라이브러리 기본값을 확인해서 추론한 것이고, 사용하시는 Windows 환경에서 직접 재현해 보지는 않았습니다.

## 로그로 알 수 있는 것

- 03:52:13의 `WorkFlowExecutionController.detail`은 `/status` 조회입니다. 이 조회는 END까지 정상으로 끝났습니다. 로그 중간에 끼어 있는 `AgentExecutor` 로그는 비동기 실행 스레드에서 찍힌 것입니다.
- 03:52:14에 Anthropic으로 요청이 나갔고(`SimpleLoggerAdvisor request`), 그 뒤로 response 로그가 없습니다. 모델이 아직 답을 주지 않은 상태입니다.

## 원인: Anthropic 클라이언트의 기본 타임아웃이 60초

`spring-ai-anthropic-2.0.1`의 `AnthropicSetup` 클래스를 확인한 기본값입니다.
- `DEFAULT_TIMEOUT = 60초`
- `DEFAULT_MAX_RETRIES = 2`

`conf/application.yml`에 있는 `spring.http.clients.read-timeout: 5m`은 RestClient 기반인 Ollama에만 적용됩니다. Spring AI 2.x의 Anthropic은 공식 Java SDK(`anthropic-java`, OkHttp)를 쓰기 때문에 이 값이 적용되지 않습니다. Anthropic 쪽 설정은 `spring.ai.anthropic.timeout`과 `spring.ai.anthropic.max-retries`이고, 지금은 둘 다 설정되어 있지 않습니다.

이번 요청은 `max-tokens: 4096`까지 한국어 JSON 분석서를 쓰게 합니다. Sonnet 4.5로 이 정도 분량을 만들면 60초를 넘기 쉽습니다. 그러면 이렇게 진행됩니다.

1. 60초에 요청이 끊깁니다.
2. SDK가 알아서 재시도합니다(최대 2번). 매번 처음부터 다시 생성하므로 토큰 비용도 매번 나갑니다.
3. 세 번 모두 끊기면 3분 남짓 뒤에 예외가 올라옵니다.
4. `WorkFlowExecutor.java:135`에서 이 예외를 잡아 **FAILED**로 저장합니다. 에러 메시지는 `step[step01] 실행 중 예외가 발생했습니다 - ...timeout...` 형태입니다.

그 사이에 `/status`를 조회하면 계속 `RUNNING`이고 step 이력도 비어 있습니다. 이 상태가 "리턴이 없다"로 보이는 것입니다. 또 `persistFailed()`는 DB에 에러를 저장만 하고 스택트레이스를 로그로 남기지 않습니다. 그래서 끝나더라도 콘솔에는 잘 드러나지 않을 수 있습니다.

## 확인 방법

몇 분 뒤 `/status/10cb6da3-...`를 다시 조회해 보세요. `FAILED`이고 에러 메시지에 timeout이 들어 있으면 이 원인이 맞습니다.

## 조치

`conf/application.yml`에 다음을 추가합니다.
```yaml
spring:
    ai:
        anthropic:
            timeout: 5m        # 기본 60초 → 긴 JSON 생성도 끝까지 기다림
            max-retries: 1     # 기본 2 → 타임아웃 때 같은 생성을 여러 번 반복하지 않게
```

## 핵심 포인트

**1. 이번에는 Anthropic이 아니라 로컬 Ollama가 호출됐습니다**
- 요청 로그에 `modelOptions=OllamaChatOptions`, 응답 로그에 `"model": "hf.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF:latest"`가 찍혀 있습니다.
- `conf/application.yml:83`이 `spring.ai.model.chat: ollama`로 되어 있어서 **1.5B짜리 초소형 모델**이 이 작업을 맡았습니다.

**2. 모델이 JSON 스키마를 이해하지 못했습니다**
- object를 요구했는데 모델은 **property 이름 5개를 배열로 나열**만 했습니다.
  ```
  ["1. 요청 배경/목적 요약", "2. 현재 상태(As-Is)", ...]
  ```
- 엔진이 이 응답을 검증해서 `array 발견, object 예상`으로 거절했고, `AgentContractException`이 step 실패로 이어졌습니다. 1.5B 모델에게 2천 토큰이 넘는 한국어 지시와 JSON Schema를 한 번에 지키게 하는 것은 무리입니다. `completionTokens: 61`로 거의 아무것도 생성하지 않았습니다.

**3. `toolsEnabled=true`로 바꿨지만 Tool이 호출되지 않았습니다**
- 응답의 `toolCalls: []`가 비어 있습니다. 소형 모델은 tool calling 능력도 약합니다.
- 설령 호출했더라도 파일을 읽을 수 있는 Tool이 사실상 없습니다.
  - `@AiTool`에는 파일 읽기 도구가 없습니다(shell/python/http/sql/날짜/RAG만 있음).
  - MCP `sample-filesystem`은 `${APP_HOME}/${APP_NAME}/mcp/server-filesystem` 폴더만 접근할 수 있습니다. `D:/.../docs/temp/dongyang-plan.md`는 그 폴더 밖이라 접근이 거부됩니다.

## 답변

제가 앞에서 말한 것은 반대입니다. **지금은 step끼리 대화 메모리가 공유되고 있고**, 그게 문제라는 뜻이었습니다. 그 문제를 이번 수정에서 고치지 않았다는 의미로 "손대지 않았다"고 쓴 것입니다.

## 무슨 뜻인가

Workflow 실행 하나 안의 모든 AGENT/SUPERVISOR/ROUTER step은 **같은 대화방(conversationId)**에서 LLM을 부릅니다. 그래서 뒤 step의 LLM은 앞 step이 주고받은 질문과 답을 **이전 대화**로 함께 받습니다.

지난번 로그의 step02 요청이 그 증거입니다.
```
System    : 리뷰어 프롬프트                         ← step02 자신의 것
User      : 파일경로 + "JSON으로만 답하라" + 스키마   ← step01의 질문 (섞여 들어옴)
Assistant : step01의 JSON 답                        ← step01의 답 (섞여 들어옴)
User      : step02 input                            ← step02 자신의 것
```
그래서 리뷰어 모델이 앞 대화의 "JSON으로만 답하라"를 따라해서 영문 키 JSON 한 줄로 답했습니다.

## 왜 그렇게 되나 (코드 흐름)

1. **세션 ID 하나 생성**: 요청에 `sessionId`가 없으면 `WorkFlowController.java:168`이 UUID를 하나 만듭니다. 이 값이 `WorkFlowExecution.sessionId`에 저장됩니다.
2. **모든 step이 같은 ID로 호출**: `AgentStepExecutor.java:54`, `SupervisorStepExecutor.java:52`, `RouterStepExecutor.java:51` 모두 `execution.sessionId()`를 그대로 `AgentExecutor`에 넘깁니다.
3. **그 ID가 대화방 번호가 됨**: `AgentExecutor.buildSpec()`이 `ChatMemory.CONVERSATION_ID = sessionId`로 설정합니다.
4. **메모리 Advisor가 자동으로 붙음**: `ConfigChatClient.java:106`에서 모든 ChatClient 호출에 `MessageChatMemoryAdvisor`가 기본으로 붙습니다. 이 Advisor는 호출할 때마다 두 가지를 합니다.
   - 호출 전: Redis에서 그 conversationId의 최근 대화(최대 20개, `dstone.ai.session.max-messages`)를 꺼내 요청 앞에 붙입니다.
   - 호출 후: 이번 질문과 답을 Redis에 추가합니다.

결과적으로 step01이 저장한 대화를 step02가 꺼내 쓰게 됩니다.

## 왜 문제인가

이 메모리 기능은 원래 **채팅 API**(`/api/ai/chat`)용입니다. 한 사용자가 여러 번 대화를 이어갈 때 앞 대화를 기억하게 하려는 것이라, 그 용도에서는 맞게 동작합니다.

하지만 Workflow에서는 step끼리 데이터를 넘기는 공식 통로가 이미 있습니다. `input: "{{steps.step01.output}}"`처럼 **명시적으로** 넘기는 방식이고, 이것이 "callee가 계약을 소유한다"는 설계입니다. 그런데 메모리가 공유되면 부작용이 생깁니다.
- **뒤 step의 지시가 오염됩니다**: 앞 Agent의 프롬프트, 출력 형식 지시, 스키마가 뒤 Agent에게 섞여 들어갑니다(이번 사례).
- **데이터가 이중으로 전달됩니다**: 같은 내용이 input과 대화 기록 양쪽으로 들어가서 토큰이 낭비됩니다. 문서 본문을 읽게 되면 수만 토큰이 중복될 수 있습니다.
- **결과를 예측하기 어렵습니다**: 같은 Agent라도 앞에 어떤 step이 있었는지에 따라 답이 달라집니다. 같은 sessionId로 다시 실행하면 이전 실행의 대화까지 섞입니다.

## 고치는 방향 (제안)

1. **Workflow step 호출에서는 메모리를 끕니다(권장)**: step은 input만 보고 답하게 합니다. 설계 원칙과 가장 잘 맞습니다.
2. **step마다 별도 대화방을 씁니다**: conversationId를 `sessionId:stepId`로 나눕니다. 재작성 루프에서 같은 step이 다시 불릴 때 자기 이전 시도만 기억하게 할 수 있습니다.

쓰임새에 따라 다릅니다. 공유가 유리한 경우도 분명히 있습니다. 다만 이 엔진 구조에서는 오염이 드문 예외가 아니라 **자주 생기는 조건**이 있어서, 기본값을 "공유"로 두기는 위험하다고 봅니다.

## 공유가 유리한 경우

- **같은 Agent가 여러 번 불리는 재작성 루프**: 예를 들어 convert → validate 실패 → convert를 다시 부르는 흐름입니다. 이전 시도와 실패 이유를 기억하면 같은 실수를 덜 반복합니다.
- **대화형 흐름**: 사람과 여러 턴을 주고받거나 APPROVAL 뒤에 이어서 수정하는 경우입니다. 맥락이 이어지는 편이 자연스럽습니다.
- **원문 맥락이 뒤 step에도 필요한 경우**: 뒤 step이 앞 step의 요약 결과만이 아니라 원문 뉘앙스까지 봐야 할 때입니다. 템플릿으로 일일이 넘기지 않아도 됩니다.

## 오염이 생기는 조건

"특정 상황에서만"이 맞습니다. 다만 그 상황이 이 엔진에서는 흔합니다.

**① 앞 step의 output이 string이 아닐 때 (가장 흔함)**
- 엔진은 object/list output인 Agent를 부를 때마다 사용자 메시지 끝에 "Your response must be a single JSON value only…"와 스키마를 붙입니다(`AgentExecutor.java:185`).
- 이 지시가 대화 기록에 남습니다. 그래서 **구조화 output step 뒤에 오는 모든 step**이 이 지시를 보게 됩니다.
- SUPERVISOR/ROUTER도 항상 엔진이 정한 JSON 스키마로 호출됩니다. 그래서 이들 뒤에 오는 step도 마찬가지입니다.

**② 앞뒤 step의 역할(Agent)이 다를 때**
- 기록 속 앞 step의 답은 `Assistant` 메시지로 들어갑니다. 뒤 step 모델은 이것을 **자기가 한 말**로 받아들입니다.
- 이번 사례에서 리뷰어 입장에서는 "분석가로서 JSON으로 답한 게 나였다"가 되니, 같은 형식을 이어가려는 경향이 생깁니다.
- 모델이 클수록 덜하지만, 7B급에서는 거의 항상 나타납니다.

**③ 같은 내용이 두 번 들어갈 때**
- `input: "{{steps.step01.output}}"`로 넘기면 같은 내용이 기록에도, 이번 input에도 들어갑니다.
- 문서 본문처럼 큰 입력이면 토큰이 두 배가 되고, 로컬 모델에서는 context 초과나 타임아웃으로 바로 이어집니다.

**④ 구조적으로 불안정해지는 경우 (모델 품질과 무관)**
- **forEach 병렬 실행**: 여러 반복이 같은 대화방에 동시에 쓰기 때문에 기록 순서가 뒤섞입니다.
- **최대 20개 창(`max-messages`)**: step이 많거나 루프가 돌면 앞쪽 기록이 조용히 잘려 나갑니다. 무엇이 남는지 실행마다 달라집니다.
- **같은 sessionId 재사용**: 다시 실행하면 **이전 실행의 대화**까지 섞입니다.

## 정리

| 상황 | 공유 |
|---|---|
| 같은 Agent의 재시도/재작성 루프 | 유리 |
| 사람과 이어지는 대화형 흐름 | 유리 |
| 역할이 다른 Agent를 잇는 파이프라인(이번 testApp) | 오염 가능성 높음 |
| 구조화 output step이나 SUPERVISOR/ROUTER 뒤의 step | 형식 지시가 거의 항상 새어 들어감 |
| forEach 병렬 실행 | 기록 순서가 깨짐 |

그래서 "전부 끄기"보다는 **기본은 끄고, 필요한 곳에서만 켜는 방식**이 나아 보입니다. 예를 들면 다음과 같습니다.
- Agent YAML(또는 step)에 `memory: true`처럼 켜는 옵션을 둡니다.
- 켜더라도 대화방은 `sessionId:stepId` 단위로 나눕니다. 그러면 재작성 루프는 자기 이전 시도만 기억하고, 다른 역할의 대화는 섞이지 않습니다.

방향을 정해 주시면 그에 맞춰 엔진과 문서(`docs/09.dstone-ai-engine.md`, YAML 가이드)를 함께 수정하겠습니다.

## 답변

**step 쪽에 두는 게 맞다**고 봅니다.

## 이유

**1. 메모리는 Agent가 "무엇인지"가 아니라 "어떻게 불리는지"의 문제입니다**
- Agent YAML은 그 Agent의 계약을 정의합니다. 무엇을 받고 무엇을 돌려주는지, 어떤 역할(prompt)인지입니다. 어느 Workflow에서 부르든 똑같이 동작해야 재사용할 수 있습니다.
- 반면 "이전 시도를 기억해야 하나"는 흐름 모양에 따라 달라집니다.
  - 예: `testApp-agent-01`이 A Workflow에서는 한 번만 불리면 메모리가 필요 없습니다.
  - B Workflow에서 검증 실패 후 재작성 루프로 다시 불리면 메모리가 필요합니다.
- Agent에 옵션을 두면 이 둘을 동시에 만족할 수 없어서, 같은 Agent를 메모리 on/off 두 벌로 복사하게 됩니다.

**2. 채팅 API와 충돌하지 않습니다**
- `/api/ai/chat`은 같은 Agent를 세션 대화로 부르는 경로라서 메모리가 항상 필요합니다.
- Agent에 `memory: false`를 두면 채팅에서도 꺼야 하는지 애매해집니다. step에 두면 Workflow 안에서의 동작만 정하는 것이 분명합니다.

**3. 지금 설계 원칙과 맞습니다**
- 이미 역할이 이렇게 나뉘어 있습니다. Agent는 계약을 소유하고, step은 "무엇을 넣고 어디로 갈지"를 정합니다.
- 대화 기록도 결국 **이번 호출에 무엇을 넣을지**의 일부이므로 step의 몫입니다.

**4. 어떤 step끼리 기억을 나눌지는 Workflow만 판단할 수 있습니다**
- 공유 범위, 루프 구조, forEach 여부는 모두 Workflow를 봐야 알 수 있습니다. Agent 하나만 봐서는 판단할 수 없습니다.

`toolsEnabled`/`ragEnabled`가 Agent 쪽에 있는 것과 비교해 보면 차이가 보입니다. 그 둘은 Agent가 **무엇을 할 수 있는지**(능력)라서 Agent에 있는 게 맞습니다. 메모리는 **호출할 때 무엇이 함께 들어가는지**(입력 맥락)라서 성격이 다릅니다.

## 구체적인 설계안

```yaml
    - id: convert
      type: AGENT
      ref: sql-converter-agent
      input: "{{input}}"
      memory: true        # 기본값 false
```

- **적용 대상**: AGENT, SUPERVISOR, ROUTER step. TOOL과 APPROVAL은 LLM을 부르지 않으므로 해당 없습니다.
- **기본값 false**: 메모리를 쓰지 않고 input만으로 호출합니다. 이번 testApp처럼 역할이 다른 Agent를 잇는 파이프라인이 기본으로 안전해집니다.
- **true일 때 대화방은 `sessionId:stepId`**: 같은 step의 재시도끼리만 기억하고, 다른 step의 대화는 섞이지 않습니다.
- **forEach와 함께 쓰면 기동 시 오류**: 병렬 반복이 같은 대화방에 동시에 쓰면 순서가 깨지기 때문입니다.
- **채팅 API는 지금처럼** 세션 단위 메모리를 그대로 씁니다.
- **나중에 필요해지면** `memory: <이름>`처럼 문자열을 받아서, 서로 다른 step이 **의도적으로** 같은 대화방을 쓰게 확장할 수 있습니다. 지금은 넣지 않고 boolean으로 시작하는 걸 권합니다.

이 방향으로 괜찮으시면 엔진 코드를 고치겠습니다.
- 각 step 정의 record에 `memory` 필드 추가
- 해당 StepExecutor에서 `AgentExecutor`로 메모리 여부를 전달
- `WorkFlowRegistry`에 forEach 조합 검증 추가

그다음 `docs/09.dstone-ai-engine.md`와 YAML 가이드도 함께 수정하겠습니다.

## 질문

net.dstone.ai.common.definition.workflow.step.StepDefinition 에서 @JsonTypeInfo, @JsonSubTypes 는 정확한 기능이 무엇인가 ?

---

## 답변

두 어노테이션은 한 묶음으로, **Jackson 다형성 역직렬화** 설정입니다. YAML의 `steps` 목록에 다섯 종류의 step이 섞여 들어올 때, 각 항목을 어느 record로 만들지 Jackson이 스스로 판단하게 해 줍니다.

## 풀어야 하는 문제

`WorkFlowDefinition.steps`의 타입은 `List<StepDefinition>`입니다. 그런데 `StepDefinition`은 sealed interface라서 인스턴스를 직접 만들 수 없습니다. Jackson 입장에서는 YAML 항목 하나를 받았을 때 `AgentStepDefinition`으로 만들지 `ToolStepDefinition`으로 만들지 알 방법이 없습니다. 두 어노테이션이 그 판단 규칙을 알려 줍니다.

## `@JsonTypeInfo`: 종류를 어디서, 어떻게 읽을지

```java
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, include = JsonTypeInfo.As.PROPERTY, property = "type")
```

| 속성 | 뜻 |
|---|---|
| `use = Id.NAME` | 종류를 **논리적인 이름**(`AGENT`, `TOOL` …)으로 구분합니다. 클래스 전체 이름(`Id.CLASS`)을 쓰지 않으므로 YAML에 Java 클래스명이 드러나지 않습니다 |
| `include = As.PROPERTY` | 그 이름이 같은 객체 안의 **일반 키 하나**로 들어 있습니다 |
| `property = "type"` | 그 키의 이름은 `type`입니다 |

그래서 아래 YAML에서 Jackson은 `type` 값인 `TOOL`을 먼저 읽고 어떤 record로 만들지 정합니다.
```yaml
- id: read
  type: TOOL        ← 이 값으로 종류를 판단
  ref: read_text_file
```

## `@JsonSubTypes`: 이름과 record의 대응표

```java
@JsonSubTypes({
    @Type(value = AgentStepDefinition.class,      name = "AGENT"),
    @Type(value = SupervisorStepDefinition.class, name = "SUPERVISOR"),
    @Type(value = RouterStepDefinition.class,     name = "ROUTER"),
    @Type(value = ToolStepDefinition.class,       name = "TOOL"),
    @Type(value = ApprovalStepDefinition.class,   name = "APPROVAL")
})
```

`type` 값이 `TOOL`이면 `ToolStepDefinition`으로 만든다는 식의 매핑입니다. 이름은 대소문자까지 정확히 같아야 합니다. `tool`처럼 소문자로 쓰면 인식하지 못합니다.

## 이 구조 덕분에 생기는 동작

**1. step 종류마다 쓸 수 있는 키가 자동으로 제한됩니다**
- `type`으로 record가 정해지면 나머지 키는 그 record의 필드에만 바인딩됩니다.
- 그 record에 없는 키가 있으면 `UnrecognizedPropertyException`이 납니다. 예를 들어 TOOL에 `routes`나 `memory`를 적으면, 앞에서 확인한 "`'memory'`는 이 자리(`ToolStepDefinition`)에서 쓸 수 없는 키입니다" 오류가 이것입니다.
- 종류별 허용 키를 검사하는 코드를 따로 두지 않아도 됩니다.

**2. `type` 키 자체는 record 필드로 들어가지 않습니다**
- `visible`의 기본값이 `false`라서, Jackson은 `type` 값을 종류 판단에만 쓰고 생성자에는 넘기지 않습니다.
- 그래서 각 record에는 `type` 컴포넌트가 없고, 대신 `type()` 메서드가 `StepType.AGENT` 같은 고정값을 돌려줍니다(예: `AgentStepDefinition.type()`).

**3. `type`이 없거나 틀리면 기동이 실패합니다**
- Jackson이 `InvalidTypeIdException`을 던집니다.
- `YamlDefinitionLoader.java:228`이 이 예외를 "step의 type이 없거나 올바르지 않습니다(적은 값 = …, 쓸 수 있는 값 = AGENT, SUPERVISOR, ROUTER, TOOL, APPROVAL)" 메시지로 바꿔 보여 줍니다.

**4. sealed interface와 함께 쓰면 누락을 컴파일러가 잡아 줍니다**
- `@JsonSubTypes`는 YAML을 읽을 때 쓰는 대응표입니다.
- `sealed ... permits`는 코드에서 `switch (step)`을 쓸 때(`refOf`/`forEachOf`/`memoryOf`, `WorkFlowExecutor.runStep()` 등) 빠진 종류가 있으면 컴파일 오류를 냅니다.
- 새 step 종류를 추가할 때는 record 추가, `permits` 추가, `@JsonSubTypes` 등록 세 가지를 모두 해야 합니다. `@JsonSubTypes` 등록을 빠뜨리면 컴파일은 통과하지만 YAML을 읽을 때 "type이 올바르지 않습니다" 오류가 납니다.

**5. 반대 방향(객체를 JSON으로 쓸 때)도 같은 규칙입니다**
- 객체를 JSON으로 쓰면 Jackson이 `"type": "TOOL"`을 자동으로 붙입니다.
- 다만 지금 엔진에서 step 정의를 JSON으로 쓰는 곳은 없으니, 실제로 쓰이는 것은 YAML을 읽는 쪽뿐입니다.

## 답변

이 파일은 엔진이 기동할 때 한 번 읽힙니다. 엔진은 여기 적힌 명령으로 MCP 서버 프로세스를 띄우고, 그 서버가 제공하는 Tool을 엔진의 Tool 목록에 합칩니다. 합쳐진 뒤에는 로컬 `@AiTool`과 똑같이 AGENT step(LLM이 선택)과 TOOL step(이름으로 직접 호출)에서 쓰입니다. 아래 경로는 모두 `dstone-ai-engine/src/main/java/net/dstone/ai/` 기준입니다.

## 전체 흐름

```
sample-filesystem-mcp.yml
  │ ① 읽기       YamlDefinitionLoader.loadMcpServers()  → McpServerDefinition
  │ ② 등록       McpServerRegistry.load()               → id별 맵
  │ ③ 접속       ConfigMcp.connect()                    → npx 프로세스 실행 + Tool 목록 조회
  │ ④ 합치기     ConfigTool.discover()                  → @AiTool + MCP Tool 통합 목록
  ▼
  ⑤ 사용   ├─ AGENT step: AgentExecutor.buildSpec() → spec.tools(...) → LLM이 선택
           └─ TOOL step : ToolExecutor.call() → ConfigTool.findByName() → 직접 호출
```

## 단계별 상세

**① YAML 읽기: `common/loader/YamlDefinitionLoader.java:129` `loadMcpServers()`**
- `classpath:mcp/**/*.yml`(`Constants.java:152-153`)에 해당하는 파일을 모두 찾습니다.
- 최상위 키 `mcpServer:`를 `McpServerDefinition` record(`common/definition/mcp/McpServerDefinition.java`)로 바인딩합니다.
- `readAs()`(`:193`)가 바인딩 전에 `resolvePlaceholders()`(`:344`)로 `${APP_HOME}`, `${APP_NAME}`을 바꿉니다. System 프로퍼티(`env.properties`에서 로드된 값)를 먼저 보고, 없으면 OS 환경변수를 봅니다. 둘 다 없으면 `${...}`를 그대로 남깁니다.

**② 등록: `common/registry/McpServerRegistry.java` `load()` (@PostConstruct)**
- `id`나 `transport`가 비어 있거나 id가 중복되면 기동이 실패합니다.
- Workflow/Agent와 달리 실행 중에 id로 조회하는 일은 없습니다. ③에서 전체 목록을 한 번 도는 용도뿐입니다.

**③ 접속: `common/config/ConfigMcp.java` (@PostConstruct `connect()` `:55`)**
- `connectOne()`(`:72`)이 서버마다 다음을 합니다.
  1. `buildTransport()`(`:104`): `transport: STDIO`이면 `StdioClientTransport`, SSE이면 `HttpClientSseClientTransport`를 만듭니다.
  2. `buildStdioParams()`(`:127`): `command`와 `args`로 실행 명령을 조립합니다. `MCP_STDIO_COMMAND_PREFIX`(Windows에서 `cmd.exe /c`)가 있으면 맨 앞에 붙입니다. 이 파일 기준으로 실제 실행되는 명령은 다음과 같습니다.
     `cmd.exe /c npx -y @modelcontextprotocol/server-filesystem D:/AppHome/framework/dstone/dstone-ai-engine/mcp/server-filesystem`
     마지막 인자가 이 서버가 접근을 허용하는 **유일한 폴더**입니다.
  3. `client.initialize()` 후 `SyncMcpToolCallbackProvider.syncToolCallbacks()`(`:82`)로 서버의 Tool 목록을 받습니다.
  4. `isAllowed()`(`:153`): `allowedTools`에 있는 이름만 남깁니다. 이 파일에서는 6개이고, 비워 두면 전부 허용합니다.
  5. 남은 Tool을 `SerializedToolCallback`(`:172`)으로 감쌉니다. 같은 서버로 가는 호출은 한 번에 하나씩만 보냅니다. STDIO 연결 하나는 동시 요청을 받지 못하기 때문입니다.

**④ 통합: `common/config/ConfigTool.java:56` `discover()`**
- `@AiTool` 빈들의 Tool과 `configMcp.toolCallbacks()`(`:62`)를 합쳐 `ToolCallbackProvider` 하나로 만듭니다.
- `ConfigTool`이 `ConfigMcp`를 `@Autowired`로 받기 때문에, MCP 접속이 끝난 뒤에 이 단계가 실행됩니다.
- 이후 호출할 때 `dstone.ai.tool.allowed-by-caller` 화이트리스트로 caller별 필터가 적용됩니다(`toolCallbackProvider(caller)` `:84`). MCP Tool에도 똑같이 적용됩니다.

**⑤ 사용**
- **AGENT/SUPERVISOR step, 채팅**: `runtime/agent/AgentExecutor.java:282` `spec.tools(configTool.toolCallbackProvider(caller))`. Agent가 `toolsEnabled: true`일 때만 목록이 전달되고, 실제로 부를지는 LLM이 정합니다.
- **TOOL step**: `runtime/tool/ToolExecutor.java:40` `call()`이 `configTool.findByName(caller, "read_text_file")`(`ConfigTool.java:107`)로 찾아 LLM 없이 직접 호출합니다. 지금 testApp-workflow의 `read` step이 이 경로입니다.
- **기동 검증**: `WorkFlowRegistry`가 TOOL step의 `ref` Tool을 찾지 못하면 기동을 막지 않고 **경고만** 남깁니다. MCP 연결이 실패했을 수도 있기 때문입니다.

## 답변

원인은 엔진 코드가 아니라 **OpenRouter 무료 모델의 요청 한도 초과(429)**입니다. 다만 확인하는 과정에서 대화 기록이 오염되는 문제가 하나 더 드러났습니다. 엔진이 18:08:36에 종료되어 재현 테스트는 끝까지 하지 못했고, 아래는 로그와 Redis 기록으로 판단한 내용입니다.

## 로그로 본 흐름 (sessionId=ADMIN01)

| 시각 | 요청 | 결과 |
|---|---|---|
| 18:07:06 | "네 이름이 뭐야?" | 성공 |
| 18:07:36 | "알겠어 그럼 네가 잘하는 일이 뭐지?" | `RateLimitException: 429: Provider returned error` |
| 18:08:17 | "오류가 나네?" | 같은 429 |

- OpenAI SDK(`RetryingHttpClient`)가 자체적으로 2번 더 재시도한 뒤 실패했습니다(18:07:36~40). 같은 오류가 여러 번 찍힌 것은 한 번의 실패가 여러 Advisor 단계에서 반복 기록됐기 때문이고, 호출이 여러 번 나간 것은 아닙니다.
- `Provider returned error`는 OpenRouter 자체가 아니라 **그 뒤의 실제 공급자**가 거절했다는 뜻입니다.

## 원인: 무료 모델의 공용 한도

- OpenRouter 공개 API로 보면 `google/gemma-4-26b-a4b-it:free`를 서비스하는 곳은 **Google AI Studio 하나뿐**입니다.
- 무료 모델은 전 세계 사용자가 같은 upstream 한도를 나눠 씁니다. 그래서 요청 수가 적어도 이렇게 자주 429가 납니다.
- 요청 하나당 SDK 재시도까지 최대 3번 호출되므로, 실패가 한번 시작되면 한도를 더 빨리 소진합니다.
- "첫 번째는 되고 두 번째부터 안 된다"는 패턴은 타이밍이 겹친 것으로 보입니다. 대화 기록 때문에 429가 나지는 않습니다. 기록이 길어지면 토큰은 늘지만, 429는 요청 수 한도에서 나는 오류입니다.

## 함께 발견한 문제: 실패한 질문이 대화 기록에 쌓임

Redis의 `dstone:ai:session:ADMIN01` 내용입니다.
```
USER      네 이름은 뭐야?
USER      네 이름은 뭐야?
USER      네 이름이 뭐야?
USER      네 이름이 뭐야?
ASSISTANT 제 이름은 없습니다. 저는 구글에서 학습시킨 대규모 언어 모델입니다.
USER      알겠어 그럼 네가 잘하는 일이 뭐지?
USER      오류가 나네?
```
- Spring AI의 `MessageChatMemoryAdvisor`는 **LLM을 부르기 전에** 질문을 저장합니다. 그래서 실패한 호출(앞의 404와 이번 429)의 질문이 답 없이 남아 USER가 연달아 쌓입니다.
- 이 세션으로 계속 대화하면 매번 이 오염된 기록이 함께 전송됩니다. USER/ASSISTANT가 번갈아 와야 하는 모델에서는 이것 때문에 답이 이상해지거나 오류가 날 수 있습니다.
- 이것은 이번 메모리 옵션 수정과는 관계없습니다. 채팅 API는 예전부터 항상 메모리를 써 왔습니다.
