## 답변

## 원인

Workflow의 `output`을 `output: string`으로 적은 것이 에러의 원인입니다.

로그의 핵심은 이 줄입니다.
```
[workflow.output] workflow.output은 value(와 schema)를 가진 맵입니다. 예: output: {value: "{{steps.마지막step.output}}"}
... no String-argument constructor ... from String value ('string')
```
`string`, `list<string>` 같은 축약형은 스키마 자리(Workflow `input`, Agent `input`/`output`)에서만 쓸 수 있습니다. Workflow의 `output`은 스키마가 아니라 "최종 결과를 무엇으로 만들지"를 적는 곳이라서 `WorkFlowOutputDefinition`, 즉 `{value, schema?}` 맵이어야 합니다. 그런데 `"string"`이라는 문자열이 들어와서 Jackson이 객체로 바꾸지 못했습니다.

## 이것만 고치면 다음에 걸릴 문제들

YAML 파일을 앞에서부터 읽다가 첫 오류에서 멈추기 때문에, 아래 문제들은 아직 에러로 나오지 않았을 뿐입니다.

1. **step02의 `output:` 키**: step에는 `output` 키가 없습니다. 위 줄의 `output: {value: ...}`는 step이 아니라 Workflow 레벨로 옮겨야 합니다. 그대로 두면 "AGENT step의 output은 없어졌습니다" 에러가 납니다.
2. **`testApp-agent-02.yml`에 `input` 키가 두 번 있음**: 두 번째 `input: string`이 첫 번째 object 스키마를 덮어씁니다(SnakeYAML은 같은 키가 또 나오면 뒤의 값을 씁니다). 아마 두 번째 줄은 `output: string`을 쓰려던 것으로 보입니다.
3. **step02의 `input: {value: "{{steps.step01.output}}"}`**:
   - agent-02의 input이 결국 `string`이 되므로, map을 넣으면 모양이 맞지 않아 기동 검증에서 실패합니다.
   - 2번을 고쳐서 input이 object 스키마가 되더라도, `value`는 그 스키마의 properties에 없는 키입니다. 그리고 필수 키 3개(`1. 요청 배경/목적 요약` 등)가 빠져 있으니 역시 맞지 않습니다.
   - step01의 output이 이미 같은 모양의 object이므로, `"{{steps.step01.output}}"`를 그대로 넘기면 됩니다. `{{x}}` 하나만 단독으로 쓰면 값의 타입(object)이 그대로 유지됩니다.

## 답변

`/status/{executionId}`로 조회하면 결국 **`FAILED`**가 나옵니다. step01이 어떻게 끝나든 step02에서 확실히 실패합니다. 아래 내용은 설정 파일과 코드를 읽고 예상한 결과이고, 실제로 실행해 보지는 않았습니다.

## 진행 순서

**0. 요청 접수**: `/submit`은 input 검사(`checkInput`)를 통과했습니다. 워크플로우 input이 `string`이고 파일 경로 문자열이 들어왔기 때문입니다. 그래서 바로 `executionId`와 함께 접수 응답이 나가고, 실제 실행은 비동기로 진행됩니다.

**1. step01 (testApp-agent-01): 결과가 매번 다를 수 있음**
- Agent는 `/app/dstone/docs/temp/dongyang-plan.md`라는 **경로 문자열만** 받습니다.
- `toolsEnabled: false`라서 파일을 읽을 방법이 없습니다. 프롬프트의 "해당 문서를 읽어서"는 실행될 수 없는 지시입니다.
- output이 object 스키마이므로 사용자 메시지 끝에 "이 스키마 모양의 JSON으로만 답하라"는 지시문이 붙습니다(`AgentExecutor.java:185`). 그런데 시스템 프롬프트는 "별도 형식 없이 이 응답 전체가 곧 분석/설계서"라고 해서 두 지시가 서로 충돌합니다.
- 그래서 결과는 두 가지 중 하나입니다.
  - **JSON으로 답한 경우**: 스키마를 통과해 성공합니다. 하지만 내용은 "문서를 열람할 수 없음" 같은 말이거나 파일명(dongyang-plan)만 보고 지어낸 추측입니다. 실제 문서 내용은 전혀 반영되지 않습니다.
  - **"파일을 읽을 수 없습니다" 같은 일반 문장으로 답한 경우**: JSON 파싱이나 스키마 검증에서 실패해 `AgentContractException`이 나고, `onFailure: FAIL`로 곧바로 **FAILED**가 됩니다.

**2. step02 (testApp-agent-02): 반드시 실패**
- `testApp-agent-02.yml`에는 아직 `input` 키가 두 번 들어 있습니다. SnakeYAML 기본 설정(`new Yaml()`)은 키가 중복되면 뒤의 값을 쓰기 때문에, 이 Agent의 input은 **`string`**이 되고 output도 기본값 `string`이 됩니다.
- step02의 input은 `"{{steps.step01.output}}"` 하나만 있는 참조라서 **object 타입 그대로** 넘어갑니다.
- `toUserMessage()`의 input 검사(`AgentExecutor.java:152-155`)에서 object가 string 스키마와 맞지 않아 `agent[testApp-agent-02]의 input 모양이 맞지 않습니다: [...]`가 발생합니다.
- 이는 step 실패로 처리되고(`AgentStepExecutor.java:55`), `onFailure: FAIL`에 따라 워크플로우가 **FAILED**로 끝납니다. LLM은 호출되지 않습니다.

## 기동 검증에서 걸러지지 않은 이유

기동 시 검사는 두 가지만 확인합니다.
- step input의 겉모양: 템플릿 문자열이 string input Agent와 맞는지
- `{{steps.step01.output}}` 경로가 실제로 존재하는지

"하나만 있는 참조가 가리키는 값의 타입(object)이 받는 쪽 스키마(string)와 맞는지"는 확인하지 않습니다. 그래서 이 불일치는 실행 중에야 드러납니다. 필요하면 이 부분을 기동 검증에 추가할 수 있습니다.

## 제대로 동작하게 하려면

1. **agent-02**: 두 번째 `input: string`을 `output: string`으로 바꿉니다. 지난번에 말씀드린 부분인데 아직 반영되지 않았습니다.
2. **agent-01이 파일을 읽을 수 있게 하기**: 다음 중 하나를 고르면 됩니다.
   - 문서 **내용 자체**를 workflow input으로 넣기
   - 파일을 읽는 TOOL step(예: MCP filesystem의 `read_text_file`)을 step01 앞에 두고, 그 결과를 agent-01에 넘기기
   - agent-01을 `toolsEnabled: true`로 바꾸고 파일을 읽는 Tool을 쓸 수 있게 하기
3. **agent-01 프롬프트 정리**: "별도 형식 없이 응답 전체가 문서" 문장을 빼거나 "각 항목을 문장 목록으로 작성"처럼 바꿔서 JSON 출력 지시와 충돌하지 않게 합니다.

## 답변

아직 Anthropic 응답을 기다리는 중일 가능성이 가장 높습니다. 요청이 끊어졌다가 재시도되는 것으로 보고 있습니다. 이 판단은 설정과 라이브러리 기본값을 확인해서 추론한 것이고, 사용하시는 Windows 환경에서 직접 재현해 보지는 않았습니다.

## 로그로 알 수 있는 것

- 03:52:13의 `WorkFlowExecutionController.detail`은 `/status` 조회입니다. 이 조회는 END까지 정상으로 끝났습니다. 로그 중간에 끼어 있는 `AgentExecutor` 로그는 비동기 실행 스레드에서 찍힌 것입니다.
- 03:52:14에 Anthropic으로 요청이 나갔고(`SimpleLoggerAdvisor request`), 그 뒤로 response 로그가 없습니다. 모델이 아직 답을 주지 않은 상태입니다.

## 원인: Anthropic 클라이언트의 기본 타임아웃이 60초

`spring-ai-anthropic-2.0.1`의 `AnthropicSetup` 클래스를 확인한 기본값입니다.
- `DEFAULT_TIMEOUT = 60초`
- `DEFAULT_MAX_RETRIES = 2`

`conf/application.yml`에 있는 `spring.http.clients.read-timeout: 5m`은 RestClient 기반인 Ollama에만 적용됩니다. Spring AI 2.x의 Anthropic은 공식 Java SDK(`anthropic-java`, OkHttp)를 쓰기 때문에 이 값이 적용되지 않습니다. Anthropic 쪽 설정은 `spring.ai.anthropic.timeout`과 `spring.ai.anthropic.max-retries`이고, 지금은 둘 다 설정되어 있지 않습니다.

이번 요청은 `max-tokens: 4096`까지 한국어 JSON 분석서를 쓰게 합니다. Sonnet 4.5로 이 정도 분량을 만들면 60초를 넘기 쉽습니다. 그러면 이렇게 진행됩니다.

1. 60초에 요청이 끊깁니다.
2. SDK가 알아서 재시도합니다(최대 2번). 매번 처음부터 다시 생성하므로 토큰 비용도 매번 나갑니다.
3. 세 번 모두 끊기면 3분 남짓 뒤에 예외가 올라옵니다.
4. `WorkFlowExecutor.java:135`에서 이 예외를 잡아 **FAILED**로 저장합니다. 에러 메시지는 `step[step01] 실행 중 예외가 발생했습니다 - ...timeout...` 형태입니다.

그 사이에 `/status`를 조회하면 계속 `RUNNING`이고 step 이력도 비어 있습니다. 이 상태가 "리턴이 없다"로 보이는 것입니다. 또 `persistFailed()`는 DB에 에러를 저장만 하고 스택트레이스를 로그로 남기지 않습니다. 그래서 끝나더라도 콘솔에는 잘 드러나지 않을 수 있습니다.

## 확인 방법

몇 분 뒤 `/status/10cb6da3-...`를 다시 조회해 보세요. `FAILED`이고 에러 메시지에 timeout이 들어 있으면 이 원인이 맞습니다.

## 조치

`conf/application.yml`에 다음을 추가합니다.
```yaml
spring:
    ai:
        anthropic:
            timeout: 5m        # 기본 60초 → 긴 JSON 생성도 끝까지 기다림
            max-retries: 1     # 기본 2 → 타임아웃 때 같은 생성을 여러 번 반복하지 않게
```

## 핵심 포인트

**1. 이번에는 Anthropic이 아니라 로컬 Ollama가 호출됐습니다**
- 요청 로그에 `modelOptions=OllamaChatOptions`, 응답 로그에 `"model": "hf.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF:latest"`가 찍혀 있습니다.
- `conf/application.yml:83`이 `spring.ai.model.chat: ollama`로 되어 있어서 **1.5B짜리 초소형 모델**이 이 작업을 맡았습니다.

**2. 모델이 JSON 스키마를 이해하지 못했습니다**
- object를 요구했는데 모델은 **property 이름 5개를 배열로 나열**만 했습니다.
  ```
  ["1. 요청 배경/목적 요약", "2. 현재 상태(As-Is)", ...]
  ```
- 엔진이 이 응답을 검증해서 `array 발견, object 예상`으로 거절했고, `AgentContractException`이 step 실패로 이어졌습니다. 1.5B 모델에게 2천 토큰이 넘는 한국어 지시와 JSON Schema를 한 번에 지키게 하는 것은 무리입니다. `completionTokens: 61`로 거의 아무것도 생성하지 않았습니다.

**3. `toolsEnabled=true`로 바꿨지만 Tool이 호출되지 않았습니다**
- 응답의 `toolCalls: []`가 비어 있습니다. 소형 모델은 tool calling 능력도 약합니다.
- 설령 호출했더라도 파일을 읽을 수 있는 Tool이 사실상 없습니다.
  - `@AiTool`에는 파일 읽기 도구가 없습니다(shell/python/http/sql/날짜/RAG만 있음).
  - MCP `sample-filesystem`은 `${APP_HOME}/${APP_NAME}/mcp/server-filesystem` 폴더만 접근할 수 있습니다. `D:/.../docs/temp/dongyang-plan.md`는 그 폴더 밖이라 접근이 거부됩니다.

## 제대로 된 부분

- 모델을 `qwen2.5-coder:7b`로 바꾸자 step01이 스키마에 맞는 object JSON을 반환했고, 검증을 통과했습니다.

## 문제 1. step01 내용이 지어낸 것입니다

- `toolCalls: []`: 이번에도 파일을 읽지 않았습니다. 앞에서 말씀드린 대로 이 경로를 읽을 수 있는 Tool 자체가 없습니다.
- 결과가 "특정 기능을 사용할 때 문제가 발생…" 같은 **실제 문서와 관계없는 일반론**입니다. 형식만 맞춘 가짜 분석서입니다.

## 문제 2. step02가 step01의 대화 기록을 그대로 물려받았습니다 (엔진 구조 문제)

step02 요청의 messages를 보면 다음 순서입니다.
```
System(리뷰어 프롬프트)
User(파일경로 + "JSON으로만 답하라" + step01 스키마)   ← step01의 질문
Assistant(step01의 JSON 답)                           ← step01의 답
User(step02 input)
```
- Workflow 실행 하나의 모든 step이 **같은 `sessionId`**로 Agent를 부릅니다. `AgentExecutor.buildSpec()`이 `ChatMemory.CONVERSATION_ID`에 sessionId를 넣기 때문에, Redis 대화 메모리가 step 사이에 공유됩니다.
- 그 결과 step02 모델이 앞 대화의 "JSON으로만 답하라" 지시를 따라했습니다. 그래서 리뷰 문장 대신 `{"progress_difficulty": "medium", ...}` 같은 **영문 키 JSON 한 줄**을 냈습니다. output이 `string`이라 JSON 모양 문자열도 그대로 통과했습니다.
- 앞 step의 지시문과 스키마가 뒤 step에 섞이는 것은 "callee가 계약을 소유한다"는 설계와 어긋납니다. Workflow step은 대화 메모리를 쓰지 않거나, step마다 별도 conversationId를 쓰는 게 맞아 보입니다. 채팅 API의 세션 유지 기능은 그대로 두면 됩니다.

## 문제 3. 속도가 타임아웃에 가깝습니다

- step01이 **236초** 걸렸습니다. 설정한 Ollama timeout 300초에 거의 닿았습니다.
- 생성은 202토큰뿐인데 prompt가 2278토큰입니다. `toolsEnabled: true`라서 Tool 정의 전체가 프롬프트에 들어가기 때문입니다. CPU 추론에서는 이 prompt 처리가 대부분의 시간을 차지합니다.
- 어차피 쓸 Tool이 없으니 `toolsEnabled: false`로 두면 훨씬 빨라집니다.

## 제안

1. **엔진 수정(문제 2)**: Workflow에서 부르는 Agent 호출은 step끼리 메모리를 공유하지 않도록 바꿉니다. 예를 들어 conversationId를 `sessionId:stepId`로 분리하거나, Workflow 경로에서는 메모리 advisor를 끕니다. 어느 쪽으로 할지 정해 주시면 반영하겠습니다.
2. **입력(문제 1)**: 문서 본문을 input으로 넘기거나, MCP filesystem 허용 폴더와 `read_text_file` TOOL step을 추가합니다.
3. **agent-01 설정(문제 3)**: `toolsEnabled: false`로 바꿔서 prompt 크기와 소요 시간을 줄입니다.
4. **agent-02 프롬프트**: 원하는 결과 형식을 명시합니다. 예: "한국어 문장으로, 진행난이도/투입인력/예상기간을 항목별로 작성".

## 답변

`toolsEnabled: true`는 **"Tool 목록을 LLM에게 보여준다"**는 뜻일 뿐입니다. **"Tool을 반드시 쓴다"**는 뜻이 아닙니다. 실제로 호출할지는 LLM이 정하는데, 이번에는 호출하지 않을 조건이 겹쳤습니다. 게다가 호출했더라도 이 경로는 읽을 수 없었습니다.

## 1. Tool 목록은 실제로 전달됐습니다

`AgentExecutor.buildSpec()`은 `toolsEnabled`가 true이면 `spec.tools(configTool.toolCallbackProvider(caller))`를 붙입니다(`AgentExecutor.java:274-277`). 이 목록에는 `@AiTool`과 MCP Tool(`read_text_file` 등)이 함께 들어 있습니다.

로그에서도 확인됩니다.
- step01(tools on)의 `promptTokens`: **2278**
- step02(tools off)의 `promptTokens`: **796**

step02 쪽에는 step01의 대화 기록까지 들어 있는데도 차이가 약 1500토큰입니다. 이 차이가 Tool 정의 분량입니다. `SimpleLoggerAdvisor` request 로그에는 Tool 정의가 출력되지 않아서 로그만 보면 안 보일 뿐입니다.

## 2. 그런데 LLM이 호출하지 않은 이유

**① 프롬프트가 Tool 호출을 사실상 막고 있습니다**
- 시스템 프롬프트는 "문서를 읽어서"라고만 하고, **어떤 Tool로 읽으라는 말이 없습니다.**
- 사용자 메시지 끝에는 엔진이 붙인 지시가 있습니다. "Your response must be a single JSON value only. Do not include … text outside the JSON." 소형 모델은 이 지시를 "바로 JSON으로 답하라"로 받아들여 tool call 단계를 건너뛰기 쉽습니다.

**② 모델의 tool calling 능력이 약합니다**
- `qwen2.5-coder:7b`는 코드 생성 특화 모델이라 Ollama에서 tool calling이 불안정합니다.
- Tool이 20개 가까이 한꺼번에 제시되면 7B급 모델은 거의 고르지 못합니다.

**③ 호출했더라도 이 경로는 거부됩니다**
- MCP filesystem 서버는 `${APP_HOME}/${APP_NAME}/mcp/server-filesystem` 한 폴더만 허용합니다(`mcp/sample/sample-filesystem-mcp.yml:24`).
- `D:/AppHome/framework/dstone/docs/temp/dongyang-plan.md`는 그 밖이라서 `read_text_file`이 "Access denied"로 실패합니다.
- `@AiTool` 중에는 파일 읽기 Tool이 없습니다.

**④ (확인 필요) Windows에서 MCP가 실제로 연결됐는지**
- `npx`는 Windows에서 `MCP_STDIO_COMMAND_PREFIX=cmd.exe /c`가 있어야 뜹니다.
- 기동 로그에서 `ConfigMcp`가 sample-filesystem에 연결했다는 로그와 Tool 목록이 찍혔는지 확인해 보세요. 연결이 실패했다면 목록에 `read_text_file` 자체가 없습니다.

## 해결: 파일은 TOOL step으로 확실하게 읽기

2. workflow를 이렇게 바꿉니다.

```yaml
  steps:
    - id: read
      type: TOOL
      ref: read_text_file
      input:

      onSuccess: step01
      onFailure: FAIL

    - id: step01
```
