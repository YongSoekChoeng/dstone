`sm-verifier-agent`는 "웹앱이 계속 리로딩된다"고 판단했지만 **재로딩은 한 번뿐**이었습니다. 그래서 기다려도 나아질 수 없었고, 20초 대기와 타임아웃도 여기서 나왔습니다.

## 원인 두 가지

**1. 재로딩 후 DB 연결이 깨짐 (핵심)**
- 테스트 드라이버는 Tomcat 공용 `lib`에 있어 재로딩해도 살아남습니다. 테스트 데이터를 커밋하지 않고 유지하려고 실제 DB 연결 하나를 계속 잡습니다(`Holder.physical`).
- 그 연결의 MySQL 드라이버는 **웹앱의 `WEB-INF/lib`에서 로딩**한 것입니다(`Holder.connectReal`이 스레드의 클래스로더를 사용).
- 재로딩 뒤에도 연결은 열린 상태라 그대로 재사용됩니다. 이때까지 로딩하지 않은 클래스(날짜 변환 클래스 등)는 중지된 로더에서 가져올 수 없어 실패합니다.
- 그래서 이미 로딩된 클래스만 쓰는 조회는 성공하고, 날짜 컬럼을 읽는 조회만 실패했습니다.

**2. JSP만 고쳐도 재로딩함**
- 도구 설명은 "JSP·정적 파일은 바로 반영"인데, `TestServerTool.java:492`는 `WEB-INF/` 아래 파일이 바뀌면 모두 재로딩합니다.
- 이번에 고친 것은 `WEB-INF/views` 아래의 JSP 하나였습니다.

## 영향
- 16:32 이후의 시간표 표시 확인은 **앱 결함인지 판정할 수 없습니다.** 이 검증 결과의 해당 항목은 믿지 말고, 수정 후 step35를 다시 돌려야 합니다.
- 재로딩이 필요한 수정(Java, XML)을 하면 다른 프로젝트에서도 같은 문제가 날 수 있습니다.

## 수정안
1. **실제 DB 드라이버를 웹앱과 분리해 로딩합니다.** 테스트 드라이버가 자체 클래스로더로 `WEB-INF/lib`의 jar를 읽게 하면, 재로딩해도 연결과 테스트 데이터가 유지됩니다. `log4jdbc`처럼 드라이버를 감싸는 경우까지 시험해야 합니다.

방향은 **"Agent가 스스로 지침을 고치는 구조"가 아니라 "실패를 자동으로 모으고, 검증된 것만 반영하는 구조"** 입니다. 이번에 그대로 자동 학습했다면 "`window.confirm`은 iframe에서 차단된다"는 **틀린 원인이 지식으로 굳었을 것**입니다. 설계서에는 "관측으로 확인됨"이라고까지 적혀 있었습니다.

## 학습 고리

```
감지 → 수집 → 분류 → 후보 작성 → 평가 → 승인 → 적용 → 효과 추적(폐기)
(엔진)  (엔진)  (Agent+규칙)  (Agent)    (엔진)  (사람)  (엔진)    (엔진)
```

### 1. 감지: 판단이 필요 없는 신호부터
엔진이 LLM 없이 알 수 있는 것들입니다.

| 신호 | 이번 사례 |
|---|---|
| 같은 의견으로 재개발이 반복됨 | 삭제 버튼 4회 이상 |
| 검증은 PASS인데 사람이 다시 지적함 | 안 닫히는 확인창 |
| 자동 수정이 "이미 해결됨"으로 끝남 (검증 오판 후보) | FAIL 2건 |
| Tool 시간 초과, 반복 호출, 형식 재시도 | `browser_wait_for`, 빈 답 |
| 비용이 평소보다 크게 늘어남 | 개발 1회 228만 토큰 |

### 2. 배울 수 있는 시점: 실패 뒤의 성공
**실패한 시도들과 성공한 수정이 모두 있고, 동작으로 확인됐을 때** 대조해서 배웁니다.
- 채택 조건은 Agent의 설명이 아니라 **검증 결과가 FAIL에서 PASS로 바뀐 것**과 사람의 최종 승인입니다.
- 검증도 틀릴 수 있으므로, 처음에는 사람 승인까지 요구합니다.
- 끝내 해결하지 못한 실행은 지식이 아니라 **평가 사례**로만 남깁니다.

### 3. 분류: 배운 것이 갈 곳은 다름
| 원인 | 반영 대상 | 자동화 정도 |
|---|---|---|
| 엔진·Tool 결함 (재로딩, 검색 제한) | 개선 요청 목록 | 보고만. Agent에게 우회법을 가르치지 않음 |
| 대상 프로젝트의 사실 (`destroy` 함정) | 프로젝트 Skill | 후보 자동 작성, 사람 승인 |
| 범용 조사·검증 방법 | 범용 Skill | 여러 프로젝트에서 반복될 때만, 평가 통과 필수 |
| 검증이 놓친 것 | 평가 사례, 합격 기준 | 사례 초안 자동 작성 |
| 모델 한계 | 모델 선택 자료 | 기록만 |

### 4. 지식은 문장이 아니라 기록으로
프롬프트에 문장을 덧붙이면 쌓일수록 서로 충돌합니다. 항목마다 다음을 갖게 합니다.

`증상` · `적용 범위(프로젝트, 기술, 버전)` · `원인과 근거(파일:줄, 관측)` · `고친 방법` · `출처 실행` · `상태(후보/승인/폐기)` · `사용·성공 횟수`

그리고 **관련 있을 때만 찾아 읽게** 합니다. 쓰였는데 도움이 안 됐거나 라이브러리 버전이 바뀌면 폐기 후보가 됩니다. 한 고객 프로젝트에서 배운 내용은 다른 프로젝트로 넘어가지 않아야 합니다.

### 5. 반영 전 관문: 평가
- 후보를 적용한 상태와 적용하지 않은 상태로 **같은 사례를 여러 번** 돌립니다.
- 해당 사례가 나아지고 **다른 사례가 나빠지지 않아야** 통과입니다.
- 이번처럼 2번 중 1번 성공하는 작업은 한 번 비교로 판단할 수 없습니다.

## 단계별 진행

| 단계 | 내용 | 얻는 것 |
|---|---|---|
| 0 | 결과 데이터 정비: 관측과 추정 분리, "확인됨"은 엔진이 판정 | **학습 재료의 신뢰성. 이것 없이는 다음 단계가 위험** |
| 1 | 실패 신호 감지, 평가 사례 초안 자동 생성 | 재발을 측정할 수 있음 |
| 2 | 학습 Workflow: 성공한 실행에서 후보 작성, 승인 화면 | 사람이 검토만 하면 지식이 쌓임 |
| 3 | 승인 전 자동 평가, 사용 효과 추적과 폐기 | 지식 품질 유지 |
| 4 | 위험이 낮은 프로젝트 지식만 조건부 자동 반영 | 충분한 실적이 쌓인 뒤에 판단 |

## 기존 자산 활용
평가 사례와 `AI_EVAL_RUN`, 프로젝트 Skill, 검증 결과 누적, 결정 기록, 변경 diff가 이미 있습니다. 새로 필요한 것은 **감지 규칙, 지식 후보의 저장·승인, 평가 자동 실행**입니다. 설계 원칙대로 엔진은 특정 Workflow를 모르게 두고, 학습 과정은 별도 Workflow 정의로 만드는 것이 맞습니다. 폐쇄망의 작은 모델은 후보를 틀리게 쓸 수 있으니, 승인과 평가 관문은 생략하지 않는 것이 좋습니다.
