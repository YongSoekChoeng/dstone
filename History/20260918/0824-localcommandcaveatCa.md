## 답변

방금 디스크에서 바뀐 부분이 문제입니다. `renderToolInput()`이 이렇게 바뀌었습니다:

```java
if( StringUtil.isJson(input) ) {
    rendered = inputTemplate.replace("{previous}", this.jsonEscape(input));
}else {
    rendered = inputTemplate.replace("{previous}", input);   // <- 이스케이프 없이 그대로 삽입
}
```

이 조건이 제가 방금 고친 JSON 이스케이프 버그를 사실상 무력화시킵니다. `{previous}`는 `{"sql":"..."}` 템플릿 안에 **JSON 문자열 값으로 끼워넣을** 텍스트인데, 그 텍스트 자체가 독립적으로 유효한 JSON 문서인지 여부는 이스케이프가 필요한지와 아무 상관이 없습니다. 지금 로그의 입력값(마크다운 코드펜스 + 여러 줄 SQL)은 당연히 `isJson()`이 `false`를 반환하므로 else 분기로 빠져서 이스케이프 없이 raw 텍스트가 그대로 삽입되고, 백틱 안의 줄바꿈 때문에 JSON이 깨져서 똑같은 파싱 오류가 재발한 겁니다. (참고로 51번 줄 `rendered = ...jsonEscape(input)`도 바로 다음 if/else에서 덮어써지는 죽은 코드입니다.)

`isJson` 분기 자체가 목적에 안 맞는 조건이라, 이 분기를 걷어내고 항상 `jsonEscape(input)`을 쓰도록 되돌리는 게 맞다고 봅니다. 이대로 수정할까요?

## 답변

방금 로그가 왜 계속 똑같은지 확인했습니다 — **prompt 수정이 실제 실행 중인 서버에 반영된 적이 없습니다.**

증거:
- `target/classes/prompts/oracle-to-postgresql/v1.st` (14:44에 빌드된 옛 버전) vs `src/main/resources/.../v1.st` (15:23, 지금까지 고친 내용) — 서로 다릅니다. 즉 마지막 빌드 이후로 rebuild가 한 번도 안 됐습니다.
- 이 호스트에 `dstone-ai-engine` 프로세스 자체가 안 보입니다(포트 8081도 없음). CLAUDE.md 아키텍처상 dstone-ai-engine은 `kind` 클러스터의 Pod로 떠 있는데, Pod는 애초에 소스 디렉토리를 직접 보지 않고 **빌드된 이미지** 안의 리소스만 읽습니다.
- 게다가 `PromptTemplateRegistry`는 `.st` 파일 내용을 `ConcurrentHashMap`에 **한 번 읽으면 프로세스 종료 전까지 캐시**해두고 다시 안 읽습니다(`computeIfAbsent`, invalidate 로직 없음).

즉 지금까지 제가 고친 RagService, ToolStepRunner, 세 차례의 프롬프트 수정 전부 로직상으로는 맞는데, **실행 중인 인스턴스가 그 코드/리소스를 전혀 안 쓰고** 예전 빌드 그대로 돌고 있어서 매번 첫 버그(RAG 거부/echo)와 똑같은 증상이 반복된 겁니다.

**필요한 조치**: `mvn clean package`로 dstone-ai-engine을 다시 빌드하고, 실제 떠 있는 인스턴스를 재기동(로컬 `java -jar`든, Jenkins 파이프라인을 통해 이미지 재빌드 후 kind Pod에 재배포하든)해야 지금까지의 수정이 실제로 테스트됩니다. 재배포 방식은 어느 쪽으로 하고 계신가요 — 로컬 `java -jar`로 직접 띄우시나요, 아니면 Jenkins/kind 파이프라인을 쓰시나요?

## 수정 내용

- 앞뒤로 감싸는 마크다운 코드펜스(` ```sql ... ``` `)를 벗겨냄
- 맨 앞의 대괄호 레이블 한 줄(`[원본 SQL]`, `[변환된 SQL]`, `[변경된 SQL]` 등 — 문구가 뭐든 상관없이 `^\[...\]` 패턴이면 매칭)을 제거

## 답변

`{question_answer_context}`(그리고 `{query}`)는 우리 코드가 아니라 Spring AI 프레임워크 안에서 치환됩니다.

**흐름**:
1. `RagService.getRagSpecAdvisor(caller)` (`RagService.java:114` 근처)가 우리가 만든 `RAG_SPEC_PROMPT_TEMPLATE`을 `QuestionAnswerAdvisor.builder(vectorStore).promptTemplate(...)`로 등록만 해둡니다. 여기서는 치환이 안 일어납니다.
2. `AgentExecutor.buildSpec()`이 `ragEnabled=true`일 때 이 Advisor를 `ChatClient` 요청에 붙입니다(`spec.advisors(...)`).
3. 실제 치환은 요청이 실행될 때 **Spring AI 라이브러리 내부의 `org.springframework.ai.chat.client.advisor.vectorstore.QuestionAnswerAdvisor.before(ChatClientRequest, AdvisorChain)`** 메서드에서 일어납니다(`spring-ai-vector-store-advisor-2.0.1.jar`, 우리 소스 트리에는 없음). 이 메서드가:
   - 원래 user 메시지 텍스트를 검색 쿼리로 삼아 `VectorStore.similaritySearch(...)` 호출
   - 검색된 `Document`들의 텍스트를 하나로 합쳐서
   - `promptTemplate.render(Map.of("query", 원본유저메시지, "question_answer_context", 합쳐진문서텍스트))` 호출 — **바로 이 지점이 `{query}`/`{question_answer_context}` 플레이스홀더가 실제 문자열로 바뀌는 곳**
   - 그 결과 문자열로 `Prompt.augmentUserMessage(...)`을 호출해서 원래 user 메시지를 통째로 교체

그러니까 우리가 건드릴 수 있는 건 `RagService`에 등록하는 `PromptTemplate`의 틀(지금은 `{query}\n\n[참고자료]\n{question_answer_context}`)뿐이고, 그 틀 안의 두 변수를 실제로 채워 넣는 로직 자체는 Spring AI 라이브러리 코드입니다.

## 답변

코드를 보면 실제로는 **첫 번째 Advisor만** 넣는 게 아니라 `advisorList`에 있는 **전체**를 다 넣습니다.

```java

return builder.defaultAdvisors(advisorList.toArray(new Advisor[0])).build();
```

아마 `new Advisor[0]`을 보고 "인덱스 0번짜리, 즉 첫 번째 하나만" 이라고 오해하신 것 같은데, 이건 인덱스가 아니라 **길이가 0인 빈 배열**입니다. `List.toArray(T[] a)`의 동작 규칙이:

- `a.length`가 리스트 크기보다 **작으면**, `a`는 그냥 "런타임 타입이 뭔지"만 알려주는 용도로 쓰이고, JVM이 그 타입으로 **새 배열을 리스트 크기만큼** 새로 만들어서 원소를 전부 채워 반환합니다.
- `a.length`가 리스트 크기보다 크거나 같으면 그 배열 자체를 재사용합니다.

즉 `toArray(new Advisor[0])`은 "`Advisor[]` 타입의 배열이 필요한데, 크기는 네가(JVM이) 알아서 정해서 전부 채워줘"라는 뜻이고, 결과적으로 `advisorList`에 담긴 **모든 Advisor**(RAG용 `QuestionAnswerAdvisor`, 나중에 governance가 추가할 `@Bean Advisor`들, 그리고 마지막에 추가된 `MessageChatMemoryAdvisor`까지 전부)가 그대로 `defaultAdvisors(...)`에 전달됩니다. `new Advisor[0]`을 쓰는 건 (`new Advisor[advisorList.size()]`로 미리 정확한 크기를 잡는 것보다) JIT 최적화에 유리하다고 알려진 흔한 Java 관용구일 뿐, 로직상 "첫 번째만 넣는다"는 의미는 전혀 없습니다.
