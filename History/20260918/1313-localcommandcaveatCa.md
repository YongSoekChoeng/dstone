## 질문

지금 dstone-ai-engine 에 대한 프로그램구조를 바꾸고 싶어.
기존 소스는 모두 무시하고 새로 작성한다는 마음으로 과감한 구조변경을 하고 싶어.
아래의 내용을 참고해서 계획을 만들어줘.

<공통지침>
- 기존 소스가 진행계획에 있어서 방해가 될 경우 억지로 우회하지 않고 과감하게 포기한다.
- 모든 소스가 및 구조가 직관적으로 명확해야 한다.
- 모든 소스의 주석이 쉽고 직관적이고 명확해야 하며 자세해야 한다.
- 소스 명명이 전반적으로 통일성을 갖춰야 한다.
- AI 프로바이더 및 모델을 설정

<지침사항>
1. 작업단위정의
    - WorkFlow : 최상위 구조. 여러개의 Step들로 구성.
        - Step : 개별 단위작업. (Agent/Tool)
            - Agent : LLM 을 호출.
            - Tool : 내부/외부 프로그램을 호출.
        - Step이 진행될 때 경우에 따라서는 휴먼이 개입해야 하는 단계가 있을 수도 있는데 이 부분은 어떻게 설계해야 할지 고민해줘.
          (예: Step1 -> Step2 -> 승인자 승인 -> Step3)
          이 경우 Step마다의 Input, Output 등이 일시적으로 저장되었다가 승인자가 승인을 한 후에야 후속 Step으로 넘어가야 할텐데 이런 경우.
        - Step 별 Input, Output 의 정의를 명확하게 해줘.
            
2. 패키지정의 - 아래와 비슷한 구조를 취하되 더 나은 방향이 있으면 권해줘.
    net.dstone.ai
        api - 외부와 통신하는 패키지 
        common - 코어가 되는 컴퍼넌트 패키지
            config - 설정관련 패키지
            consts - 고정값 패키지
            definition - 정의 패키지
            ...
        runtime - 런타임 엔진 패키지 
        tools - 툴 패키지
        ...
3. 리소스 정의 - 아래와 비슷한 구조를 취하되 더 나은 방향이 있으면 권해줘.
    3-1. 워크플로우
        resources/ai/workflows - WorkFlow 작업단위와 같다. 파일명이 ID. 내부적으로 Step 들로 이루어져 있고 각 Step 간의 플로우제어가 이 파일에서 가능해야 한다. 
        resources/ai/agents - Agent 작업단위와 같다. 파일명이 ID. 프롬프트가 여기에 들어간다.
        ...
    3-2. 기타 리소스들 
        resources/schema

4. RAG를 붙일 계획인데 기본적인 구조 및 체인 설계를 해줘.
5. tools 은 내부 java 프로그램, 내부 기타 프로그램(Python, Shell, HttpCall 등)에 대한 기본적인 골격을 갖춘 내용을 채워줘.
6. MCP 서버는 dstone-ai-engine와는 별도로 고민해야 하는 영역인가? 만일 dstone-ai-engine 안에 들어올 수 있다면 함께 고민해줘.
