## 답변

원인은 스텝의 `type`입니다. `sm-workflow`의 `step00_02_decideJobKind`는 `AGENT`이고, `pilot-workflow`의 `step01`은 `ROUTER`입니다.

- **`ROUTER` 스텝**: 엔진이 `callForSchema()`로 호출하면서 답의 모양을 `{route, reason}` JSON으로 강제하고 파싱·검증합니다. 그래서 로그에 `{route=일반, reason=...}`으로 찍힙니다.
- **`AGENT` 스텝**: `call()`로 호출하고, 답의 모양은 Agent YAML의 `output` 선언을 따릅니다. `sm-decide-job-kind-agent`에는 `output`이 없어서 기본값인 텍스트로 처리됩니다.

로그의 `**route:** 일반**reason:** ...`은 LLM이 프롬프트를 흉내 내어 쓴 마크다운 문장일 뿐입니다. 그 문장 전체가 `state.classify.route`에 문자열로 저장됩니다.

`sm-decide-job-kind-agent.yml`의 주석과 `description`에는 "ROUTER 전용"이라고 적혀 있지만, 실제 동작은 워크플로 쪽 `type`이 결정합니다.

## 고치는 방법 (둘 중 하나)

**1. 스텝을 ROUTER로 바꾸기** — 분류 결과로 경로를 가를 생각이라면 이쪽이 맞습니다.

```yaml
- id: step00_02_decideJobKind
  type: ROUTER
  agent: sm-decide-job-kind-agent
  input: "${state.request}"
  output:
    result: "state.classify"        # {route, reason} 전체가 들어감
  routes:
    신규개발: <다음 step id>
    일반: <다음 step id>
  onFailure: FAIL
```

`ROUTER`는 `next` 대신 `routes`가 1개 이상 필요합니다. 값은 `END`도 가능합니다.

**2. AGENT로 두고 Agent에 출력 계약 선언하기** — 분기 없이 값만 받고 싶을 때입니다.

```yaml
# sm-decide-job-kind-agent.yml
output:
  format: JSON
  schema: schemas/sm/sm-decide-job-kind.schema.json   # {route: enum[신규개발, 일반], reason: string}
  validation: STRICT
```

이 경우 워크플로의 저장 위치도 `result: "state.classify"`로 바꿔야 `state.classify.route`로 읽을 수 있습니다. 또 이 Agent는 `output`을 선언했으므로 ROUTER 스텝에서는 쓸 수 없게 됩니다(부팅 실패).

원하시는 방향을 알려주시면 바로 수정하겠습니다.

## 답변

두 설정 모두 Agent에게 요청서 말고 다른 자료를 보게 해 주는 장치입니다. 차이는 누가 언제 찾느냐입니다. `context`는 엔진이 LLM 호출 전에 자동으로 한 번 찾아 붙이고, `tools`는 LLM이 필요하다고 판단할 때만 직접 부릅니다.

## `context.sources: [retrievedDocuments]` — 엔진이 자동으로 붙이는 참고자료(RAG)

1. **검색**: LLM을 부르기 직전에 엔진이 이 Agent의 input(여기서는 요청서 전문)을 검색어로 `dstone-knowledge`의 `/api/search`를 호출합니다.
2. **대상**: 사람이 올려 둔 일반 문서(설계서 등)만 찾습니다. 분석된 소스 코드는 대상이 아닙니다.
3. **선별**: 유사도 0.35 미만은 버리고 상위 5건을 남깁니다(`conf/application.yml`의 `dstone.ai.rag.retrieval`). Agent YAML의 `context.retrieval: {topK, similarityThreshold}`로 Agent별로 바꿀 수 있습니다.
4. **주입**: 남은 조각을 요청서 뒤에 `[참고자료]` 블록으로 붙여 LLM에 보냅니다. LLM은 이것이 검색 결과인지 모르고 그냥 입력의 일부로 읽습니다.
5. **실패 시**: 검색이 실패하거나 결과가 없으면 WARN 로그만 남기고 참고자료 없이 진행합니다. `allowEmptyContext: false`로 두면 Agent 호출이 실패합니다.

`sources`에 쓸 수 있는 다른 값 `workflowInput`은 "호출한 쪽이 준 input"이라는 뜻이고, 항상 들어가므로 적지 않아도 같습니다.

## `tools.allowed: [knowledgeSearch, searchInFiles]` — LLM이 골라 쓰는 도구

이 Agent가 부를 수 있는 Tool을 이 둘로 제한한다는 뜻입니다. 목록에 없는 Tool은 LLM에게 보이지 않습니다. 부를지 말지, 몇 번 부를지는 LLM이 정하고, 부를 때마다 LLM 왕복이 한 번씩 늘어납니다.

- **`knowledgeSearch(projectId, query, docTypes, includeDocuments, topK)`**: `dstone-knowledge`가 분석해 둔 프로젝트에서 코드(메소드·타입), SQL, 화면을 뜻과 이름으로 찾습니다. `projectId`가 필수입니다.
- **`searchInFiles`**: 파일 시스템에서 키워드가 들어 있는 줄을 `경로:줄번호: 내용` 형태로 돌려주는 단순 문자열 검색입니다.

## 이 Agent에는 둘 다 맞지 않아 보입니다

- **프롬프트와 충돌**: `sm-decide-job-kind-agent.st`는 "소스를 조사하지 않는다. 요청서에 적힌 말만 보고 정한다"고 하는데, 설정은 소스를 조사할 도구를 쥐여 주고 있습니다. 게다가 `reasoning: none`이라 Tool을 불필요하게 반복 호출할 위험이 있습니다(`pilot`에서 같은 조합이 호출 한도까지 반복 조회한 적이 있습니다).
- **RAG는 잡음이 될 가능성**: 요청서 전문이 검색어가 되므로, 분류와 무관한 문서 조각이 요청서 뒤에 붙을 수 있습니다. `pilot` Agent들이 `context`를 뺀 이유가 이것입니다.
- **`knowledgeSearch`의 `projectId`**: 요청서에 프로젝트 ID가 없으면 LLM이 값을 지어내거나 호출이 실패합니다.

같은 일을 하는 `pilot-request-router-agent`는 `context`와 `tools`가 모두 없습니다. 요청서 문구만으로 분류하는 것이 목적이라면 두 블록을 지우는 쪽을 권합니다. 지워 드릴까요?

## 답변

## 반드시 `retrievedDocuments`라고 적어야 하나

네, 글자 그대로 적어야 합니다. `context.sources`는 정해진 값만 받는 항목이라 쓸 수 있는 값은 `workflowInput`과 `retrievedDocuments` 둘뿐입니다. 다른 값이나 오타는 기동할 때 `AgentRegistry`가 "쓸 수 있는 값이 아닙니다"로 부팅을 실패시킵니다.

이 값은 자료 이름이 아니라 스위치입니다. 엔진은 `sources`에 `retrievedDocuments`가 들어 있는지만 봅니다(`AgentDefinition.ragEnabled()`). 있으면 RAG를 켜고, 없으면 끕니다. 어떤 문서를 찾을지는 여기서 지정할 수 없습니다.

## 동작 순서

`AgentExecutor.buildSpec()`이 LLM 요청을 조립할 때 일어나는 일입니다.

1. **스위치 확인**: `agent.ragEnabled()`가 true면 `RagRetrievalChain.buildAdvisor()`로 Advisor를 하나 만들어 이번 호출에 붙입니다. Advisor는 Spring AI에서 LLM 요청이 나가기 직전에 요청을 가로채 손볼 수 있는 필터입니다.
2. **사전 점검**: `dstone.ai.rag.enabled=true`이고 `dstone.ai.tool.knowledge.base-url`이 설정돼 있어야 합니다. 아니면 LLM을 부르기 전에 예외로 끝납니다. 즉 Agent에 `retrievedDocuments`를 적어 두고 전역 RAG를 끄면 그 Agent 호출은 실패합니다.
3. **검색어 결정**: Advisor(Spring AI의 `RetrievalAugmentationAdvisor`)가 user 메시지 전체를 검색어로 씁니다. Workflow 스텝에서는 스텝의 `input`이 곧 user 메시지이므로, 이 Agent는 요청서 전문이 검색어가 됩니다. input이 object면 그 JSON 텍스트가 검색어입니다.
4. **검색 요청**: `dstone-knowledge`의 `POST /api/search`를 `sourceTypes: [DOCUMENT]`(올린 일반 문서만)로 호출합니다. 걸러 낸 뒤에도 충분히 남도록 `topK × 4`건(최소 20, 최대 50)을 받아 옵니다.
5. **서버 쪽 검색**: `dstone-knowledge`가 검색어를 임베딩(Ollama `bge-m3`)해 벡터 유사도와 이름 일치를 합친 하이브리드 검색을 합니다.
6. **엔진 쪽 선별**: 유사도가 임계값(기본 0.35) 미만인 조각은 버리고 앞에서부터 `topK`건(기본 5)만 남깁니다. 아직 임베딩이 안 된 조각은 유사도가 없으므로, 질문 속 이름이 글자 그대로 들어 있어 찾힌 경우에만 남깁니다.
7. **프롬프트 변형**: 남은 조각을 user 메시지 뒤에 붙입니다. system 프롬프트는 건드리지 않습니다.

   ```
   <원래 input (요청서 전문)>

   [참고자료]
   <조각 1>
   <조각 2>
   ...
   ```
8. **LLM 호출**: 이렇게 바뀐 메시지가 LLM으로 갑니다. Tool 호출 루프가 돌아도 검색은 호출당 한 번뿐입니다.

## 결과가 없거나 실패할 때

`context.retrieval.allowEmptyContext`가 갈라 줍니다.

| 상황 | `true` (기본) | `false` |
|---|---|---|
| 검색 결과 0건 | 원래 input 그대로 진행 | "근거가 없으면 모른다고 답하라"는 문구로 바뀜 |
| 검색 자체 실패 (`dstone-knowledge` 다운·타임아웃) | WARN 로그만 남기고 참고자료 없이 진행 | Agent 호출 실패 |

## Agent별 조정

검색 개수와 임계값은 Agent YAML에서 바꿀 수 있습니다. `context.retrieval`은 `sources`에 `retrievedDocuments`가 있을 때만 쓸 수 있고, 없이 적으면 부팅이 실패합니다.

```yaml
context:
  sources: [retrievedDocuments]
  retrieval:
    topK: 3
    similarityThreshold: 0.4
    allowEmptyContext: true
```

## Tool `searchDocuments`와의 차이

같은 검색을 LLM이 직접 부르는 방식도 있습니다(`RagSearchTool`).

- **`context` 방식**: 검색어가 input 전체로 고정되고 무조건 한 번 실행됩니다.
- **Tool 방식**: LLM이 검색어를 직접 만들고, 필요할 때만 여러 번 부를 수 있습니다.

요청서처럼 긴 글이 통째로 검색어가 되면 초점이 흐려져 무관한 조각이 붙기 쉽습니다. 그런 경우는 Tool 방식이 낫고, 짧은 질문에 답하는 Q&A형 Agent에는 `context` 방식이 잘 맞습니다.

## `workflowInput`: 검사만 통과하고 끝

`SOURCE_WORKFLOW_INPUT` 상수는 위 `SOURCES` 목록에 들어가는 것 말고는 어디에서도 읽지 않습니다. 저장소 전체를 검색해도 참조가 정의부 한 곳뿐입니다. 그래서 다음 셋은 실행 결과가 같습니다.

```yaml
context: {sources: [workflowInput]}
context: {sources: []}
# context 블록 자체가 없음
```

input은 `sources`와 무관하게 항상 LLM으로 가기 때문입니다. 그 경로는 이렇습니다.

1. `runtime/step/AgentStepExecutor.java:53`: 스텝의 `input`(표현식 계산이 끝난 값)을 `agentExecutor.call(agent, ..., input, null /*ragOverride*/, ...)`로 넘깁니다.
2. `runtime/agent/AgentExecutor.java:226` `toUserMessage()`: input을 Agent의 `inputSchema()`로 검증하고 `JsonSchemaUtil.toText(input)`으로 글자로 바꿉니다. 문자열은 그대로, object는 JSON 텍스트가 됩니다.
3. `AgentExecutor.java:280` `ask()`: `spec.user(userMessage).call()`로 user 메시지에 실어 보냅니다.

이 세 단계 어디에도 `sources`를 보는 조건문이 없습니다. `AgentDefinition`의 주석(71행)도 "항상 들어가므로 적어도 되고 안 적어도 됩니다"라고 적고 있습니다. 설계 문서 형식을 맞추려고 받아 주는 값입니다.

## `retrievedDocuments`: Advisor 하나가 추가됨

**1. 스위치 판정** (`AgentDefinition.java:286`)

```java
public boolean ragEnabled() {
    return this.contextSources().contains(SOURCE_RETRIEVED_DOCUMENTS);
}
```

**2. 요청 조립 시 분기** (`AgentExecutor.java:381`, `:435`)

```java
boolean ragEnabled = ragOverride != null ? ragOverride : agent.ragEnabled();
...
if (ragEnabled) {
    spec = spec.advisors(this.ragRetrievalChain.buildAdvisor(
        agent.ragTopK(), agent.ragSimilarityThreshold(), agent.ragAllowEmptyContext()));
}
```

`ragOverride`는 채팅 API의 `ChatRequest.ragEnabled`만 채웁니다. Workflow 스텝은 항상 `null`을 넘기므로 YAML 값이 그대로 적용됩니다. 세 `rag*()` 접근자는 `context.retrieval`이 없으면 `null`을 돌려주고, 그때는 전역 기본값을 씁니다.

**3. Advisor 생성** (`common/rag/RagRetrievalChain.java:134` `buildAdvisor()`)

- `requireRag()`가 `dstone.ai.rag.enabled`와 `dstone-knowledge` 주소를 확인하고, 아니면 여기서 `IllegalStateException`을 던집니다.
- 익명 `DocumentRetriever`를 만듭니다. 이 안의 `retrieve(Query query)`가 `search(query.text(), topK, similarityThreshold)`를 호출합니다.
- `ContextualQueryAugmenter`에 템플릿 `{query}\n\n[참고자료]\n{context}`와 `allowEmptyContext`를 넣습니다.
- 둘을 묶어 Spring AI의 `RetrievalAugmentationAdvisor`로 돌려줍니다.

이 시점에는 검색이 일어나지 않고 "나중에 실행될 필터"만 만들어집니다.

**4. 실제 검색** (`spec.user(...).call()` 실행 시)

Spring AI가 Advisor 체인을 돌리면서 `RetrievalAugmentationAdvisor`가 user 메시지 텍스트로 `Query`를 만들어 `retrieve()`를 부릅니다. 그러면 `RagRetrievalChain.search()`(`:188` 부근)가 실행됩니다.

```java
body.put("query", query);
body.put("sourceTypes", Arrays.asList("DOCUMENT"));      // 올린 일반 문서만
body.put("topK", Math.min(MAX_CANDIDATES, Math.max(limit * 4, 20)));
hits = this.knowledgeClient.post("/api/search", body).path("hits");
```

받은 hit을 순서대로 돌며 걸러 `limit`개까지 `RetrievedChunk`로 담습니다.

```java
if (score != null) {
    if (score.doubleValue() < threshold) continue;        // 임베딩된 조각: 유사도로만 판단
} else if (hit.path("keywordScore").asInt(0) <= 0) {
    continue;                                             // 임베딩 전 조각: 이름으로 찾힌 것만
}
```

**5. 실패 처리** (`retrieve()` 안의 catch)

```java
} catch (IllegalStateException e) {
    if (!optional) throw e;                               // allowEmptyContext: false → 호출 실패
    RagRetrievalChain.this.warn("RAG 검색에 실패해서 참고자료 없이 진행합니다: ...");
    chunks = new ArrayList<RetrievedChunk>();

```

**6. 메시지 변형**

`ContextualQueryAugmenter`가 템플릿의 `{query}`에 원래 user 메시지를, `{context}`에 조각들의 본문을 채워 user 메시지를 바꿔치기한 뒤 LLM으로 보냅니다.

## 코드를 보다 확인된 주의점

`ask()`는 출력 스키마가 문자열이 아니면 user 메시지 뒤에 "Your response must be a single JSON value only… (JSON Schema)" 지시문을 붙여서 보냅니다(`AgentExecutor.java:292`~). RAG Advisor는 user 메시지 전체를 검색어로 쓰므로, JSON 출력 Agent에 `retrievedDocuments`를 켜면 이 영어 지시문과 스키마까지 검색어에 섞입니다.

`sm-decide-job-kind-agent`를 ROUTER로 바꾸거나 `output`을 JSON으로 선언하면 이 경우에 해당하게 됩니다. 이 Agent에서 `context`를 빼는 편이 낫다는 근거가 하나 더 늘어난 셈입니다.

## 답변

네, 제한이 있습니다. 엔진에 등록된 Tool만 적을 수 있고, 그중 TOOL 스텝 전용 Tool은 적을 수 없습니다. 지금 적으신 `knowledgeSearch`와 `searchInFiles`는 둘 다 규칙에 걸리지 않습니다.

## 적을 수 있는 Tool

**로컬 Tool** (`@AiTool` 클래스의 `@Tool` 메서드 이름)

| 분류 | Tool 이름 |
|---|---|
| 파일 | `readFile` `readFileLines` `readFileTail` `readFileListAll` `searchInFiles` `isFileExist` `writeFile` `appendFile` `replaceInFile` `copyFileWithReplace` `editFileLines` `editFileTexts` `deleteFile` |
| 코드 분석 | `knowledgeListProjects` `knowledgeSearch` `knowledgeFindMethods` `knowledgeCallers` `knowledgeCallees` `knowledgeTableUsage` `knowledgeImpact` |
| 문서 검색 | `searchDocuments` |
| 실행·호출 | `runShellScript` `runPythonScript` `httpGet` `triggerBuild` |
| 기타 | `validateSqlSyntax` `getCurrentDateTime` |

**MCP Tool**: `definitions/mcp/**/*.yml`에 등록한 MCP 서버가 제공하는 Tool도 이름으로 적을 수 있습니다.

**`"*"`**: 등록된 Tool 전부를 뜻합니다(TOOL 스텝 전용은 제외).

## 제한 규칙

| 적은 내용 | 결과 | 검사 위치 |
|---|---|---|
| TOOL 스텝 전용 Tool (`readFiles`, `readItemFiles`, `filterList`, `checkData`, `exists`) | 부팅 실패 | `AgentRegistry.checkTools()` |
| `"*"`와 다른 이름을 함께 적음 | 부팅 실패 | 같은 곳 |
| 등록되지 않은 이름 (오타, MCP 서버 미기동) | 경고만 남기고 그 Tool은 붙지 않음 | 같은 곳 |
| ROUTER/SUPERVISOR 스텝이 쓰는 Agent에 `"*"` | 경고 | `WorkFlowRegistry` |

오타는 부팅을 막지 않으므로, 기동 로그에서 `[경고] ... 지금 등록된 Tool이 아닙니다`를 확인해야 합니다.

## 적어도 실행 시점에 더 걸러지는 것

- **caller 화이트리스트**: `dstone.ai.tool.allowed-by-caller`에 해당 caller의 목록이 있으면, Agent 목록과 그 목록의 교집합만 붙습니다. 설정이 없는 caller는 전부 통과입니다.
- **호출 횟수**: `execution.maxToolCalls`(없으면 전역 100)를 넘으면 Tool을 실행하지 않고 `실패: ...`를 돌려주며, 그런 거절이 3번 쌓이면 스텝이 실패합니다.
- **결과 길이**: 결과 한 건이 60,000자를 넘으면 잘립니다.
- **Tool 자체 화이트리스트**: `runShellScript`, `runPythonScript`, `httpGet`, `triggerBuild`는 각자의 허용 목록(`allowed-commands` 등)이 비어 있으면 호출해도 항상 실패합니다.
- **`knowledge*` Tool**: `dstone.ai.tool.knowledge.base-url`이 비어 있으면 항상 실패 문구를 돌려줍니다.

## 이 Agent를 ROUTER로 쓸 때

ROUTER/SUPERVISOR용 Agent에 금지되는 것은 `output` 선언과 `subAgents`뿐이고, `tools.allowed`는 허용됩니다. 따라서 지금 설정 그대로 ROUTER 스텝에 써도 부팅은 통과합니다.
