## 답변

## 끊긴 지점과 그 뒤에 한 일

`replaceInFile` / `copyFileWithReplace`를 넣고 신규 개발 경로를 돌려 8개 파일 중 2개가 실패한 뒤, 그 대책을 재시험하던 중이었습니다. 재시험해 보니 그 대책(편집 Agent의 추론 끄기)은 통하지 않아 방식을 바꿨습니다.

| 편집 Agent 방식 (같은 새 파일 6개) | 결과 |
|---|---|
| `replaceInFile`을 주고 추론 끔 | 3~4개가 Tool 호출 한도 30번을 다 씀 (같은 파일 다시 읽기, 실패한 호출 그대로 되풀이) |
| `replaceInFile`을 주고 추론 켬 | 4개 완료, 파일당 32초~4분 48초. 하나는 출력 토큰 한도 초과, 하나는 7분 초과 |
| **Tool 없이 줄 번호 변경 목록만 답함** | 파일당 1~27초 |

그래서 지금은 파일을 TOOL step만 고칩니다. 편집 Agent는 "몇 번째 줄을 지운다/바꾼다/뒤에 넣는다"만 답하고, 새 Tool `editFileLines`가 적용합니다.

## 추가·보강한 것

- **`editFileLines` (신규)**: 줄 번호로 여러 곳을 한 번에 고칩니다. 하나라도 틀리면(범위 밖, 구간 겹침, 그 줄의 내용이 다름) 그 파일은 아무것도 바꾸지 않습니다. 고친 뒤 괄호의 짝이 달라지면 `주의:`를 붙입니다.
- **`replaceInFile` 보강**: 못 찾으면 파일의 그 자리 글자를 알려 주고, 바꿀 것이 없는 호출은 거절합니다.
- **Workflow**: `newRead`(복사한 파일 읽기)와 `newApply`(변경 적용) step을 추가했고, `04-tasks.md`에 "확인 필요" 상태가 생겼습니다.
- **설계 Agent**: 이름 바꿈 표에 `title` 같은 흔한 낱말을 혼자 적지 않도록 규칙을 보강했습니다.
- 단위 테스트는 30개 모두 통과합니다(`FileUtilTest` 16개).
- `docs/09.dstone-ai-engine.md`와 `CLAUDE.md`를 지금 상태로 고쳤습니다.

## 답변

아니요, SAA로 바꾼다고 step 간 in/out이 고정되지는 않습니다. 오히려 지금 엔진보다 느슨해집니다. (SAA 1.0~1.1 기준으로 아는 내용이고, 쓰실 버전의 소스를 직접 확인한 것은 아닙니다.)

## SAA Graph가 데이터를 넘기는 방식

- **step별 in/out이 없습니다.** 모든 노드가 `OverAllState`라는 공용 상태 하나(key → value Map)를 함께 읽고 씁니다.
- **노드의 모양이 전부 같습니다.** `NodeAction`은 상태 전체를 받아서 "바꿀 key들의 Map"을 돌려줍니다. 어떤 노드가 어떤 key를 읽고 쓰는지는 선언하지 않고, 노드 코드 안에만 있습니다.
- **선언하는 것은 key별 합치기 방식뿐입니다.** `KeyStrategy`로 덮어쓸지 이어 붙일지를 정하는데, 값의 타입이나 구조는 검사하지 않습니다.
- **틀리면 실행 중에 드러납니다.** key 이름을 잘못 쓰거나 앞 노드가 값을 안 넣으면 기동할 때는 통과하고, 그 노드가 실행될 때 `null`이 나옵니다.

Agent 한 개의 출력은 고정할 수 있습니다. `ReactAgent`에 `outputKey`와 출력 스키마(또는 타입)를 줄 수 있습니다. 다만 그것은 "이 Agent의 답 모양"이지 "A step의 출력이 B step의 입력과 맞는가"를 보는 것은 아닙니다.

## 지금 엔진과 비교

| | 지금 엔진 | SAA Graph |
|---|---|---|
| step 출력의 위치 | `steps.<id>.output`으로 step마다 분리 | 공용 상태의 key (노드끼리 겹쳐 쓸 수 있음) |
| Agent의 in/out 계약 | YAML에 JSON Schema로 선언, 호출마다 검증 | 출력만 선택적으로, 입력은 상태에서 꺼내 씀 |
| step 입력이 계약과 맞는지 | 기동할 때 검사 | 없음 |
| 없는 step·필드 참조 | 기동 실패 (깊은 경로는 경고) | 실행 중 `null` |
| 정의하는 곳 | YAML | Java 코드 |

10월 7일에 SAA를 넣지 않기로 한 이유(Graph 런타임은 `WorkFlowExecutor`를 바꿔 끼우는 것일 뿐)도 그대로입니다. in/out 정의를 명확히 하는 것이 목적이라면 SAA는 그 방향이 아닙니다.

## 지금 엔진에서 실제로 느슨한 곳

- **Tool의 출력에 계약이 없습니다.** TOOL step의 output은 Tool이 준 대로(JSON이면 JSON, 아니면 글자) 들어갑니다. 신규 개발 경로의 jq가 `startswith("복사했습니다")`처럼 문구에 기대는 것이 이 때문입니다.
- **깊은 필드 경로는 경고만 합니다.** `.steps.x.output.없는필드`는 기동을 막지 않습니다.
- **값 전체가 표현식인 input은 실행할 때만 검사합니다.**
- **forEach의 input/output은 목록인데**, 짝을 맞추는 일을 YAML의 `transpose`로 직접 하고 있습니다.

이 네 곳을 엔진에서 조이는 편이 SAA 도입보다 작고 목적에 바로 맞습니다. Tool에 출력 스키마를 선언하게 하고 경로 경고를 기동 실패로 올리는 것부터가 좋겠습니다.

어떤 상황에서 in/out이 불명확하다고 느끼셨는지 알려 주시면, 위 네 가지 중 어디에 해당하는지 보고 그 부분부터 설계해 보겠습니다. SAA를 쓰려는 다른 이유가 있다면 그것도 함께 알려 주세요.
