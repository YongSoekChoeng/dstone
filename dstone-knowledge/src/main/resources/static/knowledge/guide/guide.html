코드 분석

사용 안내

소스를 한 번 분석해 두고, 궁금할 때마다 물어보는 곳입니다. 처음이라면 1 ~ 3을 차례로 읽어 보세요.

1. 무엇을 하나 2. 어떻게 돌아가나 3. 시작하기 4. 상황별 따라 하기 5. 화면별 쓰는 법 6. 알아 둘 말 7. 리비전 결과 읽는 법 8. 잘 안 될 때

1. 무엇을 하나

Java 프로젝트의 소스를 미리 읽어서 "어디서 무엇을 부르고, 어느 테이블을 건드리는지"를 지도로 만들어 둡니다. 그다음부터는 소스를 하나씩 열어 볼 필요 없이 화면에서 바로 물어봅니다.

이런 게 궁금할 때이 화면에서
"분석은 어디까지 됐고, 지금 돌고 있는 건 없나?" 대시보드 — 프로젝트별 분석 상태 · 최근 작업 · 임베딩 · 올린 문서를 한 화면에서 봅니다
"현행 시스템은 업무별로 얼마나 크고, 프로그램이 어떤 테이블을 쓰지?" 프로젝트 — 현행 구조 · 프로그램 목록 · 테이블 CRUD 를 보고 CSV 로 내려받습니다
"아무 데서도 쓰지 않는 건 뭐지?" 프로젝트의 "전환 제외 후보" — 아무 데서도 쓰지 않는 화면 · SQL · 클래스 · 테이블과 그 근거가 나옵니다
"주문 취소는 어디서 처리하지?" 검색 · 문서 — 말로 물어보면 관련된 메소드 · SQL · 화면이 나옵니다
"이 테이블(컬럼)을 바꾸면 어느 화면을 다시 테스트해야 하지?" 영향도 — 다시 테스트할 화면과 주소, 그렇게 판단한 근거가 나옵니다
"이번 배포에서 바꾼 코드가 어디까지 영향을 주지?" 영향도의 "변경분" — 두 번의 분석 사이에 바뀐 코드에서 출발합니다
"이 메소드를 누가 부르고, 이 메소드는 무엇을 부르지?" 노드 맵 — 호출 흐름을 그림으로 따라갑니다
"지난번 분석과 무엇이 달라졌지?" 리비전 비교 — 새로 생기거나 없어진 주소 · 메소드 · SQL · 호출이 나옵니다
"설계서에는 뭐라고 돼 있었지?" 검색 · 문서 — 문서를 올려 두면 같이 찾습니다
답을 지어내지 않습니다. 소스에 실제로 적힌 것만 보여 줍니다. 확실하지 않은 것에는 LOW 같은 표시를 붙이고, 알아내지 못한 것은 "확인 필요"로 따로 알려 줍니다.

3. 시작하기

1 ~ 3은 프로젝트마다 한 번만 하면 됩니다. 그 뒤로는 4를 필요할 때마다 씁니다.

1프로젝트 등록

"프로젝트" 화면의 "프로젝트 등록"에서 프로젝트 ID와 소스 폴더를 적습니다. 소스 폴더는 내 PC가 아니라 분석 서버에 있는 경로입니다. DB 접속 정보는 있으면 같이 적습니다.

 2분석 시작

프로젝트 화면에서 "분석 실행"을 누릅니다. 단계마다 진행 상황이 보입니다. 파일이 수백 개면 몇 분, 수천 개면 그보다 오래 걸립니다.

 3결과 확인

분석이 끝나면 프로젝트 화면의 리비전 목록에 새 리비전이 생깁니다. 리비전을 고르면 신뢰도 한 줄과 현행 구조가 보입니다.

 4물어보기

검색 · 영향도 · 노드 맵 · 리비전 비교 화면에서 프로젝트를 고르고 물어봅니다.
소스가 바뀌면 다시 분석하세요. 두 번째부터는 "증분 분석"을 체크하면 바뀐 파일만 읽어서 빨리 끝납니다.

4. 상황별 따라 하기

자주 하는 일 네 가지입니다. 예시는 저장소에 든 게시판 표본 struts-app(게시글 목록 · 저장 · 삭제)을 기준으로 적었습니다. 내 프로젝트에서는 이름만 바꿔서 하면 됩니다.

표본으로 직접 따라 해 보려면 "프로젝트" 화면에서 projectId struts-app, 소스 폴더 dstone-knowledge/src/test/resources/samples/struts-app(이 개발 서버에서는 /app/dstone/dstone-knowledge/src/test/resources/samples/struts-app)로 등록하고 분석하세요. 몇 초면 끝납니다.

A 기능이 어디 있는지 찾을 때 검색 · 문서 열기

  1. "찾을 곳"에서 프로젝트를 고릅니다. 화면을 처음 열면 "(올린 문서)"가 골라져 있으니 꼭 바꾸세요.
  2. 찾을 내용을 평소 말하듯 적습니다. 예: 게시글을 삭제하는 곳
  3. 후보 중 맞는 것을 찾았으면, 그 이름으로 한 번 더 찾습니다. 예: BoardDAO.deleteBoard
이렇게 보입니다: 말로 찾으면 관련된 화면 · 메소드 · SQL이 여럿 나옵니다. 이름으로 찾으면 바로 그것이 맨 위에 옵니다. 결과를 펼치면 그 메소드가 실행하는 SQL, 부르는 곳, 실제 소스가 함께 보입니다.

B 테이블이나 컬럼을 바꾸기 전에 영향도 열기

  1. 프로젝트를 고르고, 종류를 "테이블"로 바꾼 뒤 테이블 이름을 적고 "보기"를 누릅니다. 예: TB_BOARD
  2. 컬럼 하나만 바꾼다면 종류를 "컬럼"으로 두고 TB_BOARD.TITLE처럼 적습니다. 테이블 이름만 적으면 컬럼 목록이 나옵니다.
  3. "다시 테스트할 곳"의 줄마다 왜?를 눌러 근거를 봅니다.
이렇게 보입니다: 맨 위 숫자 네 개(다시 테스트할 곳 · 추정 관계 · 건드리는 데이터 · 확인 필요, 아래 구역과 짝)와 한 줄 요약 아래에 다시 테스트할 화면과 주소가 나옵니다. 왜?를 누르면 왜 다시 테스트해야 하는지 한 문장과 이어진 길이 보입니다. 예: edit.jsp → /board/save.do → BoardSaveAction → BoardDAO#insertBoard (Board.insertBoard 실행 · 테이블 쓰기). 추정 관계라면 짐작으로 이은 고리마다 까닭, 근거가 된 소스 줄, 확인할 것이 함께 나옵니다.
읽는 법: "다시 테스트할 곳"은 꼭 확인할 곳, "추정 관계"는 정말 이어지는지 한 번 더 볼 곳, "확인 필요"는 분석이 놓쳤을 수 있는 곳입니다.

C 이번에 고친 코드의 영향을 볼 때 영향도 열기

  1. 고치기 전과 고친 뒤에 각각 한 번씩 분석해 둡니다(두 번째는 "증분 분석"을 체크).
  2. 영향도에서 리비전을 고친 뒤의 것으로 고르고, 종류를 "변경분"으로 바꿉니다. 견줄 리비전은 바로 앞 것이 미리 골라져 있습니다. "보기".
이렇게 보입니다: 바뀐 메소드 · SQL · 화면 파일 수가 먼저 나오고, 그 변경 때문에 다시 테스트할 화면과 주소가 B와 같은 모습으로 나옵니다. 주석이나 줄 바꿈만 고친 메소드는 바뀐 것으로 치지 않습니다.

D 호출 흐름을 그림으로 볼 때 노드 맵 열기

  1. 프로젝트를 고르면 전체 그림이 그려집니다. "이름으로 찾기"에 BoardDAO.deleteBoard처럼 적으면 그 메소드의 관계 트리가, 매퍼.SQL이름으로 적으면 그 SQL의 관계 트리가 열립니다.
  2. 관계 트리는 따로 뜬 창에 그립니다. 영향도 화면의 관계 트리 보기나 미사용 탭의 이름을 눌러도 노드 맵을 거치지 않고 같은 창이 바로 뜹니다.
이렇게 보입니다: 가운데가 고른 메소드, 왼쪽이 그것을 부르는 쪽(화면까지), 오른쪽이 그것이 부르는 쪽(SQL · 테이블까지)입니다.

5. 화면별 쓰는 법

대시보드

  • 코드 분석의 첫 화면입니다. 위쪽 카드에서 서버 상태, 프로젝트 수, 돌고 있는 분석, 임베딩 진행률, 올린 문서 수를 봅니다. 카드를 누르면 그 화면으로 갑니다.
  • 프로젝트 현황: 숫자는 분석이 끝난(READY) 가장 최근 리비전의 것입니다. 프로젝트 이름을 누르면 그 리비전의 요약이 열리고, "영향도" · "노드 맵"을 누르면 그 리비전이 골라진 채로 열립니다. 호출 해석률은 95% 이상이면 초록, 80% 미만이면 빨강입니다.
  • 최근 분석 작업: 실패한 작업은 이유의 첫 줄이 빨간 글씨로 나옵니다. 돌고 있는 분석이나 임베딩이 있으면 화면이 30초마다 새로 읽습니다.
  • 올린 문서: 묶음(collection)마다 문서 · 청크 수와 임베딩이 얼마나 끝났는지 봅니다. 로그인한 사용자(API 키)의 문서만 셉니다.

프로젝트

  • 목록에서 프로젝트를 누르면 그 프로젝트의 홈이 열립니다. 위쪽에 리비전 고르기와 신뢰도 한 줄(호출 해석률, 짐작으로 이은 비율, 파싱 성공률, 가장 많이 못 푼 이유)이 있고, 그 아래 탭 네 개가 있습니다.
  • 현행 구조: 화면 → 컨트롤러 → 서비스 → DAO → SQL → 테이블이 몇 개인지와, 업무 영역별 규모입니다. 업무 영역은 패키지 · 폴더의 공통 앞부분을 뗀 첫 마디입니다.
  • 프로그램 목록: 진입점(주소 · 배치 · main)마다 요청하는 화면과, 호출을 끝까지 따라가 닿는 SQL · 테이블(C/R/U/D)입니다. AS-IS 프로그램 목록으로 CSV 를 내려받을 수 있습니다.
  • 테이블 · CRUD: 테이블마다 만들고 · 읽고 · 고치고 · 지우는 프로그램 수입니다. 프로그램 수를 누르면 그 프로그램 목록으로 가고, CRUD 매트릭스를 CSV 로 내려받을 수 있습니다.
  • 전환 제외 후보: 들어오는 참조가 하나도 없는 화면 · SQL · 클래스 · 메소드 · 테이블입니다. 확실 · 추정 등급과 근거가 붙습니다.
  • 프로젝트 설정: 소스 폴더, 라이브러리 위치와 DB 접속(여러 개)을 고칩니다. DB 접속이 있으면 테이블 · 컬럼의 정의와 한글명을 소스보다 먼저 DB 에서 찾고, DB 에만 있는 테이블도 전환 제외 후보에 나옵니다. 비밀번호는 암호화해 저장하고 다시 보여 주지 않습니다.

분석 실행 · 진단 (관리)

  • 분석을 돌리고 결과를 점검하는 사람용 화면입니다. 화면이 두 칸입니다. 왼쪽에 프로젝트 목록과 등록 칸, 분석 시작, 리비전 목록이 있고, 오른쪽에 고른 리비전의 결과가 탭 다섯 개(개요 · 연결 품질 · 분석 내용 · 미사용 · 실행 기록)로 나옵니다. 분석 칸은 왼쪽 목록에서 프로젝트를 눌러야 열립니다. 맨 위 한 줄에는 서버 상태와 임베딩 진행이 나옵니다.
  • 프로젝트 등록: 프로젝트 ID는 영문으로 짧게 적습니다(나중에 바꿀 수 없습니다). 소스 폴더는 분석 서버의 경로입니다. Maven 프로젝트 폴더든, 운영 서버에서 받아 온 WAR를 푼 폴더든 됩니다. 목록에서 프로젝트를 누르면 "프로젝트 등록 / 수정" 칸에 그 값이 채워지므로, 경로나 라이브러리 위치를 고쳐 "등록"을 다시 누르면 수정됩니다.
  • 분석 시작: 보통은 아무것도 적지 않고 누르기만 하면 됩니다.
    • 리비전 라벨 — 비우면 지금 시각이 붙습니다. 배포 이름을 붙이고 싶을 때 적습니다. 예: 2026-11-정기배포
    • 증분 분석 — 두 번째 분석부터 체크합니다. 바뀐 파일만 다시 읽습니다. 결과는 전체 분석과 같습니다.
    • 이 단계부터 다시 — 평소에는 쓰지 않습니다. 이미 있는 리비전의 뒤쪽 단계만 다시 만들 때 씁니다. 그 리비전의 라벨을 함께 적어야 합니다. 규칙 파일만 고쳤다면 SEMANTIC부터 다시 돌리면 됩니다.
  • 진행 상황: 아래 단계를 차례로 지나갑니다. 가장 오래 걸리는 것은 "관계 풀기"입니다.

  • 결과 보기: 왼쪽 리비전 목록에서 리비전을 누르면 오른쪽에 탭이 열립니다. 탭 이름 옆에 ⚠가 있으면 그 탭에 살펴볼 것이 있다는 뜻입니다(7장).

  • 보관: 분석이 끝날 때마다 오래된 리비전은 자동으로 정리됩니다(기본 최근 5개). 더 줄이고 싶으면 리비전 목록 아래 "보관 정책"을 펴서 쓰고, 하나만 지우려면 오른쪽 위의 "이 리비전 지우기"를 누릅니다. 리비전을 지우면 그 분석 결과도 함께 없어지고 되돌릴 수 없습니다.

    • 추정 관계 — 이어지는 길에 덜 확실한 고리가 낀 곳입니다(접혀 있음). 정말 이어지는지 한 번 더 봅니다.

  • 머리글 오른쪽의 관계 트리 보기를 누르면 같은 대상의 호출 흐름 그림이 새 창(관계 트리 창)에 열립니다.

노드 맵

  • 호출 흐름을 그림으로 봅니다. 왼쪽부터 화면 → 컨트롤러 → 서비스 → DAO → SQL 매퍼 → 테이블 순서로 놓이고, 선이 굵을수록 호출이 많습니다.
  • 노드를 누르면 이어진 것만 남고 나머지는 흐려집니다. 오른쪽에 위치, 계층, 처리하는 주소, 메소드 · SQL 목록이 나옵니다. 제목 옆의 "소스 보기" · "SQL 보기"를 누르면 실제 코드가 팝업으로 뜹니다(화면 파일은 앞부분만 담아 두어 소스 보기가 꺼져 있습니다).
  • 관계 트리: 전체 그림은 클래스끼리의 관계입니다. "어느 메소드가 어느 메소드를 부르는지"는 "관계 트리 따로 보기"를 눌러 새 창(관계 트리 창)에서 봅니다. 창이 뜨지 않으면 브라우저에서 이 사이트의 팝업을 허용해 주세요. 가운데가 고른 것, 왼쪽이 부르는 쪽, 오른쪽이 불리는 쪽입니다. 팝업 위쪽에서 양쪽 깊이(기본 3)를 바꾸고, "보일 계층" 칩으로 계층을 끄고 켭니다. 너무 많으면 클래스 대신 메소드 하나를 고르세요.
  • 묶음: 노드가 많은 프로젝트는 패키지별로 접혀서 나옵니다. 두 번 누르면 펼쳐집니다. "이름으로 찾기"에 이름 일부를 적으면 그리로 바로 갑니다. 다시 누르면 같은 이름의 다음 노드로 넘어갑니다.
  • 모델(VO)은 처음에 꺼져 있습니다. getter · setter 호출이 그림을 덮기 때문입니다. 위의 색깔 딱지로 켜고 끕니다.

리비전 비교

  • 같은 프로젝트를 두 번 이상 분석했을 때 씁니다. 리비전을 고르고 "비교"를 누릅니다. 기준은 "(자동)"으로 두면 증분 분석의 기준 리비전과, 기준이 없으면 바로 앞 리비전과 견줍니다.
  • 소스의 줄 차이가 아니라 구조의 차이가 나옵니다. 새로 생기거나 없어진 주소 · 메소드 · 호출, 내용이 바뀐 SQL, 새로 쓰거나 더는 쓰지 않는 테이블.
  • 배포 전에 "새로 열린 주소가 있나", "테이블을 새로 건드리는 SQL이 있나"를 확인할 때 좋습니다. 바뀐 코드가 어디까지 영향을 주는지는 영향도의 "변경분"으로 봅니다.

7. 리비전 결과 읽는 법 (모든 항목의 뜻)

"분석 실행 · 진단" 화면에서 리비전을 누르면 오른쪽에 나오는 탭입니다. 분석이 얼마나 만들어졌고, 얼마나 믿을 만한지를 보여 줍니다. 항목이 많지만 다 읽을 필요는 없습니다. 아래 순서로 보면 됩니다.

  1. 개요 탭의 "한눈에 보기"만 본다. 숫자를 말로 풀어 둔 것입니다. 초록색 ✔ 만 있으면 그대로 쓰면 됩니다. 주황색 ! 나 빨간색 ✖ 가 있으면 그 줄에 무엇을 하면 되는지 적혀 있습니다.
  2. 탭 이름 옆에 ⚠ 가 있으면 그 탭을 연다. 예: 호출이 덜 풀렸으면 "연결 품질", 진입점을 못 찾았으면 "분석 내용".
  3. 나머지 표는 "무엇이 얼마나 들어 있나"를 확인할 때 편다. 접힌 제목 옆의 한 줄 요약만 봐도 대개 충분합니다.

화면에서는 표의 영문 값 옆에 뜻이 붙어 있고, 표마다 "이 표 읽는 법"을 누르면 그 표의 설명이 나옵니다. 아래는 그 설명을 한곳에 모은 것입니다.

8. 잘 안 될 때

이럴 때이렇게 하세요
화면이 열리지 않거나 "Failed to fetch" 같은 연결 오류가 난다 분석 서버가 내려가 있습니다. 관리자에게 분석 서버(dstone-knowledge)를 띄워 달라고 요청하세요.
화면이 반응하지 않거나 목록이 비어 있다 로그인이 풀렸을 수 있습니다(로그인을 켠 환경). dstone-boot 메뉴의 "코드 분석(Knowledge)"으로 다시 들어옵니다.
등록할 때 "소스 경로가 없거나 폴더가 아닙니다" 소스 폴더는 내 PC가 아니라 분석 서버에 있는 경로여야 합니다.
"이 프로젝트는 이미 분석이 돌고 있습니다" 한 프로젝트에는 분석이 하나씩만 돕니다. 끝나기를 기다리거나 "취소"를 누릅니다.
검색 결과가 적거나 엉뚱하다 먼저 "찾을 곳"이 "(올린 문서)"로 남아 있지 않은지 봅니다. 코드에서 찾으려면 프로젝트를 골라야 합니다. 그래도 적으면 임베딩이 아직 끝나지 않았을 수 있습니다(대시보드 맨 위 한 줄의 임베딩). 그동안은 클래스 · 메소드 · 테이블 이름을 넣어 찾으세요.
검색이 몇 초 넘게 걸린다 임베딩이 뒤에서 도는 동안에는 느려질 수 있습니다. 임베딩이 끝나면 빨라집니다.
영향도에서 "그 테이블을 건드리는 SQL을 실행하는 메소드가 없습니다" 테이블 이름이 맞는지 이름 일부로 다시 찾아봅니다. SQL을 매퍼 XML이 아니라 Java 코드에 문자열로 적은 프로그램은 테이블과 이어지지 않습니다. 그럴 때는 검색에서 테이블 이름으로 찾습니다.
영향도에 다시 테스트할 곳이 하나도 없다 정말 부르는 곳이 없거나, 리플렉션 · 문자열로 만든 주소처럼 분석이 따라가지 못하는 방식으로 불리는 것입니다. "확인 필요"에 놓쳤을 수 있는 호출이 있는지 봅니다.
영향도 변경분에 "파일 단위로 견준 메소드"가 나온다 견준 리비전 가운데 하나가 예전 분석기로 분석된 것입니다. 바뀐 파일의 메소드를 모두 넣었으므로 결과가 넓게 나옵니다. 두 리비전을 다시 분석하면 바뀐 메소드만 나옵니다.
결과에 LOW가 많거나 풀지 못한 참조가 많다 분석할 때 라이브러리(jar)를 찾지 못했을 수 있습니다. 리비전의 연결 품질 탭에서 "풀지 못한 참조의 이유" 줄을 눌러 나오는 살펴보기에서 무엇을 못 찾았는지 봅니다. 같은 이름이 많이 나오면 그 타입이 든 jar가 빠진 것입니다. 등록 칸에 jar 위치를 적고 전체 분석(증분 분석 아님)을 다시 합니다. Maven 프로젝트라면 mvn dependency:build-classpath의 출력을 그대로 붙여 넣으면 됩니다.
리비전 비교나 변경분에서 "비교할 앞 리비전이 없습니다" 그 프로젝트를 한 번만 분석한 것입니다. 소스가 바뀐 뒤 한 번 더 분석하면 비교할 수 있습니다.
