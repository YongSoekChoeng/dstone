테스트 서버는 원래 서버를 흉내 낸 것이라 다른 점이 있다. 그 차이로 생긴 실패를 FAIL로 내면 자동 수정이 고칠 곳이 없는 코드를 고치려다 시간만 쓰고,
엉뚱한 공통 코드를 바꿀 수도 있다. 그래서 FAIL로 내기 전에 이 실패를 개발 결과가 설명하는지 먼저 본다.

## 1. 다른 점은 테스트 서버 결과에 있다

`startTestServer` 결과의 "원래 환경과 다른 점"과 막은 외부 접속, JDK 안내를 먼저 읽는다. 실패가 그 가운데 하나로 설명되면 환경 차이다.

## 2. 증상별로 가르는 법

| 본 것 | 확인할 것 | 판정 |
|---|---|---|
| 파일·이미지 주소가 404 | 앱이 그 파일을 저장한 실제 경로(DB의 파일 경로 칸, 서버 로그)를 찾아 `isFileExist`로 디스크에 있는지 본다 | 파일이 있는데 주소만 404이고 "지금 연 것"에 그 주소가 없으면 **BLOCKED(환경)**. 파일이 없으면 저장을 못 한 것이라 **FAIL** |
| 외부 시스템 호출 실패 | 결과의 "막은 외부 접속"에 그 주소가 있는지 | 있으면 **BLOCKED(환경)** |
| 로그인·권한 없음 | 테스트계정으로 그 메뉴를 볼 권한이 있는지 | 권한·계정 문제면 **BLOCKED(환경)** |
| 오류에 "dstone 테스트 DB … 잠금 대기" | 테스트 DB 연결을 다른 요청이 오래 쓰고 있었다 | **BLOCKED(환경)**. 다시 한 번 해 보고 그래도 같으면 BLOCKED |
| 오류에 "dstone 테스트 DB: 테스트 중에는 DDL" | 기능이 실행 중에 테이블을 만들거나 바꾸려 했다 | DDL은 사람이 반영한다. 개발 결과가 실행 중 DDL을 하면 **FAIL**, 원래 앱이 그러는 것이면 **BLOCKED** |
| 기존 데이터의 첨부 파일·이미지가 404 | 결과의 "원래 환경과 다른 점"에 업로드 폴더를 바꿨다고 적혀 있는지 | 테스트 서버의 업로드 폴더는 비어서 시작한다. 이번에 올린 파일이 아니면 **BLOCKED(환경)** |
| 테이블·컬럼이 없다는 SQL 오류 | DDL 문서에 있는 테이블·컬럼인지 | DDL을 사람이 아직 반영하지 않은 것이면 **BLOCKED(환경)**. DDL 문서에도 없으면 **FAIL** |
| 서버 오류, 잘못 저장된 값, 화면 동작이 기대와 다름 | 서버 로그의 스택, 네트워크 응답, DB의 행 | 개발 결과로 설명되면 **FAIL** |

BLOCKED의 evidence에는 무엇이 환경 차이인지와 사람이 할 일을 적는다.
예: "디스크에는 파일이 있고 주소만 404. 원래 서버가 이 주소를 웹서버로 연다면 프로젝트 관리의 '테스트서버 정적 경로'에 '/주소=폴더'를 더하면 다음부터 테스트할 수 있다."

## 3. 고치는 쪽에서

검증 결과의 FAIL을 고치기 전에 위 표로 다시 본다. 환경 차이로 설명되면 코드를 고치지 않고 unresolved에 "환경 차이: 이유와 사람이 할 일"을 적고 끝낸다.
원인을 찾다가 같은 설정·경로를 계속 뒤지고 있다면, 코드에 답이 없는 환경 차이일 가능성이 크다. 그때도 거기서 멈추고 unresolved에 남긴다.

## 4. 지난번에 된 것이 이번에 안 되면 방법부터 의심한다

지난 회차(previous)에서 해낸 동작(등록, 업로드, 화면 이동)이 이번에 안 되면, 환경이 바뀌었다기보다 이번에 한 방법이 다를 가능성이 크다.
환경 차이로 판정하기 전에 지난 회차의 steps대로(같은 진입 경로, 같은 순서) 다시 해 본다.

- 그래도 안 되고 이번에 바뀐 파일로 설명되면 **FAIL**이다.
- 지난번과 같은 방법으로 해도 안 되고 바뀐 파일과도 무관할 때만 **BLOCKED**로 내고, evidence에 지난번 방법대로 다시 해 본 결과를 적는다.
- 이번 회차에 시도한 방법 하나가 안 된 것은 "테스트 수단이 없음"이 아니다.
